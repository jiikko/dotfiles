# improve-debug-api — debug API の口を、人の操作と同じ処理に寄せる

debug API で確かめた挙動は、人が同じ操作をしたときの挙動と同じでないと意味がない。口だけが別の処理を通ると、
debug API では動くのに人の操作ではクラッシュする・人には作れない状態を debug API が作る、という形で検証が空振りする
(2026-11-08 ユーザー指示)。この skill は、口ごとに経路を突き合わせて差を issue に書き、人の入口へ寄せて直す。

この skill は方法だけを持つ。**repo ごとの値は、対象 repo の debug API の docs の「improve-debug-api の値」節が正本**
(今ある repo: my-products の `apps/vlc-multi-video-player/docs/debug-api.md` と `apps/obaket/macOS/docs/debug-api.md`)。
その節が無い repo で使うときは、手順 0 で節を書いてから始める (値の項目は下の「値の節に書くもの」)。

## 不変条件

- 操作する口は、人の操作の入口を通す。入口は次の 3 つのどれか
  - **入力の合成**: キー・マウス・メニューの項目を、本物の入力と同じ配送に載せる
  - **人の入口と同じ関数**: View の action・Binding の set・メニューの命令が呼ぶのと同じ関数を、同じ前段ごと呼ぶ
  - 上の 2 つで作れない操作 (購読・OS のパネル・合成できないドラッグや hover など) だけ、debug 専用の処理を置いてよい。
    置くなら、人の経路との差と、合成できない理由をコードのコメントと docs に書く
- 口が、人の入口にある前段 (押せなくする判定・課金のゲート・番号の範囲・状態の遷移中の断り・確認・info ログ) と後段 (結果の画面への反映) を飛ばさない。
  飛ばすと、人には届かない状態を debug API が作る
- **口を人より狭める debug 専用の安全装置は差に数えない** (テスト用の範囲に閉じる guard など。値の節に挙げてある)。人の経路を飛ばさず、触れる範囲を絞るだけ

## 値の節に書くもの

各 repo の debug API の docs の「improve-debug-api の値」節に、次を書く (この skill は読むだけ)。

| 項目 | 例 |
|---|---|
| 口の表の場所と、口を数える式 | route の振り分けのファイルと `grep -c` の式 |
| client と使い方の正本 | `bin/<app>-client`・docs の節 |
| 人の入口と同じ関数を呼ぶ仕組み | View へ依頼を届ける口・driver |
| 構造的に通らない View の前段を残す場所 | docs の節の名前 |
| 安全装置 (差に数えないもの) | guard の型の名前 |
| 作業の場所・道具 | worktree の作り方・issue の置き場所と採番・実アプリの起動 (probe)・変異の道具・テストの回し方 |

## 手順

### 0. 準備

1. 対象 repo の CLAUDE.md・`.claude/rules/` と、debug API の docs (口の一覧と「improve-debug-api の値」節) を Read する
2. 値の節にある作業の場所 (worktree) を作る
3. 前回の点検の issue を探して読む: `grep -rln 'improve-debug-api\|debug-api-parity' <issue の置き場所>`。決着した口 (debug 専用のまま残すと決めた口) は理由ごと引き継ぐ
4. 口が多ければ範囲を決める (route のファイル・口の群で区切る)。範囲は issue に書く

### 1. 口を挙げる

値の節の式で全体と範囲の件数を出し、範囲の口を全部表に載せる (数えずに「全部見た」と書かない)。振り分けの形を変えたら、値の節の式も直す。

### 2. 口ごとに段を決める

| 段 | 意味 | 確かめ方 |
|---|---|---|
| R | 読むだけ (状態を変えない) | 書き込みが無いことを読む |
| A | 入力の合成 | 本物の入力と同じ配送に載るか。view へ直接渡す形は、窓の振り分けと monitor を飛ばすので、その差を書く |
| B | 人の入口と同じ関数 | 下の 3 |
| C | debug 専用 | 人の入口が無いこと・理由がコードと docs にあること |
| G | 安全装置 | 狭めるだけで人の経路を飛ばしていないこと |

### 3. B の口は、人の入口までの前段・後段を突き合わせる

1. 口が呼ぶ関数の呼び出し元を、2 つの方法で挙げる (dupscan などの構文の検索と `rg`)。構文の検索は closure・Binding の中の呼び出しを落とすことがある
2. 人の入口 (View・メニュー・ショートカット) から、その関数までの間にあるもの (前段) と、呼んだ後にあるもの (後段: 結果の記録・toast・status) を列挙する。
   **人の経路が前提の状態で変わるなら (同じ接続か・開いているか・選択があるか)、状態ごとに通る入口を分けて突き合わせる** (2026-11-08: 同じ接続の中の移動はパンくずだけで、
   別の接続は sidebar を通ってからパンくず。1 通りで書いて、人が通らない入口を通した)。
   **処理を人と共有する場合は、人と debug で違う入力・資源の寿命 (保存先が応答の後に消える等) を挙げ、成功の後の記録・通知を含む副作用が両方で正しいかを確かめる**
   (2026-11-08: 一時の保存先を「最後のダウンロード」として記録した)
3. 分ける:
   - 口が飛ばしている前段・後段のうち、人の入口と口が共有できる層 (VM・coordinator・dispatcher) にあるもの → 差 (直す)
   - View / AppKit の側にあって、口の経路では構造的に通らないもの → 値の節の「残す場所」に載っているかを見て、無ければ足す。その前段をテストが見ているかも書く
4. 人の入口が上の層 (dispatcher など) を通るのに、口が下の層を直接呼ぶ形も差に数える

### 4. issue に書き出す

値の節の置き場所と採番で起票する (注入された issue 規約と反証レビューに従う)。本文に範囲と次の表を置き、行数を手順 1 の範囲の件数と合わせる。

| 口 | 段 | 口が呼ぶもの | 人の入口 | 口だけが飛ばすもの・差 | 対応 |
|---|---|---|---|---|---|

対応の欄は「直す」「残す場所に載せた」「debug 専用のまま (理由)」「安全装置」「差なし」のどれか。人の挙動を変える判断が要るもの (意図して入れた分岐を寄せる等) は「判断待ち」にしてユーザーに聞く。

### 5. 直す

優先の順:

1. **口を入力の合成に寄せる**: メニュー・キー・クリックで同じ操作ができるなら、口の中身をそれに替えるか、口を消して docs で案内する
2. **前段・後段を共通の関数へ移す**: 人の入口の前段・後段が View に置かれていて口が飛ばせてしまうなら、人の入口と口の両方が呼ぶ関数 (VM・dispatcher・coordinator) の中へ移す。
   口の側にだけ同じ判定を写して直さない (写しは片方だけ更新されてずれる)
3. **写すのは最後**: 前段を移せない (View の見た目の状態にしか無い) ときだけ、口で同じ判定をし、写したことと元の場所を両方のコメントに書く

**1 回の操作を人の複数の手順へ分ける場合は、元の操作が束縛していた対象 (タブ・接続・世代) を保つ。既存の入口で保証できない場合は、await をまたいだ次段の実行前に対象を照合する**
(2026-11-08: 「開く → パンくず」に分けたら、段の間に別の要求に追い越された接続へ path を当てた)。

debug 専用の処理を足して差を埋めない (例: 人の経路が落ちる所を、口の側だけで避ける)。

### 6. 確かめる

- 直した前段・後段ごとに単体テストを書き、値の節の変異の道具で、前段を外す (退行を戻す) 変異が狙ったテストだけで red になることを見る
- 値の節の実アプリの起動 (probe) で、直した口が人の入口と同じ結果 (同じ断り・同じ状態・同じ toast) になることを client で確かめる。
  段をつなぐときは、次の段の結果を読む前に、前の段で変わるはずの状態 (タブの数・スロットや一覧の中身・key window) を読む
- 判断・境界が動いた変更なので、commit の前に敵対レビューを通す (`~/.claude/CLAUDE.md` のレビュー方針)。直した差分にもう 1 周
- debug API の docs (口の一覧・値の節・残す場所) と client の usage を同じ commit で直す

### 7. 締める

issue の表の対応の欄を全部埋め (直した commit の件名・残す場所に載せた節・残す理由)、done へ送る。範囲の外に残した口は、次の点検の範囲として issue に書く。
