# 自然な日本語で書く

文法が正しくても、読み手が「何が」「どうなる」を補えない文は伝わらない。この skill は、人が読む日本語の文を書くときの規範と、
書いた後の確かめ方を持つ。

規範は 2 層に分ける。

- **人 (と Claude) が読んで守るもの**: 主語・目的語の抜け、語が機能を言い表しているか、直訳の硬さ、否定対比・擬人化・前置きと定型の結び。構文として整った文は機械の検査を素通りするので、ここが本体
- **機械 (`ja-textlint`) が見るもの**: 冗長な表現・助詞の重複・長すぎる文・文体の混在などの書き癖と、AI が書きがちな語の一部・表示されない太字

## まず避ける 3 つの失敗 (実例)

2026-11-04 に、Video Grid Player の課金案内の画面 (paywall) で出たもの。表の上 2 行の文は、`ja-textlint` に通してもどちらも指摘が出なかった (rc 0)。

| 悪い例 | 何が悪いか | 良い例 |
|---|---|---|
| 見つからない動画は先頭から再生します。 | 何が見つからないのかが無い。読み手は直前の文から推測するしかない | 飛ばす部分が見つからない動画は、最初から再生します。 |
| 動画の始まりを見つけて、そこから再生します。 | 「始まり」は機能 (先頭の無音を飛ばす・人が映る所から再生する) を言い表していない。どの動画でも 0 秒が始まりに見える | 冒頭の無音や、人が映るまでの部分を飛ばして再生します。 |
| (英語の UI の文 "Finds where each video really begins" をそのまま訳す) | 英語の名詞の組み立てを写すと、日本語では何をする機能かがぼやける | 利用者に起きること (飛ばす・再生する) を動詞で書く |

## 書く前に決めること

1. **読み手と場面**: 誰が・どの画面 (または文書) の・どの瞬間に読むか。UI の注意書きは、上の説明文を読んだ直後に読まれるとは限らない
2. **1 文で伝えること**: 「誰 (何) が」「何を」「どうする / どうなる」を、日本語で 1 回言ってみる。言えなければ、まだ書かない
3. **文体**: UI の文言・ストアの説明文・ヘルプ・ユーザーへの報告は敬体 (です・ます)。issue・コミットメッセージ・コードのコメントは常体。
   ただし、その repo に既にある文の文体が違うなら、そちらに揃える

## 規範

### 1. 主語と目的語を省かない

- 「何が」「何を」を、読み手が前後の文を読まなくても分かるように書く。日本語は主語を省きやすいが、省けるのは直前の文と主語が同じときだけ
- 「〜場合」「〜ものは」の前には、何の場合か・何のものかを置く
  - ✗ `失敗した場合は、もう一度お試しください。`
  - ✓ `購入に失敗した場合は、もう一度お試しください。`

### 2. 機能を、利用者が体験する動作で書く

<!-- textlint-disable ja-technical-writing/no-mix-dearu-desumasu -->
- 内部の仕組みや抽象的な名詞 (「始まり」「処理」「対応」) ではなく、利用者の目と耳に起きることを動詞で書く
  - ✗ `解析の結果を適用します。`
  - ✓ `無音の部分を飛ばして再生します。`
<!-- textlint-enable ja-technical-writing/no-mix-dearu-desumasu -->
- 機能の限界も同じ粒度で書く (どの動画では使えないか)。払う前に読む文なら特に

### 3. 英語を直訳しない

- 英語の UI の文を訳すときは、語順ではなく「利用者に何が起きるか」から日本語で組み立て直す
- よく出る直訳の形:
  - `〜することができます` → `〜できます`
  - `あなたの動画は解析されます` (受け身と所有格) → `動画は Mac の中で解析します` (能動。「あなたの」は省く)
  - 「〜を有効にする」が機能の名前の代わりになっている →「〜を使う」「〜を表示する」など、起きることを書く
- 英語の元の文が曖昧なら、元の文も直す (訳だけを直すと、他の言語の訳が曖昧なまま残る)
<!-- textlint-disable ja-ai-vocabulary -->
- 英語の術語や言い回しを一語ずつ写した語 (直訳語) は、2 つを問う: その分野の人が仕様や手順書を自分で書くときに選ぶ呼び名か / 英語に戻すと一語ずつ対応するか。
  前者が「いいえ」で後者が「はい」なら書き直す。同じ repo の他の文書で何度も使われていることは、前者の答えを「はい」とする根拠にならない (AI が書いた語は次の文書へそのまま移る)
  - 機械が人や物の動作をする: `再送ジョブが拾う`・`失効が効く` → 何が何をするか (`再送ジョブがもう一度送る`・`古い鍵が使えなくなる`)
  - 実物の代わりの場所のたとえ: `受け口` → 実物の名前 (エンドポイント・ロードバランサー)
  - 英語の句を写す: `足すものがない` (add value)・`〜ときに効くのは` (what matters) → 英語の意味で書く (`得られる利点がない`・`〜ときに大事なのは`)
  - 術語に当てた漢字の名詞: `背景実行`・`時間窓`・`根因`・`台本`・`見張り`・`一覧の頭` → その分野の呼び名 (バックグラウンド実行・時間帯・根本原因・スクリプト・監視・先頭)。漢語やカタカナ語になっても呼び名で書く
  - 語を 1 つ差し替えるだけで済ませず、誰が何をどうするかが読める文に組み直す。何を指すかが前後の文や資料から決まらなければ、元の語を残して書き手に聞く
  - 残す: 定着した言い方 (`テストが通る`・`キャッシュが効く`・パッケージの依存先・第 2 版)。dotfiles で定義した用語 (正本・ゲート・台帳・入口・印) も直さない
<!-- textlint-enable ja-ai-vocabulary -->

### 4. 1 文に 1 つの事柄、結論を先に

- 読点 (、) で 3 つ以上つなぐ文は分ける。条件と結果が両方あるなら、結果 (読み手がすること・起きること) を先に置く
- 箇条書きの各行は、同じ形 (全部が名詞で終わる / 全部が文) に揃える

### 5. 同じものは同じ語で呼ぶ

- 1 つの画面・文書の中で、同じものを別の語で呼ばない (「先頭」「最初」「冒頭」を混ぜる、など)。別の語を使うなら、別のものを指すとき
- 画面の名前・ボタンの名前を文の中で引くときは、画面に出ている語とそのまま一致させる (「購入画面を開く」を押す)

### 6. 表記

- UI のラベル (ボタン・見出し) は短く、句点を付けない。文には句点を付ける
- 全角と半角の間の空白は、その repo の既存の書き方に揃える (dotfiles・my-products の文書は英数字の前後に半角の空白を入れる)
- 数字は算用数字 (7 日・9 種類)
- 補助動詞と形式名詞の「事」「為」はひらがなで書く (`して下さい` → してください・`出来ます` → できます・`する事` → すること・`する為` → するため)。中身のある名詞 (事の経緯) は漢字のまま
- 閉じの `**` を約物 (「」」「)」) の直後・文字の直前に置くと、太字は表示されない (`**「x」**に`)。`**` の外側に空白を入れるか、約物を太字の外へ出す

### 7. AI が書きがちな語を、起きていることの言葉に直す

<!-- textlint-disable ja-ai-vocabulary -->
- 比喩の動詞で済ませない。何がどう変わるかを書く
  - 「〜側に倒す」→「〜を優先する」「〜に揃える」
  - 「潰す」→「直す」「取り除く」
  - 「効く」→「止まる」「反映される」
  - 「前提が崩れる」→「〜という前提が成り立たなくなる」
- 「黙って」「静かに壊れる」(silently の直訳) は、エラーや通知が出ないのか (「エラーを出さずに」)、人が気づけないのか (「気づかないうちに」) を書き分ける
- 「既定値」「既定で」「既定の」は使わない。「指定しないときは 30 日」「何も渡さないと〜する」のように、何が起きるかを書く
- ソフトウェアの「版」は「バージョン」と書く。出版物・製品の種類を表す「第 2 版」「日本語版」は残す
- テストの手法の用語「変異」(mutation) は使わない。「実装をわざと壊して、テストが落ちるかを確かめた」のように、何をしたかを書く
- 語の候補は `ja-textlint` が warning で出す (下の「ja-textlint の中身」)。言い換えると意味が変わるときは元の語を残す。
  定義した用語 (規範 3 の末尾の一覧) は直さない
- 比喩を直しても、元の文の含み (「地味に」「うっかり」「〜てしまった」) は別の語で残す。原文に無い強さの語 (必ず・確実に) は足さない
- 「骨が折れる」「手を焼く」のように、AI が広まる前から人が書いている慣用句は、比喩でも残す
<!-- textlint-enable ja-ai-vocabulary -->

### 8. 否定対比 (A ではなく B) は、否定が主張を担うときだけ残す

- A を外しても主張が変わらない文は、A を外して B だけを書く
  - ✗ `この変更は見た目の調整ではなく、読みやすさの改善だ。` (見た目の調整を打ち消す句を外しても、言いたいことは変わらない)
  - ✓ `この変更は読みやすさの改善だ。`
- 誤解や思い込みを正す否定は残す (`原因はキャッシュではなく DNS の設定だった`)。直すときも、A を「A に加えて B」の並列や順位に変えない。
  両方を認める文 (`弱みではなく視点の違いでもある`) も 1 文のまま残す
- 否定と肯定を 2 文に分けた形 (`必要だったのは新しい道具ではない。使い方を揃えることだった。`) は、否定を残して 1 文にする。
  直した形は `必要だったのは新しい道具ではなく使い方を揃えることだった。` で、「なく」の後に読点を足さない。後ろの文が別の主張を足しているときと、ストアの説明文などで短い文を意図して重ねた所は 2 文のまま
- 見出しは「A ではなく B」の形にせず、B だけを書く

### 9. 道具やコードに、人の気持ち・知識・役目を持たせない

- 道具・コード・概念を人にたとえた文は、何を受け取り、何を返し、何を呼ぶか (利用者に何が起きるか) の文に直す
  - ✗ `容量が足りなくなると、バックアップの処理は泣き言を言う。` → 警告を出すのか、エラーで止まるのかを書く
  - ✗ `この関数は呼び出し元の事情を知っている。` → 受け取る引数・呼ぶ先・返す値で書く
  - 実際に何が起きるかがコードや資料から分からなければ、元の文を残して書き手へ確かめる (「直すときに守ること」の「情報を足さない」)
- 人の判断を抽象的な名詞の作用に書いた文 (`見積もりの甘さが判断を遅らせた`) は、誰の行動かが分かるときだけ、その人を主語にする
- 残す: 働きが一読で分かる擬人化 (`センサーが異常に気づく`・`hook が push を止める`)、識別子が主語の文 (`parse()` は空の配列を返す)、設計の用語 (責務を持つ・依存する)

### 10. 前置き・定型の結び・言い直しの締めを削る

- 意味を担わない前置き (`重要なのは`・`結論から言うと`・`正直に言うと`・`それでは見ていきましょう`) は削る。
  「重要なのは」が評価を担うなら、評価を述語へ移して残す (`重要なのは X だ` → `X が重要だ`)。報告で結論を先に置く構成そのものは変えない
- 続く本文を予告するだけの文 (`次の節では〜を説明します`) は、続く文と 1 文にするか削る。数の予告 (`理由は 3 つある`) は、続く項目の数と合うときだけ続く文とまとめる。合わないときは、数と項目を変えずに書き手へ確かめる。長い説明で数の予告が読み手の案内になっているなら残す
- 定型の結びとチャットの返答の名残 (`いかがでしたでしょうか`・`お役に立てれば幸いです`・`ご希望があれば〜できます`・`ご質問ありがとうございます`) を、文書や報告に残さない。
  メールの結びの挨拶と、書き手が実際にしている申し出・勧め・決意 (`〜に取り組んでまいります`) は残す
- 文末の付け足し (`〜と言っても過言ではありません`・`〜というわけです`) は枠を外して事実を書く。推量の強さは保つ (`〜と言えるでしょう` → `〜でしょう`。断定に上げない)。
  数値の裏付けがある強調・引用・会話と、区分に当たるかを判断する文 (`〜は契約と言えるでしょう`) は残す
- 本文で言い終えたことを同じ強さで繰り返すだけの締め (`まとめると`・`要するに`・本文を繰り返す「まとめ」の節) は削る。
  新しい情報・結論の絞り込み・次にすることを述べる文と、長い文書の要約・依頼で指定されたまとめは残す。削る前に、そこにしか無い数値・条件・例外が無いかを確かめ、あれば本文へ移す

## 直すときに守ること (書いた文・人の文の手直し)

- **意味を変えない**: 直す前と後で、主張・何を認め何を否定するか・言い切りの強さ (断定・推量・許可・義務)・文の働き (依頼・説明・予定・評価) を比べ、
  1 つでも変わる案は捨てて元の文を残す。「〜してよい」を「〜する」に、「〜場合がある」を言い切りにしない
- **情報を足さない**: 元の文・依頼・資料に書いていない動作主・原因・条件・数値を、推測で足さない。補えないなら書き手に聞く
- **1 か所ずつ直す**: sed・perl などの置換で文書をまとめて書き換えない。同じ語でも、前後の文を読んで直すかを決める
- **確かめたい点は本文に入れない**: 読み取れない所への注記 (`【要確認】` など) や質問を本文に書かない。原文が読み手に伝えている「未定」「調査中」「未検証」は本文に残す。手直しを返すときは、直した所・直さずに残した所とその理由・書き手に確かめたい点を、本文とは別に分けて書く

## 書いた後に確かめること

1. **声に出して読む**: 読み手が補わないと意味が通らない所 (主語・目的語・指示語の指す先) が無いか
2. **前後を隠して読む**: その 1 文だけで、何の話が伝わるか (UI の注意書き・トースト・エラーの文は単独で読まれる)
3. **機械の検査を通す**:

   ```sh
   ja-textlint <file>...                                   # Markdown・テキストのファイル
   printf '%s\n' "<文>" | ja-textlint --stdin --stdin-filename x.md   # UI の文言・コミットメッセージの下書き
   ```

   - `ja-textlint` は dotfiles の `bin/` にあり、PATH から呼べる (どの repo の中からでも同じ)
   - Claude Code が Markdown を書くと、hook が書いた行の指摘を知らせる。
     知らせるのは `ja-ai-vocabulary` と `ja-bold-not-rendered` だけ。hook の実体は `_claude/hooks/ja-textlint-on-edit.sh` (PostToolUse の Write / Edit)。
     preset の指摘 (文の長さなど) と前からある行の指摘は知らせないので、書き上げた後の全体の検査は手で打つ。
     依存が未導入なら hook は黙る (一度手で打てば入る)
   - 指摘は直す。直さないなら、理由を報告に書く (例: 引用した原文・固有名詞)
   - `ja-ai-vocabulary` の warning は rc 0 のまま出る。rc だけを見ず、出力の warning も読む
   - rc 0 は「書き癖の指摘が無い」だけで、規範 1〜3・8〜10 を守った証拠にはならない
4. **文字列カタログ・翻訳がある場合**: 直した日本語に合わせて、英語の元の文と他の言語の訳も同じ意味に揃える

## ja-textlint の中身

<!-- textlint-disable ja-ai-vocabulary -->
- 規則は textlint の [preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing) (MIT) と、
  自作の 2 本 (`textlint/rules/`)。バージョンと設定の正本は `textlint/` (`package.json`・`package-lock.json`・`textlintrc.json`)
  - `ja-ai-vocabulary` (warning。rc は 0 のまま): 規範 7 の語 (版・〜側に倒す・黙って・静かに壊れる・潰す・溶かす・効く・前提が崩れる・既定・変異)。
    語の選び方は [yomiyasu](https://github.com/nanaism/yomiyasu) (MIT。`textlint/LICENSE-yomiyasu`) の語彙の一覧から、dotfiles で当たりの多いものを選んだ。
    書き換えはしない (`--fix` でも変わらない)
  - `ja-bold-not-rendered` (error): 表示されない `**` (規範 6)
  - 自作の規則の重さは規則の中で決めている。`textlintrc.json` に書いても、`--rulesdir` で読ませた規則には届かない
<!-- textlint-enable ja-ai-vocabulary -->
- 外している規則: `ja-no-mixed-period` (文末の句点を求める)。箇条書き・コミットの件名・UI のラベルは句点で終わらないのが普通で、
  全部の行に出る指摘は読まれなくなるため
- 例文の引用が文体の規則に引っかかるときは、その範囲を無効化のコメントで囲む。コメントは行頭に置く。
  字下げした箇条書きの中に置いたコメントは無視される。形は `<!-- textlint-disable <規則> -->` と `<!-- textlint-enable <規則> -->` (`textlint-filter-rule-comments`)
- 依存は初回の起動で `~/.cache/ja-textlint/<lock の hash>/` に `npm ci` で入れる (node と npm が要る)。バージョンを上げるときは
  `textlint/package.json` を書き換えてから、そのディレクトリで `npm install --package-lock-only --ignore-scripts` を打って lock を作り直す
  (lock が変わると別の hash のディレクトリに入れ直す。古いディレクトリは消さずに残るので、`~/.cache/ja-textlint/` の中の古いものは手で消す)
- 見ないもの: 主語・目的語の抜け・語の選び方 (`ja-ai-vocabulary` の一覧の外)・直訳の硬さ (「まず避ける 3 つの失敗」の 2 つの文は、どちらも rc 0 で通った)
