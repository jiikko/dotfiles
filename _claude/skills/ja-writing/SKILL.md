# 自然な日本語で書く

文法が正しくても、読み手が「何が」「どうなる」を補えない文は伝わらない。この skill は、人が読む日本語の文を書くときの規範と、
書いた後の確かめ方を持つ。

規範は 2 層に分ける。

- **人 (と Claude) が読んで守るもの**: 主語・目的語の抜け、語が機能を言い表しているか、直訳の硬さ。構文として整った文は機械の検査を素通りするので、ここが本体
- **機械 (`ja-textlint`) が見るもの**: 冗長な表現・助詞の重複・長すぎる文・文体の混在などの書き癖

## まず避ける 3 つの失敗 (実例)

2026-11-04 に、Video Grid Player の課金案内の画面 (paywall) で出たもの。表の上 2 行の文は、`ja-textlint` に通してもどちらも指摘が出なかった (rc 0)。

| 悪い例 | 何が悪いか | 良い例 |
|---|---|---|
| 見つからない動画は先頭から再生します。 | 何が見つからないのかが無い。読み手は直前の文から推測するしかない | 飛ばす部分が見つからない動画は、最初から再生します。 |
| 動画の始まりを見つけて、そこから再生します。 | 「始まり」は機能 (先頭の無音を飛ばす・人が映る所から再生する) を言い表していない。どの動画でも 0 秒が始まりに見える | 冒頭の無音や、人が映るまでの部分を飛ばして再生します。 |
| (英語の UI の文 "Finds where each video really begins" をそのまま訳す) | 英語の名詞の組み立てを写すと、日本語では何をする機能かがぼやける | 利用者に起きること (飛ばす・再生する) を動詞で書く |

## 書く前に決めること

1. **読み手と場面**: 誰が・どの画面 (または文書) の・どの瞬間に読むか。UI の注意書きは、上の説明文を読んだ直後に読まれるとは限らない
2. **1 文で伝えること**: 「誰 (何) が」「何を」「どうする / どうなる」を、日本語で 1 回言ってみる。言えなければ、まだ書かない
3. **文体**: UI の文言・ストアの説明文・ヘルプ・ユーザーへの報告は敬体 (です・ます)。issue・コミットメッセージ・コードのコメントは常体。
   ただし、その repo に既にある文の文体が違うなら、そちらに揃える

## 規範

### 1. 主語と目的語を省かない

- 「何が」「何を」を、読み手が前後の文を読まなくても分かるように書く。日本語は主語を省きやすいが、省けるのは直前の文と主語が同じときだけ
- 「〜場合」「〜ものは」の前には、何の場合か・何のものかを置く
  - ✗ `失敗した場合は、もう一度お試しください。`
  - ✓ `購入に失敗した場合は、もう一度お試しください。`

### 2. 機能を、利用者が体験する動作で書く

<!-- textlint-disable ja-technical-writing/no-mix-dearu-desumasu -->
- 内部の仕組みや抽象的な名詞 (「始まり」「処理」「対応」) ではなく、利用者の目と耳に起きることを動詞で書く
  - ✗ `解析の結果を適用します。`
  - ✓ `無音の部分を飛ばして再生します。`
<!-- textlint-enable ja-technical-writing/no-mix-dearu-desumasu -->
- 機能の限界も同じ粒度で書く (どの動画には効かないか)。払う前に読む文なら特に

### 3. 英語を直訳しない

- 英語の UI の文を訳すときは、語順ではなく「利用者に何が起きるか」から日本語で組み立て直す
- よく出る直訳の形:
  - `〜することができます` → `〜できます`
  - `あなたの動画は解析されます` (受け身と所有格) → `動画は Mac の中で解析します` (能動。「あなたの」は省く)
  - 「〜を有効にする」が機能の名前の代わりになっている →「〜を使う」「〜を表示する」など、起きることを書く
- 英語の元の文が曖昧なら、元の文も直す (訳だけを直すと、他の言語の訳が曖昧なまま残る)

### 4. 1 文に 1 つの事柄、結論を先に

- 読点 (、) で 3 つ以上つなぐ文は分ける。条件と結果が両方あるなら、結果 (読み手がすること・起きること) を先に置く
- 箇条書きの各行は、同じ形 (全部が名詞で終わる / 全部が文) に揃える

### 5. 同じものは同じ語で呼ぶ

- 1 つの画面・文書の中で、同じものを別の語で呼ばない (「先頭」「最初」「冒頭」を混ぜる、など)。別の語を使うなら、別のものを指すとき
- 画面の名前・ボタンの名前を文の中で引くときは、画面に出ている語とそのまま一致させる (「購入画面を開く」を押す)

### 6. 表記

- UI のラベル (ボタン・見出し) は短く、句点を付けない。文には句点を付ける
- 全角と半角の間の空白は、その repo の既存の書き方に揃える (dotfiles・my-products の文書は英数字の前後に半角の空白を入れる)
- 数字は算用数字 (7 日・9 種類)

## 書いた後に確かめること

1. **声に出して読む**: 読み手が補わないと意味が通らない所 (主語・目的語・指示語の指す先) が無いか
2. **前後を隠して読む**: その 1 文だけで、何の話が伝わるか (UI の注意書き・トースト・エラーの文は単独で読まれる)
3. **機械の検査を通す**:

   ```sh
   ja-textlint <file>...                                   # Markdown・テキストのファイル
   printf '%s\n' "<文>" | ja-textlint --stdin --stdin-filename x.md   # UI の文言・コミットメッセージの下書き
   ```

   - `ja-textlint` は dotfiles の `bin/` にあり、PATH から呼べる (どの repo の中からでも同じ)
   - 指摘は直す。直さないなら、理由を報告に書く (例: 引用した原文・固有名詞)
   - rc 0 は「書き癖の指摘が無い」だけで、規範 1〜3 を守った証拠にはならない
4. **文字列カタログ・翻訳がある場合**: 直した日本語に合わせて、英語の元の文と他の言語の訳も同じ意味に揃える

## ja-textlint の中身

- 規則は textlint の [preset-ja-technical-writing](https://github.com/textlint-ja/textlint-rule-preset-ja-technical-writing) (MIT)。
  版と設定の正本は `textlint/` (`package.json`・`package-lock.json`・`textlintrc.json`)
- 外している規則: `ja-no-mixed-period` (文末の句点を求める)。箇条書き・コミットの件名・UI のラベルは句点で終わらないのが普通で、
  全部の行に出る指摘は読まれなくなるため
- 例文の引用が文体の規則に引っかかるときは、その範囲を無効化のコメントで囲む。コメントは行頭に置く。
  字下げした箇条書きの中に置くと効かない。形は `<!-- textlint-disable <規則> -->` と `<!-- textlint-enable <規則> -->` (`textlint-filter-rule-comments`)
- 依存は初回の起動で `~/.cache/ja-textlint/<lock の hash>/` に `npm ci` で入れる (node と npm が要る)。版を上げるときは
  `textlint/package.json` を書き換えてから、そのディレクトリで `npm install --package-lock-only --ignore-scripts` を打って lock を作り直す
  (lock が変わると別の hash のディレクトリに入れ直す。古いディレクトリは消さずに残るので、`~/.cache/ja-textlint/` の中の古いものは手で消す)
- 見ないもの: 主語・目的語の抜け・語の選び方・直訳の硬さ (「まず避ける 3 つの失敗」の 2 つの文は、どちらも rc 0 で通った)
