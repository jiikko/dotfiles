# zundamon-kaisetsu の改善点の観点

動画を作り終えたとき、または「改善点を挙げて」と言われたときに、この観点で振り返って改善点を挙げる。
動画を作る手順 (SKILL.md) には使わない。

**この文書は適宜更新する**。新しい観点・測り方が見つかったら足し、決着した (直した・やらないと決めた) 観点は、
理由とともに「決めたこと」へ移す。今動いている改善の一覧は issue (epic 674 とその子 issue) にあり、ここには観点と測り方だけを書く。

## 挙げ方

1. 作った動画の流れ (手順 0〜8) を振り返り、下の観点ごとに「実際に手間になったこと」を探す。思いつきの案ではなく、
   その動画で起きた出来事 (撮り直し・見落とし・指摘) を根拠にする
2. 案ごとに、根拠 (何が何回起きたか)・効き目・コストを書く。測れるものは測る (下の「測り方」)
3. 既存の issue (`grep -rln zundamon issues/`) と、下の「決めたこと」に同じものが無いかを見てから挙げる
4. ユーザーが採ると決めたものは issue にする (epic 674 の子に足す)

## 観点

### 生成コスト

- **トークン**: サブエージェントの体数。1 体あたり仕事の量によらず約 15 万トークン使う (起動時の固定分が大半)。
  体数を増やす手順・確認の観点が足されていないか。機械で決まる確認をサブエージェントに任せていないか
- **機械時間**: mp4 の撮影で撮る「見た目の状態」の数と Chrome の起動回数。状態を増やす変更 (動く演出・状態の種類) が入っていないか
- **手戻り**: 合成し直し・撮り直しの回数。後の手順で初めて分かることを、前の手順で分かるようにできないか
  (例: 字幕の速さの警告は build の撮影の前に出ているのに、撮影を止めないので撮り終えてから気づいた。issue 676)

### 台本の精度

- 裏取り・統合確認・読みの検査が、何を見つけて何を見落としたか。見落としが同じ種類で続くなら、その種類を道具か手順で拾えないか
- main agent 自身の誤り (台本の編集の取り違え・テストの fixture を作った値で埋める 等) が、手段の側で防げないか
- 資料の語り方のモード・導入と本題の区切りなど、ユーザーに指摘された書き方が、手順と校正の観点に入っているか

### 見た目 (図とキャラクターの彩り)

- ユーザーが見て伝わりにくいと言った場面 (区切りが見えない・文字が小さい・単語の途中で折り返す)
- 図解の種類が足りず、別の種類で代用した場面 (箇条書きをコードの図解で出した 等)
- 見た目を足す案は、mp4 の撮る状態の数をどれだけ増やすかと組で見る (止まった絵で表せるなら増えない)

### 保守

- SKILL.md・README・src/zundamon-kaisetsu の README / CLAUDE.md と、実装 (キー・上限・コマンド・rc) の食い違い
- 継ぎ足しの名残 (手順を組み替えた後の古い呼び名・手順番号・数値)

## 測り方

| 測るもの | どこで見るか |
|---|---|
| サブエージェントのトークン | 完了の通知の `subagent_tokens` (キャッシュから読まれた分の内訳は出ない) |
| mp4 の撮る状態と Chrome の回数 | build の出力の「見た目の状態 N 種類を Chrome M 回で描く」 |
| 撮り直し・合成し直しの回数 | その動画で build / synth を何回回したか |
| 確認の見落とし | 欠陥を仕込んだ台本で、見つけた数を数える (2026-10-08 の試験: 12 個中 sonnet 11・haiku 10。issue 673 の進捗) |

## 決めたこと

- 書く前の裏取りは省かない (2 本とも資料の不正確な点を拾った。epic 674 の親 issue)
- HTML を経由せずに動画を描く作りにはしない (トークンは変わらず、描画の実装が 2 つになる。同上)
- mermaid の図は `npx` の mermaid-cli で描くまま (2026-10-08 にユーザー判断)。Node の依存を外す案は、版を固定した mermaid.js を同梱して
  build の Chrome で描く形が最も素直 (見た目は変わらない)。Node が問題になったら再評価する
- 確認のサブエージェントは 2 体 (書く前の裏取り・書いた後の統合確認)。haiku に替えてもトークンは減らない (issue 673 の進捗)
