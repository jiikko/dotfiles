# all-audit-on-diy

audit skill を「全タイプ × 直接実行 × その場で対応」に固定した版。監査タイプの一覧・各タイプの調べ方・発見の型 (L1〜L7 / E1〜E4 / F1〜F5 / K1〜K4 / C1〜C4)・偽陽性の除外・audit-log の書式は **`~/.claude/skills/audit/SKILL.md` が正本**。始める前に全文を Read し、ここへ写さない (写すと audit 側にタイプが増えたとき置き去りになる)。

audit skill との違いは 3 つだけ:

1. **Step 2・3 (タイプとモードの選択) を飛ばす**。タイプは audit skill の一覧の全部、モードは直接実行
2. **監査の範囲を引数の対象に絞る** (repo 全体ではない)
3. **発見をこのセッションで直す**。issue に書き出して終わりにしない (下の 3 節)

## 0. 準備

- 引数が無ければ対象を 1 問だけ聞く (何を監査するかは推測で決めない)
- 大きな作業なので、始める前に `ratelimit -source claude -check` で 5h 枠を見る。超過なら `subagent-model-tiering.md` の 5h 枠の項どおり、控える / 縮小する / リセット後に回すをユーザーに諮る
- 作業場所は repo の規約に従う (dotfiles ならセッションの worktree)。自分の作業ノートは `skill-tmpdir all-audit-on-diy` が返す dir に置く
- `issues/audit-log` を読み、同じ対象を最近回した記録と、その監査の issue に残った却下理由を先に読む (同じ指摘を再提出しない)

## 1. 対象の母集合を決める

- 対象を**ファイルの一覧**に落とし、件数を機械で数えてノートに書く (`git ls-files <dir>` / `git grep -l <symbol> -- :/`)。`:/` が無いと cwd の下しか探さない。素の `rg -l` は隠しディレクトリを読まない。どちらも `.claude/rules/` を落とす。仕様書 (docs)・規約の文書 (rule・AGENTS.md)・テストも含める。規約の文書は名前に対象を含まないことが多いので、ファイル名ではなく参照で拾う。以降の全数勘定はこの母集合に対して書く
- 対象の仕様 (docs・README・その dir の CLAUDE.md) と、対象を名指しする open / done の issue を先に読む。決めた仕様を不具合として拾わないため (audit skill の「起票の前に、その挙動が既に決めた仕様でないかを確かめる」)
- **監査の記録の issue をここで起こす** (`NNN-research-audit-<対象>-YYYY-MM-DD.md`)。骨組み (タイトル・起票日・対象・母集合の件数) だけで commit & push して番号を取る (issue 運用規約の採番の項)。中身は 4 節の形でタイプごとに足していく

## 2. タイプを 1 つずつ回す

audit skill の一覧の順に、**1 タイプずつ**監査して対応まで終えてから次へ進む (並行しない。書き込む作業が同じ木を触るため)。

- 設計系のタイプは audit skill の「設計系 (design / …) を直接実行でまとめて回すとき」の段落に従い、1 回の走査でまとめてよい。1 つの発見は一番狭く当てはまる型に 1 回だけ帰属させる
- **対象に当てはまらないタイプは、理由を 1 行書いて飛ばす** (例: UI を持たない対象の ui-components、workflow を持たない対象の ci)。黙って飛ばさない
- 発見ごとに「発火条件」を書く。示せないものは直さず「未確認」として 4 節の記録に残す
- Explore に任せてよいのは読む場所を探すところまで (audit skill の直接実行の節)

## 3. 発見をその場で対応する

発見ごとに次のどれかに決め、決めた理由をノートに 1 行書く:

| 決め方 | 当てはまるもの | やること |
|---|---|---|
| **直す** | 発火条件を再現でき、直し方が 1 つに決まり、対象の中で閉じる | 回帰テストを書いて red を見てから直す。テストは `mutation-verify-new-tests.md` の変異で red を確かめる。commit は 1 発見 (か同じ根の数件) ごと |
| **issue に起こす** | 直し方に設計の判断が要る / 対象の外へ広がる / ユーザーの判断が要る (見た目・仕様の変更) | 注入される issue 運用規約どおりに起票する。新規 issue の反証レビューも規約どおり |
| **却下** | 決めた仕様・偽陽性・再現しない | 理由を該当コードの近くにコメントで残すか (`pending-issue-rationale-in-code.md`)、4 節の記録に書く |

- 「直す」を選んでも、判断ロジック・境界・状態遷移が動く修正は `~/.claude/CLAUDE.md`「レビュー方針」の外部レビュー・敵対的レビューを通してから commit する。仕様が変わる修正は docs も同じ commit で直す
- 見た目・キー割当・文言など**ユーザーが決めるもの**は直さず、issue に選択肢を書いて起こす (`decide-layout-in-sample-renderer-first.md`)
- 直している途中で 2 回外したら、3 回目を打つ前に `escalate-to-forge-after-failed-tries.md` に従う

## 4. 記録して終える

- **1 節で起こした記録の issue に**、タイプごとに 1 行: 見た範囲 / 発見 N 件 (直した M・起票 K・却下 R) / 「攻めたが見つからなかった範囲」。却下と未確認は理由つきで残す (`move-report-conclusions-to-issues.md`。次の監査が同じ指摘を出さないため)。直した発見は commit の subject を、起票した発見は issue 番号を書く
  - タイプを 1 つ終えるたびに追記する (最後にまとめて書かない。途中で枠が尽きても、それまでの却下理由が残る)
  - 残課題が無ければ done へ送る。起票した issue があれば、それへのリンクを残したまま done にしてよい
- `issues/audit-log` (無ければ作る) にタイプごとの行を audit skill の書式で追記する。mode は `direct`、出力ファイルの欄は記録の issue のパス
- 最後に root の検査 (`make test` 等、repo の commit 前の検査) を回し、push まで済ませる (repo の規約どおり)
- ユーザーへの報告は結論から: タイプごとの件数の表 / 直したもの / 起こした issue / ユーザーの判断が要るもの

## やらないこと

- 対象の外のファイルを「ついでに」直さない。対象の外で見つけたものは、ぼやきか issue にする
- 件数を増やすための推測の起票をしない (audit skill の「推測だけで issue を量産しない」)
