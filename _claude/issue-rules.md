# issue 運用の共通規約（`issues/` を持つ repo 共通）

> この文書は `issues/`（または `issue/`）を持つ repo でだけ、SessionStart hook
> `_claude/hooks/issue-rules-inject.sh` がセッションへ注入する。正本は
> `~/dotfiles/_claude/issue-rules.md`。**各 repo の `issues/README.md` には repo 固有の
> 事項（採番コマンド・完了コマンド・lint・INDEX.md・固有ディレクトリ）だけを書き、
> ここにある規約を写さない**（写すと片方だけ更新されて乖離する。2026-09-19 に 6 アプリの
> コピーが正本より古いまま放置されていたのが起点。dotfiles issue 401）。

## ファイル名

`NNN-<type>-<slug>.md`

- **NNN**: 3 桁ゼロ埋めの連番を先頭に置く。**`issues/` 配下の全体**（直下・`next/`・`pending/`・
  `waiting/`・`done/`・`epic/<name>/` とその下の状態ディレクトリ）で最大番号 + 1。番号は再利用しない。
  採番前に `git fetch` して origin 側も数える（push 済みの他セッションの採番は working tree に見えない）。
  **採番したら即 commit & push する**（ローカルに置いている間は衝突が見えない）
- 状態ディレクトリへ移してもファイル名は変えない。**`issues/` の外（コード・docs・rules）からは番号で参照し**、
  `issues/done/012-….md` のような裸のパスを書かない（移動で切れる）
- **slug**: kebab-case の短い説明。日付を残すなら末尾に `-YYYY-MM-DD`
- 番号の無い `*.md` は issue ではない（タスクリスト・設計メモ・README）

### type 語彙（どの repo でも使ってよい）

| type | 用途 |
|---|---|
| `feat` | 新機能・機能拡張 |
| `bug` | 不具合修正（commit の `fix` 相当だが issue では `bug`） |
| `refactor` | 挙動を変えない構造改善・複雑性削減 |
| `perf` | 速度・メモリ・リソースの改善（実測を本文に置く） |
| `ux` | 操作性・使い勝手の改善 |
| `test` | テスト追加・テスト基盤・カバレッジの gap 解消 |
| `docs` | ドキュメント・コメント・ルールの整備 |
| `chore` | 雑務（依存更新・CI・ツール整備・表示の手直し） |
| `cleanup` | dead code・未使用・軽微な整理 |
| `design` | 設計判断・境界設計（実装より「どう作るか」の検討が主） |
| `architecture` | レイヤー・依存方向・モジュール境界に関わる大きめの構造 |
| `research` | 調査・設計検討（成果物がコードでないもの） |
| `risk` | 未確認リスク・観測ポイントの記録 |
| `task` | 移行・引き継ぎ等の作業トラッカー |
| `human` | **人間しかできない作業**（動作確認・目視レビュー・外部サービス操作・判断待ち）。`期限:` 必須 |
| `retro` | **セッションの振り返り**。下節 |

迷ったら「この issue の主たる成果物は何か」で選ぶ。

## 状態 = ファイルの位置

状態の唯一の出典はファイルの位置。既読ヘッダー・状態チェックボックスは使わない（書き換え忘れで嘘が残る）。

- `issues/*.md` — open
- `issues/next/` — **着手の claim**。issue ファイル本体は動かさず `ln -s ../NNN-x.md issues/next/NNN-x.md` の
  symlink を置き、**その目印だけを pathspec commit して即 push する**（push されるまで他マシンから見えない）。
  着手前に `git fetch` して既に next に居ないか見る。このディレクトリが在ることが opt-in で、無い repo では適用しない
- `issues/pending/` — 凍結。**再開の主導権は自分**。着手条件・trigger を本文冒頭に書く
- `issues/waiting/` — 着手済みで、**こちらから起こせない事象**（再現・観測・外部イベント）待ち。
  待っているものと、それが来たら何が分かるかを冒頭に書く
- `issues/done/` — 完了。移動前に `next/` の目印を消す。本文の相対リンクと他 issue からの参照を張り直す
  （repo に完了コマンドがあればそれを使う）
- `issues/epic/<name>/` — 親テーマでまとめる group issue。**固定 2 段**（これより深く掘らない。`epic/` 直下の md は迷子）。
  group 内の claim / 完了 / 保留は `epic/<name>/next/` `done/` `pending/` へ（global の `done/` へ出さない）。
  epic を新設するときは group 名と同じ番号の親 issue を同時に起票する

## 本文

冒頭のメタ行に `起票日: YYYY-MM-DD`（任意で `期限: YYYY-MM-DD`）。以降の骨子:

```markdown
# NNN (<type>): タイトル

起票日: YYYY-MM-DD

## 概要 / ## 詳細（再現手順・期待動作） / ## 対応方針 / ## 関連ファイル / ## 進捗
```

- **commit のたびに本文へ進捗を追記する**: 受け入れ条件のチェックボックス、各項目の状態と対応 commit
  （hash でなく subject）、結果の実測値、残タスク（未着手 / スコープ外 / 未検証を分ける）。chat の報告は流れる
- done へ移す commit では、その番号を参照している open issue にも「NNN で解消 / 継続」を 1 行足す
- 取りこぼしは Stop hook（`issue-progress-check.sh`）が差し戻す。ただし hook が見るのは構造までで、本文の正しさは書く側の責任
- **issue の記述を鵜呑みにしない**。着手前に実コードと git 履歴で検証する。特に「〜は存在しない」「呼び出しは 0 件」
  のような不在の主張は数え直し、結果を本文へ書き戻す
- 新規作成・大幅改訂は commit 前に反証レビューへ通す（`~/.claude/rules/issue-creation-codex-review.md`）
- `./tmp` に出した検証レポートの結論・全数勘定・却下理由は issue へ移すまでが 1 セット

## `期限:`

- 書式は**行頭 `期限:` + 半角コロン + `YYYY-MM-DD`**。🚨 箇条書き（`- 期限:`）・太字（`**期限: …**`）にすると
  hook が拾えず「期限なし」とも区別できないまま黙って埋もれる
- **`human` は必須**、他は任意。期限は「読んで確認する期限」であって「直す期限」ではない
- 未完了と期限切れは SessionStart hook（`human-tasks-due.sh`）が注入する。**期限切れが出たらセッション冒頭で一言伝える**

## `human` — 人にやってほしいことは chat に流さず issue に起こす

- 動作確認・目視レビュー・外部サービスの操作・判断待ちを `NNN-human-<何をしてほしいか>.md` で起票する
- **起票する前に「機械で測れないか」を一度問い、人が要ると判断した理由を本文に書く**（過大申告されやすい）
- 確認が済んだら `done/` へ移す（位置が既読の出典）
- hook の走査対象は `issues/` 直下・`pending/`・`next/`・`epic/*/`・`epic/*/next/`・`epic/*/pending/` だけ。
  これ以外のサブディレクトリに置くと黙って対象外になる

## `retro` — セッションの振り返り

実質的な作業をやり切ったら `NNN-retro-<slug>-YYYY-MM-DD.md` を自発的に起票する（日付サフィックス必須。
hook が経過日数をここから取る）。typo・数行の chore・調査だけのセッションは対象外。

- 中身は「どこで踏んだか / 何が回りくどかったか / 次に効きそうな改善」。うまくいった話は書かない
- **提案にするのは、抽象度が高く他の作業にも転用できる気づきだけ**。問うのは「別の repo・別の機能・
  別の種類の作業でも同じ形で効くか」。その issue・そのコード・その道具でしか起きない局所的な改善案は
  汎用性がなく価値が低いので、切り出し先を提案しない（その場で直したか、直さないかを 1 行書くだけ）。
  局所的な出来事から書き始めてよいが、提案は「どういう状況で・何をすべきか」の一般形に引き上げて書く
  （引き上げられないなら局所案として扱う）
- **提案する項目には切り出し先を添える**（新規 issue / `_claude/rules/` / 却下）。実行はユーザーの判断を待つ
- 🚨 切り出し先は**既存ルールへの追記**を既定にする。新規ルールは発動点が既存のどれとも違うと言えるときだけ
  （rules は毎セッション全文読まれ、流入の大半が retro 経由。2026-07-01 の 13 本 626 行 → 2026-09-03 に
  37 本 2480 行。整理で削れるのは 1 回百数十行で流入に負けるので、入口で絞る）。
  新規で立てるときは「なぜ既存へ追記できないか（発動点の違い）」を 1 行書く
- 却下した項目は消さずに「却下: 理由」を 1 行残す（次の retro で再生産されないように）
- **done は本文の残課題が空になったとき**（全項目が issue 化・rule 化・却下で決着）。実装の有無では判定しない
- 未決着の retro は SessionStart hook（`retro-open.sh`）が注入する。**古いものが溜まっていたら冒頭で一言伝える**
