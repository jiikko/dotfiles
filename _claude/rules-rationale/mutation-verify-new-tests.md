# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/mutation-verify-new-tests.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (起源: obaket issue 454、2026-08-03)

1 つの修正に対して 4 ラウンドのセルフレビューを回したところ、**毎回「直前ラウンドで
追加したテスト」が、そのラウンドの中心主張を何も守っていなかった**。いずれもテストは
green で実装も動いていたため、レビューを通すまで気づけなかった。

| ラウンド | テストの形 | 変異させた結果 |
|---|---|---|
| 1 | `#expect` が **1 つも無い** (「crash しないこと」だけ) | `guard` を削除しても green |
| 2 | 母集団が **恒等的に一致**する状況しか作らない (window 1 枚だけ登録) | 母集団を割る変異でも green |
| 3 | production の出力を **同じ定数**と比較する自己言及 | 定数を書き換えても green |
| 4 | 検証対象の描画が closure 内にあり **どのテストからも実行されない** | 変異する価値すら無い (カバレッジ 0) |

形が毎回違うので「パターンを覚える」方向では潰れない。一方、**変異を 1 本実行して
red を見る手順は形に依存せず、上記 4 例すべてを検出できた**。

## ルール本文から移した実例

本文には規範だけを残し、その根拠になった実例をここへ移した。
🚨 **移送時に文頭が切れて断片集になっていたので、2026-09-03 に各項の頭を復元した**
(どの規範の実例かが分かる形にした。実例の本文・日付・数値は当時のまま)。

### 手順 1.5「変異がビルドできたことを確認する」の実例

ビルドできなかった変異を green と読むと、**効いているテストを弱いと誤診して書き直す方向に走る**
(手順 0 の誤診と同じ構造で、向きが逆)。実例 (2026-08-26 obaket 544): `switch` の 1 case を
「元の未マップ fallthrough に戻す」変異が**非網羅 switch**になってビルドできず、`swift test` が
緑を返した。ビルド成否を確認して当て直したら正しく red になった。

### 手順 0「baseline が green であることを測る」の実例

baseline が red のまま変異を当てると、**red の増減が変異由来か元から壊れているせいか区別できない**。
実例 (2026-08-25): 指紋の統合直後に変異 5 本を当てて
「1/5 しか red にならない = テストが主張を守っていない」と読んだが、実際はそのとき別の理由
(テストが削除済みの関数名を呼んでいた) でテストが落ちていただけだった。baseline を直してから
当て直すと 5/5 が red になった。**数字だけ見て「テストが弱い」と誤診すると、要らないテストを
足す方向に走る**。

### 並行性のテストは 3 回連続 green を確認する、の実例

1 回の green は flaky をそのまま素通しする。これは「**baseline が安定して green か**」を見る。
実例 (2026-08-25): commit 時に green を確認した
並行性テストが、検収の再実行で 2 回連続 red だった (実測 1/3 で red)。

### 変異の red/green を件数 grep で判定しない、の実例

**runner の文言は個別 CLI の仕様なので、判定スクリプト側のコメントを正本にし、このルールには転記しない**
(実測 2026-08-25: ある runner ではサマリ行が個別失敗行を拾う pattern にも一致し、件数が混ざっていた)。

### 復元の作法 — untracked ファイルは `git checkout --` で戻せない、の実例

新規 (untracked) ファイルへ当てた変異は `cp` で 1 世代だけ控え、復元後にマーカー残骸ゼロを確認する
(実例 2026-08-21 obaket 536: 手動復元で凌いだが、復元し忘れれば変異がそのまま commit される)。

### 復元の作法 — 共有 working tree で変異を当てない、の実例

🚨 **共有 working tree で変異を当てない — 並行の相手は事前には見えない**
(2026-08-26 obaket 544 の実測):

実際に起きたこと: 自分が変異検証を回している最中に、**並行セッションも同じファイルに変異を
注入していた** (`throw ObaketError.transport("MUTANT-DIFFERENT-PAYLOAD")`)。開いた窓は 2 つ:

1. **commit を汚す窓**: 他人の変異が自分の pathspec commit に入る
   (`git status` では自分の変更と区別がつかない)
2. **観測を汚す窓**: 変異中のファイルを読んだレビュー・調査が、実在しないコードを前提にする
   (このとき read-only の red team が、その変異を実コードとして報告してきた)

### 変異は「production の機構を戻す」形にする、の起源

期待する文字列を埋めるだけの変異では、テストの検知力を何も証明できない。
起源 (2026-08-14, issue 050/061): 「一覧に進捗を出さない」を守るテストの変異検証で、期待文字列
`1/1` を直接埋めて red を見て「効いている」と判断した。本物の機構 (`ReadBody()` → `Progress()`)
を戻す変異を当て直すと **green のまま**だった (フィクスチャに checkbox が無く、進捗を出す実装に
戻しても `1/1` が生成されない)。同じ形を 1 セッションで 3 回踏んでいる — 行頭が空白か / `1/1` の
不在 / 確保の**回数** (削ったのは 1 本の大きなスライスで回数は動かない)。

### fake の「止まる回数」が変異側の呼び出し回数を想定しているか、の実例

回数に依存する止め方 (初回だけ block する fake) だと、変異検知が race 依存で非決定的になる
(実例 2026-08-25: barrier を足し戻す変異が、初回だけ block する fake のせいで最初すり抜けた)。

### 本番と同じ制約の下で観測しているか、の実例

制約を課さずに測ると「制約を超えたときの失敗」を観測できず、変異を当てても緑のまま通る。
実例 (2026-08-21): PreToolUse hook のテストが本番配線の `timeout: 10` を課しておらず、
「入力長で hook が timeout に殺されて deny が 1 byte も出ない = 安全機構が無効化される」
退行を 4 ケース書いても全部緑だった (timeout を課して初めて red になった)。
「遅い」を「素通り」として観測できる形にすること。

### 属性の存在だけを見ていないか、の実例

その属性が他の用途にも使われていると、**何も主張していない assert** になる。実例 (2026-08-23):
「使い残しはシアンで塗られる」を
`\033[36m` の存在で assert したが、シアンは「余裕」の状態色にも使われていた (変異を当てても
green のまま通って発覚)。**属性 + それが付く対象**まで見る。

### 計算ヘルパーの純関数テストだけで「配線済み」としない、の実例

呼び出し側を旧実装 (ヘルパーを呼ばない形) に戻す変異を当てて red を見るまでが 1 セット。
実例 (2026-08-24): `toastDrawBudget` の純関数テストはあったが、呼び出し側を元の式に戻す変異で
全テストが green のまま通った。

### 環境が変われば別の値になるコマンド出力を比較に使わない、の実例

**手元 1 platform の緑は「その platform では壊せなかった」でしかない**。実例 (2026-08-25):
`ps -o lstart=` の末尾パディングが macOS では入り Linux では
入らないため、指紋の正規化が末尾空白に依存していた。手元 (macOS) は緑のまま **CI (Linux)
だけが赤**になり、しかもそれはテストの問題ではなく **Linux で生存 owner の lock を奪う本番の
バグ**だった。→ **両方の形状をテスト内で作って**固定する (末尾パディングあり / なし)。

### 比較に使う正規表現の方言が両 platform で同じ意味になっているか、の実例

実測 2026-08-25: `grep -qE '\tfoo'` は BSD grep がタブとして解釈し、**GNU grep は
リテラル `t` として扱う** (= 行中の実タブにマッチしない)。POSIX ERE にタブの escape は無い。
手元だけ緑で CI だけ赤になり、しかも失敗メッセージが「無い」と言った直後にその行を表示する
という分かりにくい形で出る。**タブは変数に落として使う**。

ヘルパーへパターンを渡す形だと **`grep` の近くを grep しても見つからない**ので、掃くときは
「正規表現になる文字列」全部を見る (1 箇所見落として CI をもう 1 往復させた)。

### fake / stub が外部コマンドの exit code を模しているか、の実例

`err == nil` しか返さない fake は、
実際には exit 1 を返すコマンドの契約を再現していない。実例 (2026-08-24): claude CLI の
ログアウト判定が `err != nil` で早期 unknown に落ちる実装だったが、fake が成功しか返さないため
**一度も発火しない機能がテスト green で通った**
(関連: [`survey-receiver-guards-before-passing-new-values.md`](survey-receiver-guards-before-passing-new-values.md)
の「fake に受け側の reject 挙動を模させる」の外部コマンド版)。


## 2026-08-28: フィクスチャが production の初期状態と違い、窓を一度も踏んでいなかった (dotfiles issue 103)

lock の二重取得を防ぐレースのテストで、ハーネスが毎回「取り残しの lock を事前に作って」から
2 プロセスを走らせていた。この形状では**両者が奪取経路に入る**ので、奪取権 lock で直列化
されている側しか検査しない。production の呼び出し元 3 本はどれも **lock が存在しない状態から
始まる**ため、片方は素の `mkdir` で入り、奪取権 lock を持たないまま owner を記録する — そこが
原症状の窓だった。

「30 回試して 1 度も二重取得しない」を「窓が閉じた」と読んだが、実際は**ハーネスが窓を作れて
いなかった**。素の窓は実測 4.6ms しかなく、production 形状でも二重取得は 2/30 でしか出ない。
`tt_proc_starttime` を 0.4 秒遅らせて窓を広げたら、**ガード無し 15/15 / 有り 0/15** の決定論的な
A-B が取れた。

## 2026-08-28: A-B のケース間で `ZDOTDIR` を使い回して誤診しかけた (dotfiles issue 133)

`_zshrc` が stdout を汚す問題を直したあと、修正前後を A-B したら**両方とも「汚染あり」**という
矛盾した結果が出た。原因はケース間で `$ZDOTDIR` を共有していたこと。ケースごとに新規
ディレクトリを作って測り直したら、修正後 stdout 0 行 / 変異版 2 行と決定的になった。

危なかったのは、**最初の 1 回だけ測っていたら「修正が効いていない」と誤診して、効いている
修正を作り替えていた**こと。矛盾に気づけたのは、その前に単発で測った結果と食い違ったから。

## 2026-08-29: 正規表現の方言チェックが「macOS 専用化」で他 repo 向けに退いた経緯

本文の「比較に使う正規表現の方言」の項は、もともと dotfiles が Linux CI を持っていた時期に
書かれた。実測 2026-08-25 の内容は次のとおり:

- `grep -qE '\tfoo'` は **BSD grep (macOS) がタブとして解釈**し、**GNU grep (Linux CI) は
  `stray \ before t` と警告してリテラル `t` として扱う** (= 行中の実タブにマッチしない)
- POSIX ERE にタブの escape は無い。`\s` は両方が受ける (実測)

dotfiles は **2026-08-28 に macOS 専用**になり (issue 133。CI も全 workflow が macOS runner)、
GNU grep を被せて回す `make test-gnu` と `scripts/check_platform_dialect.sh` は
**「正しい macOS の書き方を弾く」側に回ったので撤去された**。本文の項は
**複数 platform を対象にする repo では引き続き効く**ため規範としては残し、経緯だけここへ移した。

## 2026-09-01 obaket 688 C5 — 変異が「新テストより手前」で落ちた

「永続化されない」退行を作るつもりで `UserDefaults` への書き込みを消したが、その repository は
毎回読み直す実装だったため、**relaunch を検証する新テストに到達する前**に「作成直後の行表示」で
落ちた。red は出たが、**新テストの検知力は何も証明できていなかった**。

当て直しは `load()` にプロセス内キャッシュを差し込み、「プロセス内では save→reload→delete が
全部成立するが永続化されない」形 (= issue 657 変異 2 が想定していた形) を正確に再現。
結果、**relaunch の復元検証だけが red** になり、検知力が確定した。

教訓: 変異の設計は「どんな退行か」だけでなく「**その退行で最初に落ちる assert はどれか**」まで
予測する。予測が新テストでないなら、その変異では検証できない。

## 2026-09-02 dotfiles issue 160 — 当てたつもりの変異と違う変異が入っていた (手順 1.6 の起源)

`perl -0pi -e "s/.../.../"` を**二重引用符**で書いたため、置換側の `$ROOT` / `$link` がシェルに
展開されて空文字になった。「-ef 不一致を見ない」のつもりが「常に drift 扱い」に、
「workflows の *.js フィルタを外す」のつもりが「workflows のパスを壊す」になっていた。どちらも red は
出たので気づかず、期待件数 (8 件のはずが 6 件) の不整合で発覚した。**別の変異でも red は出る**ので、
red は「意図した変異を検知した」の証拠にならない。diff を読んで初めて分かる。

同じセッションで、敵対レビュー (2 周目) は変異 8 本を全部 red にした後に P1 を 2 件出した
(setup.sh の回帰 / `ln -sfn` の並行レース)。「変異は本ルールの代わりにならない」の実測 6 回目。

## 「同じ判定を 2 箇所で別実装」の実例 (2026-09-02, dotfiles doctor / retro 164 項目 5)

glogx の doctor は、同じ `Report` から CLI (`disk.Format` / `svc.Format`) と TUI
(`diskSection` / `svcSection`) が**それぞれ別実装で**結論を描く形になっていた。2 回とも同じ壊れ方をした。

1. **「診断できず」の表示に UI 側だけテストが 0 本**だった (敵対レビュー P1)。CLI 側には
   テストがあるので「この判定は守られている」と読んでいたが、UI の分岐は全部消しても全 green で、
   brew の `Unavailable` を削ると「警告 0 件」に化けた
2. **svc の注記が CLI にしか無かった** (issue 179)。`AppleLikeOut` (`com.apple.` を名乗る登録が
   管理領域の外にある = malware の常套手段) と `BrewOrphan` が UI とコピー文に無く、
   逆に「起動状態は不明 (system ドメイン)」は UI にしかなかった。**欠落が両方向に出ていた**

2 の直し方は「UI に 2 行足す」ではなく `svc.Annotations` へ文言を一本化すること。
一本化してから、注記 4 種を網羅した fixture を CLI / UI / コピー文の 3 経路へ流す parity テストを
書き、各経路を修正前に戻す変異 3 本で red を確認した。

教訓は 2 つ。**テストがある側の存在は、無い側の証拠にならない**。そして
**parity テストは二重管理を消してから書く方が安い** (消さないと、テストが二重管理を固定してしまう)。

## fixture の置き場所で変異が素通りした実例 (2026-09-03, dotfiles issue 189 / 203)

「別サーバの予約を一覧・取消・失効件数に混ぜない」ことを固定したテストで、fixture
(`foreign.job`) を**分離後の dir** (`$STATE_ROOT/%tmp%tmux-501%othersock/`) にだけ置いていた。
退行 = 「共有 root を見る」実装は、そもそもその dir を覗かないので fixture が見えない。
敵対的レビューが変異を当てて「2 つの ✓ とも緑で通過」を実験で示した。

塞いだ形: **旧共有 dir (root 直下) にも fixture を置く**。そこは「移さないと決めた置き場」で、
退行したら必ず読まれる場所なので観測点になる。

同じセッションの同型 2 件:

- 「同じ socket に立ち直ったサーバの前任 job を失効させる」テストで、前任 job の `.pid` に
  テストシェル自身の pid を書いた。それは sleeper ではないので**通常の stale 掃除が先に消し**、
  前任判定を外す変異を当てても緑だった → 本物の sleeper を起こしてから job の 5 行目
  (サーバ pid) だけ書き換える形に直した
- 「複数予約なら最早の時刻を出す」テストで、`*.job` の glob 順で早い方が**最後**に来る
  fixture を作っていた。「最後に見た job を採る」変異でも緑 → id の並びを入れ替えて 2 回見る形へ

出典: `issues/done/189-*.md` / `issues/done/208-retro-*-2026-09-03.md` 項目 3。

## 走査・突合系テストの射程 (2026-09-03、dotfiles)

glogx の `TestDiskVerifyCommandsIDsExistInCatalog` は `doctor_view.go` の
`diskVerifyCommands` を走査し、case のカタログ ID が実在するかを `disk.CatalogHasID` で突き合わせる。
抽出は `case "([a-z0-9-]+)"` で、**`case` 直後の 1 個目のリテラルにしか当たらない**。
`case "a", "b":` の 2 個目以降は素通りするので、**11 ID のうち 7 件しか見ていなかった**
(未突合: `brew-cleanup-residue` / `xctest-spindump` / `launchd-tmp` / `swiftui-drag-cache`)。
canary も `len(ids) < 5` で、7 → 5 まで壊れても落ちない。

監査でこの分岐を「ID リネームで裏取りが黙って消える」と指摘したとき、**テストの存在を根拠に
却下**してしまった (抽出が何件を見ているかは数えなかった)。反証レビューが実測で崩した。
直した形は「case 行の全リテラルを拾う + canary を 10 へ」で、grouped case の 2 個目に
存在しない ID を混ぜる変異で red を確認 (`go vet` は通るのでビルド不能の偽陰性ではない)。
出典: `issues/226-retro-glogx-audit-2026-09-03.md` 項目 1 / commit `36237473`。
