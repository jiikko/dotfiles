# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/mutation-verify-new-tests.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (起源: obaket issue 454、2026-08-03)

1 つの修正に対して 4 ラウンドのセルフレビューを回したところ、**毎回「直前ラウンドで
追加したテスト」が、そのラウンドの中心主張を何も守っていなかった**。いずれもテストは
green で実装も動いていたため、レビューを通すまで気づけなかった。

| ラウンド | テストの形 | 変異させた結果 |
|---|---|---|
| 1 | `#expect` が **1 つも無い** (「crash しないこと」だけ) | `guard` を削除しても green |
| 2 | 母集団が **恒等的に一致**する状況しか作らない (window 1 枚だけ登録) | 母集団を割る変異でも green |
| 3 | production の出力を **同じ定数**と比較する自己言及 | 定数を書き換えても green |
| 4 | 検証対象の描画が closure 内にあり **どのテストからも実行されない** | 変異する価値すら無い (カバレッジ 0) |

形が毎回違うので「パターンを覚える」方向では潰れない。一方、**変異を 1 本実行して
red を見る手順は形に依存せず、上記 4 例すべてを検出できた**。

## 2026-08-28: フィクスチャが production の初期状態と違い、窓を一度も踏んでいなかった (dotfiles issue 103)

lock の二重取得を防ぐレースのテストで、ハーネスが毎回「取り残しの lock を事前に作って」から
2 プロセスを走らせていた。この形状では**両者が奪取経路に入る**ので、奪取権 lock で直列化
されている側しか検査しない。production の呼び出し元 3 本はどれも **lock が存在しない状態から
始まる**ため、片方は素の `mkdir` で入り、奪取権 lock を持たないまま owner を記録する — そこが
原症状の窓だった。

「30 回試して 1 度も二重取得しない」を「窓が閉じた」と読んだが、実際は**ハーネスが窓を作れて
いなかった**。素の窓は実測 4.6ms しかなく、production 形状でも二重取得は 2/30 でしか出ない。
`tt_proc_starttime` を 0.4 秒遅らせて窓を広げたら、**ガード無し 15/15 / 有り 0/15** の決定論的な
A-B が取れた。

## 2026-08-28: A-B のケース間で `ZDOTDIR` を使い回して誤診しかけた (dotfiles issue 133)

`_zshrc` が stdout を汚す問題を直したあと、修正前後を A-B したら**両方とも「汚染あり」**という
矛盾した結果が出た。原因はケース間で `$ZDOTDIR` を共有していたこと。ケースごとに新規
ディレクトリを作って測り直したら、修正後 stdout 0 行 / 変異版 2 行と決定的になった。

危なかったのは、**最初の 1 回だけ測っていたら「修正が効いていない」と誤診して、効いている
修正を作り替えていた**こと。矛盾に気づけたのは、その前に単発で測った結果と食い違ったから。

## 2026-08-29: 正規表現の方言チェックが「macOS 専用化」で他 repo 向けに退いた経緯

本文の「比較に使う正規表現の方言」の項は、もともと dotfiles が Linux CI を持っていた時期に
書かれた。実測 2026-08-25 の内容は次のとおり:

- `grep -qE '\tfoo'` は **BSD grep (macOS) がタブとして解釈**し、**GNU grep (Linux CI) は
  `stray \ before t` と警告してリテラル `t` として扱う** (= 行中の実タブにマッチしない)
- POSIX ERE にタブの escape は無い。`\s` は両方が受ける (実測)

dotfiles は **2026-08-28 に macOS 専用**になり (issue 133。CI も全 workflow が macOS runner)、
GNU grep を被せて回す `make test-gnu` と `scripts/check_platform_dialect.sh` は
**「正しい macOS の書き方を弾く」側に回ったので撤去された**。本文の項は
**複数 platform を対象にする repo では引き続き効く**ため規範としては残し、経緯だけここへ移した。

## 2026-09-01 obaket 688 C5 — 変異が「新テストより手前」で落ちた

「永続化されない」退行を作るつもりで `UserDefaults` への書き込みを消したが、その repository は
毎回読み直す実装だったため、**relaunch を検証する新テストに到達する前**に「作成直後の行表示」で
落ちた。red は出たが、**新テストの検知力は何も証明できていなかった**。

当て直しは `load()` にプロセス内キャッシュを差し込み、「プロセス内では save→reload→delete が
全部成立するが永続化されない」形 (= issue 657 変異 2 が想定していた形) を正確に再現。
結果、**relaunch の復元検証だけが red** になり、検知力が確定した。

教訓: 変異の設計は「どんな退行か」だけでなく「**その退行で最初に落ちる assert はどれか**」まで
予測する。予測が新テストでないなら、その変異では検証できない。

## 2026-09-02 dotfiles issue 160 — 当てたつもりの変異と違う変異が入っていた (手順 1.6 の起源)

`perl -0pi -e "s/.../.../"` を**二重引用符**で書いたため、置換側の `$ROOT` / `$link` がシェルに
展開されて空文字になった。「-ef 不一致を見ない」のつもりが「常に drift 扱い」に、
「workflows の *.js フィルタを外す」のつもりが「workflows のパスを壊す」になっていた。どちらも red は
出たので気づかず、期待件数 (8 件のはずが 6 件) の不整合で発覚した。**別の変異でも red は出る**ので、
red は「意図した変異を検知した」の証拠にならない。diff を読んで初めて分かる。

同じセッションで、敵対レビュー (2 周目) は変異 8 本を全部 red にした後に P1 を 2 件出した
(setup.sh の回帰 / `ln -sfn` の並行レース)。「変異は本ルールの代わりにならない」の実測 6 回目。
