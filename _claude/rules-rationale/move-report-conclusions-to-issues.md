# 検証レポートを `./tmp` に出したら、結論と却下理由を issue へ移すまでが 1 セット — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/move-report-conclusions-to-issues.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (起源: 2026-08-21 の実例)

その日 ad-hoc に組んだ Workflow が大きな検証レポートを 3 本出した。

| レポート | 中身 |
|---|---|
| `./tmp/audit-triage.md` | 監査 3 本 = **72 指摘の裏取り + 敵対的反証** (39 エージェント)。全数勘定・却下理由・着手順 |
| `./tmp/audit-refute2.md` | 未反証 medium 9 件の反証 (生存 5 / 却下 4、崩れた理由つき) |
| `./tmp/collab-review.md` | 協業 17 commit の破壊チェック (5 観点 + 敵対攻撃) |

3 本とも `tmp/` にあるため commit されない。気づいて手作業で要点を issue へ移した
(`7a36b55` の「反証・対応の結果」節 / `076` / `077`) が、**気づかなければ 72 指摘の verdict と
却下理由が丸ごと失われていた**。

構造的な原因は不注意ではなく規約の噛み合わせ:

1. `~/.claude/CLAUDE.md`「一時ファイルの配置」が `/tmp` 禁止・`./tmp` を使うと定めている
   (これ自体は正しい規約)。結果、成果物は自然と gitignore された場所に落ちる
2. **穴があるのは「skill を使わず自分で組んだ検証パイプライン」の側**。`audit` skill は課題を
   `issues/` へ書き出す作りになっているので、skill 経由なら構造的に守られている

## 追加節「done へ送るときは現状を実測する」の起源 (2026-09-01, dotfiles issue 075)

`075-human-verify-tmux-render-jitter.md` (tmux popup 表示中に背景の文字がブレる) を
ユーザー判断で done へ送るとき、決着節に「現状 `status-interval 0`」「再現には 1 へ戻す
必要がある」と書いて commit した (`44c95fc`)。

実測すると `_tmux.conf:73` も稼働サーバも **`status-interval 1`** で、前提が逆だった
(`ed7bfa7` で訂正)。`status-interval 0` は調査中の一時的な set で、conf には入っていない。

読み違えの原因は、issue 本文の**仮定法の調査メモ**:

> `status-interval 0` でブレが消えたのなら、この線が濃い。

これを「今 0 になっている」と読んだ。1 コマンド (`tmux show -g status-interval`) で測れる
値だったが、閉じる作業を「文章を書くだけ」と見なして測らなかった。

実害は「訂正しなければ、再開の trigger が実行不能な手順として残る」こと (「1 に戻して再現を
見る」= 既に 1 なので何もできない)。しかも done 配下なので、次に読まれるのは再発したとき =
**誤りが最も高くつく瞬間に発見される**。

訂正のついでに分かったのは、**現在の稼働状態がそのまま issue の言う実験条件になっていた**
こと (毎秒更新は動いていて、`terminal-features` の膨張だけが `5f12aea` で直っている)。
測っていれば、閉じる時点で「原因は terminal-features だった可能性が高い」と一段進んだ結論を
書けた。実測は正しさを守るだけでなく、結論を進める。

起源の記録: `issues/done/154-retro-glogx-viewer-crossnav-2026-09-01.md` の項目 3。
