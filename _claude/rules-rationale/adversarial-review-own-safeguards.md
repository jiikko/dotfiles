# 自分で作った「安全機構」は自己レビューで閉じない — 敵対的レビューを最終ゲートにする — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/adversarial-review-own-safeguards.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ自己レビューでは足りないのか (2026-08-03 obaket の実測)

「テストが実ユーザーのデータを汚す」問題に対策 (後始末ヘルパー + 残骸検査スクリプト) を
入れ、自己レビューで 5 件直して「塞いだ」と報告した。その後 red team 3 観点に通したら、
**対策自体に自己レビューで 1 件も見つけられなかった欠陥**が出た:

- **検査スクリプトが、対象環境ではテストを 1 本も走らせずに `make test` を落とす**
  (grep 無マッチ + `pipefail`)。私の Mac では絶対に再現しない条件だった
- **検査が保存先の 1 系統しか見ていなかった** (E2E scope の 6011 ディレクトリ / 750 MB が野放し)
- **後始末ヘルパーが実ユーザーのデータを消しうる**経路 (掃除に形状ガードが無い)
- テスト側で直したのと**同じバグが production にもあった** (`SecItemDelete` を 1 回しか呼ばない
  → profile 削除で credential が Keychain に残留)

構造的な理由は 3 つ:

1. **方向が逆**。自己レビューは「意図どおり動くか」を確かめる。red team は「壊す手順を探す」。
   前者は**自分が置いた前提そのものを検証対象にしない**
2. **環境を変えない**。自分は「今の自分のマシンの状態」でしか試さない。空の環境 /
   コマンド失敗 / 権限なし / 並行実行は、意識的に作らないと絶対に踏まない
3. **書いた本人はコードを読むと意図が再生される**。他人は書いてある文字しか読まない

## 実測 3 回目: 変異を全部 red にしても、敵対レビューは想定の外側を出す（2026-09-01, dotfiles glogx）

glogx の git log 自動追従（`5bd6715`）で、commit 前に次を全部通していた:

- 新規テスト 13 本に対して変異 11 本、すべて red を確認
- 自己レビューで fd 漏れ（`cancelAll` が watcher を閉じていない）を発見して修正
- 異常系（repo の外 / コミット 0 件 / watcher を作れない / git 失敗）を実装側で分岐済み

その後に観点を分けた敵対レビュー 3 体（壊す / 素通り / 回帰）を通したところ、**再現手順つきの
P1 / P2 が 5 件**出た。いずれも「自分が想定した不変条件」の外側にあった:

1. **TOCTOU**: 見送り判定（反映してはいけない状態か）を「測定を開始する前」にしか見ていない。
   測定（git fork）の最中にポップアップを開かれると、開いている内容のキャッシュを消す
2. **自己 reload との競合**: 自分の pull / push の直前に測った指紋が届くと、新しいコミット列と
   必ず不一致になり、無駄な再読込・トースト・API 再取得が 2 回走る
3. **`ctrl+d` の非対称**: 「先頭を見ているか」を cursor だけで判定していたが、`ctrl+d` は
   カーソルを動かさず offset だけ動かすので、読んでいた位置が先頭へ飛ぶ
4. **錨の選び方**: カーソルのコミットを錨にすると、`ctrl+d` 中のカーソルは先頭コミット
   = `--amend` で最も消えやすい SHA を指す
5. **センチネルの衝突**: コミット 0 件の指紋 `""` が「基準なし」を表す `""` と区別できない

変異検証が捕まえられなかった理由ははっきりしている。**変異は「自分が書いた不変条件を壊す」
方向にしか当てられない**ので、1・2 のような「複数の非同期イベントの順序」や 3・4 のような
「自分が気づいていない状態の組み合わせ」は、そもそも変異の候補として思いつかない。

なお同じレビューで、**変異検証が捕まえた側**もある: 修正後に足したテスト 2 本が
「pull の演出中は見送る」に助けられて green になっており、狙った不変条件を一切見ていなかった
（変異を当てて GREEN のままだったので気づけた）。**両方通す**の実例として対になっている。


## 実測 4 回目: 単純な入力検証ゲートでも、想定の外側は残る（2026-09-01, dotfiles codex-fanout, issue 150）

codex-fanout の manifest に行単位 timeout 列を足した変更 (`a181655`)。commit 前に
変異 3 本（行 timeout 無視 / CRLF 剥がし除去 / 検証除去）をすべて red にしていたが、
観点を分けた敵対レビュー 2 体（壊す / 素通り）が**再現手順つきの P1 を 2 件**出した:

1. **ロケール照合の素通り**: `*[!0-9]*` の範囲式は `ja_JP.UTF-8`（この開発機の既定）の
   照合順で全角数字（`３`）を通す。通過後は `[ -ge ]` が integer expected で常に偽を返し、
   **watchdog が die もせず hang を永久に待つ**（エラーは per-run の .log にしか出ない）

   評価エラー）。文字種検査は「整数比較できる」を保証しない

過去 3 回が並行・時間差・状態の組み合わせだったのに対し、今回は**たった 1 つの case 文の
入力検証**でも「自分が想定した文字集合の外側」（ロケール・桁数）が残ることを示した。
自分で書いた非数値テスト（`abc`）は、ガードが主張する防御範囲の最弱部を踏んでいなかった。
切り出し先: [`shell-numeric-gate-explicit-digits.md`](../rules/shell-numeric-gate-explicit-digits.md)。

## 0-B の起源: 走査が既に持っている答えを、glob の突合で作り直した (2026-09-03, dotfiles 148)

`src/doctor/disk` (macOS のディスク棚卸し) に削除経路を新設したセッション。

**1 周目の敵対レビュー**が「細工した `Result` を渡せば任意パスを消せる」と実測つきで指摘した
(`doctor-snapshot.json` は一般ユーザー権限で書けるので、そこから復元した行が削除対象になりうる)。
そこで「削除対象は、そのエントリの `Paths` を展開し直した集合に属していること」を要求する
突合 (`entryPathSet`) を足した。コメントにはこう書いた:

> guard は絞り込むだけで新しいパスを増やさないので、rm / trash の対象はこの集合に必ず属する

集合論としては正しいが、**「属する」は「消してよい」ではない**。そのエントリの候補を決めているのは
走査 (`Scan`) の guard —「Chrome が起動中か」「mtime が最終起動より古いか」「そのアプリは
まだ入っているか」— であって、glob はその入力にすぎない。

**2 周目の敵対レビュー**が、この突合を P1 として実測で崩した:

- Chrome 起動中に、live な `$TMPDIR/.com.google.Chrome.*` を削除できた
- 走査後に mtime が更新された対象を、警告なしの `deleted` で消せた
- `orphan-container` の glob 経由で、現役アプリのコンテナをゴミ箱へ移せた

**直し方は「近似をやめて本物を通す」だった**。削除の直前に 1 エントリぶん `Scan` をやり直し、
その結果だけを対象にする。結果:

- `entryPathSet` は丸ごと消えた (集合の作り方が走査側と削除側で 2 実装だったのが 1 つに)
- サイズと `(dev, ino)` も**実測値**になり、同じ変更で解放量の穴も閉じた
  (それまで `BeforeSize` も「触った Item の合計」も呼び出し元の申告値で、レビューは
  4 KiB のディレクトリを消して 999 GiB の解放を報告させた)
- 不変条件が 1 つ減った

**なぜ気づけなかったか** (ここが 0-B を足した理由):
`mutation-verify-new-tests.md` は「同じ判定・同じ結論を 2 箇所で別実装していないか」を
既に書いていて、**このセッションでその節を読んでもいた**。それでも自分の変更がその形だとは
気づけなかった。あの項は「よくある『守っていないテスト』の形」の中にあり、**発動点が
「テストを書くとき」**になっている。実装側で 2 実装を作る瞬間には効かない。

規範を足したのではなく、**同じ規範の発動点を 1 つ増やした**のが 0-B。

**コストの扱い**: 本物を通すと重いエントリで数秒かかる (DerivedData の走査は 5.7 秒の実測が
あるので、削除の前後で 2 回走ると 10 秒超)。それでも近似を選ばなかったのは、遅さは
進捗表示で扱える問題で、誤削除は扱えないため。ルール本文の「遅さは理由にならない」はこの判断。

**出典**: issue 209 項目 1 /
commit `4c824ff2` (2 周目の反映) / `d2dfd70` (1 周目の突合を入れた commit)

## §1.5 の起源: 段数を宣言したが、変異が通ったのは 1 段だけだった (2026-09-03, dotfiles 148)

破壊的操作 (`os.RemoveAll` / `renameatx_np`) を本物で呼ぶテストのために、
①サンドボックス外は既定拒否 ②XDG を差し替え ③最終違反チェック の 3 段構えを作り、
ヘッダにもそう書いた。敵対レビューが段ごとに変異を当てたところ:

| 段 | 変異の結果 |
|---|---|
| ① 既定拒否 | 許可判定は red になる。ただし**登録の解除**側は守られていなかった |
| ② XDG の差し替え | **テストが 1 本も守っていない** |
| ③ 最終違反チェック | **テストが 1 本も守っていない** |

自己テスト 2 本が証明していたのは「①の許可判定が allow-all でも deny-all でもない」ことまで。
**段数は意図であって、守られている段数ではない**。全段を同時に外す変異ではどれか 1 つが落ちて
red になるため、この穴は「段ごとに外す」変異でしか見えない。

## 2026-09-04 dotfiles issue 251 — 先に書いた「検出しない形」が実装の射程と食い違った

§8 のとおり、gate (表示の無害化を通し忘れていないかを見る go/ast の検査) を書く**前に**
脅威モデルと「検出しない形」をヘッダと README に書いた。それでも敵対的レビューが
「**実装が実際に検出しない形と、書いてある形が一致していない**」と指摘した。

書いていなかった形:

- ポインタ (`*string`) / `map[string]string` / 匿名構造体 / 他 package の named string 型
  (`stringish` が `*ast.Ident` と `*ast.ArrayType` しか見ていなかった)
- 埋め込みフィールド (型だけ書く形。`fld.Names` が空なので 1 件も記録されない)
- **関門がコピーを無害化して親へ書き戻さない形** (`r.Items = kept` の一文だけを消す)。
  この関門で唯一「実際に起きた」退行がこの形だったのに、書いていなかった
- 双子の関門 (`doctor/svc`) が対象外であること

原因は単純で、**着手前に書けるのは「意図」まで**だから。「どの型の書き方を扱えないか」は
`stringish` を実装して初めて確定する。ヘッダの「検出しない形」は、読む人にとっては
**射程の宣言**として機能する (= 書いていない形は守られていると読む) ので、意図のまま残すと嘘になる。

対応は 2 通りあり、両方使った: ①扱えない型式を **fail-closed** にする (未知の型式は
「検査できない」として違反にする = 射程の外を減らす) ②残った形をヘッダと README に足す。

## 「機構を足すほど周回が増える」と「推論でなく観測へ」の起源 (dotfiles retro 387, 2026-09-16)

lockman の issue 383 (中身を読めない lock を fail-closed にする) で、敵対レビューが **4 周連続で
P1 を出した**。内訳:

| 周 | 指摘 | 由来 |
|---|---|---|
| 1 | 代償である「人が `break` する」導線が production のどの出口にも出ない | **足した機構** (案内) |
| 2 | 後始末が**名前**で消していて、`Break` が挟まると他人の生きた lock を消す | **足した機構** (後始末) |
| 3 | 案内が危険な助言 (一過性の窓でも「剥がせ」と出る) / 分類漏れで無音 | **足した機構** (案内・分類) |
| 4 | 3 周目の修正が片手落ち (2 箇所中 1 箇所) / 新しい案内先が空振り | **足した機構** |

**核 (fail-closed = 実質 2 行) は 1 周目で閉じており、2〜4 周目は全部「足した案内文と後始末」由来**
だった。機構を足すと、その機構に固有の failure mode が生まれ、その修正がまた新しい判定を足す。

### 推論 → 観測へ置き換えるまで周回は終わらない

同じ日の issue 377 (隔離 tmux サーバの後始末) では、生死の判定を

1. 「応答が無い = 死んだ」(推論) → P1
2. 「応答と rc の三値」(推論) → P1 (版ずれ・PATH 不在・fd 枯渇でも成立する)
3. 「**socket の持ち主が居るか**」(観測) → 変異が通らなくなった

と 3 版かけた。効いた問いは「**その判定の根拠は観測か、推論か**」だった。

### 案内が危険な行動になっていた実例

383 の案内は「保持者が居ないと分かっているなら `lockman break` で剥がす」だったが、同じ観測が
**健全な保持者の `Renew` が truncate している一瞬**からも出る (毎 Renew ごとに窓が開く)。
助言に従うと**生きた保持者を剥がして二重実行**。一過性と恒久は 1 回の観測では区別できないので、
区別しようとせず**破壊的操作を促すのをやめた**。その後 4 周目に「置き換えた案内先 (`status`) が
rc=1 / 出力空で空振り」と指摘され、`Inspect` がその状態を**状態として答える**ようにして閉じた。
