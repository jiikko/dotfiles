# 書き込み権限のエージェントを 2 体以上並行させるなら、必ず worktree を分ける — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/parallel-write-agents-need-worktree-isolation.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ（起源: ThumbnailThumb #435, 2026-08-11）

構造化ログ移行の最終盤で、コード修正とドキュメント修正の codex を**同じ working tree で並行実行**した。
担当は「`.swift` / `.swiftlint.yml`」と「`.md`」で重ならない想定だった。

結果的に事故は起きなかったが、それは**運が良かっただけ**:

- 両者とも ThumbnailThumb issue 435 に手が届く位置にいた（ドキュメント側の担当、コード側も
  「lint ルールの説明を issue に書く」余地があった）
- ドキュメント側が終了報告で「作業中に別の `.swift` / `.swiftlint.yml` 変更が並行して出現した。
  これらには触れず保持している」と**明示的に述べていた**ため、後から上書きが無かったと確認できた。
  この報告が無ければ、片方の編集が消えたかどうかを知る手段がなかった

同一 tree の並行書き込みで起きうること:

- 後から書いた側が、先に書いた側の編集を含むファイルを読まずに上書きする（**サイレントに消える**）
- 片方が `xcodegen generate` などで生成物を再生成し、もう片方の未反映の変更を巻き込む
- 一方が build/test を走らせている最中に他方がソースを書き換え、**どちらの状態を検証したのか
  分からない green** が出る（最も危険。検証の意味が消える）

## read-only レビュー中に自分が書き換えると何が起きるか（2026-09-01, dotfiles glogx 自動追従）

glogx の git log 自動追従 (`5bd6715`) で、実装が一通り終わった時点で敵対的レビューを 3 体
（壊す / 素通り / 回帰）read-only で起動した。走行中に自分で `cancelAll` の fd 漏れに気づき、
**レビュワーが読んでいる最中に** `gitlog_watch.go` / `tui.go` を修正した。さらに先に返ってきた
2 体の指摘を、3 体目の走行中に適用した。

結果:

- 3 体目（壊す観点）の報告は冒頭が「**レビュー中に実装が動いた**」の断り書きになり、最初の走査で
  再現させた P1 3 件が「報告時点で既に修正済み」だった
- レビュワーは対象を別ディレクトリへ複製し、**現行版で再検証し直して**から報告した。
  つまり同じ検証を 2 回やらせた
- 報告の読み手（main agent）も、指摘ごとに「これは修正前の話か、今も残っているか」を
  照合する必要が出た

書き込み側が「良かれと思って早く直す」ほど損が大きくなる形なので、規範は
**「レビュー中はそのファイルを触らない」**まで広げるのが正しい。変異検証だけを禁じても、
通常の修正で同じことが起きる。

**代替**: レビュー結果を待つ間に手を動かしたいなら、修正は使い捨て worktree で当てて
（レビュー対象のツリーは固定したまま）、報告が届いてから統合する。

## 2026-09-04 dotfiles issue 242 — 着手前の一斉申告が、重複作業を着手前に止めた

`git worktree list` に 4 つの worktree があったが持ち主が分からなかったので、`ListAgents` で
見えた dotfiles 系 4 セッション**全部**に「触る予定のファイルと関数」を列挙して送った。結果:

- あるセッションが**別のセッターが既に push 済みの issue 240 / 241 を、これから実装しようと
  していた**ことが分かり、**着手前に止められた**（本人が origin と自分の差分を突き合わせた上で
  worktree ごと破棄した）
- 別のセッションが `src/doctor/**` に閉じてくれ、`src/glogx/**` を私が持つ分担が即決まった
- 「commit の author では持ち主を特定できない（全セッションが同じ author）」ことも共有された

**同じ日に commit の帰属推測が 4 回外れている**（私の 1 回を含む）。git state は「誰かが何かを
した痕跡」であって「誰が今それを持っているか」を答えない。`git log` の時刻も、
`git pull --rebase` が他人の commit を自分の commit の間に挟むので帰属に使えない
（`commit-with-pathspec.md` の「履歴操作の前に所有者を確認する」節が同じことを言っている）。

一斉に送るコストは 1 通の文面を使い回すだけで、**当たったときの得（重複実装の丸ごと回避）が
桁違いに大きい**。宛先を絞るために持ち主を推測するのは、この日の実測では 4 回中 4 回外れた。

## 実例: レビュワーが残した busy loop (2026-09-20 / dotfiles issue 385)

敵対的レビューを 2 周回したセッションで、1 周目のレビュワーが「負荷下でも flaky にならないか」を
確かめるために `for i in 1..8; do (while :; do :; done) & done` を **2 回**起こした。

- 本人は `kill $(jobs -p)` と `git worktree remove --force` を後始末として書いており、
  **worktree の削除は成功していた** (`git worktree list` に残骸なし)
- しかし `jobs -p` は非対話の `zsh -c` からは空で、親が先に終わったので **16 本すべてが PPID=1**
- 実測: 8 本 × ~79% (26 分) + 8 本 × ~100% (13 分)。**ユーザーが「zsh がたくさん起動している」と
  気づいて初めて発覚**した (こちらのセッションからは、レビュワーの完了報告が届いた時点で
  「後始末済み」に見えていた)

教訓は 2 つ:

1. **後始末の確認対象に「プロセス」を入れる**。ファイル (`git status`) だけ見ていると、
   「worktree は消えているのに焼き続けている」状態を観測できない
2. **負荷生成は親の終了で回収される形に限る**。busy loop は「起こすのは 1 行、回収は別の仕組み」
   という非対称があり、回収側が失敗しても**誰にも気づかれない** (エラーも出ない)
