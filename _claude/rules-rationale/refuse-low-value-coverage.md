# カバレッジ向上を要求されても「テスト困難 かつ 低価値」なら拒否する — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/refuse-low-value-coverage.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ 2 軸なのか

カバレッジは目的ではなく **回帰バグを捕まえられるか**の代理指標 (proxy)。数値だけを目標にすると、
proxy と目的が乖離する典型 (Goodhart) が起きる: 薄い委譲・getter・生成コードを覆う「mock が呼ばれた
ことしか assert しないテスト」が量産され、数値は上がるが回帰は 1 件も止まらない。

一方で「テストが困難」だけを理由に逃げると、**最も回帰で困る箇所** (状態機械・境界・並行) が
永久に無防備になる。だから容易性の 1 軸ではなく、容易性 × 価値の 2 軸で切る。拒否してよいのは
右下 (困難 × 低価値) のセルだけ、というのがルール本文のマトリクス。

## 2026-09-01 obaket (issue 692) — テスト削除の作法が決まった経緯

Settings の E2E を削除した際、ユーザーから次の指示があった:

> テスト名は E2E に限らず削除しない方が良い。削除したテストは issue にしてほしい。
> 削除するときは **e2e テストで検証していないので他の方法で検証してほしい**ことを issue に書いてほしい。

issue 692 では「元々検出できていなかった穴」と「削除で失ったもの」を**分けて**書いた。
混ぜると削除の責任範囲が過大にも過小にも見える (過大: 元から無かった保証まで失ったことにする /
過小: 削除で失った分を「元から穴だった」に紛れ込ませる)。

### テスト名は削除の理由にならない

同じ削除で `testSettingsShowsTabs` は名前どおり tabs を見ていなかった。しかし削除の理由は
「タブの同定が AX 上で成立しなかった」ことであって、名前の不一致ではない。名前が実態と
合っていないなら**名前を直す**のが正しい対応で、テストを消す根拠にはならない。

学び: 削除は「守るものを減らす」変更なので、失ったカバレッジと代替の検証案を issue に残すまでが
1 セット。切り出し先: 本ルール本文の「テストを削除するときは〜」節。
