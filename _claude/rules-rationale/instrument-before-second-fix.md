# 1 回目の修正仮説が外れたら、2 発目を打つ前に「観測を増やす」を選ぶ — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/instrument-before-second-fix.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (起源: obaket issue 227 Dropbox -1005, 2026-06-09)

`URLError -1005` の bug で、wire レベル (URLSession が実際に何を送り、サーバがなぜ接続を切ったか) が見えないまま app 層ログだけで推測 fix を 2 連続で外し、commit 4 本 (fix 2 + revert 2) と実機検証 2 周を無駄にした。1 回目が外れた時点で `CFNETWORK_DIAGNOSTICS=3` / `URLSessionTaskMetrics` / 成功経路との A-B プローブを仕込んでいれば最短で真因に寄れた。観測を仕込むコスト (数十分) の方が圧倒的に安い。

## ルール本文から移した実例

本文には規範だけを残し、その根拠になった実例をここへ移した（元の文脈のまま）。

実例 (obaket 582, 2026-08-25): アップロード完了トーストの「アプリ内で表示」が、**大文字を含む
ファイル名では 100% 失敗し、全部小文字なら成功する**バグだった (Dropbox は path を `path_lower`
由来で組むのに、呼び出し側がローカルのファイル名から要求 path を組み直していた = 表現不一致)。
症状が「たまに動く」ためタイミング仮説の修正が繰り返し入り、そのたびに再発していた。
決定打は実機ログ 1 行の**大文字**で、コードを読むより速かった。

実例 (obaket, 2026-08-23): CI の失敗を「パス解決が環境依存で壊れている」と読んで修正したが、
真因は「その実行環境に検査対象のソースが存在しない」で外した。**このとき失敗経路に環境変数の
dump を入れていたので、次の 1 往復で確定できた**。逆に言えば、確度の低い 1 回目の時点で
dump を入れていれば往復は 1 回で済んでいた。

実例 (obaket 617 M2, 2026-08-29): Swift runtime の `swift_task_dealloc` abort に対し、仮説 fix を 2 回
(Task.detached 化 / guard-let 化) 当てて 3/3 クラッシュのまま → 効かなかった修正を戻し、forge に観測データ
(crash report の frame・決定的な再現子) を手土産に escalate → probe A (stored async closure を短命 Task から
呼んで完了させると落ちる) で真因を確定。修正は protocol witness の sleeper + cancel しない単一 driver。
仮説 fix を 3 回目に進めていたら、同じ形 (`scheduleProgressFlush`) の 2 箇所目を見落としたまま
「たまに落ちる」に戻っていた。

## 「消える操作の前に観測」と「実プロセスの env」の起源 (dotfiles retro 342, 2026-08-31)

### kill する前に観測を採る

solargraph が CPU 60% で回っているのを見つけた時点で、原因究明より先に `pkill` した。
ログとソース読みで「spin ループ」までは正しく特定できたが、**その説明で観測値が全部
埋まっているかを確認しなかった**。

ユーザーの「sigdump とかして調べた?」で再現し直し、`sample` を取ったところ
**イテレーションごとに Progress の keep-alive スレッドがリークしていた** (45 秒で 34 本)。
最初のプロセスが RSS 585MB まで育っていたのはこれで説明が付く —
**spin ループだけでは 585MB は説明できないのに、説明できていないことに気づいていなかった**。

### 手元で再現しないなら実プロセスの env を読む

「rb ファイルで色が付かない」の調査で、headless nvim → 隔離 tmux の pty と 2 回
「私の環境では色が出る」を報告した。3 回目にユーザーが「今も出ない」と言って初めて
動いている実 nvim の `ps eww` を読み、`SUPPORT_TRUECOLOR` が env に無いと分かった
(親シェルが `~/.zshenv` への追記より **7 時間半前**に起動していた)。

🚨 **`.zshenv` には正しい行が書いてあった**。ファイルを読むだけでは永遠に分からない形だった。

同じセッションの前半、solargraph の調査では**最初に `ps eww` で子プロセスの env を読んで**
GEM_HOME 汚染を特定していた。**隣の問題に同じ手を適用しなかった** (issue 137 項目 2 と同型の再発)。

## 「動いているプロセスに直接聞く」と「headless は本番ではない」の起源 (dotfiles retro 368 / 378, 2026-09-12 / 09-15)

### 生きている nvim へ問い合わせる (368 項目 3)

「markdown の見出し色を変えたのに見た目が変わっていない」に対し、`_nviminit.lua` の grep・
headless の再現・`ps` の起動時刻まで見ても決着しなかった。決め手は動いている nvim の socket へ
直接問い合わせたこと:

```
sock=$TMPDIR/nvim.$USER/*/nvim.<pid>.0
nvim --headless --server "$sock" --remote-expr 'luaeval("...")'
```

「設定は入っている (H1fg=#fe8019 / pos=inline)」と「画面に出ている見出しは H3 が 4 つ」が
同時に取れ、原因が**設定ではなくスクロール位置**だと 1 手で確定した。

### headless / `-u` の nvim は「設定を読むが描画しない」(378 項目 1)

見た目を測るハーネスが 1 セッションで **4 通りの壊れ方**をし、**どれも「もっともらしい数字」を
返した**。

| 壊れ方 | 出た嘘 | 気づいた手段 |
|---|---|---|
| headless で `RenderMarkdown disable` が効かない (marks も conceallevel も変わらない) | 「toggle しても高さは変わらない」 | 出力に `conceallevel=3` と `marks=33` が両方の行に並んでいた |
| headless の `nvim_feedkeys("i")` で insert に入らない | 4 案すべて「ずれ +0 行」 | insert で marks=0 になるはずの版が 102 のままだった |
| BSD の `diff` に `--unchanged-group-format` が無い | 「画面 44 行中 44 行が変化」 | usage が stderr に出ていたが、stdout の数字だけ読めば通っていた |
| `nvim -u <別パスの init>` が描画を一切しない | 「案 B を当てると装飾が全部消える」 | **変更前の版で同じ手順を踏んだ** (canary) |

4 つ目が最も危なかった。適用直後のキャプチャが素の markdown だったので、**自分の変更が壊した
ように見えた**。`verify-execution-not-just-exit-code.md` の「隔離環境での *失敗* も本番の失敗では
ない」がそのまま当たっており、そこに書かれている「`nvim -l` はユーザー設定を読まない」の隣の形
(`-u` は読むが描画しない)。

### 機構を見つけたことと、それが主訴の原因であることは別 (378 項目 2)

`code.border = "hide"` (nvim 0.11 の既定が ``` の行を `conceal_lines` で消す) を見つけた時点で
これを主犯に据えかけた。実測すると最大 3 行で「ガバッと」には届かず、ユーザーに聞いたら
**insert モードに入った瞬間**で toggle ですらなかった。本文の「『何度直しても直らない』と
言われたら、まず非対称を特定する」を、**機構の説明を始める前に**当てる必要があった。

## 実例: view の使い回しと、効いていない再試行の合図 (obaket 859, 2026-09-19)

- 一覧 Table の選択が灰色 (first responder でない) になる不具合で、最初の仮説 (「true を true に代入しても変化にならない」) は
  実機ログで外れた。真因の 1 つは **SwiftUI がタブ切替で Table と監視用の NSView を使い回し、ViewModel だけ差し替える**ことで、
  前のタブで記録した状態が残って要求が出ていなかった。観測ログに probe のインスタンス識別子と
  「別の ViewModel に使い回された」ログを足した 5 回目の実機ログで初めて見えた
- 同じ機構に、行の投入を待つ再試行の合図を 2 つ (frame 変化の通知 / 50ms poll) 持たせていた。実機の成功は**全部 poll 経由**で、
  frame 通知は一度も発火していなかったが、それを確かめる前に frame 通知側の上限・テスト・変異検証・レビュー対応を
  3 周分積んでから削除した。成功ログに trigger 名 (`(poll)` / `(request)`) を出していたので、見れば 1 回目で分かった
