# 表示・レイアウトの意思決定は、本体へ入れる前にサンプルレンダラで回し切る — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/decide-layout-in-sample-renderer-first.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (起源: dotfiles statusline のカレンダー格子, 2026-08-23)

試作レンダラ (`tmp/pace_sample.sh`) を作るところまでは正しかったが、**途中から本体と
テストを直しながら仕様を詰めた**。結果、表示が**6 回**変わる間、そのたびにテストを
張り替えるコストを払った (2 行 → 1 行 / 日付 → 相対日 / 曜日併記 → 曜日削除 / 帯の中の色 …)。

構造的な理由: **本体に入れた瞬間、テストが「今の見た目」に張り付く**。以降は
「見た目を変える」が「見た目を変える + テストを張り替える」になり、変更コストが数倍になる。
しかも見た目はまだ決まっていないので、その支払いは**確定していない仕様に対して**発生する。

サンプルの中なら、表示が 6 回変わっても払うのは 6 回の描き直しだけで済む。

## 「見本は実物の分布で描く」の起源 (dotfiles retro 368 項目 1, 2026-09-12)

見本の `sample.md` は H1〜H6 が均等に出る作りだったが、実物 (`README.md`) は
**H1=3 / H2=5 / H3=12** で H3 が過半数だった。案 A は「変更を最小にする」つもりで H3 に
現状色 (緑 142) を据え置いたため、ユーザーの画面 (185..257 行) では **6 見出し中 4 つが
変更前と同一**になり、「見た目変わっていない」という報告になった。

見本は「レイアウトが崩れないか」は見られるが、**変更の可視性**は実物の分布でしか見えない。

## 「見本が本体の一部を再現していない」(dotfiles retro 378 項目 3, 2026-09-15)

3 案を実物 (`README.md` / `docs/README.md`) で出して 1 往復で決まった (memory の
「色/デザイン提案は視覚見本を添えると即決される」どおり)。ただし見本は `_nviminit.lua` の
ハイライト上書きループを読まないため、**採用後は見出しの文字色だけ残る**という差があり、
提示のたびに断り書きが要った。見本と本体で読む設定の集合が違うことは、見本を作る側からは
見えにくい (見本は「意図した層」だけを再現する)。
