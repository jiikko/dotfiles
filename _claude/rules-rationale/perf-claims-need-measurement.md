# 性能を主張するなら、実測値か「未実測である事実 + 実測の trigger」を残す — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/perf-claims-need-measurement.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ (obaket issue 544、2026-08-26)

種別 `perf` の issue で、主題は「preflight が 1 ファイルあたり stat を倍増させる」だった。
実装後に自分が書いた記述は:

- **効果を実測していない**こと (実 SMB 共有が要るため) に触れていなかった
- しかも**効果を過大に書いていた**。preflight を消したことだけ見て、
  **その後に走る canonical stat を数え忘れていた** — 実際は **2 回 → 1 回**であって
  **0 回にはならない**

敵対的な要件照合で指摘されるまで気づかなかった。
**perf の issue で「速くなったはず」を根拠なく書くのは、機能の issue で「動くはず」と書くのと同じ**。

## 母集合を混ぜて「実測」と書いた例 (2026-09-03、dotfiles)

`src/doctor` に lint 設定が無いことを指摘する issue で「production に 12 件」と書いたが、
12 は **production とテストを混ぜた数**だった (正しくは production 10 件 = exhaustive 4 +
未導入 linter 6、テスト込みで 18 件)。`golangci-lint` の出力を `uniq -c` で数えて合計だけを
転記し、母集合を書かなかったのが原因。設定ファイルのコメントにも同じ混同を commit している
(次の commit で production / テストに分けて訂正)。
数字そのものより、**「実測」の見出しの下に母集合の違う数を置いたこと**が問題だった。
出典: issue 226 項目 2 / issue 222。

同じ日にもう 1 件: `make test` の所要時間を個別 target の合計 (414 秒) で書き、見出しに「実測」と付けていた。
通しを測ると 433 秒で、差 19 秒は集約と起動のオーバーヘッド (ルール本文の「内訳の合計を全体の実測として書かない」の起源)。

## 2026-09-05 — 測った経路がユーザーの経路と違った (glogx 起動の律速調査)

glogx の tmux popup が「たまに突っかかる」の律速を探し、`glogx --no-pager -n 20` で初回 1.30s /
2 回目以降 0.04s を得て「初回 1.3s が律速」と報告した。しかし `--no-pager` (非 TTY) 経路には
`fetchStatic` (同期の `gh` GraphQL、ネットワーク) があり、popup (TTY) 経路では走らない。
1.3s のうち大半はそこで、popup の実コストは新バイナリの初回 exec (署名検証) の 230ms だった。
数字そのものは正しかったが**経路が違ったので内訳が違い**、ユーザーへ訂正が要った。
測りやすい経路 (パイプで時間が取れる) を選んだ時点で「実経路と同じ処理が走るか」を確かめていれば
避けられた。起源: retro 257 項目 2。

## 最初の計測の粒度 (retro 259, 2026-09-05)

make test の高速化で、最初にレーン単位 (test-lint / test-runtime / test-src) で 8 分回し、内訳が要ると
分かってテスト 1 本ずつの計測でさらに 6 分回した。最初から 1 本ずつ測っていれば 1 回で両方得られた
(レーン合計は per-test の合計から出せる。ただし通しの壁時計は別に測る)。

## 余裕・枯渇の時期も今のレートで言う (retro 501)

- 2026-09-26: 「前回は 83 日で溜まったので今夜すぐには落ちない」と午前に説明したが、17 時間後に測ると 1 時間あたり約 9.6 万個で、あと 8〜9 日の計算だった (83 日の平均から、その日の負荷を無視して外挿した。issue 500)

## 本文から移した実例 (2026-09-28 の prompt-audit。本文は規範だけにするため)

- 実測 2026-09-26 obaket 945: 仮説だけで `.animation` を外し、後から作った計測で「効果なし・別の箇所が悪化」と分かって revert した
- dotfiles 562: カード一覧の「(17 分)」を所要と読み、履歴で数え直すと 20 分だった
- swift-smbee 097 (2026-09-30、「過去の commit と比べる A/B は、測りたい経路がその commit で動くかを先に確かめる」の起源): issue 060 の
  AES-CMAC 署名の高速化 (`e91809a`) が実 Samba 転送にどれだけ効いたかを、`e91809a^` / `e91809a` の A/B で測る計画だった。ところが issue 098
  より前の SMBee は SMB 3.0.x で常に暗号化していたため、CMAC 署名は実転送では一度も wire に乗っておらず、計画どおりの A/B は「効果ゼロ」
  ではなく「測れない」だった。計画 (issue 本文) の段階では誰も気づかず、設計を codex に出させた段階で「古い commit では切断されうる」と
  指摘された。両 arm に 098 の最小 backport を当てる代替 A/B にして測った (反映率 約 102%)
- swift-smbee 099 (2026-09-30、「環境で律速が変わりうる変更は実利用を代表する系でも before / after を比べる」の起源): payload の copy を 1 本減らす
  perf 変更 (`0709833`、2026-07-23) が direct-TCP の header を別の `send()` にしたため、Linux の実 socket では往復ごとに Nagle と遅延 ACK の
  待ちが乗った (1 MiB read 168 ms。TCP_NODELAY を立てると 5.8 ms)。in-memory の性能テスト (throughput) と macOS の手元では見えず、2 か月気づかれなかった。
  既存の「測った経路がユーザーの実経路と同じか」は TTY / パイプのように走る処理が変わる例に寄っていて、コード経路が同じで環境が律速を変える形と、
  throughput が latency の退行を見ない点を書いていなかった (codex の判定)。なお `0709833` はこのルールの起源 (2026-08-26) より前の変更
