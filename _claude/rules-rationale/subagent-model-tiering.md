# サブエージェントは sonnet が使える箇所では sonnet を使い、アウトプットは必ず main agent が検閲する — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/subagent-model-tiering.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ

- main モデルを全サブタスクに使うとトークンコストと rate limit を無駄に消費する (session limit 到達で並行エージェントが途中死した実例: 2026-06-12)
- 一方で下位モデルは「もっともらしい誤り」の混入率が上がるため、コスト削減分は検閲で品質を担保する。分業: 下位モデルが作業し、main が判断する

## Codex の集計値と実行経路の疎通 (2026-10-08、obaket retro 1086)

- obaket 1006: 枠の判定が不能のまま長い run を起動し、30 分空走して空の成果物を返した。
- obaket 1063: `ratelimit -source codex -check` が rc=0 (余裕あり) を返した直後の敵対レビューが
  `You've hit your usage limit` で停止した。判定不能時だけの疎通確認ではこの形を防げないため、長い run の前には rc=0 でも同じ経路で短く確認する。
- obaket 1064: 起動前の枠チェックを省略した run が上限で停止した。これは判定の誤りではなく既存ルールの不履行で、1063 と混ぜて数えない。
- 短い確認の成功は、その時点の疎通だけを示す。長い run の完走保証には使わず、実際に止まった場合は成果物と差分を確認して扱う。

## 1 体あたりの固定分 (retro 687, 2026-10-08)

- zundamon-kaisetsu の確認で、sonnet のサブエージェントは仕事の量によらず 1 体あたり約 14〜16 万トークンを使った
  (ツール呼び出し 2 回でも 14 万台。完了の通知の `subagent_tokens`)。大半は起動時に読み込まれる共通の指示と見ている
  (キャッシュから読まれた分の内訳は通知に出ないので未確認)
- haiku に替えても 175k で減らなかった (同じ指示・同じ台本での試験)。モデルの単価は下がるが、トークン数は固定分で決まる
- 観点ごとに 5 体並べた構成は 1 本で約 74 万、1 体にまとめると約 16 万。「数回のツール呼び出しで終わる作業は委譲しない」の根拠の実測
