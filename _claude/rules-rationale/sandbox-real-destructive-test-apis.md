# なぜ: 本物の破壊的 API を呼ぶテストの隔離を、同じ commit で入れる

## 起源: dotfiles 148 段階 ④ の削除エンジン (2026-09-03)

`src/doctor/disk/delete.go` は本物の `os.RemoveAll` と `renameatx_np` を呼ぶ。
テストもそれを本物で呼んでいたが、**1 周目の時点では fixture が正しいことだけに依存**していた
(渡すパスが `t.TempDir()` 配下であることを、各テストが自分で守っていた)。

隔離ハーネスを作ったのは、ユーザーに **「絶対に実際のファイルを消さないようにハーネスを
しっかり入れて」** と言われてからだった。つまり:

- 破壊的操作を実装する commit と、テスト側の隔離を設計する commit が**別々になった**
- 指摘されるまで自分から作らなかった。「fixture は一時ディレクトリだから安全」で止まっていた

fixture 依存が危ういのは、**そのテストが正しい限り成立する**条件だという点にある。
次にテストを足す人が `os.Getenv("HOME")` 由来のパスを渡せば、その瞬間に本物が消える。
守るべきは「今あるテスト」ではなく「これから足されるテスト」。

## 段数を宣言したが、守られていた段は 1 段だけだった

作ったハーネスは ①サンドボックス外は既定拒否 ②XDG を差し替え ③最終違反チェック の
3 段構えで、ヘッダにもそう書いた。敵対レビューが段ごとに変異を当てた結果は
`adversarial-review-own-safeguards.md` の rationale (§1.5 の起源) に書いたとおりで、
**②と③はテストが 1 本も守っておらず、①も登録の解除側が守られていなかった**。

この形は本ルール単独では防げない (隔離を「入れた」ことは事実なので)。
だから本文は §1.5 へリンクして、**段数の宣言を変異の後にする**ことを要求している。

## TOCTOU: 「全部 plan → 全部 exec」が窓を分単位に広げた

`Delete` を「全ターゲットを plan → 1 件ずつ exec」と書いた。素朴で読みやすい構造だが、
破壊的操作では**検査から実行までの距離が窓そのもの**になる。

- plan と exec のあいだに再走査 (最大 60 秒) が何度も挟まる設計だったため、
  **最後のエントリは検査から実行まで分単位空いていた**
- 敵対レビューが親ディレクトリの差し替えで実測し、P1 として出した
- エントリ単位で plan → exec → verify に組み替えて解決。窓は「1 件の処理時間」に縮んだ

単独のルールにするほどではないと判断して本ルールの 1 節に置いた
(発動条件が「破壊的操作を実装するとき」で同じ、かつ隔離ハーネスと同じ commit で考える対象)。

## retro での切り出し判断

出典: `issues/done/209-retro-doctor-delete-engine-2026-09-03.md` の項目 3 と 4。
項目 3 が本ルールの本体、項目 4 が「検査と破壊的操作は隣接させる」の節。
`adversarial-review-own-safeguards.md` への追記にしなかったのは、あちらの発動点が
「壊れないことを保証する側のコードを新設した瞬間」で、**こちらは「テストから本物の破壊的
API を呼ぶ瞬間」**という別の点にあるため (あちらは機構の検査、こちらはテスト環境の隔離)。
