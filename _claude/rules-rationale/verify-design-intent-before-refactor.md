# リファクタ / 複雑度改善を提案する前に「既に意図的に選ばれた設計」でないか確認する — なぜ・実例

ルール本文: `~/dotfiles/_claude/rules/verify-design-intent-before-refactor.md`（`~/.claude/rules/` に link され、毎セッション起動時に読まれる）。
この文書は起動時には読まれない。ルールの根拠・起源・実例を保存し、ルールを疑う・改訂する・却下するときに読む。

## なぜ

確認を怠った第一印象の提案は空振りを量産する。典型: 「proxy が多い = 削除すべき」→ 実はドキュメントに「callsite を一度に書き換えないための意図的設計」と明記済 / 「全部抽出すべき」→ 過去 issue で「実需要で判断する」と決定済 / 「extension で論理分割できる」→ private member 依存で可視性を緩める必要があった / 大ファイル = 複雑と判定 → 中身は仕様の写像で分解すると逆に読みにくい。確認のコストは小さく、意図的設計を壊す手戻りは大きい。

このルールの効果は「やらなかったこと」に宿るため見えにくく形骸化しやすい。「複雑そう」と感じた瞬間が思い出す唯一のフック。

## 一階層上の共通規約を読まずに「規約違反」と書いた例 (2026-09-03、dotfiles)

`src/doctor` だけ `.golangci.yml` が無いことを issue にしたとき、`src/glogx/CLAUDE.md` の
「不変条件は lint / test が正本」を引いて「この repo が明文化した規律が効いていない」と書いた。
しかし**一階層上の `src/README.md`** には「`.golangci.yml` は任意 (無ければ既定 linter で運用)」と
明記されていた。つまり設定の不在は規約違反ではなく、明文化された選択肢の一方。
反証レビューが「これを引いておかないと、次の読者は by design で閉じる」と指摘し、
issue の根拠を「glogx と enum を共有し、かつ破壊的操作を持つモジュールである」という個別事情
1 本に絞り直した (指摘自体は P2 のまま生存)。
