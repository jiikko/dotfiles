# よくある「守っていないテスト」の形 (変異を当てる前に自問する)

> [`../rules/mutation-verify-new-tests.md`](../rules/mutation-verify-new-tests.md) のチェックリスト。
> 発動点 (新規テストを commit する / 「このテストで守られている」と書く) と手順は rule 側が持ち、常時読み込まれる。
> この表は起動時には読まれない (常時読み込みの指示ファイル合計が上限 150k 字を超えたため、2026-10-06 に rule から切り出した。dotfiles issue 414 の続き)。
> **rule が発動したら、変異を当てる前にこのファイルを Read する**。


**assert と期待値**
- assert が無い / 常に真になる assert を書いていないか。期待値を production と同じ式・定数から作っていないか
- 前提の assert が**停止しない**形になっていないか (`#expect` は記録するだけ。停止させるなら `#require`)
- **逆向き: 前提の guard が `Issue.record; return` で抜けて、後ろの副作用 assert を丸ごと飛ばしていないか**。副作用の assert は guard の手前か、guard に依存しない形に置く
- **shell で、条件文脈 (`if` / `||` / `&&` / `!`) から呼ばれる関数の中に assert を置いていないか** (仕組みの正本は
  `adversarial-review-own-safeguards.md` §2 の `set -e` の項)。assert の失敗は誰にも拾われない。fake / callback の中では値を
  **記録するだけ**にし、比較は条件文脈の外で行う
- **属性 (色・フラグ・クラス) の存在だけを見ていないか**。属性 + それが付く対象まで見る
- **文字列を部分一致で pin していないか**。コマンド・書式・生成物のように全体が契約なら**完全一致**で固定する
- **`grep` に複数行のパターンを渡していないか** (行ごとの OR なので 1 行目が一致すれば通る)。切り出して文字列比較にする
- **grep で配線を pin したなら、その grep 自身の行 (やコメント) が pin を満たしていないか** (行頭アンカーで解決する)

**fixture と前提**
- 差が出ない状況しか作っていないか (要素 1 個、空集合、恒等条件)
- **fixture を「検査対象が壊れない形」に選んでいないか**。値だけでなく**並び順**と**大きさ**でも検出力は消える
  - 順序依存の選択を検査するなら**正解を先頭以外へ置き**、production の並びと逆順の両方を回す
  - 表示のテストは**実在する最大級の入力**で見る (幅で切る実装は短い fixture では切られた先が検査されない)
  - 「fixture を短くした」「並びを変えた」理由をコメントに書いていたら黄信号
  - 性能・確保のガードの変異が緑なら、その退行が今の toolchain で測定値を変える入力域を実測する
    (標準ライブラリの最適化で、ある域では退行が等価変異になる)
- **取り違えを検出したい 2 つの値を、fixture で同じ値にしていないか**。2 つを別々の数にしてから変異を当てる
- **数値の計算を別の言語へ移したなら、実データ由来の golden に加えて、境界 (丸めのちょうど半分・比較がちょうど等しくなる値・整数の -0) を
  狙った合成の入力を入れているか**。コンパイラの演算の融合 (arm64 の Go の FMA・C の `-ffp-contract`) や組み込み関数の精度 (Python 3.12 以降の
  sum の補正) の差は、境界でしか表に出ない (issue 641: 87 行の E2E では一致し、合成の境界の入力で 1 フレームずれた)
- **framework / Core が特別な意味を持たせた値 (空文字 = root、0 = 無制限、nil = 既定) を fixture に 1 件入れているか**。
  特別な値は専用の分岐を通るので、普通の値だけの fixture はその分岐を一度も踏まない。何が特別かは呼び出し側の規約にしか
  書かれていないことが多い
- **fixture が、判定に使うコマンドの出力に現れる形になっているか** (`git status --porcelain` は未追跡
  ディレクトリを 1 行に畳むので、fixture は一度 commit してから変更する / 検査が `--name-only` を読むのに fixture を
  ワークツリーにだけ置く / 検査が stdout を見るのに fixture が stderr に出す)
- **fixture は「退行したら見えるようになる場所」に置いているか** (修正後の設計でしか読まれない場所は、
  退行からは最初から不可視)
- **フィクスチャが production の初期状態と違わないか** (違うとその経路を構造的に一度も踏まない)。並行・レースのテストでは、呼び出し元がどの状態から始まるかを実装側で確認してから形状を決める
- 「拒否する例」が、実装の拡張で静かに成立しなくなっていないか。allowlist / 収録表を増やす変更では、
  **その表の否定例も同じ commit で見直す**

**到達しているか**
- 検証したいコードが本当に実行されているか (closure / 環境変数ゲートの内側は走らない)
- **先に効く別の防御が影になって、狙った分岐に到達していないか**。本番で起きる順序を再現する
- **観測が複数の源の OR・合計なら、源ごとに観測する** (別の源が true を保つと、1 つの源の退行が覆われる)。同じ fixture に 2 つの
  条件を入れて、片方が先に効く分岐で処理ごと飛ばしていないかも見る (retro 704: 変異が緑のまま通った 4 回中 2 回)
- **予算・上限で退行を見るなら、名指しする退行 1 件ぶんの増え (変異での差) が余裕より大きいかを測ってから上限を決める**。
  題材が小さいと退行の増えが余裕に収まる (確保 +2 に余裕 +3。retro 704)
- **前提が「早期 return で素通りしていないか」を assert しているか**。fixture を作った直後に狙った状態を Fatal で固定する
  - 素通りは変異 1 本だと red の陰に隠れる。**別の場所を壊す 2 本目**で「そのケースだけ緑」を見て初めて分かる
- **処理を遅延・非同期 (返したコマンドの中・goroutine・次の tick) へ移したら、「起きないこと」を見ている assert を全部洗う**。
  遅延した先を走らせないまま「呼ばれていない」を見ると、実装を壊しても緑のまま
- **待機ループが本当に待っているか** (Swift の `for … where 条件` は待たずに飛ばす。while で書き、待つ対象が始まったことを先に assert する)
- **入れ子の UI / 多層の構造で「層の中の不変条件」を主張したなら、テストは*外側の入口*から書いているか**。
  判定: その不変条件を破る入力を、ユーザーが実際に触る入口から入れて red になるか
- **走査・突合系のテストは「実際に何件を見ているか」を数えてから根拠にする**。canary の下限も実数に近づける
- **並行に開始した処理の到達順を index で決め打ちしていないか** (「5 番目が待つ」「0 番目を解放すると進む」)。開始の順と枠を取る順は一致しない。
  到達した集合から待っている方を特定し、到達済みのものを解放する。取り消しの窓で増減する数 (lease の数と request の数など) も等号で比べず、
  守りたい性質の向きの不等号にする。非同期の入口に await を 1 つ足しただけで順が変わり、タイミング次第で落ちる (obaket 807)

**red の読み方**
- **テーブル駆動 / サブテストなら、変異で「全ケース」が red になるか**。ケース名ごとの pass/fail 一覧で判定する。
  鍵は **package 名 + ケース名** (同名テストの PASS が red を上書きする)
- **変異の red は「ケース名 × どの assert が出したか」まで特定して初めて証拠になる**。
  「このテストだけが red になる変異」を特定できないテストは、他と重複していると扱う
  - **判定する側の道具も壊れる** (`grep -E '^\s+--- FAIL'` はインデントなしの `--- FAIL:` を落とす)。判定式は実測で確かめる
- **fake の「止まる回数」が、変異側の呼び出し回数を想定しているか** (「初回だけ block」は 2 回目を足す変異に素通りされる)
- **変異で green だったテストが、別の環境で変異なしに red になるなら、検知漏れではなく flaky かつ空振り** (assert が
  race の成立した実行でしか走っていない)。直すより、守りたい不変条件を決定論的に観測できる層へ移す

**観測の設計**
- **その観測は、変異の有無で違う値を出すか** (「差が出ない状況」の一般形)
  - 主張が**効率の不変条件** (短絡・優先順位・打ち切り) なら、fallback 先が正解と一致すると返り値は同じになり、結果の assert では
    原理的に検出できない。観測点を「何件読んだか / どこで止まったか」へ移す
  - 主張が**副作用の時点**なら状態の観測では固定できない。その時点で副作用が起きたら失敗する環境を挟む (PATH を空にする / fake に reject させる)
  - 主張が**ガード**で、守る入力が生成経路から出てこないなら、計算部を関数に切り出して値を直接与えるテストにする
  - 主張が**「画面でこう見える」**なら、状態ではなく**描画結果 (出力行)** から読む
- **外部コマンドのエラーメッセージの文言で判定していないか**。文言はロケールや版で変わり、変わると検査は緑のまま空振りする
  (手元だけ・CI だけの偽の緑になる)。何が起きたか (呼び出しの記録・ファイル・exit code) で判定する。文言しか手段が無いなら
  `LC_ALL=C` を固定し、その理由をコメントに残す
- **逆向きの問い: その観測値が進んだのに、目的が達成されていない状態を作れるか** (十分性)。作れるなら
  単独の合否基準にしない (複数の観測を AND で取る)。完了・成功を表す観測値を自分で新設したときに特に効く
- **本番と同じ制約の下で観測しているか** (timeout / メモリ上限 / 実行時間の壁 / 権限)
- **資源の上限 (枠・プール・カウンタ) を新設したら、「枠が返る列」を通すテストも置く**。返す側を消す変異が red になるまで
- **観測点は副作用の後に置く** (前に置くと意図の回数を数える)
  - **guard の「前」にしか割り込めない seam では、その guard は検査できない**。seam は守りたい窓の内側に置く
  - 置く基準は「自分の fixture で修正を観測できるか」ではなく「退行が現れるか」。
    **issue の症状そのものを再現する変異が red になるか**を 1 本当てて確かめる
- **生死・存在を `kill(pid, 0)` やプロセスの有無で判定しない** (ゾンビにも fork 直後にも成功する)。`Wait()` の完了・子が書く成果物で見る
- **「案内した先」は文字列ではなく実行で確かめる** (エラーメッセージが名指ししたコマンドをテストから走らせ、rc と出力を assert する)
- **窓がミリ秒なら人為的に広げて決定論にする** (広げた条件で A-B (ガード有無) を取ると変異の当たりも安定する)

**実装の二重化・配線**
- **検査を 1 つ足したら、隣接する既存の検査の変異を当て直したか**。後から足した検査が既存の最終状態を肩代わりすると、
  既存のテストは無検査になる。観測点を最終状態から「後段へ進まないこと」へ移す
  (段を同時に書くときは [`adversarial-review-own-safeguards.md`](../rules/adversarial-review-own-safeguards.md) §1.5)
- **同じ判定・同じ結論を 2 箇所で別実装していないか。テストがある側だけ見て安心していないか**。両方へ同じ入力を
  流して突き合わせ、片側の分岐を消す変異で red になるか確かめる。根治は出典を 1 箇所へ寄せる。この項の発動点はテストを書くときで、守りを新設するときは
  [`adversarial-review-own-safeguards.md`](../rules/adversarial-review-own-safeguards.md) の 0-B
- **差分テストの oracle は、独立に由来する別実装・公開 vector で用意する**。既存処理の写しや単純な移植は誤りを共有するので独立ではない
  (上の項の「出典を 1 箇所へ寄せる」は oracle には当てない)
- **計算ヘルパーの純関数テストだけで「配線済み」としていないか**。呼び出し側を旧実装に戻す変異で red を見るまでが 1 セット

**fake / stub**
- **fake / stub が外部コマンドの exit code を模しているか**
  ([`survey-receiver-guards-before-passing-new-values.md`](../rules/survey-receiver-guards-before-passing-new-values.md) の外部コマンド版)
- **スタブが引数を受け取っているか** (捨てると「何を渡すか」を変える変異が全部緑)。渡された値を記録して assert する
- **定数を返すだけのスタブに差し替えると、その依存へ渡す設定値が無検査になる**。設定値が結果を決めるなら実物を使う。
  上の項と発動点は同じで、片方だけ直すともう片方が残る
- **fake の状態は、実物が取りうる状態を実測で列挙した表から作る** (1 回の実測を写さない)。判定は状態の名前の列挙でなく、
  名前が増えても崩れない性質で書く (偽物に無い状態が本番で出ても、テストは緑のまま判定が外れる)

**platform / シェル**
- **環境が変われば別の値になるコマンド出力を、そのまま比較に使っていないか** (`ps` / `date` / `stat`)。両方の形状をテスト内で作る
- **比較に使う正規表現の方言が、両 platform で同じ意味になっているか** (`\t` は BSD と GNU grep で違う。タブは変数に落とす。`\s` は両方が受ける)。
  ヘルパーへパターンを渡す形は `grep` の近くを探しても見つからないので、正規表現になる文字列全部を見る。
  dotfiles は macOS 専用なのでこの項は他 repo 向け
- **判定に使う外部コマンドが、テストで渡す入力の形を受けられるか** (BSD awk の `-v` は改行を受け付けない。複数行は別入力で渡す。macOS でも踏む)
- **シグナルを撃つテストは、撃つ先がサブシェルだと実体に届かない** (`exec` で置き換えるか、プロセスグループへ撃つ)
- **観測対象が生まれるのを待ってから撃つ** (生まれる前に撃つと、修正の有無で結果が変わらない観測になる。
  待ち方は [`avoid-wall-clock-assertions.md`](../rules/avoid-wall-clock-assertions.md))
- **zsh の `(( i++ ))` は古い値を返す** (`i` が 0 だと status 1。`err_exit` 下で死ぬ。`(( ++i ))` を使う)
- **bash (特に 3.2) で `$var` の直後に ASCII 以外の文字を置かない** (全角の先頭バイトまで変数名として読まれ、`set -u` で止まる。無ければ値が黙って消える。`${var}` にする。dotfiles では `make test-lint` (`scripts/check_var_before_multibyte.sh`) が落とす)
- **空になりうる出力の行数を here-string + `NR` で数えない** (`<<<` は空にも改行を足すので 0 件が 1 と数えられる。空でない行を数える)
