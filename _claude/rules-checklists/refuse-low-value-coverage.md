# カバレッジ向上を要求されても「テスト困難 かつ 低価値」なら拒否する — 発動したときに読む節

> [`../rules/refuse-low-value-coverage.md`](../rules/refuse-low-value-coverage.md) のチェックリスト。発動点は rule 側の同じ見出しの下が持ち、常時読み込まれる。
> この文書は起動時には読まれない (常時読み込みの指示ファイル合計を上限 150k 字に収めるため、2026-11-08 に rule から切り出した。dotfiles issue 414 / 1044 の続き)。

## 拒否の作法 (黙って skip しない)

1. どのセル (困難×低価値) に該当するかを、対象コードを指して具体的に言う
2. 「カバレッジは proxy。この行を覆っても守れる不変条件が無い」と根拠を述べる
3. 代替を出す: 「ここは薄い委譲なので、価値あるロジック X を pure 関数に切り出せばそちらは容易かつ有益にテストできる」等。単なる拒否で終わらせない

## テストを削除するときは、失ったカバレッジを issue に起こす

**テストの削除は「守るものを減らす」変更**なので、知らせずに消さない。消すと決めた場合も:

1. **削除したテストの中身を issue に貼る** (何を検証していたか。issue は残るがコードは消える)
2. **なぜ削除したか**を実測つきで書く (「難しかった」なら、何がどう難しかったかまで)
3. **失ったカバレッジを列挙する**。🚨 「元々検出できていなかったもの」と
   「削除で失ったもの」を**分ける** (前者は削除の責任ではない)
4. **E2E 以外で検証し直す案**を出す (unit test / debug API / 人手のチェックリスト / 受容)。
   **受容するなら、検出可能性を三値のどれかで書く**:
   `検出できることを実証済み` (実測・再現・テストを添える) / `検出可能性は未確認` /
   `確実な検出手段はない`。
   🚨 **後の 2 つで肯定的な理由を書かない** — 「限定的な条件でしか起きない」「本人が直後に気づく」の
   ような収まりのいい答えは、根拠が無いまま**受容の判断をその上に建てる**。無保護であることと
   **再評価の trigger** を記録する (「気づくはず」で終わらせない)
   🚨 これは**外す免罪符ではない**。実際に働いている guard は検出手段を用意してから外す
   ([`list-masked-failure-modes-before-removing-guard.md`](../rules/list-masked-failure-modes-before-removing-guard.md))。
   production から一度も呼ばれず何も守っていなかった機構とは分けて扱う
