# 検証レポートを `./tmp` に出したら、結論と却下理由を issue へ移すまでが 1 セット

> **トリガー型ルール。** 監査・レビュー・裏取り・反証の結果を `./tmp/*.md` に書き出した
> 瞬間に発動する。「レポートができた」と報告しそうになったら、それは**まだ半分**。

## ルール

- **`./tmp` に出した検証・監査・レビューのレポートは、①結論 ②全数勘定 ③却下した指摘とその理由
  を issue (または対象コードのコメント) へ移すまで作業を終えない**。`tmp/` は
  `~/.gitignore_global:5` で ignore されているので、レポート本体はセッションが終われば消える
- **移す優先順位は「却下理由 > 結論 > 経緯」**。却下理由は「消えると同じ誤指摘が再生成される」
  性質の情報で、失うと反証コストを丸ごと再支払いすることになる
- **移し先の使い分け**: 着手する残債は `issues/` の新規 issue へ / 「対応しない」と決めた指摘は
  該当コードの直近コメントへ ([`pending-issue-rationale-in-code.md`](pending-issue-rationale-in-code.md)) /
  出典の監査 issue が残っているなら、そこに「反証・対応の結果」節を足して全数勘定を書く
- **レポート本体を `docs/` に commit して残すのは採らない**。レポートはその時点のスナップショット
  であり、コードが動けば嘘になる ([`claude-md-maintenance.md`](claude-md-maintenance.md) の
  「What はコードが真の出典」と同型)。残すのは結論と判断理由だけ

## 同型: issue が `tmp/` のスクリプトの実行を指示していないか

レポートだけでなく**スクリプトにも同じ穴がある**。issue に

```
node tmp/probe-dex6.js   # atob 2 段目の入力を観測
```

と書いた時点で、**指示だけが残ってスクリプト本体は消える**。読んだ人は「実行しろ」と
言われた対象が存在しない状態に置かれる (しかも gitignore なので復元もできない)。

検出は簡単で、**issue / ドキュメントを `tmp/` で grep するだけ**。ヒットしたら 3 つに仕分ける:

| その参照は | 正しい形 |
|---|---|
| **同じ手順の中で書いて読む出力先** (`... \| tee tmp/out.log` して後段が grep する) | **問題なし**。tmp の正しい使い方。残っているファイルは前回実行の残骸で消してよい |
| **再取得コマンドが併記されている**成果物 (`curl ... -o tmp/x.js`) | 問題なし。消しても同じものが手に入る |
| **中身がどこにも無いスクリプトの実行指示** | ✗ ここだけが本当の問題 |

3 つ目の直し方は「とりあえず tracked に移す」ではない。**まず「その解析はもう終わって
いないか」を問う**:

- **終わっていて、製品コードに落ちている** → **スクリプトは消して、issue の該当節を
  「製品側のどこを見ろ」に書き換える**。移すと同じことをする実装が 2 箇所になる
- **まだ必要で小さい** → issue に本文ごと貼る (issue と一緒に永続する)
- **まだ必要で大きい** → tracked なパスに置いて、issue はそこを指す

実例 (2026-08-27, good-chrome-extensions): open issue が `tmp/probe-dex4.js` /
`probe-dex6.js` / `save-main.js` の実行を指示していたが、**その直後の節に
「解決: dex の第3引数は encrypt/decrypt フラグだった」と結論が書かれていた**。
つまり probe はもう役目を終えており、しかも製品側 (`bjp_download` の `dexRunner`) が
同じことを jsdom でやっていた。移さず削除し、issue を製品側へのポインタに直した。
なお probe が読む HTML ダンプは、その前の tmp 掃除で既に消えており **半分壊れていた**
(tmp に置いた道具は、置いた本人が思うより早く動かなくなる)。

## 同型: issue を `done/` へ送るときは、本文が前提にしている「現状」を実測する

閉じる作業は「文章を書くだけ」に見えるので、**本文に書かれた環境値を測り直さないまま
決着節を書いてしまう**。しかし done へ送った issue が次に読まれるのは**再発したとき**で、
そのとき前提が逆だと、書き残した「再開の trigger」がそのまま実行不能な手順になる。

- **done へ送る前に、本文の「現状は〜」「いまは〜になっている」を 1 つずつ実測する**。
  測れない値は「未実測」と明記する (推測で現状を書かない)
- ⚠️ **調査メモの仮定法を現在の設定値として読まない**。「〜でブレが消えたのなら原因は X」は
  「今 〜 になっている」ではない。issue 本文の過去形・仮定法は、書かれた時点の作業ログである
- 決着節には **実測値 + 出典 (コマンド / `file:line`) + 測った日**を書く
- **再開の trigger が実行可能かを確認する**。既に満たされている条件を「戻して再現を見る」と
  書かない (逆に、条件が既に揃っているなら「今の状態がそのまま実験条件」と書けることがある)

## なぜ

起源: 2026-08-21 の実例。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/move-report-conclusions-to-issues.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## やること / やらないこと

- ✓ `./tmp` にレポートを書いたら、同じセッションで結論・全数勘定・却下理由を issue / コードへ移す
- ✓ 却下した指摘は「なぜ崩れたか」を書く (「該当なし」だけでは次の audit が同じ指摘を出す)
- ✓ 出典の監査 issue が残っているなら、そこに全数勘定 (生存 N / 却下 M) を残して done へ送る
- ✓ issue に手順を書いたら `tmp/` で grep し、「中身の無いスクリプトの実行指示」になっていないか見る
- ✓ `done/` へ送る前に、本文の「現状は〜」を実測し直す (測れないなら「未実測」と書く)
- ✗ 「レポートを `./tmp/x.md` に出しました」で報告を終える (次のセッションには存在しない)
- ✗ レポート本体を `docs/` に commit してスナップショットを正本にする
- ✗ 却下理由を省いて「対応した分」だけ issue 化する (省いた分が再生成される)
- ✗ issue から `node tmp/foo.js` の実行を指示する (本体は残らない。貼るか tracked に置く)
- ✗ 役目を終えた調査スクリプトを「一応」tracked に移す (製品側と二重実装になる。消して製品側を指す)
- ✗ issue 本文の仮定法 (「〜なら原因は X」) を現在の設定値として決着節に書く
- ✗ 既に満たされている条件を「戻して再現を見よ」と再開の trigger に書く
