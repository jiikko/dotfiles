# 既存の呼び出しに「新しい値・フラグ・経路」を通す修正では、受け側のガードを先に洗う

> **トリガー型ルール。** 既存の関数呼び出しに新しい引数値を渡す / これまで false だった
> フラグを true にする / これまで到達しなかった経路にデータを流す — そういう修正を
> 書こうとした瞬間に発動する。
> **自分で新しい不変条件を宣言した瞬間**にも発動する (下の「自分が宣言した不変条件」節)。

## ルール

- **新しい値が受け側で「初めて到達させる分岐」を、修正を書く前に grep で列挙する**。
  受け側とその先の呼び出し連鎖にあるガード (preflight / 非空チェック / precondition /
  reject / assert) は、既存の呼ばれ方だけを想定して書かれている
- 列挙した各ガードについて「新しい呼ばれ方で発火したとき、呼び出し側はそれを
  正しく扱えるか (catch しているか / 意味論が合うか)」を確認してから実装する
- **テストの fake / stub に、受け側の reject 挙動を模させる**。fake が「常に成功」だと、
  ガード起因の失敗経路がテストから構造的に見えず、修正が悪化を作っていても green になる
- **逆向きも同じ**: 既存経路を共通 helper に差し替えるとき、**helper が新たに throw する
  error** と旧経路が throw していた error の意味論を突き合わせる。呼び出し側の catch / 変換は
  旧 error だけを想定して書かれており、新 error は素通りして汎用エラーに落ちる。
  「refactor は挙動を変えない」は error 経路の意味論には効かない — 正常系のテストが
  全 green のまま、error の意味だけが silent に変わる
- **表示のための正規化 (無害化・省略・エスケープ) を「入口 1 箇所」で当てるとき、同じ値を
  identity に使っている受け側を先に洗う**。パス・ラベル・ID を書き換えると、画面に出ている名前と
  実際に触る対象 (削除の照合キー・提示するコマンドの引数) が食い違う。書き換えず**落とす**か、
  表示用の派生値を別に持つ (実測 2026-09-04 dotfiles 228: doctor の `Item.Path` を無害化で書き換えると
  `planDelete` の照合から外れ「見えているものと消えるものが違う」を作った)

## 自分が宣言した不変条件にも、同じ手順を向ける

受け側のガードを洗うのと同じことを、**自分が今つくった不変条件**に対してやる。
「2 つのものを対にして持つ」と決めた瞬間に発動する (2 つのマップ / 値とその世代 /
述語と builder / 表示名と同一性キー)。

- **その不変条件を崩せる経路を、宣言と同じ変更の中で grep で全部挙げる**。
  片方だけを更新している箇所が既にあることが多い (自分が足した経路とは限らない)
- **崩せる経路が 2 つ以上あるなら、更新の責務を 1 つの関数へ寄せてから閉じる**。
  「両方書くのを覚えている」に依存させない
- **寄せたら、迂回を機械で止める** (その関数の外で片方だけ触る形を検出する)。
  寄せただけでは、次に足す人が同じ形を再生産する
- 🚨 **宣言をコメントに書いたことは、守られていることの証拠ではない**。
  「A は B の部分集合」と書いた直後の実装が、実際には片方しか消していない形は起きる
  (実測 2026-09-06: dotfiles で 1 セッションに 3 組)

## 手順 (修正を書く前の 5 分)

1. 新しく渡す値 / フラグ名で受け側の実装を grep する (`options.isDirectory` 等)
2. ヒットした分岐のうち「今回の呼ばれ方で初めて真になるもの」を列挙する
3. 各分岐の throw / return が、自分の呼び出し側の catch / 分岐で **意味論どおりに**
   扱われるか確認する (「catch はあるが別の意味に解釈される」も事故)
4. その分岐が前提にしている不変条件 (「呼び出し前に X が保証されている」) を、
   新しい経路が満たすかを確認する
5. fake / stub に受け側の reject 挙動を足してからテストを書く (「fake がガードを
   模していれば red になっていた」を後から言わないため)

## やること / やらないこと

- ✓ 新しい値で初めて到達する受け側ガードを、実装前に grep で列挙する
- ✓ fake に受け側の reject 挙動 (非空 preflight 等) を模させる
- ✓ ガードの発火が呼び出し側の catch で正しい意味論に落ちるか確認する
- ✗ 「渡す側の変更だけ見て、受け側は既存だから安全」と仮定する
- ✗ 常に成功する fake のまま「テスト green」を修正の正しさの根拠にする
