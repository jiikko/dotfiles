# 既存の呼び出しに「新しい値・フラグ・経路」を通す修正では、受け側のガードを先に洗う

> **トリガー型ルール。** 既存の関数呼び出しに新しい引数値を渡す / これまで false だった
> フラグを true にする / これまで到達しなかった経路にデータを流す — そういう修正を
> 書こうとした瞬間に発動する。
> **自分で新しい不変条件を宣言した瞬間**にも発動する (下の「自分が宣言した不変条件」節)。
> **既にある欄・引数・口を初めて使う / 用途を変える**ときにも発動する (コードを書かずに CLI の欄を選ぶ場面も含む)。

## ルール

- **新しい値が受け側で「初めて到達させる分岐」を、修正を書く前に grep で列挙する**。
  受け側とその先の呼び出し連鎖にあるガード (preflight / 非空チェック / precondition /
  reject / assert) は、既存の呼ばれ方だけを想定して書かれている
- 列挙した各ガードについて「新しい呼ばれ方で発火したとき、呼び出し側はそれを
  正しく扱えるか (catch しているか / 意味論が合うか)」を確認してから実装する
- **既にある欄・引数を初めて使う / 用途を変えるときも、受け側の実装でその値の意味を確かめる**。見出し・名前・usage の文面は受け側とずれていることがある
  - **自分が出す値 (進捗・ログ・メトリクス・イベント列) の出し方を意図して変えるときは、その値から別の事実 (入口・route・状態) を推定している判定・検査を変更の前に grep する**。
    値そのものを assert するテストは差分で気づけるが、推定する側は値の意味が変わると黙って別の事実を答える (obaket retro 1138)
- **外部の相手への呼び出しに時間の上限を付けるときは、上限切れの後に同じ相手へ打つ次の呼び出しまで、呼び出し元で辿る**。上限切れの主な原因が
  相手の無応答なら、次の呼び出しも止まる。上限切れを「値が無い」と同じ戻り値に畳まず「相手が応答しない」として返し、テストも呼び出し元の経路
  (問い合わせ → 本処理) で通す (retro 786: prefix の問い合わせに上限を付けて "" を返したが、直後の同じ tmux への display-popup が止まったままだった)
- **既存の呼び出しの下に新しい待ち (join・await・lock) を足すときは、呼び出し元を全部挙げ、それぞれ「以前より長く待つ最悪値」と「待っている間に
  持っているもの (直列化の serializer・lock・actor)」を表にしてから実装する**。持ったまま待つと、待ちは呼び出し元 1 つでは済まず、同じものを待つ他の操作も並ぶ
  (obaket retro 1293: 「production の挙動を変えない」段で shutdown に後片付けの join を足し、接続の保存が背景の close の最大 60 秒を serializer を持ったまま待った)
- **テストの fake / stub に、受け側の reject 挙動を模させる**。fake が「常に成功」だと、
  ガード起因の失敗経路がテストから構造的に見えず、修正が悪化を作っていても green になる
- **protocol に既定の実装つきで要件を足すときは、本物を包む conformer (proxy / decorator / wrapper) を全部挙げ、転送を同じ変更で足すか起票する**。
  既定の実装 (何もしない・1 件だけ返す) はビルドを落とさないので、包む側が転送し忘れると機能が黙って消える (vlc-multi-video-player retro 426:
  SAC の `ToastManaging` に足したホバーの停止が、obaket の logging decorator を通ると効かなかった。ビルドも警告も通り、敵対レビューで見つかった)
- **逆向きも同じ**: 既存経路を共通 helper に差し替えるとき、**helper が新たに throw する
  error** と旧経路が throw していた error の意味論を突き合わせる。呼び出し側の catch / 変換は
  旧 error だけを想定して書かれており、新 error は素通りして汎用エラーに落ちる。
  「refactor は挙動を変えない」は error 経路の意味論には効かない — 正常系のテストが
  全 green のまま、error の意味だけが silent に変わる
  - **N 個の手組みを 1 つの共通の道具に寄せるときは、設計の前に各呼び出し元の 🚨 / 「〜しない」のコメントと、前提にしている環境
    (端末・シグナル・stdin・プロセスグループ) を表にし、道具がその全部をオプションで表せるかを確かめる**。表せない呼び出し元は寄せない
    (一律に子を専用グループに置く設計が、mutate-verify の「グループを分けない」を戻すところだった。retro 644)
- **表示のための正規化 (無害化・省略・エスケープ) を「入口 1 箇所」で当てるとき、同じ値を
  identity に使っている受け側を先に洗う**。パス・ラベル・ID を書き換えると、画面に出ている名前と
  実際に触る対象 (削除の照合キー・提示するコマンドの引数) が食い違う。書き換えず**落とす**か、
  表示用の派生値を別に持つ
  - **落とすかの判定を「正規化した結果と元が一致するか」で書かない**。正規化は判定したい性質以外も書き換えるので
    (無害化が絵文字の VS16 も落とす等)、一致の比較はその副作用まで拒否に数える。「含むか」の述語で判定する (retro 755)

## 自分が宣言した不変条件にも、同じ手順を向ける

受け側のガードを洗うのと同じことを、**自分が今つくった不変条件**に対してやる。
「2 つのものを対にして持つ」と決めた瞬間に発動する (2 つのマップ / 値とその世代 /
述語と builder / 表示名と同一性キー / 実測で合わせた定数と、合わせたときの式の係数)。

- **その不変条件を崩せる経路を、宣言と同じ変更の中で grep で全部挙げる**。
  片方だけを更新している箇所が既にあることが多い (自分が足した経路とは限らない)
- 🚨 **読み取りの経路も数える**。「見せない・触らない」を 1 か所の絞り込みで宣言したら、同じ情報源を別の経路で読んでいる箇所
  (画面が自分で外部コマンドを呼ぶ等) を grep で挙げ、1 本に寄せる
- **実測で合わせた定数 (較正値・閾値・換算係数) を使う式の係数を直すときは、定数を合わせたときの式を出典で確かめる**。
  直す係数が較正の前提に入っていたら定数の意味も変わる。定数を据え置くなら組の係数も据え置き、別の用途の係数とは分けて持つ
- **崩せる経路が 2 つ以上あるなら、更新の責務を 1 つの関数へ寄せてから閉じる**。
  「両方書くのを覚えている」に依存させない
  - **寄せたら、その手順を手で組み立てているテストも寄せた関数を通す形に書き換える**。書き換えないと、寄せた関数の退行がテストから見えない
    (retro 819: 丸めてから割る関数に寄せた後、テストが 2 つの関数を手で繋いだままで、寄せた関数を壊す変異が緑だった)
- **寄せたら、迂回を機械で止める** (その関数の外で片方だけ触る形を検出する)。
  寄せただけでは、次に足す人が同じ形を再生産する
- 🚨 **検査する対象を固定したら、それを作る側・渡す側も同じ出典から決める** (「検査したもの」と「使うもの」も対の 1 つ)。片方を変数のまま残すと、
  その変数で 2 つを食い違わせられる
- 🚨 **「どちらが正か」の規則 (snapshot が正 / live が正 など) を決める・変えるとき、および例外の状態 (足りない画面・読めない・無効) を足すときは、先に「状態 × 読み手」の表を作り、全部のセルの期待値を
  書いてから実装する**。状態は未開始・途中・完了・取り消し、読み手はその値を読む経路 (保存・退避・外部からの完了通知・撮り直し) を全部挙げる。
  指摘された 1 経路ずつ規則を直すと、直した規則が別のセルを壊す (タブ切替の追い越しで、敵対的レビューのたびに直前の修正が退行を入れた。vlc-multi-video-player retro 417)
  - **プロセスの終了の扱い (シグナル・取り消し・後片付けの結果を待つ) を足すときも、先に同じ表を作る**。軸は合図 (INT / TERM / HUP / 端末の Ctrl-C) ×
    時点 (画面の中・子に端末を渡している間・閉じてから待ち始めるまで・待っている間)。指摘ごとに直すと、周ごとに別のセルが壊れる (retro 876: 敵対的レビューが 5 周)
  - **作った表は commit message か issue に残す** (読み手の列だけでよい)。残っていない変更は表を作らずに実装したことが外から見えず、レビューで初めて
    別の読み手の退行が見つかる (retro 831: 「読めなかった回は前の値を残す」で、同じ値を読む初期設定の計画が古い網で sudo の板を出し直した)
  - **UI の状態機械に自動の裏の動作 (読み直し・再試行・後片付け) を足すときも、先に表を作る**。軸は「その動作が書く・読む共有の状態 (状態の表示・busy・
    取得の世代・予約された別の動作) × 同時に走りうる他の書き手 (移動・mutation の後処理・利用者の操作)」。1 つずつ指摘されて直すと、直し方そのものが
    周回ごとに変わる (obaket retro 1171: 出発地の読み直しで敵対的レビューが 7 周した)
  - **複数の書き手の値を順序 (使用率は下がらない・新しい方が勝つ 等) で合流させるときは、一度入った外れ値を上書きできる権威の経路を同時に持つ**。
    順序の規則は、外れ値が一度入るとそれを守る側に回る。値の性質が正しくても、入力が正しいとは限らない (retro 833: 「同じ窓では高い方を残す」で
    利用枠のキャッシュが 7d=99% に張り付き、正しい 38% が来てもリセットまで戻らない状態だった)
  - **複数の書き手が書く共有の状態 (キャッシュ・状態ファイル) は、値と一緒に書き手 (誰が・いつ・どの版で) を残す**。外れ値が出たときに書き手が
    分からないと、出所を追えない。後から足しても、その時点の外れ値には効かない (retro 833: 99 を書いたセッションを特定できなかった)
- 🚨 **宣言をコメントに書いたことは、守られていることの証拠ではない**。
  「A は B の部分集合」と書いた直後の実装が、実際には片方しか消していない形は起きる

## なぜ

起源: obaket issue 514 / 518, 2026-08-21。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/survey-receiver-guards-before-passing-new-values.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 手順 (修正を書く前の 5 分)

1. 新しく渡す値 / フラグ名で受け側の実装を grep する (`options.isDirectory` 等)
2. ヒットした分岐のうち「今回の呼ばれ方で初めて真になるもの」を列挙する
3. 各分岐の throw / return が、自分の呼び出し側の catch / 分岐で **意味論どおりに**
   扱われるか確認する (「catch はあるが別の意味に解釈される」も事故)
4. その分岐が前提にしている不変条件 (「呼び出し前に X が保証されている」) を、
   新しい経路が満たすかを確認する
5. fake / stub に受け側の reject 挙動を足してからテストを書く (「fake がガードを
   模していれば red になっていた」を後から言わないため)

## やること / やらないこと

- ✓ 新しい値で初めて到達する受け側ガードを、実装前に grep で列挙する
- ✓ fake に受け側の reject 挙動 (非空 preflight 等) を模させる
- ✓ ガードの発火が呼び出し側の catch で正しい意味論に落ちるか確認する
- ✗ 「渡す側の変更だけ見て、受け側は既存だから安全」と仮定する
- ✗ 常に成功する fake のまま「テスト green」を修正の正しさの根拠にする
