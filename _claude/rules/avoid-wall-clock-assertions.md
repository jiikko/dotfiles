# 壁時計の経過時間で assert しない — 「何が起きたか」で判定する

> **トリガー型ルール。** テストに `Date()` / `ContinuousClock` / `advanced(by:)` /
> `measure` を持ち込んで **「N 秒以内に終わる」「N 秒以上かかる」を assert しようとした瞬間**
> に発動する。timeout / deadline / debounce / cancel の伝播を検証するときに出やすい。

## ルール

- **経過時間そのものを合否の基準にしない。** 壁時計の assert が測っているのは、多くの場合
  実装の性質ではなく **その瞬間のマシンの空き具合**。CI・並列実行・他プロセスの負荷で落ちる
- 代わりに **「何が起きたか / 何回起きたか / どの順で起きたか」** で判定する:
  - **回数**: 停止したはずのループが回り続けていないか (呼び出し回数を数える)
  - **順序**: A の後に B が起きたか (イベント列を記録する)
  - **状態**: cancel / close / invalidate が観測されたか (フラグ・stream の終了)
  - **注入した clock**: 時間そのものが仕様なら **fake clock を注入して進める**
    (`clock.instant = clock.instant.advanced(by:)`)。**実時間を待たない**
- **閾値を広げるのは対症療法**。1 秒で落ちたから 3 秒にする、を繰り返すと、
  最終的に「何も検出しない assert」になる (通るまで緩めた閾値は、壊れても通る)

## なぜ

起源: obaket, 2026-09-01。壁時計の assert (`1 秒以内に返る`) が CI の負荷で false red になり、
判定を「時間」から「condition が呼ばれた回数」へ書き直したら、成功側 1 回 / 失敗側 670 万回で
**6 桁の差**がつき、閾値をどこに置いても判別できるようになった。根拠・実測値・
「マシンが速くなるほど判別しやすくなる」性質は
`~/dotfiles/_claude/rules-rationale/avoid-wall-clock-assertions.md` に置く（起動時には読まれない。
ルールを疑う・改訂するときに読む）。

## 判定の作法

- **「差」ではなく「絶対値の上限」で見る**場面がある。並行実行中のカウンタを
  「操作前後で不変」と書くと、**操作が効くまでの間も相手は走っている**ので race で偽陽性になる
  (2026-09-01 に実際に踏んだ)
- 上限を置くときは、**成功側の実測と失敗側の実測に何桁の差があるか**を確かめてコメントに残す。
  桁差が 1 桁未満なら、その指標は判別に使えていない
- **その閾値が本当に判別するかは変異で確かめる** (成立させている機構を外して、
  桁が変わって red になるか)。[`mutation-verify-new-tests.md`](mutation-verify-new-tests.md) の適用

## 例外 (時間で測ってよい場面)

- **時間そのものが仕様**のとき (debounce 300ms / TTL / backoff の間隔)。ただし
  **fake clock を注入して進める**のであって、実時間を待つのではない
- **性能そのものを測る**ベンチマーク。ただし合否ではなく**傾向**として扱い、
  絶対値を CI の gate にしない (`perf-claims-need-measurement.md` の「比・伸び率で測る」)
- 「無限に待たない」ことだけを保証する **安全網の timeout** (テストの `.timeLimit` 等)。
  これは合否の基準ではなく、ハングでスイートが止まるのを防ぐ装置

## やること / やらないこと

- ✓ 回数・順序・状態など**時間以外の観測**で判定する
- ✓ 時間が仕様なら fake clock を注入して進める (実時間を待たない)
- ✓ 上限を置くなら、成功側と失敗側の桁差を実測してコメントに残す
- ✓ その閾値が判別することを変異で確かめる
- ✗ 「N 秒以内に終わる」を合否にする (測っているのはマシンの空き具合)
- ✗ 落ちたから閾値を広げる (通るまで緩めた assert は、壊れても通る)
- ✗ 並行実行中のカウンタを「操作前後で不変」と書く (race で偽陽性)
