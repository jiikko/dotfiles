# 外部 CLI の stdout / stderr / exit code は分離して実測する

> **トリガー型ルール。** 外部コマンドの出力や終了コードを「判定材料」にして、設計の前提を書く /
> 実装を始めようとした瞬間に発動する。過去ログや既存の実測表を根拠に着手する場合も同じ。

## ルール

- **stdout / stderr / exit code を最初から別々に採る** (`cmd >out 2>err; echo $?`)。
  `2>&1` や `| head` を通した結果を「実測事実」として設計に書かない。混ぜた観測では
  **どの stream が判定材料か**を確定できない
- **rc は同じ行のコマンド置換で壊れる。先に変数へ退避してから使う**。
- **1 つのログに混ぜた 2 stream の「順序」も判定材料にしない**。stdout (buffered) と stderr (unbuffered) は
  flush のタイミングが違うので、同じログ上の前後関係は実際の発生順を表さない。時系列が要るなら**同一 stream に、
  テスト固有の識別子を付けて**出す (同名の行が別テストにもある前提で、関数名でスコープを切る)
- 記録には **CLI のバージョン・関係する環境変数・認証状態**を併記する。stream を分けただけでは
  条件の違う観測が並ぶだけで、再現可能な事実にならない
- **出力があっても契約を確定できない終了形** (timeout / signal / コマンド未発見 / 権限不足) を、
  正常な空出力と分けて扱う。途中まで出た文字列を正常な判定材料にしない
- 🚨 **`--help` の文面を、破壊的操作の「範囲」の根拠にしない。** help は要約であって契約ではなく、
  実行時の警告文・実挙動と食い違う。範囲を決めるなら**対象 0 件になる条件で 1 回実行して、
  その CLI 自身が何と言うか**を採る (それも stdout / stderr / rc を分けて採る)
- **非対話で走らせる予定のコマンドは、`</dev/null` で 1 回試してプロンプトの有無を先に実測する** (確認を求める CLI は EOF で何もせず rc=0 を返す。
  [`verify-execution-not-just-exit-code.md`](verify-execution-not-just-exit-code.md) の「確認を求める外部コマンド」節)
- **個別 CLI の現在仕様をこのルールに転記しない**。ルールが正本として持つのは**測定方法**だけで、
  「どの CLI が何をどこに出すか」は実装側のコメント (例: `src/glogx/cli_health.go`) か測定記録に
  一箇所だけ置く。両方に書くと CLI のバージョンが上がったときにルール側が黙って腐る
- **実 CLI の一時実行は「契約の独立確認」であって seam テストの代替ではない**。seam テストは
  「測定した契約が正しい」前提で判定ロジックと異常系を再現可能に守り、実 CLI の実行は
  **測定表そのものの読み違い**を検出する。役割が違うので、片方があるから他方が要らない、にならない
- 実 CLI を足すのは **副作用を隔離できる場合に限る**。認証情報・ネットワーク・Keychain・daemon・
  設定ファイルを隔離しきれない CLI では強行せず、**確認できていない範囲を明記する**
  (環境変数で HOME や設定ディレクトリを差し替えれば隔離できることが多いが、Keychain や
  daemon 経由の状態は差し替えられない)
  - **「測ると本物の設定を変える」で未実測にする前に、使っていない同種の資源 (IP の無い network service・予備の I/F・テスト用の
    アカウントやボリューム) で切り替え → 読む → 戻す、を探す**。隔離と言ってよいのは、その資源を今使っているものが無く、戻す手順が
    1 コマンドで前後の読み出しを diff して一致を確かめられ、他の資源に触れないときだけ。変える対象と戻し方を示して確認を取ってから打つ
- **外部ソース (upstream のソースコード・ドキュメント・WebFetch の要約) は「仮説」であって
  実測ではない。設計の前提にする前に、手元で再現できる実験を 1 本通す。**
  読んだ版と手元の版がずれる (upstream の `main` と使っている release)、要約が条件を落とす、
  といった形で普通に外れる。実測 2026-08-28: SwiftPM の `main` を根拠に「不正 archive は evict される」と
  書いたが、6.3.3 では残った。手元実験なら数分で確定した
  - **型定義・ドキュメントが「使える」と書く拡張点 (plugin / hook の API) も同じく仮説**。組織のポリシーや managed settings で無効化されうるので、
    設計に載せる前に、その環境で届くかを probe で確かめる
  - **それを読んで自分が書いた fake の振る舞いも同じく仮説**。外部 CLI の状態遷移 (再開・再起動・停止で id / pid / 時刻が
    どう変わるか) を模す fake は、書く前に本物で 1 回測る。**テストの fixture に「本物の出力」と書くなら、本物を呼んで取った値を貼る**
    (取れない値は「作った値」と書く。作った値は照合の規則の誤りを隠す。retro 687)
  - **外部の道具の意味論 (パターン・escape・照合) を自分で書き直すなら、ケースを書く前に、本物を oracle にして同じ入力を両方へ通す差分の検査を作り、テストに残す**。
    手で選んだケースは自分の理解の範囲しか試さず、レビューの周ごとに次の差が出る (retro 1015: Go の `path.Match` を zsh の glob へ写して 4 周)。
    oracle の選び方は `~/dotfiles/_claude/rules-checklists/mutation-verify-new-tests.md` の「差分テストの oracle」
  - **移植元・upstream の上限値や閾値も同じく仮説**。実行の形 (同期か非同期か・UI のスレッドか) が違う実装へ持ち込むときは、
    その上限ちょうどの入力で 1 回時間を測ってから採る
  - **外部の道具が出すログ・メッセージの 1 行も同じく仮説**。「remembered」「cached」「skipped」のような語は、どの範囲で
    (プロセスをまたぐか)・いつまで効くかを語らない。設計の前提にするなら、それを出しているコードか実験で範囲を確かめる
  - **外部の道具の出力 (log・stderr) から失敗の原因を読み取る判定は、文言を字面で探さず、出力の中の位置で決める**。位置の境界は
    出力を書いた側 (自分の driver) が控える (追記の前の長さ・自分が書いた区切り)。出力にはプロンプトの echo・実行したコマンドの出力・
    応答の本文が混ざり、どれも同じ文言を引用しうる。区切りの文字列で切っても、それ自体が引用される
- **外部のサービスに届く処理を周期的に起こすなら、サーバ側の rate limit を前提に、全ての呼び出し元 (全プロセス) の合計の
  頻度を 1 か所で持つ**。ローカルのコスト (トークン・CPU・時間) が小さいことは、サーバが許す頻度について何も言わない。
  呼び出し元ごとに周期を下げても、呼び出し元が増えれば合計が増える。既に別の経路で届いている値 (応答ヘッダ由来の値など) が
  あるなら、それを使ってサーバへ聞かない
