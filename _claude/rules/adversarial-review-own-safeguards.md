# 自分で作った「安全機構」は自己レビューで閉じない — 敵対的レビューを最終ゲートにする

> **トリガー型ルール。** 破壊的操作 (削除 / 上書き / 移動)、後始末、検査・ゲート・
> lint・CI チェックなど **「壊れないことを保証する側」のコードを自分で新設した瞬間**
> に発動する。「セルフレビューしたので大丈夫」と書きそうになったら必ず思い出す。

## ルール

- **自分が新設した安全機構は、自己レビューを通しただけで完了報告しない**。
  CLAUDE.md「レビュー方針」の敵対的レビュー (red team) を最終ゲートとして通す。
  外部レビュー (codex) が使えない状況でも、**観点を分けた別視点**を最低 2〜3 用意する
- **red team には「壊す手順を見つけろ。壊せなければ壊せなかったと明記しろ」**と指示する。
  「レビューして」では追認が返る
- 指摘は**実コードで裏を取ってから**採否を決める (敵対レビューの出力も無検閲で採用しない。
  作法の正本は `~/.claude/CLAUDE.md`「レビュー方針」)

## なぜ自己レビューでは足りないのか (2026-08-03 obaket の実測)

「テストが実ユーザーのデータを汚す」問題に対策 (後始末ヘルパー + 残骸検査スクリプト) を
入れ、自己レビューで 5 件直して「塞いだ」と報告した。その後 red team 3 観点に通したら、
**対策自体に自己レビューで 1 件も見つけられなかった欠陥**が出た:

- **検査スクリプトが、対象環境ではテストを 1 本も走らせずに `make test` を落とす**
  (grep 無マッチ + `pipefail`)。私の Mac では絶対に再現しない条件だった
- **検査が保存先の 1 系統しか見ていなかった** (E2E scope の 6011 ディレクトリ / 750 MB が野放し)
- **後始末ヘルパーが実ユーザーのデータを消しうる**経路 (掃除に形状ガードが無い)
- テスト側で直したのと**同じバグが production にもあった** (`SecItemDelete` を 1 回しか呼ばない
  → profile 削除で credential が Keychain に残留)

構造的な理由は 3 つ:

1. **方向が逆**。自己レビューは「意図どおり動くか」を確かめる。red team は「壊す手順を探す」。
   前者は**自分が置いた前提そのものを検証対象にしない**
2. **環境を変えない**。自分は「今の自分のマシンの状態」でしか試さない。空の環境 /
   コマンド失敗 / 権限なし / 並行実行は、意識的に作らないと絶対に踏まない
3. **書いた本人はコードを読むと意図が再生される**。他人は書いてある文字しか読まない

## やること

### 1. 環境を変えた実験を必ず 1 セット回す

安全機構は「異常時に正しく振る舞うこと」が本体なので、正常系だけ試しても意味がない。

| 作る条件 | 確かめること |
|---|---|
| **対象が 0 件 / 空のディレクトリ / 新品環境** | 落ちないか (grep 無マッチ・空配列・nil) |
| **依存コマンドが失敗する** (偽の実行ファイルを PATH 先頭に置く) | 「検査できなかった」を緑にしていないか |
| **権限が無い / ファイルが消えた** | 握り潰していないか |
| **並行して別プロセスが動いている** | 誤検出・誤削除しないか |

偽の `HOME` や一時ディレクトリでハーネスを組めば、実データを触らずに全部試せる。

### 2. 「沈黙 = 成功」になっていないか確認する

検査・ゲートは**検査できなかったときに緑を返さない**こと。`2>/dev/null` と
`|| true` は「失敗を無視する」と同義になっていないか、1 つずつ見る。

### 3. 同型バグの横展開を grep する

**テスト側で見つけた不具合は、production 側の同じ API 使用箇所を必ず grep する**
(逆も同じ)。2026-08-03 は test helper の `SecItemDelete` 単発呼び出しを直した後、
production の `deleteAllForService` にも同じバグが残っていた。直した本人が
「同じ間違いが別の場所にもあるのでは」と考えないのが典型的な見落とし。

### 4. その機構が CI で実際に走るか、同じ commit で確認する

手元で緑になっただけでは「退行を止められる」ことにならない。**新設した検査・ゲート・テストが
CI 環境で実際に実行されているか**を、同じ commit の中で確かめる。確かめ方は 1 つ:
**その機構が守っている修正を revert して、CI が赤くなるか**を見る (手元ではなく CI で)。

- 実例 (2026-08-21): 孤児サーバ回収の保護を pin する静的検査を新設したが、`lsof` の有無で
  skip する gate の**下**に置いてしまい CI で一度も走っていなかった。**修正を revert しても
  CI は緑**のままで、退行を止める力が 0 だった
- 典型的な埋没先: 依存コマンドの有無で skip する gate の下 / `if [ -t 1 ]` のような対話判定の
  内側 / CI では設定されない環境変数のゲート / 対象 0 件で早期 return するループの中
- ⚠️ 「CI で走っているか」は**ログに検査名が出ているかで確かめる**。テストスイート全体が緑
  なのは「走った」の証拠にならない (skip は緑に見える)

### 5. 観点を分けて別視点に投げる

1 人 (1 エージェント) で全部見ると注意が薄まる。**観点ごとに分ける**と、片方が
「削除の安全性」に集中している間に、もう片方が「検査の false green」に集中できる。
最低限の分け方: ①**壊す** (データ消失・回避経路) ②**素通りする** (false green・検査の無効化)
③**並行・中断** (途中終了・並列実行・非同期)。

## やらないこと

- ✗ 自分が作った安全機構を「セルフレビュー済み」で完了報告する
- ✗ 正常系だけ試して「動いた」と書く (異常系こそが安全機構の本体)
- ✗ `2>/dev/null` / `|| true` で失敗を握り潰したまま緑を返す
- ✗ テスト側のバグを直して、production の同型を grep せずに閉じる
- ✗ red team の指摘を裏取りせずにそのまま修正する (推測に基づく防御コードを足さない)
- ✗ 新設した検査が CI で走っているかを確かめずに「これで退行を止められる」と書く
