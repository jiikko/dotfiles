# 自分で作った「安全機構」は自己レビューで閉じない — 敵対的レビューを最終ゲートにする

> **トリガー型ルール。** 破壊的操作 (削除 / 上書き / 移動)、後始末、検査・ゲート・
> lint・CI チェック・**突合や allowlist のような「正当性の検証」**など
> **「壊れないことを保証する側」のコードを自分で新設した瞬間**に発動する。
> 「セルフレビューしたので大丈夫」と書きそうになったら必ず思い出す。
> **書き始める前に §0 の 2 つの問い**、書いた後に §1 以降を通す。

## ルール

- **自分が新設した安全機構は、自己レビューを通しただけで完了報告しない**。
  CLAUDE.md「レビュー方針」の敵対的レビュー (red team) を最終ゲートとして通す。
  外部レビュー (codex) が使えない状況でも、**観点を分けた別視点**を最低 2〜3 用意する
- **red team には「壊す手順を見つけろ。壊せなければ壊せなかったと明記しろ」**と指示する。
  「レビューして」では追認が返る
- 指摘は**実コードで裏を取ってから**採否を決める (敵対レビューの出力も無検閲で採用しない。
  作法の正本は `~/.claude/CLAUDE.md`「レビュー方針」)

## なぜ

起源: 2026-08-03 obaket の実測。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/adversarial-review-own-safeguards.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## やること

### 0. 機構を作る前に「作らずに済む構造」を 1 度問う

新設しようとした瞬間に発動する。安全機構は**それ自体が新しい失敗の入口**なので、
作らずに済むならその方が安い。問いは 2 つある。

#### 0-A. 掃除機構: 「そもそも発生させない構造」はないか

「残骸を消して回る」より「残骸を出さない」方が安全で、しかも往々にして安い。
掃除機構は本質的に**破壊的操作を新設する**ことなので、パターンを 1 つ間違えれば本物のデータを消す。

- 問い: 「この残骸は**どこで生まれるか**。生まれる側を差し替えれば掃除は要らないのでは?」
- 実例は rationale (obaket 688 C7: sweep を作る代わりに永続化層を in-memory へ差し替え、破壊的操作ゼロで済んだ)
- **同じ形の問題に前回下した結論を、無検証で持ち越さない**。上の実例では、直前に別の層で
  「fake 注入は具象型保持のせいで高い」と判断しており、その結論を credential 側にも
  そのまま当てはめて検討を飛ばしていた。**依存の型が違えばコストは変わる**

#### 0-B. 検証・突合・allowlist: 「その答えを既に出している経路」はないか

守り (「この対象は今も正当か」を確かめる判定) を足そうとしたとき、**その答えを既に出している
経路がコード内にあるなら、近似を書かずにその経路をもう一度通す**。

- 問い: 「この判定の答えは、どこかで既に計算されていないか。それを呼べないか?」
- 判定: 書こうとしている近似について **「本物の経路のどの部分を再現していないか」を列挙できるか**。
  列挙できないなら、それは近似ではなく**別の判定**を新設している (2 実装は必ず食い違う)
- **遅さは理由にならない**。本物を通すのが数秒かかっても、破壊的操作の正しさを近似や
  呼び出し元の申告値に預けるより安い。かかる時間は進捗表示の問題であって、正しさの問題ではない
- 実例は rationale (dotfiles 148: 削除対象の正当性を glob の突合で確かめ、走査側の guard を
  再現し損ねて「今は消してはいけない対象」を通した)
- 🚨 この形は [`mutation-verify-new-tests.md`](mutation-verify-new-tests.md) の
  「同じ判定・同じ結論を 2 箇所で別実装していないか」と同じだが、**あちらの発動点はテストを書くとき**。
  守りを足すときには効かなかった (実測 2026-09-03: ルールを読んでいたのに気づけなかった)

機構が要ると確定したら、以降の節 (異常系の実験 / false green / 敵対レビュー) を通す。

### 1. 環境を変えた実験を必ず 1 セット回す

安全機構は「異常時に正しく振る舞うこと」が本体なので、正常系だけ試しても意味がない。

| 作る条件 | 確かめること |
|---|---|
| **対象が 0 件 / 空のディレクトリ / 新品環境** | 落ちないか (grep 無マッチ・空配列・nil) |
| **依存コマンドが失敗する** (偽の実行ファイルを PATH 先頭に置く) | 「検査できなかった」を緑にしていないか |
| **権限が無い / ファイルが消えた** | 握り潰していないか |
| **並行して別プロセスが動いている** | 誤検出・誤削除しないか |

偽の `HOME` や一時ディレクトリでハーネスを組めば、実データを触らずに全部試せる。

### 2. 「沈黙 = 成功」になっていないか確認する

検査・ゲートは**検査できなかったときに緑を返さない**こと。`2>/dev/null` と
`|| true` は「失敗を無視する」と同義になっていないか、1 つずつ見る。

**テストハーネス自身の失敗も緑に畳まない**。「判定できなかった」は「合格」でも「不合格」でも
ない第 3 の結果として出す。畳むと、原因が「実装の誤り」に見える形で報告されて調査が逸れる。

- 安全側に倒す向きを間違えないこと: production の検査は「判定不能 → 拒否 (fail-closed)」へ
  倒すのが安全側だが、**テストの判定は「判定不能 → 専用の値 (harness-error 等)」**であって
  allow / deny のどちらかに丸めてはいけない (丸めると偽陽性か偽陰性のどちらかを必ず作る)
- **skip したことは「テスト自身の出力」に出す**。子プロセス (headless nvim 等) のログへ
  print するだけでは、そのログが**失敗時のみ表示される**設計だと沈黙と区別できない

**逆向きの沈黙 —「失敗はするが原因が消える」にも注意する。** `set -euo pipefail` の下で
`var=$(... | grep ...)` と書くと、**無マッチの時点で代入ごとスクリプトが死ぬ**。直後に
「抽出できなかったら FAIL を出す」ガードを置いていても**そこへ到達しない**ので、ガードは
飾りになり、出力ゼロの exit 1 だけが残る。CI のログは「テスト名の次が即 `make: ***`」に
なり、どの assert が落ちたのか分からない。

- 直し方: 抽出に `|| true` を付け、**空を受け取ってから明示的に FAIL を出す**方へ倒す
  (「判定できなかった」を専用の結果として出す、の一形態)

### 3. 同型バグの横展開を grep する

**テスト側で見つけた不具合は、production 側の同じ API 使用箇所を必ず grep する**
(逆も同じ)。直した本人が
「同じ間違いが別の場所にもあるのでは」と考えないのが典型的な見落とし。

### 4. その機構が CI で実際に走るか、同じ commit で確認する

手元で緑になっただけでは「退行を止められる」ことにならない。**新設した検査・ゲート・テストが
CI 環境で実際に実行されているか**を、同じ commit の中で確かめる。確かめ方は 1 つ:
**その機構が守っている修正を revert して、CI が赤くなるか**を見る (手元ではなく CI で)。

- 典型的な埋没先: 依存コマンドの有無で skip する gate の下 / `if [ -t 1 ]` のような対話判定の
  内側 / CI では設定されない環境変数のゲート / 対象 0 件で早期 return するループの中
- 🚨 「CI で走っているか」は**ログに検査名が出ているかで確かめる**。テストスイート全体が緑
  なのは「走った」の証拠にならない (skip は緑に見える)

### 5. 観点を分けて別視点に投げる

1 人 (1 エージェント) で全部見ると注意が薄まる。**観点ごとに分ける**と、片方が
「削除の安全性」に集中している間に、もう片方が「検査の false green」に集中できる。
最低限の分け方: ①**壊す** (データ消失・回避経路) ②**素通りする** (false green・検査の無効化)
③**並行・中断** (途中終了・並列実行・非同期)。

### 6. 自作の計測に予算を付けるなら「その計測が構造的に見落とすもの」を先に書く

閾値・予算ゲートは「測れている前提」で初めて意味を持つ。**何を測っていないかを先に
言語化し、見落としが致命的なら形に依存しない指標 (比・伸び率) を併置する**。

- 例 (fork 数の予算は直接の子しか数えない): 「比を測る」— 行数 10 倍で 1 tick の時間が何倍になるかを併置すると、fork が
  どんな形で隠れていても伸び率に出る (かつ比なので runner の速度差が打ち消える)
- 節 2 との違い: あちらは「検査が動かない」、こちらは「検査は動くが構造的に見えない」

### 7. 敵対レビューの指摘を直したら、直した差分にもう 1 周回してから閉じる

1 周目の「指摘なし」「壊せなかった」は**修正前のコード**に対する結果で、指摘への修正で
新設した機構 (橋渡し・分岐・後始末) はまだ誰にも攻められていない。**指摘への修正は新しい
安全機構**なので、本ルールの発動条件をそのまま満たす。「1 周目を通した」で閉じない。

- 実例は rationale (SnapTrim 237: 1 周目の P1 を塞ぐために新設した橋渡しそのものが、2 周目で P1 ×2 に崩れた)
- 2 周目は 1 周目の全文再走査でなくてよい。**「1 周目の指摘に対して何を新設したか」を列挙して
  攻め口として渡す** (上の例なら「橋渡しの中点変換・キャンセル配線・長さ未確定の非固定」)
- 打ち切り条件: 2 周目で採用する指摘が出なくなるまで。修正を入れた周は必ずもう 1 周ある

### 8. 字句 / 構文 gate は「脅威モデル」と「何を検出しないか」を先に書いてから閉じる (stopping rule)

lint / grep / 正規表現で「書いてはいけない形」を止める gate は、**typecheck が通る迂回が原理的に無限に
ある** (generic alias / 括弧 / 引数ラベル / 文脈型 `.init` / regex literal …)。「全部塞ぐ」を目標にすると
§7 の「修正した周はもう 1 周」が**収束しない**。

- 実例 (obaket 645 M6b, 2026-09-03): closure-based stream 構築の構文を検出する gate に、敵対レビューが
  r1〜r3 で毎回 6〜11 件の迂回を出した。r3 後に主規則を**構築側の構文ではなく使用側の効果**
  (`.yield` = backlog が生まれる操作) へ移し、r4 後に構文解析を削除して 2 規則へ縮約、
  脅威モデル (「うっかり書く典型形を止める。意図的迂回は review の責務」) をヘッダに書いて r6 で閉じた
- 手順: gate を書く**前に** ①脅威モデル (誰の・どの失敗を止めるか) ②「検出しない」と決めた形
  ③ その形を review で見る責務の所在、をヘッダと CLAUDE.md に書く。敵対レビューの迂回指摘は
  ②に該当するなら**採用せず記録**する (§7 の「もう 1 周」は①②の範囲内の指摘にだけ当てる)
- 判定: 迂回を直すたびに新しい迂回が出るなら、それは gate の穴ではなく**規則の軸が構文にある**印。
  構文 (どう書いたか) でなく効果 (何が起きるか) へ軸を移す

## やらないこと

- ✗ 掃除機構 (破壊的な後始末) を、残骸を発生させない構造を検討せずに新設する
- ✗ 既に答えを出している経路があるのに、守りのために近似の判定を新設する
  (「本物のどの部分を再現していないか」を列挙できないまま書く)
- ✗ 別の層で下した「その手は高い」の結論を、依存の型を確かめずに持ち越す
- ✗ 自分が作った安全機構を「セルフレビュー済み」で完了報告する
- ✗ 正常系だけ試して「動いた」と書く (異常系こそが安全機構の本体)
- ✗ `2>/dev/null` / `|| true` で失敗を握り潰したまま緑を返す
- ✗ テスト側のバグを直して、production の同型を grep せずに閉じる
- ✗ red team の指摘を裏取りせずにそのまま修正する (推測に基づく防御コードを足さない)
- ✗ 新設した検査が CI で走っているかを確かめずに「これで退行を止められる」と書く
- ✗ 予算ゲート・閾値を置くとき、その metric が**何を数えないか**を書かずに閾値だけ決める
- ✗ 敵対レビューの指摘を直した差分を、もう 1 周攻めさせずに「1 周目は通した」で閉じる
- ✗ 字句 / 構文 gate で「全部塞ぐ」を目標にし、脅威モデルと「検出しない形」を書かずに迂回指摘を直し続ける
