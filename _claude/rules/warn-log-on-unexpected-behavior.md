# 想定外の動作 (握り潰した失敗・起きないはずの分岐) は warn ログに出す

> **トリガー型ルール。** production のコードで、失敗を捨てる形 (`try?`・空の `catch`・`|| true`・`2>/dev/null`・best-effort) か、
> 正常系では通らない分岐 (`guard … else { return }` の断り・fallback・既定値への置き換え) を書こうとした瞬間に発動する。

## ルール

- **想定外の動作が起きたら warn 以上のログを出す**。処理を続けてよい (best-effort のまま) が、黙らない。
  例: キャッシュの保存に失敗した・保存を断った、設定が読めず既定値にした、来ないはずの値を捨てた
  (ユーザー指示 2026-10-30: ソフトウェアの運用に必須)
- ログには**どの断り・どの失敗か (理由)** と、追える識別子 (path・id) を入れる。「失敗した」だけでは原因を追えない。
  秘密 (認証情報・presigned URL) は入れない
- 断りの `guard` が複数あるなら、**どれで断ったかが区別できる**ように出す (理由ごとに文言か field を分ける)
- 正常に起きる分岐 (キャッシュの miss・取り消し・利用者の中止) は warn にしない。debug / info に留めるか出さない。
  warn が日常的に出ると誰も読まなくなる
- 同じ失敗が繰り返し起きうる経路 (ループ・毎描画) では、件数をまとめるか間引いて、ログを溢れさせない
- テストで振る舞いを固めるときは、warn が出ること (ログの sink を差し替えて記録する) も一緒に確かめる

`~/.claude/CLAUDE.md`「不具合対応の原則」の「追加ログは最後の手段」は、症状を追うための調査ログの話で、この rule と矛盾しない。
この rule は、壊れたときに最初から理由が見えるよう、捨てる失敗を運用のログに残すもの。
