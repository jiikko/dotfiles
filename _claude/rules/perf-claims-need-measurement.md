# 性能を主張するなら、実測値か「未実測である事実 + 実測の trigger」を残す

> **トリガー型ルール。** 変更の主題が性能のとき (issue の種別が `perf` / commit message が
> 「速くなる」「削減する」を主張するとき) に発動する。

## ルール

- **性能が主題の変更では、次のどちらかを成果物 (issue / commit message / コメント) に必ず残す**:
  - **実測値** (before / after と測定条件)
  - **「未実測である」という明示 + 測れない理由 + いつ測れるか (trigger)**
- **「削減した」「速くなった」を数字なしで書かない**
- 特に **「N 回 → 0 回」のような強い主張は、経路を最後まで追ってから書く**

## なぜ

起源: obaket issue 544、2026-08-26。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/perf-claims-need-measurement.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 測れないときの書き方

測定に実機・実サーバ・大規模データが要ることは普通にある。**そのときは黙って主張を書かず、
測れない理由と trigger を書く**:

> **実測はしていない** (SMB 実共有が要る)。adapter コメントの既存実測
> 「親 1,800 件までは 1 往復 = 追加コストほぼゼロ」に照らすと、親が小さい共有では
> 体感差はほぼ無いはず。効果が出るのは親ディレクトリが大きい共有。
> **trigger**: SMB で drop が遅いという報告が出たとき、before/after を実測する。

**既にコード / issue にある実測値に照らして効果の大きさを見積もる**のは有効
(上の例では「効果がほぼ無い条件」が既存コメントから読み取れた)。
見積もりは実測ではないので、**見積もりだと分かる形で書く**。

## やること / やらないこと

- ✓ 数字 (何が何回 / 何 ms から何になったか) を書く
- ✓ 測れないなら「未実測」+ 理由 + trigger を書く
- ✓ 強い主張 (N → 0) は経路を最後まで追ってから書く
- ✓ 既存の実測値があるなら、それに照らして効果の大きさを見積もる (見積もりと明示する)
- ✗ 数字なしで「削減した」「速くなった」と書く
- ✗ 変更した箇所だけ見て効果を数え、後続の処理を数え忘れる
