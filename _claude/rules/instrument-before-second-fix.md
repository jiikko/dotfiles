# 1 回目の修正仮説が外れたら、2 発目を打つ前に「観測を増やす」を選ぶ

## ルール

- **1 回目の仮説 fix が「効かなかった」と分かったら、2 つ目の修正をコードに打つ前に、観測手段 (ログ / 計測 / wire capture / A-B プローブ) を仕込んで「見えていない事実」を可視化する**
- **情報を増やさないまま 2 発目の blind fix を打つことを禁止する**。「次はこれで直るかも」は確度の低い推測の連鎖であり、当たっても理由が分からず、外れればコードが汚れる
- 「1 回外れた」= その不具合の実際の振る舞いが自分には見えていない証拠。次にやるべきは「別の修正案」ではなく「**何が見えていないかの観測**」

## なぜ

起源: obaket issue 227 Dropbox -1005, 2026-06-09。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/instrument-before-second-fix.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 「不具合対応の原則」(CLAUDE.md) との関係

矛盾しない。原則が戒めるのは「調査の**最初**に print を撒いて症状を追う」こと。本ルールは「構造的仮説の 1 回目が**外れた後**」に発動し、症状でなく **不変条件・状態遷移・境界 I/O・wire という構造** を観測する。原則の「必要なら『イベント／状態遷移』が観測できる設計にする」の発動タイミングを定めたもの。

## 手順 (1 回目の仮説 fix が外れたら)

1. STOP。2 つ目の修正案を考え始めない
2. 問いを変える: 「次に何を直すか」→「何が見えていないか」。失敗は結果しか見えていないか? 成功している隣接経路との差分のどこが観測できていないか? 「X は動く」という前提は今この環境で検証済みか?
3. **その経路に既存の観測が無いか先に grep する** (`grep -rn 'os_log\|NSLog\|Logger\|<自作 log facade>' <対象>`)。過去の調査で仕込まれた probe が残っていることが多く、**足すより先に読む方が速い**
   - **CI でしか出ない不具合は、新しい run を取る前に既存の失敗 run のログを全部取る**
     (`gh run view <id> --log-failed` / `--log`。GHA の retention は 90 日)。issue や過去の自分が
     「観測するには CI で 1 run 要る」と書いていても、**まずアーカイブを読む**。
     実測 2026-09-08 (swift-smbee 080): 4 run 分のログで、失敗テストの全数・実時間ギャップ・
     サーバ側ログまで揃い、**CI run 0 回で真因を確定したうえに issue の前提 3 点の誤りまで出た**
4. 無ければ観測手段を仕込む (下表)
5. 観測データで仮説を作り直す。データが仮説と矛盾したらデータを優先する
6. 前提が確定してから、はじめて 2 つ目の修正を打つ

| 観測したいもの | 手段 |
|---|---|
| 状態遷移 / イベント順序 | 構造化ログ (`print` でなく `NSLog`/`os_log`。tee pipe で block-buffered になり出ないため) |
| 境界の入出力 | request/response・引数/戻り値・契約違反を境界でログ |
| ネットワーク wire | `CFNETWORK_DIAGNOSTICS=3` / `URLSessionTaskMetrics` / proxy で byte 比較 |
| 成功 vs 失敗の差分 | 動いている隣接経路と同条件で A-B プローブ |
| 前提の再検証 | 「X は動く」を今この環境で実測し直す (過去ログの思い込みを排除) |
| 再現条件 | 毎回か / 初回からか / 特定入力か を切り分ける |
| **人の操作を待つ観測** | 時間窓で区切らず**追記型のログ**にする (「N 秒以内に押してください」は外れる)。🚨 `... \| sort -u >> log` のようにパイプ終端へ整列を置くと**ループが終わるまで 1 行も書き出されない** (実測 2026-09-05: 10 分間まったく記録されないログを作った) |
| **成功する入力と失敗する入力の差** | 同じ操作を **成功する入力**でも 1 回やり、何が違うかを言語化する (文字種 / 大文字小文字 / 正規化 / 長さ / provider / 空・1 件・多数)。「たまに動く」は乱数ではなく**分類**であることが多い |

## 🚨 観測対象が**消える操作**の前に観測を採る (kill / 再起動 / 削除 / 再インストール)

異常なプロセス・壊れた状態が**生きているうちだけ**取れる情報がある。消してしまうと
二度と同じ状態を作れない (再現手順が分かっていても、同じ育ち方をするとは限らない)。

- 発動点: **異常なプロセスを見つけて `kill` / `pkill` / 再起動しようとした瞬間**
  (本ルールの他の節が「修正の後」なのに対し、これは**破壊の前**)
- 最低限: `sample <pid>` (スタックとスレッド一覧) / `ps eww <pid>` (env) / RSS と CPU と起動時刻
- 🚨 **観測値のうち、自分の仮説で説明できていないものを列挙する**。「原因はこれ」と書く前に
  「この仮説で CPU / RSS / スレッド数は全部説明が付くか」を 1 度問う。**説明できない値が
  残っているのに気づかない**のが典型的な見落とし

## 手元で再現しないなら、**動いているプロセスの env / cwd / 起動時刻**を読む

「私の環境では再現しません」を 2 回言う前に発動する。

- **設定ファイルの内容と、動いているプロセスの環境は一致しない**。長命なシェル・tmux ペイン・
  エディタは、設定へ追記した後に起動していなければその値を持っていない
- ファイルを `cat` しても永遠に分からない。`ps eww <pid>` で**実プロセスの env** を読む
- 起動時刻 (`ps -o lstart`) と設定の更新時刻を突き合わせると、この形かどうかが 1 発で分かる
- 🚨 **同じセッションで既に使った手を、隣の問題にも当てる**。片方で `ps eww` を使って
  原因を特定したのに、もう片方では使わない、が実際に起きる
- 🚨 **バイナリ・パッケージを直接測るときは、まず「今走っている実体はどれか」を確かめる**
  (`ps` の実行パス / `which -a` / `--version`)。版が同居する環境で `find` が最初に当てた古い install を
  数えると**結論が逆になる** (実測 2026-09-10 dotfiles 343: nodenv 配下 3 版のうち古い 2.1.17 で
  enum を数えて 4 値、走っていた 2.1.266 は 14 値。そのまま報告すれば「縮んだ」になっていた)

## 観測後の判断

- 真因を指したら → 観測駆動で 1 発修正
- まだ不明 / framework 内部挙動 → [`escalate-to-forge-after-failed-tries.md`](escalate-to-forge-after-failed-tries.md) へ。観測データを手土産にすると専門家の収束が段違いに速い (観測なしで投げると専門家も同じ app 層ログから推測することになる)
- 観測自体を仕込むのが重い (実機専用 / 再現困難) → ユーザーに具体的な観測手順を渡す (blind fix を投げ続けるより誠実)

## 「何度直しても直らない」と言われたら、まず**非対称**を特定する

同じ症状の**再修正**を頼まれたときは、1 回目・2 回目が外れているのと同じ状態なので本ルールが
発動している。このとき最初にやるのは修正案でも新しい観測でもなく、
**「いつ動いて、いつ動かないか」を分ける軸の特定**。

- 「たまに動く」はタイミング仮説を無限にもっともらしくする。**分類 (入力の形) で説明できないか**を
  先に潰す。説明できたなら、タイミング側をいくら直しても原理的に直らない
- 成功する入力を 1 つ作って比べるのが最短。手元で再現しないなら、ユーザーに
  「動いたケースと動かなかったケースの具体名」を聞く (「たまに」で止めない)

## 1 回目から観測を入れてよい場合

本ルールは「1 回目が外れたら」を発動条件にしているが、**着手時点で「なぜ壊れているか分かって
いない」自覚があるなら、1 回目の修正と同時に観測を仕込んでよい**。判定は「修正が外れたとき、
次に何を見ればよいか答えられるか」。答えられないなら観測が足りていない。

**観測を人に依頼したなら、その結果が返る前に修正を commit しない。** 返る前に出したいなら、
**壊れ方の特定に依存しない直し方** (壊れやすい前提そのものを外す) を採る。診断コマンドを issue に
書いただけで先に commit すると、「治っていない」の往復が 1 回増える (実測 2026-09-04 av1ify 255)。

## 例外 (発動不要)

- typo / build error / lint のような結果が自明なミス
- 以前直したパターンの完全な再発 (観測済みの既知問題)
- ユーザーが特定アクションを明示している場合
- 1 回目がそもそも検証 (仮説の確認) であって修正でない場合

## やること / やらないこと

- ✓ 1 回目が外れたら 2 発目の前に観測を仕込む (構造を見る設計で)
- ✓ 観測を足す前に、その経路の既存の観測を grep する (過去の調査の probe が残っていることが多い)
- ✓ 「何度直しても直らない」報告では、成功する入力と失敗する入力の**非対称**を先に特定する
- ✓ 前提を今この環境で実測し直す
- ✓ 効かなかった修正は revert する（CLAUDE.md「不具合対応の原則」の一項。ここでは再掲であり一次情報は CLAUDE.md）
- ✓ 異常なプロセスを kill する前に `sample` / `ps eww` / RSS・CPU・起動時刻を採る
- ✓ 「私の環境では再現しない」と言う前に、動いている実プロセスの env / 起動時刻を読む
- ✗ 情報を増やさず 2 発目・3 発目の blind fix を打つ
- ✗ 仮説で説明できていない観測値が残っているのに、原因を確定したと書く
- ✗ 古いログ・別条件の結果を「現環境でも真」と思い込む
- ✗ 症状を場当たりに追う print の乱射
