# 多数の view が要素ごとに読む状態は、辞書・集合の 1 プロパティで観測させない (Swift)

> **トリガー型ルール。** 一覧の行・grid のカードのように、同じ種類の view が何十も並びうる画面で、各 view が `@Observable` の型から
> 自分の要素 (identity・key) の分だけを読む状態を足す・変えるときに発動する。並ぶ数が件数とともに増える一覧なら、今の数が少なくても発動する。
> 並ぶ数が固定の数個の画面では要らない。

## ルール

- **値の更新で、view が読む辞書・集合のプロパティそのものに書かない**。Observation はプロパティ単位で追跡するので、`dict[key]` や `set.contains(id)` を
  body で読むと、どの key の書き込みでも読んでいる全部の view が評価し直される。観測させてよいのは次のどちらか
  - キーの出入りだけを辞書で観測させ、値は要素ごとの `@Observable` の参照型に持つ (辞書への代入はキーの集合が変わったときだけ。読み取りで要素を作るなら、次の形にする)
  - 要素ごとの `@Observable` の参照型 (枠) だけを観測させ、持ち主の辞書は `@ObservationIgnored` か非 `@Observable` にする。
    まだ無い key を読む view のために読み取りで空の枠を作るなら、この形にする。観測される辞書へ body の中で書くと、その辞書を読む全部の view を評価し直す
- 枠が別の正本 (永続化した集合など) の写しなら、正本の didSet などの 1 か所だけが枠に書く。枠そのものが正本なら、この項は要らない。
  読み取りで枠を作るときの初期値は、正本の観測されない保存先から取る (観測される集合を読むと、その view が集合全体に依存し直す)
- 枠の辞書は、上限と捨てる時機を決めてから足す。view の読み取りで枠を作るなら、まだ値の無い枠の数にも上限を置く
- **枠を辞書から捨てるとき、その枠を読む view がまだ生きうるなら、view に届く変化を書いてから捨てる**。外れた枠を観測し続ける view は、
  同じ key への後の書き込みに気づかない。読む view が先に消えると言える (同じ更新で一覧から外れる) なら、書かずに捨ててよい
- 書く値は必ず変わる値にする。`@Observable` のマクロは、少なくとも `Equatable` な値で等しい値を書いたときと、参照型の同じ instance を書いたときに
  通知を省く。値が足りない枠 (Bool・Optional) には、捨てたことを表す状態 (`.removed` など) を足す
- 要素ごとにすると、body の再評価に頼っていた副作用 (LRU の recency の更新など) が起きなくなる。分ける前にそれを挙げ、別の経路で守る
- 1 要素の値を書き換えて、評価し直す view がその 1 つだけかをテストで確かめる (view の body の評価回数か、`withObservationTracking` で他の要素の読み取りが
  発火しないこと)
