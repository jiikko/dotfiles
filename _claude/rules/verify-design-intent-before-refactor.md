# リファクタ / 複雑度改善を提案する前に「既に意図的に選ばれた設計」でないか確認する

> **トリガー型ルール。** 「このコード複雑だな / 消したい / 分解したい / proxy 多すぎ」と
> *第一印象で構造を変えたくなった瞬間* にだけ発動する。逆にそう感じたら、手を動かす前に必ず発動させる。

## ルール

「複雑すぎる / 分解すべき / facade が肥大化」と判断する前に、提案・実装より先に以下を確認する:

1. [ ] **ドキュメント (CLAUDE.md / README / docstring)** に「意図的にこうした」と明記されていないか。
       対象ディレクトリだけでなく**一階層上の共通規約** (親の README 等) も読む — そこに
       「任意」「どちらでもよい」と書かれていれば、規約違反ではなく選択肢の一方になる
2. [ ] **既存 issue / PR / 設計メモ (完了済み含む)** で同じ分解が既に検討され「やらない」と決定されていないか
3. [ ] **実 callsite** を grep して、提案が breaking change にならないか
4. [ ] **可視性 (private / internal)** を確認して、「API を変えずに論理分割」が本当に可能か
5. [ ] **行数ではなく、分割で何が良くなるか**で測る (基準は下節の 3 問)。大ファイルが domain 複雑度 (仕様・プロトコル・状態機械の写像) 由来なら、分解は downgrade になりうる

1 つでも「意図的」「判断済」が見つかったら、**提案を取り下げるか、その制約を踏まえて scope を絞る**。

加えて:

- **「共通部を 1 箇所へ集める」提案は、移す前に「その参照機構が実際に展開されるか」を実測する**。
  展開されない参照先へ移すのは**削除と同じ**で、しかも移した本人にもレビューにも
  「ファイルは在る」ので気づけない
- **speculative refactor (先回り分解) より「実変更 trigger 待ち」を default にする**。「将来困りそうだから今分解」ではなく、trigger (「次にこの facade を触る機能追加が来た時」「N 個目の sub-component を足す時」等) を明記して実需要まで構造を凍結する
- 改善の**効能を誇張しない**。「構造的に防止できる」と書く前に全経路を防げるか確認する (一部しか防げないなら「探索範囲を局所化できる。ただし〜は手動更新が残る」と正確に書く)

## リファクタリングの目的は「複雑性を下げる」こと。行数分割はリファクタではない

「行数が多い」を根拠に**ファイル / クラスを単純に分けるのはリファクタリングではない**。ファイル分割は複雑性を別の場所へ **「移動」** するだけで **「削減」** しない。

- **薄い委譲・状態を持たない・ドメイン間の結合が無い**コードは、行数が多くても分割で複雑性が下がらない (むしろ「どのファイルにあるか」の探索コストとファイル数が増えてわずかに悪化しうる)。例: 各メソッドが `getAPI() → null チェック → 委譲` だけの bridge/facade を、ドメイン別ファイルに割っても認知負荷も結合も変わらない
- 「過度な行数」は**予兆の入口にすぎない**。巨大なクラス・ファイルを分割するかは、分割の後に次の 3 つが**実際に良くなるか**で判断する。どれも良くならないなら分割しない
  1. **責務を分離できるか**: 変更理由の違うものが別の単位に分かれ、片方の変更がもう片方へ波及しなくなるか
  2. **今後の改修で探すコストが下がるか**: 変更箇所にたどり着くまでの jump 数と、1 つの変更で触る箇所の数が減るか
  3. **参照範囲が局所に閉じるか**: 1 つの変更を理解するために読む範囲 (呼び出し元・共有状態・依存先) が、分けた単位の中に収まるか
- 3 問のどれかが良くなる分割案でも、採る前に分けた後の形を確かめる
  - **依存の向き**: 分けた単位どうしが循環依存にならないか。変わりにくい側が変わりやすい側へ依存していないか
  - **名前が付くか**: 分けた単位に Manager / Helper / Util 以外の、責務を言い表す名前が付くか。付かないなら境界が責務に沿っていない
  - **公開面が狭いか**: 呼び出し側が内部の手順 (呼ぶ順序・中間状態) を知らずに使えるか。知らないと使えないなら、結合を単位の外へ移しただけ
- 単純な行数分割 (量の分散) も**無益ではないが優先度は低い**。優先すべきは複雑性が実際に下がる変更 = **重複除去 / 責務分離 / 結合の切断 / 状態の局所化**
- **要件・受け入れ条件・完了判定にも行数を書かない**。共通化は typed API と doc の分だけ行数が**増える**のが普通で、行数を要件に書くと複雑性が下がった変更が「未達」になる。
  測るなら「同じ状態機械の実装数」「変更時の touch 箇所数」「依存の数」で書く
- 「分割しない」と判断したら、その理由を**当該コードにコメントで残す** ([`pending-issue-rationale-in-code.md`](pending-issue-rationale-in-code.md))。将来の audit / レビューで「God Facade だから分割しろ」のような同じ誤指摘が再生成されるのを即棄却できる

## 「自律改善」(CLAUDE.md) との境界

自律改善は「**触っている範囲**の明らかな劣化 (重複・到達不能・責務混在) を変更と同時に直す」。本ルールが止めるのは「**依頼と無関係に**第一印象で先回り分解する」こと。

| 状況 | どちら |
|---|---|
| 変更した関数内の到達不能コード / 自分の変更で死んだ分岐 | 自律改善 (消す) |
| 別ファイル・別レイヤーの似たコード / 「ついでにこの大きいファイルも割りたい」 | 本ルール (止まる・trigger 待ち) |

迷ったら「**今の依頼で必然的に触る範囲か?**」で切る。必然なら改善、「ついで」なら凍結。

## やること / やらないこと

- ✓ 提案前にドキュメント / 既存 issue / callsite / 可視性を確認
- ✓ speculative refactor は trigger を明記して watch に回す
- ✓ 複雑度評価 / refactor 提案は外部レビュー (codex 等) を通す
- ✗ ドキュメントに「意図的」とある構造を「複雑」と判定して分解提案
- ✗ 既存 issue で「やらない」と決定済の分解を逆転提案
- ✗ 「API 変えず論理分割」を可視性確認なしで主張
- ✗ 効能の誇張 (「構造的防止」と書いて一部しか防げない)

- `~/.claude/CLAUDE.md`「レビュー方針」 — refactor 提案も外部レビューに通す
