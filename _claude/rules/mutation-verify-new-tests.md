# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する

> **トリガー型ルール。** 回帰テストを書き終えて green を確認した瞬間、
> または「このテストで守られている」と commit message / doc に書こうとした瞬間に発動する。

## ルール

- **新規追加・変更したテストは、その不変条件を壊す変更を 1 つ実際に適用し、
  red になることを確認してから commit する**。確認した変異の内容を commit message に残す
- **「テスト green」を検証の証拠として報告しない**。green は「その書き方では壊せなかった」に過ぎない
- 変異させて **green のままだったテストは、書き直すか捨てる**
- **green のままの変異を「等価変異 (到達不能)」と判定するときは、変異箇所に到達する全経路を
  列挙してから言う**。テスト名から挙動を推測しない
- 🚨 **既存の assert を「何も検査していない」として消すときも、消す前に変異を 1 本当てる**
  (当てずに vacuous と断じた assert が、実は唯一の上限だったことがある)

## なぜ

起源: obaket issue 454、2026-08-03。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/mutation-verify-new-tests.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 手順 (特別なツールは要らない)

```
0. **変異を当てる前に baseline が green であることを測る**
1. 不変条件を壊す最小の変異を当てる
   (guard 削除 / 定数の反転 / ?? 0 で埋める / filter 条件の除去 など)
1.5. **その変異が実際にビルドできたことを確認する**
1.6. **変異の diff を目視し、意図した箇所だけが変わっていて、その行が対象テストの実行経路上にあることを確認する**
2. 対象テストだけ実行して red を確認する
3. 変異を revert して green に戻す
4. commit message に「どの変異で red を確認したか」を書く
```

🚨 **手で組む前に `bin/mutate-verify` を見る** (issue 408)。下の「復元の作法」と手順 0〜3 の guard
(baseline green / 当たったか / 誤ファイル / 構文 = 第 3 の結果 / zero execution / red の帰属 /
未コミット差分があれば拒否) を機械で強制する。使い捨て worktree の中だけで変異させるので作業ツリーを触らず、
未コミットの変更は持ち込むので「今書いたテスト」も検証できる。変異の当て方 (`--apply`) は呼び出し側の責任。
射程の外 (assert の誤り・観測設計・fixture / seam) はスクリプト冒頭に書いてある。
🚨 rc=0 が保証するのは「`--expect` の検査が落ちた」**まで**で、「それだけが落ちた」ではない。
表示される baseline との出力の差 (消えた行・増えた行) で巻き添えを見てから採用する。

- 🚨 **手順 0**: baseline が red のまま変異を当てると、red の増減が変異由来か区別できない
- 🚨 **並行性を扱う新規テストは、3 回連続 green を確認してから commit する** (1 回の green は flaky を素通しし、その後の変異判定も汚染する)
- 🚨 **手順 1.5**: 変異がコンパイルできていないと runner は **stale build** を走らせて green を返し、
  効いているテストを弱いと誤診する。ビルド段の成否は**テスト実行とは別に見る**
  (`swift build --build-tests` / `go build ./...` / `bash -n`)。ビルド不能は
  **red でも green でもない第 3 の結果**として扱い、当て直す
- 🚨 **手順 1.6**: 変異は当てたつもりの形になっていないことがある (置換の `$` はシェルと perl の両方で
  展開されうる)。別の箇所が壊れても red は出るし、コメント行に当たれば緑になる。**赤か緑かを読む前に diff を読む**
  - **構文が通ることは挙動中立を意味しない**。変異が出力や副作用を足していたら、その red はテストの検知力を
    何も証明しない (zsh の同一スコープでの 2 度目の `local` は変数を stdout へ出す)
- 🚨 **手順 1.5 / 1.6 と未コミット差分の拒否は、人が覚えるのをやめ変異ハーネス側に guard として置く**
  (`diff -q` で当たったか、`bash -n` / `zsh -n` / `go build` で構文、`git status --porcelain` が空か)
- 🚨 **モジュール境界を跨ぐ定数・型を変異させたら、クリーンビルドを挟む**。部分ビルドは 1 実行の中に
  新旧 2 つの値を作り、ビルドは成功する。①クリーンビルド ②フルログ ③実行 0 件を第 3 の結果に
  ④diff と参照カウントの目視、を揃える
- 🚨 **判定式を「rc が変異前と違うか」で書かない** (3 値を 2 値に丸め、壊れた変異を「検知した」と出す)。
  構文を先に確認し、変異前と変異後の rc を両方名指しで見る
- 🚨 **red/green は失敗行の件数ではなく、runner の実行サマリ行で判定する** (件数は「0 件実行」と
  「全部 pass」を区別できない)。取れなければ第 3 の結果にする (どのテストが落ちたかを読む列挙は別用途で、禁じていない)。runner の文言は判定スクリプト側のコメントを正本にし、ここへ転記しない
- 🚨 **red を確認したら、その red を成立させていた入力が HEAD にまだ在るかを見る**。同じ commit の別の修正が
  根拠の fixture を消していると、「変異で確認済み」は変異体については真、HEAD については偽になる。
  **前回 red だった変異が green に転じたとき**も、実装より先にテスト本体・fixture が巻き添えで消えていないか疑う

🚨 **復元の作法** (`bin/mutate-verify` を使えば下は構造的に起きない):

- **`cp` のバックアップを世代で持たない** (古い世代を書き戻して配線が消える)。作業ツリーで変異させるなら
  1 ファイルにつき 1 世代に限り、当てる前後で `git diff --stat` を読む
- **`git checkout -- <path>` を常用手順にしない**。未コミットの変更 (自分の途中作業・並行セッションの作業) を
  まとめて消す (commit 済みを確認しても、確認から実行までの間に他セッションが書けば同じ)。🚨 **発動点は「レビュー指摘を直した直後」** — 直後は必ず未コミットなので、
  **指摘を直したら変異の前に commit する** (WIP でよい)
- **worktree でも `git checkout --` は安全にならない** (その worktree の自分の未コミット変更は消え、旧実装が
  通れば green のまま気づけない)。変異対象に未コミット変更があるなら一度 commit してから当てる
- **バックアップと復元は絶対パスで行う** (`trap` はスクリプトが `cd` した後に走る)
- **変異は使い捨て worktree で当てる** (正本は `~/.claude/skills/codex-drive/SKILL.md` の `[3.8]`)。
  skill を使わない手動の変異検証でも同じ
- **新規 (untracked) ファイルは `git checkout --` で戻せない** (worktree にも乗らない)。`cp` で 1 世代控え、復元後に
  `grep -c MUTANT` 等でマーカー残骸ゼロを確認する
- **破壊的な clean を検証手順に入れたら、報告前に `git status` で追跡ファイルと lock ファイル**
  (`Package.resolved` 等) **の変化を確認する**。変わっていたら pin を戻して測り直す

🚨 **A-B のケース間で状態を共有しない**。`HOME` / `ZDOTDIR` / 一時ディレクトリはケースごとに新規作成し、
測る対象が環境変数なら親から落とす (`env -u <名前>`)。矛盾する結果が出たら、まずハーネスの隔離を疑う。

🚨 **共有 working tree で変異を当てない — 並行の相手は事前には見えない**
([`parallel-write-agents-need-worktree-isolation.md`](parallel-write-agents-need-worktree-isolation.md) は
自分が起こした並行だけを対象にする)。他人の変異が自分の pathspec commit に入る / 変異中のファイルを読んだ
レビューが実在しないコードを前提にする。**既定は worktree**。共有 tree で当てるなら変異中は一切 commit しない。

## 変異は「production の機構を戻す」形にする

変異が red を出しても、それは**その変異を検出できた**だけ。**変異の当て方自体が偽物になりうる。**

- ✗ 期待している文字列・値を直接埋め込む / `return` を足して早期に抜ける・定数を返す
- ✓ **削除・最適化した機構をそのまま戻す** (呼び出しを復活させる / 旧実装を貼り直す)

判定: **「この変異は、実際に起こりうる退行の形か?」**

**当てる前に「この変異で最初に落ちるのはどの assert か」を予測し、実行後に一致を確かめる。**
別の既存 assert が先に落ちているなら、今回書いたテストの検知力は何も証明できていないので、先に落ちうる assert を潰した形の変異を設計する。
予測と一致しなければ、変異かテストのどちらかが的を外している。
**その assert が見ている量は、壊れたときに動くのか**も先に問う (総数・行数・存在の否定は動かないことが多い)。

## 検査の不在を主張するときの裏取り

「〜を検出するテストが無い」「callsite が 0 件」のような**不在の主張**は、テストを書く / 書かない判断を決める。green と同じ重さで裏を取る。

- **grep 1 本で確定させない** (テストはリテラル値で書かれていることがある)。確定させる唯一の方法は
  **変異を当てて green を見ること**。やっていないなら「未検証」と書く
- 「手段が無い」型の主張は、**同じ問題を既に解いている既存テストが repo に無いか**を見る。見送り判断の根拠も、
  逆を書いている doc / テストコメントを探してから断定する
- 🚨 **2 者が独立に数えて一致しても、数え方が同じなら独立ではない**。独立させるのは主体ではなく**方法**。
  件数や不在が設計・削除の根拠になるときは、方法を変えた列挙を最低 2 通り用意し、食い違いを精読する
  (走査 / 到達可能性 / API 網羅 / 実行時の観測)

## 適用範囲

- ✓ バグ修正の回帰テスト / 不変条件を主張するテスト / 「これで守られている」と書くテスト
- ✗ 機械的なリネーム・fixture 追加・既存テストの分割など、新しい主張を伴わない変更

## よくある「守っていないテスト」の形 (変異前に自問する)

**assert と期待値**
- assert が無い / 常に真になる assert を書いていないか。期待値を production と同じ式・定数から作っていないか
- 前提の assert が**停止しない**形になっていないか (`#expect` は記録するだけ。停止させるなら `#require`)
- **逆向き: 前提の guard が `Issue.record; return` で抜けて、後ろの副作用 assert を丸ごと飛ばしていないか**。副作用の assert は guard の手前か、guard に依存しない形に置く
- 🚨 **shell で、条件文脈 (`if` / `||` / `&&` / `!`) から呼ばれる関数の中に assert を置いていないか**。そこでは `set -e` も
  ERR trap も効かず、assert の失敗は誰にも拾われない。fake / callback の中では値を**記録するだけ**にし、比較は条件文脈の外で行う
- **属性 (色・フラグ・クラス) の存在だけを見ていないか**。属性 + それが付く対象まで見る
- **文字列を部分一致で pin していないか**。コマンド・書式・生成物のように全体が契約なら**完全一致**で固定する
- 🚨 **`grep` に複数行のパターンを渡していないか** (行ごとの OR なので 1 行目が一致すれば通る)。切り出して文字列比較にする
- 🚨 **grep で配線を pin したなら、その grep 自身の行 (やコメント) が pin を満たしていないか** (行頭アンカーで解決する)

**fixture と前提**
- 差が出ない状況しか作っていないか (要素 1 個、空集合、恒等条件)
- **fixture を「検査対象が壊れない形」に選んでいないか**。値だけでなく**並び順**と**大きさ**でも検出力は消える
  - 順序依存の選択を検査するなら**正解を先頭以外へ置き**、production の並びと逆順の両方を回す
  - 表示のテストは**実在する最大級の入力**で見る (幅で切る実装は短い fixture では切られた先が検査されない)
  - 🚨 「fixture を短くした」「並びを変えた」理由をコメントに書いていたら黄信号
  - 性能・確保のガードの変異が緑なら、その退行が今の toolchain で測定値を変える入力域を実測する
    (標準ライブラリの最適化で、ある域では退行が等価変異になる)
- **取り違えを検出したい 2 つの値を、fixture で同じ値にしていないか**。2 つを別々の数にしてから変異を当てる
- **fixture が、判定に使うコマンドの出力に現れる形になっているか** (`git status --porcelain` は未追跡
  ディレクトリを 1 行に畳むので、fixture は一度 commit してから変更する / 検査が `--name-only` を読むのに fixture を
  ワークツリーにだけ置く / 検査が stdout を見るのに fixture が stderr に出す)
- **fixture は「退行したら見えるようになる場所」に置いているか** (修正後の設計でしか読まれない場所は、
  退行からは最初から不可視)
- **フィクスチャが production の初期状態と違わないか** (違うとその経路を構造的に一度も踏まない)。並行・レースのテストでは、呼び出し元がどの状態から始まるかを実装側で確認してから形状を決める
- 「拒否する例」が、実装の拡張で静かに成立しなくなっていないか。allowlist / 収録表を増やす変更では、
  **その表の否定例も同じ commit で見直す**

**到達しているか**
- 検証したいコードが本当に実行されているか (closure / 環境変数ゲートの内側は走らない)
- **先に効く別の防御が影になって、狙った分岐に到達していないか**。本番で起きる順序を再現する
- **前提が「早期 return で素通りしていないか」を assert しているか**。fixture を作った直後に狙った状態を Fatal で固定する
  - 🚨 素通りは変異 1 本だと red の陰に隠れる。**別の場所を壊す 2 本目**で「そのケースだけ緑」を見て初めて分かる
- 🚨 **処理を遅延・非同期 (返したコマンドの中・goroutine・次の tick) へ移したら、「起きないこと」を見ている assert を全部洗う**。
  遅延した先を走らせないまま「呼ばれていない」を見ると、実装を壊しても緑のまま (実測 2026-09-24 pro-con: attach を裏に回したとき 3 本がこの形になりかけた)
- **待機ループが本当に待っているか** (Swift の `for … where 条件` は待たずに飛ばす。while で書き、待つ対象が始まったことを先に assert する)
- **入れ子の UI / 多層の構造で「層の中の不変条件」を主張したなら、テストは*外側の入口*から書いているか**。
  判定: その不変条件を破る入力を、ユーザーが実際に触る入口から入れて red になるか
- **走査・突合系のテストは「実際に何件を見ているか」を数えてから根拠にする**。canary の下限も実数に近づける

**red の読み方**
- **テーブル駆動 / サブテストなら、変異で「全ケース」が red になるか**。ケース名ごとの pass/fail 一覧で判定する。
  🚨 鍵は **package 名 + ケース名** (同名テストの PASS が red を上書きする)
- 🚨 **変異の red は「ケース名 × どの assert が出したか」まで特定して初めて証拠になる**。
  「このテストだけが red になる変異」を特定できないテストは、他と重複していると扱う
  - 🚨 **判定する側の道具も壊れる** (`grep -E '^\s+--- FAIL'` はインデントなしの `--- FAIL:` を落とす)。判定式は実測で確かめる
- **fake の「止まる回数」が、変異側の呼び出し回数を想定しているか** (「初回だけ block」は 2 回目を足す変異に素通りされる)

**観測の設計**
- **その観測は、変異の有無で違う値を出すか** (「差が出ない状況」の一般形)
  - 主張が**副作用の時点**なら状態の観測では固定できない。その時点で副作用が起きたら失敗する環境を挟む (PATH を空にする / fake に reject させる)
  - 主張が**ガード**で、守る入力が生成経路から出てこないなら、計算部を関数に切り出して値を直接与えるテストにする
  - 主張が**「画面でこう見える」**なら、状態ではなく**描画結果 (出力行)** から読む
- 🚨 **外部コマンドのエラーメッセージの文言で判定していないか**。文言はロケールや版で変わり、変わると検査は緑のまま空振りする
  (手元だけ・CI だけの偽の緑になる)。何が起きたか (呼び出しの記録・ファイル・exit code) で判定する。文言しか手段が無いなら
  `LC_ALL=C` を固定し、その理由をコメントに残す
- 🚨 **逆向きの問い: その観測値が進んだのに、目的が達成されていない状態を作れるか** (十分性)。作れるなら
  単独の合否基準にしない (複数の観測を AND で取る)。完了・成功を表す観測値を自分で新設したときに特に効く
- **本番と同じ制約の下で観測しているか** (timeout / メモリ上限 / 実行時間の壁 / 権限)
- **資源の上限 (枠・プール・カウンタ) を新設したら、「枠が返る列」を通すテストも置く**。返す側を消す変異が red になるまで
- **観測点は副作用の後に置く** (前に置くと意図の回数を数える)
  - 🚨 **guard の「前」にしか割り込めない seam では、その guard は検査できない**。seam は守りたい窓の内側に置く
  - 🚨 置く基準は「自分の fixture で修正を観測できるか」ではなく「退行が現れるか」。
    **issue の症状そのものを再現する変異が red になるか**を 1 本当てて確かめる
- 🚨 **生死・存在を `kill(pid, 0)` やプロセスの有無で判定しない** (ゾンビにも fork 直後にも成功する)。`Wait()` の完了・子が書く成果物で見る
- 🚨 **「案内した先」は文字列ではなく実行で確かめる** (エラーメッセージが名指ししたコマンドをテストから走らせ、rc と出力を assert する)
- **窓がミリ秒なら人為的に広げて決定論にする** (広げた条件で A-B (ガード有無) を取ると変異の当たりも安定する)

**実装の二重化・配線**
- 🚨 **検査を 1 つ足したら、隣接する既存の検査の変異を当て直したか**。後から足した検査が既存の最終状態を肩代わりすると、
  既存のテストは無検査になる。観測点を最終状態から「後段へ進まないこと」へ移す
  (段を同時に書くときは [`adversarial-review-own-safeguards.md`](adversarial-review-own-safeguards.md) §1.5)
- **同じ判定・同じ結論を 2 箇所で別実装していないか。テストがある側だけ見て安心していないか**。両方へ同じ入力を
  流して突き合わせ、片側の分岐を消す変異で red になるか確かめる。根治は出典を 1 箇所へ寄せる。🚨 この項の発動点はテストを書くときで、守りを新設するときは
  [`adversarial-review-own-safeguards.md`](adversarial-review-own-safeguards.md) の 0-B
- **計算ヘルパーの純関数テストだけで「配線済み」としていないか**。呼び出し側を旧実装に戻す変異で red を見るまでが 1 セット

**fake / stub**
- **fake / stub が外部コマンドの exit code を模しているか**
  ([`survey-receiver-guards-before-passing-new-values.md`](survey-receiver-guards-before-passing-new-values.md) の外部コマンド版)
- 🚨 **スタブが引数を受け取っているか** (捨てると「何を渡すか」を変える変異が全部緑)。渡された値を記録して assert する
- 🚨 **定数を返すだけのスタブに差し替えると、その依存へ渡す設定値が無検査になる**。設定値が結果を決めるなら実物を使う。
  上の項と発動点は同じで、片方だけ直すともう片方が残る

**platform / シェル**
- **環境が変われば別の値になるコマンド出力を、そのまま比較に使っていないか** (`ps` / `date` / `stat`)。両方の形状をテスト内で作る
- **比較に使う正規表現の方言が、両 platform で同じ意味になっているか** (`\t` は BSD と GNU grep で違う。タブは変数に落とす。`\s` は両方が受ける)。
  ヘルパーへパターンを渡す形は `grep` の近くを探しても見つからないので、正規表現になる文字列全部を見る。
  dotfiles は macOS 専用なのでこの項は他 repo 向け
- **判定に使う外部コマンドが、テストで渡す入力の形を受けられるか** (BSD awk の `-v` は改行を受け付けない。複数行は別入力で渡す。macOS でも踏む)
- 🚨 **シグナルを撃つテストは、撃つ先がサブシェルだと実体に届かない** (`exec` で置き換えるか、プロセスグループへ撃つ)
- 🚨 **観測対象が生まれるのを待ってから撃つ** (生まれる前に撃つと、修正の有無で結果が変わらない観測になる。
  待ち方は [`avoid-wall-clock-assertions.md`](avoid-wall-clock-assertions.md))
- **zsh の `(( i++ ))` は古い値を返す** (`i` が 0 だと status 1。`err_exit` 下で死ぬ。`(( ++i ))` を使う)

## やること / やらないこと

- ✓ 確認した変異を commit message に残す (再現可能な検証記録として)
- ✗ 環境変数や DEBUG でゲートされた出力を、seam 無しで assert しようとする (必ず vacuous になる)
- ✗ 期待する文字列・値を埋めるだけの変異で「テストは効いている」と結論する
- ✗ ビルドできなかった変異の緑を「変異を検知できなかった」と読む
