# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する

> **トリガー型ルール。** 回帰テストを書き終えて green を確認した瞬間、
> または「このテストで守られている」と commit message / doc に書こうとした
> 瞬間に発動する。

## ルール

- **新規追加・変更したテストは、その不変条件を壊す変更を 1 つ実際に適用し、
  red になることを確認してから commit する**。確認した変異の内容を commit message
  に残す
- **「テスト green」を検証の証拠として報告しない**。green は「正しい」ではなく
  「その書き方では壊せなかった」に過ぎない (CLAUDE.md「レビュー方針」の一般則は、
  テスト自身にも適用される)
- 変異させて **green のままだったテストは、書き直すか捨てる**。そのテストは主張を
  何も守っていない

## なぜ (起源: obaket issue 454、2026-08-03)

1 つの修正に対して 4 ラウンドのセルフレビューを回したところ、**毎回「直前ラウンドで
追加したテスト」が、そのラウンドの中心主張を何も守っていなかった**。いずれもテストは
green で実装も動いていたため、レビューを通すまで気づけなかった。

| ラウンド | テストの形 | 変異させた結果 |
|---|---|---|
| 1 | `#expect` が **1 つも無い** (「crash しないこと」だけ) | `guard` を削除しても green |
| 2 | 母集団が **恒等的に一致**する状況しか作らない (window 1 枚だけ登録) | 母集団を割る変異でも green |
| 3 | production の出力を **同じ定数**と比較する自己言及 | 定数を書き換えても green |
| 4 | 検証対象の描画が closure 内にあり **どのテストからも実行されない** | 変異する価値すら無い (カバレッジ 0) |

形が毎回違うので「パターンを覚える」方向では潰れない。一方、**変異を 1 本実行して
red を見る手順は形に依存せず、上記 4 例すべてを検出できた**。

## 手順 (特別なツールは要らない)

```
0. **変異を当てる前に baseline が green であることを測る**
1. 不変条件を壊す最小の変異を当てる
   (guard 削除 / 定数の反転 / ?? 0 で埋める / filter 条件の除去 など)
2. 対象テストだけ実行して red を確認する
3. 変異を revert して green に戻す
4. commit message に「どの変異で red を確認したか」を書く
```

⚠️ **手順 0 を飛ばさないこと**。baseline が red のまま変異を当てると、**red の増減が変異由来か
元から壊れているせいか区別できない**。実例 (2026-08-25): 指紋の統合直後に変異 5 本を当てて
「1/5 しか red にならない = テストが主張を守っていない」と読んだが、実際はそのとき別の理由
(テストが削除済みの関数名を呼んでいた) でテストが落ちていただけだった。baseline を直してから
当て直すと 5/5 が red になった。**数字だけ見て「テストが弱い」と誤診すると、要らないテストを
足す方向に走る**。

⚠️ **並行性を扱う新規テストは、3 回連続 green を確認してから commit する**。1 回の green は
flaky をそのまま素通しし、**その後のミューテーション判定を汚染する** (変異を当てて red が出ても、
それが変異由来か flaky 由来か区別できなくなる)。手順 0 が「baseline が green か」を見るのに対し、
これは「**baseline が安定して green か**」を見る。実例 (2026-08-25): commit 時に green を確認した
並行性テストが、検収の再実行で 2 回連続 red だった (実測 1/3 で red)。

⚠️ **変異の red/green は失敗行の件数ではなく、runner の実行サマリ行で判定する**。件数 grep は
「1 本も走らなかった (0 件)」と「全部 pass (0 件)」を区別できず、走っていないものを
「変異を検知できなかった」と誤読する。サマリ行が取れなければ、red でも green でもない**第 3 の結果**
(`<テストが走っていない>` 等) として出す。どちらかに丸めない。
禁じているのは**件数を red/green の判定に使うこと**であって、どのテストが落ちたかを読むために
個別行を列挙するのは別の用途 (そちらは禁じていない)。
**runner の文言は個別 CLI の仕様なので、判定スクリプト側のコメントを正本にし、このルールには転記しない**
(実測 2026-08-25: ある runner ではサマリ行が個別失敗行を拾う pattern にも一致し、件数が混ざっていた)。

作業ツリーを汚さないよう、変異の前に対象ファイルを控えておき、確認後に必ず戻す。

⚠️ **復元の作法** (2026-08-24 に 2 通りの事故が起きた):

- **`cp` のバックアップを世代で持たない**。同じセッションで `x.bak` / `x.m2bak` / `x.e2e.bak` と
  増やすと**古い世代を書き戻して配線が消える** (全テストが FAIL になって気づいた)。作業ツリーで
  変異させるなら **1 ファイルにつき 1 世代**に限り、当てる前後で `git diff --stat` を読む
- **`git checkout -- <path>` を常用手順にしない**。未コミットの変更 (自分の実装途中・**並行セッションの
  作業**) をまとめて消す。commit 済みを確認しても、確認から実行までの間に他セッションが書けば同じこと
- **最も安全なのは使い捨て worktree で変異させること** (正本は
  `~/.claude/skills/codex-drive/SKILL.md` の `[3.8]`)。復元事故が構造的に起きない
- **新規 (untracked) ファイルは `git checkout --` で戻せない**
  (`did not match any file(s) known to git`。worktree にも乗らない)。変異前に `cp` で
  1 世代だけバックアップし、復元後に `grep -c MUTANT` 等でマーカー残骸ゼロを確認する
  (実例 2026-08-21 obaket 536: 手動復元で凌いだが、復元し忘れれば変異がそのまま commit される)

## 変異は「production の機構を戻す」形にする

変異が red を出しても、それは**その変異を検出できた**だけで、テストが守るはずの不変条件を
検査した証明にはならない。**変異の当て方自体が偽物になりうる。**

- ✗ 期待している文字列・値を直接埋め込む (「テストがその文字列を見つけられるか」しか分からない)
- ✗ `return` を足して早期に抜ける・定数を返す (壊れ方が実際の退行と違う)
- ✓ **削除・最適化した機構をそのまま戻す** (呼び出しを復活させる / 旧実装を貼り直す)

判定: **「この変異は、実際に起こりうる退行の形か?」** 実装者が将来やりそうな編集 (最適化を
戻す・条件を緩める・呼び出しを足す) を再現していなければ偽物。

**その assert が見ている量は、壊れたときに動くのか**を先に問う。動かない量 (総数・行数・
存在の否定) を見ていると、本物の変異を当てても素通りする。

起源 (2026-08-14, issue 050/061): 「一覧に進捗を出さない」を守るテストの変異検証で、期待文字列
`1/1` を直接埋めて red を見て「効いている」と判断した。本物の機構 (`ReadBody()` → `Progress()`)
を戻す変異を当て直すと **green のまま**だった (フィクスチャに checkbox が無く、進捗を出す実装に
戻しても `1/1` が生成されない)。同じ形を 1 セッションで 3 回踏んでいる — 行頭が空白か / `1/1` の
不在 / 確保の**回数** (削ったのは 1 本の大きなスライスで回数は動かない)。

## 適用範囲

- ✓ 対象: バグ修正の回帰テスト / 不変条件を主張するテスト / 「これで守られている」と
  commit message・doc に書くテスト
- ✗ 対象外: 機械的なリネーム、fixture 追加、既存テストの分割など、**新しい主張を
  伴わない**変更

## よくある「守っていないテスト」の形 (変異前に自問する)

- assert が無い / 常に真になる assert を書いていないか
- 期待値を production と同じ式・同じ定数から作っていないか (自己言及)
- 差が出ない状況しか作っていないか (要素 1 個、空集合、恒等条件)
- **fake の「止まる回数」が、変異側の呼び出し回数を想定しているか**。上項の変種。
  「初回の呼び出しだけ block する」fake は、変異が**2 回目の呼び出しを足す**形だと素通りされ、
  変異検知が race 依存になる。永久 suspend (cancel 協調) 等、回数に依存しない止め方にすると
  決定的になる (実例 2026-08-25: barrier を足し戻す変異が、初回だけ block する fake のせいで
  最初すり抜けた)
- 検証したいコードが本当に実行されているか (closure / 環境変数ゲートの内側は走らない)
- **本番と同じ制約の下で観測しているか** (timeout / メモリ上限 / 実行時間の壁 / 権限)。
  制約を課さずに測ると「制約を超えたときの失敗」を観測できず、変異を当てても緑のまま通る。
  実例 (2026-08-21): PreToolUse hook のテストが本番配線の `timeout: 10` を課しておらず、
  「入力長で hook が timeout に殺されて deny が 1 byte も出ない = 安全機構が無効化される」
  退行を 4 ケース書いても全部緑だった (timeout を課して初めて red になった)。
  「遅い」を「素通り」として観測できる形にすること
- 前提の assert が**停止しない**形になっていないか (`#expect` は記録するだけ。前提が
  崩れたら後続が自己無矛盾に pass する。停止させたいなら `#require` 系を使う)
- **属性 (色・フラグ・クラス) の存在だけを見ていないか**。その属性が他の用途にも使われていると、
  何も主張していない assert になる。実例 (2026-08-23): 「使い残しはシアンで塗られる」を
  `\033[36m` の存在で assert したが、シアンは「余裕」の状態色にも使われていた (変異を当てても
  green のまま通って発覚)。**属性 + それが付く対象**まで見る
- **計算ヘルパー (予算・閾値・設定値・判定) の純関数テストだけで「配線済み」としていないか**。
  「計算が正しい」と「呼び出し側がその値を使っている」は別の主張で、前者のテストは後者を 1 mm も
  守らない。**呼び出し側を旧実装 (ヘルパーを呼ばない形) に戻す変異**を当てて red を見るまでが 1 セット。
  実例 (2026-08-24): `toastDrawBudget` の純関数テストはあったが、呼び出し側を元の式に戻す変異で
  全テストが green のまま通った
- **環境が変われば別の値になるコマンド出力を、そのまま比較に使っていないか** (`ps` / `date` /
  `stat` の書式・区切り・パディング)。**手元 1 platform の緑は「その platform では壊せなかった」
  でしかない**。実例 (2026-08-25): `ps -o lstart=` の末尾パディングが macOS では入り Linux では
  入らないため、指紋の正規化が末尾空白に依存していた。手元 (macOS) は緑のまま **CI (Linux)
  だけが赤**になり、しかもそれはテストの問題ではなく **Linux で生存 owner の lock を奪う本番の
  バグ**だった。→ **両方の形状をテスト内で作って**固定する (末尾パディングあり / なし)
- **比較に使う正規表現の方言が、両 platform で同じ意味になっているか**。上の項が「測られる値」
  の platform 依存なら、これは**測る側**の版。実測 2026-08-25: `grep -qE '\tfoo'` は
  **BSD grep (macOS) がタブとして解釈し、GNU grep (Linux CI) は `stray \ before t` と警告して
  リテラル `t` として扱う** (= 行中の実タブにマッチしない)。POSIX ERE にタブの escape は無い。
  手元だけ緑で CI だけ赤になり、しかも失敗メッセージが「無い」と言った直後にその行を表示する
  という分かりにくい形で出る。**タブは変数に落として使う** (`tab="$(printf '\t')"`)。
  `\s` は両方が受けるので使える (実測)。**ヘルパー関数へパターンを渡す形だと `grep` の近くを
  grep しても見つからない**ので、掃くときは「正規表現になる文字列」全部を見る (1 箇所見落として
  CI をもう 1 往復させた)。
  → **dotfiles には `make test-gnu` がある** (`scripts/with_gnu_grep.sh`)。GNU grep を `grep` として
  見せて tests/ 全体を回すので、この差を push 前に手元で潰せる。grep のパターンや観測ログ系の
  assert を触ったら回す。GNU grep が無い環境では skip せず**失敗する** (緑を返さない)
- **fake / stub が外部コマンドの exit code を模しているか**。`err == nil` しか返さない fake は、
  実際には exit 1 を返すコマンドの契約を再現していない。実例 (2026-08-24): claude CLI の
  ログアウト判定が `err != nil` で早期 unknown に落ちる実装だったが、fake が成功しか返さないため
  **一度も発火しない機能がテスト green で通った** (関連:
  [`survey-receiver-guards-before-passing-new-values.md`](survey-receiver-guards-before-passing-new-values.md)
  の「fake に受け側の reject 挙動を模させる」の外部コマンド版)

## やること / やらないこと

- ✓ 新規テストは変異 1 本で red を確認してから commit する
- ✓ 確認した変異を commit message に残す (再現可能な検証記録として)
- ✓ 変異で green のままなら、そのテストを書き直す
- ✓ 変異を当てる前に baseline が green であることを測る
- ✗ 「テスト green」を検証済みの根拠として報告する
- ✗ 期待する文字列・値を埋めるだけの変異で「テストは効いている」と結論する
- ✗ 環境変数や DEBUG でゲートされた出力を、seam 無しで assert しようとする
  (テストからは観測できず、必ず vacuous になる)
- ✗ 本番が課している制約 (timeout 等) を外した条件で測って「守れている」と結論する
