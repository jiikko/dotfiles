# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する

> **トリガー型ルール。** 回帰テストを書き終えて green を確認した瞬間、
> または「このテストで守られている」と commit message / doc に書こうとした
> 瞬間に発動する。

## ルール

- **新規追加・変更したテストは、その不変条件を壊す変更を 1 つ実際に適用し、
  red になることを確認してから commit する**。確認した変異の内容を commit message
  に残す
- **「テスト green」を検証の証拠として報告しない**。green は「正しい」ではなく
  「その書き方では壊せなかった」に過ぎない (CLAUDE.md「レビュー方針」の一般則は、
  テスト自身にも適用される)
- 変異させて **green のままだったテストは、書き直すか捨てる**。そのテストは主張を
  何も守っていない

## なぜ

起源: obaket issue 454、2026-08-03。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/mutation-verify-new-tests.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 手順 (特別なツールは要らない)

```
0. **変異を当てる前に baseline が green であることを測る**
1. 不変条件を壊す最小の変異を当てる
   (guard 削除 / 定数の反転 / ?? 0 で埋める / filter 条件の除去 など)
1.5. **その変異が実際にビルドできたことを確認する**
1.6. **変異の diff を目視し、意図した箇所だけが変わっていることを確認する**
2. 対象テストだけ実行して red を確認する
3. 変異を revert して green に戻す
4. commit message に「どの変異で red を確認したか」を書く
```

⚠️ **手順 1.5 を飛ばさないこと**。変異がコンパイルできていないと、runner は**直前の
stale build** を走らせて **green を返す**。それを「変異を検知できないテスト」と読むと、
効いているテストを弱いと誤診して書き直す方向に走る (手順 0 の誤診と同じ構造で、向きが逆)。
ビルド段の成否は**テスト実行とは別に見る** (`swift build --build-tests` / `go build ./...` /
シェルなら `bash -n`)。runner の出力だけを見ると、ビルド失敗と実行結果が同じ画面に混ざる。
「機構を戻す」形の変異は型検査に引っかかりやすいので、**型が強い言語ほど踏む**。

ビルドできなかった変異は **red でも green でもない第 3 の結果** (`<変異がビルド不能>`) として
扱い、当て直す。どちらかに丸めない。

⚠️ **手順 1.6 を飛ばさないこと**。変異は当てたつもりの形になっていないことがある (置換スクリプトの
引用符でシェル変数が展開され、別の箇所が壊れる等)。**別の変異でも red は出る**ので、red だけ見ていると
「意図した不変条件が守られている」と誤認する。判定の前に diff を読み、変わった行が意図した行だけか確かめる。

⚠️ **判定式を「rc が変異前と違うか」で書かない**。それは 3 値 (red / green / 測れていない) を
2 値に丸める形で、**壊れた変異の rc をそのまま「変異を検知した」と表示する**。判定は
「構文が通ることを先に確認 → **変異前と変異後の rc を両方名指しで**見る」。

⚠️ **手順 0 を飛ばさないこと**。baseline が red のまま変異を当てると、**red の増減が変異由来か
元から壊れているせいか区別できない**。**数字だけ見て「テストが弱い」と誤診すると、要らないテストを
足す方向に走る**。

⚠️ **並行性を扱う新規テストは、3 回連続 green を確認してから commit する**。1 回の green は
flaky をそのまま素通しし、**その後のミューテーション判定を汚染する** (変異を当てて red が出ても、
それが変異由来か flaky 由来か区別できなくなる)。手順 0 が「baseline が green か」を見るのに対し、
これは「**baseline が安定して green か**」を見る。

⚠️ **変異の red/green は失敗行の件数ではなく、runner の実行サマリ行で判定する**。件数 grep は
「1 本も走らなかった (0 件)」と「全部 pass (0 件)」を区別できず、走っていないものを
「変異を検知できなかった」と誤読する。サマリ行が取れなければ、red でも green でもない**第 3 の結果**
(`<テストが走っていない>` 等) として出す。どちらかに丸めない。
(禁じているのは**件数を判定に使うこと**で、どのテストが落ちたかを読む列挙は別用途。)
**runner の文言は個別 CLI の仕様なので、判定スクリプト側のコメントを正本にし、このルールには転記しない**。

作業ツリーを汚さないよう、変異の前に対象ファイルを控えておき、確認後に必ず戻す。

⚠️ **復元の作法** (2026-08-24 に 2 通りの事故が起きた):

- **`cp` のバックアップを世代で持たない**。`x.bak` / `x.m2bak` / `x.e2e.bak` と増やすと
  **古い世代を書き戻して配線が消える**。作業ツリーで変異させるなら **1 ファイルにつき 1 世代**に
  限り、当てる前後で `git diff --stat` を読む
- **`git checkout -- <path>` を常用手順にしない**。未コミットの変更 (自分の実装途中・**並行セッションの
  作業**) をまとめて消す。commit 済みを確認しても、確認から実行までの間に他セッションが書けば同じこと
- **worktree でも `git checkout --` は安全にならない**。worktree が消すのは**他人の混入**だけで、
  **その worktree にある自分の未コミット変更**は同じように消える。しかも戻った旧実装が build も
  test も通せば **green のまま気づけない**。変異対象に自分の未コミット変更があるなら
  **一度 commit してから当てる**のが最も単純 (それが嫌なら `cp` 1 世代)
- **バックアップと復元は絶対パスで行う**。`trap` は**スクリプトが `cd` した後に走る**ので、
  相対パスで復元すると**別のディレクトリに元ファイルのコピーを撒く**。実例 2026-09-03:
  末尾で `cd "$HOME/dotfiles"` していた変異スクリプトの trap が、repo root に 5 個の
  `*.go` を作った (Go の package main のコピーなのでどのビルドにも入らず、`git status` を
  見なければ静かに残る)
- **変異は使い捨て worktree で当てる** (正本は `~/.claude/skills/codex-drive/SKILL.md` の
  `[3.8]`)。復元事故が構造的に起きないうえ、下記の「並行の相手が見えない」問題も同時に消える。
  **skill を使わない手動の変異検証でも同じ**
- **新規 (untracked) ファイルは `git checkout --` で戻せない**
  (`did not match any file(s) known to git`。worktree にも乗らない)。変異前に `cp` で
  1 世代だけバックアップし、復元後に `grep -c MUTANT` 等でマーカー残骸ゼロを確認する
  (復元し忘れれば変異がそのまま commit される)

⚠️ **A-B のケース間で状態を共有しない**。`HOME` / `ZDOTDIR` / 一時ディレクトリは**ケースごとに
新規作成**する。前のケースが残した状態が次に効くと、A と B が同じ結果を返し「修正が効いて
いない」「変異を検知できない」と**誤診**する (効いている修正を作り替える方向に走る)。
矛盾する結果が出たら、まずハーネスの隔離を疑う。

⚠️ **共有 working tree で変異を当てない — 並行の相手は事前には見えない**。
[`parallel-write-agents-need-worktree-isolation.md`](parallel-write-agents-need-worktree-isolation.md)
は「自分が並行させるとき」を対象にするが、同じ checkout を使うのは自分が起こした並行だけではない
(別セッションが同じ repo にいて、自分からは見えない)。開く窓は 2 つ: **他人の変異が自分の
pathspec commit に入る** (`git status` では自分の変更と区別がつかない) / **変異中のファイルを
読んだレビュー・調査が、実在しないコードを前提にする**。
→ **既定は worktree**。共有 tree で当てるなら **変異中は一切 commit しない**。

## 変異は「production の機構を戻す」形にする

変異が red を出しても、それは**その変異を検出できた**だけで、テストが守るはずの不変条件を
検査した証明にはならない。**変異の当て方自体が偽物になりうる。**

- ✗ 期待している文字列・値を直接埋め込む (「テストがその文字列を見つけられるか」しか分からない)
- ✗ `return` を足して早期に抜ける・定数を返す (壊れ方が実際の退行と違う)
- ✓ **削除・最適化した機構をそのまま戻す** (呼び出しを復活させる / 旧実装を貼り直す)

判定: **「この変異は、実際に起こりうる退行の形か?」** 実装者が将来やりそうな編集 (最適化を
戻す・条件を緩める・呼び出しを足す) を再現していなければ偽物。

**当てる前に「red になったとき、それは*対象の assert が*検知したと言えるか」を書く。**
変異が red でも、**別の (既存の) assert が先に落ちている**なら、今回書いたテストの検知力は
何も証明できていない。先に落ちうる assert を潰した形の変異を設計する。

- 実例は rationale (obaket 688 C5: 書き込みを消す変異が、新テストより手前の別 assert で落ちた)
- 手順に落とすと: 変異を当てる前に「この変異で最初に落ちるのはどの assert か」を予測し、
  実行後にその予測と一致したかを見る。一致しなければ変異かテストのどちらかが的を外している

**その assert が見ている量は、壊れたときに動くのか**を先に問う。動かない量 (総数・行数・
存在の否定) を見ていると、本物の変異を当てても素通りする。

## 適用範囲

- ✓ 対象: バグ修正の回帰テスト / 不変条件を主張するテスト / 「これで守られている」と
  commit message・doc に書くテスト
- ✗ 対象外: 機械的なリネーム、fixture 追加、既存テストの分割など、**新しい主張を
  伴わない**変更

## よくある「守っていないテスト」の形 (変異前に自問する)

- assert が無い / 常に真になる assert を書いていないか
- 期待値を production と同じ式・同じ定数から作っていないか (自己言及)
- 差が出ない状況しか作っていないか (要素 1 個、空集合、恒等条件)
- **テーブル駆動 / サブテストなら、変異で「全ケース」が red になるか**。スイート全体の red は
  「どれか 1 つが落ちた」でしかなく、**緑のまま残ったケースは何も守っていない**。実測 2026-09-02
  (glogx の C/X 配線): 変異 4 本すべてで red が出たので効いていると読んだが、落ちていたのは
  別のサブテストで、status ケースは全変異で緑のままだった (敵対レビューが指摘)。判定は
  **ケース名ごとの pass/fail 一覧**で行い、スイートの rc で読まない
- **fake の「止まる回数」が、変異側の呼び出し回数を想定しているか**。上項の変種。「初回だけ
  block する」fake は、変異が**2 回目の呼び出しを足す**形だと素通りされ、変異検知が race 依存に
  なる。永久 suspend (cancel 協調) 等、回数に依存しない止め方にする
- 検証したいコードが本当に実行されているか (closure / 環境変数ゲートの内側は走らない)
- **本番と同じ制約の下で観測しているか** (timeout / メモリ上限 / 実行時間の壁 / 権限)。
  制約を課さずに測ると「制約を超えたときの失敗」を観測できず、変異を当てても緑のまま通る。
  「遅い」を「素通り」として観測できる形にすること
- 前提の assert が**停止しない**形になっていないか (`#expect` は記録するだけ。前提が
  崩れたら後続が自己無矛盾に pass する。停止させたいなら `#require` 系を使う)
- **属性 (色・フラグ・クラス) の存在だけを見ていないか**。その属性が他の用途にも使われていると、
  何も主張していない assert になる。**属性 + それが付く対象**まで見る
- **その観測は、変異の有無で違う値を出すか**。「差が出ない状況」(上項) の一般形で、
  今の生成経路・状態のスナップショットからは変異前後で同じ値しか出ない形が 2 つある:
  - 主張が**副作用の時点**なら (「Update の中で fork しない」等)、**状態の観測では固定できない**。
    その時点で副作用が起きたら失敗する環境を挟む (PATH を空にする / fake に reject させる)。
    実測 2026-09-02: 「Cmd を作る時点で同期に読み、結果を握った Cmd を返す」変異はモデルを
    触らないので、状態 assert を素通りした
  - 主張が**ガード**で、守る入力が今の生成経路から構造上出てこないなら (「blocked は Size 0 だから
    合計に足しても変わらない」)、**生成経路を経由せず値を直接与える**テストにする
    (計算部を関数に切り出して、ありえない値を直接渡す)
- **同じ判定・同じ結論を 2 箇所で別実装していないか。テストがある側だけ見て安心していないか**。
  CLI と TUI、production と debug 表示のように「同じデータから同じ結論を描く」形は、片方のテストが
  もう片方を 1 mm も守らない (片方には分岐が無いことすら気づけない)。**両方へ同じ入力を流して
  出力を突き合わせるテスト**を書き、片側の分岐を消す変異で red になるか確かめる。
  根治は判定・文言の出典を 1 箇所へ寄せること (寄せれば突き合わせるテストが 1 本で足りる)
- **計算ヘルパー (予算・閾値・設定値・判定) の純関数テストだけで「配線済み」としていないか**。
  「計算が正しい」と「呼び出し側がその値を使っている」は別の主張で、前者のテストは後者を 1 mm も
  守らない。**呼び出し側を旧実装 (ヘルパーを呼ばない形) に戻す変異**を当てて red を見るまでが 1 セット
- **環境が変われば別の値になるコマンド出力を、そのまま比較に使っていないか** (`ps` / `date` /
  `stat` の書式・区切り・パディング)。**手元 1 platform の緑は「その platform では壊せなかった」
  でしかない**。→ **両方の形状をテスト内で作って**固定する
- **比較に使う正規表現の方言が、両 platform で同じ意味になっているか**。上の項が「測られる値」
  の platform 依存なら、これは**測る側**の版。実測 2026-08-25: `grep -qE '\tfoo'` は BSD grep が
  タブとして解釈し、GNU grep はリテラル `t` として扱う (POSIX ERE にタブの escape は無い)。
  **タブは変数に落として使う** (`tab="$(printf '\t')"`)。`\s` は両方が受ける。**ヘルパーへ
  パターンを渡す形だと `grep` の近くを grep しても見つからない**ので、掃くときは「正規表現に
  なる文字列」全部を見る。⚠️ dotfiles は macOS 専用なのでこの項は**他 repo 向け**
- **fake / stub が外部コマンドの exit code を模しているか**。`err == nil` しか返さない fake は、
  実際には exit 1 を返すコマンドの契約を再現していない (関連:
  [`survey-receiver-guards-before-passing-new-values.md`](survey-receiver-guards-before-passing-new-values.md)
  の「fake に受け側の reject 挙動を模させる」の外部コマンド版)
- **フィクスチャが production の初期状態と違わないか**。違うと、その経路を**構造的に一度も
  踏まない**。並行・レースのテストでは「呼び出し元がどの状態から始まるか」を実装側で確認して
  から形状を決める
- **窓がミリ秒なら人為的に広げて決定論にする**。素の窓のままだと「たまに出る」ので、緑を
  「閉じた」と読み違える。広げた条件で A-B (ガード有無) を取ると、変異検証の当たりも安定する

## やること / やらないこと

- ✓ 新規テストは変異 1 本で red を確認してから commit する
- ✓ 変異を当てる前に「最初に落ちるのはどの assert か」を予測し、実行後に一致を確かめる (既存の assert が先に落ちる変異は、新テストの検知力を証明しない)
- ✓ 確認した変異を commit message に残す (再現可能な検証記録として)
- ✓ 変異で green のままなら、そのテストを書き直す
- ✓ 変異を当てる前に baseline が green であることを測る
- ✓ 変異を当てたら**ビルドできたことを確認してから** red/green を読む
- ✓ 変異は使い捨て worktree で当てる (共有 tree では、見えない並行セッションの変異と混ざる)
- ✗ 「テスト green」を検証済みの根拠として報告する
- ✗ ビルドできなかった変異の緑を「変異を検知できなかった」と読む (第 3 の結果として扱う)
- ✗ 共有 working tree で変異を当てたまま commit する
- ✗ 期待する文字列・値を埋めるだけの変異で「テストは効いている」と結論する
- ✗ 環境変数や DEBUG でゲートされた出力を、seam 無しで assert しようとする
  (テストからは観測できず、必ず vacuous になる)
- ✗ 本番が課している制約 (timeout 等) を外した条件で測って「守れている」と結論する
