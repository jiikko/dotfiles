# 新規テストは「壊す変更を 1 つ当てて red を見る」まで確認する

> **トリガー型ルール。** 回帰テストを書き終えて green を確認した瞬間、
> または「このテストで守られている」と commit message / doc に書こうとした瞬間に発動する。

## ルール

- **新規追加・変更したテストは、その不変条件を壊す変更を 1 つ実際に適用し、
  red になることを確認してから commit する**。確認した変異の内容を commit message に残す
- **「テスト green」を検証の証拠として報告しない**。green は「その書き方では壊せなかった」に過ぎない
- 変異させて **green のままだったテストは、書き直すか捨てる**
- **green のままの変異を「等価変異 (到達不能)」と判定するときは、変異箇所に到達する全経路を
  列挙してから言う**。テスト名から挙動を推測しない
- **既存の assert を「何も検査していない」として消すときも、消す前に変異を 1 本当てる**
  (当てずに vacuous と断じた assert が、実は唯一の上限だったことがある)

## なぜ

起源: obaket issue 454、2026-08-03。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/mutation-verify-new-tests.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 手順 (特別なツールは要らない)

```
0. **変異を当てる前に baseline が green であることを測る**
1. 不変条件を壊す最小の変異を当てる
   (guard 削除 / 定数の反転 / ?? 0 で埋める / filter 条件の除去 など)
1.5. **その変異が実際にビルドできたことを確認する**
1.6. **変異の diff を目視し、意図した箇所だけが変わっていて、その行が対象テストの実行経路上にあることを確認する**
2. 対象テストだけ実行して red を確認する
3. 変異を revert して green に戻す
4. commit message に「どの変異で red を確認したか」を書く
```

**手で組む前に `bin/mutate-verify` を見る** (issue 408。dotfiles の `bin/` は PATH 上にあり、どの repo でも `mutate-verify` で呼べる。issue 585)。下の「復元の作法」と手順 0〜3 の guard
(baseline green / 当たったか / 誤ファイル / 構文 = 第 3 の結果 / zero execution / red の帰属 /
未コミット差分があれば拒否 / 各 run の時間の上限 = `--timeout`、超えたら rc=10) を機械で強制する。使い捨て worktree の中だけで変異させるので作業ツリーを触らず、
未コミットの変更は持ち込むので「今書いたテスト」も検証できる。変異の当て方 (`--apply`) は呼び出し側の責任。
射程の外 (assert の誤り・観測設計・fixture / seam) はスクリプト冒頭に書いてある。
rc=0 が保証するのは「`--expect` の検査が落ちた」**まで**で、「それだけが落ちた」ではない。
表示される baseline との出力の差 (消えた行・増えた行) で巻き添えを見てから採用する
(40 行を超えた分は、終わりに出る「全体のログ」の `diff.txt` にある)。
**変異を何本も当てるなら `bin/mutate-verify-list`** (issue 580): 一覧 (`defaults` / `mutant` の 2 関数で書く bash の断片) を
全部読んでから 1 本ずつ `mutate-verify` に渡し、名前 / rc / 意味の表を出す。判定は `mutate-verify` のまま (並べ役を手で書かない)。

- **手順 0**: baseline が red のまま変異を当てると、red の増減が変異由来か区別できない
- **並行性を扱う新規テストは、3 回連続 green を確認してから commit する** (1 回の green は flaky を素通しし、その後の変異判定も汚染する)
- **手順 1.5**: 変異がコンパイルできていないと runner は **stale build** を走らせて green を返し、
  効いているテストを弱いと誤診する。ビルド段の成否は**テスト実行とは別に見る**
  (`swift build --build-tests` / `go build ./...` / `bash -n`)。ビルド不能は
  **red でも green でもない第 3 の結果**として扱い、当て直す
- **手順 1.6**: 変異は当てたつもりの形になっていないことがある (置換の `$` はシェルと perl の両方で
  展開されうる)。別の箇所が壊れても red は出るし、コメント行に当たれば緑になる。**赤か緑かを読む前に diff を読む**
  - **構文が通ることは挙動中立を意味しない**。変異が出力や副作用を足していたら、その red はテストの検知力を
    何も証明しない (zsh の同一スコープでの 2 度目の `local` は変数を stdout へ出す)
- **手順 1.5 / 1.6 と未コミット差分の拒否は、人が覚えるのをやめ変異ハーネス側に guard として置く**
  (`diff -q` で当たったか、`bash -n` / `zsh -n` / `go build` で構文、`git status --porcelain` が空か)
- **モジュール境界を跨ぐ定数・型を変異させたら、クリーンビルドを挟む**。部分ビルドは 1 実行の中に
  新旧 2 つの値を作り、ビルドは成功する。①クリーンビルド ②フルログ ③実行 0 件を第 3 の結果に
  ④diff と参照カウントの目視、を揃える
- **判定式を「rc が変異前と違うか」で書かない** (3 値を 2 値に丸め、壊れた変異を「検知した」と出す)。
  構文を先に確認し、変異前と変異後の rc を両方名指しで見る
- **red/green は失敗行の件数ではなく、runner の実行サマリ行で判定する** (件数は「0 件実行」と
  「全部 pass」を区別できない)。取れなければ第 3 の結果にする (どのテストが落ちたかを読む列挙は別用途で、禁じていない)。runner の文言は判定スクリプト側のコメントを正本にし、ここへ転記しない
- **実行件数は baseline と突き合わせ、一致したときだけ red / green を読む** (不一致は判定不能)。filter の書き損じ・
  テストのレーン違い・変異由来の hang はどれも「件数が違う」で出る。件数を取る式も baseline の既知の件数で先に較正する
  (runner は集計行を複数出すことがあり、最後の 1 行が別 suite の数のことがある)
- **変異を当てる run には timeout を付ける** (無いと hang が「まだ走っている」と区別できず、第 3 の結果が消える)。
  テストに「止める」フックを仕掛けたら、前提の待ちが失敗したらフックを解放して止める形にする
  (`#expect` のまま先へ進むと、残ったフックで後続が止まり red ではなく無限待ちになる)
- **red を確認したら、その red を成立させていた入力が HEAD にまだ在るかを見る**。同じ commit の別の修正が
  根拠の fixture を消していると、「変異で確認済み」は変異体については真、HEAD については偽になる。
  **前回 red だった変異が green に転じたとき**も、実装より先にテスト本体・fixture が巻き添えで消えていないか疑う

🚨 **復元の作法** (`bin/mutate-verify` を使えば下は構造的に起きない):

- **`cp` のバックアップを世代で持たない** (古い世代を書き戻して配線が消える)。作業ツリーで変異させるなら
  1 ファイルにつき 1 世代に限り、当てる前後で `git diff --stat` を読む
- **`git checkout -- <path>` を常用手順にしない**。未コミットの変更 (自分の途中作業・並行セッションの作業) を
  まとめて消す (commit 済みを確認しても、確認から実行までの間に他セッションが書けば同じ)。🚨 **発動点は「レビュー指摘を直した直後」** — 直後は必ず未コミットなので、
  **指摘を直したら変異の前に commit する** (WIP でよい)
- **worktree でも `git checkout --` は安全にならない** (その worktree の自分の未コミット変更は消え、旧実装が
  通れば green のまま気づけない)。変異対象に未コミット変更があるなら一度 commit してから当てる
- **バックアップと復元は絶対パスで行う** (`trap` はスクリプトが `cd` した後に走る)
- **変異は使い捨て worktree で当てる** (正本は `~/.claude/skills/codex-drive/SKILL.md` の `[3.8]`)。
  skill を使わない手動の変異検証でも同じ
- **新規 (untracked) ファイルは `git checkout --` で戻せない** (worktree にも乗らない)。`cp` で 1 世代控え、復元後に
  `grep -c MUTANT` 等でマーカー残骸ゼロを確認する
- **破壊的な clean を検証手順に入れたら、報告前に `git status` で追跡ファイルと lock ファイル**
  (`Package.resolved` 等) **の変化を確認する**。変わっていたら pin を戻して測り直す

**A-B のケース間で状態を共有しない**。`HOME` / `ZDOTDIR` / 一時ディレクトリはケースごとに新規作成し、
測る対象が環境変数なら親から落とす (`env -u <名前>`)。矛盾する結果が出たら、まずハーネスの隔離を疑う。

🚨 **共有 working tree で変異を当てない — 並行の相手は事前には見えない**
([`parallel-write-agents-need-worktree-isolation.md`](parallel-write-agents-need-worktree-isolation.md) は
自分が起こした並行だけを対象にする)。他人の変異が自分の pathspec commit に入る / 変異中のファイルを読んだ
レビューが実在しないコードを前提にする。**既定は worktree**。共有 tree で当てるなら変異中は一切 commit しない。

## 変異は「production の機構を戻す」形にする

変異が red を出しても、それは**その変異を検出できた**だけ。**変異の当て方自体が偽物になりうる。**

- ✗ 期待している文字列・値を直接埋め込む / `return` を足して早期に抜ける・定数を返す
- ✓ **削除・最適化した機構をそのまま戻す** (呼び出しを復活させる / 旧実装を貼り直す)

判定: **「この変異は、実際に起こりうる退行の形か?」**

**当てる前に「この変異で最初に落ちるのはどの assert か」を予測し、実行後に一致を確かめる。**
別の既存 assert が先に落ちているなら、今回書いたテストの検知力は何も証明できていないので、先に落ちうる assert を潰した形の変異を設計する。
予測と一致しなければ、変異かテストのどちらかが的を外している。
**その assert が見ている量は、壊れたときに動くのか**も先に問う (総数・行数・存在の否定は動かないことが多い)。

## 検査の不在を主張するときの裏取り

「〜を検出するテストが無い」「callsite が 0 件」のような**不在の主張**は、テストを書く / 書かない判断を決める。green と同じ重さで裏を取る。

- **grep 1 本で確定させない** (テストはリテラル値で書かれていることがある)。確定させる唯一の方法は
  **変異を当てて green を見ること**。やっていないなら「未検証」と書く
- 「手段が無い」型の主張は、**同じ問題を既に解いている既存テストが repo に無いか**を見る。見送り判断の根拠も、
  逆を書いている doc / テストコメントを探してから断定する
- **2 者が独立に数えて一致しても、数え方が同じなら独立ではない**。独立させるのは主体ではなく**方法**。
  件数や不在が設計・削除の根拠になるときは、方法を変えた列挙を最低 2 通り用意し、食い違いを精読する
  (走査 / 到達可能性 / API 網羅 / 実行時の観測)

## 適用範囲

- ✓ バグ修正の回帰テスト / 不変条件を主張するテスト / 「これで守られている」と書くテスト
- ✗ 機械的なリネーム・fixture 追加・既存テストの分割など、新しい主張を伴わない変更

## よくある「守っていないテスト」の形 (変異前に自問する)

🚨 **変異を当てる前に `~/dotfiles/_claude/rules-checklists/mutation-verify-new-tests.md` を Read する**
(起動時には読まれない。常時読み込みの合計を上限 150k 字に収めるために切り出した)。
見出しは assert と期待値 / fixture と前提 / 到達しているか / red の読み方 / 観測の設計 / 実装の二重化・配線 / fake・stub / platform・シェル。

## やること / やらないこと

- ✓ 確認した変異を commit message に残す (再現可能な検証記録として)
- ✗ 環境変数や DEBUG でゲートされた出力を、seam 無しで assert しようとする (必ず vacuous になる)
- ✗ 期待する文字列・値を埋めるだけの変異で「テストは効いている」と結論する
- ✗ ビルドできなかった変異の緑を「変異を検知できなかった」と読む
