# 検証は「exit code」ではなく「実行された証拠」で判定する

## ルール

- **検査・テスト・gate を「通った」と判断する前に、それが実際に実行された証拠を出力で確認する**。
  exit code 0 は「合格」ではなく「**失敗しなかった**」であり、
  「**そもそも走らなかった**」も含む
- **新設した検査を最初に配線したときは、必ず「その検査の出力が現れること」を確認する**。
  `make lint && echo ok` / `pytest -k new_test` の exit 0 だけで満足しない
- **パイプの終端の status を見ない**。`cmd | tail` の `$?` は `tail` の status。
  必要なら `set -o pipefail` を使うか、リダイレクトしてから exit code を取る
- **検証コマンドの出力を `tail` / `head` / `grep` で削って読まない。ファイルへ落としてから読む**。
  削るのは status だけでなく**失敗の原因そのもの**。集約 target は「✗ 失敗したターゲット: X」を
  最後に出す設計が多いので、`| tail -n` は**結論だけ残して理由を捨てる**形になりやすい。
  捨てた後に再実行して緑だと、その失敗はもう調べられない (`cmd > out 2> err; echo $?` の形にする)
  - 🚨 **stdout / stderr を分けたら両方読む**。片方だけ見て「通った」と読まない (実測 2026-09-04:
    err だけ見て shellcheck 通過と読んだが、指摘も「✗ 失敗したターゲット」も stdout に出ていた)

## なぜ

起源: 2026-08-23 obaket、同一セッションで 3 回踏んだ。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/verify-execution-not-just-exit-code.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 確認の仕方

| 対象 | 「走った証拠」の取り方 |
|---|---|
| lint gate / 検査スクリプト | その gate 固有の出力行を `grep` する (件数を出す設計にしておくと確実) |
| 新規テスト | テスト名が実行一覧に出ることを確認する (`-only-testing` の vacuous pass 対策と同根) |
| CI 上の検査 | ログに出力行があることを確認する。**緑という結果だけで判断しない** |
| 集約 target への配線 | 集約 target 経由で実行して出力を確認する。個別に直接叩いた結果で代用しない |

**「件数を出す」設計が効く**: `検査対象 N 件を確認` のように数を出しておくと、
0 件や想定より少ない数を見た瞬間に空振りが分かる。収集 0 件を失敗扱いにするのも同じ発想。

## 非同期・background の完了も「成果物」で判定する

- 完了通知・プロセスの生死は完了の証拠にならない。判定は「**その run 固有の成果物が、非空で、
  終了コードつきで存在する**」で行う
- `until [ -f <artifact> ]` だけでは足りない。**前回の残骸ファイル / 起動直後に作られた空ファイル /
  書き込み途中のファイル**を完了と誤認する。出力先は毎回新規にし、rc と非空をあわせて見る
  (`codex-fanout` が outdir の使い回しを拒否し `runs.tsv` に rc を残すのはこのため)
- **`pgrep` の存在確認で待たない**。`-f` は command line 全体を見るため、パターンが
  **待機コマンド自身の command line に現れると自分にマッチする** (2026-08-26 実測)。
  パターンを凝らすより、**自分が起動した子は `wait` して rc を取り、その後に成果物を見る**
  (`bin/codex-fanout` もそうしている)
- **rc は `wait` 後のものを使う**。`cmd > out &` の直後の `$?` は**起動の成否**であって
  `cmd` の終了コードではない。書き込み途中の成果物を掴まないよう、公開は完了時の
  atomic rename か done marker で行う
- **background / detach する出力先は repo root からの絶対パスをリテラルで書く。`$PWD` や相対パスを使わない**。
  Bash ツールの cwd は呼び出し間でハーネスの primary cwd に戻ることがあり、`$PWD/tmp/...` が**別 repo の tmp**
  に出る (実測 2026-09-02 obaket 696: codex run が SnapTrim 側に成果物を出し、待機タスクは obaket 側を永遠に
  待った。2026-09-04 の 715 で再発、今度は逆向きに誤認して `find` で探す往復が出た)。
  codex 等の外部エージェントの起動も `cd <root> && codex exec -C <root>` で作業根を明示する
  (cwd がサブディレクトリのまま workspace-write を起動すると、その外を書けず「対応できませんでした」で終わる)
- **待つのは「driver が必ず書く成果物」で、外側のラッパが書く rc ファイルではない**。
  `(nohup driver …; echo rc > X.rc) &` の形で、run 単位の成果物は全部揃ったのに外側 `X.rc` だけ無く、
  `until [ -f X.rc ]` が回り続けた例がある (obaket 696 項目 10、原因未特定)。待機ループには deadline を置き、
  超えたら「判定不能」を出す (timeout に頼らない)
- **待つと決めたら待つ**。`until` ループ / Monitor を張ったら、その完了通知が来るまで
  `grep -c` 等の手動ポーリングを重ねない (ターンとトークンを消費するだけで、完了は 1 秒も早くならない。
  ユーザーには「進行中です」の繰り返しとして見える)。張った待ちが信用できないなら、待ちの側を直す
- **TaskStop は process group ごと殺す**。待機 (poll) 用の background Bash の中で `nohup` した長寿命プロセス
  (アプリ・サーバ) は、待機タスクを止めた瞬間に道連れになる (obaket 696 項目 9: `make dev-fg` のアプリが消えた)。
  長寿命プロセスは待機タスクとは別の Bash 呼び出しで起こす

**実害は「待ち直し」では済まない**: 早すぎた判定は「相手が空振りした」という**誤った因果**を作り、
代替作業への切り替え → 遅れて完了した出力が同じパスを上書き → **commit された成果物の出所を
取り違える**、まで連鎖する。「まだ走っている」を「壊れている」と読むと、後続の判断が全部その誤診の上に建つ

## 実行環境を変えたら、変更前後の出力を全行 diff する

CI の runner / OS / 依存を差し替えたときは、**緑の比較で終わらせない**。同じ「全部緑」でも、
**中身が入れ替わっている**ことがある。

- **件数は当てにならない**。テストファイル数が同数でも、その中で skip に化けたものがある
  (実例: 96 → 96 ファイルのまま `✓` 行が 68 件消えていた)
- **skip はファイル単位では合格に見える**。runner の集計が `[ok]` を出すので、緑の側からは
  観測できない。消えたことが分かるのは**両 run の出力を全行突き合わせたとき**だけ
- 「skip しそうなガードを grep する」では弱い。それは自分が思いつく形しか見つけられない

## 確認を求める外部コマンドは、非対話だと「何もせず rc=0」で返る

`rm -i` / `docker ... prune` / `brew` の一部のように **`[y/N]` を出す CLI** は、stdin が
EOF (TTY 無しの exec / `</dev/null`) だと**中止して成功終了**する。呼び出し側から見ると
「実行できた」で、しかも**出力にはプロンプト文が出ている**ので一見動いたように見える。

- 判定は「rc が 0 か」でも「出力が空でないか」でもなく、**その操作の効果が観測できるか**
  (消したはずのものが減ったか)。効果を測れないなら、非対話用のフラグを付けて
  プロンプト自体を出さない側へ倒す
- 🚨 **表示・コピー用と実行用でコマンド文字列を分けない**。画面が出しているものと走るものが
  違う状態を作らない。プロンプトの代わりが要るなら、**自分の確認画面**で持つ
- 実例は rationale (2026-09-04: `docker builder prune --filter ... </dev/null` が rc=0 +
  プロンプトだけを stdout に出して終了した。`-f` を付けるまで「実行できた」と報告しながら
  1 バイトも減らない配線だった)

## 「有無で結果が変わらない観測」を証拠に数えない

観測が**対立仮説を棄却できるか**を先に問う。修正・機構の**有無に関わらず同じ結果になる**観測は、
何も確かめていない。exit code の話 (上記) は「走ったか」の版で、これは「**効いたか**」の版。

- 実例は rationale (obaket 688 C7: 「実行後に item が増えていない」は、機構の有無に関わらず同じ結果になる観測だった)
- 判定: 「その機構を外したら、この観測結果は変わるか?」に yes と答えられないなら観測を設計し直す
  (= 観測版のミューテーション検証。[`mutation-verify-new-tests.md`](mutation-verify-new-tests.md) の姉妹)
- **切り分けで動かした変数を数える。** 「環境のせい」と結論する前に、自分が何を変えたかを
  数え上げる。一時ディレクトリの差し替えのように**副作用で別のものまで変わる**操作があり
  (実測 2026-09-04: `TMPDIR` を変えると go のビルドキャッシュも空になるので変数が 2 つ動く)、
  「別の環境では再現しなかった」は原因の否定にならない。正しい切り分けは
  **①条件を変えずに同じ HEAD で 2 回回す** (1 回目赤・2 回目緑なら環境でなく非決定性)
  **②緑だった時点と赤い時点を同じコマンドで比べる**
- 「前後の比較」を使うときは、**比較の前後で同じ抽出方法を使う**。方法が違うと数字が動いた
  ように見えて誤診する (同日実測: `grep -oE '"svce"...'` と素の `grep -c` で件数が 30 と 49 に割れた)

## 抽出・判定を書いたら、同じ経路を通る canary を先に置く

検査の本体が「対象を抽出して判定する」形のとき、**抽出が空を返すと「違反 0 件」= 緑**になる。
検査は走っており出力も出るので、上の 2 節では捕まらない (「走ったか」でも「効いたか」でもなく、
**何を見たか**が空になる形)。

- **既知の入力で既知の答えが出ることを、本走査の前に固定する**。canary が落ちれば抽出が壊れた
  ことが分かる
- 🚨 **canary と本走査は同じ関数を通す**。式をコピーして別に書くと、canary は「コピーした
  ロジック」を検査するだけになり、本走査の破損を検出しない
- **対象 0 件 / 抽出 0 件は失敗にする** (上節「収集 0 件は失敗扱い」の抽出版)。加えて
  「**この repo なら必ず 1 件は当たる**」入力を canary に選ぶと、絞り込みの条件を間違えた
  ときも落ちる
- 実例は rationale (2026-09-03 に 4 形: `set -euo pipefail` 下の無マッチ grep が代入ごと
  スクリプトを殺す / フィルタがパス名を前提にして worktree で 0 件になる / sed の式の破損 /
  `sort` だけ `LC_ALL=C` にして `comm` の引き算が崩れる)

## 構造で守れるなら守る

同じ配線漏れが繰り返す箇所は、運用ではなく機械で止める
(実例: obaket `macOS/bin/check-lint-gate-wiring` = gate target が集約 target に
配線されているか / `.PHONY` 漏れ / allowlist の stale を検出する meta-gate)。

## やること / やらないこと

- ✓ 検査の合格判定は「その検査の出力が出たか」で行う
- ✓ 「その機構を外したら観測結果は変わるか」に yes と答えられない観測を証拠に数えない (前後比較は同じ抽出方法で行う)
- ✓ 新設検査は集約経路から実行して出力を確認する
- ✓ 収集 0 件 / 対象 0 件は成功にせず失敗扱いにする
- ✓ 実行環境を差し替えたら、変更前後の出力を全行 diff する (緑どうしの比較で終わらせない)
- ✓ 非同期・background は、毎回新規の出力先に出た**非空の成果物 + `wait` 後の rc** で完了を判定する
- ✓ パイプを挟むなら `set -o pipefail`
- ✓ 検証の出力はファイルへ落としてから読む (削るのは後。失敗の原因を捨てない)
- ✓ 抽出・判定を書いたら、**本走査と同じ関数を通る** canary を置く (抽出が空 = 違反 0 件 = 緑 を塞ぐ)
- ✗ exit code 0 だけを見て「通った」と報告する
- ✗ `cmd | tail` の `$?` を cmd の status として扱う
- ✗ 検証コマンドを `| tail -n` に通して回す (結論だけ残って理由が消え、再実行で緑なら追えない)
- ✗ 個別に直接叩いた結果を「集約経路でも走る」証拠として使う
- ✗ 完了通知・プロセスの生死で非同期の完了を判定する (まだ走っているものを「壊れている」と誤診する)
- ✗ 抽出の式をコピーして canary を別に書く (本走査の破損を検出しない)
