# 検証は「exit code」ではなく「実行された証拠」で判定する

## ルール

- **検査・テスト・gate を「通った」と判断する前に、それが実際に実行された証拠を出力で確認する**。
  exit code 0 は「失敗しなかった」であり、「**そもそも走らなかった**」も含む
- **新設した検査を最初に配線したときは、必ず「その検査の出力が現れること」を確認する**
- **パイプの終端の status を見ない** (`cmd | tail` の `$?` は `tail` の status)。`set -o pipefail` を使うか、リダイレクトしてから rc を取る
  - 🚨 **成否で後段を走らせる `&&` のつなぎを書いた瞬間にも発動する**。`git push ... 2>&1 | tail -2 && <後段>` は push が落ちても後段が走る。
    前段は `> log 2>&1; rc=$?` で取り、`[ $rc -eq 0 ] || exit 1` で止めてから出力を読む
- **検証コマンドの出力を `tail` / `head` / `grep` で削って読まない。ファイルへ落としてから読む** (削ると失敗の原因そのものが消え、再実行で緑なら追えない)
  - 🚨 **stdout / stderr を分けたら両方読む**

## なぜ

起源: 2026-08-23 obaket、同一セッションで 3 回踏んだ。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/verify-execution-not-just-exit-code.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 確認の仕方

| 対象 | 「走った証拠」の取り方 |
|---|---|
| lint gate / 検査スクリプト | その gate 固有の出力行を `grep` する (件数を出す設計にしておく) |
| 新規テスト | テスト名が実行一覧に出ることを確認する |
| CI 上の検査 | ログに出力行があることを確認する。緑という結果だけで判断しない |
| 集約 target への配線 | 集約 target 経由で実行して出力を確認する。個別に直接叩いた結果で代用しない |

**収集 0 件 / 対象 0 件は失敗扱いにする**。`検査対象 N 件を確認` のように数を出しておくと空振りが見える。

## 非同期・background の完了も「成果物」で判定する

- 完了通知・プロセスの生死は完了の証拠にならない。判定は「**その run 固有の成果物が、非空で、終了コードつきで存在する**」
- 出力先は毎回新規にし、rc と非空をあわせて見る (前回の残骸 / 起動直後の空ファイル / 書き込み途中を完了と誤認しない)。
  公開は完了時の atomic rename か done marker で行う
- **自分が起動した子は `wait` して rc を取る**。`cmd > out &` の直後の `$?` は起動の成否でしかない
- 🚨 **`pgrep -f` で待たない**。パターンが待機コマンド自身の command line に現れると自分にマッチし、
  `until ! pgrep -f "..."` は**永久に待つ**。待つ対象はプロセスではなく成果物にする (`until [ -f <outdir>/runs.tsv ]`)
- 🚨 **ラッパーの rc を本体の rc と読まない** (複合コマンドを丸ごと非同期で回すと、報告される rc は最後の `echo` のもの)。自分が仕込んだ `rc=` 行を読む
- **検証の手順は `&&` で繋ぎ、`;` で繋がない**
- **background / detach する出力先は repo root からの絶対パスをリテラルで書く** (`$PWD` / 相対パスはツールの cwd が呼び出し間で戻るため別の場所に出る)。
  待つ対象は実行側が必ず書く成果物にし、待機ループには上限を置いて、超えたら「判定不能」を出す
- **待つと決めたら待つ**。張った待ちの完了通知が来るまで手動ポーリングを重ねない。同じ条件の待ちを 2 本以上張らない (信用できないなら待ちの側を直す)
- **待機タスクを止めると同じ process group の子も死ぬ**。長寿命プロセスは待機とは別の呼び出しで起こす

早すぎた判定は「相手が空振りした」という誤った因果を作り、後続の判断が全部その誤診の上に建つ。

## 実行環境を変えたら、変更前後の出力を全行 diff する

CI の runner / OS / 依存を差し替えたら、緑どうしの比較で終わらせず、**両 run の出力を全行突き合わせる**。件数は当てにならず
(ファイル数が同じでも中で skip に化ける)、skip はファイル単位では合格に見える。「skip しそうなガードを grep する」では
自分が思いつく形しか見つからないので弱い。

## 確認を求める外部コマンドは、非対話だと「何もせず rc=0」で返る

`[y/N]` を出す CLI は stdin が EOF だと中止して成功終了する (出力にはプロンプト文が出ている)。

- 判定は rc でも出力の有無でもなく、**その操作の効果が観測できるか**。測れないなら非対話用のフラグでプロンプト自体を出さない
- 🚨 **外部コマンド / アプリへ設定を書いたら、同じ手順の中で読み戻して比較する** (受け側が黙って代替値へ差し替えることがある)
- 🚨 **表示・コピー用と実行用でコマンド文字列を分けない**

## path filter 付きの CI では、HEAD の緑を「直前までの緑」と読み替えない

- `paths:` 付きの workflow は、対象を触らない commit では起動しない。判定は commit ではなく**範囲**で行い、
  最後にその workflow が走った commit から HEAD までに対象を触った commit が挟まっていないかを見る
- HEAD が対象を触っていないなら、その緑は HEAD を検証していない
- 🚨 **`make test` に lint が入っていない repo では、Go / shell を触った commit ごとに lint を別に回す**

## 集約テストが赤いまま、その上で検証を続けない

取れる手は 2 つだけ: **直す**か、**落ちている検査の名前を控えて「この検証はその検査を含まない」と報告に明記する**。
「環境由来なので無関係」と分類しただけで黙って続けない。

## 隔離環境での成功は、本番での成功ではない

- 報告の前に「私が動かしたファイルは、ユーザーの環境で実際に読まれるファイルか」を問う。実体パスから起動されるもの
  (hook / bind が指すスクリプト / PATH 上のコマンド) は push しただけでは反映されない
  (dotfiles の正本は `.claude/rules/worktree-per-session.md`)。`status -sb` の `behind N` や mtime で版を見る
- 🚨 **裏返しも同じ。隔離環境での失敗も本番の失敗ではない**。赤を報告する前に、用意した実行環境が本番と同じものを読んでいるか確かめる
  (`nvim -l` はユーザー設定を読まない、等)

## キャッシュされた緑と path filter は、鍵に数えない入力の変化を見ない

テストがキャッシュ鍵にも paths filter にも入らない入力 (module の外のファイル・生成物・環境) を読むなら、**cached の緑は証拠ではない**
(Go の testcache は module root の外の open/stat を再チェックしない)。**キャッシュ無効で走らせ、そのテスト固有の PASS 行を grep する** +
読む対象を workflow の paths に載せ、その配線を検査で固定する。

## 「有無で結果が変わらない観測」を証拠に数えない

観測が**対立仮説を棄却できるか**を先に問う。判定: **「その機構を外したら、この観測結果は変わるか?」** に yes と答えられないなら観測を設計し直す
([`mutation-verify-new-tests.md`](mutation-verify-new-tests.md) の観測版)。

- **切り分けで動かした変数を数える** (副作用で別のものまで変わる操作がある。`TMPDIR` を変えると go のビルドキャッシュも空になる)。
  「別の環境では再現しなかった」は原因の否定にならない。正しい切り分けは ①条件を変えずに同じ HEAD で 2 回回す
  (1 回目赤・2 回目緑なら環境でなく非決定性) ②緑だった時点と赤い時点を同じコマンドで比べる
- 前後の比較は**同じ抽出方法**で行う
- 🚨 **崩し・fixture・変異体を作ったら、走らせる前に「作る前と違う状態になった」ことを機械で確認する** (`diff -q`)。
  整形・正規化を通すときは、その整形が崩しを打ち消さないか特に見る (コードへの変異は mutation-verify の手順 1.6 が正本)
- 🚨 崩れを確認しても、「放っておいても同じ結果になる」可能性は別に潰す (機構を外した**負の対照**を 1 本置く)。
  崩れの確認が言えるのは「入力が違う」までで、「直したのが自分の機構か」は言わない
- 🚨 **観測できた経路と、主張する範囲を一致させる**。1 経路で確かめたことを「常に」「全経路で」と書かない。一般化する前に
  分岐しうる条件 (署名・sandbox・環境変数・ビルド構成) を挙げ、挙げられないなら主張を観測した経路に限定する。
  成果物が在ることは「その経路が一度使われた」証拠にしかならず、無いことは経路の不在の証明にならない

## 抽出・判定を書いたら、同じ経路を通る canary を先に置く

抽出が空を返すと「違反 0 件」= 緑になる (走ってもいるし出力も出るので上の節では捕まらない)。

- **既知の入力で既知の答えが出ることを、本走査の前に固定する**。「この repo なら必ず 1 件は当たる」入力を選ぶ
- 🚨 **射程は自作の検査スクリプトに限らない。その場の調査の使い捨て 1 行にも要る**。発動点は「不在を根拠にしようとした瞬間」で、
  **必ず在るはずのもので先に較正してから**使う (`strings <binary> | grep` は Swift の文字列リテラルを拾えない、等)
- 🚨 **canary と本走査は同じ関数を通す** (式をコピーすると canary はコピーを検査するだけ)
- 🚨 **派生を複数持つ検証スクリプトは、派生どうしが違う値を出すことを先に確かめる** (同じ値なら片方が適用されていないを疑う)
- 🚨 **分類器の fallback ラベルは、真の判定と見分けが付かない**。発火しない枝それ自身にカウンタを持たせる
- 🚨 **集計は bash で書く** (zsh は無マッチの glob を NOMATCH でコマンドごと中断する)

## 構造で守れるなら守る

同じ配線漏れが繰り返す箇所は、運用ではなく機械で止める (実例: obaket `macOS/bin/check-lint-gate-wiring`)。

## やらないこと

- ✗ exit code 0 だけを見て「通った」と報告する
- ✗ 個別に直接叩いた結果を集約経路の証拠として使わない (集約経路から実行して確認する)
- ✗ 完了通知・プロセスの生死で非同期の完了を判定する (まだ走っているものを「壊れている」と誤診する)
