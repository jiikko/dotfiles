# 検証は「exit code」ではなく「実行された証拠」で判定する

## ルール

- **検査・テスト・gate を「通った」と判断する前に、それが実際に実行された証拠を出力で確認する**。
  exit code 0 は「失敗しなかった」であり、「**そもそも走らなかった**」も含む
- **利用者 (人・agent) に「こうすれば〜になる」と約束する出力文 (usage・`--help`・エラーの案内・先頭の一行) は、書いた同じ変更の中で、約束の操作を実機で 1 回通す**。隣の経路 (`gate` など) で成り立つことを、同じ名前の別の経路に当てはめて書かない (dotfiles の dupscan: `sweep` の「`dupscan:allow` で静かになる」は、`sweep` が許可印を見ておらず偽だった。retro 953)
  - **出力が次の操作を案内する機能 (続きの取得・ページング・診断の直し方) では、代表の案内を実際に打ち直し、新しい情報が得られるか、同じ案内を繰り返さずに続きが終わるかを確かめる**。
    argv が実行できること (rc=0・構文・scope) と、その操作が進展することは別に確かめる
- **新設した検査を最初に配線したときは、必ず「その検査の出力が現れること」を確認する**
- **最後の編集の後に、変更したファイルを実際に検査する gate (CI と同じ lint・テスト) を回す**。途中で回した検査の緑は、その後の編集を
  検査していない。push の前に他人の commit を rebase / merge で取り込んだら、それも編集に数えて push する木で回し直す (obaket retro 1062)。別の検査 (analyze で strict lint の代わりにする等) で代用しない。関係しそうな suite だけを選んで回すのも代用で、
  応答の形・外部への request の列を変える変更は、名指ししない suite の stub (contract / golden) に効く。実行を禁じた検査は既存 rule のとおりユーザーに委ねる
  - **non-fast-forward で弾かれた push を再試行するときは、rebase で入った差分が自分の検査の範囲 (モジュール・パッケージ) に触れるかを数え、
    触れるならその検査を回す段を再試行の中に置く**。手で打つ再試行は「もう一度 push するだけ」に縮む。**触れないと数えたなら、その検査は回し直さず pre-push の gate だけで push してよい**
    (上の「取り込んだら回し直す」の例外。触れるかはファイルではなくモジュール・パッケージの単位で数える。別のファイルでも共有の API・設定を通じて効く。
    数えずに省かない)
  - **手元の検査が CI より狭い範囲しか回さないと知っている変更 (scope の切り替え・`-run` の絞り込み) では、push の後に CI の結果を待ってから次の push・完了報告へ進む**。
    待たないなら CI の範囲を手元で 1 回回す
  - **手元の検査のログに skip / fallback の行 (`not found; skipping` / `falling back to`) が出ていたら、「狭いと知っている」状態に数える**。
    緑を読む前にその行を探す
- **パイプの終端の status を見ない** (`cmd | tail` の `$?` は `tail` の status)。`set -o pipefail` を使うか、リダイレクトしてから rc を取る
  - 🚨 **成否で後段を走らせる `&&` のつなぎを書いた瞬間にも発動する**。`git push ... 2>&1 | tail -2 && <後段>` は push が落ちても後段が走る。
    前段は `> log 2>&1; rc=$?` で取り、`[ $rc -eq 0 ] || exit 1` で止めてから出力を読む
    (検査 (make / go test / lint 等) の出力を tail / head / grep に通して `&&` で commit / push へ繋ぐ形は、PreToolUse の
    `_claude/hooks/deny-piped-push-then-destroy.sh` が止める。字面で見る粗い判定で、検出しない形は hook の冒頭)
- **検証コマンドの出力を `tail` / `head` / `grep` で削って読まない。ファイルへ落としてから読む** (削ると失敗の原因そのものが消え、再実行で緑なら追えない)
  - **stdout / stderr を分けたら両方読む**

## なぜ

根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/verify-execution-not-just-exit-code.md` (起動時には読まれない。改訂するときに読む)。

## 確認の仕方

| 対象 | 「走った証拠」の取り方 |
|---|---|
| lint gate / 検査スクリプト | その gate 固有の出力行を `grep` する (件数を出す設計にしておく) |
| 新規テスト | 指定した検証経路で対象テストが pass したことを確認する。テスト名・started・suite passed だけで判断せず、skip を実行の証拠に数えない (環境や profile が合わないと XCTSkip するテストは、名前も suite passed も出たまま何も検査しない。swift-smbee retro 109) |
| CI 上の検査 | ログに出力行があることを確認する。緑という結果だけで判断しない |
| 集約 target への配線 | 集約 target 経由で実行して出力を確認する。個別に直接叩いた結果で代用しない |
| CI のジョブに足す依存 | 足す前に、それを使う検査がそのジョブの target から呼ばれる鎖を Makefile / workflow で辿り、ログに検査名が出ることを見る (手動専用の検査のために Go を足しかけた。retro 644)。**依存を要するテストを足すときも逆向きに同じ鎖を辿り、そのテストが走るジョブに依存があるかを見る** (concat のテストに Go を要する検査を足したのに、heavy のジョブは Go を入れていなかった。retro 690) |
| 既存の物に足す依存 | スクリプト・module に新しい依存 (source する lib・replace・設定ファイル) を足したら、**その物を別の場所へ写して動かすテスト**と**依存を名指しで並べる一覧** (CI の paths・走査の根・allowlist) を同じ変更の中で grep し、写しと一覧にも足す (本体のテストは緑のまま、写した先・一覧の検査だけが赤くなる。retro 784 で 2 回) |

**収集 0 件 / 対象 0 件は失敗扱いにする**。`検査対象 N 件を確認` のように数を出しておくと空振りが見える。
入力 (ディレクトリ・ファイル群) が複数あるなら、**入力ごとに**「無い」「列挙に失敗した」「在るが見た対象が 0 件」を失敗にする
(数えるのは見た対象の件数で、違反の件数ではない)。合計だけで判定すると、1 つの入力が空振りしても他の入力の件数で緑になる (obaket 854)。
**測る API が値を返さない・0 を返すときも同じで、「測れない」と「0」を別の値で持つ**。空・描かれない・取得できないを 0 に畳むと、
検査はそれを「問題なし」か「最大の問題」のどちらかに誤読する。「測れないなら飛ばす」に直すのも同じ畳み方で、測れない対象は失敗か
判定不能として出す (retro 813: 外接矩形 (0,0,0,0) を座標として読み、直した「矩形が無ければ測らない」が display: none を黙って通した)。

**「全件の検査が見ている」を完了の根拠にするなら、対象を選ぶ filter (選択可能・登録済み・有効など) を辿り、
新しく足した項目が実際に検査されたことを、その項目固有の実行結果か対象一覧で確認する**。
件数で確認するなら期待する対象集合と照合する。合計件数が非ゼロ・想定どおりでも、別の項目との入れ替わりや skip は検出できない。

## 非同期・background の完了も「成果物」で判定する

- 完了通知・プロセスの生死は完了の証拠にならない。判定は「**その run 固有の成果物が、非空で、終了コードつきで存在する**」
- 出力先は毎回新規にし、rc と非空をあわせて見る (前回の残骸 / 起動直後の空ファイル / 書き込み途中を完了と誤認しない)。
  公開は完了時の atomic rename か done marker で行う
  - **起動に失敗した run (引数エラーで即終了など) が書いた成果物も「前回の残骸」に含まれる**。起動し直すときは出力先を変える。
    「死んだ」と判断して起動し直す前に、前の run のプロセスが生きていないことを確かめる (生きているのに 2 本目を起こすと、同じ作業根に 2 本が書く)
- **自分が起動した子は `wait` して rc を取る**。`cmd > out &` の直後の `$?` は起動の成否でしかない
- 🚨 **`pgrep -f` で待たない**。パターンが待機コマンド自身の command line に現れると自分にマッチし、
  `until ! pgrep -f "..."` は**永久に待つ**。待つ対象はプロセスではなく成果物にする (`until [ -f <outdir>/runs.tsv ]`)
- **ラッパーの rc を本体の rc と読まない** (複合コマンドを丸ごと非同期で回すと、報告される rc は最後の `echo` のもの)。自分が仕込んだ `rc=` 行を読む
- **検証の手順は `&&` で繋ぎ、`;` で繋がない**
- **background / detach する出力先は repo root からの絶対パスをリテラルで書く** (`$PWD` / 相対パスはツールの cwd が呼び出し間で戻るため別の場所に出る)。
  待つ対象は実行側が必ず書く成果物にし、待機ループには上限を置いて、超えたら「判定不能」を出す
- **ツールの実行時間上限を超えうるコマンドは、起動前に継続実行と終了コードの取得方法を決める**。
  ツールが実行を維持する session / yield を提供するならそれを使う。上限後のプロセス・出力経路が保証されないなら、
  最初から detach し、実行本体の終了コードを run 固有のファイルへ書く。detach だけを接続切断の対策と見なさない
  - **push は pre-push の gate 通過だけで成功扱いにしない**。push 本体の rc=0 と remote の対象 ref に commit が載ったことを確認する。
    hook の成功行だけを見て後段の参照更新や worktree 削除を進めない
- **待つと決めたら待つ**。張った待ちの完了通知が来るまで手動ポーリングを重ねない。同じ条件の待ちを 2 本以上張らない (信用できないなら待ちの側を直す)
  - **待ち始めに「いつまで待つか・超えたらどうするか」を決めてユーザーに伝える** (長いレビュー・CI・計測)。黙って待つと
    「スタックしていない？」と聞かれるまで何も見えない
- **待機タスクを止めると同じ process group の子も死ぬ**。長寿命プロセスは待機とは別の呼び出しで起こす
- **検証・計測がバックグラウンドで走っている間は、止めるか終了を見届けるまで同じ対象を編集・計測しない** (ツールの上限で回ったものも、
  自分で背景に起こしたものも)。続きは古い版のまま走り、残骸と計測値を新しい版のものに見せる。編集したくなったら、止めてから編集するか
  別の worktree で編集する

早すぎた判定は「相手が空振りした」という誤った因果を作り、後続の判断が全部その誤診の上に建つ。

## 実行環境を変えたら、変更前後の出力を全行 diff する

CI の runner / OS / 依存を差し替えたら、緑どうしの比較で終わらせず、**両 run の出力を全行突き合わせる**。件数は当てにならず
(ファイル数が同じでも中で skip に化ける)、skip はファイル単位では合格に見える。「skip しそうなガードを grep する」では
自分が思いつく形しか見つからないので弱い。

**手元と CI で toolchain の版が違うなら、push の前に CI と同じ版でも 1 回回す** (CI が go.mod の `go` 行・`.tool-versions` 等から
版を決める repo。Go なら `GOTOOLCHAIN=go<版> go test ./...`)。その版でだけ出る不具合は、CI が赤くなるまで見えない
(dotfiles の chromecookie: go1.25.0 でだけ `os.Root` 由来の `DirEntry.Info()` が失敗した。esa-cli issue 014)。

## 確認を求める外部コマンドは、非対話だと「何もせず rc=0」で返る

`[y/N]` を出す CLI は stdin が EOF だと中止して成功終了する (出力にはプロンプト文が出ている)。

- 判定は rc でも出力の有無でもなく、**その操作の効果が観測できるか**。測れないなら非対話用のフラグでプロンプト自体を出さない
- **対話の中で書き込み・保存の成否を例外や rc で判定するときも同じ**。確認で断られる・一部だけ書ける経路でも例外 / rc が出るかを
  確かめ、出ないなら結果の状態 (変更が残っていないか・書いた内容) で判定する (retro 872: nvim の `pcall(vim.cmd, "wall")` は上書きの確認に
  n と答えると例外を投げずに戻り、続く `:cquit` が編集を捨てた)
- **外部コマンド / アプリへ設定を書いたら、同じ手順の中で読み戻して比較する** (受け側が黙って代替値へ差し替えることがある)
  - **読み戻しは、書いた道具ではなく、アプリが実際に読む置き場所で行う**。書いた道具と同じ道具で読むと、両方が同じ別の場所を見ていても一致する
    (screen-share-app 813: sandbox の container が残っていると `defaults` は container の plist を読み書きし、sandbox なしのアプリは `~/Library/Preferences` を読んでいた。`plutil -p <実ファイル>` で分かった)
  - ファイルを書くツールも同じ: 渡した内容の `\uXXXX` の表記が、文字そのものに変わって保存されることがある (2026-10-06 に 2 回。Go の
    `"\u003c"` が `"<"` になった)。書いた直後に表記を grep し、化けるなら `\x5c` などツールが解釈しない形にする (retro 642)
  - **ツールが自分の判定に使う値 (spec・hash・fingerprint・schema の版) を手で移行・修復するときは、その値をツール自身に計算させる** (ツールの関数・subcommand を呼ぶ)。
    計算式を写して手で出さない (呼ばれ方の違いでずれ、ずれると判定が黙って逆に働く)。書いた後は、壊さない操作 (status・dry-run) でツールが「変わっていない」と
    答えることを確かめてから、作り直しうる操作を走らせる
- **表示・コピー用と実行用でコマンド文字列を分けない**

## 起動しなかった / 取り消された run は、その commit を検証していない (path filter・concurrency)

- `paths:` 付きの workflow は、対象を触らない commit では起動しない。判定は commit ではなく**範囲**で行い、
  最後にその workflow が走った commit から HEAD までに対象を触った commit が挟まっていないかを見る
- HEAD が対象を触っていないなら、その緑は HEAD を検証していない
- **`make test` に lint が入っていない repo では、Go / shell を触った commit ごとに lint を別に回す**
- **concurrency で取り消された (cancelled) run は、失敗でも成功でもない**。続けて push すると前の commit の run は取り消される。
  その commit は、それを含む後の commit の run で確かめ、待ちもそちらに張り直す (`gh run list --commit` は完全な sha で渡す。retro 647)
- **CI の起動経路を増やしたら (手動起動の入力など)、同じ SHA の複数 run を読み手 (verifier・集計) が区別できるか確かめ、必要な修正を同じ変更で行う** (event・ref・入力・run ID)。
  起動の前に concurrency group と取消の条件も読み、必要な検証の run を取り消さない経路を選ぶ (swift-smbee retro 110)

## 集約テストが赤いまま、その上で検証を続けない

取れる手は 2 つだけ: **直す**か、**落ちている検査の名前を控えて「この検証はその検査を含まない」と報告に明記する**。
「環境由来なので無関係」と分類しただけで黙って続けない。
- **赤の帰属は、集約が最後に出す「失敗した対象」の一覧を全部読んでから決める**。予想した種類の失敗の行だけを grep して拾うと、別の種類の検査の赤が
  帰属から漏れる

## 隔離環境での成功は、本番での成功ではない

- 報告の前に「私が動かしたファイルは、ユーザーの環境で実際に読まれるファイルか」を問う。実体パスから起動されるもの
  (hook / bind が指すスクリプト / PATH 上のコマンド) は push しただけでは反映されない
  (dotfiles の正本は `.claude/rules/worktree-per-session.md`)。`status -sb` の `behind N` や mtime で版を見る
- **テストが cwd の repo の git の状態 (branch・upstream・`@{push}`・設定) を読む経路は、既定で差し替える**。worktree (detached)・CI の checkout
  (branch が origin と並ぶ)・開発機の本体で同じテストの結果が変わり、どこか 1 か所でしか赤くならない
- **裏返しも同じ。隔離環境での失敗も本番の失敗ではない**。赤を報告する前に、用意した実行環境が本番と同じものを読んでいるか確かめる
  (`nvim -l` はユーザー設定を読まない、等)
- **「複数の版 (bash / Go / Python) で通った」と書く前に、検査対象そのものがその版で走ったことを出力で確かめる**。テストを起動した
  版は子プロセスの版を決めない (shebang・PATH・toolchain の指定で決まる)。版が効く検査なら、テスト側で対象を版ごとに明示して起動し、
  走った版を出力に出す

## キャッシュされた緑と path filter は、鍵に数えない入力の変化を見ない

テストがキャッシュ鍵にも paths filter にも入らない入力 (module の外のファイル・生成物・環境) を読むなら、**cached の緑は証拠ではない**
(Go の testcache は module root の外の open/stat を再チェックしない)。**キャッシュ無効で走らせ、そのテスト固有の PASS 行を grep する** +
読む対象を workflow の paths に載せ、その配線を検査で固定する。

## 「有無で結果が変わらない観測」を証拠に数えない

観測が**対立仮説を棄却できるか**を先に問う。判定: **「その機構を外したら、この観測結果は変わるか?」** に yes と答えられないなら観測を設計し直す
([`mutation-verify-new-tests.md`](mutation-verify-new-tests.md) の観測版)。

- **切り分けで動かした変数を数える** (副作用で別のものまで変わる操作がある。`TMPDIR` を変えると go のビルドキャッシュも空になる)。
  「別の環境では再現しなかった」は原因の否定にならない。正しい切り分けは ①条件を変えずに同じ HEAD で 2 回回す
  (1 回目赤・2 回目緑なら環境でなく非決定性) ②緑だった時点と赤い時点を同じコマンドで比べる
  **隔離した値が検査対象の中で実際に使われたかを、「再現しない」と結論する前に 1 回確かめる** (環境変数・設定 dir・一時 dir で環境を隔離した調査すべて。`go test` の `t.TempDir()` は `GOTMPDIR` を使うので、`GOTMPDIR` を小さい dir にして「実 `$TMPDIR` では再現しない」と読みかけた。対象の中で一時 dir の実パスを出して、隔離したパスが現れたかを見る)
- 前後の比較は**同じ抽出方法・同じ入力**で行う。修正の後は、修正の前に赤を見たのと同じ入力で測る。入力を変えるなら、変えた入力で
  修正の前も赤になることを先に見る (直した機構を通らない入力は、修正の有無に関係なく緑になる)。**最適化が近道 (早く返る分岐) を足すなら、測る操作がその近道を通るかを数え、前後で同じ仕事の量を
  測る** (近道を通ると 1 回の操作の中身が変わり、比が改善を誇張する。retro 730)
- **崩し・fixture・変異体を作ったら、走らせる前に「作る前と違う状態になった」ことを機械で確認する** (`diff -q`)。
  整形・正規化を通すときは、その整形が崩しを打ち消さないか特に見る (コードへの変異は mutation-verify の手順 1.6 が正本)
  - **ファイルを書き換えるスクリプト全般 (python の replace・sed・perl) も、置換が当たった件数を確かめ、0 件なら落とす**。0 件の置換は黙って成功し、
    後の検査は「直したつもり」の状態を緑で検査する
- 崩れを確認しても、「放っておいても同じ結果になる」可能性は別に潰す (機構を外した**負の対照**を 1 本置く)。
  崩れの確認が言えるのは「入力が違う」までで、「直したのが自分の機構か」は言わない
- **観測できた経路と、主張する範囲を一致させる**。1 経路で確かめたことを「常に」「全経路で」と書かない。一般化する前に
  分岐しうる条件 (署名・sandbox・環境変数・ビルド構成) を挙げ、挙げられないなら主張を観測した経路に限定する。
  成果物が在ることは「その経路が一度使われた」証拠にしかならず、無いことは経路の不在の証明にならない
- **プロセス・シグナルの観測は、「残り 0」を読む前に照合が当たること・シグナルが届く相手であることを確かめる**。macOS の `ps` は `-ww` が無いと
  コマンド行を切り詰める / 非対話のシェルが `&` で起こした子は SIGINT を無視した状態で始まる / 子の `mktemp` は渡した `TMPDIR` を使わないことがある

- **入力の母集合も同じ。効果を実データで測るなら、利用者が使う入力源を挙げ、規約の違うものを最低 2 つ含める**
  (別の repo・別の書き手・別の形式)。1 つの母集合での成功率を一般の成功率として書かず、測れなかった入力源は「未測定」と書く

## 抽出・判定を書いたら、同じ経路を通る canary を先に置く

抽出が空を返すと「違反 0 件」= 緑になる (走ってもいるし出力も出るので上の節では捕まらない)。

- **既知の入力で既知の答えが出ることを、本走査の前に固定する**。「この repo なら必ず 1 件は当たる」入力を選ぶ
- **射程は自作の検査スクリプトに限らない。その場の調査の使い捨て 1 行にも要る**。発動点は「不在を根拠にしようとした瞬間」で、
  **必ず在るはずのもので先に較正してから**使う (`strings <binary> | grep` は Swift の文字列リテラルを拾えない、等)
- **非同期に索引を作る道具 (LSP・Spotlight・IDE) の検索も、同じ検索経路で既知の名前を先に引く**。既知の名前まで0件なら、索引未完了・対象範囲の違い等の原因は未確定として、本検索の0件を不在の根拠にしない
- **canary と本走査は同じ関数を通す** (式をコピーすると canary はコピーを検査するだけ)
- **派生を複数持つ検証スクリプトは、派生どうしが違う値を出すことを先に確かめる** (同じ値なら片方が適用されていないを疑う)
- **操作の台本を流す道具 (計測・E2E・負荷) を書いたら、段ごとに「その段で状態が変わった」ことを、作った時点の煙テストで名前の完全一致で確かめる**。
  状態を記録する列を作るだけでは読み手が空打ちを読み流し、「前と違う」「空でない」のような緩い確かめは別のキーが効いただけで満たされる

- **分類器の fallback ラベルは、真の判定と見分けが付かない**。発火しない枝それ自身にカウンタを持たせる
- **集計は bash で書く** (zsh は無マッチの glob を NOMATCH でコマンドごと中断する)

## 構造で守れるなら守る

同じ配線漏れが繰り返す箇所は、運用ではなく機械で止める (実例: obaket `macOS/bin/check-lint-gate-wiring`)。
