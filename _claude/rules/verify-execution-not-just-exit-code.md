# 検証は「exit code」ではなく「実行された証拠」で判定する

## ルール

- **検査・テスト・gate を「通った」と判断する前に、それが実際に実行された証拠を出力で確認する**。
  exit code 0 は「合格」ではなく「**失敗しなかった**」であり、
  「**そもそも走らなかった**」も含む
- **新設した検査を最初に配線したときは、必ず「その検査の出力が現れること」を確認する**。
  `make lint && echo ok` / `pytest -k new_test` の exit 0 だけで満足しない
- **パイプの終端の status を見ない**。`cmd | tail` の `$?` は `tail` の status。
  必要なら `set -o pipefail` を使うか、リダイレクトしてから exit code を取る

## なぜ

起源: 2026-08-23 obaket、同一セッションで 3 回踏んだ。根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/verify-execution-not-just-exit-code.md` に置く（起動時には読まれない。ルールを疑う・改訂するときに読む）。

## 確認の仕方

| 対象 | 「走った証拠」の取り方 |
|---|---|
| lint gate / 検査スクリプト | その gate 固有の出力行を `grep` する (件数を出す設計にしておくと確実) |
| 新規テスト | テスト名が実行一覧に出ることを確認する (`-only-testing` の vacuous pass 対策と同根) |
| CI 上の検査 | ログに出力行があることを確認する。**緑という結果だけで判断しない** |
| 集約 target への配線 | 集約 target 経由で実行して出力を確認する。個別に直接叩いた結果で代用しない |

**「件数を出す」設計が効く**: `検査対象 N 件を確認` のように数を出しておくと、
0 件や想定より少ない数を見た瞬間に空振りが分かる。収集 0 件を失敗扱いにするのも同じ発想。

## 非同期・background の完了も「成果物」で判定する

- 完了通知・プロセスの生死は完了の証拠にならない。判定は「**その run 固有の成果物が、非空で、
  終了コードつきで存在する**」で行う
- `until [ -f <artifact> ]` だけでは足りない。**前回の残骸ファイル / 起動直後に作られた空ファイル /
  書き込み途中のファイル**を完了と誤認する。出力先は毎回新規にし、rc と非空をあわせて見る
  (`codex-fanout` が outdir の使い回しを拒否し `runs.tsv` に rc を残すのはこのため)
- **`pgrep` の存在確認で待たない**。`-f` は command line 全体を見るため、パターンが
  **待機コマンド自身の command line に現れると自分にマッチする** (2026-08-26 実測)。
  パターンを凝らすより、**自分が起動した子は `wait` して rc を取り、その後に成果物を見る**
  (`bin/codex-fanout` もそうしている)
- **rc は `wait` 後のものを使う**。`cmd > out &` の直後の `$?` は**起動の成否**であって
  `cmd` の終了コードではない。書き込み途中の成果物を掴まないよう、公開は完了時の
  atomic rename か done marker で行う

**実害は「待ち直し」では済まない**: 早すぎた判定は「相手が空振りした」という**誤った因果**を作り、
代替作業への切り替え → 遅れて完了した出力が同じパスを上書き → **commit された成果物の出所を
取り違える**、まで連鎖する。「まだ走っている」を「壊れている」と読むと、後続の判断が全部その誤診の上に建つ

## 実行環境を変えたら、変更前後の出力を全行 diff する

CI の runner / OS / 依存を差し替えたときは、**緑の比較で終わらせない**。同じ「全部緑」でも、
**中身が入れ替わっている**ことがある。

- **件数は当てにならない**。テストファイル数が同数でも、その中で skip に化けたものがある
  (実例: 96 → 96 ファイルのまま `✓` 行が 68 件消えていた)
- **skip はファイル単位では合格に見える**。runner の集計が `[ok]` を出すので、緑の側からは
  観測できない。消えたことが分かるのは**両 run の出力を全行突き合わせたとき**だけ
- 「skip しそうなガードを grep する」では弱い。それは自分が思いつく形しか見つけられない

## 構造で守れるなら守る

同じ配線漏れが繰り返す箇所は、運用ではなく機械で止める
(実例: obaket `macOS/bin/check-lint-gate-wiring` = gate target が集約 target に
配線されているか / `.PHONY` 漏れ / allowlist の stale を検出する meta-gate)。

## やること / やらないこと

- ✓ 検査の合格判定は「その検査の出力が出たか」で行う
- ✓ 新設検査は集約経路から実行して出力を確認する
- ✓ 収集 0 件 / 対象 0 件は成功にせず失敗扱いにする
- ✓ 実行環境を差し替えたら、変更前後の出力を全行 diff する (緑どうしの比較で終わらせない)
- ✓ 非同期・background は、毎回新規の出力先に出た**非空の成果物 + `wait` 後の rc** で完了を判定する
- ✓ パイプを挟むなら `set -o pipefail`
- ✗ exit code 0 だけを見て「通った」と報告する
- ✗ `cmd | tail` の `$?` を cmd の status として扱う
- ✗ 個別に直接叩いた結果を「集約経路でも走る」証拠として使う
- ✗ 完了通知・プロセスの生死で非同期の完了を判定する (まだ走っているものを「壊れている」と誤診する)
