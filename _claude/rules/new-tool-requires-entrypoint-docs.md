# 新しいツール・スクリプトを導入したら、同じ変更で「入口のドキュメント」を更新する

## ルール

- **再利用される道具（スクリプト / CLI / Makefile target / lint ルール / ヘルパー）を新設したら、
  それを見つけられる「入口」を同じ変更の中で更新する。** 道具だけ足して終わりにしない
- 更新すべき「入口」は、**その作業をこれからやる人が実際に読む場所**:
  - その作業手順を持つ **skill (`SKILL.md`)** ← 最優先。手順書に載っていない道具は使われない
  - その領域の **CLAUDE.md / README**（規約や運用の正本）
  - 既存の類似ツールの **一覧表 / 関連リンク**（`cutout-sheet` があるなら `cutout-single` も並べる）
- **ツール自身のヘッダコメントは「入口」に数えない**。そのファイルを開いた人にしか届かず、
  開く動機は「存在を知っている人」にしかない。循環しているので単独では機能しない。**rationale はコードに、使い方は手順書に**置く
- 既存ツールと**紛らわしい/使い分けが要る**ものを足したときは、**判断基準を 1 行で書く**。
  「どちらを使うか」が読んで即決できない記述は、書いていないのとあまり変わらない
- 道具を**消した / 置き換えた**ときも同じ。入口に古い道具が残っていると、存在しないものへ誘導する

## なぜ

根拠・起源・実例は `~/dotfiles/_claude/rules-rationale/new-tool-requires-entrypoint-docs.md` (起動時には読まれない。改訂するときに読む)。

## タイミング

**道具を commit する変更に含める。** 「あとでまとめて」にしない。

理由: ツール単体の commit は「動くから完了」と感じられて、そこで作業が閉じる。
一度閉じたものを開き直す動機は生まれない（起源の実例では翌日まで放置された）。

## チェック（道具を足したら自問する）

- [ ] この道具を**使うべき場面に遭遇する人**は、どの手順書を読むか。そこに書いたか
- [ ] 似た道具がすでにあるか。あるなら**どちらを使うかの判断基準**を書いたか
- [ ] 一覧表・関連リンクに並べたか（片方だけ載っている状態にしていないか）
- [ ] 自分が半年後にこの作業をするとき、**ツールの存在を思い出せなくても**たどり着けるか

## 適用しなくてよいもの

- そのタスク限りの使い捨てスクリプト（`./tmp` に置いて消すもの）。
  ただし**2 回目に使いたくなった時点で**このルールの対象になる
- 既存の道具の内部実装だけを直した場合（使い方が変わらないなら入口の更新は不要）
