# 800 (research): 複数の Mac に同時に高性能モードで繋げるか

起票日: 2026-10-16

> epic 793 の子。要望の 5 つ目。自作する意味が一番大きく変わる問い。

## 要望 (ユーザーの言)

「ハイパフォーマンスに接続できる mac が 1 台だけで制限が多い」

## 調べたこと (2026-10-16)

- Apple:「Only one High Performance screen sharing session can be active on each Mac at a time.」
  ([Apple](https://support.apple.com/guide/remote-desktop/apdf8e09f5a9/mac)。Apple Remote Desktop のガイドの文書で、Screen Sharing.app の文書ではない)。
  文言は見る側にもかかると読めるが、文言だけでは決まらない。標準アプリで 2 台に同時に繋げないことの根拠は、ユーザーの体験 (要望の「1 台だけ」)
- この制限が、見る側のアプリ (Screen Sharing.app) の中の制限か、相手の Mac が断る形かは、文書から分からない
- 見る側の 1 台から 2 本同時に高性能で繋いだ報告は見つからなかった (反証レビュー)
- iShareScreen と rootshell-vnc の README には、複数のセッションについての記述が無い

## 実測 (2026-10-16 18:40、手元 = kojiM3MacBook-Pro。標準アプリで 2 台に繋いでいる最中を、読むだけの観測で測った)

| 相手 | モード (判定の根拠) | 経路 | 網の往復 (ping 20 回) | 流量 (nettop、2 秒あけて 3 回取った差) |
|---|---|---|---|---|
| m2macmini.local (169.254.217.100) | **高性能**: avconferenced が UDP 5900 をこの相手と結び、UDP 5901 も持つ | en13 (Thunderbolt Ethernet、有線) | 平均 0.48 ms (最小 0.38 / 最大 0.60) | 映像の UDP 5901 は約 4 KB/秒 (約 35 kbps)、UDP 5900 は約 2.7 KB/秒。制御の TCP 5900 はほぼ 0 |
| m1prombp.local (fe80::1093:de36:851:b7fa。mDNS の PTR で特定) | **標準**: Screen Sharing.app の TCP 5900 (IPv6) だけで、UDP の相手にならない | en13 (同上) | 平均 1.01 ms (最小 0.50 / 最大 1.28) | TCP で約 50〜90 KB/秒 (0.4〜0.7 Mbps) |

- 標準アプリ 1 つ (pid 1223) が、高性能 1 本と標準 1 本を同時に持っている。ユーザーの言う「高性能で繋げるのは 1 台だけ」と合う (2 本目は標準に落ちる)。
  これは「見る側の Mac で 1 本」を支持する観測で、相手の Mac が断っているのかは分からない (2 本目の相手に高性能を試したわけではない)
- UDP 5901 は相手を固定しない受け口 (`*:5901`) で、高性能の映像はここに届く。高性能を 2 本持てたとき、2 本目の映像が同じ口に来るかは未確認
- 測ったのは網の往復と流量だけ。**キーを押してから相手の画面が変わって手元に映るまでの時間 (操作の遅れ) は測っていない**。網の往復が 1 ms 前後なので、
  遅れの大半は相手の撮影・符号化と手元の復号・描画にあるはず (見積もり)。測るなら、手元の画面を 120 fps で撮ってコマを数える
- 流量はその時点の画面の動き次第 (アイドルに近い状態で測った)。高性能のアイドル中は 35 kbps 程度で、常時接続の重さ (798) は小さい見込み

## 確かめること

- [ ] 手元の Mac から 2 本起こし、別々の 2 台へ同時に高性能モードで繋ぐ。2 本とも映像が流れるか。起こし方:
  - iShareScreen を Terminal から 2 本 (一番安い。ただし Terminal から走らせた道具はローカルネットワークのプライバシーの対象外で、自作のアプリの条件を代表しない。796)
  - rootshell-vnc のビューア (Catalyst) は 1 つのアプリなので、`open -n` で 2 つ起こすか、1 つの中で 2 セッションを持つ
- [ ] 繋がらない場合、どちらが断ったか (相手の Mac のログ・制御の TCP の応答)
- [ ] 2 本目が繋がったとき、1 本目が切られないか (見る側の Mac で標準アプリが同時に動いていないことも確かめる)
- [ ] 2 本同時のときの帯域と手元の復号の負荷 (VideoToolbox の HEVC の復号を 2 本並べられるか)

## 結果で決まること

- 繋げる → 自作の意味がある。798 の常時接続を複数台で組む
- 繋げない (相手側が断るのではなく、手元の何かが止める) → 何が止めているかを調べる
- 繋げない (仕組みとして 1 本) → 高性能は 1 台だけにし、残りは標準モード (VNC) で繋いでおく形を考える。または 795 の系統 2
  (相手に自作のサーバを置く) を検討する

## 案: 使っていない間は標準に落とし、触り始めたら高性能に上げる (ユーザー案 2026-10-16)

「高性能モードで接続しても inactive になったら標準モード相当に落として、操作を始めたら高性能モードに自動でモードが変わる」

- 高性能の 1 枠を、いま触っている Mac に渡し続ける。「1 本まで」が仕組みとして外せない場合 (上の「結果で決まること」の 3 つ目) の本命の回避策
- 合図: 自作アプリでその Mac の画面を前面にした瞬間 (ショートカットでの切り替え・一覧で選ぶ) に上げ、前面から外れたら落とす
- 確かめること (段 0。802):
  - [ ] 標準から高性能への切り替えにかかる時間。モードを繋いだまま変えられるか、繋ぎ直しになるか (標準アプリで高性能に繋ぐまでの秒数を測る)。
    1 秒を超えると「選んだらすぐ切り替わる」(798 の受け入れ条件 0.5 秒) とぶつかる。上げている間は、前の標準の画面を映したままにして待ちを隠せるか
  - [ ] 行き来のたびに相手の Mac のディスプレイの構成が変わり (高性能は仮想ディスプレイを作って実物を暗くする、標準は実物をそのまま映す)、
    相手のウインドウの位置や解像度が並び替わらないか。仮想ディスプレイを「ミラー」で使えば避けられるか
  - [ ] 落とす・上げるを短い間に繰り返さない工夫 (前面から外れてから落とすまで数秒待つ、など)

## 標準モードで足りないか (ユーザーの問い 2026-10-16)

「ハイパフォーマンスにしなくても有線で接続しているなら、遅延がほぼなく画面共有できるのだろうか」

- **未実測**。標準と高性能を同じ有線で比べた数値の資料は見つからなかった (Apple の文書にも数値は無い)
- 見積もり: 有線の網の往復は 1 ms 未満なので、遅れの大半は網ではなく相手の Mac の撮影と符号化にある。標準モードは VNC (TCP) で、画面の
  変わった部分を CPU で符号化して送る。文字の入力・ターミナル・ブラウズのように変わる面積が小さい作業は有線なら軽いはず。動画・スクロール・
  ウィンドウの移動のように画面全体が動くと、コマが落ちて遅れて見えやすい。高性能モードは Apple silicon の専用回路で HEVC に符号化し、
  4:4:4 の色・相手側の仮想ディスプレイ (手元の画面の大きさ・HiDPI)・音声が付く
- 確かめ方: 同じ有線で、同じ相手へ標準と高性能で繋ぎ、普段の作業 (ターミナル・ブラウザのスクロール・ウィンドウの移動) を比べる。
  数値が要るなら、手元の画面を 120 fps で撮り、キーを押してから相手の画面の文字が出るまでのコマを数える
- **標準モードで足りるなら、この issue の結論が「繋げない」でも問題が小さくなる** (高性能は 1 台、残りは標準で常時接続)

- [ ] 同じ有線で標準と高性能を比べ、普段の作業で標準モードが足りるかをユーザーが判断する
