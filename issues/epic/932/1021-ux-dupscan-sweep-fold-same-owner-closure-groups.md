# 1021 (ux): dupscan sweep の節 2 で、1 つの単位の中のクロージャだけの組 (表の行) を畳む

起票日: 2026-11-04

## 概要

treefiler で「統合できるメソッドはあるか」を `dupscan sweep src/treefiler` で調べた (2026-11-04)。節 2 の先頭 3 組 (28 件) と 5 組目・7 組目は、
`settings.go` の `items` の表・`tfperf` の `summarize` の列・`model.go` の `init` のキーの割り当ての、表の行のクロージャだった。
寄せる先が無いのに、読む順の先頭を占めていた。同じ組は 965 (2026-10-29 の treefiler の dogfood) でも「表の行で、寄せる対象ではない」と見送られており、
読み捨てたのは 2 回目。

## 対応

- 節 2 で、メンバーが全部クロージャで、囲む単位が同じ組を、組ごとの一覧から外す。外した組は節の最後に、囲む単位ごとに
  `<file> {closure} in <単位>: N 組 M 件` の 1 行へ畳む (消さない)。`-v` で畳まずに組ごとに出す
- 囲む単位が無いクロージャ (Go の package の変数の初期化子) は、ファイル・型・変数の名前で同じ単位とみなす
- 節 1 (既定の下限 20 節) は畳まない。節 2 でも、節が 20 (クロージャの既定の下限。`-min-closure-nodes` に連動させない) 以上の組は畳まない:
  大きいクロージャの写しは本物のことが多く、同じ関数で登録する handler の、メンバー名だけ違う本体は L1m なので節 2 にしか出ない
- 名前が `_` の変数の初期化子 (`var _ = register(…)` の並び) は宣言ごとに別の単位なので畳まない
- 畳んだ行も `-limit` で打ち切る
- 入れ子のクロージャは、すぐ外側のクロージャの鍵で数える (同じ関数の中でも、別のクロージャの中にある組は畳まない)

## 結果 (実測 2026-11-04)

- `src/treefiler`: 節 2 は 8 組 → 3 組 (`init` の 25 節のキーの割り当て、`intItem` / `boolItem` の set、tfprobe の `cycle` / `tile`)。畳んだ行は `items` 3 組 28 件・`summarize` 1 組 6 件・`init` 1 組 2 件
- `src` 全体: 29 組を畳んだ (20 節以上を畳まない前は 33 組)。2 件ずつの小さい組 (gate の `matchLoose` の照合関数の並び・restartable の `actor.run` の defer・
  doctor の `judgeSmart` の表・zundamon の `newEnv` の差し替え・glogx の testenv の panic の stub ほか) も読み、どれも同じ単位の中で並べた行で、寄せる写しは無かった

## 敵対的レビュー (opus 1 本、読み取りのみ)

P1 なし。直したもの: P2 大きい本物の写し (L1m の handler の対) まで畳む → 節が下限以上の組を畳まない / P3 `var _ =` の並びを 1 単位に数える → `_` を除く /
P3 `-v` の help に sweep の意味が無い → 共通の help に書き足す / P3 畳んだ行に `-limit` が効かない → 効かせる。
記録だけ (直さない): P3 Swift で関数の中に置いた局所の型の格納 property のクロージャは、囲む関数を鍵にするので、別の型・別の property でも 1 単位に畳む。
関数の中に局所の型を置き、その property に同じ形のクロージャの表を持つ形は稀なので、出たら property の鍵を owner に入れる。

2 回目 (直した差分だけ、opus 1 本): P2 畳む上限が `-min-closure-nodes` に連動し、0 で全部残す・上げると大きい写しまで畳む → 既定の定数 (20) に固定 /
P3 共通の `-v` の help に足した sweep の文が他の subcommand にも出る → sweep の説明の行へ移す。P3 `-limit N` で節 2 が最大 2N 行になるのは、数が合っているので残す。

## 見送り

- 節 3 の「mutex を取って欄を 1 つ読み書きする getter」の対 (treefiler の `diffJob.result` ~ `explodeJob.finished` ほか) も 965 と今回の 2 回出た。
  共有している部分木の大半が `mu.Lock()` / `defer mu.Unlock()` の定型。ただ、lock の定型を重みから外すと、lock の中身まで同じ本物の写しの順位も下がる。
  3 回目が出たら、定型の部分木を割り引く案を測る
