# 986 (design): dupscan を構造から直して grep の置き換えと類似メソッドの量産の抑止を実現する

起票日: 2026-10-30

## 概要

dupscan の 2 つの狙い (①定義・呼び出し元を探すときに grep に戻らなくて済む ②似たメソッドの量産を止める) が、今の構造でどこまで実現できているかの評価と、
構造に手を入れる改善の順。着手するときは項目ごとに子 issue に分ける (この issue は設計の地図と優先順位を持つ)。
一般的な効果は今も未実証で、測定は 948 で続いている。ここに書く「効いていない」「効きそう」は、下に挙げた個別の実測と構造の読みからの見立て。

## 今どこまで効いているか

### ① grep の置き換え: 広い名前では効く。狭い検索と型が要る検索では効かない

- 広い名前では軽い: `Join` で rg 446,145 B に対し `index` 2,900 B (epic 932 の「使われやすさと context 消費」)
- 定義 1 件の狙い撃ちでは rg の方が軽い: 942 で固定の注意書きを削って 738 B → 604 B にしたが、rg の 340 B には届かず未達のまま閉じた (948 の B が引き継ぎ)
- 型を解決しない: Go の `def` / `refs` が無い (944 は保留)。`callers` は名前だけで照合するので、`callers New` の出力の 55% (38 行中 21 行) が `errors.New` / `rand.New` だった (965 F4)
- 起点 (走査する dir) の中しか読まないので、起点で答えが変わる (966 F4・973。起点を絞ると allow-group の人数が狂う。973 で言語ごとに判定する形にしたが、判定の単位の限界は残る)

### ② 量産の抑止: 正規化して同じ形の写しの「追加」だけを止める

- 止めるのは CI と `make test` の gate (`dupscan gate`。止める段 `-fail-levels` の既定は L1・L2、下限 20 節、変わった単位が対象) の、正規化した形が一致する写しの追加
- 取りこぼしが多い: 4 module で寄せた 21 件のうち、既定の report が出したのは 4 件 (946)。量産の主な形は次の 2 つで、どちらも gate に入っていない
  - 少し変えた写し (文が 1 つ多い・リテラルが違う): opt-in の `near -similar` と sweep の節 3 でしか見えない
  - 既存の小さい helper の本体を手で書き直した所: sweep の節 5 でしか見えず、下限 20 節未満の単位とテスト関数の中は比べない (965 F1)
- 書く前に引く仕組み (hook の案内 `suggest-dupscan-for-*.sh`、新しい関数の直前に候補を差し込む `inject-dupscan-candidates-on-new-func.sh` = 948 の A1) はあるが、
  A1 は**名前の一致だけ**で引く (hook の冒頭の「名前の一致だけを出す」)。名前の違う同じ役割の関数は引けない。954 の P1 は戻り型で引けば見つかった本番の `location(at:)` の写しを作って push した例
- A1 の効果は測れていない: 948 の A-B は「既存関数を書き直した run が A 0/17・B 0/18」で天井効果。n=1 の観測では注入が出ても写しが増えた

## 既に決めてあること (この issue では変えない)

- **型の解決・LSP**: 899 の結論 (2026-10-27)「通常探索は構文近似を維持し、LSP・常駐 server・自動 build を導入しない」。強い根拠が要る場面の将来候補は、Go は明示実行の `go/packages`、Swift は新鮮な index store の読み取り
- **永続の索引・cache**: 924・925 で「永続 cache や常駐プロセスを最初から前提にしない」「初期版は永続検索 index を作らず、実測で必要性を判断する」。README は「キャッシュは持たず、引くたびに読む (DualNoteApp の 1130 単位で 0.5 秒。issue 897)」。
  解析結果の cache は持たない (gate の結果の記録 `-record` は別にある。976)

## ユーザー決定 (2026-10-30): C で進める

改善の 2・3 (量産の抑止) を進め、あわせて Go の型の解決 (grep の置き換えの壁を越える構造の変更) も入れる。「今の方式に超えられない壁があるなら、構造改革を視野に入れたい」。
型の解決は 899 の決定を Go について変える (LSP・常駐 server は引き続き入れない)。子 issue: 987 (改善 2)・988 (改善 3)・989 (Go の型の解決)。改善 1 (指標) は 948 に置く。

## 改善の順 (反証レビューを受けて組み直した)

### 1. 効果の指標を先に決める (948 に寄せる)

- 何が良くなるか: 2〜3 のどれが効いたかを言えるようになる (932 の本文も「一般的な効率改善は未実証」)
- 指標の案: commit あたりの新しい写しの数 (gate の記録から)、新しい関数を書く前に dupscan で引いた割合 (`scripts/dupscan_usage_report.py`)、定義・呼び出し元の探索で grep に戻った割合
- 定義は 948 に置き、この issue は「改善の前後で同じ指標で測る」約束だけを持つ。A1 の A-B が天井効果で測れなかった (小さい fixture を agent が全部読める) ので、課題の大きさの条件も 948 で決める

### 2. 書く前の候補を、名前以外 (戻り型・引数型) でも引く

- 何が良くなるか: A1 の弱点 (名前の一致だけ) を直す。954 の P1 の形 (名前は違うが戻り型が同じ本番の関数) を、書く直前に出せる
- 形の案: A1 の hook で、新しい関数の戻り型・引数型を `dupscan index -returns` / `-param-type` でも引き、名前の一致と合わせて出す。索引も型の解決も要らない (構文の字面の型で引く。899 の範囲の中)
- 未決: 雑音 (`error` や `string` を返す関数は多い。型の字面が汎用なら引かない等の規則)、hook の時間の予算 (今は全体で 6 秒)

### 3. gate に「変わった単位だけを既存の全部と近似比較する」段を、索引なしで試作して測る

- 何が良くなるか: 量産の本体 (少し変えた写し・既存の helper の手書き) を commit の時点で見つけられる
- 形の案: 差分で変わった単位 N 個を、既存の単位 M 個と部分木の Dice (sweep の節 3) と手書きの展開 (節 5) で比べる。仕組みは sweep にあり、足りないのは gate の差分範囲に絞る経路
- 費用: N × M に比例する (M にも比例する。Dice は部分木の多重集合どうしで 1 回が重い。sweep の `-similar-max-units` の既定 8000 が総当たりの上限)。
  移動・生成・一括の rename の commit では N が跳ねる。参考: 977 の obaket の実績で gate の中央値 44 秒 (同じ条件のベンチではない)。試作で時間と誤検知の率を実測してから入れるかを決める
- 入れ方: はじめは報告だけ。止める (rc=1) に上げる条件 (誤検知の率の閾値と、測る母集合 = どの repo で何件) を試作の前に決める。
  報告だけの段は読まれずに積み上がるので、報告の期間と見直しの日も決める。テスト関数の中は fixture の似た形で誤検知が増える見込み (965 F1) なので、はじめは見ない
- 受け入れ条件: 自分で作る検査なので、名指しする退行 (少し変えた写しを足す・helper の本体を手で展開する) を当てて赤を確認する (`adversarial-review-own-safeguards.md` §1.5) と、敵対的レビューを最終ゲートにする

## 記録だけにした案 (再開の条件つき)

- **常設の索引 (repo 全体・ファイルの hash で差分更新)**: 924・925 の決定 (実測で必要性を判断) を維持する。
  - 再開の条件: 3 の試作で M に比例する費用が実際に問題になったとき、または 2 の hook の時間の予算を超えるとき
  - 入れるなら先に決めること: 古い索引が「写しなし」の緑を返す形 (dupscan の版・正規化の規則の変更・worktree をまたぐ混線) の検出、複数のセッションが並行に書くときの排他、CI では毎回作り直すので手元の速さのためだけになる点
  - 索引では起点に依存する問題 (966 F4・973) は消えない: 原因は「どの範囲を母集合にするか」の定義で、読み直しの省略ではない
- **型の情報 (Go の go/packages、Swift の index store)**: Go はユーザー決定 (上) で 989 へ進めた。Swift は 899 の決定を維持する。下は決定の前に書いた条件 (Swift に残る)。
  - 再開の条件: 2 の後も、型が要る見落とし (名前も字面の型も違うが同じ役割) や `callers` の雑音 (965 F4) で grep に戻る割合が 1 の指標で下がらないとき。そのときも 899 の候補 (明示実行の go/packages) の範囲で、壊れた木で何を返すか (899 の「unknown を残す」) を先に決める
  - 944 (Go の def。本体つきで定義を返す) は別の軸で、この案の一部ではない (再開の条件は 944 本文の「943 の後も Read が続く割合」)

## 反証レビュー (2026-10-30、sonnet 2 体、読み取りのみ、観点は事実と設計)

最初の版は「1. 常設の索引 → 2. 型の情報 → 3. gate の近似段 → 4. 書く瞬間の候補 → 5. 指標」の順で、1 と 5 から始めるとしていた。次の指摘で組み直した:

- 事実 P2 (採用): 1 と 2 は 899・924・925 で既に「入れない / 実測で判断」と決めた方向で、触れていなかった → 「既に決めてあること」に書き、記録だけの案へ移した
- 事実 P2 (採用): 「340 B / 738 B」は 942 の前の値 (今は 604 B 対 340 B)
- 事実 P3 (採用): 944 は型の解決の一部ではない / 「結果を残す仕組みは無い」は解析結果の cache に限れば真 (gate の記録はある)
- 設計 P1 (採用): 「書く瞬間の候補が一番効く」は 948 の実測 (天井効果・n=1 で写しが増えた) の裏づけが無い。A1 の弱点は遅さではなく名前の一致だけで引くことで、索引では直らない → 2 を「名前以外でも引く」に置き換えた
- 設計 P1 (採用): 「索引で起点の依存が消える」は崩れる (母集合の定義の問題) → 記録の案の中に書いた
- 設計 P2 (採用): 3 の費用は M にも比例し、大きな commit で N が跳ねる / 3 は sweep の仕組みで索引なしに試作できる / 順は 指標 → 名前以外で引く → 近似段の試作 → 索引は必要が実測されたら
- 設計 P3 (採用): 自作の検査の受け入れ条件 (§1.5)・rc=1 に上げる条件の母集合・索引の並行の書き込み → 3 と記録の案に書いた
- 反証できなかった: 引用の数値 (446,145 B / 2,900 B、55%、21 件中 4 件、gate の段と下限)、関連番号の指す内容、5 (指標を先に) の方針
