## 1. 所属ターゲットの解決 (894・896・897 から移した)

- 各ファイルが属するターゲットを `Package.swift`・XcodeGen の `project.yml`・追跡されている `project.pbxproj` から解き、組のメンバー・索引の 1 行に出す (近似の印つき)。
  どれも無ければ「不明」。追跡されていない `project.pbxproj` は読まない (手元と CI で結果が割れないように)。`project.yml` の `include:`・templates など読めない書き方に当たったら、その target は「不明」
- 作っていない理由: `project.yml` を読むには YAML の parser の依存が要る (dupscan は Go の標準だけで作る方針。設定ファイルを JSON にしたのと同じ理由。897 の 2026-10-25 の進捗)。
  DualNoteApp と obaket はディレクトリがターゲットにほぼ対応し、パスで所属が読める
- **優先着手の判断材料**: 索引で、別のターゲットから使えないヘルパーを「使える」と誤って引いた事例が出たとき。または組の寄せ先を決めるのにターゲットが要る事例が出たとき

## 2. リテラルの違いの表 (896 から移した)

- 組のメンバー間で違うリテラルを表にし、プロパティから値を読むメンバーは初期値を 1 段解決して並べる (寄せてよいかの判断の材料)。近似の値には近似の印を付ける (人が読む形と JSON の欄の両方)
- 受け入れの例: PR 24 の 6 つで、プロパティから値を読む 2 つ (`BuildMoveManifestUseCaseTests` / `MovePathMappingTests`) の `connectionID` / `namespace` の初期値が解決され、直書きの 4 つの `"conn"` / `"bucket"` と並ぶ
- 今の代わり: `dupscan explain <file>:<関数名>` で段ごとの形を 1 つずつ見る
- **優先着手の判断材料**: obaket で組を寄せる作業 (obaket の issue 1298) をしていて、メンバーごとの値の違いを 1 つずつ explain で見るのが手間になったとき

## 利用可能性の誤判断を避ける境界

候補のpublic/internal/unexportedやshared表示だけで、別module/targetから再利用できるとは判断しない。ビルド構成と依存関係を解く範囲を明示し、不明なら不明を返す。今回のopen管理への移動は調査/実装の記録先を用意するもので、候補が実際に利用可能だと判定する機能は未実装。リテラル表の既存範囲を維持し、同じ形が同じドメイン責務を持つという自動判断は追加しない。
