# 943 (perf): index / callers の結果行の形 — doc 先頭の長さと終端行

> **再開の条件**: 941 の測り直しと同じ日に、`index` の直後 3 手以内の `Read` を数える。今ある残りは利用データでしか測れない項目だけ (下の「引き継ぎ後の確認」)。

起票日: 2026-10-28

## 概要

結果 1 行が `rg -n` の 1 行より大きく、さらに `index` / `callers` の行に**終端行を表示していない**ため、見つけた関数 1 つを読むのに Read が範囲を決められず、ファイル全体を読みやすい。行の形を見直し、1 回の探索から次の読み込みまでの合計 byte を減らす。[942](done/942-perf-dupscan-fixed-notice-overhead.md) が検索ごとの固定費、本 issue は行ごとの変動費である。

## 実測 (2026-10-28、dotfiles の `src`)

| 項目 | 値 |
|---|---|
| `rg -n Join` の 1 行 | 平均 **111 B** (4,009 行) |
| `dupscan index -name Join` の結果行 | 平均 **173 B** (14 行、合計 2,429 B)。うち `// doc` の先頭行が 1,069 B (**44%**) |
| `dupscan index -name ReadCookies` の結果行 | 267 B (1 行)。うち doc が 127 B (**48%**) |
| `ReadCookies` の関数 | `cookie.go:291-349` の 59 行・約 1,684 B |
| `cookie.go` 全体 | 365 行・14,882 B (関数の約 9 倍) |

- 行は `file:開始行 名前(署名) [tag] (呼び出し ~N) // doc先頭` の形で、**終端行がない**。ただし単位は終端行を既に持つ (`tree.Unit` の `EndLine`)。`search` は候補ごとに範囲つきの `read_argv` (`sed -n '開始,終了p'`、最大 80 行) を既に出す (`src/dupscan/search_cmd.go`)。足りないのは `index` / `callers` の行表示である。Read に offset と limit を渡すには終端行が要る。無いと、agent は関数 1 つ (約 1.7 KB) ではなくファイル全体 (約 14.9 KB) を読むか、offset だけ指定して余分に読む。
- doc の先頭行は日本語で 1 文字 3 byte のため、行の大きさに効く。ただし 925 の「用途語から既存の helper を見つける」目的では doc が判断材料になる。**削ると発見が減る恐れ**がある。

## 方針 (候補)

1. **終端行を足す**: `file:291-349` の形。選択肢は、(ア) `index` / `callers` の行へ表示する、(イ) agent を範囲つき `read_argv` を出す `search` へ誘導する。(ア) を先に評価する。増えるのは数 byte で、Read の範囲を exact にできる。ジェネリクス・メソッド・複数行の署名・クロージャで正しい終端を出す。
2. **doc の先頭行を byte 数で切る** (`…` で省略)。または `-doc=N` で長さを選べるようにする。既定の長さは 925 の固定正例が到達し続ける範囲で決める。
4. **打ち切ったときだけ、先頭に件数ヘッダと次の手を出す** (ユーザー提案 2026-10-28)。例: `index: 該当 N 件 (20 件表示 / 全部出すと約 X KB)。語を足して絞るか、次の rg へ: rg -n -i 'Name' src -g '*.go'`。
   - 現状は末尾に「他 14 件 (-limit 0 か -format json で全部。語を足して絞る)」が出る (`index -name append -limit 3` で確認)。足りないのは**先頭での総件数・全件の byte の目安・実行できる次の手**である。
   - **dry-run モードは採らない**: 走査が 2 回・往復が 2 回になり、狭い検索ではかえって重い ([942](done/942-perf-dupscan-fixed-notice-overhead.md) の固定費と同じ構造)。出力は既定で 20 件に抑えられているので、事前に大きさを聞く必要は小さい。本当に困るのは [927](done/927-feat-dupscan-agent-context.md) の同名 `append` 461 件のように、byte でなく**目的が埋もれる**場合で、件数ヘッダがその気づきになる。
   - **dupscan 自身は grep を実行しない**。出すのは実行可能な `rg` の argv の提示だけ ( `search` の `read_argv` と同じ作り)。結果が構文木から文字列の一致に変わるので、提示の文に「コメント・文字列も当たる。0 件は不存在の証明ではない」を添え、2 つの契約を混ぜない。提示する `rg` は dupscan の照合 (大小を無視) と同じ対象を引く形にする。
   - **打ち切りがないときは出さない** (942 の固定費を増やさない)。
3. 行の平均が現行より増えない (終端行の増分 ≦ doc 短縮の減分) ことを、採用の条件にする。

## 実装と測定 (2026-10-28)

### 実装

- `index` の text の行を `file:開始-終了 …` にした (1 行の単位は `file:行`)。`IndexEntry.EndLine` を追加し、JSON は `end_line` のみ追加。
- text の doc を「最初の文まで・100 byte まで」に縮める (`ShortDoc`)。`-doc-bytes N` で変え、0 で縮めない。文の終わりは `。` か、後ろが空白で次が大文字・非 ASCII の `.`。`e.g.` / `Dr.` などの略語の後ろでは切らない。上限で切ったときだけ `…`。
- 打ち切ったときだけ先頭に `該当 N 件 (M 件表示 / 全部で約 X)。絞るか、文字列 (コメント含む) で探すなら: rg -n -i -e 名前 -g '*.go' -- dir` を 1 行出す (`callers` は `呼び出し N 件` で大小を区別。`-selector` や名前の無い問い合わせでは rg を出さない)。dupscan は rg を実行しない。`-e` と `--` で、`-` で始まる名前や dir が rg のオプションに読まれないようにし、単引用符で引用する。
- 「全部で約 X」は全件を同じ形式で組み立てた byte 数。
- `callers` の行は呼び出し箇所なので終端行は付けない。

### 採らなかったこと

- dry-run モード。2 往復になり、出力は既定で 20 件に抑えられているため。
- `callers` の rg の提示を dupscan の結果と同値にすること。`target(` の文字列一致なので、後置クロージャ・改行を挟む呼び出しは外れ、`xtarget(` は余分に当たる。提示の文に「文字列 (コメント含む)」と書いて断っている。
- 略語の許可リストを超えた、文の意味を読む切り方。2 文目に理由や条件がある doc (`Do not use X. It is unsafe.`) は最初の文で切れる。全文が要るときは `-doc-bytes 0` か JSON。

### 測定 (dotfiles の repo root から。byte は stdout + stderr)

| 問い合わせ | 変更前 | 変更後 |
|---|---|---|
| `index -limit 0 src` (7,008 行) | 1,360,819 | **1,202,322** (-11.6%) |
| `index -limit 0 -file src/chromecookie/workspace.go` | 4,866 | **4,585** (-5.8%) |
| `index -name Join` | 2,742 | **2,431** |
| `index -name append` | 3,711 | **3,292** |
| `index -name ReadCookies` | 580 | **561** (-3%) |
| `callers Join` (打ち切りあり) | 3,135 | **3,298** (+163 B) |

- 行の平均は 179 B → 153 B 前後と見積もっていた (doc の分布から計算)。実測では 7,008 行の全体で -11.6%、終端行の増分 (1 行あたり数 byte) を含む。`rg -n` の平均 (約 111 B) よりは大きいまま。
- **`callers` は行を縮めていないので、打ち切ったときは案内ヘッダの分だけ増える** (+163 B)。この例は 4,068 件・全部で約 685 KB と示すので、大きさに気づける代わりに、打ち切りのないときは何も変わらない。
- `ReadCookies` の定義 1 件はほとんど変わらない (-3%)。doc の先頭文が 100 byte を超えて `…` で切られ、減りが終端行の増分で相殺される。
- 打ち切りの案内の「全部で約 X」は、反証レビューで 8 つの名前の `-limit 0` の実 byte と 0.0% のずれ。提示された `rg` はそのまま実行でき、`index -name append` の例で 3,312 行を返した。

### 反証レビュー (別視点 1 体) の結果

- 壊せなかったもの: panic・不正な UTF-8 の出力・範囲の逆転・コマンド注入 (引用符つきで包み、メタ文字は `regexp.QuoteMeta` 済み)・終端行の誤り・「全部で約 X」と「M 件表示」の嘘・打ち切りなしの出力の退行・終了コード。
- 直したもの: 提示に `-e` と `--` が無く、`-` で始まる dir が rg のオプションに読まれる (P2) / 名前の無い問い合わせ (`-file`・`-doc` だけ等) のヘッダに「語を足して絞る」が出て不適切 / 略語 (`e.g. Foo bar. Baz` → `e.g.`、`Dr. Smith does X.` → `Dr.`) の後ろで文を切っていた / 上限が最初の文字より小さいと `…` だけになる / テストが `-` 始まりの dir・空白を含む dir・不正 UTF-8・小さい上限を見ていなかった。
- **意図の確認が要る変更**: `IndexEntryText` を共有するので、`def` と `context` の型メンバーの行も `file:開始-終了` になる。本 issue の対象 (`index` / `callers`) の外だが、同じ行の形で終端行が分かる利点があり、増える byte は数 byte のため、そろえる側を選んだ。

### 検証

- 変異 18 本 (終端行の欠落・1 行の単位の `-` 表示・ヘッダの常時表示・最初の文での切断・rune の途中での切断・略語・シェルの引用・callers の `-i`・JSON の doc の縮め・`-e`・`--`・略語の許可リスト・1 文字は残す・名前が無いときの助言) で、該当のテストだけが赤になることを確認した。
- 既存の 3 テストは期待値を更新した (`:8` → `:8-11` など)。行の形が変わったことの期待値だけで、主張は変えていない。
