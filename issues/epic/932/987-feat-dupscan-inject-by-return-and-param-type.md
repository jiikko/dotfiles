# 987 (feat): 書く前の候補の注入で、戻り型・引数型でも既存の関数を引く

> 🚨 **担当中: kojiM3MBP (glogx)**（2026-10-30〜）

起票日: 2026-10-30

## 概要

986 の改善 2。新しい関数を書く直前に候補を差し込む hook (`_claude/hooks/inject-dupscan-candidates-on-new-func.sh`。948 の A1) は、名前の一致だけで引く
(hook の冒頭「名前の一致だけを出す」「検出しない形: 名前が違うが同じ役割の関数 (署名の近さは見ない。dupscan search / index -returns で引く)」)。
954 の P1 は、名前の違う本番の `location(at:)` を戻り型で引けば見つかったのに、写しを作って push した例。書く関数の戻り型・引数型でも `dupscan index -returns` / `-param-type` で引き、名前の一致と合わせて出す。

## 対応方針

- 新しい関数の署名から、戻り型と引数型の字面を取る (今の hook は `func name(` を見つけている。署名の残りも同じ所で読む)
- `dupscan index -returns <型>` / `-param-type <型>` で引く。型の解決はしない (構文の字面。899 の範囲の中)
- **型だけでは引かず、新しい関数の名前の語と組み合わせる**: 954 の実測では、`index -returns StorageLocation` は 173 件で `location(at:)` が 7 番目、
  `index -name location -returns StorageLocation` は 118 件で 1 番目だった (954 の「引いていれば見つかったか」)。今の注入は名前ごとに最大 3 行なので、型だけで引くと目的の関数が上限で落ちる。
  名前の語 (`locationFor` なら `location`) と戻り型の組み合わせで引き、順位の付け方を先に決める
- 雑音を抑える規則を先に決める: 汎用の型 (`error`・`string`・`bool`・`int`・`Bool`・`String` など) は引かない、候補の数の上限、名前の一致の候補と重なるものは 1 回だけ出す
- 時間の予算は今の 6 秒の中に収める (引く回数が増えるので、名前 1 つにつき引く回数と所要を測る)
- 計測: 注入のログ (`claude-dupscan-inject.log`) に、どの引き方 (名前・戻り型・引数型) で出した候補かを残し、948 の指標で前後を比べられるようにする

## 受け入れ条件

- 954 の P1 の形 (名前は違うが戻り型が同じ既存の関数) を、書く直前に出す。fixture は**実物と同じ規模** (同じ戻り型の関数が 100 件を超える) で作り、
  目的の関数が注入の上限の中に残ることを確かめる (1 件だけの小さい fixture では、上限で落ちる形が素通りする)
- 汎用の型だけの関数では何も出さない
- 時間の予算を超えない (実測を本文に書く)
- 変異: 戻り型で引く経路を外すと、上の fixture のテストが赤

## 結果 (2026-10-30)

- 実装: hook が新しい関数の署名から戻り型の字面を取り (`return_type`)、汎用の型でなければ、名前の照合の後に残りの予算で `dupscan index -name <名前> -returns <型>` も引き、出た候補を先頭に置く。
  名前の照合より先に引かないのは、1 回が 2 秒かかる大きい repo で名前の照合が予算切れで走らなくなるため (敵対的レビュー P1)。時間切れはその問い合わせだけを空にする (以前は例外で hook 全体が黙り、それまでの候補も捨てていた)
- **引数型では引かない** (方針で書いた「引数型」は見送り): `string`・`context.Context`・`int` のような型が多く、名前と組み合わせても雑音になる見込み。必要が出たら、汎用の型の除外と同じ規則で別に足す
- 汎用の型 (`error`・`string`・数値・`Self`・`Element`・`struct` など。`GENERIC_RETURNS`) と 1〜2 文字の型引数では引かない。修飾 (`Swift.String`) は外してから判定する。Go の名前付きの戻り (`(lo, hi int)`) は型だけを見る。本体の無い protocol の要件では、次の行の別の要件の戻り型を読まない
- ログに 5 列目 (`name` / `returns`) を足した。`returns` は「戻り型の問い合わせで、名前の照合の上位 3 件に無い候補が出た」とき。`scripts/dupscan_usage_report.py` は 4 列・5 列の両方を数え、戻り型で出した注入の数も出す (948 の書式の行も直した)

### 実物の規模の実験 (本物の dupscan)

`location` という名前で別の型 (`CGPoint`) を返すメソッド 120 個と、目的の `StorageConnection.location(at:) -> StorageLocation` を 1 つ (パス順で後ろの `src/zz/`) 置いた Swift の repo で、
`func location(path: String) -> StorageLocation` を書く入力を流した:

| hook | 目的の定義 | 所要 |
|---|---|---|
| 変更前 (master) | 出ない (名前だけの照合の上位 20 件を別の型の定義が埋める) | 0.13 秒 |
| 変更後 | 先頭に出る (ログは `returns`) | 0.17 秒 |

目的の定義をパス順で前 (`src/core/`) に置くと、変更前でも先頭に出た (dupscan の並びはパス順に見える)。埋もれるかは置き場所による。
dotfiles の `src/dupscan` で `loadConfig` を書く入力では、2.24 秒で既存の `loadConfig` を `returns` の経路で出した (予算は 6 秒)。

### 確かめた方法

- テスト (偽物の dupscan): 名前と戻り型で埋もれた定義を出す (Swift・Go の `(T, error)`)・汎用の型 (`Swift.String`) では型で引かない・汎用の型でも名前の照合の結果は出す・
  本体の無い protocol の要件で次の行の型を読まない・戻り型の問い合わせが時間切れでも名前の照合の候補を出す。57 件 ok
- 変異 (mutate-verify・狙ったテストだけが赤): 戻り型の経路を外す / 汎用の型の判定を外す / 時間切れを受けない
- `make test-lint` rc=0、`tests/scripts/test_dupscan_usage_report.sh` rc=0

### 敵対的レビュー (opus、読み取りのみ)

- P1 (採用): 型の問い合わせを先に足したので、大きい repo で名前の照合が予算切れになり、時間切れの例外で候補が全部消える → 順を後ろへ回し、問い合わせごとに時間切れを受ける
- P2 (採用): 修飾つきの汎用の型が判定をすり抜ける / 汎用の型のテストが「何も出ない」でも緑 / 偽物が実物の規模を模さない (→ 本物で上の実験をした)
- P3 (採用): 名前付きの戻り・`struct` / `interface`・protocol の要件・型引数・ログの `returns` の意味・hook の冒頭の「1 回」の記述・948 の書式の行
- P3 (記録): stamp は問い合わせの前に書くので、時間切れの名前は同じ session で引き直さない (変更前から。時間切れでも候補は出すようになった)
