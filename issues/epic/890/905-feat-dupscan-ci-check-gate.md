# 905 (feat): make test と CI で、新しく入った重複を落とす (dupscan gate)

起票日: 2026-10-24

## 概要

ユーザー決定 (2026-10-24):
- **検出できる種類の重複 (Type-2 と L3 の一致) は止めたい。ただし実行コスト次第**
- **止める頻度は、編集のたびの hook ではなく、`make test` の中に dupscan を含める程度にする**

そこで、使う側の repo の `make test` に `dupscan gate` を組み込む。CI も `make test` を回すので、同じ検査が CI でも走る。
Claude は `make test` の失敗として受け取り、既存のメソッドへ寄せる。編集のたびの hook ([902](pending/902-feat-dupscan-claude-code-hook.md)) は保留にした。

## `dupscan gate` (名前は仮。897 の索引の `--check` と紛らわしくしないため `check` にしない)

- **比べる 2 つ**: base (下記) と、今の作業ツリー。作業ツリーは未コミットの変更と、ignore されていない untracked のファイルのうち adapter の拡張子のものを含む
  (Claude が新しく作ったファイルや、Bash で書き換えたファイルもここで拾う)。untracked から拾ったファイルは別に一覧で出す (CI と手元の結果の差が見えるように)。
  追跡しているが作業ツリーで消えたファイルは読まずに「消えた」と数える
- **違反の判定** (反証レビュー 2026-10-24 で組み直した。数だけの判定は、許可で数を相殺できる・どの単位が新しいかを名指しできない、ので採らない):
  1. **変わった単位**を決める: base から作業ツリーまでに変わったファイルの単位のうち、鍵 (ファイル + 名前・署名) が base に無いか、本体のハッシュが base と違うもの
  2. 変わった単位ごとに、段 (L1 → L2 → L3 の順) で同じ形のハッシュを持つ**他の**単位を探す。最初に一致した段だけを、その単位の一致の段にする (L1 で一致すれば L2・L3 でも一致するので、重ねて出さない)
  3. その形のハッシュを持つ単位の**数が base より増えている**ときだけ違反にする。移動・改名・署名の変更・整形では数が増えないので落ちない。既存の写しを寄せる作業では数が減るので落ちない
  4. 違反の出力は、変わった単位 (寄せる側) と、同じ形の既存の単位 (寄せる先の候補) を分けて名指しする
  - **検出しない形** (README に書く): 同じ組の古い写しを 1 つ消して新しい写しを 1 つ足す入れ替え (数が増えないので、重複の量は増えていないと読む)
  - L3 で本体全体が 1 記号に畳まれる単位 (本体で引数を使わない単位) は、無関係な単位とも一致して数が揺れる。この単位の L3 の扱い (除くか別の桶にするか) は [898](898-test-dupscan-obaket-calibration.md) で決め、決まるまで L3 は報告だけにする
- **base** (直接 push する運用でも何かを確かめるように):
  - 手元の `make test`: 今のブランチの upstream (`@{u}`)。push していない commit と作業ツリーの変更が対象になる。upstream が無ければ `--base` を求めて判定不能で終わる
  - CI の push: push の前の commit (GitHub Actions の `github.event.before`)。新しいブランチ (before が全部 0) なら既定のブランチとの merge-base
  - CI の pull request: 対象のブランチとの merge-base
  - どれも `--base <ref>` で明示して渡す形を README の組み込みの例にする (既定のブランチの名前を `origin/HEAD` から推すのは、CI の checkout に無いことがあるので頼らない)
  - base の commit が手元に無い (浅い clone など) ときは、黙って全部を「新しい」と数えずに、判定不能として非 0 で終わる。CI では base まで fetch する
- **段ごとに止めるか報告だけかを選べる** (例: L1 / L2 は止め、L3 は報告だけ)。既定は下の「コスト」の測定で決める
- **意図した写しの許可**: 変わった単位の直前のコメント `dupscan:allow <理由>` (書き方は決めること)。許可は**その単位が変わった単位として違反になるのを外すだけ**で、数には影響しない
  (古い単位に許可を付けても、新しい写しの違反は消えない)。理由の無い許可は違反にする。**新しく足された許可は、違反とは別の一覧として毎回出す**
  - 🚨 コメントに書き手は残らないので、「Claude が許可を書いてよいか」は機械では強制できない。止める手段は、新しく足された許可の一覧を人が PR やログで見ることだけ ([891](891-design-dupscan-requirements.md) の「決めること」)
- **対象**: test と prod の両方。テスト関数そのもの (Swift の `@Test` / `func test…`) は除く (891 の adapter)。test と prod にまたがる組も違反にするかは決めること
- **出力**: 896 の組の形 (人が読む形と `--json`)。違反があれば非 0。読めない構文で確かめられなかった単位は件数と場所を出し、黙って緑にしない
- **組み込みの例**: 使う側の repo の Makefile の `test` に足す例と、CI で `--base` を渡す例・fetch の深さを README に書く (obaket の組み込みは obaket issue 1298)
- 単位の一覧の作り方とキャッシュの仕組みは 897 と共通 (作業ツリーの側は変わったファイルだけ作り直し、base の側は commit を鍵にする)

## コスト (止めるかを決める材料。測った値をユーザーに見せて決める)

- **所要**: `make test` に足される秒数。base と作業ツリーの 2 回の走査が要る (parse だけなら obaket の Swift 1626 ファイルで 5.0 秒。891 の実測。正規化と組分けを含む通しは未実測)。
  base の単位の一覧は base の commit ごとにキャッシュできる (鍵は commit。中身が変わらない)
- **誤って止める割合**: obaket の過去の commit を N 本 (例: 直近 100 本) 流し直し、1 本ずつ親を base にして `gate` を回し、落ちた本数と、そのうち誤検知の本数を段ごとに数える。
  repo 全体の組の誤検知 (898) とは別の量で、こちらが「make test が誤って赤になる頻度」に当たる
- この 2 つを見て、ユーザーが段ごとに「止める / 報告だけ / 回さない」を決める

## 受け入れ条件

- [ ] obaket の PR 24 の前の木を base にし、6 つのうち 1 つを新しく足した作業ツリーで `gate` が非 0 になり、足した単位を寄せる側として名指しする。未コミットのまま・untracked の新しいファイルに足した場合も
- [ ] 否定: 既存の写しのファイルの移動・関数の改名・整形の変更では落ちない。既存の写しを 1 つ共通の置き場所へ寄せた変更で落ちない。base の時点で在った組だけでは落ちない
- [ ] 理由つきの許可を付けた単位では落ちず、理由の無い許可では落ちる。古い単位に許可を付けても、新しい写しの違反は消えない。新しく足された許可が別の一覧に出る
- [ ] base の commit が無いとき・手元で upstream が無く `--base` も無いとき、判定不能として非 0 で終わる
- [ ] 直接 push の運用: push の前の commit を base にした CI で、push した写しが落ちる
- [ ] 写し 1 つの違反が、段を重ねずに 1 つの段で出る
- [ ] 読めない構文の単位を、件数と場所つきで報告する
- [ ] 所要と、過去の commit の流し直しで数えた誤って止める割合を段ごとに書き、ユーザーの決定 (段ごとに止める / 報告だけ / 回さない) を書く
