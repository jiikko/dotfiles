## 検証 1: 書く前に引く効果の A/B

**検証 1〜3 とも、obaket の入っている別のマシンで行う** (ユーザー指示 2026-10-25)。手順は dotfiles の中だけでも回せる形で書いてあるが、このマシンでは着手しない。


skill の有る無しを変えて、headless の Claude Code (`claude -p`。`bin/skill-eval` は Bash を許さず作業ツリーの成果物を判定できないので使わない) に同じ作業をさせ、写しを書いた割合を比べる。

- **腕** (どれも同じ隔離した HOME で回し、ユーザーの CLAUDE.md・rules は読ませない。腕の違いを skill だけにするため。現実の条件より CLAUDE.md の skill の表の分だけ A に不利):
  - **A (書く前に引くだけ)**: skill `dupscan` あり。Bash は `dupscan index` / `near` / `callers` と grep だけを許し、`dupscan gate` は許さない (セルフレビューで後から寄せる効果を混ぜない)
  - **A+ (gate も使う)**: skill あり。`dupscan gate` も許す (実際の運用の形。A との差が gate の上乗せ)
  - **B (無し)**: skill なし。dupscan は PATH にあるが、存在を知らせない
- **入力の repo**: 使い捨ての Swift の repo を `tmp/` に作る。既存のヘルパーを仕込み、**依頼文には型の名前・関数の名前・ファイル名を出さない** (出すと grep で見つかり、B との差が消える。903 の試験はこの形で、index の前に Grep を打っていた)。
  依頼文は「何をする値か」で書く (例: 「保存先のキーをバケット名から作るヘルパーを用意して、アップロードのテストを書いて」。既存は `Tests/AppTests/Support/Fixtures.swift` の `func makeStoreKey(bucket: String) -> StorageKey`)
  - 種類を 3〜5 個にする (戻り値の型で引けるもの・名前の一部でしか引けないもの・doc の語でしか引けないもの・既存が private で寄せる必要があるもの・既存が無いもの = 否定の対照)
  - 仕込むヘルパーは gate の下限 (節 10) より大きくする (小さいと gate が数えず、判定が全部「書いていない」になる)
  - 依頼文に「セルフレビュー」「既にある」のような skill の description の語を入れない (発火を語で誘導しない)
- **試走**: 本番の前に B だけを 1 種類 3 回回し、B が写しを書く割合 (基準率) を見る。基準率が 0 に近ければ依頼文がまだ見つけやすすぎるので、作り直す
- **回数と費用**: 腕 × 種類ごとに 5 回 (結果は揺れるので 1 回で決めない。`.claude/rules/skill-eval-after-edit.md` の「--runs を増やして割合で見る」)。
  3 腕 × 3〜5 種類 × 5 回 = 45〜75 回、1 回 $0.6 前後 (903 の実測) で約 $27〜45 の見込み (B は安く済む)。**回す前に 5h 枠を見て、ユーザーに規模を諮る** (`_claude/rules/subagent-model-tiering.md`)
- **測るもの** (stream-json の道具の呼び出しと、終わった後の作業ツリーから取る):
  - **写しを書いたか**: 2 つの判定を併用する。①終わった後の `dupscan gate -base <初期の commit>` の rc ②新しく書いた関数と仕込んだヘルパーの本体を人 (か main agent) が diff で読み、同じ値を作るかを判定する (dupscan が見逃す写しを数えるため。測る道具だけで判定すると循環する)
  - 既存のヘルパーを使ったか: 新しいテストが既存のヘルパーを呼んでいるか
  - **最初に関数を書く (Write / Edit) 前に `dupscan index` を呼んだか** (stream-json の順で見る)。A・A+ で skill を読んだか
  - grep / Read の回数・返った文字数・費用 (`total_cost_usd`)・turn 数
- **判定**:
  - A の「写しを書いた割合」が B より明らかに低い (例: 5 割以上減る) なら、書く前に引く効果があると言う。A の中でも「書く前に index を呼んだ回」と「呼ばなかった回」に分けて比べる (skill を読まなかった回は A から外さず、読んだ割合として別に書く)
  - A と B に差が無く、A+ だけが低いなら、効いているのは gate (後から見つける側) だけ。skill を「セルフレビューで gate を回す」中心に縮めることを検討する
  - 否定の対照 (既存が無い種類) で、A が「既存がある」と誤って使う・書かずに止まる回が出たら、それも書く
- **限界**: 使い捨ての repo は小さく、実際の repo より grep で見つけやすい (効果は小さく出る側に寄る)。隔離した HOME はユーザーの環境と違う。モデル (sonnet / opus) で結果が変わりうるので、使ったモデルを書く
