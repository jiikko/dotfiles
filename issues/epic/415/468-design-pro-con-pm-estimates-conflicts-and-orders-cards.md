# 468 (design): PM がカードどうしの衝突を見積もり、同じ判断を変えるカードには順番を付けて dispatcher に守らせる

起票日: 2026-09-25

親: [415](415-design-claude-pm-worker-orchestration.md)

## 概要

ユーザーの指摘 (2026-09-25): 「複数のカードを投げ込んだら PM 側が、衝突する可能性があるのか見積もった上で pg に投げるんじゃないの？」。
今はそうなっていない:

- 分解済みのカードは、枠が空いた順に dispatcher が起動するだけ (`dispatcher.go` の `dispatch`: 再開が先、その中は古い順)。カードに「この後に」を持つ欄が無い
  (`card.Card` にあるのは親子の `ParentID` だけ)。PM が見積もっても dispatcher に伝える口が無い
- `pm-guide.md` に衝突を見積もる役目が無い
- 2026-09-25 の dogfooding で PM (人間の代わりの Claude) は、PG に「review の前に rebase する」とだけ頼んで 4 本を並べた。C-007 (437: PM を終了で止める対象に入れる) と
  C-010 (457: 記録に無い PG を止める対象に入れる) は、どちらも「終了のときに何を止めるか」を変えると分かっていたのに順番を付けなかった。466 だけは本文に「457 の後」と書いてキューに積まなかった

## 分け方 (叩き台)

1. **同じファイルに別々のものを足す** (依頼の種類を 1 つ足す・README の行を足す・別の関数を足す): 並べてよい。取り込むときの rebase で解ける。PG に rebase を頼むだけでよい
2. **同じ判断・同じ不変条件を別々に変える** (何を止めるか・枠に何を数えるか・「止まった」の判定・状態の遷移の規則): 順番に走らせる。後のカードは前の変更を読んでから作る。
   並べると、文字の上でぶつからなくても、合わせた結果が片方のテストでしか守られない形になる

## 期待する動作 (候補)

- `pro-con card plan <カード> --after <カード>` (複数可) で順番を付ける。dispatcher は前のカードが完了 (閉じた / 削除した) するまで後のカードを起動しない。
  前のカードが消えた・却下されたときの扱いを決める。循環は受けない
- ボードで「待っている理由: C-007 の後」が見える (455 の「待ち」と同じ所に出す)
- `pm-guide.md` の役目 3 (issue に分けてキューに積む) に、見積もりのしかたを書く: 各カードが触る場所 (ファイル・関数) と変える判断を 1 行で書き、2 に当たる組に `--after` を付ける。
  見積もりはカードの本文 (issue) に残す
- 取り込むときの確かめ (PM / 人): 先に入ったカードとの組み合わせで、2 に当たる所をテストで見る

## 関連

- 437 (PM を起こす。分けるのは自動の PM になる) / 455 (待ちの理由を出す) / 440 (dogfooding の記録) / 466 (「457 の後」を本文だけで守った例)

## 実装 (2026-09-25 / カード C-023)

決めたこと:

- **順番は `card.Card.After` (前のカードの ID の列)**。`pro-con card plan <カード> --after <カード>` (複数可) で、依頼の列から積むときだけ付けられる (分解済みより右には後から付けない)
- **完了 = `Done` (終わり方を問わない)**。却下された前のカードも待たない (後のカードは今の master を読んで作る)。レビューの列はまだ完了ではない (取り込み前)
- **削除は完了と同じく待ちを解く**。`card.Drop` が後のカードの `After` から外し、履歴に「C-007 が削除されたので、その完了を待たない」を残す (依頼の列の即時削除と dispatcher の `dropCard` の両方がこれを通る)。削除を諦めてカードが残れば待ち続ける
- **循環は `card.Check` の不変条件**。**相手の確かめは plan の適用で「振った番号か」を見る** (まだ振っていない番号 = 打ち間違いを除ける)。
  **記録に無い前のカードは待たない**: 記録から外れるのは完了して書庫へ移ったカード (478) と削除したカードだけで、どちらも戻らない。
  🚨 「相手が記録に在る」を不変条件にしない (最初はそうしていた): 478 の `store.Archive` は `newViolation` を通すので、前のカードが完了から 24 時間で書庫へ移るときに違反になり、**他の終えたカードも含めて書庫への移動がまとめて止まっていた** (差し戻しで rebase して `TestArchivedPredecessorReleasesSuccessor` で再現)。後のカードの `After` は書庫へ移っても消さない (`card show` の「順番」と取り込みの確かめのため)
- **dispatcher が止めるのは初めての起動だけ** (`Session` も `Launching` も空のとき)。一度起動したカードの再開は止めない。待たせた理由は履歴と出来事の記録 (`hold`) に、変わったときだけ「順番: C-001 の完了を待つ」と書く
- 表示: 一覧・詳細 (`待ち: C-001 の後` / `順番: C-001 の後`)、画面のバッジ (`…C-001 の後`) と引き出し。起動の指示 (Prompt) にも順番を書く
- `pm-guide.md` の役目 3 に見積もりのしかた (触る場所と変える判断を 1 行ずつ・2 の組に `--after`・迷ったら順番・見積もりは後のカードの issue に残す)、役目 5 に取り込みの時の組み合わせの確かめ

検証: 発火条件 (前のカードが作業中なのに後のカードが起動する) を偽物の launcher で作って red を見てから直した。`bin/mutate-verify` で dispatcher の待ち・履歴の重複抑止・`Drop` の外し・循環の検出・`Blockers` の完了判定・一覧と画面の表示の 7 変異がすべて想定のテストで red。repo の root の `make test` は rc=0 (6m3s。`ok` 75 行・FAIL 0。テストの係が差し戻し前の e41af51a で実行)。
差し戻し (478 との合わせ) の後: 書庫へ移った前のカードを待たない・振っていない番号を除ける・「相手が記録に無い」を違反に戻す、の 3 変異も想定のテストで red。

敵対的レビュー (読み取り専用のサブエージェント 1 本): P1 なし。

- P3 (直した): 待ちの重複抑止が履歴の最後の 1 行と比べていて、btw の答え (直近の出来事を引用する) が挟まると同じ待ちを書き直した。テストで再現してから、「順番: 」で始まる最後の行と比べる形にした
- **残るリスク (P2・未再現)**: 旧版の dispatcher が動いたまま新版の CLI で `plan --after` を打つと、旧版は知らない `after` 欄を捨てて待たずに起動し、記録を書き直すと全カードの `After` が消える。欄を足す変更に共通の形で、依頼・記録に版の照合は無い。起きうる時間の幅は未確認
- 規模の目安 (P3・測定はレビュー側): 循環の検出は長い鎖で O(N²)。2000 枚の鎖で `Check` 1 回 162 ms、今の規模 (数百枚) なら数 ms
