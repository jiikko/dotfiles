## 概要

ユーザーの依頼 (2026-09-25): 「作業中のレーンでは worker プロセス (claude code) が 2 つとか限られているはずだが、作業中レーンと作業中待ちは区別したいね」。

## 詳細 (今の実装。2026-09-25 に読んだ)

- 作業中の列 (`card.Running`) には、PG が動いているカードのほかに、PG の turn が終わって待っているカードが入る:
  テストの係の結果待ち (`WaitResource`。`pro-con card run` の後)・利用枠の回復待ち (`WaitQuota`)。`src/pro-con/card/card.go` の `WaitKind` に
  「Running 列のまま」と書いてある
- 🚨 **PG の枠 (`--limit`) は作業中の列のカードを全部数える** (`src/pro-con/dispatcher/dispatcher.go` の `dispatch` の `running++`)。
  テストの結果待ちで PG が idle のカードも 1 本ぶん枠を使うので、枠が 2 なら「テスト待ち 1 + 作業 1」で新しいカードが起動しない
- 分解済み (`card.Planned`) は「PG の空き待ち」の列。これはすでに作業中と分かれている

## 期待する動作

- ボードで「今 PG のプロセスが動いている (turn の途中)」カードと、「待っている (テストの係・利用枠・PG の空き)」カードが一目で分かれる。
  列を分けるか、作業中の列の中で分けるかは、見本で候補を並べてユーザーに選んでもらう (`decide-layout-in-sample-renderer-first.md`)
- 動いている PG の数と枠 (例: `PG 1/2`) がゲージと一致する (今のゲージの「PG n/m」が何を数えているかも合わせて確かめる)

## 決めること

- **枠に何を数えるか**: 候補は ①今のまま (作業中の列を全部) ②turn の途中の PG だけ (テスト待ち・利用枠待ちは数えない)。
  ②にすると、テストの結果が届いて再開するときに枠を超えうる (再開を先にする並び (resume-first) があるので、待たせる / 超えてよいかを決める)。
  枠の目的 (利用枠とマシンの負荷) に照らして決め、理由を本文に書く。idle の PG はトークンを使わないが、プロセスとメモリは残る
- 「待ち」の理由 (テスト / 利用枠 / 空き) をカードに出すか

## 順番の見積もり (PM, 2026-09-26。C-033 を C-029 の後に積んだ)

- 触る場所: `dispatcher/dispatcher.go` の `dispatch()` の `running` の数え方、`card/card.go` の作業中の列の判定、`ui/view.go` の `pgGauge()` / `gauge()`
- 変える判断: PG の枠 (`--limit`) に何を数えるか (作業中の列の全部か、turn の途中の PG だけか)
- 順番の理由: C-029 (456 の dispatcher 側) は、枠の上限の値の出どころ (`pro-con config set limit`・利用枠の絞り・起動の引数の優先) を変える。こちらは枠と比べる側の数を変える。どちらも `dispatch()` の「枠が空いているか」の判断を変えるので、456 の後にする。476 (C-038) はこの行に PM のゲージを足すので、この後に積んだ

## 決定: 枠は turn の途中の PG だけを数える (② を採る。C-033, 2026-09-26)

- **数えるもの**: 作業中の列のカードのうち、テストの係に頼んでいない (`Card.AwaitsRun()` が偽) もの、
  または頼んだが一覧でまだ idle と出ていない (turn の途中 / 一覧に居ない) もの。判定は `card.HoldsPGSlot` の 1 か所で、
  dispatcher の `dispatch()` と画面のゲージ・PG の一覧の見出し (`backend.Snapshot.SlotsUsed`) が同じものを使う
- **理由**: 枠の目的は利用枠 (トークン) とマシンの負荷。テストの係の結果を待つ PG は turn を終えて idle でトークンを使わない。
  重い処理 (make test / 実機 E2E) はテストの係が repo の lock を取って 1 本ずつ回すので、PG を増やしてもこの負荷は増えない。
  残るのは idle の claude のプロセスとメモリで、枠を 1 本塞ぐほどの重さではない (実例の 21:02 では 3 本を塞いで 2 枚を 15 分待たせた)
- **再開は枠を超えない**: 結果が届くと `finishRun` がカードを分解済みへ戻し、`dispatch()` の列に入る (再開が先)。
  枠が埋まっていれば空きを待つので、「再開で枠を超える」は起きない。テストで固定: `dispatcher/slot_test.go`
- **idle と確かめられないうちは数える**: `pro-con card run` の直後はまだ turn の途中のことがある。一覧で idle と出るまで数える
  (一覧を取れない・session が居ないときも数える側に倒す)
- 利用枠の回復待ち (`WaitQuota`) は、本物のモードではまだどこも立てない (模擬だけ) ので、判定に入れていない
- 既知の制約 (敵対的レビューで出た。どれも変更前からある形):
  - 結果待ちで idle の PG を dispatcher の外から起こす (人が attach して打つ) と、その間は枠を超えて busy になる。次の Tick からは busy として数えるので、新しい起動は止まる。超えた分を止める仕組みは無い
  - ゲージの母数は一覧に居る PG だけで、dispatcher は一覧に居ない作業中の PG と起動の結果が分からない (Launching) カードも数える。起動の直後・落ちた PG が居ると、ゲージは dispatcher より少なく出る。一致させるなら dispatcher の数を dispatcher-state.json に書いて画面が読む (未着手)
  - 模擬 (`--mock`) はテストの係を持たず、結果待ちの PG が idle にならないので、この数え方を模擬では見られない
- 🚨 作業中の列のカード数と `PG n/m` は一致しなくなる (待っている PG は列に居るが数えない)。ボードでの分け方は下の見本で決める

## 決定: ボードの見分け方 (C-033, 2026-09-26。ユーザーの決定)

- 見本の A (列を分ける) / B (列の中で上下に分ける) / C (頭に ● / ◌) はどれも採らず、**並びと列はそのまま、spinner の有無と地の明度で見分ける**
  - 動いている (PG が turn の途中 = status が busy): バッジの頭に spinner。地はカード固有の色のまま
  - 待っている (作業中の列でテストの係の結果待ち = 実行中も含む / 分解済みの列で再開待ち = session がある): spinner を出さず、
    地を**そのカード固有の色のまま明度 ×0.55** にする (別の色に塗り替えない。列を移っても追える決まりを守る)。見本 `tmp/pro-con-455-spinner-sample.py` で ×0.55 / ×0.4 から選んだ
  - まだ起動していない分解済みのカード (空き待ち) は暗くしない
  - 暗い地は RGB (truecolor) で出す (cardPalette は 256 色の cube の最も暗い段なので、256 色のままでは色相を保って暗くできない)。truecolor の通らない端末で近い 256 色に落ちるのはユーザー了承済み
- 実装: `ui/spinner.go` の `waiting` / `processing`、`ui/view.go` の `cardCell`、`ui/style.go` の `bgDim` / `waitDim`。テスト: `ui/waitdim_test.go` / `ui/spinner_test.go`
