# 478 (perf): cards.json は終えたカードも持ち続け、dispatcher は空の Tick でも 8 回読み直す (費用が使った日数に比例して増える)

起票日: 2026-09-25

親: [415](../415-design-claude-pm-worker-orchestration.md)

## 概要

リソースリークの監査 (479) で見つけた。カードの記録 `cards.json` から終えたカードが消えないのは、438 の「片付けは画面から外すだけ (記録からは消さない)」の決定どおり。
ただ、上限・回し・書庫への移し替えが無いまま、dispatcher と画面が毎回ファイル全体を読んで JSON を解く。
そのため費用は、今動いているカードの数ではなく、これまでに作ったカードの総数に比例して増え続ける。

## 詳細

- 該当: `src/pro-con/store/store.go` の `Load` (`os.ReadFile` → `json.Unmarshal` を全体に) と `writeAtomic` (全体を書き直す)。
  dispatcher の `Tick` (`tickRuns` はテストの係の実行中なら 2 度、`stopMarked`・`pm.go` ほか)。画面は `live.Backend.refresh` で 3 秒ごと + dispatcher に知らされるたびに読む。
  取り除くのは削除の依頼 (451) だけ。`Applied` / `Rejected` は `keepApplied` で上限がある
- 発火条件: 使った日数。2026-09-25 の dogfooding では 1 日で 15 枚・57KB (1 枚あたり約 4KB。本物の cards.json を読んで数えた)。この速さなら 50 日で約 750 枚になる
- 実測 (module の一時コピーで。本物の cards.json の写しを使った):
  - 空の Tick 1 回あたりの `store.Load` の呼び出し: 9 回 (1 回目) / 8 回 (2・3 回目)。コピーの `Load` に数える口を足し、既存の偽物 (`newDispatcher` / `fakeLauncher`) で回した
  - `Load` 1 回の所要 (本物の 15 枚を複製した記録。20 回の平均):

    | 枚数 | ファイル | Load | writeAtomic |
    |---:|---:|---:|---:|
    | 15 | 57KB | 0.5ms | 0.2ms |
    | 150 | 575KB | 3.7ms | 0.2ms |
    | 750 | 2.9MB | 17.2ms | 2.3ms |
    | 3000 | 11.5MB | 70.0ms | 4.0ms |

  - 750 枚なら、Tick ごとの読み直しだけで 3 秒あたり約 140ms (1 コアの約 5%)。3000 枚なら約 560ms (約 19%)。これに開いている画面ごとの読み直しと、状態が変わるたびの全体の書き直しが加わる
- 漏れたとき: 何も壊れないまま、dispatcher と画面の CPU・電池と、Tick の遅れ (知らせてから画面に出るまで) が日ごとに増える。人が気づくきっかけが無い
- 意図の反証: 438 は「記録からは消さない」と決めている。これは履歴 (`card show`・449 の起動時刻の集計) を失わないための決定で、読み直しの費用には触れていない。
  events.jsonl には `MaxBytes` の回しがあり、runs/・sessions-retired.json・inbox/rejected/ が増え続けることは 460 に既知。cards.json はどちらにも入っていない

## 対応方針 (候補)

- 終えたカード (完了・片付け済み) を、一定時間後に書庫 (`cards-archive.jsonl` のように足していくだけのファイル) へ移す。Tick と画面は動いているカードだけを読む。
  `card show` と履歴の集計は書庫も読む (438 の「記録からは消さない」を守る)
- 1 Tick の中では 1 度読んだ State を渡し回す (8 回を 1〜2 回に)。書き手は dispatcher だけなので、Tick の中では読み直さなくても食い違わない
- 性能の予算: N 枚の記録での Tick の所要を bench にする (直す前後を同じ bench で測る)

## 決定 (2026-09-25)

- **終えたカードは記録 (`cards.json`) から書庫 (`cards-archive.jsonl`。足していくだけ) へ移す**。書くのは dispatcher だけ (Tick の Apply の直後の `store.Archive`)。
  438 の「記録からは消さない」は書庫で守る (カードの中身は履歴ごとそのまま 1 行にする)
- 移す条件: 完了 **かつ** (片付けた (x) **または** 完了から 24 時間 (`store.AutoClearAfter`)) **かつ** 次のどれでもない
  - PG を止め終えていない (`StopAfterClose`)・削除の途中 (`DeleteAt`): dispatcher がまだ記録の上でそのカードを扱う
  - 答えていない btw がある: 移すと tickBtws が見なくなり、答えないまま書庫に残る (btw はどの列でも受ける。敵対的レビューで指摘)
  - 記録に残る子カードの親: 外すと子が「親カードが存在しない」の違反になる (子を移すなら一緒に移す。孫まで辿る)
- **完了のカードの自動の片付けは入れる** (完了から 24 時間)。入れないと、x を押さない使い方では完了のレーンが記録に溜まり続け、書庫があっても費用が戻る。
  24 時間は「翌日に開いても前日の完了が見える」長さ。自動で片付けたカードは Archived にして履歴に「完了から 24 時間たったので自動で片付けた」を足し、
  出来事 (`pro-con log` の `archive`) にも出す (画面から消えた理由を残す)。人が x で片付けたカードは画面に出ていないので出来事にしない
- 読む側: `card show` / `card wait` は記録に無ければ書庫を読む (`store.Find`)。`card list --all` は記録 + 書庫。**画面と dispatcher は書庫を読まない**
- 失敗モード: 書庫に足した後・記録を書き直す前に落ちる → 次の Tick がもう一度足す。読む側は書庫の同じ ID を後の行で上書きし、記録にあれば記録を正とする。
  書庫の末尾が書きかけ → 足す前に改行を補う。読めない行は飛ばしてその数をエラーで返す。書庫は `fsync` してから記録を書き直す
- **見送り: 1 Tick の中の読み直し (8 回) を 1〜2 回にする**。書庫へ移した後の記録は動いているカード + 完了して 24 時間以内のカードだけで、
  下の bench では空の Tick が 0.35ms (8 回の読み直し込み)。State を渡し回す改修は Tick の全段 (`register` / `stopMarked` / `tickRuns` / `pm.go` …) の
  署名を変える大きさなので、記録の大きさが効かなくなった今は割に合わない。動いているカードが数十枚を超える使い方が出たら測り直す

- 仕様の変化 (受ける。敵対的レビューで指摘):
  - 書庫へ移ったカードには、依頼 (回答・追加オーダー・btw・attach・別件の親・削除) を出せない (「カードが無い」/「親カードが存在しない」で除けて rejected/ に理由が残る)。
    完了から 24 時間を過ぎた完了のカードへは別件を出す口が無くなる。画面が見ている間に自動の片付けを跨ぐと、置いた依頼が除けられうる (窓は Tick 1 回ぶん)
  - 削除の「子カードの親なので消せない」は記録の子だけを数える。子が書庫へ移った親は消せ、書庫の子の `ParentID` は消えた親を指したまま残る
- 未確認のリスク: `writeAtomic` は rename の前に fsync しない (Apply と共通の既存の穴。電源断で記録が空に戻ると Load が壊れた扱い)。
  `cards.json` を手で消して作り直すと NextID が 1 に戻り、書庫と ID が衝突する (`card list --all` は記録の側を正とするので古いカードが隠れる)

## 実測 (bench)

`go test ./dispatcher -run '^$' -bench BenchmarkTickWithFinishedCards -benchtime 3s` (終えたカード 750 枚・1 枚に履歴 40 行。Apple M3 Max):

| | 空の Tick 1 回 |
|---|---:|
| 直す前 (Tick から `store.Archive` を外した版) | 333ms |
| 直した後 (最初の Tick で書庫へ移す) | 0.35ms |
