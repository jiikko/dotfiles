# 483 (feat): マシンのクラッシュ・再起動の後に、止まった作業を 1 コマンドで復旧する (起動オプション)

起票日: 2026-09-26

## 概要

2026-09-25 23:53 に macOS が落ちた後、作業中だった 4 枚 (C-025 / C-026 / C-027 / C-029) と PM を再開させるのに、
手で次をやる必要があった (ユーザーの要望: 「復旧用のコマンド、起動オプションが欲しい」)。

1. `pro-con --view` を開いても dispatcher は起きず、カードは「作業中」のまま見えているだけ (PG は居ない)。
   画面を見ても「止まっている」ことが分からない
2. dispatcher を手で起動 (`setsid` で切り離し)。前回の上限 (`--limit 4`) は記録に残っておらず、既定の 2 で起きた
3. 作業中のカードは watchdog (15 分進捗なし) → 1 分後に「一覧から消えて戻らない」として戻され、再開された (設計どおり)。
   C-027 のテストの係の実行はクラッシュで中断し `rc=-1` として PG に渡った
4. 上限を戻そうと `--stop` したら、pid 無し・`failed` の session を止め直し続けて抜けなかった (482)

## 決定 (2026-09-26 ユーザー。C-042 の質問への答え)

- **復旧はコマンドも引数も足さず、dispatcher の起動時に自動で判断する** (画面が起こしたときも手で起動したときも同じ)。`--recover` / `recover` は作らない
- 起動時に、足りないプロセス (記録にある作業中のカードの PG・PM・取り込みの係の session が一覧に居ない・pid 無し・クラッシュ後の failed) を調べ、
  復旧が要るかを判定し、要るなら待たずに復旧する (旧案 A の検出 + 旧案 B の復旧)
- 🚨 **判定を誤ると PG を二重に起こす・利用枠を焼く。判定できないときは復旧せず、出すだけに倒す** (その後はいつもの経路 = 458 の 1 分待ちに任せる)
- `--view` の画面で dispatcher が居ないときに「dispatcher が動いていない」と出す (旧案 D) は入れる
- 前回の `--limit` を覚える (旧案 C) は採らない。上限を残すのは `pro-con config set limit` (456)

### 実測で分かった遅れの中身 (2026-09-26 00:18 の起動。events.jsonl)

- 起動して最初の Tick で watchdog が C-025 / C-026 を「15 分進捗なし」にした (進捗の時刻がクラッシュ前のまま。PG は居ない)
- C-027 のテストの係は `rc=-1` (「dispatcher が実行の途中で止まったので結果が無い。もう一度頼むこと」) で PG に返り、PG の再開 1 回ぶんを使った
- failed の session は `claude agents --json` (--all なし) に出ないので、458 の経路が 1 分 (restartWait) 待って戻した。
  待つのは Claude Code の自動の再開 (kill -9 の後の約 25 秒) と重ねないためで、再起動の後には自動の再開が無い (482 の実測: 30 分以上 failed のまま)

## 起動時の判定 (dispatcher が一覧を取れた最初の Tick で 1 度だけ)

対象は記録にある「動いているはずの session」: 作業中のカードの PG (起動・再開の結果待ちの印が無く、起動の記録に行がある) と、
PM・取り込みの係 (様子のファイルに session があり、終了で止めた印が無く、起動の記録に行がある)。対象が無ければ「前回は止め処理を経て終わった」。

| 形 | 判定 | すること |
|---|---|---|
| 一覧 (--all なし) に同じ session id で pid ありで居る | 生きている | 何もしない |
| **マシンの起動時刻 (`kern.boottime`) より前に始まった session で、`--all` の一覧に pid 無し・止まった state (failed / stopped / done) で居る** | **復旧が要る** (プロセスは再起動で必ず消えていて、Claude Code は再開しない) | 待たずに復旧する (下) |
| 起動時刻より後に始まった session が居ない (dispatcher だけが落ちた・外から止めた・kill) | 判定できない (自動の再開の途中かもしれない) | 出すだけ。いつもの経路 (458 の 1 分待ち) に任せる |
| 起動時刻より前だが、`--all` にも居ない / pid 無しの working・知らない state | 判定できない | 出すだけ |
| 起動の記録に session の開始時刻が無い (古い行・startedAt を出さない版) | 判定できない (「起動時刻より前」が常に真になるので使わない) | 出すだけ |
| 起動時刻・`--all` の一覧を読めない | 判定できない (対象すべて) | 出すだけ |
| 起動・再開の結果待ちの印があるカード・役 | 判定しない | いつもの確かめ (launchGrace) に任せる |

復旧のしかた:

- 待たない理由は「消えた時刻 (DeadSince) = マシンの起動時刻」で与える (プロセスは遅くとも再起動で消えた。起動から 1 分以内なら起動から 1 分までは待つ)。
  🚨 終了の印 (Stopped) は使わない: Stopped は落ちた回数・起こし直しの回数を数えない側で、PG・役がマシンを落としている形で再起動のたびに上限なく起こし直す
  (敵対的レビューの指摘。直す前の版がこの形だった)
- 作業中のカードの PG: 分解済みへ戻し、同じ session を「マシンの再起動で止まった。続きから」の文で再開する。
  落ちた回数に 1 回数え、458 と同じ上限 (30 分に 2 回) に達したら再開せずに人の回答待ちへ送る (両方が同じ `countCrash` を通る)。
  人の判断なしの再開には印 (`Revived`) を付け、再開で落ちた回数の数え始めを今に戻さない
  (前は「再開の文が 458 の文か」で判じていたので、文の違う再起動の復旧・テストの係の結果での再開では数え直していた)
- テストの係の結果を待っているカード: 戻さずに作業中のまま、テストの係に同じコマンドを頼み直す (下)。結果が出たら、待たずに PG を再開して渡す
- PM・取り込みの係: 消えた時刻を起動時刻にするだけ (知らせる物があるときだけ、待たずに起こし直す。起こし直しの回数 = 30 分に 3 回に数える)

テストの係の中断 (起動時の判定に限らない): 実行の途中で dispatcher が止まった実行は、残ったプロセスを止めてから同じコマンドを頼み直す
(PG に `rc=-1` を返して頼み直させない)。🚨 頼み直すのは 1 回だけ: 頼み直した実行がまた中断したら、実行がマシンか dispatcher を落としている
疑いがあるので `rc=-1` で PG に返す (頼み直した実行の途中で人が dispatcher を起動し直しただけでも rc=-1 になる。二重には走らないので、疑う側に倒したまま)。結果を待っているカードは、PG が一覧から消えても 458 の経路で戻さない (結果が出てから再開する)。

起動直後の watchdog の誤報: 復旧で分解済みへ戻したカードは見ない (上の復旧が watchdog より先に走る)。

### 出す形 (1 行)

- `pro-con log` (events.jsonl): 起動時の確かめの出来事 1 件。例:
  `起動時の確かめ: マシンは 09-25 23:52 に再起動した。待たずに復旧した: C-025・C-026・C-029・PM / テストの係を頼み直す: C-027 / 生きている: なし / 判定できないので待つ: なし`
- 画面のヘッダーのゲージの行: dispatcher が起動してから 10 分のあいだ、`起動時: 復旧 4 / 判定できない 0 (pro-con log)` の形で出す
  (dispatcher-state.json に要約を持たせる。復旧・判定できないが 0 なら薄く「起動時: 復旧は要らない」)
- `--view` を含む画面: dispatcher の lock のファイルの pid が居なければ (kill 0 が ESRCH)、Tick の古さを待たずに赤で「dispatcher が動いていない」
