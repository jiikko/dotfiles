# 426 (design): pro-con の未決の論点を決める

起票日: 2026-09-24

親: [415](../415-design-claude-pm-worker-orchestration.md) の論点 2〜11

## 概要

本物の PM / PG の backend ([427](../427-feat-pro-con-real-pm-pg-backend.md)) を作る前に決めることの一覧。
415 の各論点に叩き台はあるが、以下は決まっていない。実測 ([425](425-research-claude-bg-remaining-measurements.md)) の結果で決まるものと、ユーザーが決めるものがある。

## 決定 (2026-09-24 にユーザーへの聞き取りで決めた。細部は既定値で始め、動かしながら直す)

1. **カードの書き手は daemon だけ**。PM / PG はカードを直接書かず、`pro-con` のコマンド (例 `pro-con card add` / `ask` / `done`) で daemon に頼む。
   採番と不変条件の検査は daemon の 1 か所
2. **質問への回答は daemon が `claude stop` → `claude --bg --resume <id> "<回答>"` で届ける**。PG は AskUserQuestion を使わず、
   コマンドで質問を書いて turn を終える (425: AskUserQuestion には SendMessage で答えられない / daemon は SendMessage を呼べない)
3. **追加オーダー (追記) は PG の turn の区切りを待って届ける** (カードに積み、idle になったら stop → resume)。方針変更だけは止めて差し替える
4. **PG のプロセスが落ちたら Claude Code の自動の再開に任せ、回数で止める**。watchdog が再開の回数を数え、同じカードで短い間に 2 回 (既定)
   落ちたら session を止めてカードを失敗にし、人間に上げる。415 論点 5 の「落ちたら failed にして自動で再実行しない」はこれで置き換え
5. **make test / 実機 E2E の直列化は「テストの係」で巻き取る**。PG は係に頼み (コマンド)、**daemon が PG の worktree でコマンドを順番に実行**して
   ログと rc を返す。失敗したときだけ安いモデル (haiku) の Claude がログを読んで要約する (成功では token を使わない)。
   415 論点 9 の hook / shim で横取りする案は採らない (PG がテストの係を通すのは規律。通さずに回したら気づけるかは動かしながら見る)
6. **最初の役割は 4 つ**: PG (実装) / テストの係 (上の 5) / 調べる係 (安いモデル) / レビューの係
7. **調べる係は PG が作業中に呼ぶ**
8. **レビューの係は、カードがレビューの列に入ったら daemon が割り当てる**。diff と実行結果を読んで所見を PM に渡し、完了にする判断は PM に残す
9. **PM は 1 つで始める** (受付と担当を分けない)。レビューの列が溜まり続けたら担当 PM を足し、そのときに振り分けの単位を決める (415 論点 6 の実装は保留)
10. **watchdog の知らせは tmux の status と macOS の通知の両方**。status には常に件数 (質問待ち・停滞) を出し、macOS の通知は
    質問待ちと落ち続けた PG のときだけ (間引きの規則は動かしながら決める)。daemon が状態をファイルに書き、status がそれを読む

既定値で始めるもの (動かしながら直す): 停滞と判定するまでの時間 (`card.StallThreshold`) / 落ちた回数の上限 (2 回) /
役割ごとの体数 (`~/.config/pro-con/config.toml` に役割ごとに書く。最初は PG 2・調べる係 1・レビューの係 1、テストの係は daemon の列 1 本) / 通知の間引き

## 決めること (聞き取り前の一覧。上の決定で閉じた)

- [x] **カードの置き場所と書き手** (論点 3): PM の Claude がカードのファイルを書き pro-con が読むか、pro-con (daemon) がカードを持ち PM はコマンドで報告するか。叩き台は `~/.local/state/claude-pm/cards/`
- [x] **振り分けの単位** (論点 6): 受付 PM から担当 PM へ repo / 領域 / 負荷のどれで振るか。担当 PM を dispatcher が自動で増やすか
- [x] **質問への回答の届け方** (論点 8): 425 の実測で候補が増えた。PG は質問を書いて turn を終え (AskUserQuestion は使わせない。SendMessage で答えられない)、
  idle の PG へ SendMessage で答えを送る形が、`--resume` を使わずに文脈を保てる。これにするかを決める
- [x] **追加オーダーの届け方** (論点 11): SendMessage は busy の PG にも積めて、turn の区切りで届く (425 結果 3)。これで足りるか、方針変更だけ `stop` → `--resume` にするか
- [x] **PG が落ちたときの扱い** (論点 5): daemon がプロセスの死を自動で再開する (425 結果 1)。「落ちたら failed にして自動で再実行しない」を捨てて daemon に任せるか、
  再開された PG を watchdog が見張るだけにするか
- [x] **リソースの宣言** (論点 9): 宣言の書式と置き場所 (project ごとの設定ファイル)、入口を hook にするか PATH の shim にするか、占有中に固まったコマンドを自動で止めるか人間に上げるか
- [x] **watchdog** (論点 10): 通常の停滞の閾値、TUI を開いていないときの通知

## 役割ごとの session と、その数の設定 (2026-09-24 の要望)

「テストを回す係・ファイルを探す係のように、役割ごとの Claude Code の session を立ち上げたい。役割ごとに何体立てるかを設定したい」。
今は PG がすべてをやり、数は模擬の中で上限 2 に固定 (415 の決定事項)。

- [x] **役割の単位**: 役割ごとに `claude --bg` の起動のしかたを変えられる (モデル / `--agent` / `--settings` で使えるツールを絞る)。
  候補は「PG (実装)」「テストを回す係」「調べる係 (haiku)」。ファイルを探すだけなら PG の中のサブエージェントでも足りるので、
  別の session にするのは「安いモデルで回す」「同時に 1 つに絞る」ときに限る案
- [x] **テストを回す係と論点 9**: 占有リソース (make test / 実機 E2E) を回す係を 1 体に固定すれば、直列化を係の数で満たせる。
  PG は係へ頼み、結果を受け取る (頼み方は SendMessage か、カード / キューを介すか。425 結果 3)。論点 9 の hook / shim 案と比べて決める
- [x] **誰が役割を割り当てるか**: PM がカードかタスクに役割を付けるか、PG が作業中に係へ頼むか
- [x] **数の設定の置き場所**: `~/.config/pro-con/config.toml` に役割ごとの体数を書く (例 `[roles.pg] count = 2` / `[roles.test-runner] count = 1 model = "haiku"`)。
  実行中に増減するキーは、要るとわかってから足す。専用の設定画面は作らない案
- 前提 (425 結果 6): session 1 体ごとに起動時の context が約 13 万 token かかる。役割を増やすほど、この費用が体数に比例して増える
