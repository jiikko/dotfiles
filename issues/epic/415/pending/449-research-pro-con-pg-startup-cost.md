## 概要

今の pro-con は、カード 1 枚ごとに新しい PG の session (`claude --bg`) を起動する。同じカードの再開 (回答・テストの結果・差し戻し) でも、
会話は続けるがプロセスは起こし直して session の ID が変わる。ユーザーが「新しいカードを消化するたびに PG を立ち上げ直すってこと?」と聞き、
その起動コストを測った (「起動コストを測って issue に書いて」)。PG を常駐させて使い回す形 (プール) に替える価値があるかの判断材料にする。

## 分かったこと

1. **起動 1 回に固有のコストは小さい**。最初の応答まで 3〜8 秒 (うちプロセスが立って transcript に最初の記録が出るまで 1〜5 秒)。
   キャッシュへの書き込みは約 23.5k トークンで、残りはキャッシュから読んでいる。読んだ量は 24,645 (C-003 / C-004) と 26,601 (C-002 / C-005 / C-006) の
   2 種類で、PG どうしで先頭の一部を共有していると思われる (中身と 2 種類に分かれる理由は未確認)。起動の書き込み約 23.5k は、そのカードの書き込みの計の 18〜35%、
   読みを含めた入力の計の 0.3〜2.9% (カードが小さいほど比率が上がる: 応答 11 回の C-005 で 2.9%、59 回の C-002 で 0.3%)
2. **大きいのは起動ではなく、要求のたびに読み直す文脈**。各要求はそれまでの会話全体をキャッシュから読み直す
   (読み = 前の要求の読み + 前の要求の書き込み。C-004 で 20 回中 20 回成り立つ。C-002 の読みは 26,601 から 153,661 まで伸びる)。
   その先頭に毎回、最初の要求の約 48〜50k (CLAUDE.md・常時読まれる rules を含む) が同じ形で入っている。この先頭の分は、C-004 では
   21 回 × 約 48k ≈ 1.0M で読みの計 1.56M の約 65%、C-002 では 59 回 × 約 50k ≈ 2.95M で 7.04M の約 42%。残りはその session の会話の伸びの分。
   **PG を常駐させて使い回しても、先頭の分は減らない** (要求ごとに乗るため)。しかも同じ session で次のカードを続けると、
   前のカードの会話まで毎回読み直すので、読みはむしろ増える。減らすなら先頭そのもの (常時読まれる rules の量) を減らす
3. **再開はプロセスを起こし直しても、前の会話をほぼキャッシュから読む** (書き込み 163〜3,161)。
   1 回 (C-002) だけ 119k を書き直した (キャッシュに当たらなかった)。間隔は 5.7 分で、当たった回 (4.2〜5.5 分) と大差がない。
   原因は下の「C-002 の再開がキャッシュに当たらなかった理由」。**1 回だけではなく、C-002〜C-037 の再開 87 回のうち 22 回がこれだった**
4. **利用枠への換算** (下の「利用枠への換算」節。粗い値): 5 時間枠の 1% ≈ API 料金換算 $3.5、週の枠の 1% ≈ $22。
   起動 1 回 (書き込み約 23.5k) ≈ 5 時間枠の 0.05%、カード 1 枚 (中央値) ≈ 2.2%、再開の外れ 1 回 (平均 145k の書き直し) ≈ 0.33%

## C-002 の再開がキャッシュに当たらなかった理由 (2026-09-26、既存の transcript だけで調べた。PG も claude も起こしていない)

**結論: 再開したプロセスの最初の要求で tools の並びが起動時と変わり、要求の先頭からキャッシュと食い違った**。
並びが変わるのは `SendFeedback` が最初の要求の tools に入るかどうかで、これがプロセスの起動ごとに揺れる (揺れる理由は未確認)。

- 起動時の先頭の読みが 2 種類 (26,601 / 24,645) だったのはこの違い。transcript の `prompt_snapshot` (起動時の system prompt と tools) を
  C-002 (26,601) と C-003 (24,645) で比べると、違いは tools の `SendFeedback` (26,601 の側にだけ在る) と、system prompt の `EndConversation` の案内の段だけ
  (他は session ごとの job の置き場のパスで、先頭の共有部分より後ろ)。24,645 の側では両方とも、最初の応答の数秒後に `deferred_tools_delta` で会話へ足される
- C-002 は 26,601 の側で起動し、再開の最初の要求は 24,645 しか読めなかった = `SendFeedback` の無い側の共有部分だけが当たった。
  直前に `thinking_drop` (reason `prefix_mismatch`、前の会話の thinking 35 ブロックを落とした) が記録され、会話全体 119k を書き直した。
  再開時の tools そのものは transcript に残らない (`prompt_snapshot` は起動時だけ) ので、「tools が変わった」は読みの量と `prefix_mismatch` からの推定
- 同じ形は C-002 だけではない。C-002〜C-037 の再開 (前の起動・再開から 60 秒以上空いたプロセスの最初の要求) 87 回を分けると:

| 起動時の先頭 | 再開 | 当たり | 外れ (`thinking_drop` 付き) | 外れ (その他) |
|---|---|---|---|---|
| 26,601 (`SendFeedback` 在り、33 session) | 74 | 50 | 22 (18 session) | 2 |
| 24,645 (`SendFeedback` 無し、5 session) | 13 | 13 | 0 | 0 |

- 22 回のうち各 session の最初の外れ 18 回は、どれも読みがちょうど 24,645。残る 4 回は同じ session の 2 回め以降で、読みは 28,876 / 28,875 / 26,919 / 26,601
  (C-030 の 2 回めは 26,601 = 1 回めで `SendFeedback` 無しの形に書き直された会話が、今度は在りの側で再開して外れた。向きは逆でも同じ仕組み)。
  28,875 / 28,876 / 26,919 がどの並びに当たるかは未確認
- 間隔では分かれない (前の起動・再開から、外れ 3〜63 分・当たり 2〜43 分)。1 時間の TTL を越えたのは「その他」の 1 回 (C-022、115 分) だけ。
  もう 1 回 (C-013、4 分、読み 0) は理由が分からない
- 外れの直前には毎回、`EndConversation` を外す `deferred_tools_delta` がある (18 回中 18 回) が、同じ記録があって当たった再開も 7 回あるので決め手ではない
- 版はどれも claude 2.1.282
- **損の大きさ**: 外れ 22 回で書き直したのは計 3.20M トークン (1 回平均 145k、= その時点の会話の大きさ)。
  2026-09-25 の PG (C-002〜C-046) の書き込みの計 8.98M の約 36%。起動 1 回の書き込み約 23.5k の 6 倍前後を、再開の 4 回に 1 回ほど払っている

## 利用枠への換算 (2026-09-26、LLM を呼ぶ起動 0 回)

**結論 (粗い値)**: 5 時間枠の 1% ≈ API 料金換算 $3.5、週の枠の 1% ≈ $22 (5 時間枠 100% ≈ 週の枠の 16%)。
ただし「枠は API の料金と同じ比で減る」と仮定したときの値で、**書き込み・読み・出力の重みは分けられなかった** (下記)。

### 測り方

- `claude -p /usage --model haiku --output-format json` で % を取る。LLM を呼ばない (`num_turns` 0・トークン 0 を結果の JSON で確認)。
  ユーザーの決定 (2026-09-26): 区間は PG が決めてよい・取るのは 3 区間 (claude の起動 6 回) まで。取ったのは 4 点 (起動 4 回)
- 区間のトークン: `~/.claude/projects` 配下の全 transcript (subagent を含む、pro-con 以外も) から、区間内の応答を `message.id` で重複を除いて model ごとに足す。
  `claude agents --json --all` の一覧と照合して、区間に応答があって一覧に無い session は 0
- **数え方が `/usage` 自身と合っていることを確かめた**: `/usage` の「Last 24h · 7493 requests · 189 sessions」「Last 7d · 12622 requests · 231 sessions」に対し、
  同じ数え方で 7,494 回・189 session / 12,623 回・231 session (差の 1 回は、取った直後の自分の応答と思われる。未確認)
- `/usage` の % は枠の始まりからの累計なので、**「枠の始まり → 1 点め」も区間として使える** (追加の起動なし)。枠の始まり = リセット時刻 − 5 時間 / − 7 日
  (5 時間枠 2026-09-25T22:39Z、週 2026-09-24T22:59Z)
- 重みの仮定: API の料金 (claude-api skill 同梱の表。Opus 5.5 は入力 $4・出力 $20/MTok、読み 0.1 倍、書き込み 5 分 1.25 倍・1 時間 2 倍。Sonnet 5 は $2 / $10、Haiku 4.5 は $1 / $5) で重み付けして足す

  $3.5 / 1% の見当と矛盾しない ($1.28 ≈ 0.4%)
- **重みを分けられない理由**: 大きい 2 区間は内訳がほぼ同じ (読みが 6〜7 割) で、式が 2 本でも独立にならない。読み中心・出力中心など混ぜ方の違う区間が要る。
  料金と同じ比という仮定そのものも、この測り方では検証できていない
- `/usage` は「Approximate, based on local sessions on this machine — does not include other devices or claude.ai」と出す。この注記が内訳の欄だけか % にも掛かるかは未確認
  (glogx の `src/glogx/usage/usage.go` は % にも掛かると読んでいる)。% にも掛かるなら問題ない。掛からずに他の端末・claude.ai の分も % に入っているなら、手元のトークンだけで割った $/1% はその分だけ小さく出ている

## 判断材料 (2026-09-26 決定: プールしない)

- プールで減らせるのは、カード 1 枚あたり 3〜8 秒と書き込み約 23.5k トークンだけ。代わりに、文脈が混ざる・worktree を切り替える・
  止める対象 (カードと session の 1 対 1) を別の仕組みで守る、が要る。**今の「カード 1 枚 = 新しい session」を続けるのを推す**
- 効くのはむしろ 2 の固定の文脈の方。PG に常時読ませる rules を減らす (PG 向けに `--setting-sources` などで絞る) 案は、
  PG が rules に従うこと (変異の確認・pathspec commit) と引き換えになるので別に検討する (未起票)
- 再開の外れ (上節) は、起動そのものより大きい。PG を常駐させれば再開でプロセスが変わらないので起きないが、
  それより安い手として **PG を起こすときに tools の並びを揃える** (例: pro-con が `--disallowedTools SendFeedback` を付けて、どのプロセスでも `SendFeedback` を tools に入れない)
  がある。**未検証**: 付けたときに tools から消えるか、`EndConversation` の段も揃うか、28,875 などの別の並びが残らないかは、起動して確かめる必要がある (未起票)
- 再評価の trigger: 応答が数回で終わる小さなカードが多数になったとき (起動の比率が上がる) / 再開でキャッシュに当たらない回が増えたとき

## 反証レビュー (2026-09-25、sonnet・別の数え方: requestId で束ね、再開の写しを親 session の uuid で除く)

- 2 つの表の数字は C-002〜C-005 で一致 (C-006 は作業中で伸びている)
- 採った: 読みの仕組みの説明 (固定の文脈が乗るのではなく会話全体の読み直しで、その先頭に固定の文脈が入る) / 先頭の共有は 2 種類に分かれる
- 却下: 「先頭の分の見積もりは偶然の一致」— 最初の要求の文脈は後のどの要求にも先頭として入るので、n × 最初の文脈 は先頭の分をそのまま数えている /
