# 475 (design): 見張りの係 — 決まった判定は dispatcher に、要約と判断は常駐の haiku (monitor 役) に

起票日: 2026-09-25

親: [415](415-design-claude-pm-worker-orchestration.md)

## 概要

ユーザーの提案 (2026-09-25): 利用枠が 80% に達して dispatcher が同時に動かす PG を 1 本に絞ったのを見て、「ratelimit に合わせて消費を抑えるムーブはいいね。
dispatcher なのか、monitor ロール (haiku) あたりを常駐して定期的にチェックさせてもいいかもね」。
2026-09-25 の夜、PM (人間の代わりの Claude) は使い捨ての見張りのスクリプト (カードの状態の変化・`git merge-tree` で master と PG どうしの取り込みの衝突・
PG ごとの最新の commit を 60 秒ごとに見て、変わったら PM を起こす) を手で回していた (440 の 5 回目)。

## 分け方 (叩き台)

1. **決まった手順で判定できるものは dispatcher** (トークンを使わない。今の利用枠の絞り (stage 5) と同じ形):
   カードの状態の変化 / 取り込みの衝突 (commit 済みの分を `git merge-tree` で。master と、作業中どうし) / 停滞 (watchdog) / テストの順番の長さ / 枠の枯れ。
   結果は出来事 (444 の events.jsonl) に出し、画面・PM・外の Claude (441) が読む
2. **判断・要約が要るものは monitor 役 (haiku)**:
   - 進み具合の要約 (「C-009 は変異の検証の 21 本目・あと 5 分ほど」。467 / 469 / 473 の中身を人向けに 1 行へ)
   - テストの失敗が、その変更のせいか・負荷で落ちただけか・前から落ちるかの一次判定 (2026-09-25 の C-010 の tmux のテスト = 単独では緑。471)
   - 人が見るべきことの知らせ (人の番 (452)・止められない PG・枠の枯れ・同じ判断を変えるカードが並んだ (468))
   - 今のテストの係の要約役 (`dispatcher/runner.go` の `HaikuSummarize`。426 の決定 5) と同じ系列の役として置く
- 🚨 常駐と起動のコスト: 1 回の起動で約 5 万 token の固定の文脈 (449 の実測)。決まった間隔で起こすより、**dispatcher の出来事をきっかけに起こす** (1 の結果が変わったときだけ) 方がよい。
  利用枠が高いときは monitor 役を起こさない (stage 5 の絞りに含める)
- monitor 役は読むだけ (カードの記録・受付の箱・PG に書かない。知らせは出来事として dispatcher が書く)。`--setting-sources` と `--no-session-persistence` で軽く起こす (460 の P3: 要約の係の transcript が残る件も合わせて直す)

## 設計案 (2026-09-26。487 の役の仕組みを踏まえて)

### 487 の役 (`dispatcher/role.go`) に載せるか → 載せない案を推す

role.go の役は「知らせる物のカードがあれば `claude --bg` の常駐の session を起こし、居れば idle を待って再開する」状態機械。見張りに当てると 4 点合わない:

1. 知らせる物の鍵がカード (`key func(card.Card)`)。見張りのきっかけは衝突・停滞・テストの失敗・枠など**カードの状態ではない出来事**が多い
2. `Launcher.Start` / `Resume` にモデルの口が無く、`sessionSettings` は `~/.claude/CLAUDE.md` を残す (PG・PM 向け)。haiku で軽く起こす形にならない
3. 常駐すると会話が伸び、要求のたびに会話の全体を読み直す (449 の 2)。見張りは知らせの回数が PM より多いので、伸びた分が効いてくる
4. 見張りは読むだけで、書く先は出来事だけ。`-w` で worktree を作る必要がない

案: **常駐させない。dispatcher の出来事をきっかけに、使い捨ての `claude -p --model haiku` を起こす** (`runner.go` の `haiku()`。`HaikuSummarize` / `HaikuAsk` と同じ系列)。

- **材料は dispatcher が集めて prompt に入れ、haiku は判断と要約だけをする** (`HaikuSummarize` がログの末尾を渡すのと同じ形)。tools を渡さなければ「読むだけ」は指示書の規律ではなく構造で決まる
- `haiku()` に `--no-session-persistence` を足す (460 の P3。今は要約の係の transcript が 1 回あたり約 200KB 残る)
- 1 回あたりの固定の文脈は、`--setting-sources project,local` と `claudeMdExcludes` があるので PG の 48〜50k (449) より小さいはず。**未実測**なので、実装の最初に 1 回測る
- role.go から借りるのは、枠を見て起こさない判断 (`capacity`) だけ

### 何を見るか (2 段に分ける)

段 1 — dispatcher が決まった手順で判定する (token を使わない)。状態の変化・停滞 (`KindWatchdog`)・枠 (`KindHold`) は既に出来事になっているので、新しく作るのは次の 2 つ:

- **取り込みの衝突**: commit 済みの PG のブランチを `git merge-tree --write-tree origin/master <branch>` で master と、作業中の PG どうしとも突き合わせる。
  レビューの列に来る前に分かれば、取り込みの係 (487) が rework で戻す往復を 1 回減らせる。新しい出来事の種類 `conflict`
- **テストの順番の長さ** (471): 順番待ちの本数と、先頭の待ち時間

段 2 — haiku が出来事をきっかけに判断・要約する:

| 中身 | きっかけ | 回数 | 備考 |
|---|---|---|---|
| テストの失敗の一次判定 (その変更のせいか / 負荷で落ちただけか / 前から落ちるか) | テストの係の失敗 | 少ない | 今の `HaikuSummarize` の prompt に「カードの diff の stat・master の同じテストの直近の結果」を足すだけで、**起動は増えない** |
| 同じ判断を変えるカードが並んだ (468) | カードが増えた | 少ない | 決まった手順では判定できないのはこれだけ。人の番・止められない PG・枠の枯れは段 1 で足りる |
| 進み具合の要約 (「C-009 は変異の検証の 21 本目・あと 5 分ほど」) | カードの活動 (467) の変化 | **多い** | コストの大半はここ。画面が開いていて、同じカードは N 分に 1 回まで、に絞る |

### 枠の使い方

- stage 5 の絞りに含める。PG を 1 本に絞る (80%) より先に haiku を削る
- 段 1 は token を使わないので、枠と関係なく続ける

## 決めること (人間に質問中。2026-09-26)

1. 常駐させるか: (推) 常駐させず出来事ごとの使い捨ての haiku / role.go の役として常駐させる / haiku を使わず段 1 だけ
2. 最初に作る範囲: (推) 段 1 の 2 つ + テストの失敗の一次判定 (今の要約役を広げる)。468 の知らせと進み具合の要約は後 / 段 2 まで全部
3. 枠: (推) 80% で進み具合の要約を止め、失敗の一次判定は 95% まで続ける / 80% で haiku を全部止める
