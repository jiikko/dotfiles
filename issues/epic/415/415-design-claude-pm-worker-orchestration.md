## 概要

Claude Code の使い方を「session を立ち上げてそこで作業する」から、**要件を聞く PM と作業する PG を分ける**形へ移す。
人間は基本的に PM とだけ話し、PM が積んだタスクを PG が消化する。**人間の依頼はすべてタスクカードとして記録し、
どこへ行ったか分からなくなる状態を作らない**。PG の数は待ち時間を見て自動で増減させ、カードの進捗・溜まり具合・
タスクごとのログを TUI で見られるようにする。

## 背景 (いまの困りごと)

いまは session を PG に見立て、人間が各 session に直接作業させている。

- **session を行き来すると、その session が何をしていたか忘れる**。状態が人間の頭の中にしか無い
- **コンフリクトを人間がうっすら考えている**。どの session がどのファイルを触るかの管理が人間の仕事になっている
- 話しかける相手が N 個あり、切り替えのたびに文脈を思い出すコストがかかる
- Claude Code Desktop で複数 session をマルチウィンドウで立ち上げると、**全 session のウィンドウが常に表示されて邪魔**。PG は画面を持たず裏で動き、必要なときだけ前に出す形にしたい
- PM を挟むと、今度は **「PM に依頼した後、そのタスクがどこへ行ったか分からなくなる」** のが怖い

## 要件

1. **窓口は PM**。人間は PM に依頼し、PM がタスク (要件・受け入れ条件・触る予定のファイル) を書いてキューに積む
2. **PG の自動スケーリング**。キューの滞留 (件数・最古の待ち時間) を見て PG を起動し、キューが空になったら増やさない。上限を持つ
3. **タスクごとのログ**。PG はタスク単位でログを残し、後から読める
4. **TUI でキューの溜まり具合を表現する**。状態ごとの件数と最古の待ち時間が一目で分かる。タスクを選ぶとログを tail できる
5. **たまに PG と直接話せる**。TUI から該当 PG の session を対話で開ける (本物の Claude Code の画面で。論点 7 の「PG との対話」)
6. **コンフリクトを人間が考えなくてよい**。触る予定のファイルが重なるタスクは同時に走らせない。PG ごとに worktree を分ける
7. **依頼はタスクカードとして仕組みで管理する**
   - 人間が PM に依頼したら、PM は**作業に入る前に**カードを 1 枚作る (安定 ID / 依頼の原文をそのまま / 日時)
   - カードは作成から終了まで必ずどこか 1 つの状態に居て、担当 (PM / どの PG / 人間待ち) が分かる。状態が変わるたびに履歴へ追記する
   - 1 つの依頼を複数のタスクに分けた場合は、親子関係で元の依頼までたどれる
8. **進捗を TUI で視覚的に見る**。カンバン風に、カードを状態の列に並べる。カードを選ぶと、履歴とそのタスクのログが見られる
9. **TUI から btw 的な横入り質問ができる**。カードを選んで「今どうなってる？」と聞ける。**作業中の PG は止めず、その文脈も汚さない**
   (Claude Code の `/btw` と同じ性質。回答は PG の最新出力 (`claude logs <id>` 等) を元に、別プロセスで返す)
10. **カードと issue の紐づけを可視化する**。**PM への依頼が必ずしも issue になるわけではない**
    - カードは必ず作られるが、紐づく issue は 0 件のことも複数件のこともある (その場で回答した / 調べて終わった / 却下した)
    - issue に紐づかないカードは**終わり方**を必ず持つ: `回答済み` / `調査のみ` / `却下 (理由)` / `issue 化待ち`
    - 🚨 **`issue 化待ち` のまま放置されたカードは TUI で目立たせる** (依頼が行方不明になる典型的な形)
    - TUI はカードに紐づきのバッジ (`#415 #416` / `issue なし: 回答済み` / `⚠ issue 化待ち`) と、紐づく issue の状態 (open / next / done) を出す
    - 逆方向もたどれる: issue 側から、元になったカード (依頼の原文) を参照できる
11. **PG からの質問に TUI から直接答えられる**
    - 質問待ちのカードを選ぶと、質問文とその前後の文脈 (PG の最新出力) が出て、その場で回答を書ける
    - 回答は PG へ届き、作業が再開する。質問と回答はカードの履歴に残る (PM を経由しない回答も、後から PM と人間が読める)
    - PM が答えられる質問は PM が先に答えてよい。人間が答えるべきものだけが人間の列に来る
12. **長時間占有するリソースを PG 間で直列化する**
    - 対象: `make test` / `make lint` / 実機の E2E テスト / xcodebuild のように、並行させると遅くなる・壊れる・固まるもの
      (実例: xcodebuild と同じ checkout の SwiftPM を並行させると無限待ちになる。`~/.claude/rules/no-concurrent-spm-build-during-xcodebuild.md`)
    - どのコマンドがどのリソースを占有するかは **project ごとに宣言**する (例: 実機 E2E は `device`、xcodebuild 系は `xcode`)
    - 取れなければ**順番待ち**にする (FIFO)。待っている PG は「リソース待ち」として TUI に出る (何の後ろに何番目か、何分待っているか)
    - PG が宣言を知らずに素の `make test` を打っても列に並ぶよう、**実行の入口で横取りする** (PreToolUse hook か wrapper)。PG の規律に頼らない
13. **watchdog (heartbeat 確認役) が常にいる**
    - よくある故障: PG がプログラムの完了を待っているのに**ポーリングを忘れて無限に待つ** / 背景ジョブは終わったのに PG が気づかない / 出力が止まったまま動かない
    - watchdog は PG ごとに「最後に進んだ時刻」(transcript の更新・ツール呼び出し・出力) を見て、決めた時間を超えたら
      ①PG に「待っているものの状態を確認して」と促す → ②それでも進まなければカードを `停滞` にして人間に知らせる
    - **正当な待ちは停滞に数えない**: リソース待ち (要件 12)・質問待ち (要件 11)・利用枠待ちは状態として分かっているので除外する
    - watchdog 自身と daemon が止まっていないかも見える形にする (誰が watchdog を見張るか、の答えを持つ)
14. **どこが落ちても復元できる** (Claude Code Desktop のように、開き直せば元どおり)
    - **TUI のクラッシュ**: 何も失わない。TUI は状態を持たないので、開き直せば同じ画面に戻る。
      書きかけの回答 (要件 11) と選択中のカード・列は下書きとして保存し、開き直したら戻す
    - **daemon のクラッシュ**: PG (`claude --bg`) は Claude Code 側が持つ session なので、daemon が落ちても作業は続く。
      daemon は再起動時に、カードとキューのファイルと `claude agents` の一覧を突き合わせて状態を組み立て直す
      (カードでは running なのに session が居ない → `failed`。session は居るのにカードが無い → 人間に見せる。黙って消さない)
    - **マシンの再起動**: 会話は残る (`claude stop` 後も `attach` / `--resume` できると help にある)。bg session が再起動を越えて
      自動で戻るかは未実測。戻らないなら daemon が `--resume` で起こし直す
    - **PM**: Desktop の session なので Desktop 側の復元に乗る。PM が落ちても、依頼はカードとしてファイルにあるので失われない
15. **作業中のタスクへ追加オーダーを出せる**
    - 受け口は受付 PM か TUI (作業中のカードを選んで書く)。どちらの経路でも**元のカードの子カード (追加オーダー)** として記録する。
      PG の session へ直接言うだけにしない (カードに残らず、依頼が行方不明になる)
    - 担当 PM が 3 種に仕分ける: **追記** (同じ範囲の小さな追加 → 作業中の PG へ届ける) / **方針変更** (今の作業と矛盾 → PG を止めて指示を差し替えて再開) /
      **別件** (範囲が違う → 新しいカード。同じファイルを触るなら元のカードの後ろに並べる)
    - 届く前に PG が終えて自分のブランチへ push していたら、同じブランチの続きのタスクにする (PM のレビューは 1 回にまとめる)

**カードの単位は「人間の依頼 1 件」** (2026-09-24 に確認)。プロンプト 1 回分とは一致しない:
1 回のプロンプトに依頼が複数あれば PM がカードを分ける (親子) / 同じ依頼への追いかけの指示は追加オーダー (子) /
質問への回答はそのカードの履歴 / その場で答えて終わる質問も 1 枚 (終わり方は「回答済み」)。

### 不変条件

- **依頼は失われない**: カードの無い作業も、どの状態にも居ないカードも存在しない
- **すべてのカードは「紐づく issue を持つ」か「終わり方を持つ」のどちらか** (終了済みのカードについて)
- **カードが指す issue は実在する**: issue が done へ移動・改番されても切れない (パスでなく番号で参照する)
- **占有リソースは同時に 1 つの PG だけが持つ**。待っている PG は必ず列のどこかに居る (列から消えた待ちを作らない)
- **running のカードは、進んでいるか、既知の理由で待っているか、`停滞` として人間に見えているかのどれか** (黙って止まっているカードを作らない)
- **状態の正本はファイルだけ**。どのプロセスのメモリにも、ファイルから組み立て直せない状態を置かない (書き込みは atomic rename で行い、途中で落ちても壊れた状態を残さない)
- **追加オーダーは必ず元のカードの子として記録され、PG へ届いたか未達かがカードで見える**
- **1 つの worktree で動く PG は常に 1 体**
- これらは検査で確かめられる形にする (例: 状態の場所を全部数えた数 = カード総数 / 紐づく番号が issues/ 配下に実在する)

## 想定する使い方 (いつ pro-con を使うか)

- **ゼロから作るときは使わない**。設計を固めながら 1 本の流れで書く段階は、Claude Code を直接使う方が速い (PM を挟むと依頼 → カード → レビューの往復が増えるだけ)
- **使うのは、動くものができてから修正点が五月雨式に出てくる段階**。小さく互いにほぼ独立した修正が次々に来て、並列数が 4 前後になると人間では収拾がつかなくなる。そこを引き受けるのがこのツールの価値
- **直接使う session と pro-con は同居する**。人間は必要に応じて Desktop で直接作業し、その session も一覧に出る (`claude agents --json` が `kind: interactive` で返す)
  - 🚨 **リソースの直列化 (要件 12) は直接使う session にも効かせる**。PG の環境だけに掛けると、人間の session の `make test` / xcodebuild が PG と競合する。
    hook は `_claude/settings.json` 経由で全 session に効くので、横取りの入口はそちらに置く
- 五月雨式の修正で起きやすいこと (設計で前提にする):
  - **同じファイルに修正が集まる**。触る予定のファイルの重なりによる直列化 (要件 6) が効く場面が多い
  - **1 件が小さい**。カード 1 枚あたりの手間 (PM の分解・レビュー) が作業そのものより重くなりうる。関連する小さな修正を PM が 1 タスクにまとめてよい
- 並列数: 初期値は 2 (決定事項)。**目標は 4 前後**。上げるかどうかは review の滞留で判断する (レビューが追いつかないうちに PG を増やさない)

## ツールの形 (2026-09-24 に決めたこと)

- **名前は `pro-con` (仮)**。producer-consumer から。役割も **PM = producer / PG = consumer** と呼ぶ。
  ハイフン区切りは `bin/ci-log` / `bin/mutate-verify` と同じ流儀。PATH と Homebrew に同名なし (2026-09-24 に確認)
- **glogx のような TUI**。glogx からショートカットで開ける
- **画面は TUI を主にし、Web は後から足せる構造にする**。TUI を選ぶ理由: glogx / `src/tuikit` の部品とキー操作の流儀を流用できる、
  「開いて見て閉じる」なので常時表示のウィンドウを増やさない、ネットワークに口を開けない。Web が勝つのは多列のカンバンと、
  **席を離れているとき (スマホ) に PG の質問へ答える**場面。そのため daemon が状態をファイルで持ち、画面は読むだけ + daemon へ指示を送るだけの薄い層にする
  (ロジックを画面に置かない)。🚨 Web を足すなら、localhost のサーバーが「エージェントに指示を送る口」になるので、認証と公開範囲の設計が別に要る
- TUI を閉じているときの質問待ち・停滞は macOS の通知で知らせる (手段は未決)
- **TUI と常駐プロセスを分ける** (プロセスとしては別。TUI は状態ファイルを読み、指示を出すだけ)。daemon は 1 つに限る (daemon.lock の flock)。
  - 🚨 **開閉と daemon・PG の寿命は 2026-09-25 にユーザーが決め直した**: 画面を開くと daemon が居なければ起こし (`pro-con daemon` を別のプロセスグループで)、
    画面を閉じると daemon と pro-con が起動した PG を止める。作業中のカードは次に開いたとき続きから再開する (427 の「終了の扱い」)。
    もとの「TUI を閉じても daemon と PG は裏で動き続ける」は捨てた。閉じる操作は **Q を押して quit と打って enter** だけ
    (q や ctrl+c の 1 打では閉じない。閉じると PG を止めるので、打ち間違いで止めない)
  - 画面を開かずに動かし続けたいときは、今は手で `pro-con daemon` を起動する (閉じたときに画面が止めるのは同じ daemon)。
    席を離れている間も回す形 (launchd で常駐・スマホから答える) を入れるなら、この決定を見直す
  - 「TUI 起動時に居なければ起こす」はもとの設計にあったが、2026-09-25 まで実装されていなかった (画面だけ開くと依頼が箱に溜まったまま進まなかった)
- **人間は普段 Claude Code Desktop で session を動かしている**。tmux の `@claude_state` は Desktop の session を見られないので、
  段階 1 の見える化は transcript (`~/.claude/projects/*/*.jsonl`) を読む。Desktop の全 session が同じ形式で書かれるかは未実測

## 設計案 (未確定の叩き台)

```
人間 ⇄ PM (対話 session)
          │ ① 依頼を受けたら即カードを作る (原文・ID)
          │ ② 必要ならタスク / issue に分解してキューへ
          ▼
      カード + キュー (ファイル。状態は位置で表す)
          │ dispatcher (決定論的なスクリプト) が滞留を見て PG を起動
          ▼
      PG = claude --bg -w (1 タスク 1 session / Claude Code が作る worktree)
          │ claude agents --json で状態、transcript で出力を読む
          ▼
      glogx の PG 画面 (カンバン + ゲージ + ログ tail + attach + btw)
```

### 論点 1: スケーリングを誰が決めるか — **決定: dispatcher (機械)** (2026-09-24)

要望は「PM に連絡して、PM が待ち時間を考慮して PG を立ち上げる」。ただし判断そのものは
**決定論的な dispatcher に置き、PM (LLM) は「積む」と「上限の変更・即時の増員依頼」を行う**形を推す。
要望 (PM が待ち時間を考慮する) からの変更点だったが、2026-09-24 にユーザーが dispatcher で合意した。

- LLM に常時監視させると、判断のたびにトークンを使い、判断もぶれる。滞留件数・待ち時間・上限の比較は機械で足りる
- スケーリングの判断材料: キュー件数 / 最古の待ち時間 / 稼働中の PG 数 / 利用枠の残量 / **worktree のディスク使用量とビルドキャッシュの肥大** (PG 1 体ごとに worktree が増える)

### 論点 2: PG の形態 — `claude --bg` を第一候補にする

反証レビューで、Claude Code (2.1.281 で `claude --help` 実測) にネイティブの background session 管理があると分かった:
`claude --bg` (起動して id を返す) / `claude agents` (一覧) / `claude attach <id>` (対話で開く) / `claude logs <id>` (最近の出力) /
`claude stop <id>` (会話は残り、再度 attach 可) / `claude rm <id>` (安全なら worktree ごと削除) / `claude respawn`。

| 形態 | 利点 | 欠点 |
|---|---|---|
| **`claude --bg`** | 要件 5 (直接話す) を `attach` でそのまま満たす。一覧・ログ・停止が CLI にある。worktree の後始末も `rm` が持つ | trust 済みの repo の下でしか起動しない (`-w` で worktree を作らせて回避。下記) |
| タスクごとに `claude -p --output-format stream-json` | 起動・終了・完了判定が簡単。出力がそのままログになる | 実行中に割り込めない (終わってから `--resume` で開く) |
| tmux pane に常駐する対話 session | 途中で話しかけやすい | 何件もこなすと文脈が混ざり compaction で前タスクの前提が残る。自動化が send-keys 頼み |

**`--bg` の実測** (2026-09-24 / Claude Code 2.1.281 / `~/dotfiles` から haiku で 1 本起動して確認。stdout・stderr・rc を分けて採った):

- ✅ **権限プロンプトで止まると `claude agents --json` に出る**: `"status":"waiting","waitingFor":"permission prompt","state":"blocked"`。
  `waiting` の検出 (論点 5 / 要件 13) はこれで機械的にできる。`--permission-mode default` でファイル作成を頼むと、Write の確認で止まった
- ✅ **`claude agents --json` は機械で読める** (TTY 不要)。項目は `pid` / `id` / `cwd` / `kind` (`interactive` / `background`) / `startedAt` /
  `sessionId` / `name` / `status` (`idle` / `busy` / `waiting`)、bg には `waitingFor` / `state` も付く。**Desktop の対話 session も `kind: interactive` で並ぶ**
  (実測時 6 本: `status` は idle / busy のみ観測)。段階 1 の見える化の情報源に使える。`--all` で完了済みも含む。完了と異常終了の区別は未確認
- ❌ **`claude logs <id>` は端末の生の描画 (ANSI エスケープ込み)** で、機械で読むのには向かない。ログは transcript (`sessionId` から引ける jsonl) を読む
- 🚨 **trust していないディレクトリでは `--bg` が起動しない** (`Workspace not trusted. Run claude in <dir> once and accept the trust prompt` / rc=1)。
  dispatcher が自前で作った worktree は trust されていないので起動できない。**`claude --bg -w <name>` で Claude Code に worktree を作らせる**と、
  trust 済みの repo の下 (`<repo>/.claude/worktrees/<name>`、ブランチ `worktree-<name>`) にでき、そのまま起動した。したがって **PG の worktree は `-w` で作る**
- ✅ **`claude rm <id>` は session と、`-w` で作った worktree を消す** (ブランチも残らなかった)。未 push の commit や未コミットの変更がある worktree は、
  help によると `--discard-unpushed` / `--force-remove-worktree` を渡さない限り消さない (この安全側の挙動は未実測)
- 起動時に `TMUX` / `TMUX_PANE` を落とした (論点 5)。落とさない場合の上書きは未実測
- 🚨 **実測時点で weekly limit の 79% を使用中だった** (bg session の描画に出た)。枠の残量は bg session の画面からは読めるが、機械で読む口は未調査

### 論点 3: カードとキューの置き場所

- **カードは issue と別物**として持つ (要件 10: issue にならない依頼がある)。repo 横断の置き場 (`~/.local/state/claude-pm/cards/`) に置き、
  issue へは `repo + 番号` で紐づける
- タスクの本文は各 repo の `issues/` に置く (claim は `next/` の symlink。既存の規約・hook・glogx の issues viewer が使える)
- 人間の依頼は複数 repo にまたがるので、カード側は repo 横断で 1 つの TUI に出す

### 決定事項 (2026-09-24)

- **PG は master へ直接 push しない**。PG は自分の worktree で commit し、自分のブランチまで push する。PM がレビューを通してから master へ載せる
- **PG の権限**: 自分の worktree の中での編集・テスト・commit は許可する。push は自分のブランチまで。外部への送信 (PR 作成・API) と削除系は PM を経由する
- **依頼のカード化は PM の規律に任せる** (機械で強制しない)
- **複数 repo に対応する**。カードは repo 横断で持ち、タスクは各 repo の `issues/` に置く (論点 3)。最初に流すのは dotfiles の件だけの見込み
- **PG の同時実行数の上限は 2 から始める** (未回答のため推しの値。実測で調整する)

### 論点 4: カードの状態遷移

`依頼 → 分解済み → queued → running → review (PM が diff と実行結果を読む) → done`。分岐は `waiting` (質問待ち) / `failed` と、
issue にならない終わり方 (`回答済み` / `調査のみ` / `却下` / `issue 化待ち`)。

- PG の「完了」は証拠にならない。**PM が diff と実行結果を読んでから done にする** (subagent-model-tiering の検閲と同じ扱い)
- `waiting` になったら PM か人間が答え、再びキューへ戻す

### 論点 5: 失敗モード (設計で吸収するもの)

| 失敗モード | 吸収の仕方 (案) |
|---|---|
| PG が途中で落ちる / マシン再起動 | 結果が無いまま session が居ない → `failed` にして worktree は残す。自動で再実行しない |
| **dispatcher 自体が落ちて誰も気づかない** (起動 0 のまま滞留) | TUI のゲージに dispatcher の生存 (最終 tick の時刻) を出し、古ければ警告する |
| dispatcher が 2 つ起動する | `lockman` で dispatcher 自体を排他する |
| **PG が権限プロンプトで止まる** | 許可するツール / permission mode を起動時に固定する。それでも止まったら `waiting` として検出する (検出方法は論点 2 の実測待ち) |
| **dispatcher を tmux pane から起動すると、PG が `TMUX_PANE` を継承する** | `_claude/hooks/tmux-pane-state.sh` は `TMUX_PANE` があれば `@claude_state` を書くので、PG の状態が起動元 pane のバッジを上書きする。PG の起動時に `TMUX_PANE` / `TMUX` を落とす |
| 利用枠 (5h / weekly) の枯渇・429 | 新規起動を止めて待つ。並列の上限は枠の残量で下げる。枠の読み方は未調査 |
| push の衝突 | PG は自分のブランチへ push するだけなので、master との衝突は PM が統合するときにだけ起きる。PM が解消できなければ人間に上げる。自動 rebase はしない |
| 触るファイルの申告漏れで衝突 | 申告は目安であって保証ではない。衝突したら上と同じく `review` で PM が統合する |
| PM がカードを作り忘れる | **カード化は PM の規律に任せる (2026-09-24 決定)**。取りこぼしは不変条件の検査で「カードの無い作業」を拾う (PG の起動はカード ID を必須にする)。人間の発言そのものの取りこぼしは検出できない (機械化案 = PM の session の hook で発言ごとに下書きを作る、は採らなかった。取りこぼしが実際に起きたら再検討する) |
| PM を複数立てたときの採番衝突 | カード ID と issue の採番は 1 箇所に寄せる (この repo で既に 4 回衝突している。`.claude/rules/worktree-per-session.md`) |

### 論点 6: PM の数と役割 — 受付 PM + 担当 PM (2026-09-24 改訂)

レビューがボトルネックになる (PG を増やしても、PM のレビューが追いつかなければ `review` 列に溜まるだけ) ので、**PM を並列化する**。
ただし人間の窓口は 1 つに保つ。

```
人間 ⇄ 受付 PM (1 つ)  … 依頼を聞き、カードを作り、担当 PM へ振り分ける。人間が話す相手はここだけ
          ├─▶ 担当 PM A … 分解・PG への割り当て・レビュー (repo か領域ごと)
          └─▶ 担当 PM B
                 └─▶ PG 群
```

- 担当 PM どうしは直接話さない。受け渡しはカード経由にする (PM 同士の会話を調整の手段にすると、いまの困りごとが 1 段上へ移るだけ)
- **カードの担当 PM は常に 1 つ**。振り分け直すときは担当を書き換える (2 つの PM が同じカードをレビューしない)
- 採番 (カード ID・issue 番号) は受付か dispatcher の 1 箇所に寄せる (論点 5)
- 最初は受付 PM 1 つ + 担当 PM 1 つ (= 実質 PM 1 つ) で始め、review の滞留が続いたら担当 PM を足す
- 未決: 振り分けの単位 (repo / 領域 / 負荷)、担当 PM を dispatcher が自動で増やすか (PG と同じくスケーリング対象にするか)

### 論点 7: TUI

- glogx に PM / PG 画面を足す
  - **カンバン**: カードを状態の列に並べる。カードには紐づきのバッジ (要件 10) と担当を出す
  - **ゲージ**: 状態ごとの件数・最古の待ち時間・稼働中の PG 数 / 上限・dispatcher の生存
  - **詳細**: 選んだカードの依頼原文・履歴・紐づく issue の状態・ログ tail
  - **キー**: attach (下記) / btw (要件 9)
- **PG との対話は「画面を切り替える」方式にする (2026-09-24 決定)**。カードを選んで Enter → TUI を一時停止し、同じ端末で
  `claude attach <id>` を起動する (bubbletea の `tea.ExecProcess`)。抜けたら pro-con の画面に戻る。
  - 採った理由: 本物の Claude Code の画面そのものなので、権限プロンプトも含めて再現の手間が無く、Claude Code の版が上がっても崩れない。数十行で作れる
  - `claude attach` の help: 「← で agent view に戻る、Ctrl+Z でシェルに戻る。どちらでも session は動き続ける」。抜けても PG は止まらない
    (← で抜けた先は Claude Code の agent view なので、pro-con へ戻るには agent view も抜ける必要がある。戻り方は実物で確かめて案内を決める)
  - 採らなかった案: TUI の中に端末エミュレータを持って埋め込む (Claude Code の画面は truecolor・全画面の再描画・キー操作を多用し、
    `claude logs` の出力もほぼ制御コードだった。崩れやすく、版が上がるたびに壊れうる) / transcript を読む自前のチャット UI
    (権限プロンプト等を自前で再現することになる) / tmux の popup (重ねると抜けにくく使われなくなった記録が `docs/claude-fork-popup.md` にある)
  - 未確認: Claude Code 自体の agent view (`claude agents` を TTY で開く画面) と役割が重なるか。重なるなら、session の一覧と対話は agent view に任せ、
    pro-con はカード・キュー・レビュー・watchdog に絞る割り切りもありうる
- 🚨 **見た目は本体に入れる前にサンプルレンダラで決める** (`decide-layout-in-sample-renderer-first.md`)。
  カンバンは列が複数並ぶので、サンプルでも複数列・複数カードで描く
- 既存の `@claude_state` (`scripts/tmux_agent_panel.sh` / `scripts/tmux_agent_jump.sh`) は tmux pane を持つ対話 session の状態。
  `--bg` の PG は pane を持たないので、PG の状態は `claude agents` 側から読む

### 論点 8: 質問への回答を PG へどう届けるか (要件 11)

- 候補 A: PG は質問を書いて終了し、回答を足して**同じ session を `--resume` で再開**する (PG が生きたまま待たない。資源を食わない)
- 候補 B: PG は生きたまま待ち、回答を **session へ直接送る** (`attach` 相当を TUI が代行する / SendMessage)
- A は状態が単純で再起動にも強い。B は文脈を保ったまま即座に再開できる。**`--bg` で待たせたとき何が起きるかは未実測** (論点 2 の実測に含める)
- どちらでも、PG が「質問した」ことを機械で検出する口が要る (PG の最終出力を文字で推測しない。カードへ書く専用の手段を用意する)
- **二重回答を作らない**: PM と人間が同じ質問へ同時に答えられる。回答は「カードがまだ質問待ちなら書く」の 1 回の比較付き更新にし、
  負けた側には「既に回答済み」を返す (両方の回答で 2 回 resume しない)

### 論点 9: リソースの直列化 (要件 12)

- 🚨 **`lockman` をそのまま列にはできない**。`lockman --help` に「待ち行列は持たない。`--wait` を付けても公平性は保証しない」「再入不可」とある。
  順番 (FIFO) は **daemon が列として持ち**、占有の排他だけを `lockman with` に任せる形が候補
- 入口: PG が打つ Bash コマンドを PreToolUse hook で見て、宣言に一致したら `pro-con run --resource <名前> -- <元のコマンド>` に包む (または拒否して包み方を案内する)。
  宣言の書式と置き場所 (project ごとの設定ファイル) は未決
- 🚨 **hook の静的検出は迂回される** (引用符・heredoc・変数分割・スクリプト経由の間接実行・Makefile が内部で xcodebuild を呼ぶ形。
  同じ穴は `~/.claude/rules/tmux-probe-requires-socket-isolation.md` の hook 節に記録がある)。取りこぼしを減らすなら、PG の環境だけ
  **PATH 先頭に `make` / `xcodebuild` 等の shim を置いて実行時に横取りする** 方が間接実行も拾える (実体は絶対パスで解決する。
  `~/.claude/rules/path-shim-must-resolve-real-binary.md`)。どちらでも「検出しない形」を先に書いてから作る
- デッドロック: 1 つの PG が複数のリソースを同時に持つなら、取る順番を固定する (`lockman` の注意書きと同じ: 絶対パスの辞書順)
- 🚨 **占有中のコマンドが固まると、リソースは永久に返らない**。`lockman with` は子プロセスが生きている限り保持を更新し続けるので、
  TTL 切れは起きない (xcodebuild の `Reload Package` の無限待ちがまさにこの形)。したがって watchdog (論点 10) は PG だけでなく
  **リソースを握っているコマンド**も見る (ログの更新時刻・CPU)。固まったと判定したときに止める対象は、`pro-con run` が起こしたプロセスグループだけに限る。
  止める前に観測を採る (`sample` / ログの末尾。`~/.claude/rules/instrument-before-second-fix.md` の「消える操作の前に観測を採る」)。
  自動で止めるか、人間に上げて止めさせるかは未決 (破壊的な操作なので、最初は人間に上げる側から始める)
- ジョブの長さ: 実機 E2E のように長いものは、待ち時間の見積もり (前回の所要時間) を TUI に出せると良い

### 論点 10: watchdog (要件 13)

- **決定論的な監視で作る** (LLM に見張らせない)。daemon の中の 1 役にする
- 「進んだ」の判定材料 (候補): transcript の最終更新 / 最後のツール呼び出し / `claude logs` の出力の変化 / 占有リソースの子プロセスの生死と CPU
- 🚨 **活動していることは、進んでいることではない**。上の材料は活動の有無しか見ないので、**同じツール呼び出しを延々繰り返すループ**
  (完了を確かめに行って「まだ」を受け取り続ける等) は毎回 transcript が更新され、進んでいるように見える。
  「実質的な進捗」の定義も持つ: 同じツール + 同じ引数の呼び出しが N 回続く / worktree の diff とカードの履歴が一定時間変わらない、など
- 閾値は状態ごとに変える: **コマンドの実行中は「見込みの所要 (前回の実測) の 2 倍」と通常の閾値の長い方**、それ以外は通常の閾値 (2026-09-24 に決定。`card.StallThreshold`)。通常の閾値は最初は固定値で始め、実測で詰める
- 促しの届け方は論点 8 と同じ口を使う
- 🚨 **watchdog 自身が止まると、すべての停滞が無音になる**。daemon の最終 tick 時刻を TUI に出し、古ければ TUI 側が警告する (TUI を開いていないときの通知は未決)

### 論点 11: 追加オーダーを作業中の PG へどう届けるか (要件 15)

- 🚨 **実行中の session に `claude --bg --resume <session-id>` を使わない**。help に「session が実行中なら、コピーを起動してそう告げる」とあり、
  同じ worktree で PG が 2 体動く (要件 6 の競合をそのまま作る)。dispatcher は `--resume` の前に `claude agents --json` で session が
  止まっていることを確かめる (確かめから起動までのすき間に PG が動き出す窓は残るので、起動は dispatcher の 1 箇所からに限る)
- 届け方の候補: ①PG が手を止めたとき (ターンの区切り・質問待ち) に同じ session へ送る (実行中の session へ直接送れるかは未実測) /
  ②送れないなら、今のターンが終わって `idle` になるのを待ってから `--resume` する
- 方針変更は `claude stop` → 指示の差し替え → `--resume`。止める前にその時点の diff をカードに記録する (差し替えで途中の作業を失わない)

## 段階

1. **見える化だけ先に作る**。いまの使い方 (対話 session を PG に見立てる) のまま、session ごとの担当 issue・最後の発言・状態を一覧する。
   「何をしていたか忘れる」はこれだけで大半が消える
2. `claude --bg` の実測 (論点 2) と、カードの形式・不変条件の検査
3. PM を 1 つ置き、カードとキューと dispatcher (上限固定・手動起動) を入れる。**質問への回答 UI と watchdog もここで入れる**
   (PG が 1 体でも「質問に答えられない」「無限に待つ」は起きるので、スケーリングより先に要る)
4. リソースの直列化 (PG が 2 体以上になると要る)
5. 自動スケーリング (滞留と枠の残量で起動数を決める)、カンバン・btw
