# 908 (retro): dupscan の gate と除外の敵対的レビューの周回 (2026-10-25)

起票日: 2026-10-25

## 概要

dupscan の gate (905) と除外の設定 (906) を作り、敵対的レビューを gate で 6 周・除外で設計 1 周 + 実装 7 周回したセッションの振り返り。本文は反証レビューの後に入れる。

## どこで踏んだか / 回りくどかったか

(2〜4 の経緯はセッションの中の出来事で、commit と 905・906 から裏が取れるのは 3 の hash だけ)

1. **敵対的レビューの指摘を「規則を足す」で直し続け、周ごとに自分の直しが次の見逃しを作った**。
   除外の実装は 7 周回し、3〜6 周目の指摘はどれも、前の周で足した名指しの規則 (除外の下の単位を外してから選ぶ・
   除いて判定する・付け替えの条件) の穴だった。名指しは出どころの当て方 (名前・並び) に左右されるので、そこで rc を
   決める限り塞がらない。6 周目の後に「除外は、変わった単位が全部名指ししない単位のときだけ違反を消す」という
   不変条件に組み替え、乱数の入力で検査するテストを足したら、7 周目は壊せなかった (906 の進捗)。gate 本体の
   出どころの当て方も 6 周回し、4〜6 周目は下限まわりの組み合わせに寄って実データでの差がほぼ無かった (905)
2. **変異の控えをファイル名 (basename) で取り、`internal/gate/gate.go` と `internal/report/gate.go` で衝突した**。
   変異を戻すときに gate の判定のファイルを report の中身で上書きし、その周の未コミットの直しを失った (HEAD から戻して当て直した)。
   以後は「変異の前に commit し、`git checkout --` で戻す」に変えた
3. **検査の rc を見ずに push まで 1 本のコマンドで進め、lint の赤を master に入れた** (7e474df6。027d79d9 で直し、CI の緑を確かめた)。
   `make lint > log; ...; git push` の形で、検査の失敗が push を止めなかった
4. **合成の fixture の既定値が「全部同じ」で、テストの入力そのものが意図しない一致を作った** (L2・L3 のハッシュを空で揃えて
   全部の単位が L2 で組になった・base 側の名前を付け忘れて名前の段で当たらなかった)。どちらもテストが赤になってから気づいた
5. 変異を当てて緑だったので分かった死んだ分岐が 1 つ (除外の下の新しい単位はそれだけの出どころなので、除外が無ければ必ず違反)

## 次に効きそうな改善 (切り出し先の提案)

- **A. 既存の規範の発動が遅れた事例**。`_claude/rules-checklists/adversarial-review-own-safeguards.md` の §7 は既に「近似を差し替えて直した指摘が、
  次の周で同じ不変条件を別の入力で破られたら (2 周続いたら)、3 周目の修正を当てる前に 0-B へ戻る」「『同じ』は破られ方ではなく、守りたい性質で数える」と言っている。
  除外では 3 周目から規則を足し続け、組み替えたのは 6 周目だった (破られ方が周ごとに違い、別の指摘に見えた)。新しい規範は要らない。
  足すなら §7 の同じ項に「戻った後の不変条件は、乱数 (property) の検査で固定する」の 1 句だけ (今回はそれで 7 周目が壊せなかった)
- **B. 作業ツリーで複数のファイルに変異を当てるなら、控えはファイル名でなくパスで一意にする**。切り出し先: 既存の
  `_claude/rules/mutation-verify-new-tests.md` の「復元の作法」への追記 (名前の衝突は書かれていない)。同節は「`git checkout --` を常用手順にしない」と
  「指摘を直したら変異の前に commit する」も言っており、今回採った「commit してから `git checkout --` で戻す」は後者の向きで、前者と緊張する。
  追記するなら、既定は同節冒頭のとおり `bin/mutate-verify` (使い捨て worktree で変異させるので、控えも復元も要らない) と書き、手で当てるときの注意として足す
- **C. 3 は既存の `verify-execution-not-just-exit-code.md` の「成否で後段を走らせるつなぎ」の違反で、新しい規範は要らない**。
  hook (`deny-piped-push-then-destroy.sh`) は検査の出力をパイプに通したまま `&&` で commit / push へ繋ぐ形を見るもので、冒頭の「検出しない形」に
  `;` で繋いだ形を挙げている。`> log; …; git push` は止まらない — 却下: 規範は既にあり、`;` のつなぎを字句で判定すると成否で止める意図の無い形まで拾う
- **D. 4 は局所的** (この fixture の helper の作り)。その場でテストを直したので切り出さない

## 反証レビュー (2026-10-25、sonnet)

周回の数・hash・ファイルの実在は反証できなかった。A が §7 の既存項と重複していた (「§7 は収束しないときの切り替えを言っていない」は誤り) ので、発動が遅れた事例に書き直した。
B は「復元の作法」の `git checkout --` の項との緊張を書き足した。C の hook の説明 (「パイプの形しか見ない」) を実装の冒頭の記述に合わせた。
