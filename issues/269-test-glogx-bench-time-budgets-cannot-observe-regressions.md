# test: glogx の bench 時間予算が緩すぎて退行を観測できない（確保予算だけが効いている）

起票日: 2026-09-05
カテゴリ: test
優先度: 中（ゲートの実効性の問題。今の値でも false red は出ないが、真の回帰も出ない）

## 何が起きているか

`tests/glogx/bench_budgets.ci` の **時間 metric は全 12 件が CI 実測の 16〜125 倍**の上限を
持っており、桁が変わらない限り赤くならない。一方 **確保 (alloc) metric は全 11 件が 1.0〜1.1 倍**
で締まっている。つまり「確保のゲートは効いているが、時間のゲートは実質存在しない」。

実例として、issue 268 の退行（`issues_view_2000` が 1 commit で 2.8 倍）は
**Bench workflow が緑のまま通過した**。

## 全数勘定（CI run 33964922996 / job 101303286129, headSha `eb8d670e`, 2026-09-05T12:04Z）

較正器 `glogx_calib` は 0.089（基準 0.15 を下回る = 静穏 run、rel のスケールは 1 倍）。

| metric | CI 実測 (ms) | 予算 | 余裕 |
|---|---:|---:|---:|
| `view_diff` | 0.040 | 5 rel | **125.0x** |
| `view_steady` | 0.031 | 3 rel | 96.8x |
| `view_panel` | 0.033 | 3 rel | 90.9x |

中央値はおよそ **75 倍**（正確には 76.1）。最も締まっている `render_large_patch` でも 16 倍。

† `glogx_calib` は較正器で、abs 予算の役目は**ドリフト検知**であって速度予算ではない。
表には全数勘定のために載せているが、**締める対象ではない**（推奨対応 4）。

### 確保 metric

11 件すべて **1.03〜1.06 倍**（最大は `issue_scan_alloc_kb` の 1.062、最小は
`view_diff_alloc_kb` の 1.027）。
これは「絶対値 +3%」の運用（`tests/glogx/bench_budgets.ci` の確保 metric 節が根拠を持つ）どおりで、
**こちらは機能している**。

🚨 **これは対称な問題ではない**。確保側は `issues/done/051-perf-glogx-bench-gates-time-only.md`
（2026-08-14）で「時間しか見ていない」と起票され、実際に `-benchmem` を取って
`*_alloc_kb` metric を足し、**実測 +3% の上限まで締めるところまでやり切られている**。
時間側は最初から緩いまま一度も締められていない。051 で足した側だけが今も効いている、
という非対称がこの issue の中身。

## 発火条件

- 桁が変わらない性能退行（1.5〜10 倍程度）は、時間予算をすり抜ける
- **確保を伴わない退行**は特にすり抜ける。issue 268 の退行は alloc が 213 → 215 allocs
  （+0.9%）でしかなく、確保予算（余裕 1.0 倍）でも観測できなかった。時間だけが 2.8 倍
- **silent**: Bench workflow は success を返す。誰も見なければ気づかない

## 予算ファイル自身が「締めろ」と書いている

`tests/glogx/bench_budgets.ci` のコメントは 3 箇所で同じことを言っている:

- 冒頭: 「CI (ubuntu-slim) の実測がまだ無いため『桁級の回帰だけ捕まえるログ観測フェーズ』として
  緩く始める。**CI の Step Summary に実測が数 run 溜まったら、その ~4 倍を目安に締めること**」
- 体感系 (2026-07-29 追加): 「既存と同じ ~20 倍の粗い上限で導入し、**CI 実測が溜まったら
  ~4 倍を目安に締める**」
- 較正器: 「基準 0.15 は…暫定値。**CI の静穏 run 実測が出たらその値へ取り直すこと**」

CI 実測はもう溜まっている（Bench workflow は push ごとに回っている）。
issue 268 がその代償。

🚨 ただし「**締める作業だけが行われていない**」は正確ではない。推奨対応 2 のとおり、
`check_bench_budgets.sh` の `rel` は実効上限を 0.1 ms 刻みに丸めるので、
**今の実装ではフレーム系の ×4 の値を表現できない**（0.108 も 0.15 も 0.1 になる）。
書式を直さずに予算値だけ書き換えると、宣言した数字と enforce される数字が食い違う。

## 🚨 「CI 実測の ~4 倍へ締める」は 268 の退行を原理的に捕まえられない

予算ファイル自身が指定している方針だが、**そのまま当てても目的を果たさない**。
算術だけで示せる（測定不要）:

- **×N の絶対予算は、N 倍未満の退行を定義上すべて通す**
- 268 の退行は CI で 0.027 → 0.074 = **2.74 倍**。**2.74 < 4** なので、どんな基準点から
  ×4 を取っても赤くならない
- しかも上の表の値は**退行後**の実測なので、`0.074 × 4 = 0.3` は**退行そのものを新しい予算へ
  焼き込む**形になる（以後 0.074 が恒久的に「正常」になる）
- 退行**前**の値から導いても救われない: CI の 40 件が 0.027 なので退行前の 2000 件は 0.025 前後
  （推定）、×4 = 0.10 > 0.074 でやはり緑

つまり「予算ファイルが ~4 倍と書いているから ~4 倍」を無検証で継承すると、
**この issue が捕まえたい退行を捕まえられないゲート**ができる。

## 推奨対応

### 1. 主案: 「同一 run 内の比」を metric にする（この repo に既に前例がある）

件数比例を見るなら、絶対時間ではなく **2000 件 / 40 件の比**を metric にする。
**混雑に一切晒されない**（同じ run の 2 測定に同じ倍率が乗るので打ち消える）ので、
較正器のスケールも `rel` も要らない。

この repo は既にその形を運用している:

- `tests/check_bench_budgets.sh:unit_of` が `*_scale_x100` を「比は単位を持たない」として正式にサポート
- `tests/tmux/bench_budgets.ci` の `agent_panel_tick_scale_x100 400` が稼働中。直上のコメントは
  本 issue の却下欄への直接の反論になっている — 「**比なので runner の速度差・混雑が打ち消え、
  rel も不要**」
- `tests/tmux/bench_tmux.sh` が `panel_us10` / `panel_us100` から `agent_panel_tick_scale_x100` を
  出す形は、まさに「行数を 10 倍にしたときの伸び率」= 「見えない行のために働いていないか」

issues 側は**両端が既に同じ run にある**（`issues_view_frame` = 40 件 / `issues_view_2000` =
2000 件、入力 50 倍）。実測した比:

| リビジョン / 出典 | 40 件 | 2000 件 | 比 (×100) |
|---|---:|---:|---:|
| `1a1a6425`（退行前、ローカル min-of-5） | 21.78 µs | 20.32 µs | **93** |
| 062 導入時記録（`bench_budgets.ci` のコメント） | 0.022 ms | 0.024 ms | **109** |
| `edc7738f`（現 master、ローカル min-of-5） | 25.25 µs | 61.54 µs | **244** |
| CI run 33964922996（退行後） | 0.027 ms | 0.074 ms | **274** |

**`issues_view_scale_x100 150` を足せば `fc0f65ab` は赤になる。** しかも下の 2 / 3 が招く
false red のリスクを一切負わない。`status_view_*` にも同じ形が使える。

### 2. 🚨 絶対時間予算を締めるなら、同じ変更で `check_bench_budgets.sh` の書式を直す

`tests/check_bench_budgets.sh` の `rel` 判定は実効上限を **0.1 ms 刻みに丸める**:

```sh
eff=$(awk -v l="$limit" -v s="$scale" 'BEGIN { printf "%.1f", l * s }')
```

実測:

```
0.15  -> 0.1     # 「view_steady を ×4 = 0.15」が実際には 0.1 で回る (33% 厳しくなる)
0.108 -> 0.1     # issues_view_frame ×4
0.256 -> 0.3     # 逆に緩む向きにも動く
0.04  -> 0.0     # eff=0.0 は任意の正の値が超過 = 恒久赤
```

glogx のフレーム系は全部 0.027〜0.12 ms の帯にいるので、**締めると全件がこの量子化に落ちる**。
宣言した値と enforce される値が違う状態でゲートを締めるのは
`~/.claude/rules/verify-execution-not-just-exit-code.md`「予算を付けるなら、その計測が
構造的に見落とすものを先に書く」に真正面から反する。`%.1f` を `%.4g` 等へ直すこと。

これは本 issue の非対称テーゼを**強くする**: 確保 metric は `eff="$limit"` でこの行を通らない。
051 が +3% まで締められて時間側が締められなかったのは怠慢だけでなく**書式の制約**でもあり、
「締める作業だけが行われていない」は正確には「**今の実装では ×4 の値を表現できない**」。

### 3. 較正器の基準を取り直すなら、`CALIB_MAX_SCALE` も同時に見る

スケールは `check_bench_budgets.sh` が `s = 実測 / 基準; if (s < 1) s = 1` で出す。
静穏 run の実測が 0.089 なのに基準が 0.15 だと、混雑が約 1.7 倍に達するまで補正が効かない。

🚨 ただし取り直しには**逆向きの失敗**もある。`CALIB_MAX_SCALE=4` は scale > 4 のとき
rel の gating を `::warning` へ落とす（= CI 緑）:

- 基準 0.15 → 転落点は calib = 0.6 ms
- 基準 0.089 → 転落点は calib = **0.356 ms**

つまり取り直すと**より軽い混雑でゲートが丸ごと無効化される**。しかも出力が warning なので
誰も気づかない。基準を下げるなら `CALIB_MAX_SCALE` を上げて絶対の転落点を保つ
（4 → 6.7 相当）か、少なくとも転落点が下がる事実を予算ファイルに書くこと。

### 4. 一律 ×4 の対象から外すもの

- **`glogx_calib`**: 較正器の abs 予算は**ドリフト検知**であって速度予算ではない
  （`check_bench_budgets.sh` のヘッダが「較正器自身は絶対予算で別途ゲートしてドリフトを
  検知する」と定義し、較正器への `rel` は構成エラーとして拒否される）。0.089 × 4 = 0.356 に
  締めると**混雑吸収器が混雑検出器になる**。上の 3 と重なると最悪で、calib = 0.4 の run で
  「`glogx_calib` だけ赤、本物の rel ゲートは全部 warning」になる
- **`issue_scan`**: 予算ファイル自身が直上で「ファイル I/O を含み、共有 runner のディスク揺れは
  CPU 系の較正器では吸えないため **rel でも他 metric より flake しやすい**」と書いている。
  ×4 = 4.0 へ締めると false red の最有力候補。実測中央値に対する余裕で別に持たせること

### 5. 締めたことを検証する

`~/.claude/rules/mutation-verify-new-tests.md` の予算版。`fc0f65ab` をそのまま CI にかけて
`issues_view_2000`（または 1 の比 metric）が赤くなるかを見る。
🚨 **受け入れ条件は「268 の実測比 2.74 倍で赤になること」**。この数字を明記しておかないと、
次に締める人が同じ ×4 の矛盾を再生産する。

## 却下した案

- **run を跨ぐ差分でゲートする（前回 run との比較）**: 採らない。shared runner の混雑は
  乗法的に乗る（予算ファイル冒頭の実測が根拠）ので、隣接 run の差分は混雑ノイズに埋もれる
  - 🚨 **「同一 run 内の比」はこれとは別物**で、混雑が打ち消えるので有効。推奨対応 1 がそれ
    （初版はこの 2 つを同一視して比ごと却下していた。敵対レビューの指摘で訂正）
- **時間予算を全部やめて確保予算だけにする**: 採らない。268 の退行は B/op が +0.36%
  （予算の余裕 +4.4%）でしかなく、確保予算では構造的に見えない。時間の退行は時間でしか観測できない
