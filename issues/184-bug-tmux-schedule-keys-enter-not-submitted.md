# 184 bug: 入力予約の発火で Enter が効かず、文字列が入力欄に残ることがある

起票日: 2026-09-02
関連: `scripts/tmux_schedule_keys.sh` (`fire_send`) / `src/schedkeys/` (ウィザード TUI) /
`_tmux.conf` の `bind m` / issue 166 (予約の pane 表示) / issue 135 (tmux key guide の human 確認)

## 症状 (ユーザー報告 2026-09-02)

prefix+m の入力予約を使ったところ、**発火時に Enter が押されず、予約した文字列が送り先 pane の
入力欄に入ったまま残っていた**ことがある。毎回ではなく「〜の時があった」= 間欠。
やりたいことは「確実に submit / Enter される」こと。

⚠️ **再現条件・発生時の送り先アプリ・件数は未確定** (報告時点で判明していない)。

## 現状の実装 (実測 2026-09-02, コード確認)

`scripts/tmux_schedule_keys.sh:388` — 本文と Enter は **1 回の tmux 呼び出し** (コマンドリスト) で送る:

```sh
tmux send-keys -t "$REPLY_PANE" -l -- "$send_text" ';' send-keys -t "$REPLY_PANE" Enter 2>/dev/null
```

- この形は 2026-08-28 に「2 回に分けると同時刻の別予約が割り込んで 1 行に連結される」事故を
  受けて導入されたもので、コメントは「分けないことで『本文は送れたが Enter が失敗』も構造的に
  消える」と書いている。**今回の症状はこの主張と食い違う**ので、まずそこを疑う
- 直前に `pane_in_mode` なら `send-keys -X cancel` で mode を抜ける (`:372-375`)
- 送信の成否は `send-keys` の rc だけで判定し、成功時は `log "fire $id: sent to ..."` を書いて
  toast を出す。**「送った」と「受け側が submit した」は区別していない**

## まず観測する (修正案を書く前に)

`instrument-before-second-fix.md` / `verify-execution-not-just-exit-code.md` に従い、
仮説から入らず「何が見えていないか」を先に埋める。

1. **ログを読む**: `~/.cache/tt-schedule-keys.log`。症状が出た回に
   `sent to %N` が出ているか (= tmux は rc=0 を返していたのか)、それとも `送れず破棄` か。
   ここで分岐が変わる:
   - `sent` が出ている → tmux は両方送っている。**受け側 (アプリ) が Enter を食っている**
   - `破棄` が出ている → コマンドリスト全体が失敗。本文だけ届いて Enter が落ちる経路がある
2. **rc の粒度**: 上の 1 呼び出しはコマンドリストなので、**前半が成功し後半が失敗したときの rc が
   どうなるか**を隔離 tmux サーバ (`-L`) で実測する (`tmux-probe-requires-socket-isolation.md`:
   破壊的コマンドの前に隔離を実証する)。前半成功 + 後半失敗が rc=0 になるなら、
   ログの `sent` は Enter の到達を何も保証していない
3. **送り先アプリごとに分ける**: 素の zsh プロンプト / Claude Code の TUI / vim など、
   受け側で挙動が変わるかを隔離サーバで A-B する。
   「たまに動く」はタイミングではなく**分類 (送り先の種類)** で説明できることが多い
4. **リテラル送信と Enter の間隔**: TUI (Ink / bubbletea 等) は入力をデバウンスしたり、
   短時間に届いたバイト列をペーストとして扱って改行を「入力欄の改行」に変えることがある。
   `send-keys -l` に続く `Enter` が同一 flush で届く形が受け側でどう解釈されるかを実測する

## 直し方の候補 (観測後に選ぶ。今は決め打ちしない)

- **A. 送達確認して再送**: 送信後に `#{pane_current_command}` / `#{cursor_y}` 等で
  「入力欄が空になったか」を見て、残っていたら Enter を再送する。⚠️ 冪等性が要る
  (二重 submit は破壊的になりうる)
- **B. Enter を別呼び出しに戻し、割り込みは別の手段で塞ぐ**: 2026-08-28 の連結事故は
  「同時刻の 2 予約」が原因なので、発火の直列化 (ロック) で塞げるなら分割に戻せる
- **C. 受け側に合わせたキー送出**: 送り先が特定 TUI のときだけ `C-m` / 二段 Enter 等へ切り替える。
  ⚠️ アプリ判定が増えるので最後の手段
