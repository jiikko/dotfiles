# 184 bug: 入力予約の発火で Enter が効かず、文字列が入力欄に残ることがある

起票日: 2026-09-02
関連: `scripts/tmux_schedule_keys.sh` (`fire_send`) / `src/schedkeys/` (ウィザード TUI) /
`_tmux.conf` の `bind m` / issue 166 (予約の pane 表示) / issue 135 (tmux key guide の human 確認)

## 症状 (ユーザー報告 2026-09-02)

prefix+m の入力予約を使ったところ、**発火時に Enter が押されず、予約した文字列が送り先 pane の
入力欄に入ったまま残っていた**ことがある。毎回ではなく「〜の時があった」= 間欠。
追加情報: **入力に改行コードが含まれていたときに起きていた気がする** (ユーザーの記憶)。

## 調査 (2026-09-02、隔離 tmux サーバ `-L` で実測)

### 1. 過去の発火記録は残っていない — ログからは追えない

- `~/.cache/tt-schedule-keys.log` は**存在しない** (`XDG_CACHE_HOME` は未設定なので既定パス)
- job ディレクトリ `~/.local/state/tmux-schedule-keys/` は**空** (作成 2026-08-28 13:56)

つまり「症状が出た回に `sent` が出ていたか」は確認不能。ログが 1 行も無いのは、
`log()` が呼ばれる経路 (予約作成・発火・取消) を**このマシンで通っていない**ことを意味する。

### 2. A 形式 (現行実装) は受け側に 1 chunk で届く — 機構の差は実在した

`fire_send` (`:388`) は本文と Enter を 1 回の tmux コマンドリストで送る。受け側で `read()` の
chunk 境界を記録する probe を pane に置いて測った:

| 送り方 | 受け側が受け取る chunk |
|---|---|
| **A = 現行実装** (`send-keys -l -- "$text" ';' send-keys Enter`) | `b'HELLO-A\r'` を **1 chunk (len=8)** |
| B = 2 回に分けた呼び出し | `b'HELLO-B'` (len=7) と `b'\r'` (len=1) の **2 chunk** |

TUI には「1 read chunk に複数バイト + 改行」をペーストとみなし、改行を submit に使わない実装が
あるので、これは症状を説明しうる機構。**ただし下記 3 のとおり、手元の受け側 3 種では再現しなかった**。

### 3. 受け側 3 種で再現せず (A 形式・改行入りも含む)

| 受け側 | 結果 |
|---|---|
| 素の zsh プロンプト | A 形式で **submit された** (`echo SUBMITTED_A` が実行された) |
| bubbletea TUI (`bin/schedkeys`) | A 形式・B 形式とも **Enter が効いた** (次の画面へ進む) |
| **Claude Code (Ink 系)** | 改行入り `AAA\nBBB` を A 形式で送っても **submit された**。LF は捨てられ `AAABBB` として送信 |

### 4. rc の粒度: `sent` ログが保証するのは「tmux が送ったこと」だけ

コマンドリストの前半・後半のどちらが失敗しても `rc=1` (存在しない pane を混ぜて実測)。
したがって rc=0 は**両方の send-keys が成功したこと**を保証する。一方で
**受け側が submit したかは保証しない** — ここはログの語彙 (`sent`) が実態より強い。

### 5. 改行入りテキストは、今の UI では job に入らない (2026-08-28 以降)

- `src/schedkeys/editor.go:201 acceptable()` が制御文字 (LF 含む) を弾く。導入は `7695eeae` (2026-08-28)
- 貼り付け経路 `form.go:96 paste()` も `acceptable` を通す。導入は `1909c221` (2026-08-28)
- `main.go:101 formatResult()` が `\t` `\n` `\r` を空白へ置換

**ユーザーが遭遇したのはこれらの防御が入る前の版だった可能性が高い**。
現行版で同じ入力を作る経路は、UI からは無い。

### 6. ただし job ファイルの構造的な脆さは残っている (実測)

job は 5 行の行区切りで、文字列は 3 行目 (`:208` の `printf` / `:111` の `read -r`)。
同じ書式で改行入りテキストを書いて読み出すと**フィールドが 1 つずつずれる**:

```
text='AAA\nBBB' → TEXT=AAA  SOCK=BBB  SRVPID=/tmp/tmux-501/default
                  srvpid ガード: 不一致 → fail-closed で送らない
```

つまり改行が job に入った場合の症状は「**何も送られない**」であって、
「文字列だけ届いて Enter が効かない」ではない。UI 以外から job を書く経路 (手書き・将来の別 UI) が
できたときに、**無言で予約が消える**形になる。

## 現時点の結論

- **報告された症状は、現行コード + 手元の受け側 3 種では再現しなかった**
- 改行入りが原因だったなら、**2026-08-28 の UI 側の防御 (5) で既に塞がっている**可能性が高い
- A 形式が 1 chunk で届く事実 (2) は残っており、**まだ試していない受け側 (他の Ink/TUI アプリ、
  別バージョンの Claude Code) では再現しうる**。「壊せなかった」であって「正しい」ではない

## 却下・保留した対応 (次の調査が同じ道を通らないため)

- **A 形式を B 形式 (2 回送信) へ戻す**: 保留。1 コマンドリスト化は 2026-08-28 に
  「同時刻の予約 2 件が 1 行に連結される」実害を塞ぐために入れたもの (`:381-385`)。
  再現しない症状のために、実害が確認済みの防御を外さない
  (`list-masked-failure-modes-before-removing-guard.md`)
- **送達確認して Enter を再送**: 保留。二重 submit は破壊的になりうるうえ、
  再現していない症状に対する推測の防御コードになる
