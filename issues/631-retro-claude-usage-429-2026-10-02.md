# 631 (retro): Claude の利用枠が 429 で取れなくなった件 (627) の振り返り

起票日: 2026-10-02

対象: issue 627 (done)。glogx が `claude -p /usage` を 1 分ごとに起こして `/api/oauth/usage` が 429 になり、
最終的に利用枠の出所を statusline の `rate_limits` に切り替えた。

## どこで踏んだか / 何が回りくどかったか

1. **動いている入口と比べる前に、壊れている入口だけで設計した**。対話の `/usage` は 429 の間も見えていたのに、
   「`/usage` = `/api/oauth/usage` を叩く」と決めて共有ゲート (5 分の間引き・停止) を作り込んだ。
   ユーザーの「このセッションの /usage は見えている」で初めて、対話側は応答ヘッダの値で答えていると分かり、
   出所そのものを変えることになった。ゲートの 3 周分のレビューの大半は、この前提の上に積んだもの
2. **外部 CLI のログ 1 行の意味を、コードを読まずに解釈した**。「429 remembered for this bearer; not asking again for Ns」を
   「CLI が覚えている間はサーバへ行かない」と読み、止める時間を 10 分にした。実際は覚えがプロセスをまたがず、
   `claude -p` を起こすたびに叩いていたので、10 分ごとに 429 の窓を延ばしていた。ユーザーの「本当に？キャッシュか？」で
   CLI のコードを読んで訂正した
3. **「観測した時刻」として書き手の書いた時刻を使い、書き手が新しい値なしでも書くことを確かめなかった**。statusline の
   `refreshInterval` (60 秒) の再描画で、古い値が「今の観測」として書き直され続ける形を、ユーザーの指摘と 2 本のレビューで知った
4. **並行セッションが同じ API を作り替えていた** (626: `FetchAll` を消して出所ごとの取得へ)。push の直前に rebase で衝突し、
   載せ直しとテストの書き直しが 1 回増えた。着手時の `ListAgents` には dotfiles のセッションが見えなかった
5. 変異検証で、テストの入力が分岐を見分けない形が 2 回見つかった (もう片方の窓も空 / 既存のファイルが無い)。仕組みは働いた

## 次に効きそうな改善 (一般形)

- **A. 同じ機能に「動いている入口」と「壊れている入口」があるなら、設計の前に 2 つの経路の差を確かめる**
  (同じ CLI の対話と `-p`、同じ API の別クライアント等)。差が分かる前に壊れている側の防御を作り込まない。
  - 切り出し先: 既存 `_claude/rules/check-other-platform-reference.md` へ追記 (「別 platform」だけでなく「同じ道具の別の入口」も
    参照実装に数える)。発動点は既存ルールと同じ (調査開始の最初の 5 分)
- **B. 外部の道具のログ・メッセージの意味を設計の前提にするなら、それを出しているコードか実験で確かめる**
  (「remembered」「cached」「skipped」のような語は、どの範囲で・いつまで効くかを語らない)。
  - 切り出し先: 既存 `_claude/rules/measure-external-cli-streams-separately.md` の「外部ソースは仮説」の項へ追記
    (ログ 1 行の解釈も仮説に数える)
- **C. 周期的に外部のサービスを叩く処理を足すときは、サーバ側の rate limit を前提に、全プロセスの合計の頻度を 1 か所で持つ**。
  ローカルのコスト (トークン・CPU) が小さいことは、サーバが許す頻度について何も言わない (glogx の 1 分周期は
  「トークン課金ゼロ」を根拠にしていた)。
  - 切り出し先: 新規の rule は立てず、既存 `_claude/rules/measure-external-cli-streams-separately.md` へ 1 項追記を提案
    (外部 CLI を周期的に起こす場面が発動点として近い)
- 却下: 「観測時刻は書き手が新しい値なしでも書いていないか確かめる」(3) — 既存 `mutation-verify-new-tests.md` の
  「逆向きの問い: その観測値が進んだのに、目的が達成されていない状態を作れるか」(十分性) がそのまま当たる。追記ではなく
  適用漏れなので、ルールは増やさない
- 却下: 並行セッションとの衝突 (4) — 着手時に見えるセッションへの申告は既存ルールどおり行っており、相手は見えていなかった。
  rebase で吸収できた局所的な出来事
- 却下: テストの入力が分岐を見分けない (5) — 既存 `mutation-verify-new-tests.md` の「差が出ない状況しか作っていないか」で
  検出できた (変異が働いた)
