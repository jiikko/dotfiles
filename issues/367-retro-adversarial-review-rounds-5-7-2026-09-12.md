# retro: issue 358 の敵対的レビュー 5〜7 周目 (2026-09-12)

起票日: 2026-09-12
カテゴリ: retro / 対象セッション: dotfiles-c9
対象 issue: [358](done/358-refactor-lockman-cleanup-selftoken-is-production-unreachable.md)（done）

## 何をしたか

358 の残タスク「敵対的レビュー 5 周目の要否がユーザー判断待ち」をユーザー指示で消化した。
5 周目を ①壊す ②素通り ③並行・中断 の 3 観点に分けて opus を直列に回し、
6 周目は「5 周目の差分だけ」、7 周目は「6 周目の差分だけ」に絞って各 1 体。
production 3 commit + テスト 2 commit、新規 issue 5 本（362 / 363 / 364 / 366 と本 retro）。
7 周目で初めて「直前の周が新設したものが 1 つも崩れない」状態になり閉じた。

## 気づき

### 1. 守る対象の列挙そのものが、最初の攻撃面だった

5 周目に入る前に §8 の stopping rule（脅威モデル / 検出しないと決めた形 / 打ち切りの判定）を
本文へ固定した。**その表から「掃除が lock 本体を消す」が落ちていた**。
落ちた結果、`cleanup.go` の最も強い 🚨 を守っていたのがコメントだけという状態が残り、
観点①がそこを突いて P1 を出した（`sweepDir("")` を 1 行足すと全 33 テスト緑で二重取得まで到達）。

脅威モデルを書くこと自体は正しかったが、**書いた表の網羅性を誰も検査していない**。
「守る対象を 1 つ落とす」は、機構を 1 つ落とすのと同じ効果を持つ。

- 切り出し先候補: [`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md)
  §8（脅威モデルを書く節）へ「**列挙した守る対象に、コード内の 🚨 / 「絶対に」と書かれた
  不変条件が全部入っているか照合する**」を 1 行足す。新規ルールは立てない（発動点が同じ）

### 2. 観測チャネルを広げると、正常系の偽陽性チャネルにもなる

3 周目が「失敗したら打刻しない + verbose 非依存で stderr」という観測チャネルを作った。
5 周目はそこへ「打刻そのものの失敗」を足した。6 周目が実測したのは、
**`.cleanup_at` が umask に削られた 0644 のままなので、共有では別ユーザーの打刻が恒久 EACCES**
になり、その警告が**正常系で鳴り続ける**こと。

これは **4 周目 P2-1（良性 ENOENT を失敗に数えて正常系で鳴っていた）と同型**で、
4 周目に自分で直した形を、5 周目に別の入口から再生産した。

- 気づきの核: 「見えるようにする」修正は、**その失敗が正常系で起きうるかを同じ commit で問う**
  必要がある。可視化は片側だけでは完成しない（鳴らす条件と鳴らさない条件の両方が要る）
- 切り出し先候補: [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
  の「沈黙 = 成功」節へ、**逆向き（可視化が偽陽性を作る）**を 1 行足す。
  新規ルールは立てない（発動点は同じ「沈黙を潰すとき」）

### 3. 教義を援用しておきながら、当の定数を pin していなかった

6 周目で `TestScratchDirNamesAreDirectChildren`（3 定数のリテラル pin）を足したが、
7 周目が「その修正が依存している `lockFileMode` / `metaDirMode` は未 pin」を出した。
実測で両方とも縮める変異が**全 42 ケース緑**。

- 気づきの核: 「リテラル pin する」と決めたら、**その判断が依存している定数を同時に数え上げる**。
  1 つ pin して満足する形は、`mutation-verify-new-tests.md` の
  「同じ変更の中に shim が複数あるとき片方だけ直して満足する」と同族
- 切り出し先候補: 既存ルールへの追記で足りる（上と同じく発動点が同じ）。**却下でもよい**
  — 3 例とも「同じ変更の中で母集合を数え直す」に還元でき、それは既にいくつかのルールが言っている

### 4. 事前の合意は、採番の証明にならない（361 の姉妹形）

起票前に並行セッションへ「362 / 363 / 364 を予約した。新規は 365 以降を」と伝え、
相手からも「365 以降を使い、その時点で改めて連絡します」と返答があった。
それでも **365 で衝突した** — 相手が 365 を取ったときに連絡が無く、採番から push までの
数分、こちらからは 365 が空いて見えていた。

[361](361-retro-claim-visibility-and-attribution-2026-09-11.md) の
「**解放の連絡は取得の証明にならない**」と同じ構造で、向きが逆
（あちらは「空けた」の連絡、こちらは「これから取る」の合意）。
どちらも **push されるまでは誰の物でもない**。相手も同じ結論を自分から述べている。

- 切り出し先候補: [`claim-issue-in-next-and-push.md`](../_claude/rules/claim-issue-in-next-and-push.md)
  の「🚨 fetch は着手を決めた直前にもう一度打つ」の並びへ、
  **「採番も同じ。予約の合意があっても、採番の直前に `git fetch` して最大番号を取り直す」**を 1 行。
  361 の残課題とまとめて扱うのが自然

### 5. サブエージェントの観点分けは効いた（記録）

3 観点を分けた結果、**片方にしか出ない指摘**が実際に出た:
①の `sub` 軸（②③には出ず）、②の偽の検証記録 4 件（①③には出ず）、③の 362 / 363（①②には出ず）。
一方 `serverNow` の非対称は **3 体が独立に**出した。
`adversarial-review-own-safeguards.md` §5 の「観点を分けると注意が薄まらない」を追認する実測。
切り出しは不要（ルールは既にある）。
