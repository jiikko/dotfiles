# 295 retro: epic 配下の done を既定表示にする (291) の振り返り

起票日: 2026-09-06

対象セッション: issue 291 の起票 → 実装 → 敵対的レビュー 2 周 → 294 の分離まで。

## 1. 変異検証の復元で、自分が入れたレビュー修正を消した

敵対レビュー P2-1 を `move.go` で直し、**commit する前に**その修正へ変異を当てた。変異を戻すのに
`git checkout -- src/glogx/issues/move.go` を打ったので、**変異と一緒に修正も消えた**（テストが
red のままだったので即座に気づき、再適用した）。

`_claude/rules/mutation-verify-new-tests.md` の「復元の作法」は、この形を発動点まで名指しで
書いている（「発動点は**レビュー指摘を直した直後**。直後は必ず未コミットで、そこで変異を回すと
復元のたびに変異でなく**修正の方**が捨てられる。指摘を直したら**変異の前に commit する**」）。
**読んでいるルールを、読んでいる状況で踏んだ**のが本質で、規範の不足ではない。

- 切り出し先の提案: **新規 issue（機械化）**。`git checkout --` / `git restore` を、対象パスに
  未コミットの変更がある状態で打とうとしたときに PreToolUse hook で警告する。規範は既にあり、
  それでも踏むなら止められるのは hook だけ（`deny-bare-tmux-kill.sh` と同じ立て付け）。
  🚨 ただし「未コミットを消す」のは正当な用途（変異の復元そのもの）でもあるので、deny ではなく
  **注意の注入**にする設計が要る。ここを詰めずに deny にすると変異検証が回らなくなる

## 2. 契約を変えたとき、「宣言」は全部寄せたのに「手順」を寄せ忘れた

group issue の完了先を `issues/done/` → `issues/epic/<name>/done/` に変えたとき、
spec・`issues/README.md`・rules・CLAUDE.md・hook のコメントは同じ変更で直したが、
**`_claude/skills/issue-sync/SKILL.md` の Step 6-1（実際に `git mv` する手順）が旧契約のまま**
だった。敵対レビュー 1 周目の P1。

漏れた理由がはっきりしている: **`grep "完了は global"` のような文言で探した**が、skill の手順は
「issue ファイルを `issues/done/` に移動する（`git mv`）」と書いてあって、その文言に当たらない。
宣言（何が正しいか）と手順（どう動かすか）は語彙が違う。

- 切り出し先の提案: **`_claude/rules/claude-md-maintenance.md` の「適用タイミング」表への追記**。
  同表には既に「ディレクトリ階層・置き場所の契約を変えた」行があり、そこは**深さ前提の検査**を
  grep しろと言っている。ここに「**その置き場所へ実際にファイルを動かす手順書**（skill / hook /
  スクリプト）も同じ変更で直す。探すのは文言ではなく `git mv` / `mv` / `os.Rename` などの**動作**」を
  足す。新規ルールは立てない（発動点は同じ「置き場所の契約を変えた」）

## 3. 敵対レビューへ渡す観点に「書き側」を入れていなかった

1 周目に渡した観点は 6 つとも**読み側**（走査・表示・フィルタ・監視・テスト）で、
「この契約に従って**ファイルを動かす**のは誰か」を渡していなかった。P1 はレビュワーが観点の外から
拾ってくれた形。項目 2 と同じ穴を、レビューの依頼文でも開けていた。

- 切り出し先の提案: 項目 2 の追記に含める（依頼文のテンプレを別に持つほどではない）。却下でもよい

## 4. false positive の issue を起票しかけた

「done な子に `n` を押すと dangling な目印ができて CI が落ちる」を issue 294 として書いた。
`git add` の直後に裏取りしたら **`MoveToSubdir` は直下に居る issue にだけ symlink を置き、
`done/` に居るものは rename で運ぶ**（`isOpenPlacement`）ので、症状ごと成立しなかった。取り下げて
番号を空きへ戻した。

書く前に該当関数を読めば 1 分で分かった。規範（CLAUDE.md「issue の記述を鵜呑みにしない」/
`issue-creation-codex-review.md`）は既にあり、**実行の問題**。

- 切り出し先の提案: **却下**（新しい規範を足しても、同じ規範を守らなかっただけの再発になる）。
  ただし「壊れる」と書くときは**その壊れ方を作るコードを読んだか**を自問する、という 1 行が
  項目 2 の追記に紛れ込ませられるなら足す程度

## 5. 「空きへ戻した」と伝えた番号を、自分で取った

false positive の issue を取り下げたとき、並行セッションへ「295 は取らずに空きへ戻した」と伝え、
その 30 分後に**同じ 295 を retro で取った**。相手は 295 で起票して push が non-fast-forward で
弾かれ、296 へ振り直す手間を払った（実害は無い。弾かれたので上書きは起きていない）。

「空きへ戻す」は宣言だが、**取るのは push で確定する**。宣言と確定の順序が逆転すると、
相手は宣言を信じたぶんだけ損をする。`claim-issue-in-next-and-push.md` の「claim は push されて
初めて claim になる」と同じ構造で、**解放の側にも同じ非対称がある**（解放は宣言した瞬間に効くが、
再取得も宣言では効かない）。

- 切り出し先の提案: **`_claude/rules/claim-issue-in-next-and-push.md` への 1 行追記**。
  「番号や issue を『空きへ戻す』と他セッションへ伝えたら、**自分が取り直すときも fetch して
  取り直しを宣言する**（解放を信じた相手が先に取っている可能性がある）」。新規ルールは立てない
  （発動点は同じ「番号の採番と claim」）
