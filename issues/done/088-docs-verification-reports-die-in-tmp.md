# 088 docs: 検証レポートを `./tmp` に出すと消える (結論を issue へ移す工程が規約に無い)

起票日: 2026-08-21
種別: docs
優先度: **P2** (今日 1 回、72 指摘の裏取り結果が消える寸前だった)

## 何が起きたか (2026-08-21 の実例)

その日の作業で、ad-hoc に組んだ Workflow が大きな検証レポートを 3 本出した:

- `./tmp/audit-triage.md` — 監査 070/071/072 の **72 指摘の裏取り + 敵対的反証** (39 エージェント)。
  全数勘定・却下理由・着手順・衝突注意が入っていた
- `./tmp/audit-refute2.md` — 未反証 medium 9 件の反証 (生存 5 / 却下 4、崩れた理由つき)
- `./tmp/collab-review.md` — 協業 17 commit の破壊チェック (5 観点 + 孤児回収への敵対攻撃)

**`tmp/` は `~/.gitignore_global:5` で ignore されている**ため、この 3 本は commit されない =
セッションが終われば消える。気づいたので手作業で要点を issue へ移した
(`7a36b55` = 070/071/072 の「反証・対応の結果」節 / `076` / `077`)。
**気づかなければ、72 指摘の verdict と却下理由が丸ごと失われていた。**

## 構造的な原因 (誰か 1 人の不注意ではない)

1. `~/.claude/CLAUDE.md`「一時ファイルの配置」が **`/tmp` 禁止・`./tmp` を使う**と定めている
   (正しい規約)。結果、成果物は自然と gitignore された場所に落ちる
2. **却下理由は「消えると同じ誤指摘が再生成される」性質の情報**。次の audit は同じコードを見て
   同じ指摘を出すので、「なぜ却下したか」が残っていないと反証コストを丸ごと再支払いする
3. `audit` skill 自体は課題を `issues/` へ書き出す作りになっている (description に明記) ので、
   **skill 経由なら問題ない**。穴があるのは「skill を使わず自分で組んだ検証パイプライン」の側

## 対応方針

`~/.claude/CLAUDE.md` か `_claude/rules/` に 1 項足す。文面の骨:

> 検証・監査・レビューのレポートを `./tmp` に出したら、**結論・全数勘定・却下理由を issue
> (または対象コードのコメント) へ移すまでが 1 セット**。`tmp/` は gitignore なのでレポート本体は
> 消える。特に「却下した指摘とその理由」は、残さないと次の audit が同じ指摘を再生成する。

置き場所の候補と判断:

- `_claude/rules/` に新規 1 ファイル (例 `move-report-conclusions-to-issues.md`) — 独立した規律
  なので単独ファイルが素直。CLAUDE.md からは既存の「Issue管理」節から 1 行リンクする
- あるいは `issue-creation-codex-review.md` に併記 — あちらは「issue を作ったら codex に通す」で
  トリガが違うので、混ぜると両方の発火条件がぼやける (**分ける方を推す**)

## 却下も検討したこと (記録)

「レポートを `docs/` に置いて commit する」案は採らない。レポートは**その時点のスナップショット**で
あり、コードが動けば嘘になる (`claude-md-maintenance.md` の「What はコードが真の出典」と同型)。
残すべきは結論と判断理由だけで、それは issue とコードコメントの担当。
