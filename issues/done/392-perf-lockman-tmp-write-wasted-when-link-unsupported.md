# `link(2)` が使えない FS では、`tryPlace` の tmp 書き込み (fsync 込み) が丸ごと捨てられる

起票日: 2026-09-18
カテゴリ: perf / priority: **low** (2026-09-18 に medium から下げた。下の「訂正」節)
対象: `src/lockman/lock.go` の `tryPlace`
出典: [issue 391](391-bug-lockman-os-exit-skips-defer-leaves-scratch.md) の調査中に発見
反証レビュー: 実施済み (2026-09-18)。**前提と数値が訂正されている。下の「訂正」節を先に読むこと**

## 問題

`tryPlace` は必ず `writeFileSync(tmp, b)` (**fsync 込み**) してから `link(2)` を試すが、
**fallback 枝 (O_EXCL) は tmp を 1 バイトも読まない** — lock のパスを直接開いて
同じバイト列を書く。つまり `link` が失敗する FS では、fsync 付きの書き込みが 1 回分
丸ごと捨てられる (その後 `defer` で unlink もする)。

`lock.go` 自身が「macOS の smbfs では ENOTSUP になりうるので O_EXCL に落とす」と
書いており、**それが本番の経路**。

## 実測 (2026-09-18、ローカル APFS)

`tryPlaceLinkFn` を `syscall.ENOTSUP` 固定にしたビルドで、acquire の所要時間 (中央値、80 試行):

| 版 | 中央値 |
|---|---|
| 現行 (tmp を必ず書く) | 32.3ms |
| 計測専用 (tmp を書かない) | **24.0ms (-26%)** |

参考: `link` が使える枝の現行は 28.4ms。

🚨 **これは節約の上限であって、実装の効果ではない。** 計測版は「link を使わないと
分かっている」前提で tmp を省いただけで、**そのままでは実装にならない** (link の可否は
試すまで分からない)。

🚨 **SMB では未実測**。fsync が往復になるので差は開くはずだが、数字は無い。
`perf-claims-need-measurement.md` に従い、**「SMB で速くなる」とは書かない**。

## なぜ今の形になっているか (壊す前に確認したこと)

`link(2)` 経由だと lock は「最初から中身が入った状態」で現れる = **途中経過が他者に
見えない**。O_EXCL 枝はこの性質を持てず、そのぶん issue 383 が
「中身を書けなかった lock を消す」後始末 (`cleanupOwn`) を足している。
**tmp は link 枝の正しさのために要る**ので、単純に消すことはできない。

## 対応の候補 (未決。着手前に再評価すること)

- **何もしない**。26% は「起動時間込みの中央値」に対する比で、絶対値は約 8ms。
  `lockman` は 1 ファイル 1 回の呼び出しなので、体感に出るかは不明
- **link の可否を 1 度だけ判定して覚える**。判定自体が I/O で、どこに覚えるか
  (プロセス内 / dir 内のマーカー) で意味が変わる。**dir 内に持つと新しい状態が増える** ので、
  `adversarial-review-own-safeguards.md` §0-A の対象
- **link を先に試してから tmp を書く**。`link` の材料が無いと試せないので、
  「0 バイトの tmp で link を試す → 使えたら書き直す」等の形になり、
  **中身の無い lock が見える窓**を作る (383 が潰した failure mode の再導入)。おそらく不可

## 2026-09-18 反証レビューによる訂正 (この issue の前提が 2 つ崩れた)

| 当初の主張 | 判定 | 正しくは |
|---|---|---|
| 「`link` が ENOTSUP になる FS (**smbfs = 本番の経路**)」 | **二重に誤り** | ① smbfs が ENOTSUP を返すかは**一度も測られていない**。[091](091-feat-lockman-directory-lease-lock.md) の表は「ENOTSUP の**可能性が高い**」という予想のままで、実測担当の [092](092-human-verify-lockman-over-smb.md) は**測らずに** done へ送られている (「SMB 越しの lockman は当分使わない」というユーザー判断)。`lock.go` の原文も「ENOTSUP に**なりうる**」と正しくヘッジしていた ② **現在の実運用は SMB ではない**。`zshlib/_av1ify_lock.zsh` はロックを `~/.lockman/av1c/<key>/` = ローカル HOME に置き、同ファイルが「これは同一マシン内の排他になる」と明記している。そこでは `link` が成功するので**この無駄は発生していない** |
| 「現行 32.3ms → 24.0ms (-26%)」 | **絶対値が誤り** | 計測ハーネスが 1 反復あたり `python3` を 2 回起動しており、**2 回目の起動 (約 20ms) が測定値に混入**していた。Go の起動は実測 **2.6ms** (20ms ではない) |
| 「26% は起動時間込みの中央値に対する比で、絶対値は約 8ms」 | **誤り** | 分母の説明も絶対値も外している |

### 測り直した値 (1 プロセスの中で計測。起動の混入なし。80 試行の中央値)

| 版 | 中央値 |
|---|---|
| 現行 (tmp を書く / link=ENOTSUP) | 13.9ms |
| 計測専用 (tmp を書かない) | **9.7ms (-30%)** |
| 参考: link が使える枝 (現行) | 9.1ms |

差は **約 4.2ms**。link が使える枝 (9.1ms) と tmp を省いた ENOTSUP 枝 (9.7ms) がほぼ同じで、
**ENOTSUP 枝は fsync 付きの書き込みを 2 回払っている**ことが数字にも出ている。

### priority を medium → low へ下げた理由

**この無駄が発生する経路が、現在は存在しない。** 発生するのは
「`link` が使えない FS に lock dir を置く」ときだけで、それは 092 の判断で当分来ない。

**再開の trigger (差し替え)**: SMB (または link が使えない FS) 上で lockman を使う判断が
戻ったとき。**その時点でまず 091 の表の「link(2) が使えるか」を実測すること** —
この issue の前提そのものが、その 1 回の実測で決まる。

## 2026-09-18 前提の実測 (SMB は用意できないが、**link が使えない実在の FS** で測った)

反証レビューが「前提が測られていない」と指摘した点を、**seam の偽装ではなく本物の FS** で
確かめた。SMB 共有は用意できないので、`hdiutil` で作った ExFAT / FAT32 を使った
(どちらも `link(2)` を持たない実在の FS)。

### ① `link(2)` は実在の FS で ENOTSUP を返す

| FS | `link(2)` | mtime の粒度 |
|---|---|---|
| APFS (この repo の置き場) | **成功** | — |
| **ExFAT** | **失敗 errno=45 ENOTSUP** | 0.05s |
| **MS-DOS FAT32** | **失敗 errno=45 ENOTSUP** | **2.0s** |

→ 「link が使えない FS では ENOTSUP」は**実在の FS で成立する**。
🚨 **smbfs がそうだとは、これでも言えない** (091 の表の空欄は埋まっていない)。
言えるのは「ENOTSUP という失敗の形は実在し、その FS で lockman は動く」まで。

### ② lockman は ExFAT (本物の ENOTSUP) で正常に動く

`acquire` rc=0 → `status` が `held by ...` → `release` rc=0。
O_EXCL の fallback 枝が本番相当の条件で機能することの確認でもある。

### ③ 無駄の実測 (本物の ENOTSUP。60 試行)

| FS | 現行 (tmp を書く) | 計測専用 (tmp を書かない) | 差 |
|---|---|---|---|
| **ExFAT** | 27.29ms (p90 36.31) | **18.74ms (p90 23.82)** | **-8.55ms / -31%** |
| APFS (link 成功) | 8.97ms | 8.90ms | **差なし** |

APFS で差が出ないのは当然で、そこでは tmp は**使われている**。
**無駄は link が使えない FS でだけ発生し、そこでは acquire の 3 割**。
(前回の「-30%」は seam で ENOTSUP を偽装した数字だった。**本物の FS でも同じ比**になった)

## 2026-09-18 §0-A: 「検出を新設せずに済む構造」を探した結果

`adversarial-review-own-safeguards.md` §0-A を通した。**最有力候補は実験で否定された。**

| 案 | 判定 |
|---|---|
| **`renameatx_np(tmp, lock, RENAME_EXCL)` で tmp を「捨てる」のでなく lock そのものにする** | 🚨 **実験で否定**。APFS では成功し排他も EEXIST で成立する (使える) が、**ExFAT では `link` と同じ errno=45 ENOTSUP**。つまり**節約したい FS でだけ使えない**。検出も要らず 2 回目の書き込みも消える理想形だったが、成立しない |
| tmp の fsync を `link` の**後ろ**へ移す (成功時だけ fsync) | **採らない**。crash が `link` と `fsync` のあいだに入ると**中身の無い lock** が残る = issue 383 が閉じた「誰も引き継げない恒久 wedge」を再導入する。`list-masked-failure-modes-before-removing-guard.md` に照らして、消してよい防御ではない |
| 空の tmp で `link` を試して可否を知る | **不可**。link が成功したら**0 バイトの lock を publish する**ことになる (同上の failure mode を確実に作る) |
| tmp/ の中だけで probe link する (`a`→`b`) | 成立はするが、**link が使える FS に 3〜4 syscall を足す**。ローカルでは誤差だが、遅いマウントでは往復が増える。**節約したい側が不明なまま、動く側を確実に遅くする** |
| `Locker` に「link 非対応」を覚える (プロセス内・永続化なし) | 追加 I/O ゼロで安全だが、**効くのは 1 プロセスで `tryPlace` が 2 回以上走るときだけ** (引き継ぎ後の再試行 / `--wait` のループ)。CLI の一発実行は 1 回なので**実効はほぼゼロ** |

## 2026-09-18 の判断: **何もしない**

- 無駄は実在し、その FS では 31% と大きい (推測ではなく実測)
- しかし **その FS を使う運用が無い**。[391](391-bug-lockman-os-exit-skips-defer-leaves-scratch.md) で確認したとおり
  現在の実運用 (`zshlib/_av1ify_lock.zsh`) はローカル HOME = link が成功する側で、
  そこでは**この変更の効果は 0** (実測 8.97 vs 8.90ms)
- 検出を足す案は、**効果のある側が不明なまま、確実に動いている側にコストを載せる**
- 理想形 (`renameatx_np`) は**実験で否定済み**

**再開の trigger**: `link(2)` が使えない FS (SMB / ExFAT / FAT) の上で lockman を使う判断が
戻ったとき。**そのときは検出を作らず、まず「その FS で link が使えるか」を 1 回測る** —
使えるなら何もしなくてよく、使えないなら上の表の最後の 2 案を比べ直す
(実測の手順はこの節がそのまま使える)。
