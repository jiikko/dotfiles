# 637 (perf): 放置フェードの段の計算で、時刻の展開をセル 1 個につき 1 回にする

起票日: 2026-10-04

## 概要

547 (タイピングのもっさり) を pending にした代わりに、`_tmux.conf` の重い箇所を静的 + CPU 時間で探した記録。
**結論: format の修正 (案 A / 案 B) はどちらも入れない。** 本番の tmux サーバの CPU を一番使っていたのは、
開きっぱなしの scratch の popup だった (閉じたら 4.4% → 1.3〜2.1%)。

## 測り方 (このマシンは負荷の奪い合いが激しいので、待ち時間ではなく CPU 時間で読む)

- **部品ごとの format 展開のコスト**: 本番の `_tmux.conf` を隔離サーバ (`-L`、`tests/tmux/lib/isolate_env.sh` で HOME 等も隔離) に読ませ、
  12 window × 3 pane を作り、`display -t <対象> -p '<式>'` を 1 起動に 50 個 × 40 起動並べて、サーバの `ps -o time=` の差分を
  展開回数で割る。`display -p x` の分を引く。2 回測って ±5% 程度で揃った
- **本番サーバの負荷**: `ps -o time= -p <server pid>` を 60 秒あけて 2 回読む (影響ゼロ)。内訳は `sample <pid> 10` の call graph
  (採取の瞬間にサーバがごく短く止まる。読み取りのみ)
- **時刻の展開回数**: `display -v` の展開ログの `after time expanded:` の行数 (1 回の `#{T:}` につき 1 行)

## 分かったこと

### 1. format の部品ごとのコスト (隔離サーバ、tmux 3.7c / macOS)

| 部品 | 1 回 |
|---|---|
| 非 current セル、フェード途中 (最後の操作から 18 秒未満。段 0〜4 と、段 5 のうち経過 15〜17 秒) | 505〜545µs |
| 非 current セル、消灯 (経過 18 秒以上) | 220〜225µs |
| 非 current セル、busy / 未 stamp | 95〜100 / 80µs |
| current セル / status-left / status-right | 5〜20µs |
| pane 枠 1 個 | 40µs |
| `#{T:@epochfmt}` (strftime `%s`) 1 回 | ≈ 135µs (`%S` でも ≈ 85µs。`%s` は `mktime` を通る分重い) |
| 参考: `TZ=Asia/Tokyo` を明示したサーバでの `#{T:}` | ≈ 100µs (−25% 程度) |

- `#{T:}` は format の中で桁違いに重い。macOS の `localtime` / `mktime` が毎回タイムゾーン (`tzsetwall_basic` → `tzload`) を確かめ直している (`sample` の call graph で確認)
- 旧 `@fade-bucket` は clamp の 3 か所で経過を書き下していて、`#{T:}` の展開回数は経過で変わる: 最初の条件
  (`経過 ÷ 3 > 5`) が真になる経過 18 秒以上は 1 回、負の経過 (時計ずれ) は 2 回、それ以外は 3 回。
  経過 15〜17 秒は表示は消灯 (段 5) だが最初の条件が偽なので 3 回払う (反証レビューの指摘)
- 🚨 一度「stamp 付きセルは全部 510µs」と見積もったのは誤り。段の秒数を 1000 にした計測で「消灯」のつもりのセルが段 1 だった

### 2. 本番サーバの使い方と負荷 (2026-10-04 0 時台)

- クライアント 5 (うち 1 つは scratch の popup の中)、window 69、Claude は working 2 / input 3 / seen 3、load average ≈ 6〜8
- 各セッションの非 current セル: stamp 付き 27 個 (ほぼ全部消灯)、busy 14、未 stamp 4。経過 18 秒未満のセルは 5 秒おきに 3 回数えて 3 回とも 0 個 (数えた条件は 15 秒未満。15〜17 秒の分は数えていない)
- サーバの CPU: **popup を開いた状態で 60 秒に 2.66 秒 (4.4%)**。起動からの平均は 3.0% (5 日 15 時間で 243 分)
- `sample` 10 秒の内訳 (tmux が動いていたサンプル 357 個に対して):

| 何に使っているか | 割合 |
|---|---|
| scratch の popup の中身の読み直し (`popup_job_update_cb` → `input_parse`) | ≈ 32% |
| status 行の描き直し (時刻の展開を除く) | ≈ 15% |
| 時刻の展開 (`strftime` / `mktime` / `localtime_r` / `tzload`) | ≈ 12% |
| pane の描き直し・pane の出力の処理など | 残り |

- scratch の popup は `tmux attach -t scratch` を popup の中で動かす形 (`scripts/tmux_scratch_popup.sh`)。**同じサーバ**の scratch クライアントが
  status 2 行 (毎秒の点滅・スピナー・時計) と中の window を描き、その出力を外側のサーバが端末の出力として読み直して popup に描き直す。
  点滅・時計の分と中のプログラムの出力の分の切り分けはしていない
- **popup を閉じた後**: 60 秒に 0.77 / 1.26 秒 (1.3〜2.1%)。`sample` 10 秒で tmux が動いていたサンプルは 357 → 112 個、`popup_job_update_cb` は 0

## 判断 (案ごとの効果と採否)

| 案 | 中身 | 効果 (見積もりを含む) | 採否 |
|---|---|---|---|
| B | `@fade-elapsed` (未 clamp の段) を 1 回だけ計算し、clamp のテンプレート (`@EB@`) へ文字列置換で流し込む | フェード途中のセル 525 → 248µs (実測)。経過 18 秒以上のセルは変化なし。本番では window を離れて 18 秒未満のセルにしか効かず、普段は 0 | **却下**: 効果がマイクロ秒で、置換の印が 1 つ増える |
| A | 「今」を `status-format[0]` で描き直し 1 回につき 1 回だけ計算し、window list 全体へ流し込む | 時刻の展開 ≈ 12% がほぼ消える。tmux の CPU 4.4% → ≈ 3.9%、全クライアントの描き直し 1 回 ≈ 3ms 短縮 (見積もり、未実測。stamp 付き 27 セル × 135µs ≈ 3.6ms から、描き直し 1 回につき 1 回残る分を引いた暗算)。12% は popup を開いた状態の内訳での割合 | **却下**: 体感できる差ではなく、`status-format[0]` を tmux の既定から写して持つ保守が増える |
| — | scratch の popup を使わないときは閉じる (`C-t t`) | 4.4% → 1.3〜2.1% (実測) | **運用で採用** (コード変更なし) |

案 B は実装・検証まで済ませてから捨てた。再挑戦するときの材料:
- 新旧の展開結果を、段の秒数 3 種 (1 / 3 / 1000) × 経過 24 通り (未 stamp・負・境界・巨大値) で `@fade-bucket` / `@fade-ramp-color` /
  セル全体について突き合わせて差分 0 (70 件。秒を跨いだ 2 件は捨てた)
- `tests/tmux/test_window_fade_render.sh` に「時刻の展開回数」(`after time expanded:` の行数) の検査を足し、旧式へ戻す変異で
  段 1 が赤くなることを `mutate-verify` で確認した (消灯は旧式でも 1 回なので赤くならないのが正しい)

## 再開の trigger

- tmux サーバの CPU が popup を閉じた状態で常時 3% を超えるようになったとき (`ps -o time=` の 60 秒差分で測る)。
  その時点で `sample` を採り、時刻の展開の割合が大きければ案 A を検討する
- scratch の popup を開いたまま使うのが常態になったとき: scratch の status (点滅・スピナー・毎秒の時計) を popup 内では止める案を検討する。
  まず popup の 32% のうち点滅・時計の分と中の出力の分を切り分ける
