# 645 (feat): zundamon-kaisetsu の画面に、字幕以外の図解の要素 (重要語の大写し・比較カード・コード・図) を出す


起票日: 2026-10-07

## 概要

zundamon-kaisetsu の動画は、映像が「字幕・2 人の立ち絵・表情・口パク・タイトル・日付・トピック名」だけで、5〜10 分を超える技術解説では
目で追える情報が少ない。台本の行ごとに、図解の要素を画面に出せるようにする。

起点は外部からのフィードバック (2026-10-07)。台本の書き方 (導入のフック・予想・具体例・型の切り替え・小まとめ) は同じ日に SKILL.md へ
反映し、映像の改修は規模が違うのでこの issue に分けた。

## 出したいもの (効果の大きい順)

1. **重要語の大写し**: その行の要点の語を画面の中央付近に大きく出す (例: 「タイムアウト ≠ ネットワーク」)
2. **比較カード**: 「A と B の違い」を 2〜3 点に絞って左右に並べる
3. **コードの数行表示**: 説明している箇所のコードを 3〜8 行ほど出す (等幅・最小限の色分け)
4. **図**: 画像 (SVG / PNG) を出し、めたんの「説明」(指差し) の表情と組み合わせる

## 対応方針 (案)

- **台本 JSON**: 行に任意の `show` を足す (例: `{"show": {"type": "keyword", "text": "…"}}` / `{"type": "compare", "left": […], "right": […]}` /
  `{"type": "code", "lang": "go", "lines": […]}` / `{"type": "image", "src": "…"}`)。次に別の `show` を持つ行か、`{"show": null}` の行が来るまで出し続ける。
  `show` の綴り違い (`shows` 等) は検出しない (`loadScript` は行の未知のキーを検査しない既存の挙動のまま。止めたいなら行のキーの許可リスト化は別の変更)
- **データの持ち方**: トピック名 (`chapters` の表 + 行の `Chapter` 番号) と同じく、図解の中身は `PlayerData` の共有の表に 1 回だけ置き、
  行はその番号だけを持つ。行ごとに中身を入れると、同じ図が続く行の数だけ画像の data URI が複製されて HTML が膨らむ。表の中でも同じ `src` は 1 回だけ読む
- **mp4 の撮影**: 図解は行の関数なので、撮影の状態 (行・話し中か・口の開き) の種類も `frames` の形も変わらない (状態のキーに行が入っている)。
  増えるのは 1 枚あたりの重さ: まとめ撮りは舞台を最大 20 個複製するので、画像も 20 個複製され、3000ms の `--virtual-time-budget` の中で
  全部デコードされて撮れるかは未確認。画像つきで撮影が崩れないことを実測する
- **画像の読み込み**: 立ち絵 (`loadFaces`) と同じく `assemble` の頭で読み、ファイルの欠けで長い処理を無駄にしない。`loadScript` では形だけを
  検査する (未知の type・欠けた欄は理由つきで止める)。`loadScript` は synth / kana にも使うので、そこで画像の有無まで見ると、合成だけしたい場面で止まる。
  `src` の相対パスは立ち絵の `cast.*.faces` と同じく台本の実パス (symlink を解決したもの) から解決する。data URI のサイズに上限を置く
  (音声は 64kbps で 10 分あたり約 5MB。画像が 1 枚でそれを超えうる)
- **配置**: 今の配置では空きが小さい。立ち絵の箱は左右とも幅 40%・高さ 96%、字幕は下端、タイトルと日付は上端、トピック名は上端 17% の中央にあり、
  中央に空いているのは幅 18% ほど。比較カードや 3〜8 行のコードは、立ち絵を縮める・図解の間だけ立ち絵を小さくする、などの配置の変更が要る見込み。
  サンプルを描いて見た目を決めてから本体に入れる (`decide-layout-in-sample-renderer-first.md`)
- **描画**: 図解の CSS はテーマの変数に載せる (mp4 は明るい配色に固定し、HTML はダークモードに従う。画像そのものの配色は制御できない)。
  同じ図解が続く行では DOM を触らない (描き直すと HTML の再生で画像が一瞬消える)。まとめ撮りでも同じ結果になるよう、描画は図解の番号だけから決める
- **SKILL.md**: どんな行で使うかを書く (重要語は 1 チャプターに 1〜2 回まで、など。台本の仕掛けの上限と同じ考え方)
- **テスト**: 図解の無い台本で、既存の golden (build のデータ・キャッシュの鍵) が変わらないこと。キャッシュの鍵は `lineParams` が `show` を
  読まないので変わらない。build のデータは、行に足す欄を図解の無い行では出さない (`omitempty`) か、共有の表のトップレベルのキーを
  `golden_test.go` の `keysAddedAfterPort` に載せる (載せないと「Python 版に無いキー」で落ちる)。`show` の決め方 (出し続ける・null で消す) と
  検査のテスト。撮影の状態の種類が図解の有無で同じであること

## 決定 (2026-10-07)

- **配置**: 図解を出している間だけ、立ち絵を幅 26%・高さ 72% に縮めて左右の端に寄せ、中央の箱 (左 27%・上 30%・幅 46%・高さ 52%。2 で上 27%・高さ 50% から動かした) に
  カードを出す。図解の無い行・図解を使わない台本は今の見た目のまま。サンプル 3 案 (縮めて中央 / 左にまとめて右にパネル / 重ねる) を
  720p で撮り、ユーザーが「縮めて中央」を選んだ
- **進め方**: 重要語から作り、仕組み (`show`・共有の表・配置・撮影) を固めてから、残り 3 種類を同じ仕組みに足す
- **図の作り方**: 画像ファイル (PNG / JPEG) を指す形を先に作り、mermaid を台本に書く形は後から足す (2026-10-07 ユーザー決定)。
  小さい図・複雑すぎる図は逆効果なので入れない (同日のユーザーの指示)。画像の大きさは build で止め、複雑さは SKILL.md の基準と目での確認に任せる
