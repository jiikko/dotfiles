# test: `✗` を出しても exit code に出ないテストがあり、失敗が CI から不可視になっている

起票日: 2026-09-07
カテゴリ: test
優先度: 中（**失敗が緑として集計される**形。issue 139（skip が `[ok]` になっていた）と同じクラス）
出典: issue 306 の修正中に実測で踏んだ

## 何が起きているか

`make test` のテストランナー（`Makefile:run_tests`）は **exit code しか見ない**:

```make
if "$$t"; then :; else rc=$$?; if [ "$$rc" -eq 77 ]; then ... skips ... else ... fails ... fi; fi
```

出力の `✗` は**一切見ていない**。したがって「`✗` を printf するだけで非 0 にならない」
アサーションは、**失敗しても `[ok]` に集計される**。

## 実測（2026-09-07。これが唯一の確実な証拠）

`tests/zshrc/av1ify/test_av1ify_prefetch.sh` に、issue 306 の看取りを無効化する変異を当てた:

```
変異後の出力: ✗ 正常終了後に prefetch が 1 個残った (issue 306)
変異後の rc : 0        ← ランナーはこれを合格として集計する
```

このファイルには **`✗` を出す分岐が 39 箇所**あり、`exit 1` は 7 箇所とも
`cd "$TEST_DIR" || exit 1`（ディレクトリ移動の失敗）だけ。
**アサーション failure から非 0 へ至る経路が 1 本も無い。**

issue 306 の commit では、私が足した Test 18 **だけ**を `exit 1` にして塞いだ。
残る 38 箇所はそのまま。

## 🚨 静的検査では母集合を確定できない（実際に外した）

`✗` を含むが非 0 の仕掛けが無いファイル、という grep で 115 ファイルを走査したところ
**2 件**（`test_video_health.sh` / `validate-mp4/test_validate_mp4.sh`）しか出ず、
**当の `test_av1ify_prefetch.sh` は漏れた**。`cd ... || exit 1` が正規表現に当たってしまうため。

→ **「`exit 1` があるか」では判定できない。** 判定できるのは
「**アサーションを 1 つ壊したときに rc が非 0 になるか**」という実験だけ。

## 推奨対応（順序つき）

1. **まず `test_av1ify_prefetch.sh` の残り 38 箇所**を、失敗が rc に出る形へ揃える
   （`fail=1` を立てて末尾で `exit $fail`、または各所で `exit 1`。
   同 repo の `tests/scripts/test_run_make_targets_parallel.sh` が
   `fail=0` + `bad()` + 末尾 `[ "$fail" -eq 0 ] || exit 1` の形を持っており、これが参照実装）
2. **母集合を実験で確定する**: 各テストファイルへ機械的に「必ず失敗する assert」を 1 つ注入し、
   rc が非 0 になるかを見る meta-test。緑のまま通ったファイルが対象
   - 🚨 これは**自作の検査**なので
     [`adversarial-review-own-safeguards.md`](../../_claude/rules/adversarial-review-own-safeguards.md)
     が発動する。異常系（注入に失敗した / ファイルが構文エラーになった）を
     **「合格」に丸めず第 3 の結果として出す**こと
   - 全ファイルへ毎回やるのは重いので、**CI の別 lane か手動の棚卸し**に置くのが現実的
3. 恒久策として、テストの**書き方の規約**（`fail` カウンタ + 末尾 `exit`）を
   `tests/CLAUDE.md` に 1 行足す

## 🚨 「✗ を grep する」方向へ逃げないこと

ランナー側で出力を grep して `✗` を失敗にする案は、一見安そうだが採らない:

- 正常な出力に `✗` を含むテスト（否定の説明・fixture の中身）を誤って落とす
- **失敗の判定を出力の文字列に預ける**形になり、文言を変えた瞬間に静かに壊れる
  （[`mutation-verify-new-tests.md`](../../_claude/rules/mutation-verify-new-tests.md) の
  「文字列を部分一致で pin していないか」）

直すべきは**テスト側が rc を返さないこと**であって、ランナーの判定基準ではない。

## 対応結果 (2026-09-08)

### todolist（issue の「推奨対応（順序つき）」）

- [x] 1. `test_av1ify_prefetch.sh` の残り 38 箇所を、失敗が rc に出る形へ揃える

- [x] 3. 書き方の規約を `tests/CLAUDE.md` に足す

### 1. `test_av1ify_prefetch.sh`（40 箇所）

`fail` カウンタ方式（issue が指した `tests/scripts/test_run_make_targets_parallel.sh` と同型）へ揃えた。

```zsh
typeset -gi FAIL_COUNT=0
bad() { printf "$@"; FAIL_COUNT=$(( FAIL_COUNT + 1 )); }
...
if (( FAIL_COUNT > 0 )); then printf '✗ 失敗 %d 件 ...' "$FAIL_COUNT"; exit 1; fi
```

- 変換は `printf '✗ …'` → `bad '✗ …'` の**コマンド名の置き換えだけ**（書式も引数もそのまま）。
  40 箇所すべてで第 1 引数がシングルクォートのリテラルであることを機械で数えて確認した
  （`bad "$var"` の形は 0 件 = 書式文字列に変数が入る事故は無い）
- 即 `exit 1` を残したのは**前提の崩れ**の 1 箇所だけ（prefetch が 1 つも起きていないなら、
  その後の「全部死んだか」は何も検査しないまま緑になる）
- 🚨 **サブシェル / パイプ右辺に居る `✗` は無い**ことを事前に確認した（`fail=1` が親へ返らない形は
  変換しても直らないため）。全 40 箇所がトップレベルか、トップレベルから呼ばれる関数の中

**変異検証（4 本）**

| 変異 | 失敗の位置 | rc | 経路 |
|---|---|---|---|
| `_av1ify.zsh` の正常終了時の看取りを外す（= issue 306 の退行そのもの） | 末尾 | **1** | カウンタ |
| `__av1ify_prefetch` が PID を track しない | 冒頭 | **1** | カウンタ |
| `__av1ify_is_valid_variant_tag` が `dnN` を弾く | 中盤 | **1** | err_exit（関数の戻り値） |
| `__av1ify_input_is_encoded_form` が出力形式を検出しない | **中盤のみ・8 件** | **1** | カウンタ（`✗ 失敗 8 件`） |

4 本目が本命。**ファイル中盤で失敗し、最後まで走り切ってからカウンタで rc=1 になる**ことを見た
（末尾だけで確認すると「カウンタが末尾にしか無い形」を見落とす）。
1 本目は issue 本文が実測した退行そのもので、以前は `✗` が出ても rc=0 だった。

### 2. 母集合を確定する道具

`scripts/check_assert_reaches_exit.sh` / `make test-assert-reaches-exit`。

**注入の形を作り替えた。** 最初は「ファイル自身の報告文（`printf '✗ …'` 等）を正規化して
トップレベルへ注入する」方式にしたが、**是正済みの `test_av1ify_prefetch.sh` を「出ない」と誤判定した**
（末尾の集計行 `printf '✗ 失敗 %d 件'` を assert の形と読んでしまい、裸の printf を注入していた）。
そこで **「`✗` の分岐へ必ず入るように条件を固定する」**方式へ変えた
（`if COND; then ✓ else ✗ fi` → `if false; then` / ✗ が then 側なら `if true; then` /
`COND || <報告>` なら左辺を `false`）。報告の形はファイル自身のものがそのまま通るので、
引数の数も書式も推測しなくてよい。

**この検査が退行を観測できることの確認（canary）**

| 対象 | 結果 |
|---|---|
| `test_av1ify_prefetch.sh`（是正前 = `git checkout HEAD --` で戻したもの） | **出ない** rc=1 |
| `test_av1ify_prefetch.sh`（是正後） | **rc に出る** rc=0 |

**異常系**

| 作った条件 | 結果 |
|---|---|
| 対象 0 件（空ディレクトリ） | rc=1 +「1 件も見つからない」 |
| 存在しないパス | rc=1（`find` のエラーも出る） |
| コピーの素の実行が非 0（skip / 環境依存 / 自分のファイル名への依存 / timeout） | **判定不能**（合格に丸めない） |
| `✗` へ入る条件を固定できない書き方 | **判定不能** |
| 成功パスの残骸 | プローブのコピーは 0 件（`find tests -name '.probe-*'` で確認） |

🚨 一時名を `$$` だけで作っていたのを `パスの cksum + $$ + $RANDOM` へ直した。timeout で殺した
worker が残骸を置いたまま pid が再利用されると、**もっともらしい「出ない」/「不明」**を作る
（エラーにならないので出力の表からは見分けられない）。直してから sweep をやり直している。

**結果（母集合）**

```
検査 115 件 / 結果を報告 115 件: rc に出る 55 / 出ない 18 / 判定不能 12 / ✗ を出さない 30
```

一覧と、**「✗ を出さない 30 件」のうち 16 件が `FAIL:` / `ERROR` で報告していて道具の射程外**である
ことは **issue 329** に移した（残債の消化はそちら）。

### 3. 規約

`tests/CLAUDE.md` に「アサーションの失敗は exit code に出す」節を新設
（fail カウンタ / 即 exit の 2 択・`err_exit` 下でも `if/else` の中は rc に出ないこと・
`✗` を grep する方向へ逃げない理由・棚卸しの入口）。
Makefile の target にも「**当面は赤いのが正常**」を明記した
（次のセッションが赤を見て「自分が壊した」と読まないため）。

### 却下した案

- **runner 側で `✗` を grep して失敗にする**: issue 本文のとおり採らない。正常な出力に `✗` を含む
  テストを誤って落とすうえ、失敗の判定を出力の文言に預ける形になる
- **道具のマーカーを `FAIL` / `ERROR` へ広げる**: `MOCK_FFMPEG_FAIL` のような変数名にも当たる。
  射程外であることを明記して issue 329 へ回した
- **母集合を baseline ファイルに固定してラチェットにする**: `make test` に入れていない（重い）ので
  自動では効かず、baseline が腐るコストと引き合うか未判断。案として issue 329 に残した
