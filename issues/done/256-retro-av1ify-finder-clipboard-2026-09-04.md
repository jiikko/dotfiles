# 256 retro: Finder 複数選択のクリップボード入力を直したセッション (2026-09-04)

起票日: 2026-09-04
種別: retro
関連: [255](255-human-verify-av1ify-finder-multiselect.md) / [094](done/094-human-verify-av1ify-clipboard-input.md) / [095](done/095-retro-av1ify-clipboard-input-2026-08-22.md)

やったこと: `av1ify` / `av1c` の引数なし呼び出しで、①ペーストボードのファイル参照 (file URL) を
最優先で読む ②1 行に空白区切りで並んだ複数パスを案内でなく分割して受け取る、の 2 点を入れた。

## 1. 「文字列をパースする」設計が入口から間違っていた

報告は「Finder で複数選択したときにパースできていない」だった。パーサを直しに行く前に
ペーストボードそのものを測ったところ、**Finder の Cmd+C はプレーンテキストを 1 バイトも
載せない**（複数 `public.file-url` を載せた状態で `pbpaste` は空）ことが分かった。
つまり従来実装は Finder のコピーに対して構造的に無力で、パーサをいくら直しても届かない。

`~/.claude/CLAUDE.md`「不具合対応の原則」の「同一性は安定キーに統一し、表示用文字列に
依存しない」がそのまま当てはまる事例だった。**切り出し先の提案: 却下**（既存の原則で
言い切れている。新しいルールは要らない）。

## 2. 検証コマンドの stdout / stderr を分けて測ったのに、片方しか読まなかった

1 回目の `make test` を `> out 2> err` で分けて回し、**err だけを見て「shellcheck は通った」と
読んだ**。実際は shellcheck の指摘は stdout に出ており、`✗ 失敗したターゲット: test-lint` も
出ていた。2 回目に `2>&1` で回して初めて気づいた。

さらに background 実行の**完了通知の exit code 0 を成否と読みかけた**（通知の rc は
ラッパーコマンドのもので、`make` の rc ではない）。

[`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md) は
既に「検証の出力はファイルへ落としてから読む」「完了通知で判定しない」と書いてある。
足りなかったのは**落とした後に全部読む**こと。**切り出し先の提案: 同ルールへ 1 行**
（「stdout / stderr を分けたら**両方**読む。片方だけ見て『通った』と読まない」）。
新規ルールにはしない（発動点が既存と同じ）。

## 3. 敵対的レビューが変異検証を全部通した後の P1 を出した

変異 6 本（M1〜M6 相当）を当てて red を確認した後で codex の敵対的レビューを回したところ、
**KSH_ARRAYS 下で分割行の先頭が消え末尾が空文字になる**（一覧と処理対象がずれる = `av1c` では
削除対象がずれる）P1 が出た。しかもこれは 2026-08-23 に旧 `__av1ify_invocation_name` で
踏んだのと同じ罠で、**そのとき書いた注意書きは削除した関数と一緒に消えていた**。

[`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md) の
「変異は自分が想定した不変条件しか試さない」の 3 例目。**切り出し先の提案: 却下**
（ルールは既にこの現象を名指ししている。実例として rationale へ 1 行足すかはユーザー判断）。

ただし**「関数を消すときに、その関数のコメントが持っていた教訓の行き先を決める」**は
どのルールも言っていない。今回は `setopt LOCAL_OPTIONS no_ksh_arrays` として実装に固定し、
コメントで旧関数の実例を引き継いだ。**切り出し先の提案:
[`list-masked-failure-modes-before-removing-guard.md`](../_claude/rules/list-masked-failure-modes-before-removing-guard.md)
へ 1 行**（「関数ごと消すときは、そのコメントが記録していた failure mode の行き先も決める」）。
判断はユーザーに委ねる。

## 4. 「案内する」より「確認付きで受け取る」方が安全だった

旧実装は空白区切りの行を検出したら `av1c ${(Q)${(z)"$(pbpaste)"}:#\;}` を案内していたが、
**案内先の位置引数経路には一覧も [y/N] も無い**（だから赤字で「確認が出ずゴミ箱移動まで
走る」と警告していた）。同じ判定条件のまま自分で受け取れば、確認を通せる。
「安全のために手数を増やす」つもりの設計が、実際には**確認の無い経路へ人を送っていた**。

**切り出し先の提案: 却下**（一般則にするほど形が固まっていない。この issue の記録で足りる）。

## 5. 真因を掴まないまま 1 回目をコミットして、直っていなかった

ファイル URL 経路（Finder の Cmd+C）は実測で裏を取ったが、**ユーザーが実際に踏んだ
テキスト経路の失敗理由は「再構成すると案内が出る」までしか分かっていなかった**。
そのままコミットし、ユーザーの追試で「治っていない」と返ってきた。

[`instrument-before-second-fix.md`](../_claude/rules/instrument-before-second-fix.md) は
「1 回目が外れたら観測を増やす」だが、今回は**1 回目を打つ時点で「何が見えていないか」を
自覚していた**（issue に「未解決」と書いていた）。同ルールの末尾「着手時点で『なぜ壊れて
いるか分かっていない』自覚があるなら、1 回目の修正と同時に観測を仕込んでよい」に該当する
場面で、観測（診断コマンド）は issue に書いたのに**ユーザーに走らせてもらう前にコミットした**。

2 回目は分かっている情報だけで確実に効く形へ倒した:「`(z)` という**壊れやすい前提**に
依存するのをやめる」。壊れ方の型を特定できなくても、型に依存しない切り方を足せば直る。

**切り出し先の提案**: `instrument-before-second-fix.md` へ 1 行
（「観測を人に依頼したなら、その結果が返る前に修正をコミットしない。または**壊れ方の
特定に依存しない直し方**を採る」）。判断はユーザーに委ねる。

## 6. `(z)` を「貼り付けテキストのパーサ」として使っていたのが構造的な誤り

`(z)` はシェル入力の字句解析であって、任意のテキストのトークナイザではない。
**引用符の対応が崩れた瞬間に全体の解釈が壊れる**という all-or-nothing の性質があり、
コード内にも「対応の取れないクォートを含む行は 1 トークンに畳む」と既知の取りこぼしとして
書いてあった。**既知として記録したまま、それが実際に踏まれる形（貼り付け）を放置していた**。

**切り出し先の提案**: 却下（この教訓は当該コードのコメントに書いた。一般ルールにするには
zsh 固有すぎる）。
