# glogx: dispWidth の ASCII fast-path が実質死んでいて、View 1 フレームの CPU の 64% が幅計測

起票日: 2026-08-14
種別: perf (実測駆動)
優先度: **P1** (フレーム描画の最大コスト。修正の効果が数値で確定している)

## 観測した事実

`BenchmarkViewSteady` (一覧 1 フレーム・120x40) の CPU プロファイルで、
`browseModel.View` の cum 2.01s のうち **`dispWidth` が 1.29s = View の CPU の 64%**。
その 98.8% は `ansi.StringWidth` → `FirstGraphemeCluster` → uax29 の grapheme 走査。
呼び出し元は `clipMeasure` が 81%。

`width.go` の `dispWidth` は 2026-07-29 に「印字可能 ASCII だけなら `len(s)` を返す」
fast-path を入れてある。**この fast-path がほぼ機能していない。**

計測 (200 フレーム分の全 `dispWidth` 呼び出しを分類。ログ: `tmp/glogx-perf/dispwidth_probe.txt`):

| 画面 | 総呼び出し | fast-path 到達 | slow-path |
|---|---|---|---|
| 一覧 | 16501 | 5900 (35.8%) | 10601 (**64.2%**) |
| status viewer | 53901 | 19700 (36.5%) | 34201 (**63.5%**) |
| diff popup | 28701 | 12100 (42.2%) | 16601 (**57.8%**) |

slow-path に落ちる要因の内訳 (fast-path を外した最初のバイト):

| 画面 | 要因 1 | 要因 2 | 要因 3 |
|---|---|---|---|
| 一覧 | `ESC` 96.2% | `→` U+2192 3.8% | `─` U+2500 0.0% |
| status | `ESC` 78.9% | `…` U+2026 18.7% | `─` / `→` 各 1.2% |
| diff | `ESC` 97.6% | `→` U+2192 2.4% | `─` U+2500 0.0% |

## なぜ死んでいるか (前提の誤り)

fast-path のガードは `s[i] < 0x20 || s[i] > 0x7e` で、**ESC (0x1b) が `< 0x20` に該当する**。
色付きの行は必ず SGR (`ESC[...m`) を含むので、**色を付けた行は 1 つ残らず fast-path を通れない**。
`colored` が既定 (TTY かつ `NO_COLOR` 未設定) なので、実運用ではほぼ全行が slow-path。

さらに、SGR だけを許しても足りない。「ASCII + SGR のみ」で構成される文字列は
実測で **0.0〜0.7%** しかない — glogx が出す行にはたいてい幅 1 の非 ASCII 記号
(CI 状態の `✓ ✗ ● ⊘ ↑`・枠線 `─ │`・切り詰めの `…`・`→`・スピナー `⠋`) が混ざるため。
**「ESC を通すだけ」の素朴な修正では効かない**ことが計測で確定している。

## 対応方針 (計測で裏付けのある形)

> 🚨 以下は**起票時点の方針**。実装時に敵対的レビュー R1 の指摘で「幅 1 の許可リスト」を
> 「幅はライブラリから引く表」へ改めた。最終形と理由は末尾の「対応の記録」を見ること。

fast-path を「**印字可能 ASCII + SGR (`ESC[` 数字/`;` `m`) + 幅 1 の記号の許可リスト**」まで広げ、
それ以外 (`≥0x80` で許可リスト外 / SGR 以外のエスケープ / 途中で切れたエスケープ / C0) は
従来どおり `ansi.StringWidth` へ落とす。

この候補で拾える範囲を実測済み (同ログ):

| 画面 | slow のうち候補が拾える | 全体に対して | `ansi.StringWidth` との幅の不一致 |
|---|---|---|---|
| 一覧 | 10401/10601 (**98.1%**) | 63.0% | **0 件** |
| status | 33801/34201 (**98.8%**) | 62.7% | **0 件** |
| diff | 16201/16601 (**97.6%**) | 56.4% | **0 件** |

### 正しさが構造的に保てる理由

許可リストに入れるのは「単独で 1 個の grapheme クラスタを成し、幅 1」の記号だけ。
クラスタが結合するには**後続**が combining mark / ZWJ / 異体字セレクタ / regional indicator
である必要があり、**それらは許可リストに入れない**。よって許可リストの文字同士は
決して結合しない = 1 文字 1 幅の単純加算が `ansi.StringWidth` と一致する。

`truncateKeepANSI` が意図的に作る「閉じていない色」や途中で切れたエスケープは、
終端 `m` が見つからない時点で fallback に落ちるので誤らない (この repo は
`width.go` の doc どおり幅モデルをエンジンと一致させる必要があるため、
**一致が崩れる可能性のある入力は必ずライブラリへ委ねる**)。

### 検証条件 (これを満たさないと入れない)

- 許可リストの各文字について `ansi.StringWidth(string(r)) == 1` を **テストで実証**する
  (表を手で書いて信じない)
- `dispWidth` の新旧を **差分 fuzz** (`go test -fuzz`) で `ansi.StringWidth` と突き合わせる。
  部分的なエスケープ・8bit・結合文字・絵文字・CJK を含む入力で不一致 0 を確認する
- 変異検証: 許可リストから 1 文字外す / SGR の終端判定を壊すと red になること

## やらないこと

- **`dispWidth` のメモ化 (`sync.Map` 等) はしない。** 既存ベンチは毎 iteration で同じ内容を
  描き直すため、メモ化すると**測定が嘘をつく** (実運用ではフレームごとに内容が変わる)。
  fast-path はステートレスで O(n) なので、この罠を構造的に避けられる
- 幅モデルの変更はしない (`GraphemeWidth` のまま。`width.go` 冒頭の doc が一次情報)

# 対応の記録 (2026-08-14)

## 直したこと

`fastDispWidth` を「印字可能 ASCII + SGR + 幅を表に持っている記号」まで拡張した。
受理判定 (`acceptSymbol`) と幅 (`symWidthTable`) を分離し、**幅はライブラリから
`init` 時に 1 度引く**形にした (下記 R1 の指摘への対処)。

## 実測 (min of N・ベースラインと同一条件)

| bench | before ns/op | after ns/op | 倍率 |
|---|---|---|---|
| ViewSteady (ASCII subject) | 78,561 | 28,670 | ×2.74 |
| **ViewSteadyJA (日本語 subject 77 セル = 実運用相当)** | **85,970** | **41,609** | **×2.07** |
| 参考: R3 が実 commit subject 20 本で測ったもの | 88,513 | 44,122 | ×2.01 |
| ViewWithPanel | 89,552 | 33,982 | ×2.64 |
| StatusViewFrame | 97,506 | 38,036 | ×2.56 |
| StatusViewFrame2000 | 123,819 | 62,594 | ×1.98 |
| CursorMoveView | 166,137 | 60,720 | ×2.74 |
| ViewWithDiff | 126,948 | 38,992 | ×3.26 |
| ModelInit200 | 166,781 | 115,055 | ×1.45 |
| RenderLinesLargePatch (対照) | 583,997 | 583,371 | 1.00 |
| HighlightDiff (対照) | 412,609,917 | 410,419,750 | 1.01 |
| Calibrate (較正器) | 72,866 | 71,139 | 1.02 |

対照 3 本が動いていないので、マシン変動ではない (R3 の交互 A/B 測定でも再現。
そちらでは較正器が after 側で 1.03 倍**遅い**方向に振れており、なおさら
「マシンが速くなった」では説明できない)。

確保について:

- `allocs/op` (確保の**回数**) は全ベンチで完全一致 (178 / 199 / 359 / 364 / 356 / 254 / 1386)
- 🚨 **B/op は systematic に +0.8〜1.0% 増えている**。固定 iteration (`-benchtime=4000x`・各 4 本)
  で before 39,663〜39,932 / after 39,996〜40,177 と帯が重ならない。回数が同じでバイトだけ
  増えるので「どこかの確保が僅かに大きい」ことになるが、**機構は特定できていない**
  (alloc profile は sampling なので 1% を分離できない)。R3 の指摘で判明。
  したがって「確保の挙動を変えていない」とは書かない
- `init` で表を焼くコストはプロセス 1 回きり 48µs / 3,248 B / 812 allocs (定常フレーム約 1.6 枚分)

**報告する数値は「内容依存で ×2.0〜×2.6」**。実運用の一覧は 98% が CJK 混在なので
日本語側 (×2.0) が実勢で、ASCII の ×2.6 は上限側。日本語を含む行は fast-path を通れず
ansi へ落ちるため、ASCII 固定フィクスチャだけで測ると過大評価になる
(R2 の指摘で `BenchmarkViewSteadyJA` を追加して初めて分かった)。
R3 が**実 commit subject 20 本をそのまま使ったフィクスチャ**で測ると ×2.01 で、当初の
フィクスチャ (表示幅 54 セル) は実物 (中位 75 セル) より短く 4〜5% 楽な数字だった。
そこでフィクスチャを 77 セルへ寄せ直して測り直したのが上表の ×2.07 で、実 subject の
×2.01 とほぼ一致する。

## 敵対的レビュー 3 ラウンドの指摘と反映

### R1 (正しさ / 等価性) — **P1 の実退行を検出。反映済み**

記号の幅を `1` と決め打ちしていたため、`RUNEWIDTH_EASTASIAN` が真の環境で
`ansi.StringWidth` だけが幅 2 に転び (x/ansi の `method.go` の `init` が env を読む)、
glogx の自前幅と `ansi.Truncate` / `ansi.TruncateLeft` が同じ文字について別の幅を見る状態に
なっていた。受理 812 rune のうち 212 個が幅 2 に転ぶ (Box Drawing は 128 個中 112 個)。

実害の再現 (自分でも実測して確認):

| 式 | 期待 | EASTASIAN=1 での実際 |
|---|---|---|
| `dispWidth("─")` vs `ansi.StringWidth("─")` | 一致 | 1 vs **2** |
| `fillRight(罫線10個, 30)` の実幅 | 30 | **40** |
| `truncateDispLeft(罫線10個+"abc", 8, "…")` の実幅 | 8 | **19** |

旧実装 (印字可能 ASCII だけ) は ASCII が East Asian Ambiguous になり得ないため
この env でも `ansi` と一致していた = **本修正が持ち込んだ退行**だった。

**反映**: 幅の決め打ちを廃止し、`init` で `ansi.StringWidth` から引いて `symWidthTable` に
焼く形へ変更。env の設定が何であれ幅モデルが構造的に一致する。検証として
`RUNEWIDTH_EASTASIAN=1` の**子プロセス**を起こすテストを追加した (env は x/ansi の `init` が
読むので、同一プロセス内の `os.Setenv` では捕まえられない)。

R1 の P3 2 件も反映:
- 総当たりテストが U+FFFF で止まっていた → 表の範囲外 (BMP 外・負値含む) を明示的に検査
- クラスタ結合の理由付けが「後続」の規則しか挙げていなかった → **先行**側の規則
  (GB9b Prepend / GB9c Indic conjunct) を追記し、受理集合の全ペアで結合しないことを
  総当たりで検査するテスト (`TestAcceptedSymbolsNeverCombineWithEachOther`、663,404 ペア) を追加

### R2 (回帰と副作用) — 悪化は検出されず。**ぼやきを 1 件反映**

- 呼び出し元 11 箇所を横断確認、`clusterWidth` との整合も含め問題なし
- 隔離 worktree で速度向上を独立に再現 (罫線 120 文字は ×8.2、SGR + ASCII 行は ×13.7)
- P3: CJK を含む行は fast-path を外すまでの走査が純オーバーヘッド (実測 +4〜25ns / 呼び出し、
  0.5〜2.5%)。フレーム 30〜90µs に対し無視できる規模なので**修正しない**
- **反映**: 「既存 View ベンチが ASCII 固定フィクスチャで日本語混在行を踏んでいない」
  という指摘を受け `BenchmarkViewSteadyJA` を追加。実運用の数値が ×2.74 ではなく
  ×2.0 台であることが判明した (上表)

### R3 (検証の検証) — **P1: 退行を守るテストが実質 1 本で、2 経路で無言に空回りしていた。反映済み**

R1 が見つけた退行 (幅 1 の決め打ち) を**その変異を当てて**確かめた結果、既定 env の
`go test .` で red になるのは `TestDispWidthAgreesUnderEastAsianEnv` の **1 本だけ**だった。
しかもその 1 本が次の 2 経路で無言に無力化される:

1. **run filter がリテラル**: `-test.run=TestDispWidthAgreesUnderEastAsianEnv` を文字列で
   書いていたため、関数名を変えて直し忘れると子は「no tests to run」で **0 本走って exit 0**、
   親は緑を返す。R3 は「幅 1 の決め打ち + 関名 rename」の合成で `ok glogx` になることを実証した
2. **env が効いていることを確かめていない**: assert が `dispWidth == ansi.StringWidth` の形
   なので、x/ansi が env の読み方を変えた日に**両辺が同じ幅モデルに乗って恒真**になる。
   実際 `GLOGX_EAW_CHILD=1` だけ (EAW 無し) で子の本体を走らせると、退行を入れたままでも `ok`

加えて **P2**: `TestSymbolWidthTableMatchesLibrary` は既定 env では両辺が同じ関数由来の
恒等式で、守れるのは表のエンコード崩れだけ。しかも子が自分 1 本しか走らないため、
このテストが EASTASIAN 環境で走る経路がどこにも無かった。

**反映** (3 点。いずれも変異で red を確認):

- run filter を `t.Name()` から組み立て、rename と構造的に同期させた
- 子の先頭で `ansi.StringWidth("─") == 2` を止まる形で要求し、env が効かない環境で
  緑を返さないようにした
- 子で走らせる集合を幅系 4 本へ広げた (`TestSymbolWidthTableMatchesLibrary` /
  `TestFastDispWidthMatchesLibrary` / `TestAcceptedSymbolsNeverCombineWithEachOther` を含む)。
  🚨 suite 全体には広げられない — EASTASIAN=1 では幅 1 前提の既存テストが 22 本 fail する
  (本修正の前からそう)
- 親が **PASS した本数 (4 本) を出力で照合**するようにした。「落ちなかったこと」を成功の
  根拠にすると 0 本走っても緑になるため

検証 (変異):

| 変異 | 期待 | 結果 |
|---|---|---|
| 幅引きを `1` の決め打ちへ戻す (= R1 の退行そのもの) | 既定 env の `go test` で red | ✅ red (子が EAW で幅系 4 本を走らせて落ちる) |
| run filter のテスト名を 1 つ typo にする | red | ✅ red (「PASS したのが 3 本 (want 4)」) |

**R3 の P3 も反映**:

- `allocs/op` 一致を「確保の挙動を変えていない」根拠に使うのをやめた (上記「確保について」)。
  B/op が +0.8〜1.0% 増えていることを自分でも固定 iteration で再現して記録した
- 非 SGR CSI の 2 ケースは「幅の不変条件」ではなく「SGR 以外は ansi に委ねる方針」を
  固定しているものだと、テストにコメントで明記した (将来 CSI 扱いを広げるときに
  正しさの red と誤読しないように)
- `init` の焼きコスト (48µs / 3,248 B / 812 allocs・プロセス 1 回) を記録した
- フィクスチャの表示幅を実物 (中位 75 セル) に寄せて 77 セルへ直し、測り直した

**R3 が崩せなかった点** (記録):

- `init` で焼いた表が stale になる経路は無い (`ansi` の幅設定は unexported で、
  同 package の `init` 以外に書き手が無く、依存ツリーに変更 API の使用が 0 件)
- 受理集合の全ペア総当たりは本物 (表の範囲内に「幅 1 を通るのに結合する rune」が 185 個
  実在し、それを混入する変異で red になることを確認)
- 「同一内容の反復が有利」説は否定 (内容が毎 iteration 変わる変種でも ×2.72 / ×2.14 で同値)
- コード内の変異検証コメント (C0/DEL の早期棄却は無害) は正確

## 変異検証 (mutation-verify-new-tests.md)

| 変異 | 結果 |
|---|---|
| Box Drawing の範囲受理を消す | ✅ red |
| SGR の終端 `m` 検査を無効化 | ✅ red (`\x1b[2Ka` を受理してしまう) |
| 幅 2 の文字 (`漢`) を受理集合へ足す | ✅ red |
| 記号の受理判定を常に true | ✅ red (CJK / 全角スペース / ZWSP / 不正 UTF-8 を受理) |
| C0/DEL の早期棄却を消す | 🚨 **green のまま** |

最後の 1 件はテストが弱いのではなく**変異が意味的に無害**だった: この分岐を消しても
`default` が rune を復号して表で落とすので結果が同じ。正しさに寄与しない最適化である
ことをコードのコメントに明記した (load-bearing だと誤読されないように)。

## 未確認リスク / 記録に留めたもの

- **`RUNEWIDTH_EASTASIAN=1` では `width_test.go` が本修正の前から fail する**
  (`dispWidth("→") == 1` を期待値に焼いているが、その env では ansi も 2 を返す)。
  つまりこの env はもともと未サポート領域。本 issue では直さない
  (「glogx がこの env を支持するか」は設計判断で、perf 修正の範囲外)
- `truncateDispLeft` は全角グリフが切り位置をまたぐと `ansi.TruncateLeft` の丸めで
  要求幅 +1 を返す (EASTASIAN=1 で要求 8 に対し 9)。**fast-path 導入前から同じ**なので
  本修正の責任範囲ではない。テストは「要求幅以下」ではなく「ansi 基準と同じ結果」を主張する形にした
- `truncateDispLeft` が `dispWidth` (自前幅) と `ansi.TruncateLeft` (ライブラリ幅) を
  1 つの式で混ぜている構造は、今は両者が一致するので実害ゼロだが、
  「同一モデルであること」を暗黙の前提にしている (R1 のぼやき)
