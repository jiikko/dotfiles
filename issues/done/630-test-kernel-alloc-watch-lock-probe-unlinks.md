# 630 (test): test_kernel_alloc_watch.sh のロック待ちの判定が `-k` 無しの lockf で、`make test` の中でだけ落ちる

起票日: 2026-10-02

## 概要

`tests/bin/test_kernel_alloc_watch.sh` の「ほかの記録がロックを握っている間は消さない (rc=75)」の節で、
ロックを握る側が握れたかを待つ判定 `lock_is_held` が `-k` 無しの `lockf` を使っている。
BSD の `lockf` は `-k` が無いと、ロックを取ってコマンドを終えたあとにロックファイルを消す。
判定が握る側より先にロックを取ると、握る側が消されたファイルのロックを掴み、以後の判定は新しく作ったファイルを毎回取れてしまう。
結果、握る側が生きているのに 20 秒待っても「握られている」と見えず、`ng "ロックを握る側が 20 秒たってもロックを取れない (判定できない)"` で落ちる。

本体 (`bin/kernel-alloc-watch`) は 2 か所の `lockf` (`record` と `destroy-all-logs`) とも `-k` を付けていて、
「ロックの印 (.lock) は消さない: 消すと … 2 本が同時に書き換える窓ができる」と 🚨 のコメントもある。テストの判定だけがその罠を踏める形になっている。

### 仕組み (再現した部分と、していない部分)

該当箇所 (`tests/bin/test_kernel_alloc_watch.sh` の「ほかの記録がロックを握っている間は消さない」の節):

```sh
/usr/bin/lockf -k "$d/.lock" sleep 30 & holder=$!
lock_is_held() { ! /usr/bin/lockf -t 0 "$d/.lock" true 2>/dev/null; }
TT_WAIT_TICKS=400 TT_WAIT_TICK=0.05 tt_wait_until lock_is_held && held=1
```

握る側を背景で起こした直後に判定が走るので、判定が先にロックを取ることがある。そのとき:

1. 判定が `.lock` を作ってロックを取り、`true` を走らせる
2. その間に握る側が同じ `.lock` を開き、ロックが空くのを待つ
3. 判定が終わり、`-k` が無いので `.lock` を消して離す
4. 握る側が、消されたファイルのロックを取る (`-k` の側は消されたかを確かめない)
5. 以後の判定は新しい `.lock` を作るので、毎回ロックを取れる → 20 秒の待ちが切れて ng

2 の窓に握る側の open が入るかは時間の運で、これが負荷の高いときにだけ出る理由と考えている。

- 起票者が手で再現したのは 3〜5 まで (`-k` 無しの側が終わってファイルを消したあと、握る側が生きていても判定がロックを取れる)。下の手順
- 反証レビューのサブエージェントが、本物の順序 (握る側を `&` で起こした直後に判定をポーリング) を、並列 12 本 + CPU 負荷 8 本の下で回した。
  `-k` 無しの判定は 400 回中 80 回、200 回中 35 回で最後まで取れ続けた。その全件で、握る側の子の `sleep` は生きていて、
  握る側が持つ fd の inode は今の `.lock` と別だった (lsof)。判定に `-k` を付けると、同じ負荷で 400 回中 400 回が「握られている」になった。
  **この頻度の実測はレビュワーのもので、起票者は再実行していない**

再現の手順 (2026-10-02、macOS の `/usr/bin/lockf`):

```sh
d=$(mktemp -d); f="$d/.lock"
/usr/bin/lockf -t 0 "$f" /bin/sleep 1 & probe=$!   # -k 無し: 終わると .lock を消す
/bin/sleep 0.2
/usr/bin/lockf -k "$f" /bin/sleep 5 & holder=$!     # 握る側: 先の側が離すまで待つ
wait $probe; /bin/sleep 0.3
ls "$f"                                             # → No such file or directory
/usr/bin/lockf -k -t 0 "$f" true && echo 取れた     # → 取れた (握る側は生きている)
pkill -P $holder; kill $holder; wait $holder; rm -rf "$d"
```

`man lockf` の記述: `-k` が無いとコマンドの後にファイルを消す。また「`-k` を使わないならロックの順序は保証しない」とある。

### 期待

判定は、握る側が握った後に「握られている」と答える。判定がロックファイルを消さない。

## 対応方針

- `lock_is_held` の `lockf` に `-k` を付ける (`/usr/bin/lockf -k -t 0 "$d/.lock" true`)。両方が `-k` なら誰もファイルを消さないので、
  判定が先に取っても、離したあと握る側が同じファイルを取り、次の判定で「握られている」と見える
- あわせて、判定は `lockf` の rc が 75 (ロック待ちの時間切れ) のときだけ「握られている」と読む。今の `! lockf … 2>/dev/null` は
  fork の失敗 (71) や open の失敗 (73) も「握られている」と読む
- 「20 秒たっても取れない」の ng に、握る側 (の子) が生きているかを添える。次に落ちたとき、握る側が遅れたのか孤児になったのかを区別できる
- 直すときに、351〜352 行のコメント (待ちきれずに進んだのを「CI の負荷で実際に起きた」とする説明) も今の理解に合わせる
- 同じ仕組みの別の箇所: repo 全体 (`.git` と `issues/` を除く) の `lockf` を `-k` 無しで探すと、該当はこの 1 か所だけ (2026-10-02)
