### 1. 🚨 「red の根拠が HEAD にまだ在るか」は、変異検証とは**別の問い**

2 周目の P1-A。commit message に「接頭辞になる名前（`PROT` vs `$PROT_DIR`）で red を確認した」と
書いたが、**その red は変異体にしか存在しない fixture に依存**していた。同じ commit が `PROT_DIR` の
被覆を直した結果、**HEAD には接頭辞衝突する変数が 0 件**（実測: 6 変数の総当たりでペア 0）。
「境界照合は変異で確認済み」は**変異体については真、HEAD については偽**で、
その防御は HEAD では誰にも守られていなかった。

`mutation-verify-new-tests.md` の既存項目はすべて「変異を**当てた瞬間**」の話。
`0714d0e0` が足したハーネス側 guard（`diff -q` / `bash -n`）とも発動点が違う（grep で確認済み）。

**切り出し先の提案**: `mutation-verify-new-tests.md` へ 1 行。

> 🚨 **変異で red を確認したら、その red を成立させていた入力が HEAD にまだ在るかを見る。**
> 同じ commit の別の修正が fixture を母集合から消していると、「変異で確認済み」は
> **変異体については真、HEAD については偽**になる。

### 2. 🚨 pin の自己参照 — pin の**その行自身**が pin を満たす

自分で変異を当てて見つけた 2 形。

- この検査自身の trap を `grep -q 'trap tt_cleanup_all EXIT INT TERM HUP' "$SELF"` で pin したが、
  **その検査行のテキスト**が一致し、本物の trap を消す変異が**緑**（行頭アンカーで解決）
- `grep -q 'reap_mktemp.sh' "$REAP"` が直前の `# shellcheck source=…` という**コメント**に一致し、
  source を消す変異が緑

`path-shim-must-resolve-real-binary.md` の「自己参照」は **PATH 解決**が発動点で、こちらは
**grep ベースの pin**。

**切り出し先の提案**: `mutation-verify-new-tests.md` の「よくある『守っていないテスト』の形」へ 1 行。

> 🚨 **grep で配線を pin したら、その grep 自身の行が pin を満たしていないか確かめる。**
> 検査コードと検査対象が同じ文字列を含むとき、変異を当てても緑のまま通る。

### 6. 🚨 「照会に答えられない」は宛先の形ではなく**セッションが持つツールの違い**だった

`issues/done/348` の追記（dotfiles-cd）が「`from=` をコピーすれば届く。ただし a8 / 4b が何を `to` に
入れたかは**未検証**」と書いている。**こちらから答えを出す。**

私 (4b) が試したのは 3 形で、**全部同じエラー**だった:

| `session_id` に入れた値 | 結果 |
|---|---|
| `dotfiles-71`（名前） | — そもそも受け付けない |
| `c9eab2`（`ListAgents` の短 ref） | `session c9eab2 not found` |
| **`uds:/tmp/cc-socks/94374.sock`（`from=` をそのままコピー）** | **`session uds:/tmp/cc-socks/94374.sock not found`** |

つまり **`from=` のコピーでも届かない**。私のセッションが持つのは
`mcp__ccd_session_mgmt__send_message` で、これは **CCD のセッション ID（`local_…`）しか受けない**。
`to` を取る `SendMessage` は私のツール一覧に無く、`ToolSearch` でも出てこない。

**結論**: 「宛先の形の問題」ではなく **セッションによって使えるツールが違う**。
UDS のセッションへ返信できるのは `to` を取るツールを持つセッションだけで、
`ccd_session_mgmt` しか無いセッションは**原理的に返信できない**。

**切り出し先の提案**: `claim-issue-in-next-and-push.md` の hook 節へ 1 行。

> 🚨 **照会に答えられないことがある**（`ccd_session_mgmt` しか持たないセッションは UDS の相手へ
> 返信できない。`from=` のコピーでも届かない）。**沈黙は「空いている」と読まれる**ので、
> 返信できないと分かったら**その事実をユーザーへ上げる**。

### 8. 🚨🚨 **この作業が本番 tmux サーバ (30 セッション) を kill した** (2026-09-11 00:28)

詳細は [305 の事故記録](305-bug-tmux-and-go-test-temp-resources-not-swept-at-startup.md)。fix は `83296178`。

**気づき 3（自分の検証装置が検証対象と同じ残骸を作る）の最悪版**。あちらは 0 バイトの socket が
97 件だったが、こちらは**本番を落とした**。共通しているのは「安全機構を書いた本人が、その機構の
射程を実際より広く見積もっていた」こと:

- コメントに「**二重の保険として名前で弾いている**」と書いたが、その除外は `rm` の手前にしか無く
  `kill` の手前に無かった。**書いた本人が、書いた行の位置を確認していない**
- 隔離を `TMUX_TMPDIR` の差し替え 1 段に預け、**その 1 段が崩れたときどこへ行くかを測っていなかった**
  （空 / 不在 / 未設定のいずれでも本番へフォールバックする、は今回初めて測った）

`adversarial-review-own-safeguards.md` §1 の表は「対象 0 件 / 依存コマンド失敗 / 権限なし / 並行」を
挙げるが、**「隔離が崩れたときの行き先」**が無い。`tmux-probe-requires-socket-isolation.md` は
「隔離が効いていることを実証してから打つ」と書いており規範としては足りているが、
**今回は隔離を「実証」ではなく「変数を渡した」で済ませていた**。

**切り出し先の提案**: `tmux-probe-requires-socket-isolation.md` へ 1 行。

> 🚨 **隔離を環境変数 1 つに預けるなら、その変数が空 / 不在のときの行き先を実測する。**
> `TMUX_TMPDIR` は空・不在・未設定のいずれでも `/private/tmp/tmux-<uid>/`（= 本番）へ
> フォールバックする（実測 2026-09-11）。**破壊的コマンドの側にも、隔離と独立した
> 名前ベースの拒否を置く**（`default` を最初に弾く）。

🚨 **サブエージェントに破壊的なテストを走らせるときは、渡す環境変数が実在するかを確認させる。**
発火させたのは私が起こした 4 周目レビューのサブエージェントで、`TMPDIR=/tmp/a4rv/y`（不在）を
渡していた。指示に「`tests/tmux/test_reap_orphan_servers.sh` は実行するな」とは書いたが、
`test_socket_cleanup.sh` の直接実行は止めていなかった。
