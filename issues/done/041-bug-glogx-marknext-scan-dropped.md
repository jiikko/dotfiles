# glogx: `n` の next/ 移動が、スキャン飛行中だと一覧へ反映されない

起票日: 2026-08-13

issues viewer の `n`（次にやる目印 = `next/` へ実ファイルを移動）は、移動後に `scanCmd` を返して
一覧を取り直す。ところが `scanCmd` は single-flight で、**既にスキャンが飛んでいると `nil` を返す**。
その結果「実ファイルは動いたのに一覧は旧位置を出し続ける」窓ができる。

## 発火条件

1. 何らかの再スキャンが飛んでいる（`v.scanning == true`）。外部編集の自動反映が入ってからは、
   Claude Code が issue を書くたびに再スキャンが走るので珍しい状態ではない
2. その最中に `n` → `y` を打つ
3. `issues.MoveToSubdir` は成功し「1 件 next へ移しました」のトーストが出る
4. しかし `scanCmd` が `nil` を返すため取り直しが走らない。**しかも飛行中のスキャンは移動より前に
   開始されている**ので、その結果が届いても移動は反映されない
5. 復帰は fsnotify の次周期（debounce + 指紋の安定確認）待ち。fsnotify が無音な環境
   （NFS 等。`issues_watch.go` が自ら警告している）では保険のポーリング周期まで残る

## 何が問題か

- 「操作は成功した」とトーストで宣言しながら、画面は操作前の状態を出し続ける。viewer が最も
  嫌う「確信を持って嘘をつく」型
- 旧位置を指したままの行に対して続けて操作できる。`e`（エディタ）は実体確認で弾かれるように
  なった（`editCmd`）が、`y`（パスをコピー）は消えたパスを渡す
- `n` は toggle なので、旧位置の行に再度 `n` を打つと「戻す」向きの判定がカーソル行の状態で
  決まる。ここが実体とずれていると、意図と逆の向きに動く可能性がある（未検証）

## 関連コード

- `src/glogx/issues_view.go` の `scanCmd`（single-flight の本体）と `markNextKey`（移動後に
  `scanCmd` を返す側）
- `src/glogx/issues_watch.go`（fsnotify の debounce と保険のポーリング）

## 対応案

single-flight 自体は「`i` / `r` の連打で同じ探索のゴルーチンを積まない」ための正しい仕組みなので
外さない。**「自分がファイルを動かした後の取り直し」を落とさない**形にする。案:

- **A: 再予約フラグ**。`scanning` 中に取り直しが要求されたら `rescanPending` を立て、飛行中の
  スキャン結果を `receive` した直後に 1 回だけ再スキャンを張る。write 操作（`n` の移動）だけでなく
  「自分の変更後の取り直し」全般に効く
- **B: write 経路だけ single-flight を貫通**。`markNextKey` からは強制スキャンを使う。単純だが、
  貫通経路が増えると single-flight の意味が薄れる

A を推す（貫通の穴を増やさず、要求を 1 回に畳める）。

## 受け入れ条件

- `scanning == true` の最中に `n` → `y` を実行しても、飛行中スキャンの完了後に取り直しが走り、
  一覧が移動後の位置を出す
- 上を固定するテスト（`scanCmd` が nil を返す状況を作り、`receive` 後に再スキャンの Cmd が
  出ること）。⚠️ 変異（再予約を消す）で red になることまで確認する
- 連打で再スキャンが 2 回以上積まれないこと（single-flight の目的を壊していない）

## 補足

`e`（エディタ）側の実害は commit `132cc81` で閉じてある（起動前に `os.Stat` で実体を確認し、
無ければ開かずに取り直す）。本 issue は「一覧そのものが古いままになる」側の穴で、そちらとは別。
