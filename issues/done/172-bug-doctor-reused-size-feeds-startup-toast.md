# 172 bug: 再利用した計測値がトーストの材料に乗り、実体が消えても最大 1 時間「解放できます」と言い続ける

起票日: 2026-09-02
重要度: **P3**
関連: [issues/163](163-audit-doctor-implementation-red-team.md) (体 2) / [issues/148](148-feat-glogx-doctor-disk-diagnosis.md) (「追記」のスキャンのコスト = `Reuse` / 「トースト」)

## 対象

`src/glogx/doctor_view.go` の `receiveDisk` → `saveCache(*rep)` (`rep.Total` は Reused 分を含む) / `doctorReuseFrom`

## 何が起きるか

issue 148 は「再利用中に実体が変わっていれば表示は古い (最大 1 時間)。行の注記で分かる形にしてある」を許容と書いたが、
**その古い値がトースト用の `doctor-disk.json` にも書き込まれる**。トーストには注記が無いので、
ユーザーには「消したのにまた同じ量を消せると言ってくる」ようにしか見えない。

さらに悪いのは、トーストは**次に doctor 画面を開くまで更新されない**こと。「開けば直る」が 1 時間効かない。

## 再現手順 (実証済み。worktree の demo test で Total=20GB / toast に 20.0GB を確認)

1. T0: doctor を開いて完全走査。DerivedData が 20GB (計測 5.7 秒 → 重いエントリとして再利用対象になる)
2. T0+10m: 手で `rm -rf ~/Library/Developer/Xcode/DerivedData/*` する
3. T0+20m: doctor を開く。snapshot の 5 分 TTL は切れているので走査は走る
4. DerivedData は「計測から 1 時間以内 + 前回 2 秒以上」なので**再利用**され、20GB の行が出る
5. 完了時に `saveCache` が走り、`doctor-disk.json` の Total が 20GB に**更新される**
6. 次回 glogx 起動時のトースト: 「20.0GB 解放できます (Xcode 20.0GB)」

## 対応案

どちらか:

- Reused を含む完了では `doctor-disk.json` を更新しない (前回値を維持する)
- `doctorDiskCache.Entries` に reused フラグを持たせ、トーストの合計から除外するか注記を添える

前者が単純。トーストは「最後に実測した値」を出す方が意味的にも正しい。

- [ ] 変異検証: 除外を外すとトーストに再利用値が乗ることを確認する
## 対応 (2026-09-03、commit `6bc006c1`)

予約セッション (05:00) が worktree で実装したが未コミットで終了していたため、後続セッションが
差分を検証してから master へ当てた。**予約セッションの「変異検証済み」の主張は証拠に数えず、
master 上でやり直した。**

**修正した。** `doctorCacheFromReport` (`src/glogx/doctor_cache.go`) が **Reused (今回実測していない)
エントリの `Size` をトーストの材料にしない**。代わりに前回キャッシュの同じ ID の実測値を引き継ぐ
(無ければ持たない)。表示文言だけは今のカタログに合わせる。

対応案の「前者 (Reused を含む完了では書かない)」は**採らなかった**: `doctorReuseFrom` の 1 時間は
エントリごとに実測でリセットされるので、重いエントリが 2 件以上あると「常にどれか 1 件が再利用中」
が持続し、**キャッシュが恒久的に凍結する** (予約セッションの敵対レビューが再現: 20 分おきに 6 時間
開いても一度も更新されず、軽いエントリが 1GB → 100GB でも反映されなかった)。エントリ単位でマージする。

引き継ぎには上限 `doctorCarryTTL = 24h` を置いた。無期限だと Esc の連続で一度も検証されない
エントリが残り続ける。

### 変異検証 (master 上、2026-09-03)

Reused エントリを実測扱いで `put` する (= 除外を外す) → `TestDoctorSaveCacheKeepsLastRealMeasurement`
が red。復元で green。

## 敵対的レビューの経緯 (sonnet / read-only / 6 周、2026-09-03)

**3 周連続で「凍結」欠陥が形を変えて再発した**ので、その都度設計をやり直した。commit `6bc006c1` は
その 6 周目時点の形。

| 周 | 実測された欠陥 | 対応 |
|---|---|---|
| 1 | ガードが one-shot latch になり、1 エントリが恒久的に測れない Mac でキャッシュが凍結 (5 回連続の走査で 45GB / failed=0 のまま動かず) | 時間で区切る形にした |
| 2 | その時間の**起点が誤り**。「前回の完全結果の古さ」は「今回の結果が途中経過か」と無関係で、doctor をたまにしか開かない普通の運用が丸ごと無保護に (3 時間前の 45GB が「開いて即 Esc」の 1MB で潰れた) | 時間軸を捨て、不完全さの種類ごとに扱いを分けた |
| 3 | 「Reused があれば書かない」が staggered reuse で恒久凍結 (20 分おきに 6 時間・18 回開いても一度も更新されず、軽いエントリの 1GB → 100GB が反映されない) | **エントリ単位の差分マージ**へ (レビュワーが根本原因として挙げた形) |
| 4 | partial の洗い替えで、走査が届かなかったエントリと Failed 件数が消える (`failed=1` → `failed=0`) | partial は前回の記録に重ねて書く |
| 5 | 重ねるだけだと**無期限に延命** (10 回連続で書き込みが成功しても 44GB が一度も減衰せず) / partial ガードが冗長かつ矛盾 / 並び替えを守るテストが無い | `doctorCarryTTL` を導入 / ガードを撤去 / テスト追加 |
| 6 | (実施中。結果が出たら追記する) | |

採用 12 件 / 却下 0 件。各周で**ケース名ごとの pass/fail** まで確認してもらい、vacuous な assert を
2 件潰した (① `?` のケースが escape 集合の変異で緑のまま残る形 ② ガードの副作用で偶然 green に
なっていた既存テスト)。

🚨 **この 6 周から得た教訓**: 「消す / 消さない」を**結果全体の二値**で切り替えるたびに、切り替えた側の
失敗モードが形を変えて再発した。落ち着いたのは**エントリ単位**で「今回実測したか / 前回の記録を
どこまで引き継ぐか」を決める形にしてから。同種の「キャッシュを更新するかどうか」の設計では、
最初からエントリ単位を疑ってよい。
