## 1. 変異を 2 回当て直した — 「red でも緑でもない」を最初に red と読みかけた

`tests/issues/test_issue_numbers_unique.sh` の変異検証で、最初に当てた 2 本が

- `sed` でガードの行を削除 → 構文が壊れて **rc=2**
- `uniq -d` を無意味な式に置換 → 壊れ方が不正で **rc=1 のまま**

になった。このとき判定を「rc が変異前と違うか」で書いていたため、**rc=2 を「✓ 素通り =
防御が効いている」と表示してしまった**。実際には「変異が壊れていて何も測れていない」であり、
`mutation-verify-new-tests.md` が言う第 3 の結果 (`<変異がビルド不能>`) だった。

気づけたのは出力を読んだからで、判定ロジックは間違ったままだった。直した形は
「`bash -n` で構文が通ることを先に確認 → rc=0 かつ変異前が rc=1 のときだけ ✓」。

**切り出し先の提案**: `_claude/rules/mutation-verify-new-tests.md` の手順 1.5 は既に
「変異がビルドできたことを確認する」と書いてあり、ルール自体は正しい。足りなかったのは
**判定式を「rc が変わったか」で書かない**という一段細かい話。ルール本文に 1 行足すか、
却下か。個人的には足す価値があると思う (「rc が変わった」は 3 値を 2 値に丸める典型で、
同じルールが別所で戒めている形そのもの)。

## 2. 「2 つとも漏れている」と一括で言ってしまった (実際は片方が分岐依存)

`ee5e2b7` の報告で「同じ Visual 漏れが `LspSignatureActiveParameter` と `SnippetTabstop` にも
及ぶ」と書いたが、issue 134 を書くために実測したら **`LspSignatureActiveParameter` は 256色
(retrobox) 分岐だけ**で、truecolor (gruvbox) 側は `Search` (reverse) を独自に持っていて無傷だった。

原因は、`Visual` に link しているグループを **1 回の `nvim_get_hl` 走査 (retrobox 側だけ) で
列挙して、そのまま両分岐の話として書いた**こと。同じセッションの中で「colorscheme 分岐で
`LspReferenceTarget` の link 先が違う」ことを既に踏んでいたのに、隣の項目に適用しなかった。

**切り出し先の提案**: ルールにするほど一般的ではない。`docs/theme-colors.md` に
「link の解決は colorscheme ごとに違うので、両分岐で採ること」を 1 行足すのが妥当か。
あるいは却下 (テスト側が両分岐を回す形になったので、次に同じ判断をする人は分岐差に気づく)。

## 3. 番号衝突が同日に 2 件出た — write 時に検査すれば両方止まった

> 2 度書き直している。初稿「一声かけなかったのが根」→ 2 稿「番号は前に決まっているので
> write 時の検査では遅すぎる」→ 本稿。2 稿の結論は**誤り**で、並行セッション
> (dotfiles-87) の反証と git の実測で覆った。初稿の実測表にも数字の誤りがあった
> (schedkeys 側 127 の作成を `7a2254d` 09:18 としていたが、実際は `74ec363` 08:48)。

`acc5673` で**事後**の検出 (テスト) は入れた。**事前**の導線は `issues/README.md` の
「番号を取る前に一声かける」だけで、これは人間 (と Claude) の規律に戻っている。
衝突の解消コストは「参照の張り替え」か「改番」のどちらかを必ず払う形で、事後検出は
**払うべき額を教えてくれるだけ**で額そのものは減らさない。

### 実測 (git、2026-08-29 に採り直し)

| 番号 | 2 件の作成 | 作成の間隔 | 衝突成立 → 解消 |
|---|---|---|---|
| 133 | `35172a9` 21:44 / `d470d15` 21:47 | **3 分** | 21:47 → `7158fca` 23:04 = **1:17** |
| 127 | `c14a632` 07:33 / `74ec363` 08:48 | **1 時間 15 分** | 08:48 → `56f377b` 23:09 = **14:21** |

**(a) 2 本目を書いた時点で、1 本目は既に tree にコミット済みだった (両方)。**

```
git ls-tree -r --name-only d470d15^ -- issues/ | grep 133-
  → issues/133-human-verify-tmux-key-guide.md      (133 の 1 本目が見えている)
git ls-tree -r --name-only 74ec363^  -- issues/ | grep 127-
  → issues/127-human-verify-glogx-width-model.md   (127 の 1 本目が見えている)
git merge-base --is-ancestor c14a632 74ec363       → 祖先 (同じ履歴上)
```

したがって **write の瞬間に検査すれば、どちらの衝突も発火して止められた**。
番号が頭の中でいつ決まったかは関係ない — **実体化するのは write の瞬間**であり、
その時点で相手のファイルは既に見えている。

**機序** (dotfiles-87 の transcript 由来。git では裏が取れないので出典を明記する):
133 側は「132 を起票する直前に 1 回だけ `ls issues/*.md issues/done/*.md | ...| tail -3` を
走らせて最大 131 を得た → 132 を書いた → **133 は再走査せずセッション内でインクリメント**」
だった。**同時走査ではなく、走査が 1 回きりで古くなった**形。127 の 1 時間 15 分差も同じ
機序なら矛盾なく説明できる (127 の 2 本目が誰かは特定できていないので断定しない。
dotfiles-87 は `src/schedkeys` を触っていないという間接証拠のみ)。

**(b) 検出までの時間が 11.2 倍違う。** 133 は `issues/` 直下に並ぶので目に入ったが、127 は
片方が `issues/done/` にいて**視界から外れていた**。この差は声かけでは説明できず、
**「検出器が無い」+「ディレクトリを跨ぐと隠れる」**が効いている。

→ `acc5673` の検査を**ディレクトリ列挙ではなく `find -maxdepth 2` で掘る**形にしたのは、
まさにこの「14 時間隠れた形」を狙っている。変異検証で `-maxdepth 1` にすると 127 の形
(直下と `done/` の跨ぎ) だけが rc=0 へ素通りしたのは、その設計判断が単独で効いている証拠。

**切り出し先の提案**: 新規 issue。**write を止める形**にすること (警告では機序が閉じない —
セッション内インクリメントは「走査しない」ことが本体なので、走査を促すメッセージは届かない)。
`_claude/hooks/deny-bare-tmux-kill.sh` と同型の PreToolUse hook が候補。
🚨 **`paths:` 系の条件ロードは Write では発火しない**ことが 2026-08-27 に実測されている
(root の `CLAUDE.md` に記載) ので、hook 側でパスパターンを見る必要がある。
拒否だけでなく「空き番号を提示する」まで入れると、止められた側が次に何をすればよいか迷わない。

## 4. `make test` を全体で回せなかった (並行セッションの中途状態)

並行セッションが `Makefile` / `_zshrc` / `zshlib/` / `.github/` / tests 4 本を編集中だったため、

範囲を絞って回し、そのことを報告した。

これは運用としては正しく回ったが、**判断の根拠が「git status を見て気づいた」という属人的な
もの**だった。セッション開始時は clean で、途中から他セッションの変更が現れた
(CLAUDE.md の「並行作業者がいるときの worktree 退避」が想定している状況そのもの)。
今回は worktree へ移らず、pathspec commit + 変異は使い捨て worktree、で凌いだ。

**切り出し先の提案**: 却下。CLAUDE.md の既存ルールで足りており、実際そのとおりに動けた。
強いて言えば「共有ツリーで並行作業者を検出したら、全体テストの結果は自分の変更の証拠に
ならない」は `verify-execution-not-just-exit-code.md` の親戚だが、新ルールを足すほどではない。

## 6. 衝突の当事者を事後に特定できなかった

項目 3 で「127 の 2 本目は誰か」を追ったが、**特定できずに終わった**。いま schedkeys 群
(`70ed815` / `79e2453` / `74ec363` / `7a2254d` / `b4d50fc`) を自分の作業だと名乗っている
セッションが 1 つも無い。dotfiles-87 は指示リスト (101 / 124 / 111 / 109 / 103) と自分の
コミットが 1 対 1 で対応し schedkeys を含まないと言い、かつ compact 済みで当時の詳細を
復元できない。こちらも別作業をしていた。

特定を阻んだもの (実測):

- `issues/audit-log` は 4 列 (日付 / タイプ / モード / issue パス) で、**実行主体の列が無い**
- git の author は全コミットで同一 (`jiikko <n905i.1214@gmail.com>`)。**コミットにセッションの
  識別子が無い**
- 同じ時間帯に別セッションのコミットが交互に積まれている (07:10〜09:47 の 9 本が
  schedkeys 系と dotfiles-87 の担当分で入り混じっている)

候補は「第 3 のセッションがいた」「dotfiles-87 の compact 前の作業で本人が復元できない」の
どちらかで、**どちらかは決まらない**。

これは番号衝突と同じ根 — **並行セッション間の調整が、その場の記憶と申告に依存している**。
今回それが機能したのは `SendMessage` で互いに名乗り合ったからで、記録としては残らない。

**切り出し先の提案**: 却下 (記録として残すに留める)。解決するなら commit trailer に
セッション識別子を入れる等になるが、全コミットの形式を変える割に、得られるのは
「事後の犯人探し」がしやすくなることだけで釣り合わない。番号衝突の実害は項目 3 の
write 時検査で閉じるので、そちらを先にやる。**この節は「特定を試みて失敗した」記録**であり、
次に同じ問いを立てる人が同じ調査を繰り返さないために残す。
