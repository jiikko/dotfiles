## 反省

### 1. issue 番号を採番してから push するまでに時間を空け、衝突した

`244` を書き上げてから push しようとしたら、その間に別セッションが同じ `244` を push していた
（`aa9014ce`）。改番（244 → 246）と参照の直し、commit message の食い違いの説明で 1 commit 余計に使った。

- **規範は既にある**（`_claude/rules/worktree-per-session.md` の「issue 番号は採番したら即 push する」）。
  守れなかった理由は「本文を書き上げてから push したい」という気持ちで、**空ファイルで番号だけ
  押さえる**のが正しかった
- 🚨 **番号だけ先に押さえられなかった構造的な理由もある**: push はブランチ単位なので、
  実装 commit が未検証（make test 前）の状態では issue だけを飛ばせない。今回は
  「実装を先に commit → issue を採番 → push」の順にしたため、採番から push まで
  make test 1 回ぶん（約 7 分）空いた
- **切り出し先の提案**: `worktree-per-session.md` の該当項に「本文は後でよい。空ファイルで
  番号だけ押さえて push する」「実装が未検証で push できない時間帯は、採番も遅らせる（先に
  採番して抱えると衝突する）」の 2 行を足す。**新規ルールは立てない**（発動点は既存項と同じ）
- 🚫 **判断（2026-09-04、ユーザー）: 却下。ルールは変更しない**。
  理由は「**衝突しても後から降り直せばよい**」。実際、今回の改番は 1 commit（ファイルの rename と
  参照 3 箇所の書き換え）で閉じており、事前に規律を足して毎回「空ファイルで番号を押さえる」手間を
  払うより安い。`worktree-per-session.md` の「issue 番号は採番したら即 push する」は現状のまま残す
  （**それを守れなかったときの損失が小さい**ことが今回分かった、が結論）

### 2. 変異を perl で当てて壊し、「全テスト red」を変異の検知と誤読しかけた

絵文字を含む置換を `perl -0pi -e '…\x{1F6AB}…'` で当てたところ、`Wide character in print` の
警告とともにファイルが壊れ、**変異と無関係なテストまで全部 red** になった。
`sed` で当て直したら、狙ったテスト 2 本だけが red になった。

- **規範は既にある**（`mutation-verify-new-tests.md` の手順 1.6「変異の diff を目視し、意図した
  箇所だけが変わっていることを確認する」）。今回は**出力の tail だけ見ていて先頭の警告を見落とした**
- 🚨 この形の怖さは「**red は出る**」こと。ビルドは通る（手順 1.5 では捕まらない）ので、
  「変異を検知した」と読んで先へ進める
- **切り出し先の提案**: `rules-rationale/mutation-verify-new-tests.md` に実例として追記。
  ルール本文は既に手順 1.6 を持っているので**本文は変えない**

### 3. worktree の未コミット変更で rebase が 2 回止まった

`git rebase origin/master` が `cannot rebase: You have unstaged changes` で止まり、
先に commit する順序に組み替えた。`git stash` は禁止なので選択肢は「commit してから rebase」しかない。

- **提案なし**（規範どおりに動いた結果で、コストも小さい）。ただし
  「レビュー中はファイルを書き換えない」と「rebase したい」が競合するので、
  **レビューを投げる前に rebase を済ませる**のが順序として正しかった

- 「commit の author では持ち主を特定できない（全セッション同じ author）」ことも共有された

### 7. 「同じ Outcome でも、いつ表示されるかで語の意味が変わる」に独立に 2 回当たった

同じ日に、**私（242 の P3-1）と別セッション（246）が独立に同じ壁**に当たった。

- **私**: 結果画面の語（`🚫 触れず` = 実行したが触らなかった）を確認画面（下見）へ流用したら、
  直下に出る理由「いまは対象外です: …」と 1 行の中で矛盾した。一覧と同じ `🚫 対象外` へ戻した
- **246 の担当**: 中断の語を DryRun と実削除で 1 つの定数に寄せたら、下見の結果は**その直後に
  確認画面になる**ため「このエントリには触っていません」が「この行は消えない」と読める形になった。
  語を分けて「消してよいかを確認できていません」にした

どちらも「**語の出典を 1 箇所に寄せる**」という正しい原則を適用した結果、**表示位置の違いを潰した**もの。
どちらも敵対的レビューが見つけている（変異検証は両方とも全部 red で通っていた = 自分が想定した
不変条件しか試していない）。

**確かめ方**（両方で共通に効いた形）: その表示位置で**語の直下に出る理由文と語が矛盾しないか**を、
実装と突き合わせる。

**切り出し先の提案**: 発動点は「**結末語・状態語を新しい表示位置へ流用しようとした瞬間**」で、
既存ルールに同じ発動点のものは見当たらない（`comment-no-restate-enforced.md` は出典の一元化を
扱うが表示位置の話ではない）。ただし本文 1 節で足りる規模なので、新規で立てるか
`no-mixed-width-columns-in-terminal-ui.md` の「端末 UI の語彙」系へ足すかは判断が要る。
**CLAUDE.md の「retro の切り出し先は既存ルールへの追記を既定にする」に照らすと後者寄り**。
