# `os.Exit` が defer を走らせないため、見捨てた goroutine の probe / tmp が残る

起票日: 2026-09-18
カテゴリ: bug / priority: **low**
対象: `src/lockman/lock.go` の `serverNow` (probe) と `tryPlace` (tmp)、`src/lockman/cleanup.go` の `sweepDir`
出典: [issue 362](../362-bug-lockman-abandoned-timeout-goroutine-leaves-lock.md) の敵対的レビュー 3 周目 (観点「並行・中断」) のぼやき
反証レビュー: 未実施。**数値は起票者の実測**（下表）

## 問題

`serverNow` は probe を、`tryPlace` は tmp を作り、どちらも **goroutine 内の `defer` で自分で消す**
設計になっている。しかし `--io-timeout` で見捨てられた goroutine は `os.Exit` と競走しており、
**`os.Exit` は defer を走らせない**ので、負けた分がそのまま残る。

362 の本文が「④ 書きかけ (`tmp/<token>.json`) は数えなくてよい」としていた根拠は
「`defer os.Remove(tmp)` が見捨てられた goroutine の中でも走る (goroutine が完走すれば消える)」で、
**「完走すれば」の条件が満たされない割合が実測で無視できない**、というのが本 issue。

## 実測 (2026-09-18)

`--io-timeout 3ms`、8 並行 × 40 ラウンド = 320 起動、毎回新規 dir。
🚨 **計測には `minIOTimeout` を 1ms へ下げたビルドを使った** (製品の下限は 100ms)。
出荷バイナリはローカルの速い FS では timeout が発火しないため、この現象を再現できない
(実測: 出荷バイナリ + `--io-timeout 100ms` で 40 起動 / 残骸 0)。

| 版 | probe 残骸 | tmp 残骸 | lock 残骸 |
|---|---|---|---|
| 362 の修正前 (`a75ffe3d`) | 24 | 148 | **73** |
| 362 の修正後 (`e8fe1374`) | 24 | 135 | **0** |

- **この件は 362 の変更以前からの性質**で、悪化していない (probe は同数、tmp は微減)
- lock の 73 → 0 は 362 の成果であって本 issue の対象ではない

## なぜ気にするか (掃除の担当が居るのに)

残骸の担当は `Cleanup` の `sweepDir(tmp, 1h)` / `sweepDir(probe, 1h)` で、**通常はこれで足りる**。
気にするのは次の 2 点:

1. **残骸が出る条件と、掃除が効かない条件が同じ**。残骸は「I/O が `--io-timeout` を超えた」ときに
   出る = マウントが遅いとき。その同じマウントで `CleanupTimed` も同じ期限で切られるため、
   **最も残骸が出る場面で、最も掃除が届かない**
2. **`sweepDir` は 1 時間より新しいものを消さない**。高頻度で呼ぶ運用 (av1ify のような per-file の
   ロック) では、1 時間あたりの残骸が回収より速く積む状況がありうる

## 全数勘定 (2026-09-18 時点)

見捨てられた goroutine が残しうるもののうち、**362 が閉じたもの**と**本 issue のもの**:

| 物体 | 362 の扱い | 本 issue |
|---|---|---|
| lock 本体 | 閉じた (実測 73 → 0) | 対象外 |
| `tmp/<gen>.takeover` (claim) | 閉じた | 対象外 |
| `tmp/<gen>.takeover.<nanos>` (mark) | ほぼ閉じた (7 → 1) | 対象外 |
| **`probe/<token>`** | ④ として対象外とした | **本 issue** |
| **`tmp/<token>.json` (書きかけ)** | ④ として対象外とした | **本 issue** |

## 対応の候補 (未決。着手前に再評価すること)

- **何もしない**。残骸はロック dir の排他を 1 mm も壊さない (名前が一意で、誰も参照しない)。
  1 時間後に sweep が拾う。**これが既定の判断でよいと思われる**
- `sweepDir` の保持期間を probe / tmp について短くする。🚨 ただし `minRetention = 10 分` の
  下限があり、これは「飛行中の他プロセスの probe を消さない」ための下限なので、
  **下げるなら飛行中との区別を先に作る**必要がある
- 残骸を出さない構造にする (probe を作らずサーバ時刻を得る / tmp を使わず書く)。
  🚨 `adversarial-review-own-safeguards.md` §0-A の「作らずに済む構造」に当たるが、
  **probe は「サーバの時計を読む」唯一の手段**として選ばれた設計なので、代替の検討から要る

## 2026-09-18 実測: 積むのか (この issue のゲート)

### 掃除の機構 (コードで確認)

- `sweepDir(tmp|probe, scratchRetention = 1h)` — **1 時間より新しい残骸は消さない**
- `cleanupDue()` は `cleanupInterval = 10 分`のレート制限。打刻 (`.cleanup_at`) の mtime で判定
- **失敗したら打刻しない** (`len(res.Errors) == 0` のときだけ `stampCleanup`)。
  つまり掃除が失敗し続けるとレート制限が死に、acquire のたびにフル走査する

→ 定常状態の残骸 ≈ **生成率 × 1 時間**（sweep が完走する限り）。

### ① 回収の担当は実際に機能する

1 時間超に打刻した残骸 1000 件 (tmp 500 / probe 500) に `cleanup` を当てて
`removed=1000 errors=[]`、残り 0 件。**「担当が居る」は実測で成立している**。

### ② 生成率 (同じ dir を使い続ける形で測った)

| 条件 | 起動 | rc≠0 | 残骸 | 生成率 |
|---|---|---|---|---|
| 直列 / `--io-timeout` 3ms | 200 | 200 | 5 | 0.025 件/起動 |
| 直列 / 5ms | 200 | 200 | 5 | 0.025 件/起動 |
| 直列 / 8ms | 200 | 4 | 1 | 0.005 件/起動 |
| **8 並行・同一 dir / 3ms** | 400 | — | 729 | **1.823 件/起動** |
| **直列 / 100ms (製品の下限)** | 200 | **0** | **0** | **0** |
| **8 並行・同一 dir / 100ms (製品の下限)** | 400 | — | **0** | **0** |

🚨 **製品が受け付ける最小の `--io-timeout` (100ms) では、並行でも残骸は 0 件**。
ローカルの速い FS では timeout が発火しないため。**残骸は「マウントが実際に遅い」ときだけ出る**。
3〜8ms の行は `minIOTimeout` を 1ms へ下げた計測用ビルドの数字で、製品では設定できない。

### ③ 積んだときのコスト (定常状態の走査コスト)

tmp/ に 1 時間未満の件数 K を置いて `cleanup` の所要を測る (K 件は掃除対象外 = 走査だけ):

| tmp/ の件数 | cleanup (ms) | acquire (ms) |
|---|---|---|
| 0 | 22 | 31 |
| 500 | 24 | 29 |
| 2,000 | 29 | 32 |
| 10,000 | 52 | 39 |
| 50,000 | 178 | 42 |

Go の起動が約 20ms 含まれるので、走査自体は **約 3.2µs/件** (ローカル APFS)。

### ④ 暴走するか (この issue の核心)

暴走の条件は「掃除が `--io-timeout` を超えて失敗 → 打刻しない → 毎回フル走査 →
さらに遅くなる」の正のフィードバック。**入口は掃除が期限を超える件数**。

- ローカル APFS: 走査が 100ms (製品の下限) を超えるのは **約 3 万件**
- 定常状態を 3 万件にするには、**劣化した状態で毎時 1.6 万回以上** acquire する必要がある
  (1.823 件/起動 × 16,000 ≒ 29,000)
- 実運用 (av1ify のような per-file のロック) の桁ではない

🚨 **SMB では未実測**。走査の 1 件あたりコストが桁で上がれば入口の件数も桁で下がる。
**trigger**: SMB 共有で「acquire が遅い」「cleanup のエラーが続く」報告が出たとき、
③ の表を SMB で採り直す。

## 2026-09-18 の判断: **何もしない**

理由 (上の実測):

1. **製品の設定範囲では残骸が出ない** (100ms で並行 400 起動・0 件)
2. 出るのは劣化時だけで、そのとき**回収の担当は実測で機能している**
3. 暴走の入口 (約 3 万件) は実運用の桁から 3 桁離れている

保持期間を縮める案は採らない — `minRetention = 10 分`は「I/O が返らないまま飛行中の
他者を巻き込まない」ための下限で、縮めるなら**飛行中との区別を先に作る**必要がある。
得られるものは上の勘定どおり小さく、失うものは二重取得の側にある。

**この判断の根拠はコード直近にも残した** (`serverNow` / `tryPlace` のコメント)。

## 2026-09-18 の副産物: `link(2)` が使えない FS では tmp の書き込みが丸ごと無駄

調査中に見つけた**別の問題**。`tryPlace` は必ず `writeFileSync(tmp)` (fsync 込み) してから
`link(2)` を試すが、**fallback 枝 (O_EXCL) は tmp を 1 バイトも使わない** —
lock のパスを直接開いて同じバイト列を書く。

`lock.go` 自身が「macOS の smbfs では ENOTSUP になりうるので O_EXCL に落とす」と書いており、
**それが本番の経路**。つまり本番では毎回「fsync 付きの書き込み → 使わずに捨てる」が挟まる。

`tryPlaceLinkFn` を ENOTSUP 固定にしたビルドで測った (ローカル APFS、acquire の中央値):

| 版 | 中央値 |
|---|---|
| 現行 (tmp を必ず書く) | 32.3ms |
| 計測専用 (tmp を書かない) | **24.0ms (-26%)** |

🚨 **これは節約の上限**。計測版は「link を使わないと分かっている」前提で tmp を省いただけで、
**実装にはならない** (link の可否は試すまで分からない)。実装するなら可否の判定が要り、
その判定自体のコストと複雑さを勘定に入れる必要がある。SMB では fsync が往復になるので
差は開くはずだが**未実測**。

→ 残骸の出どころ (tmp) が本番では**そもそも不要**なので、この issue の候補
「残骸を出さない構造」の費用対効果が変わる。**別 issue へ切り出す**。

## 2026-09-18 反証レビュー: 結論は残り、**根拠は 3 つ崩れた**

観点「反証」の red team を通したところ、上の節の根拠が実測で否定された。
**「何もしない」という結論は覆らなかったが、書いた理由はほぼ全部差し替えになる。**

| 上の節の主張 | 判定 | 正しくは |
|---|---|---|
| 「掃除が効かないのは**遅いマウント**のときだけ」(「なぜ気にするか」①) | **誤り** | **滞留量だけで期限を超える**。ローカル APFS でも tmp/ が 1 万件あると `--io-timeout 100ms` の掃除が期限切れし、打刻しないのでレート制限が死ぬ (3 千件なら完走)。実測で再現 |
| 「暴走の入口は**約 3 万件**」(③ の走査コストから) | **1 桁誤り** | 走査だけを測っていた。**定常状態には必ず削除対象が含まれる**。削除を伴うと約 35µs/件 = 走査の 16 倍で、100ms を超えるのは**約 3 千件** |
| 「実運用の桁から **3 桁**離れている」 | **過大** | 上の訂正で **1〜1.5 桁**。1.823 件/起動なら劣化状態で毎時 1,650 回の acquire で届く |
| 「計測は走査コスト 3.2µs/件」 | **ハーネスの誤り** | 計測ハーネスが 1 反復あたり `python3` を 2 回起動しており、**2 回目の起動 (約 20ms) が測定値に混入**していた。Go の起動は 2.6ms。修正後は走査 2.1µs/件 |

### 実測し直した掃除コスト (ローカル APFS、中央値)

| tmp/ の件数 | 走査のみ | **削除を伴う** |
|---|---|---|
| 500 | 4.8ms | 16.3ms |
| 2,000 | 9.9ms | 70.2ms |
| **3,000** | 12.9ms | **95.1ms** ← 100ms の境目 |
| 10,000 | 35.3ms | 328.5ms |
| 30,000 | 91.9ms | 1,063ms |

### 滞留 1 万件・製品の下限 100ms・打刻を 20 分前にしたときの挙動 (実測)

| 回 | rc | tmp 残 | 打刻 | stderr |
|---|---|---|---|---|
| 1 | 0 | 7,451 | **されない** | `removed=0 errors=[I/O timeout]` |
| 2 | 0 | 5,019 | **されない** | 同上 |
| 3 | 0 | 2,564 | **されない** | 同上 |

**暴走はしない** (1 回あたり数千件は削れるので数回で排水される) が、そのあいだ
acquire ごとにフル走査し、stderr が鳴り続ける。3 千件なら 1 回で完走して打刻する。

🚨 **`removed=0` は嘘**。実際は毎回約 2,500 件削除している。`CleanupTimed` が期限切れ時に
部分結果を捨てるため → [issue 393](../393-bug-lockman-cleanup-timeout-discards-partial-result.md) へ切り出した。

## 2026-09-18 判断の差し替え: **何もしない (ただし理由が違う)**

当初書いた理由 (「製品の設定範囲では出ない」「暴走の入口が 3 桁遠い」) は上のとおり崩れた。
**現在の唯一の実運用経路の形**が正しい理由:

`zshlib/_av1ify_lock.zsh` は
1. ロックを **`~/.lockman/av1c/<key>/` = key ごとに別 dir** に置く (`_av1ify_lock.zsh:26,115`)
   → **滞留が 1 箇所に集まらない**ので、上の 3 千件に届く経路が無い
2. **`--io-timeout` を渡さない = 既定の 10s** → 残骸が出るにはまず 10s の I/O が要る。
   100ms を前提にした上の勘定は、実運用には当てはまらない
3. 置き場所は**ローカル HOME** (同ファイルが「これは同一マシン内の排他になる」と明記)

保持期間を縮める案を採らない理由は変わらない (`minRetention` の 10 分は飛行中の他者を
巻き込まないための下限)。

**再評価の trigger (差し替え)**: ①`--io-timeout` を既定より短くする運用が出たとき
②1 つの lock dir を共有する呼び出し元が増えたとき。
(旧 trigger「SMB で遅いと報告が出たとき」は**発火しない** — [092](092-human-verify-lockman-over-smb.md) が
「SMB 越しの lockman は当分使わない」というユーザー判断で閉じられているため)
