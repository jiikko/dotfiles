# glogx: viewer の「キー案内」と「幅上限」が複数箇所に散り、片方だけ古くなる

起票日: 2026-08-13

issues viewer にキーを 1 本足すと、**4 箇所を手で揃える**必要がある。揃え忘れても lint も
テストも通る（＝ドキュメントが静かに嘘になる）。

## 実測: キー 1 本の追加で触った箇所

2026-08-13 に `e`（issue をエディタで開く）を追加したとき、実際に編集が必要だったもの:

| 場所 | 何を持っているか |
|---|---|
| `issues_view.go` の `hint()` | 画面に出る 1 行の案内（本文モード / 一覧 / ピッカー / 番号入力の 4 モード分） |
| `options.go` の `--help` | viewer のキー一覧 |
| `src/glogx/README.md` | viewer のキー一覧（散文中） |
| `docs/issues-viewer-spec.md` | キーへの言及が多数（順序規約の根拠・選択対象の規約・再スキャンの表） |

このとき **spec とコード内 doc コメントに旧キー `v`・旧ツール名 `nvim` が 7 箇所残り**、
後続のレビューで指摘されて別 commit で直した。つまり「4 箇所を手で揃える」は実際に失敗している。

## もう 1 つ: 幅上限 84 が 3 箇所

`hint` は 1 行で、popup 実幅を超えた分は末尾から黙って切られる。その上限 `84` が独立に 3 箇所ある。

- `issues_view.go` の `hint()` のコメント（散文で「84 桁」）
- `issues_view_test.go` の `const popupWidth = 84`（幅テストが使う）
- `url_picker_test.go` の `issuesRenderOpts{width: 84}`（リテラル）

popup の実幅を変えたら 3 箇所を揃える必要があり、揃え忘れると「テストは通るが実機で末尾が切れる」
または逆に「実機は平気だがテストだけ落ちる」になる。

## 何が問題か（複雑性の観点）

単なる「重複」ではなく **強制手段が無いことが問題**。今あるのは:

- 幅: `TestIssuesViewHintFitsPopupWidth` が上限超過を落とす（強制あり）
- 案内キーと実際の割当の対応: `TestIssuesViewBodyHintAdvertisedEditorKeyWorks` が **`e` の枠だけ**を
  繋いでいる（2026-08-13 追加。それ以前は hint に**未割当キー** `z: nvim` と書いても全テストが
  green になることが mutation で実証されていた）。**`e` 以外のキーは今も未強制**で、
  `j/k/Space` や `p` / `u` の案内を割当と食い違わせても何も落ちない
- `--help` / README / spec との一致: 強制なし

`docs/issues-viewer-spec.md` は「hint が案内するキーが 1 つも案内どおりに動かない」事故を
既知の失敗モードとして明記しているのに、その不変条件がテストで固定されていない。

## 対応案

**A（推奨・小さい）: hint と割当の対応を全キーで強制する。**
`hint()` の文字列から `X: 説明` の `X` を抜き出し、各キーを本文モードの `handleKey` に流して
「反応がある（副作用 or 非 nil な Cmd）」を assert する 1 本を書く。⚠️ `j/k/Space` や `Enter/h/q` の
ような複合トークンの扱いを決める必要があるので、パースは hint 側の書式を規約として固定してから。

**B: 幅上限 84 を 1 つの定数にする。** `popupWidth` 相当を production 側に置き、テストとレンダラが
それを参照する。3 箇所のリテラルを消す。

**C（大きい・trigger 待ち）: キー表を 1 つのデータに寄せ、hint / `--help` / README を生成する。**
今は「4 箇所を手で揃える」だが、生成にすると 1 箇所になる。⚠️ ただし hint は幅の都合で
**意図的に一部のキーを案内しない**（`v` は別名なので出さない、一覧モードは幅が足りない等）ので、
単純な生成では表現できない。「案内する/しない」を表側に持たせる設計が要る。spec も散文で
キーに言及しているので生成対象にはできない。**次に viewer のキーを増やす作業が来たときの trigger 待ち**に
するのが妥当で、先回りでは着手しない。

A → B の順で入れ、C は trigger を待つ。

## 受け入れ条件

- A: hint が案内する全キーが本文モードで反応することを 1 本のテストが固定する。
  ⚠️ 変異（hint に未割当キーを書く / 割当だけ消す）の両方向で red になること
- B: `84` のリテラルが production 側の 1 定数に集約され、テストがそれを参照する
