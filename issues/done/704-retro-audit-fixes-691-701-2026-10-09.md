## どこで踏んだか

1. **変異が緑のまま通った (4 回)。どれも「観測が別のものに覆われていた」形**

   - 694: `walker.busy` から未取り込みを外す変異が緑。`Model.Busy` は walker と git の OR で、git の未取り込みが true を保って walker の退行を覆った
   - 696: places の opened の行の `\r` の判定を戻す変異が緑。同じテストでカーソルにも `\r` を入れていたので、場所ごと書かない分岐が先に効いた
   - 699: 入れ子のたびに span を歩き直す変異が、10 秒の hang guard の手前 (9.8 秒) で緑。入力の大きさを決めるとき、退行したときの所要を測っていなかった
2. **性能の直しが、直した入力の族とは別の形で旧より遅くなった** (699)。閉じない記法の 2 乗は直したが、中身を再帰で読み直すたびに表を作り直したので、
   入れ子のリンクでは旧の 2.4 倍・リンクの中の強調では 7 倍遅くなっていた。敵対レビューの 1 周目が実測で見つけ、2 周目も別の再帰の形
   (入れ子のたびに span を歩き直す) を見つけた。自分で測ったのは issue に書かれた入力の族だけだった
3. (局所) Write / heredoc でテストに書いた `‮` が文字そのものに化けて保存され、lint (bidichk) で気づいた。rule の既知の罠どおりで、
   `string(rune(0x202e))` に書き直して済んだ。新しい提案は無い

## 次に効きそうな改善 (提案。実行はユーザーの判断)

1. **観測が複数の源の OR・合計・最初に効く分岐でできているなら、源ごとに観測する。予算や上限で退行を見るなら、名指しする退行 1 件ぶんの
   増え (変異での差) が余裕より大きいことを確かめてから上限を決める** (1 の 4 回が全部この形)
   - 切り出し先: `_claude/rules-checklists/mutation-verify-new-tests.md` の「到達しているか」へ追記 (既にある「先に効く別の防御が影になる」の隣。
     あちらは分岐の順、こちらは観測の集約と余裕の大きさ)
2. **時間の上限 (hang guard) で 2 乗の退行を見る検査は、退行を戻した変異の所要を測り、上限の数倍になる入力の大きさにする** (1 の 699)
   - 切り出し先: `_claude/rules/avoid-wall-clock-assertions.md` の「判定の作法」へ追記 (「成功側と失敗側の桁差を実測して残す」の具体形。
     hang guard は合否の基準ではないが、退行の検出に使うなら同じ実測が要る)
3. **性能の直しは、旧実装と所要を比べる入力に、直した族のほかに入れ子・再帰・連結の形を必ず入れる** (2)。直すと、自分が触った経路
   (再帰のたびの作り直し・歩き直し) が新しい非線形の入口になる
   - 切り出し先: `_claude/rules/perf-claims-need-measurement.md` へ追記 (「経路を最後まで追ってから書く」の性能の直し版)
