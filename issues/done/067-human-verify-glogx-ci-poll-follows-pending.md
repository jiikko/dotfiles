# glogx: pending の CI を状況を問わず追い続けるかの動作確認

起票日: 2026-08-20
期限: 2026-08-23
種別: human
対象コミット: `ab56510` (feat(glogx): pending なコミットは状況を問わず追い続ける)

## なぜ人の目が必要か

`make test` は全 green で、変異検証も 8 種通してある。だが確認できていないのは
**「実際に GitHub Actions が走っている間、画面の表示が追従するか」**で、これはテストの
外側 (実 gh・実 CI・実時間) にしかない。旧実装は「pending を検知した時点でポーリングを
降りる」ため一覧の表示が固まっていた ([README](../src/glogx/README.md) の「実行中の CI を追う」)。

## 確認手順 (何を叩いて / 何が見えたら OK か)

1. 何かを push した直後に `glogx` を開く → **数秒で tip の CI が ● (pending) になる** (スピナーのまま固まらない)
2. **パネルを開かずに一覧のまま 3〜10 分放置** → **● が ✓ / ✗ に変わる** (旧実装ではここが固まっていた。本命の確認項目)
3. `Enter` で job パネルを開き、実行中 job の経過時間が 3 秒ごとに進む → `q` でパネルを閉じてさらに放置 → **閉じたままでも 1 の行が決着まで更新される**
4. 決着後に無駄に叩き続けていないこと: `gh api rate_limit --jq '.resources.graphql.remaining'` を決着直後と 5 分放置後で比較 → **減っていない** (減っていたらポーリングが止まっていない)
5. job パネルで `r` (失敗 job の再実行) → **30 秒以内にパネルの ✗ が ● に変わる** (rerun が GraphQL に映るまでの猶予が効いているか)

## 確認できたら

このファイルを `issues/done/` へ移動する (既読の唯一の出典はファイルの位置)。
2 か 4 が期待どおりでなければ `issues/` に残したまま症状を追記する。

## 未確認のまま残す条件 (期限内に CI が走らなかった場合)

期限を +3 日して残す。CI が走らない週は 1 の前提が作れないため、無理に別 repo で代替しない
(この repo の workflow 構成 = 1 push で複数 workflow 並走が確認対象に含まれる)。

## 結果 (2026-08-20)

ユーザー判断で **確認済み扱い**としてクローズ。🚨 上の手順 1〜5 を実際に走らせた記録は無い
(実 CI・実時間でしか観測できない項目のため)。したがって「実機で追従した」という証拠は無く、
根拠はテストと変異検証 (ab56510 / 8ca3015) までである。CI 追従の不具合が後で出たら、
未実施のこの手順から当たるのが最短。
