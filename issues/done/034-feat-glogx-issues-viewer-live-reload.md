# 034 feat: issues viewer を別プロセスの編集で即時更新する

issues viewer を開いている間に**別プロセス** (Claude Code / 別ターミナルの $EDITOR / git pull) が
`issues/*.md` を書き換えたら、一覧と開いている本文をその場で更新してほしい (ユーザー要望
2026-07-31)。今は `r` を押すまで古い内容を出し続ける。

viewer の仕様が最も嫌うのは「viewer が確信を持って嘘をつく」状態 (`reloadAfterEdit` の doc)。
自分で `v` (nvim) を叩いた編集はその経路で塞いだが、**別プロセスの編集は同じ嘘が残っている**。
Claude Code に issue を書かせながら viewer で眺める使い方では、こちらが主経路になる。

## 反映の機構は既にある — 足りないのは「変わったと気づく」ことだけ

`reloadAfterEdit()` (`issues_view.go`) が必要な処理を全部持っている:

- 開いている本文を読み直す (`v.open.ReadBody()`。`Body` は読み込み時の内容を握るため)
- 一覧を再スキャンする (`scanCmd`。`Issue.LoadMeta` は一度読んだら二度読まないので作り直しが必要)
- `receive` が安定キー (パス・タブ名) でカーソル・タブ・フィルタを引き直す
- `scanCmd` は single-flight (`v.scanning`) なので連続発火でゴルーチンが積まれない

つまり実装するのは**検出とトリガだけ**で、`reloadAfterEdit` を呼ぶ経路を 1 本増やす形になる。

## 検出の方針: viewer 表示中だけ mtime を見る (fsnotify を入れない)

推奨は **B (mtime ポーリング)**。

| | A: fsnotify | B: mtime ポーリング (推奨) |
|---|---|---|
| 依存 | 新規 dep (`fsnotify`) | 追加なし |
| 遅延 | ~即時 | ポーリング周期 (1s なら最大 1s) |
| 機構 | watcher の生成/破棄・イベントのバースト (エディタは tmp + rename で書く) の debounce・ディレクトリ追加の再登録 | tea.Tick の自己再アーム 1 本 |
| 失敗モード | watcher fd リーク・NFS で無音 | 取りこぼしなし (次の周期で必ず気づく) |

コストは実測で問題にならない: この repo の 32 ファイルを stat して **36µs**。1s 周期なら CPU への
影響は無視できる。読み直し (`Scan` + `LoadMeta` の N ファイル read) は**変化を検出した時だけ**走る。

人間の体感では 1s 以内の反映は「即時」で足りる (別プロセスの編集は自分の打鍵と同期しないので、
数百 ms の差は認識されない)。fsnotify の機構をこの遅延差のために抱えない。

### 実装の形

- **tick は autobuildWatch の型を踏襲する** (`autobuild.go`)。`spinnerActive()` に足して 12.5fps の
  フレーム tick を常時回すのではなく、**自分の周期 (1s) で自己再アームする独立チェーン**にする。
  viewer を閉じたら止める。🚨 フレーム tick に混ぜると「viewer を開いている間ずっと 12.5fps で
  起きている」= glogx が守ってきた「動くものがある間だけ tick を回す」設計を崩す
- 監視対象は 2 種類。**ディレクトリの mtime だけでは本文の書き換えを検出できない** (dir の mtime は
  create/delete/rename でしか動かない):
  - `v.dirs` の mtime → ファイルの追加・削除・`done/` への移動
  - `v.all` の各ファイルの mtime+size → 本文・front matter の書き換え
- 開いている本文は `v.open.Path` の mtime+size を見る (一覧の集合に含まれるが、本文だけ変わった
  ケースを最短で拾うため個別にも見る)
- **書きかけの検出を避ける**: mtime が動いた直後の 1 周期は読まず、次の周期で mtime が同じなら
  読む (エディタの tmp+rename なら atomic だが、`>>` で追記するツールもある)。あるいは
  「読んだ結果が壊れていたら次の周期で再試行」でもよい (`ReadBody` の失敗は現状も無視される)
- URL ピッカーを開いている間は反映を遅らせる (ピッカーは本文の URL 集合を握っており、下から
  差し替えると選択が別 URL に化ける)。drawer のアニメ中も着地まで待つ

### 実装しないこと

- **`v` (nvim) 経路の置き換え**: あちらは editorClosedMsg で確実に反映できるので、ポーリングに
  寄せる必要がない (即時性も上)。両方残す
- **viewer を閉じている間の監視**: 開いた瞬間に必ず `scanCmd` が走るので不要。閉じている間に
  tick を残すのは「動くものがある間だけ」の原則に反する

## 検証

- viewer を開いたまま別プロセスで `issues/*.md` を書き換え → 1s 以内に一覧の行・状態バッジが変わる
- 本文を開いたまま同じファイルを書き換え → 本文が変わり、`bodyOff` (スクロール位置) は保たれる
- 別プロセスで新規 issue を作る / `done/` へ移動する → 一覧とタブ件数が追従し、カーソルは
  同じ issue に留まる (パスで引き直す既存の規律)
- viewer を閉じたら tick が止まる (閉じた後に mtime を変えても何も起きない)
- 書きかけのファイル (途中まで書いた md) を掴んでも viewer が壊れない
- `make -C src/glogx test` / Bench (起動時間は無関係だが tick 周りを触るため確認)
