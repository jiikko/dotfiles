## 残っている 2 項目

### (a) 実機での fd / プロセスグループの観察

Go のテスト内では測ったが、**実機で `bin/glogx` を起動した状態での観察**が残っている。

- `lsof -p <glogx pid> | wc -l` を doctor の開閉 20 回の前後で比べる
- `pgrep -g <pgid>` で `Setpgid` 後の孫が cancel で消えることを実機で見る
- `brew doctor` (60 秒 timeout) を開いて即閉じ、**60 秒待たずに `ps` から消える**か

### (b) `bin/glogx` の起動時間の before / after

`Init` で `loadDoctorDiskCache` (ファイル 1 本読み) を足したので、受け入れ条件の
「起動時間が悪化しない」を実測で言えるようにする。単体は 26.5µs なので**悪化しないはず**だが、
[`perf-claims-need-measurement.md`](../../_claude/rules/perf-claims-need-measurement.md) に照らすと
「未実測」のまま「悪化しない」と書くのは避けたい。

- doctor を足す前の commit と現在で、起動〜初回描画を 10 回ずつ測って中央値を比べる
- 既存の Bench 経路 (`.github/workflows/bench.yml`) に乗せられるなら乗せる

## 着手の判断材料

**急がない**。(a) は Go のテスト側で「漏れていない」ことが既に確認できていて、実機観察は
その独立確認にあたる。(b) は単体の実測値から悪化しないと見積もれている。

🚨 ただし **④ (削除) を実装するときは (a) を先にやる**。削除は破壊的操作を新設するので、
「閉じた後に何が残るか」を実機で確かめていない状態で進めるべきではない
([`adversarial-review-own-safeguards.md`](../../_claude/rules/adversarial-review-own-safeguards.md) 節 1)。

## 対応 (2026-09-03) — (a)(b) とも実測した。**どちらも問題なし**

### (a) 実機での fd / 子孫プロセスの観察

隔離 tmux (`-L`) で `glogx` を起動し、doctor を実際に開いて測った。⚠️ **画面に「ディスク占有」が
出たことを確認してから計測する** — 起動直後は前回画面 (issues viewer) が復元されてキーを先に取るので、
`D` を押しただけでは開かない (最初の 3 回はこれで空振りした)。

#### 🚨 最初の観測は構造的に何も測れていなかった

`pgrep -g <glogx pid>` で子を数えていたが、**`runner.Exec` は `Setpgid: true` で子を
「自分自身の pgid」にする**ので、glogx のプロセスグループには最初から入らない。
「子 0 件」は漏れの不在ではなく、**観測手段の不在**だった (規範:
[`verify-execution-not-just-exit-code.md`](../../_claude/rules/verify-execution-not-just-exit-code.md)
「有無で結果が変わらない観測を証拠に数えない」)。親子関係 (`pgrep -P` の再帰) へ直して測り直した。

| 測ったもの | 実測 | 判定 |
|---|---|---|
| doctor 開閉 20 回の前後の fd 数 (`lsof -p`) | **76 → 74** (実際に開けたのは 19/20) | 漏れなし |
| 同 子孫プロセス数 | 1 → 0 | 漏れなし |
| スキャン中の子孫 (ピーク) | 2〜6 件。`ruby` (brew) / `simctl` / `bash` | 捕捉できた |
| 子孫の pgid | **pid == pgid** (54324/54324 等)。その子の `curl` が同じ pgid を継承 | `Setpgid` が効いている |
| 子が生きている状態で閉じてから消えるまで | **5 試行すべて 0.05 秒** | 60 秒 timeout を待たない |

⚠️ **1 度だけ 10.07 秒かかった試行がある** (改良前のハーネスでの 1/8)。改良後の 5 試行では
再現していないため原因は未特定。`du` が大きなディレクトリを走査中だった可能性がある。
**再現したら追う** (trigger: 閉じた後に doctor の子孫が数秒残るのを見たとき)。

⚠️ **2 回目以降の開閉ではスキャンが走らない** (キャッシュ再利用)。子を捕まえるには開いた後に
`r` を押す必要がある。これを知らずに測ると「子孫 0 件 = 漏れなし」と誤読する。

結論は `src/doctor/runner/runner.go` の `Setpgid` の直近にも残した (issue は移動するがコードは現場に残る)。

### (b) 起動〜初回描画の before / after

`cb832dc6`「D で開く doctor 画面」の親 (`b2f8ede1`) と HEAD でバイナリを建て、隔離 tmux で
「セッション作成〜画面が非空になるまで」を 10 回ずつ測った (同一 cwd = dotfiles、連続実行)。

| | 中央値 | 最小 | 最大 | 分布 |
|---|---|---|---|---|
| before (`b2f8ede1`) | **327.8ms** | 322.8 | 632.4 | 322.8 / 325.7 / 325.9 / 327.3 / 327.7 / 327.9 / 333.3 / 333.9 / 336.4 / **632.4** |
| after (HEAD) | **329.5ms** | 321.4 | 340.9 | 321.4 / 324.2 / 326.7 / 328.9 / 329.1 / 329.8 / 330.1 / 330.6 / 340.5 / 340.9 |

**中央値の差は +1.7ms で、群内のばらつき (外れ値を除いて 14〜19ms) より小さい。**
`loadDoctorDiskCache` 単体の実測 26.5µs は **この測定の分解能の 1/60** なので、
壁時計では原理的に見えない。悪化していないと言える。

⚠️ before 側に 632.4ms の外れ値が 1 件ある (中央値の 1.9 倍)。この計測は tmux のサーバ起動と
`git log` / `gh` を含むので、単発の外れ値は環境ノイズとして扱う (だから中央値で比べている)。

### Bench 経路には乗せない

受け入れ条件の「乗せられるなら乗せる」は**乗せない**が答え。`tests/glogx/bench_glogx.sh` の
冒頭が「バイナリ起動の壁時計 / プロセス RSS は意図的に対象外。実起動は git log / gh の fork と
ネットワークに依存し CI では flake 枠」と既に判断を書いており、上の実測 (外れ値 1.9 倍) はその
判断を裏づけている。Go 側の起動コストは既存の `model_init_200` が代理する。
