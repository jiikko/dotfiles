### 🚨 第 3 のケースがある（(a)/(b) の二分法は不足。初版を訂正）

`<C-k>` の keymap は `on_attach` 内で **buffer-local** に張られる（`lsp.lua:681-683` の
`map()` が `buffer = bufnr` を渡す）。したがって **LSP client が attach していないバッファでは
`<C-k>` が存在せず、記録側が完全に正常でも 1 行も増えない**。

これは (b)「記録側のバグ」とは別のケースで、**初版が書いた 30 秒の手順では区別できない**
（押しても増えないのを見て、正常な機構をバグと誤診する）。確認手順に
`:map <C-k>` と `vim.lsp.get_clients({ bufnr = 0 })` を足す必要がある。

### 増分ゼロが意味することは (a) より広い

記録経路は `<C-k>` だけではない。`lsp.lua:700` の `<leader>K`（LSP で引き直す）も
`usage().record("lsp", ...)` を呼ぶ。またログは全 filetype 共通なので、Go や shell で
`<C-k>` を押していれば `kind:"lsp"` の行が増える。

つまり増分ゼロが示すのは「Ruby の参照検索を使っていない」ではなく、
**全 filetype の `<C-k>` と `<leader>K` の両方が 1 回も走っていない**こと。
「使われない機能に sidecar を作る理由は無い」という結論を出すには、
**Ruby の参照検索を使っていない**のか、**この 3 日間 nvim 自体をほとんど使っていない**のかを
分ける必要がある（後者なら 344 の母数不足は「機能が不要」の証拠にならない）。

## 対応: 344 の判定基準を「終わる」形に直す

**「母数が集まらないこと自体を答えとして扱う」条項を 344 に足した**（延長は 1 回 =
2026-11-09 まで。そこでも 20 回未満なら ripgrep のまま確定して閉じる）。

根拠は 3 日の観測ではなく、**基準の表に終端が無いこと**（上の「本当の問題」節）。
1 か月使った上で母数が集まらないなら、rg の false positive で実際に困った回数は測れておらず、
**測れない困りごとのために sidecar（常駐 + IPC + 差分更新 + 定数の解決）を作る理由は無い**。
issue 334 段階 1 の目的は「重い仕組みを作る前に数字で決める」ことなので、
「1 か月使って数字が集まらない = 作らない」は目的に沿った決着であって、判断の放棄ではない。

🚨 **これは 344 の判定基準の変更である**（`issues/344-*.md:22` が「迷わないように固定しておく」と
書いている表に、新しい終端分岐を足した）。元の表は「20 回未満 → 延長」しか持たないので、
条項を足さずに (a) を根拠に閉じると**基準の無断の上書き**になる。

## `:DotfilesRefsStats` / `:DotfilesRefsReset` の前提

コマンドの登録は `refs_usage.lua:148-158` の `M.setup()` で、それを呼ぶ `dotfiles.lsp` の
`M.setup`（`lsp.lua:805`）は nvim-lspconfig の spec から走る。その spec は
`event = { "BufReadPre", "BufNewFile" }` の遅延ロード（`_nviminit.lua:358-362`）なので、
**ファイルを 1 つも開いていない nvim では両コマンドが存在しない**。
344 の「nvim で `:DotfilesRefsStats` を実行し…」はファイルを開いた後に読む。

## この調査で見つかった別件（354 の原因ではない）

**rg 経路は LSP を一切必要としないのに、`<C-k>` は `on_attach` の中でしか貼られていない。**

- `lsp.lua:679` の `on_attach(client, bufnr)` は先頭が `if not client then return end` で、
  `:895-899` の `LspAttach` autocmd から呼ばれる
- `<C-k>` の実マッピングは `:704` のここ 1 箇所だけ（`grep -rn '<C-k>' nvim/` で全数確認）
- しかし rg 経路の実体は `telescope.grep_string`（`references_action` が `route="ripgrep"` を返す
  場合）で、LSP クライアントを 1 つも使わない

つまり **solargraph も ruby-lsp も起動しない Ruby repo では `<C-k>` が丸ごと存在しない**。
issue 332 が rg へ振り替えた動機は「LSP が遅い（11.2s）」ことだったのに、その速い経路が
遅い経路の attach に依存している。`ruby_lsp_failed` / `ruby_lsp_fallback_reason` という
失敗経路が実装されている（= 起動しないことは想定内）ので、到達しうる。

この環境では両サーバが起動するため 354 の原因ではない。別 issue に切り出す候補。
