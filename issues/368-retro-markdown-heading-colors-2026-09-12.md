# 368 retro: markdown 見出しの配色 (2026-09-12)

対象: nvim の markdown 表示が「目が滑る」という相談から、見出しの階層色・アイコン位置の
修正 (4887d531 / a8d41fa7 / fe56c180) と issue 365 の起票・決着まで。

## 気づき

### 1. サンプルの母集合が実物と違い、「変化が 0 件」の画面を作った 🔴

見本の `sample.md` は H1〜H6 が均等に出る作りだったが、実物 (`README.md`) は
**H1=3 / H2=5 / H3=12** で H3 が過半数。案A は「変更を最小にする」つもりで H3 に
現状色 (緑 142) を据え置いたため、ユーザーの画面 (185..257 行) では
**6 見出し中 4 つが変更前と同一**になり、「見た目変わっていない」という報告になった。

見本は「レイアウトが崩れないか」は見られるが、**変更の可視性**は実物の分布でしか見えない。

→ 切り出し先: [`decide-layout-in-sample-renderer-first.md`](../_claude/rules/decide-layout-in-sample-renderer-first.md)
への**追記**。既存の「繰り返す単位が複数あるレイアウトは複数単位を描く」の隣に、
「**見本は実物の分布で描く (要素の出現比が違うと、変更が見えない画面ができる)**」を足す。
発動点が同じ (見本を作る瞬間) なので新規ルールにはしない。

### 2. 見本スクリプトが「偽の "変わっていない"」を出していた 🔴

`a3.lua` / `b.lua` / `a-inline.lua` が `vim.fn.expand("%:p:h")` で兄弟ファイルを
`dofile` していた。これは**スクリプトの dir ではなく開いているバッファの dir**なので、
見本を任意のファイルに当てられるようにした瞬間に外れた。

**外れ方が最悪**だった: dofile がエラーになるとチャンクが中断し、**本体の設定がそのまま
残る** → 出力は「本体の値」= 一見もっともらしい。`a3` が `a` と同じ値を出していたので
気づいたが、気づかなければ「案A3 は案A と見分けが付かない」と報告していた。

これは「有無で結果が変わらない観測を証拠に数えない」の一種だが、あちらは *観測が変化を
捉えられない* 形で、こちらは **観測装置が黙って無効化され、無効化された結果が正常な
出力と区別できない** 形。

→ 切り出し先: [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
への**追記**。「抽出・判定を書いたら canary を置く」節の隣に、
「**見本 / 検証スクリプトが複数の派生を持つなら、派生どうしが違う値を出すことを確かめる
(同じ値なら片方が適用されていない)**」を足す。

### 3. 「設定が入っているか」は動いている nvim に直接聞ける 🟢

「見た目変わっていない」に対し、`_nviminit.lua` の grep・headless の再現・`ps` の
起動時刻まで見ても決着しなかった。決め手は **動いている nvim の socket へ問い合わせた**こと:

```
sock=$TMPDIR/nvim.$USER/*/nvim.<pid>.0
nvim --headless --server "$sock" --remote-expr 'luaeval("...")'
```

これで「設定は入っている (H1fg=#fe8019 / pos=inline)」「画面に出ている見出しは H3 が 4 つ」
が同時に取れ、原因が**設定ではなくスクロール位置**だと 1 手で確定した。

→ 切り出し先: [`instrument-before-second-fix.md`](../_claude/rules/instrument-before-second-fix.md)
への**追記**。「手元で再現しないなら、動いているプロセスの env / cwd / 起動時刻を読む」節に
「**nvim なら `--server <socket> --remote-expr` で生きているセッションの状態を直接読める**」
を 1 行足す (`ps eww` の nvim 版)。

### 4. 全数勘定の metric が「画面」でなく「generic capture」を測っていた 🔴

issue 365 の最初の版は `@markup.heading` (言語サフィックス無し) の色を見ており、
**既に直したはずの markdown を「潰れている」と報告**していた。advisor の指摘で気づき、
ハイライタが実際に解決する名前 (`@capture.<lang>`) で測り直した。

canary を「**markdown の `@markup.heading` が潰れていると報告されないこと**」に置いたら、
その後の測定で実際に 1 度落ちた (markdown バッファを開かずに測った run)。canary が無ければ
その run の結果をそのまま issue に書いていた。

→ 切り出し先: **なし (既存ルールで足りている)**。
`verify-execution-not-just-exit-code.md` の「抽出・判定を書いたら canary を置く」と
`subagent-model-tiering.md` の「実装は正しいが検査対象の集合が想定と違う」が
そのまま当てはまる。**ルールを読んでいても踏んだ**ことが記録の価値なので、
規範の追加ではなく実例として rationale 側へ回すのが妥当。

### 5. 採番から push までの数分で番号が衝突した 🔴

365 を採番して本文を書いているあいだに、並行セッション (dotfiles-c9) が同じ 365 を
取りかけた。こちらは事前に「起票するときは 365 以降を使う」と伝えていたが、
**実際に取ったときに連絡していなかった**。

→ 切り出し先: **却下 (重複)**。dotfiles-c9 の issue 367 が「事前の合意は採番の証明に
ならない」として同じ件を扱っている。規範の切り出しはそちらへ寄せる。
本 retro では、**このセッションで実際に採った対策**だけ記録する:
368 は本文を書く前に skeleton だけ commit → push → 直後に並行セッションへ通知、
の順にした (衝突なし)。
