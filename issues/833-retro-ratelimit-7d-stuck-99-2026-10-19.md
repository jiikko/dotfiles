# 833 (retro): glogx / ratelimit の 7d が 99% に張り付いた件の振り返り

起票日: 2026-10-19

## 概要

glogx と `bin/ratelimit` の 7d が 99% と出ていた (サーバの `/usage` も、Claude Code が今 statusline へ渡す
`rate_limits.seven_day` も 38%)。statusline が書くキャッシュ `~/.cache/glog/claude-rate-limits.json` の書き手が、
同じ窓では「使用率の高い方が新しい」として高い値を残すので、一度 99 が入るとリセット (10/21 18:00) まで戻らなかった。

- 修正の commit: 「fix(statusline): 利用枠の同じ窓を「使用率の高い方」で比べない (7d が 99% に張り付いた)」
- 記録の commit: 「feat(statusline): 利用枠のキャッシュに、窓ごとに値を書いたセッションを残す」
- 99 を書いたセッションは特定できていない (記録を入れたのはこの後)

## どこで踏んだか / 何が回りくどかったか

### 1. 「値は単調に増える」を合流の規則にして、外れ値を戻す経路が無かった

複数のセッションが同じキャッシュへ書くのを、「同じ窓の使用率は下がらない」というドメインの性質で合流させていた。
性質が正しくても、入力が一度でも外れる (出所不明の 99) と、規則がその外れ値を守る側に回る。観測時刻 (observedAt) も
別の経路で進み続けたので、「古くなったら予備へ落ちる」安全網も働かなかった。張り付いたのは 2 つの機構の組み合わせ。

- 最初の修正では観測した形 (同じリセット時刻の 99) だけを直し、敵対的レビューで「リセット時刻ごとずれて入った外れ値も
  戻せない」(旧規則からあった穴) を指摘されて足した。症状の形でなく「誤った値が残り続ける経路」を全部挙げていれば 1 周で済んだ

### 2. 書き手の出所を記録していなかったので、原因の半分が追えない

キャッシュには値と observedAt と版しか無く、どのセッションが 99 を書いたかが残っていなかった。並行して動く対話セッションが
5 本あり (9/30 起動のものを含む)、後から辿る手段が無い。記録は修正の後に足したので、今回の 99 には効かない。

### 3. 局所の記録 (提案にしない)

- bash 3.2 でテストを回すときに PATH を `/bin:/usr/bin` に絞り、go まで外れて rc=127 になった。go の場所を足して取り直した
- python で行末を置換した際、置換先の文の頭と後続の語が重なって README に「窓ごとに」が 2 回入った。次の commit で直した
