## 1. 自分のテストが production の形状を一度も試していなかった

103 のレースハーネスは毎回 `mkdir "$dir"` で**取り残しを事前に作って**いた。この形状では
両プロセスが奪取経路に入るので、奪取権 lock で直列化されている経路しか検査しない。
production の呼び出し元 3 本はどれも **lock dir が存在しない状態から始まる**ので、片方が素の
`mkdir` で入り、奪取権 lock を持たないまま owner を記録する — そこが原症状の窓だった。

「30 回で 1 度も二重取得を観測しない」を「窓が閉じた」と読んだが、実際は
**ハーネスが窓を作れていなかった**。レビューの指示に「窓が閉じたからか、ハーネスが作れて
いないからか」を入れていたのに、自分では区別できていなかった。

- 素の窓は実測 4.6ms しかなく、production 形状でも二重取得は 2/30 でしか出ない
  (確率的にしか落とせない)。`tt_proc_starttime` を 0.4s 遅らせて窓を広げたら
  **ガード無し 15/15 / 有り 0/15** の決定論的な A-B が取れた

**切り出し先の提案**: `_claude/rules/mutation-verify-new-tests.md` の「よくある『守っていない
テスト』の形」に 1 項目。「**フィクスチャが production の初期状態と違う**と、その経路を
構造的に一度も踏まない。並行・レースのテストでは『呼び出し元がどの状態から始まるか』を
実装側で確認してから形状を決める」。加えて「窓がミリ秒なら**人為的に広げて決定論にする**
(確率的な green は変異検証の当たりも不安定にする)」。

## 2. 同じファイルの 100 行上にある helper を探さずに重複を作った

mtime 取得のために `tt_mtime_epoch` を新設したが、**同じ `guards.sh` に既に `tt_mtime_of` が
あり、正しい順序 (GNU 優先) と 2026-07 の実測注記まで書いてあった**。しかも私が書いた方は
順序が逆で、Linux で壊れる側だった。CI が赤になって初めて気づいた。

`claude-md-maintenance.md` は「共通 helper を**新設・抽出する**ときは実装前にその領域の
CLAUDE.md を読む」と言っているが、今回は CLAUDE.md ではなく**同じファイルの中**にあった。

**切り出し先の提案**: `claude-md-maintenance.md` の該当トリガー行に半行足す。
「共通 helper を足す前に、**まず同じファイル/同じ lib 内を helper 名と用途で grep する**
(規約の参照より先に、実物の重複を見る)」。新規ルールは作らない (既存の一項の拡張で足りる)。

## 3. BSD/GNU 方言を 1 セッションで 3 件踏んだ → 静的ゲートで構造化した

`stat -f %m` ×2 (guards.sh / schedkeys の prune) と `date -r <epoch>` ×1。**3 件とも正しい形と
注記が repo 内に既にあった**。運用では止まらないと判断して `scripts/check_platform_dialect.sh`
を新設し `make test-lint` に配線した (`c1383b9`)。

計測しないと間違える点が 1 つあった: 密着形 `stat -f%z` は GNU で `%` が invalid option になり
**stdout が空**なので、フォールバックが正しく効く。危険なのは**空白区切りだけ**。
「`stat -f` は全部だめ」にすると動いている既存 4 箇所を壊すところだった。

**切り出し先の提案**: **却下** (対応済み)。ゲートとテスト、`tests/CLAUDE.md` の新節で閉じている。
ルール文書には書かない (`comment-no-restate-enforced.md`: 実装が強制していることを再掲しない)。

## 4. 検証ハーネスを zsh で回して、実装のバグと誤診しかけた

`tt_lock_sweep_stale` の `.steal` 回収が「効いていない」と読んだが、原因は
**Bash ツールのシェルが zsh** (ユーザーの profile で初期化される) で、zsh の glob が
ディレクトリに `/` を付けたため `$d.steal` が別パスになっていたこと。lib は冒頭に
「前提: 呼び出し元は bash」と書いてある。`bash -c` で測り直したら正しく動いていた。

`| head` 越しに `$?` を読んで GNU `date -r` の rc を誤読しかけた件も同じ日にあった
(こちらは `verify-execution-not-just-exit-code.md` が既に扱っている既知の形)。

**切り出し先の提案**: `tests/CLAUDE.md` に 1 行。「**bash 前提の lib を手検証するときは
`bash -c` で回す**。このリポジトリの対話シェルは zsh で、glob・配列・単語分割が違う
(実例: zsh の MARK_DIRS で `*.lock` が `foo.lock/` になり、`$d.steal` が別パスを指した)」。
ルール化はしない (dotfiles 固有の環境事情なので、領域の入口に置くのが適切)。

## 5. 敵対的レビューが 2 度、私の「直った」を覆した

103 では「修正が原症状を閉じていない」を実測つきで示し、その修正過程では**既存テスト**が
私の入れた退行 (mkdir 不能を rc=2 でなく rc=1 に化けさせ、装置不在を無音にする) を捕まえた。
指摘は 5 件とも実コードで裏を取ってから採用し、示せなかった 1 件 (奪取権 lock の TTL 奪取に
よる多重取得) は「未確認リスク」として issue に残した。

**切り出し先の提案**: **却下** (記録のみ)。CLAUDE.md「レビュー方針」の
「『指摘なし』は『正しい』ではない」がそのまま効いた実例。
