## 反省・気づき

### 1. 🚨 「自分が直したバグを、自分の回帰テストが守っていない」が **3 issue で再発**した

同じ形が 383 / 393 / 385 で出た。どれも**敵対レビューが変異で示すまで気づかなかった**:

- **383**: 不変条件 (「`lockman break` を促さない」) をコメントで宣言しながら、**3 hop 中 2 hop しか
  pin していなかった**。残る 1 hop (`status`) が実際に promote していた
- **393**: seam を「窓の手前」(`.cleanup_at` の FIFO = sweep の後) に置いたため、
  **カウンタを一括計上する変異 = issue の症状そのもの**が全スイート緑で通った
- **385**: 要の 1 行 (`break` 文) を守るテストが 1 本も無く、外すと「昇格が永久に来ない」=
  無制限の二重実行になるのに全緑。既存テストが FIFO しか使わず、**エラー枝を 1 本も
  通っていなかった**

共通の原因は「**自分の fixture で修正が観測できる場所**に seam / pin を置いた」こと。
退行が現れる場所とは別で、そこがズレていても**緑は出る**。

**切り出し先の提案**: `mutation-verify-new-tests.md` へ 1 項 —
「**修正を観測できる場所ではなく、退行が現れる場所に seam / pin を置く**。判定は
『その fixture で、issue の症状そのものを再現する変異が red になるか』」。
既に「seam は守りたい窓の内側に置く」があるので、**その項へ「退行が現れる経路を先に数える」を
追記**する形で足りる (新規ルールは立てない)。

### 2. 🚨 変異を当てずに「vacuous だ」と判定して、**効いていた assert を消した**

393 の 2 周目で「報告 ≤ 実態」の assert を「見捨てた goroutine が消し続けるのでほとんど何も
検査しない」と判断して削除した。3 周目のレビューが変異 (`removed` を 2 倍に水増し) で
**決定論的に効いていた**ことを示し、戻した。`mutation-verify-new-tests.md` は
「green のままの変異を等価変異と判定するときは経路を列挙してから言う」と書いているが、
**発動点が「変異を当てた後」**になっており、今回のように「変異を当てずに vacuous と
断じる」形は射程の外だった。

**切り出し先の提案**: 同ルールの該当項へ「**assert を『何も検査していない』として消すときも、
消す前に変異を 1 本当てる**」を追記 (発動点が同じ項なので追記で足りる)。

### 3. 🚨 サブエージェントの副作用を「成果物の検閲」だけで見ていた — **ユーザーが気づくまで CPU を焼いていた**

敵対レビュワーが負荷生成に使った busy loop が **16 本孤児化**し、合計 600〜800% の CPU を
13〜26 分焼いた。本人は worktree の削除まで済ませており (`git worktree list` に残骸なし)、
**私の側からは「後始末済み」に見えていた**。気づいたのはユーザーの「zsh がたくさん起動している」。

**切り出し済み** (本セッションで実施): `parallel-write-agents-need-worktree-isolation.md` へ
「残骸にプロセスを含める / 負荷は親の終了で回収される形に限る」を追記済み (commit a25ce170)。

**追加の切り出し提案**: `subagent-model-tiering.md` の「検閲の観点」は成果物 (diff・報告文) しか
見ていない。**「そのエージェントがマシンに残したもの」を観点に 1 行足す**か、上記ルールへの
参照を 1 行置く。どちらか一方だけにする (両方書くと二重管理)。

### 4. issue 本文の前提が **2 本で誤っていた**。着手前の実測が両方とも報われた

- **384**: 「子が `setsid()` すると `kill(-pgid)` が EPERM」→ **誤り**。`Setpgid` の子は
  グループリーダーなので **`setsid()` 自身が EPERM** で失敗する (EPERM を受け取る主体の取り違え)。
  実測で EPERM は**ゾンビだけのグループ**で再現し、生きたメンバーが 1 つでもあれば kill は成功した
- **405**: 「1.25.4 の bin にも実体が無い可能性」→ **誤り**。goenv は GOPATH を版ごとに分けるので
  実体は `~/go/1.25.4/bin` に在り、**版上げで go 製ツール 17 本がまとめて消えていた**

どちらも CLAUDE.md の「issue の記述を鵜呑みにしない」が効いた例。**切り出し不要** (既存規律どおり)。

### 5. `make test` の赤を「環境由来」と分類したまま、半日走り続けた

405 に着手するまで、`make test` は毎回 `staticcheck` の行で赤かった。私はそれを
「全プロジェクトで `command not found` = 環境由来 / 私の変更と無関係」と分類し、**そのまま
8 issue ぶんの検証に使い続けた**。実際の原因は**ガード 1 行のバグ**で、着手したら 30 分で直り、
`make test` は緑に戻った。

分類自体は正しかった (私の変更由来ではない) が、「**集約テストが毎回赤い状態を、検証の土台に
したまま作業を続けた**」のは判断として弱い。赤が固定化すると、新しい赤が埋もれる。

**切り出し先の提案**: `verify-execution-not-just-exit-code.md` へ 1 項 —
「**集約テストが赤いまま検証を続けない**。原因が自分の変更でなくても、赤が固定化すると
新しい赤が埋もれる。直すか、**落ちている検査の名前を控えて『この検証はその検査を含まない』と
明示する**」。
