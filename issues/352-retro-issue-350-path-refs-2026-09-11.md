## 1. 分類スクリプトが無音で壊れ、その出力をユーザーへ報告した

全数勘定の 1 回目を zsh で回したところ、`ls issues/${n}*` が **NOMATCH で毎回中断**していた。
`alt` が常に空になり `MOVED->` 分岐は**一度も実行されなかった**が、`else` 側のラベル
`NOFILE(他repo?)` が 100 行以上に付いて、**壊れた分類ではなくデータに見えた**。
そのまま「切れている参照は 0 件」とユーザーへ報告した。bash + `nullglob` で数え直すと
**実際の腐りは 2 件**（`src/lockman/README.md` / `tests/zshrc/test_print_p_injection.sh`）。

一般化できるのは「**分類器の fallback ラベルは、真の判定と見分けが付かない**」こと。
`[ -e ]` で判定した `OK` は生き残り、glob に依存した枝だけが死んだのに、出力は同じ顔をしていた。
防ぐには**発火しない枝それ自身にカウンタを持たせる**（「MOVED 判定を N 回試行した」を出す）。

- 切り出し先の提案: [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
  の「抽出・判定を書いたら canary を置く」節へ追記。発動点（抽出が空 → 緑）が同じで、
  新規ルールを立てる理由が無い
- 併せて: **数字がユーザーへ届く前に、その数字を出した経路が全部走ったかを見る**。
  今回は shell の方言（zsh NOMATCH）が原因なので、集計は bash で書くのが既定でよい

## 2. `grep | while read` が「正常系」でスクリプトを殺した

新設した検査が、**腐り 0 件のとき** rc=1 で落ちた。`grep '^VIOL' … | while read …` が
無マッチで status 1 を返し、`set -e` がそこで終了させていた（`grep` の後ろに printf が
残っていたのに到達しない）。エラーメッセージは 1 行も出ないので、原因の特定に bash -x が要った。

[`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md) §1 の
異常系の表（対象 0 件 / 依存コマンド失敗 / 権限なし / 並行）は**検査対象**の異常系を並べているが、
今回落ちたのは「**検査対象が正常だったとき**」で、表のどれにも当たらない。

- 切り出し先の提案: 同ルール §1 の表に「**違反 0 件 / ヒット 0 件の正常系**」の行を足す
  （検査を書いたら、まず違反ゼロの入力で緑になるかを見る）

## 4. 候補件数の下限が母集合の縮小を検出しきれない

新設した検査は候補 113 件に対して下限 `-lt 50`。母集合の大半はテスト fixture で、
`tests/claude/test_next_claim_push.sh` だけで 28 件を占める。将来そのテストが整理されると
**候補が半減しても下限は通る**。

- 切り出し先の提案: **却下（今は直さない）**。下限を上げると fixture の正当な削除で赤くなり、
  検査が邪魔になる。**再評価の trigger**: 候補件数が 90 を下回ったら下限と母集合の構成を見直す
  （検査は毎回件数を出すので、人が読めば気づける）
- コード側にこの trigger を残すかは判断待ち

## 5. 良かったこと（再現したい手順）

- **判定軸を「番号」から「番号 + スラッグ」へ変えたことで、除外リストが 1 件も要らなくなった**。
  最初に考えた「番号一致 + 除外リスト」案は fixture と他 repo で偽陽性が出て、
  除外を足し続ける形（§8 の「軸が構文にある」印）になっていた

  スラッグ一致なら fixture は誤爆しないので、母集合の錘として残せた
