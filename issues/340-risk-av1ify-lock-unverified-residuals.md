# av1ify の lockman 排他: 発火条件を実証できていない残リスク

2026-09-09 の敵対的レビュー (codex、3 周) が挙げたが、**再現手順を示せなかった / 閉じるには
設計変更が要る**ものの記録。同じ指摘が次の監査で再生成されるのを防ぐために残す。

対象: `zshlib/_av1ify_lock.zsh` / `_av1ify_encode.zsh`、`src/lockman/`。
関連コミット: `187ab4d0` (導入) → `07e53917` / `f066db0a` (1 周目) → `0050997c` (2 周目) →
`584c0775` (3 周目)。

## 1. lockman の `Renew` が期限を検査せず `O_TRUNC` で開き直す

`src/lockman/lock.go` の `Renew` は token を照合した後、lock ファイルを `O_TRUNC` で
開き直す。**期限切れ lease の復活**と、**照合後に他者へ引き継がれた lock の上書き**が
コード上は可能に見える。

- **なぜ直していないか**: 実 lock を使った時間差の再現をしていない。lockman は
  「期限切れの引き継ぎは存在しない名前への rename で勝者を 1 人に絞る」設計なので、
  `Renew` 側にも同じ保証が要るかは実測しないと決められない
- **これに依存している箇所**: av1ify は `finalize` の直前に `lockman renew` の rc で
  「まだ保持しているか」を判定する (`__av1ify_lock_still_held`)。renew の rc=0 が
  所有権の証明としてどこまで使えるかは、この issue の結論に依存する
- **再開の trigger**: 実 lock で「期限切れ後の renew が成功する」を再現できたとき。
  再現できたら `Renew` に期限検査と操作対象の同一性確認を足す
- 🚨 **2026-09-09: [issue 312](done/312-bug-lockman-renew-skips-lease-expiry-check.md) で解消**。
  再開の trigger は満たされた — `TestRenewRefusesExpiredLease`（TTL 50ms・3 倍待って誰も
  引き継いでいない状態で `Renew`）で「期限切れ後の renew が成功する」を**実 lock で再現**し、
  `Renew` の token 照合の直後へ `serverNow` + `expired(now, mtime, holderTTL(m))` を足した
  （判定は `Release` と共有。新しい判定は書き起こしていない）。期限検査を外す変異で
  そのテストだけが red になることも確認済み。
  **`__av1ify_lock_still_held` への影響**: `renew` の rc=0 は「token 一致 **かつ** 期限内」を
  意味するようになったので、所有権の証明として使ってよい。ただし `Renew` は probe が
  1 往復増える（既定の renew 間隔は TTL/3 = 10 分なので許容と判断した）。
  「照合後に他者へ引き継がれた lock の上書き」（`readLock` と `OpenFile` の隙間）は
  窓が縮んだだけで 0 にはなっていない — **その部分はこの issue の残課題のまま**

## 2. `pgrep` と kill の間の競合 / PID 再利用

`__av1ify_lock_release` は renewer を止めるとき、`pgrep -P` で子 (sleep) を列挙してから
kill する。列挙と kill の間に子が入れ替わる / 終了済み PID が再利用される可能性がある。
また `kill -0` はプロセスの**同一性**を証明しない (renewer が監視する所有者 PID も同じ)。

- **なぜ直していないか**: 再現していない。閉じるには親子間の生存通知 (パイプ等) を持つ
  必要があり、shell の範囲では重い
- **今の影響**: 取りこぼした sleep は最大 renew 間隔 (10 分) で自然に消える。
  stdio は `/dev/null` に落としてあるので、呼び出し元のパイプは掴まない
- **再開の trigger**: 孤児 renewer が lease を持ち続けて後続が SKIP され続ける事象が
  実際に観測されたとき

## 3. 共有 tmp の名前を実行ごとの固有名にするか

`<stem>-enc.mp4.in_progress` は入力パスから決まる**共有名**で、renew 成功と `rm` は
不可分ではない。その間に長時間停止して他者へ引き継がれると、誤って相手の作業中
ファイルを消しうる。

- **なぜ直していないか**: 3 周かけて削除経路を 1 箇所 (`__av1ify_rm_own_tmp`) へ寄せ、
  保持確認を通すようにしたが、**窓を 0 にはできない**。0 にするには一時出力名に
  取得トークンを混ぜる必要があり、`__av1ify_default_output_exists` や残骸削除など
  「決定論的な名前」を前提にした周辺コードを一緒に変えることになる
- **再開の trigger**: 実 lease を使った並行実験で誤削除を再現できたとき。
  または一時出力名を変える別の理由が出たとき (そのとき一緒に閉じる)

## 4. 複数マシンでマウントパスが違うとキーが一致しない

ロックのキーは「出力ディレクトリの実パス + ASCII 小文字化した basename」の SHA-256 で、
`AV1IFY_LOCK_ROOT` を共有上のパスへ向ければ複数マシンで共有できる。しかし
**同じ共有をマシンごとに違うマウントパスで見ている場合、キーが一致しない**。

- **今の既定**: `~/.lockman/av1c` (ローカル HOME) なので**同一マシン内の排他**。
  今回塞ぐと決めた経路 (別ディレクトリからの二重起動 / 綴り違い / 手動の av1c) は
  すべて同一マシン内
- **再開の trigger**: 複数マシンから同じ共有を触る運用に変えるとき。そのときは
  共有内の相対パスなど、マウントパスに依存しない識別子へ変える

## 5. キー生成のパイプライン途中の失敗検出が `PIPE_FAIL` に依存する

`__av1ify_lock_dir_for` の `printf | tr` / `printf | shasum | cut` は、途中段の失敗を
`pipefail` が有効なときしか検出できない。`av1ify()` は 1110 行付近で `setopt pipefail`
するので通常の入口では有効だが、ヘルパーを直接呼ぶと無効な場合がある。

- **なぜ直していないか**: 通常の入口 (`av1ify` / `av1c` / `bin/av1ify`) からの誤動作を
  実証できていない。ヘルパーの直接呼び出しはテストと調査用
- **再開の trigger**: pipefail 無効の経路からヘルパーを呼ぶ実装が入るとき

### 🚨 2026-09-09: 実験の結果、**この項目の前提は誤りだった** — 却下する

「途中段の失敗を `pipefail` が有効なときしか検出できない」が成り立たない。検出しているのは
`pipefail` ではなく**出力の検証**で、そちらは無条件に効いている:

```zsh
[[ -n "$folded" ]] || return 1
[[ ${#h} -eq 64 ]] || return 1
[[ -z "${h//[0-9a-f]/}" ]] || return 1
```

`zsh -f` + `unsetopt pipefail`（`setopt | grep -c pipefail` = 0 を確認）で、PATH 先頭に
失敗する shim を置いて実測:

| 条件 | rc |
|---|---|
| 正常 | 0（64 桁の hex が返る） |
| `tr` だけ失敗 (exit 1) | **1** |
| `shasum` だけ失敗 (exit 1) | **1** |
| `shasum` が **rc=0 で短い出力**を返す (`abc  -`) | **1** |

3 形とも loud に落ちる。とくに 4 行目は `pipefail` では**そもそも検出できない**形
（途中段が成功しているため）で、出力の検証しか捕まえられない。つまり
**`pipefail` は元々この防御の担い手ではなかった**。

「pipefail 無効の経路からヘルパーを呼ぶ実装が入るとき」という再開の trigger も、
その経路で既に落ちることが分かったので**不要**。この項目は閉じる。
