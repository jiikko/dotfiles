## 気づき・反省

### 1. 🚨 自分が「上限」として入れた機構が、守るべき不変条件を壊していた

goroutine の蓄積を止めるために `ticker.Stop()` を入れたが、それは**一過性の I/O ヒカップを
本物の lease 喪失に変える**。更新が二度と走らないので lease は実際に期限切れになり、
他マシンが正当に引き継ぐ = 子が走ったまま二重実行。**lockman が防ぐために存在するもの**を、
リソースリーク対策のつもりで作っていた。

- 見落とした問い: 「この上限は、**何を止めているのか**」。私は goroutine を止めるつもりで
  **製品の機能 (lease の維持)** を止めていた
- commit message に書いた「outcome は sticky なので、ここから先の更新は結論を変えない」は
  **終了コードについては真、lease については偽**。同じ文の中で 2 つの対象を混ぜていた
- **切り出し先**: `list-masked-failure-modes-before-removing-guard.md` の発動点は
  「防御を**外す**とき」だが、これは「**別の目的で止める**とき」だった。
  同ルールに「機能を止める形の対策を入れるときも、それがマスクしていたものを列挙する」を
  1 行足すのが妥当か、**ユーザー判断を仰ぐ**

### 2. 🚨 新しく書いたテストが、退行を当てても緑だった

`TestLeaseSurvivesTransientRenewBlock` の初版は、詰まりの窓を 400ms にしていた。
最初の tick (300ms) + 期限 (200ms) より短いので、**検査したい状態に入る前に復旧**しており、
退行 (`ticker.Stop()` 版) を当てても緑だった。窓を 900ms に広げて RED を確認した。

- `mutation-verify-new-tests.md` の「差が出ない状況しか作っていないか」そのもの。
  ルールは読んでいたが、**タイミングを持つテストでは「差が出ない状況」が時間軸に現れる**
  ことに気づくのが遅れた
- **切り出し先**: 既存ルールで足りている → **却下**（実例だけ rationale へ）

上限を置くか決めろ」と **trigger 付きで**書いてあった。私は 357 の実装で包みを入れただけで
上限を置いておらず、Stop hook が 359 への書き戻しを促したときに初めて気づいた。

- **却下した指摘に trigger を書く**ことの価値が実測で出た例 (`move-report-conclusions-to-issues.md`
  が求めている形)。ただし**気づいたのは hook 経由**で、自分から 359 を読み直してはいない
- **切り出し先**: 既存ルールで足りている → **却下**

### 4. 「素通りする経路はもう無い」を、自分の検査の射程で判定していた

配線テスト (`timeout_wiring_test.go`) が「Locker のメソッド呼び出し」しか見ないのに、
主張は「production の I/O はもう素通りしない」と書いていた。レビューが
`NewLocker` の `os.Stat` (全サブコマンドが通る) を実測で出した。

- **検査が緑 = 主張が真**、ではない。**検査の射程 = 主張の射程**に揃える必要がある
- `adversarial-review-own-safeguards.md` §8 の「実装後に射程と突き合わせる」が未了だった
  (着手前に書いた「検出しない形」のまま放置していた)
- **切り出し先**: 既存ルール (§8) で足りている → **却下**。ただし実例は rationale へ
