# retro: Ruby の LSP が効かない調査と、選択方式の入れ替え (2026-09-08)

対象: issue 332 (`feat(332): Ruby の LSP サーバ選択を allowlist から Gemfile + 実起動プローブへ`)

## このセッションでやったこと

「nvim で Rails の rb を開くとジャンプできない」の診断 → 原因特定 (mason の solargraph が
project と違う ruby で走り bundle の gem 解決が全滅) → サーバ選択方式の入れ替え →
敵対的レビュー → 変異検証 → landing → 実 project での動作確認。

## 反省・気づき

### 1. ハーネスの失敗を「実装の壊れ」として報告しかけた

`nvim -l script.lua` はユーザー設定を読まない。これに気づかず最初のプローブが
`attached=false clients=` を返し、**「LSP が attach していない」という誤った事実**を
一度手元で確定させた。次の一手 (`--headless -c "lua dofile(...)"`) で覆った。

- 既存の [`verify-interactive-prompt-with-pty-driver.md`](../_claude/rules/verify-interactive-prompt-with-pty-driver.md) が
  「対話の確認が失敗したら実装を疑う前にハーネスを疑う」を持っているが、**発動点が「対話プロンプト」に
  限定**されていて、今回の「headless で設定を読ませる検証」には掛からなかった
- **切り出し先の提案**: 既存ルールへの追記。
  [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md) の
  「隔離環境での成功は、本番での成功ではない」節に**裏返し**を 1 項足す
  ——「隔離環境での**失敗**も、本番の失敗ではない。自分が用意した実行環境が本番と同じ
  ものを読んでいるかを、赤を報告する前に 1 回確かめる」。新規ルールは立てない
  (発動点は既存節と同じ「隔離環境で観測した」)

### 2. 再現率を確かめずに「常に壊れる」と断定した

6 分ポーリングで誤答のままだった run を根拠に「214 秒待っても必ず誤答」と報告したが、
その後の別 run では既定の solargraph が正答を返した。ユーザーへ訂正した。

- 既存の [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md) に
  「条件を変えずに同じ HEAD で 2 回回す (1 回目赤・2 回目緑なら環境でなく非決定性)」が**既にある**。
  読んでいたのに、切り分けではなく**症状の恒常性の主張**には当てはめなかった
- **切り出し先の提案**: 却下 (ルールは既にある。増やしても同じ見落としを防げない)。
  ただし rationale へ実例 1 行を足す価値はある

### 3. 「テストのスタブが引数を捨てている」が変異検証を素通りした

新テストの `vim.system` スタブが `function()` で引数を受け取っていなかったため、
**`{ cwd = dir }` を落とす変異**と**`--version` を落とす変異**がスイート全体緑で通った。
これはこの変更の**唯一の前提**(「その project の ruby で測る」) で、変異 7 本を全部 red に
した後でも穴が残っていた。敵対レビュー (opus) が指摘。

同型で、`vim.fs.root` を定数関数へ差し替えていたため **marker 配列そのものが無検査**だった
(空配列にする変異まで緑)。marker の順序が load-bearing なのに。

- **切り出し先の提案**: [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md) の
  「よくある『守っていないテスト』の形」へ 1 項追記:
  **「スタブ / fake が引数を受け取っていないか。捨てていると、呼び出し側が渡す値
  (cwd・オプション・コマンド列) を変える変異が全部緑で通る。差し替えた依存が
  『何を渡されたか』を記録して assert する」**。
  併せて「定数を返すだけのスタブに差し替えると、その依存へ渡す**設定値**
  (marker 配列・順序) が無検査になる。設定値が結果を決めるなら、そこだけは実物を使う」
- 発動点は既存項と同じ (テストを書き終えた瞬間) なので新規ルールは立てない

### 4. 敵対レビューの指摘 1 件が事実として外れていた

「activerecord のソースへ飛ぶと gem が root になる」は誤りで、activerecord は Gemfile を
同梱していないため root は repo root だった。裏を取って訂正したうえで、**Gemfile を同梱する
gem では成立する**ことを実測 (`json-2.3.1`) して採用した。指摘の骨子は正しく、実例だけが外れていた。

- **切り出し先の提案**: 却下 (`~/.claude/CLAUDE.md`「レビュー方針」の「敵対レビューの出力こそ
  無検閲で採用しない」が正しく効いた事例。ルールの追加は不要)。
  rationale へ「骨子は正しいが実例が外れる形がある」の 1 行を足すのは可

### 5. ユーザーが `gem i ruby-lsp` だけして詰まった

3 案を提示した中に「allowlist に 1 行足す必要がある」は書いていたが、**gem を入れれば直ると
読める配置**になっていた。実際ユーザーは gem を入れて「まだジャンプできない」と戻ってきた。

- 学び: 手を動かしてもらう手順を出すときは、**「あなたがやること」と「私がやること」を
  分けて書く**。案の比較表の中に必要手順を埋めない
- **切り出し先の提案**: 却下 (ルール化するほど一般性がない。応答の書き方の問題)

### 6. 診断が長く、ユーザーに「スタックしていませんか」と聞かれた

6 分ポーリングのような長い計測を、事前に「何を測っていて何分かかるか」を言わずに走らせた。

- 既存の CLAUDE.md「進捗更新のペース」(重要な発見か方針転換のときだけ短く挟む) は満たしていたが、
  **数分ブロックする計測を始める前の一言**が抜けていた
- **切り出し先の提案**: 却下 (既存の指針の範囲。過剰な進捗報告はむしろ禁止されている)。
  ただし「数分かかる計測を始めるときは所要時間を先に言う」は覚えておく
