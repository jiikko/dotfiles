# 642 (retro): zundamon-kaisetsu の Go 化 (issue 641) の振り返り

起票日: 2026-10-06

issue 641（dialogue_video.py を Go で書き直す）をやり切ったセッションの振り返り。うまくいった話は書かない。

## どこで踏んだか

1. **正解役を自分で先に壊した**: 設計の段階で、テンプレートを Python 版の置き場から Go module へ `git mv` した。Python 版は
   そのテンプレートを読むので、正解役の build が動かなくなり、Python 版と Go 版の E2E の突き合わせができなくなっていた。
   設計レビューの P1-2 で指摘されるまで気づかなかった（`git status` ではステージ済みの rename だった）。移動を戻し、
   Python 版を消すのは E2E の後に回した
2. **数値の再現で、言語の側の振る舞いを前提から外していた**:
   - Python 3.12 以降の `sum()` が Neumaier の補正つきで足すことは、最初の設計に入っていなかった（設計レビューの P1-4 で指摘）
   - Go は arm64 で `acc += s.d * ratio` を FMA（掛け算と足し算を 1 回の丸めでまとめる命令）にまとめ、最後の桁が Python と違う。
     境目がフレームの中点と重なると口の開きが 1 フレーム反転する。これは設計レビュー（opus の反証）でも出ず、敵対的レビュー 1 周目の
     「口パクの分岐を fixture が通らない」という素通りの指摘を受けて、境界を狙った合成の query で golden を作ったときに初めて再現した。
     実データ由来の golden と、87 行の台本の E2E では差が出ていなかった
   - 正解役の Python の振る舞いは版に依存していた（3.12 以降の `sum`、3.14 の `Path.stem`、3.14 の `realpath`）
3. **ツールがエスケープ表記を書き換えた**: Write / Edit ツールに渡した Go のソースの `\u003c`（6 文字のエスケープ表記）が、ツールの段階で
   `<` に変わって保存された。HTML に埋め込むデータの `<` のエスケープが黙って消え、`</script>` を含む字幕でデータが途中で切れる
   不具合になった。テストを書いたから見つかった。直すときも Edit ツールの old と new が同じ文字列に化け、ツールが「変更なし」を返した。
   最後は `"\x5cu003c"` と書いて回避した。この振り返りを Write ツールで書いたときも、本文の `\u003c` が `<` に化けた
   （2 回目の再現。直すときはバックスラッシュを Python の chr(92) から組み立てた）
4. **敵対的レビューが 4 周かかった**。周ごとの内訳:
   - 1 周目: 引数の解析・パスの解決・出力の書き込みが大半。中断に関するものは「親だけに SIGINT が届いたとき子が残る」1 件
   - 2 周目: 1 周目に足した「中断の後始末の登録表」が、子を止める前に一時ディレクトリを消す・rc=130 で普通に終えて bash のループが
     止まらない、の 2 件で壊れた。context の取り消し + 普通の defer + 同じ signal での死に直しに作り直した
   - 3 周目: 無視されていた signal の無視を解く（作り直しの穴）に加え、symlink のループで指数時間・umask・`--help` の略記など別系統
   - 4 周目: ほぼ 3 周目の修正への指摘（下の 5）。中断に関するものは文言 1 件
   自前の登録表が直接生んだ周は 2 周目と 3 周目の一部で、周の多さの全部の原因ではない
5. **指摘への修正が、新しい退行を生んだ**: 3 周目に「読み取り専用の既存の出力は置き換えない」を入れたとき、出力だけでなく合成の
   キャッシュの書き込みにも同じ関数を使った。Python 版のキャッシュは「一時ファイルに書いて rename」なので読み取り専用でも置き換わる。
   結果として、キャッシュの扱いが Python 版より悪くなった（4 周目の P2-1）。出力と同じ「置き換え」でも、Python 版の意味が 2 通りあった
6. **CI と同じ検査を手元で回したと思い込んでいた**: push の前に回したのは、module の `make lint` / `make test` と、Go プロジェクト共通の
   検査の一部（`test_golangci_*`・`test_no_failfast_entrypoints`・go_autobuild の検査）だった。root の `make test-lint` に含まれる
   `test-go-project-lanes`（依存の無い module にも空の go.sum を要求する）を回しておらず、CI の Lint が落ちた（39fe8c02。cff4d18d で修正）。
   issue 641 とコミットの文面の「緑」は、この個別の範囲での結果だった

## 次に効きそうな改善（提案）

- **A. 実装を置き換えるときは、旧実装が正解役として動く状態を、突き合わせが終わるまで保つ。正解役の版も記録する**（1・2 の一般形）。
  旧実装が読むファイルの移動・削除は、突き合わせと旧実装の削除と同じ段階に回す。旧実装を消した後も `git show HEAD:<旧実装>` を
  一時ファイルに出せば正解役として呼べる（今回、境界の golden はこの方法で追加で作れた）。正解役の振る舞いが版に依存するなら
  （Python 3.12 の sum 等）、golden を作った版を golden の横に残す
  - 切り出し先: `_claude/rules/adversarial-review-own-safeguards.md` の 0-B（旧実装を正解役にする既存の項）への 1〜2 行の追記
- **B. 数値の計算をビット単位で別の言語へ移すときは、golden を実データ由来だけで作らず、境界（フレームの中点ちょうど・丸めの
  ちょうど半分・整数の -0）を狙った合成の入力でも作る**（2 の一般形）。言語の側の差（コンパイラの演算の融合 = FMA、組み込みの sum の
  補正、round の偶数丸め）は、境界の入力でしか表に出ない。Go なら明示的な `float64()` の変換で融合を止められる（C / C++ の
  `-ffp-contract` と同じ問題）
  - 切り出し先: `_claude/rules-checklists/mutation-verify-new-tests.md` の「fixture と前提」の項への追記
- **C. ツールで書いたファイルに、エスケープ表記（`\u` の後に 16 進 4 桁）が意図どおり残っているかを、書いた直後に grep で確かめる**
  （3 の一般形）。2 回再現した。書くなら `\x5c` のようにツールが解釈しない形にするか、スクリプトでバックスラッシュを組み立てる
  - 切り出し先: `_claude/rules/verify-execution-not-just-exit-code.md` への 1 行の追記。あわせて Claude Code へのフィードバックの下書きを作った
- **D. 後始末・中断の仕組みは、自前の登録表より、言語が用意する構造（Go なら context の取り消しと defer、Python なら例外と with）に
  載せる**（4 の一般形）。自前の表は順序・競合・終了の仕方を全部自分で正しくする必要がある
  - 切り出し先: `_claude/rules/adversarial-review-own-safeguards.md` の 0-A（作らずに済む構造を問う）への 1 行の追記
- **E. 指摘を直すとき、直す関数の呼び出し元が複数の意味で使っていないかを確かめてから変える**（5 の一般形）。同じ「置き換え」の
  関数でも、呼び出し元ごとに守る意味が違うことがある
  - 切り出し先: `_claude/rules/adversarial-review-own-safeguards.md` の §7（指摘への修正は新しい安全機構）への 1 行の追記
- 却下: 6 を新しい規則にすること。`verify-execution-not-just-exit-code.md` の確認表の「集約 target への配線 → 集約 target 経由で実行して
  出力を確認する。個別に直接叩いた結果で代用しない」が既にあり、今回はそれを守らなかった。代わりに、新しい Go プロジェクトの手順書
  `src/README.md` の 3 点セットに、空の go.sum と root の `make test-lint` を書き足した（このコミットで直した。入口の手順書の不足だった）
- 局所（提案にしない）: `mutate-verify` の「全体のログ」が `$TMPDIR` に 1 本ずつ残る（設計どおり残しているもの。今回は手で消した）。
