# 148 feat: glogx doctor — 環境の健全性診断 (ディスク占有 / サービス)

## 背景

2026-09-01、手動でディスク棚卸しをして **41GB** を解放した。問題は「解放できたこと」ではなく
**誰も気づけない場所に、誰も掃除しない仕組みで、9ヶ月分積もっていた**こと。

実測で確認した事実 (この issue の設計根拠):

| 事実 | 実測値 |
|---|---|
| `/private/var/tmp` は**再起動でクリアされない** | 起動 (2026-07-27) より古いファイル **576 件** |
| `/private/tmp` はクリアされる | 同条件で **0 件** |
| 掃除する仕組みが**存在しない** | `/etc/periodic/daily/` が現在の macOS に無い (廃止済み) |
| 結果、放置期間 | XCTest ログの最古が **2025-12-27** (9ヶ月) |

つまり `/var/tmp` は「消えない設計」なのに「掃除する仕組みが無い」。置かれたものは永久に残る。
これは macOS の仕様どおりの動作で、バグではない。**だから自動では絶対に解決しない。**

解放の内訳 (今回の実績):

| 対象 | 解放 |
|---|---|
| Xcode DerivedData (最終更新 6〜7月) | 19GB |
| Xcode iOS DeviceSupport | 11GB |
| npm `_cacache` | 9.9GB |
| Finder 残骸 `TemporaryItems/NSIRD_Finder_*` | 4.3GB |
| XCTest ログ `/var/tmp/*.logarchive` | 1.8GB |
| TorBrowser-Data | 662MB |

**同じ日の 2 回目の棚卸しで、上の表より大きい塊がもう 1 つ出た。**
この issue の初稿を書き終えた後に別の切り口 (マウント済みディスクイメージ) で調べたところ、
**シミュレータランタイム 33.2GB** が見つかった。加えて brew の残骸 801MB、
未参照のバージョンマネージャ root 2.2GB、孤児コンテナ 1.0GB。

| 追加で見つかった対象 | 解放 | なぜ 1 回目で見つからなかったか |
|---|---|---|
| シミュレータランタイム | **33.2GB** | 実体が SIP 配下にあり、`du` でホームを掘っても出ない |
| `~/.nodenv` (未参照の nodenv root) | 2.2GB | 現役の `~/.rbenv` と**見た目が同じ**で区別がつかない |
| brew 残骸 (`var/mysql` / 古い portable-ruby 等) | 801MB | `~/Library/Caches/Homebrew` の外にある |
| `~/Library/Containers/com.docker.docker` | 1.0GB | アプリが無いことに気づく手段が無い |

**これは「初稿の列挙が甘かった」ではなく、この issue の存在意義そのものである。**
1 回目で 41GB 見つけた人間が、同じ日に**もう一度探したら 37GB 出てきた**。
手作業の棚卸しは網羅できない。カタログを持つ意味はここにある。

**同じ日に、プロセス側にも同型の問題が見つかった。** アンインストール済みの
`mysql@8.0` の launchd 登録が残り、**35 日間ずっと起動に失敗し続けていた**
(`last exit 78` / penalty box 入り)。ディスクと同じく、**誰も気づけない場所で、
誰も掃除しない仕組みで、放置されていた**。詳細と設計は `4. サービス診断` に置く。

## ゴール / 非ゴール

**ゴール**
- **既知の掃除候補を、リスク付きで一覧できる**ようにする (どこが太いか + 消すと何が起きるか)
- **壊れた launchd 登録** (起動対象が無い / 失敗し続けている) を検出する (`4. サービス診断`)
- 一度スキャンしたら、その結果を**起動時に思い出させる** (放置を「気づけない」状態にしない)
- 削除は**人間が対象を選んで明示的に実行**する。安全ガードはツール側が持つ

**非ゴール**
- 自動削除。**しない**。閾値超過でも勝手に消さない (後述「安全性ハーネス」の第一原則)
- **サービスの停止・削除をツールが実行すること。しない。** サービス診断は
  **検出とコマンド提示まで** (`4. サービス診断 > 出力は「検出とコマンド提示」まで`)
- **孤児・残骸プロセスの検出。しない** (当初やる予定だったが、
  **判定材料が実測で全部崩れた**。経緯と実測値は `5` 章に記録として残す)
- **自動スキャンもしない。** 起動時に走査しない以上、
  「放置を自動検出する」ことは**この機能の守備範囲外**
  (一度も doctor を開かないユーザーには何も起きない。これは受け入れる)
- 汎用ディスク解析ツール (`ncdu` / DaisyDisk の再実装) にすること。
  **既知の掃除候補に限定**し、代わりに「消してよいか」の判断材料 (リスク・復元方法) を持つ
  ことで差別化する。「どこが太いか」だけなら既存ツールで足りる
- **常駐プロセスの要不要の判定。しない** (ツールには判断できない。
  `4. サービス診断 > 対象化しない判断と根拠`)
- ユーザーデータの整理 (Downloads の動画重複など) — 別 issue

## 1. 対象ディレクトリの分類

**allowlist 方式**で定義する。「ここは消していい」を列挙するのであって、
「ここ以外は消す」ではない。未知のディレクトリは**常に対象外**。

**カタログに載せる条件は「大きいこと」ではなく「消したまま戻らないこと」。**
サイズだけで拾うと、`sleepimage` (次のスリープで再生成) や unified logging
(ローテート済みの定常状態) のような**消しても戻るもの**を毎回提案し続けることになる。
候補を追加するときは必ず「消した後どうなるか」を実測してから登録する
(この 2 件を実際に除外した経緯は後述)。

各エントリは以下を持つ:

```
id           識別子 (xcode-deriveddata 等)
path         対象パス (テンプレート展開可)
tier         1〜4
label        人間向け表示名
recover      復元方法の一文 (「次回ビルドで再生成」等) ← UI に必ず出す
guard        追加判定 (orphan 判定 / プロセス判定など。後述)
deleteVia    削除経路 (rm | trash | cli:<コマンド> | propose)。後述
sudo         true なら提案のみ・実行しない
```

### Tier 1 — 純粋なキャッシュ (無条件に安全・再生成される)

| id | path | recover | deleteVia |
|---|---|---|---|
| `xcode-deriveddata` | `~/Library/Developer/Xcode/DerivedData/*` | 次回ビルドで再生成 (初回は遅くなる) | `rm` |
| `xcode-devicesupport` | `~/Library/Developer/Xcode/*` + ` DeviceSupport/*` | 実機再接続で再取得 | `rm` |
| `npm-cache` | `~/.npm/_cacache` | `npm cache clean --force` 相当 | `rm` |
| `swiftpm-cache` | `~/Library/Caches/org.swift.swiftpm` | 次回解決時に再取得 | `rm` |
| `electron-cache` | `~/Library/Caches/electron` | 再ダウンロード | `rm` |
| `playwright-cache` | `~/Library/Caches/ms-playwright` | `npx playwright install` | `rm` |
| `homebrew-cache` | `~/Library/Caches/Homebrew` | 再ダウンロード。⚠️ 下記のとおり **`brew cleanup` を先に案内**する | `rm` |
| `simulator-runtimes` | `xcrun simctl runtime list` が返す各 image | Xcode / `simctl runtime add` で再取得 (数GB/個) | **`cli:simctl`** |
| `go-modcache` | `~/go/<ver>/pkg/mod` | 次回 build で再取得 | **`cli:go clean -modcache`** |
| `go-build` | `~/Library/Caches/go-build` | 次回 build で再生成 | `rm` |
| `headless-chrome-dl` | `~/.cache/rod`, `~/.cache/chrome-devtools-mcp` | 各ツールが再ダウンロード | `rm` |
| `node-gyp-cache` | `~/Library/Caches/node-gyp` | 次回ネイティブビルドで再取得 | `rm` |

2026-09-01 の実測 (棚卸し後の残量): `swiftpm-cache` 3.0GB / `electron-cache` 1.8GB /
`playwright-cache` 891MB / `simulator-runtimes` **33.2GB** / `go-modcache` 2.4GB
(`~/go/1.24.4` 1.7GB + `~/go/1.26.0` 690MB) / `go-build` 160MB /
`headless-chrome-dl` 496MB / `node-gyp-cache` 117MB。

> `~/go/<ver>/pkg/mod` が**バージョンごとに分かれている**のは goenv の GOPATH レイアウトによる。
> 現行が 1.26.0 でも **1.24.4 の GOPATH に 1.7GB が残る**。「今使っている版のキャッシュ」だけを
> 見ると 4 割しか見えない。`~/go/*/pkg/mod` を**全世代**走査すること。

> **`xcode-devicesupport` のグロブは iOS 限定にしないこと** (2026-09-01 レビュー)。
> Xcode は watchOS / tvOS の実機を繋ぐと `watchOS DeviceSupport` / `tvOS DeviceSupport` も作る。
> ⚠️ ただしこの機には現在 `iOS DeviceSupport` しか存在せず、**他 OS 版は未実測**。
> カタログの登録条件 (実測してから登録) に厳密に従うなら、
> グロブ拡張の可否は `8. 未決事項` の判断待ちとして扱う。

> 小物の同型キャッシュ (`electron-builder` 82MB / `typescript` 31MB / `deno` 27MB) も
> 構造は同じだが、**1 件あたりが小さく行が増えるだけ**なので初期リリースでは載せない
> (`8. 未決事項`)。

### Tier 2 — 残骸 (孤児判定が要る)

| id | path | guard |
|---|---|---|
| `xctest-logarchive` | `/private/var/tmp/*.logarchive` | mtime が起動時刻より古い |
| `xctest-spindump` | `/private/var/tmp/XCTestTesting.*.spindump.txt` | 同上 |
| `coresimulator-orphan` | `/private/var/tmp/com.apple.CoreSimulator.SimDevice.*` | **`simctl list devices` に無い UUID のみ** |
| `launchd-tmp` | `/private/var/tmp/com.apple.launchd.*` | mtime が起動時刻より古い (容量はほぼ 0。件数削減が目的) |
| `finder-nsird` | `$TMPDIR/TemporaryItems/NSIRD_Finder_*` | **中身がユーザーファイルの可能性あり → 常に中身を一覧表示** |
| `swiftui-drag-cache` | `~/Library/Caches/com.apple.SwiftUI.Drag-*` | **同上 (`finder-nsird` と同型)。常に中身を一覧表示** |
| `orphan-container` | `~/Library/Containers/<bundle-id>` | アプリ実体が無い。⚠️ 判定方法に罠あり (後述) |
| `brew-orphan-state` | `/opt/homebrew/{var,etc}/*` | 対応 formula が `brew list` に無い |
| `brew-cleanup-residue` | `/opt/homebrew/Library/Homebrew/vendor/portable-ruby/*` | `brew cleanup --dry-run` が対象に挙げるもの |
| `versionmanager-orphan-root` | `~/.rbenv`, `~/.nodenv`, `~/.goenv` | `*_ROOT` の実効値と一致しないもの |

> `coresimulator-orphan` の孤児判定は今回実際に効いた: 9 件すべてが孤児 (現存シミュレータ 0 件)
> だった。UUID を照合せずにパターンだけで消すと、**現役シミュレータの作業領域を壊す**。

> `finder-nsird` は今回 4.3GB あり、中身は**動画ファイル**だった。Finder のコピー/移動が
> 中断した残骸で通常は元ファイルが別にあるが、**唯一のコピーである可能性を排除できない**。
> よってこのエントリだけは「サイズ」ではなく**中身のファイル名一覧**を UI に出す。

> **`swiftui-drag-cache` は `finder-nsird` と完全に同型** (2026-09-01 実測で追加)。
> `~/Library/Caches/com.apple.SwiftUI.Drag-<UUID>/` に **258MB**、中身は 2026-02-10 の
> 動画ファイル 1 件で、**ドラッグが完了せず取り残された実体**だった。
> パスが `Caches` 配下なので Tier 1 に入れたくなるが、**中身はユーザーファイル**である。
> 「`Caches` にあるから再生成される」という推論が成立しない実例として、
> `risk: confirm` + 中身一覧 + ゴミ箱移動を `finder-nsird` と同じく適用する。

> **`brew-cleanup-residue` は `homebrew-cache` のパスでは検出できない** (2026-09-01 実測)。
> `brew cleanup` が消す古い `portable-ruby` (今回 **12 世代 424MB**) は
> `~/Library/Caches/Homebrew` ではなく `/opt/homebrew/Library/Homebrew/vendor/` にある。
> つまり現行カタログは「`brew cleanup` を案内する」と書きながら、
> **その案内が解放する 424MB を事前のサイズ表示に載せられていない**。両方を対象にする。

> **`brew-orphan-state` はディスクとサービスの両面に同じ孤児が現れる** (2026-09-01 実測)。
> `mysql@8.0` は `brew uninstall` 済みだが `/opt/homebrew/var/mysql` に **376MB** の
> DB データが残り、同時に `~/Library/LaunchAgents/homebrew.mxcl.mysql@8.0.plist` の
> 壊れた登録も残っていた (`4. サービス診断` の分類 C)。
> **片方だけ消すともう片方が残る**ので、両診断の結果は同一の孤児として相互参照させる。
> ⚠️ `var/<formula>` は**データ本体**なので `risk: confirm` (中身を見せてから確認) にする。
> 「formula が無い = 消してよい」ではない (DB の中身は formula とは別に価値を持つ)。

> **`versionmanager-orphan-root` は `*_ROOT` の実効値で判定する** (2026-09-01 実測)。
> `~/.nodenv` に **2.2GB** (node 4 世代) があったが、`NODENV_ROOT` の実効値は
> `~/.anyenv/envs/nodenv` で、`.zshrc` の lazy loader は anyenv 側が存在する限り
> `~/.nodenv` へ fallback しない。shell 設定に `~/.nodenv` を指す記述は**ゼロ件**だった。
> ⚠️ **`~/.rbenv` は同じ形をしているが現役**だった (anyenv 側に rbenv が無いため fallback が効き、
> `ruby` / `gem` / `bundle` がすべてここの shim を通っていた)。
> **ディレクトリの存在ではなく、実効 ROOT との一致で判定すること。**
> 判定は `<TOOL>_ROOT` を解決してから行い、解決できなければ **fail-closed で候補にしない**。

### Tier 3 — アプリ起動中は触らない

| id | path | guard |
|---|---|---|
| `chrome-tmp` | `$TMPDIR/.com.google.Chrome.*` | **`Google Chrome` プロセスが無いときのみ** |
| `speech-model-cache` | `/private/var/tmp/SpeechModelCache` | ⚠️ **初期リリースでは採用しない** (下記) |

> **`homebrew-cache` は公式経路を先に案内する** (codex 反証):
> Homebrew には `brew cleanup` / `brew cleanup --dry-run` という**公式の掃除経路**がある。
> ディレクトリを raw delete する前に、まず `brew cleanup` の実行を案内すること。
> ただし今回の実測では `brew cleanup` 実行後も **200MB が残った**
> (「最新版が未インストールなので古い版を消せない」と判断してスキップした formula がある)。
> よって「`brew cleanup` を案内 → それでも残る分を候補として出す」の二段構えにする。

> **`speech-model-cache` は初期リリースの対象から外す** (codex 反証):
> `/private/var/tmp/SpeechModelCache` は 840MB の `.bnnsir` 群で、**OS / システムサービスの
> 管理物**に見える。「mtime が起動時刻より古い」だけでは使用中でない証明にならず
> (read-only で開かれても mtime は変わらない)、**再生成の条件も副作用も不明**。
> カタログ登録の条件 (「消したまま戻らないこと」を実測で確認) を満たせていないため、
> **調べがつくまで載せない**。載せるなら `lsof` による使用中判定と、
> 削除後に音声機能が壊れないことの確認が要る。

### Tier 3 の追加ガード

Tier 3 は「アプリ起動中は触らない」だけでは足りない。**OS / サービス管理物**については
`lsof` で**開いているプロセスが無いこと**を確認する。それでも確証が持てないものは
カタログに載せない (上記 `speech-model-cache` がその例)。

### Tier 4 — sudo 必須 (**検出のみ。実行しない**)

現時点で**該当エントリなし**。当初 `unified-log` と `sleepimage` を候補にしたが、
実測の結果**どちらも対象外**と判断した (下記「対象化しない判断と根拠」参照)。

Tier 4 という枠自体は残す。将来 sudo が要る候補を見つけたときは、
**コマンド文字列を表示するだけ**とし、ツールからは絶対に実行しない
(sudo をツールに持たせない)。

### 削除経路 (`deleteVia`) — tier とは直交する軸

**tier は「どれくらい危険か」を表すが、「どうやって消すか」は表せない。**
初稿は削除手段を `rm` と `sudo` (提示のみ) の 2 択で捉えていたが、
2026-09-01 の実測で**どちらでもない対象が最大の塊だった**ため、独立した属性に切り出す。

| `deleteVia` | 意味 | 例 |
|---|---|---|
| `rm` | ツールが直接削除する | Tier 1 の大半 |
| `trash` | ゴミ箱へ移動 (`risk: confirm` は必ずこれ) | `finder-nsird`, `swiftui-drag-cache` |
| `cli:<コマンド>` | **専用 CLI を実行する。`rm` してはいけない** | `simulator-runtimes`, `go-modcache` |
| `propose` | コマンドを表示するだけ。ツールは実行しない | Tier 4 (sudo 必須のもの) |

`cli:` が必要な理由 (`simulator-runtimes` の実測):

- 実体は `/System/Library/AssetsV2/com_apple_MobileAsset_*SimulatorRuntime/` にあり
  **SIP 配下で `rm` できない**
- 同時に `/Library/Developer/CoreSimulator/Volumes/<name>` へ**マウントされている**。
  `hdiutil` でアンマウントしても**登録は残る**ので容量は戻らない
- 正しい経路は `xcrun simctl runtime delete <id>` のみ。
  削除後は `xcrun simctl delete unavailable` で**孤児デバイスも掃除**する
  (ランタイムを消すとデバイスが宙に浮く)
- 候補の抽出とサイズは `xcrun simctl runtime list -v` から取れる。
  同出力の **`Last Used At`** が古さの根拠になる (`mtime` 相当の一次フィルタ)

⚠️ `cli:` は「外部コマンドを実行する」ため、`4. サービス診断` が
**削除サブコマンドを持たない**と決めたのとは方針が異なる。線引きは次のとおり:

- **ディスク**は「消す対象」が allowlist で確定しており、消した結果も `recover` で戻せる
  → ツールが実行してよい (ただし `2. 安全性ハーネス` の全ガードを通す)
- **サービス**は「止めてよいか」がユーザーの用途に依存し、機械的に確定しない
  → 実行しない (`4. サービス診断 > 出力は「検出とコマンド提示」まで`)

### ⚠️ `orphan-container` の孤児判定を `mdfind` 単独に置かないこと

**この機で実際に偽陽性が出た** (2026-09-01 実測)。bundle id からアプリを探して
見つからなければ孤児、という素朴な実装は次を出した:

| 判定 | 実測 |
|---|---|
| `com.docker.docker` 1035MB → 孤児 | ✅ 正しい (`Docker.app` は実在しない) |
| `com.jiikko.dropbox-video-player` 151MB → 孤児 | ❌ **偽陽性**。アプリは実在する |

`/Applications/Multi-Video Player for Dropbox.app` は**実在していた**。
`mdfind "kMDItemCFBundleIdentifier == ..."` が返さなかっただけで、
**Spotlight のインデックス欠落**が原因である。しかもこのコンテナの中身は
そのアプリのトライアル状態 (`entitlement.json`) で、消せば開発環境の state が飛ぶ。

したがって:

- **`mdfind` を単独の判定根拠にしない。** `/Applications` と `~/Applications` を実走査し、
  各 `Info.plist` の `CFBundleIdentifier` を読んで突き合わせる (インデックス依存を外す)
- 走査に失敗したら **fail-closed** (「孤児でない」に倒す)。
  `2. 安全性ハーネス > 検出の健全性` に従い「走査できず」として表示する
- それでも残る偽陽性は**除外リスト**で塞ぐ (下記「明示的除外リスト」に自作アプリを追加済み)

### 対象化しない判断と根拠 (2026-09-01 実測)

「技術的には消せる」が「消す価値がない」ものを、再検討が繰り返されないよう根拠つきで残す。

**`/private/var/db/diagnostics` (unified logging, 2.4GB) — 対象外**

正常にローテートしており、2.4GB は上限に張り付いた**定常状態**。実測:

| 領域 | サイズ | 件数 | 保持期間 |
|---|---|---|---|
| `Persist/` | 501M | 51 | **0.7 日** |
| `Special/` | 1.5G | 1001 | **8.8 日** |
| `Signpost/` | 331M | 171 | **7.2 日** |

最古でも 8.8 日前で、それ以前は自動破棄されている。消しても数日で同サイズに戻る一方、
**過去のログを失って調査能力が落ちる** (「先週から時々おかしい」系の追跡ができなくなる)。
割に合わない。

**`/private/var/vm/sleepimage` (2.0GB) — 対象外**

ハイバネーション用のメモリイメージ。実測: 物理メモリ 32GB / `hibernatemode 3` /
`standby 1`。**次のスリープで再生成される**ため、消しても 2GB はすぐ戻る。
恒久的に消すには `pmset -a hibernatemode 0` が要るが、**バッテリー切れ時に
作業状態を失う**トレードオフになる。ディスク解放の手段として不適切。

**`~/Library/Caches/Google/Chrome` (3.5GB) — 対象外**

2026-09-01 実測で 3.5GB あり、サイズだけ見れば上位に入る。しかし Chrome は
**通常のブラウジング中に自分でキャッシュを再生成し、上限も自分で管理する**。
`sleepimage` と同じ「消しても勝手に戻る」型で、提案しても数日で同じ行が復活する。

⚠️ **`~/Library/Application Support/Google` (7.4GB) と混同しないこと。**
こちらはプロフィール・履歴・拡張機能などの**ユーザーデータ**で、
除外リスト側 (絶対に対象化しない) の扱いになる。名前が似ていて隣接しているため、
グロブを緩めると片方から他方へ簡単に踏み込む。

> どちらも「サイズが大きい」だけで候補に見えるが、**再生成される / 定常状態である**という
> 性質を見ずにサイズだけで拾うと、この 2 つのような無駄な提案を毎回出すことになる。
> **カタログに載せる条件は「大きいこと」ではなく「消したまま戻らないこと」**。

### 明示的除外リスト (絶対に対象化しない)

allowlist 方式なので原理的に不要だが、**将来の追加時に誤って入れないための番人**として
明示し、テストで固定する:

- `~/Library/CloudStorage/**` — Dropbox の実体。走査すると**オンライン専用ファイルを
  materialize してディスクを逆に食う**
- `~/Library/Messages/**` — iMessage 履歴 (ユーザーデータ)
- `~/Documents`, `~/Desktop`, `~/Pictures`, `~/Movies` — ユーザーデータ
- `~/Downloads` — 中身はユーザーデータ。ただし `*.crdownload` (中断DL) のみ Tier 2 候補として
  検討可 (別 issue で判断)
- `~/src/**` の `node_modules` / `build` — 再生成可能だが**プロジェクト単位の判断**が要る。
  一括削除の対象にしない (別 issue)
- Time Machine ローカルスナップショット — `tmutil` の領分
- **自作・開発中アプリの sandbox コンテナ** — `~/Library/Containers/<自分のアプリの bundle-id>`。
  開発中のアプリは「実体が見つからない」状態を頻繁に通過する (ビルド前 / 再インストール中 /
  TestFlight 版のみ)。中身は entitlement・トライアル状態などの**検証用の状態**で、
  消すと手元の開発環境が壊れる (下記の偽陽性の実例を参照)
- `~/.cache/dein` — パスは `.cache` だが中身は `repos/` = **neovim プラグインの実体**。
  「`.cache` という名前だから再生成される」という推論が成立しない実例 (2026-09-01 実測 355MB)

## 2. 安全性ハーネス

破壊的操作 (削除) を持つツールなので、ここが本体。
`~/.claude/rules/adversarial-review-own-safeguards.md` に従い、
**自己レビューで閉じず、異常系を実験で作って敵対的レビューを最終ゲートにする。**

### 第一原則: 自動削除しない

- 検出・通知・一覧表示までが自動。**削除は必ず人間の明示操作**
- 「閾値を超えたので消しました」は**実装してはならない**
- `--yes` 相当のフラグも作らない (CI もこのツールを使わない)

### パス安全性 (実行前ガード)

今回の作業で実際に踏みかけた事故を潰す:

1. **空パス展開の禁止**: `$TMPDIR` 等が空のまま `rm -rf "$T"/foo` を組み立てると
   `rm -rf /foo` になる。**変数が空なら即中止**。今回は手作業でガードを入れて回避した
2. **接頭辞検査は「リンクを解決せずに」行う**
   - ⚠️ `filepath.EvalSymlinks` を正規化に使わないこと。**最終ターゲットまで解決してしまう**ため、
     prefix 検査を通った後に**リンク先の実体を消す**設計になりうる (下の 3 と矛盾する)
   - 使うのは `filepath.Abs` + `filepath.Clean` + **`..` を含まないことの確認**に留める
   - 親ディレクトリ側は `os.Lstat` で辿り、**経路の途中にリンクが挟まっていたら拒否**する
3. **シンボリックリンクを辿らない**: 対象がリンクなら**リンク自体だけ**を消す (`os.Remove`)。
   リンク先には絶対に踏み込まない (`~/Library/Caches` に外部ボリュームへのリンクがある事例)。
   走査時も `filepath.WalkDir` の既定どおり**リンクを辿らない**
4. **TOCTOU を塞ぐ**: スキャン〜確認〜削除の間にパスを差し替えられる余地がある
   (`/private/var/tmp` は `drwxrwxrwt` で**誰でも書ける**)。
   - 削除の直前に `os.Lstat` を取り直し、**スキャン時に記録した `(dev, ino)` と一致すること**を
     確認してから消す。一致しなければ**そのエントリを飛ばして報告**する
   - 「スキャン時に見たもの」と「今消すもの」が同一である保証を、パス文字列に置かない
5. **深さ・ルートのガード**: `/`, `/Users`, `/Users/<name>`, `$HOME` そのもの、
   パス深さが閾値未満のものは**問答無用で拒否**
6. **ワイルドカード展開結果が 0 件なら何もしない** (`no matches` を成功に畳まない)

### プロセス使用中の判定

**部分一致でプロセスを判定しない。** 今回 `pgrep -i "tor"` が
`thermalmonitord` / `CotEditor` / `Activity Monitor` にマッチし、
TorBrowser-Data の削除を誤ってスキップした (誤検出と気づけたのは目視したから)。

- プロセス名は**完全一致** (`pgrep -x`) か、実行パスでの判定を使う
- 判定に使う名前は allowlist エントリに明示的に持たせる (推測しない)

### 「使用中でない」ことの判定

今回有効だった手法を採用する:

- **システム起動時刻 (`kern.boottime`) より mtime が古いものだけを候補にする**
- 根拠: 再起動を生き延びている = **少なくとも起動後に書かれてはいない**

⚠️ **ただしこれは「使用中でない」の証明にはならない** (codex 反証で判明):
**起動後にプロセスが古いファイルを read-only で開いても mtime は更新されない。**
`launchd-tmp` / `xctest-*` / `speech-model-cache` のような **OS・サービス管理物**で
この判定だけを削除ゲートにするのは危険。

したがって:

- mtime は**候補を絞る一次フィルタ**として使う (安いので最初に効かせる)
- **削除の可否は別の根拠で決める**:
  - `coresimulator-orphan` → **`simctl` との UUID 照合** (存在しないデバイス = 孤児)
  - `chrome-tmp` → **プロセス不在** (完全一致判定)
  - OS 管理物 (`speech-model-cache` 等) → **`lsof` で開いているプロセスが無いこと**を確認、
    それでも確証が持てないものは**カタログから外す** (下記 Tier 3 の注記を参照)
- 「mtime が古い」だけを根拠にできるのは、**生成元が明確に終了している残骸**
  (`xctest-logarchive` = 特定のテストセッションの産物) に限る
- `sysctl kern.boottime` のパースに注意。**`sec` と `usec` を取り違えると起動時刻が
  1970 年になり、判定が全件通過/全件棄却に化ける** (今回実際に踏んだ。
  `sed -n 's/.*sec = \([0-9]*\),.*/\1/p'` のようにカンマまで含めて `sec` を取る)
- パースに失敗したら**候補 0 件として扱う** (fail-closed)

### dry-run と記録

- **デフォルトが dry-run**。実削除には明示フラグが要る
- 削除実行時は**削除前のインベントリ** (パス・サイズ・mtime・`(dev, ino)`) を
  **`cacheBaseDir()` 配下**の `doctor-history/<timestamp>.json` に残す。何を消したか後から追える
  - ⚠️ パスをハードコードしないこと。既存の `cacheBaseDir()` (`src/glogx/cache.go`) は
    **`$XDG_CACHE_HOME/glog` (未設定時 `~/.cache/glog`)** を返す。
    **`glogx` ではなく `glog`** である点に注意 (codex 反証で判明)
  - ⚠️ インベントリは**記録であって復元手段ではない**。消したファイルは戻らない
- 削除は**エントリ単位**で行い、途中失敗しても他に波及させない

### 検出の健全性 (sinking silently の禁止)

- 走査中の権限エラー・パス消失を `2>/dev/null` 相当で握り潰して「0 件」にしない。
  **「走査できなかった」を第 3 の状態**として持ち、UI に出す
- 「候補 0 件」と「走査に失敗した」を同じ表示にしない

### 削除の健全性 (「消えたつもり」の禁止)

上の「検出の健全性」はスキャン側の規律だが、**削除側にも同じ規律が要る**。
2026-09-01 に実地で踏んだ (`simulator-runtimes` の削除):

```
$ xcrun simctl runtime delete all     # 出力ゼロ。成功に見える
$ xcrun simctl runtime list           # 6 個 (33.2G) がそのまま残っている

$ xcrun simctl runtime delete <UUID>  # ID 指定で初めて実体が見える
rc=24
stdout=[]
stderr=[Please retry in 48s, if the image is not removed]
```

**削除は非同期で、真相は stderr にしかなく、stdout は空**だった。
`2>&1` で混ぜて `| tail` に流していたら、この行を成功ログの一部として読み飛ばす。

したがって:

- **解放量は「削除コマンドが成功したこと」から計算しない。**
  削除後に**対象を再スキャンし、実際に消えたことを確認してから**数字を出す
- 外部コマンド (`deleteVia: cli:`) は **stdout / stderr / exit code を最初から分離**して測る
  (`~/.claude/rules/measure-external-cli-streams-separately.md`)
- **非同期削除を想定する。** 「コマンドが返った = 消えた」ではない。
  再スキャンで消えていなければ「削除を要求したが未完了」を**第 3 の状態**として表示する
  (成功にも失敗にも畳まない)
- 消えなかったエントリは**次回スキャンでまた出る**のが正しい。
  「一度消したことにする」キャッシュ更新をしない

### テストハーネス

- **偽の HOME / 偽の TMPDIR** の下にツリーを作って全ケースを回す (実データを触らない)
- 必ず作る異常系:
  - 対象 0 件 / ディレクトリ自体が存在しない
  - 変数が空 (`TMPDIR=""`)
  - 対象がシンボリックリンク (リンク先に実データを置き、**消えていないこと**を assert)
  - 対象が `/` や `$HOME` になるよう仕込む → **拒否されること**
  - `simctl` が失敗する / 存在しない → 孤児判定が**全件「孤児でない」に倒れること** (fail-closed)
  - `kern.boottime` のパース失敗 → **候補 0 件**になること
  - 走査中に権限エラー → 「走査失敗」として報告されること
- **新規テストは変異を 1 つ当てて red を見るまで確認する**
  (`~/.claude/rules/mutation-verify-new-tests.md`)。
  例: ルートガードを外す変異を当てて、テストが確実に落ちること

## 3. glogx doctor 機能

### 要求 (ユーザー原文)

> glogx を起動して、10GB 以上のファイルを削除可能性です、みたいなトーストが出て欲しい

> glogx 起動時にボトルネックの調査をして欲しいが、時間がかかる気がするので、
> **本機能を起動した時にスキャンを開始**をして、どのディレクトリにどのくらい占めているのかが
> **占有量の並びでリスト**していて、**削除のリスクとかのアドバイス**も書いていて欲しい

> この機能は **doctor 機能**にしよう

> **起動時のスキャンはやらなくていい**。**明示的にスキャンを開始**して、
> **その結果を起動時に参照**できれば、削除可能なサイズをトーストで出す、ってやりたい

↑ **この最後の一文がこの機能の骨格**。スキャンは常に人間の操作で始まり、
起動時は「前回の結果を読むだけ」。**起動時に走査する実装は要件違反**とする。

### 位置づけ: doctor = 健全性診断の集約画面

`brew doctor` / `flutter doctor` と同じ枠組み。**「今この環境で問題になっていることを
並べて見せる」画面**とし、今回は診断項目を **2 つ**実装する:
**①ディスク占有** (`1`〜`2` 章) と **②サービス** (`4` 章)。

**この 2 つは「器」の設計を検証するためのペアでもある。** 片方は走査が重くて削除を伴い、
もう片方は外部コマンド依存で削除を伴わない。**性質が違う 2 項目が同じ器に載る**ことを
確認しておくと、将来の診断項目 (例: 古い worktree の残留、巨大な git object、期限切れ証明書) を
**同じ枠に足せる形**になっているか判断できる。既存の CLI health 検査 (`cli_health.go`:
claude / codex のログイン状態) も概念的には doctor の一項目だが、
**今回は移設しない** (起動時トーストとして既に機能しており、動かす必要がない。
doctor 側から参照だけできるようにする)。

### スキャンの三層構造 (この機能の核)

ディスク走査は重い (今回の実測で `~/Library/Developer` の 30GB に数十秒)。
一方 `bin/glogx` は tmux popup (`C-g`) 起動で、冒頭コメントが
「ビルド待ちを popup 内に見せない」と書いており、**起動を待たせないことが重視されている**
(ただしこのコメントは再ビルド待ちについての記述であり、
「glogx の起動が一切の同期処理を持たない」という意味ではない。
制約の根拠としてはこれを過大に読まないこと)。

この2つを両立させるため、**タイミングを3層に分ける**:

| # | タイミング | 動作 | 待たせるか |
|---|---|---|---|
| 1 | **glogx 起動時** | **走査しない。** キャッシュを読むだけ。閾値超えならトースト | ❌ 絶対にブロックしない |
| 2 | **doctor を開いた時** | **ここでスキャン開始。** 進捗を出し、終わったものから順次表示 | ⭕ 待たせてよい |
| 3 | doctor 内で `r` | 明示的な再スキャン (キャッシュを無視) | ⭕ 待たせてよい |

**なぜ 2 で待たせてよいか**: doctor は「診断したくて自分で開く」画面なので、
数十秒かかることに納得感がある。逆に 1 で待たせると popup 起動が壊れる。

スキャン結果は毎回キャッシュに保存し、**次回の 1 (起動時トースト) の材料**になる。
つまり初回はトーストが出ない (キャッシュが無い) が、一度 doctor を開けば以降は出る。
これは仕様として許容する。

### スキャン中の振る舞い

- **インクリメンタル表示**: 全項目の完了を待たない。終わったエントリから順にリストへ足す
  (今回の実測でも `/var/tmp` は数秒、`~/Library/Developer` は数十秒と**桁が違う**)
- **進捗表示**: `スキャン中 3/12 (~/Library/Caches/electron)` のように
  「今どこを見ているか」を出す。無言で固まらせない
- **キャンセル可能**: `Esc` で中断。中断時は**部分結果を捨てず**、
  完了済みエントリだけをキャッシュに書く (`partial: true` を立てる)
- **並行実行**: `checkCLIHealthCmd()` と同じく goroutine + `sync.WaitGroup`。
  ただし**ディスク I/O が競合する**ため同時実行数に上限を設ける (既定 4)
- **タイムアウト**: エントリごとに上限 (既定 60 秒)。超えたら
  そのエントリを「走査失敗」として記録し、**他を巻き込まない**

### 終了時の後始末 (走査プロセス・goroutine を残さない)

**問題**: doctor を開いてスキャン中に glogx を閉じると、走査が残り続ける恐れがある。
glogx は popup (`C-g`) 運用で**開閉が頻繁**なため、残留すると多重に積み上がり、
ディスク I/O を飽和させて**マシン全体を重くする**。しかもユーザーからは
「何も動いていないのに遅い」としか見えず、原因に到達しにくい。

**方針**:

1. **外部コマンド (`du` 等) を exec しない。Go の `filepath.WalkDir` で実装する**
   - 子プロセスを作らなければ、**後始末の問題が原理的に消える**
   - `exec.CommandContext` は ctx cancel 時に `Process.Kill()` を呼ぶが、
     **孫プロセスまでは殺さない** (プロセスグループを落とすには `Setpgid` が要る)。
     この複雑さを最初から抱えない
   - 副次的な利点: 権限エラーを**パス単位で捕捉**でき、
     「走査失敗」の第3状態 (前述) を作りやすい。`du` の出力パースも不要

   ⚠️ **サイズの意味論を `du` に合わせること** (codex 反証で判明)。
   素朴に `FileInfo.Size()` を合計すると **`du` と数字が食い違う**:

   | | `du` (今回の実測に使った) | `FileInfo.Size()` |
   |---|---|---|
   | 数えるもの | **実際に割り当てられたブロック** | apparent size (見かけのサイズ) |
   | ハードリンク | **同一 inode は 1 回だけ** | リンクの数だけ重複計上 |
   | sparse file / APFS clone | 実消費のみ | 実体より**大きく**出る |

   → **`Stat_t.Blocks * 512` を使い、`(dev, ino)` で dedupe する**。
   これを外すと「解放可能 GB」が**実際に空く量とずれる** (特に APFS の clone と
   Xcode/npm キャッシュのハードリンクで顕著)。**表示する数字は「消したら実際に空く量」であること。**

2. **`cancelAll()` に必ず結び付ける** (`src/glogx/tui.go` の `browseModel.cancelAll`)
   - `main.go` の「quit 経路 (q/Ctrl-C) 以外でも後始末を保証する多重防御
     (cancelAll は冪等)」にそのまま乗る
   - ⚠️ 既存の `cli_health.go` は**意図的に `cancelAll` と結び付けず**
     `context.Background()+timeout` を使っている。**その理由は「5 秒だから」ではなく**、
     コメントに書かれているとおり**既存のバージョン検査・`usage.Fetch` と
     `Background + timeout` の契約で揃えているため**。
     つまり「短いから許される」のではなく「既存契約に合わせた」もの
   - **それでもディスク走査は同じ契約に乗せない。** 理由は時間の桁が違うこと
     (5 秒 vs 60 秒級) と、**走査が I/O を占有してマシン全体を重くする**点で
     version check とは影響が異なるため。既存契約への追従より**残留させないこと**を優先する
   - **この判断はコードコメントに残す。** でないと「既存の検査群と揃える」名目で
     `context.Background()` に戻され、残留が復活する
     (`cli_health.go` のコメント自身が「検査群全体を終了時 cancel へ揃える改修時に見直す」
     と書いており、揃える方向の圧力が実在する)

3. **キャッシュ書き込みは atomic に** (temp file + `os.Rename`)
   - 中断・強制終了が書き込みと競合しても、**壊れたキャッシュを残さない**
   - 壊れたキャッシュを読んだ場合はクラッシュせず、**無視して再スキャンを促す**

4. **多重スキャンの抑止**
   - doctor の開閉・再スキャン連打で走査が多重化しないこと。
     実行中に再度要求されたら、**新規に始めず既存の走査に合流する**
   - CLI (`bin/diskdoctor`) 側はロックファイルで多重起動を防ぐ
     (将来 cron / launchd から回す場合にも効く)

**検証**: スキャン中に glogx を quit し、**残留プロセスと残留 goroutine が無いこと**を確認する。
子プロセスを作らない設計だが、退行検出として `pgrep` による確認も残す。

**表示ルール**:

- **占有量の降順で並べる**。tier 順ではない (ユーザーが見たいのは「どこが太いか」)
- 各行に**リスク記号 + 一行のアドバイス**を必ず添える。サイズだけの行を作らない
- 「走査できなかった」エントリも**リストに出す** (サイズは `---`)。
  黙って消すと「ゴミが無い」と誤解される (後述の差異を参照)
- ヘッダの**合計は「今消せる量」だけ**を数える。`blocked` (guard で対象外) と
  「走査できず」は行としては出すが**合計に足さない** (トーストの発火判定も同じ合計を使う)

### リスク助言のデータ

カタログの各エントリに、UI に出す文言を**データとして持たせる** (コードに散らさない):

```
risk      safe | caution | confirm | blocked   ← 記号と色に対応
advice    一行の助言 (「次回ビルドで再生成されます」)
detail    補足 (任意。「初回ビルドが遅くなるだけ」)
blockedBy 対象外の理由 (「Chrome 起動中」) — guard が弾いたときに埋まる
inspect   true なら [Enter] で中身一覧を出す (finder-nsird 用)
```

- `safe` … 再生成される。副作用は速度低下のみ
- `caution` … 再取得に時間・通信が要る、または設定が戻る
- `confirm` … **ユーザーデータの可能性**。中身を見せてから確認する (`finder-nsird`)
- `blocked` … guard により今は対象外 (プロセス起動中など)。理由を必ず出す

### 既存 `cliHealthSpec` との関係

宣言的な項目定義と並行実行は**既存パターンをそのまま踏襲**する
(`cli_health.go` の `cliHealthSpec` / `checkCLIHealthCmd`)。

**ただし「判定不能」の扱いは意図的に逆にする。**

| | cli_health (既存) | doctor のディスク診断 (本件) |
|---|---|---|
| 判定不能のとき | **無通知** | **「走査できず」と表示する** |
| 理由 | 誤ってログアウト警告を出すより黙るほうが無害 | 黙ると「ゴミが無い」と誤解され、**放置の再発**につながる |

既存コードのコメントは「判定不能は正常ではないが、誤ってログアウト警告を出すより
無通知にする」と明記しており、これは CLI health では正しい。
一方ディスク診断は**検出漏れが目的を殺す**ため、
`2. 安全性ハーネス > 検出の健全性` の方針 (走査失敗を第3の状態として出す) を優先する。
**この差異は実装時に必ずコメントで残すこと** (でないと「既存に揃える」名目で潰される)。

### トースト (起動時、キャッシュベース)

既存 API をそのまま使う (`src/glogx/toast.go`):

- `m.toast.showInfo(text)` — 情報色
- ⚠️ `toast` の内部状態は `toast.go` の外から触らない
  (`ruleguard.rules.go` の `toastEncapsulation` が禁止済み)

**発火条件**: **保存済みスキャン結果**の合計解放可能サイズが閾値以上 (既定 **10GB**)。
起動時に走査しないので、トーストの数字は**必ず過去のスキャン由来**である。

**文面案**:

```
45.4GB 解放できます (Xcode 30GB / npm 9.9GB ほか) — doctor で確認
```

- 「合計」と「上位 2 件」、そして**どこを開けばいいか**だけ。一覧は詰めない
- 閾値未満なら**何も出さない** (静かであることを既定とする)
- **一度出したら N 日 (既定 3 日) は再表示しない** (`lastNotifiedAt`)。
  毎起動出すと無視されるようになり、通知の意味が消える

**保存結果が無い / 古いときの扱い** (確定):

| 状態 | トースト |
|---|---|
| 結果が**無い** (一度も doctor を開いていない) | **出さない。** 起動時に走査しない以上、出せる数字が無い |
| 結果がある (期間を問わない) | **出す。** ただし 7 日超なら文末に `(N 日前の診断)` を添える |
| 結果が**壊れている** | **出さない** (クラッシュせず黙って無視) |

> 「結果が無いと出ない」= **初回は必ず沈黙する**。これは仕様として受け入れる。
> 起動時に走らせない以上、初回に数字を出す方法は無い (走らせたら要件違反)。
> ユーザーが一度 doctor を開けば以降は出るようになる。
>
> 古い結果でも**数字は出す**。「古いから隠す」と、放置しているときほど無言になり、
> **この機能が解こうとしている「気づけない」問題を再現してしまう**。
> 古さは添え字で伝えて、判断はユーザーに委ねる。

### 削除の導線

- `Space` で選択 → `d` で削除。**確認プロンプトを必ず挟む** (対象と合計サイズを再掲)
- `D` は dry-run。何が消えるかだけ出す
- `risk: confirm` のエントリは、**中身一覧を一度表示しないと選択できない**
- 削除後は該当エントリを再走査して表示を更新する (成功したことを数字で見せる)

**`risk: confirm` は削除せず「ゴミ箱へ移動」する** (codex 反証を受けて変更):

`finder-nsird` は中身がユーザーの動画ファイルでありうる。確認プロンプトを挟んでも
**誤削除の復元手段が無い**のは危ういため、この risk 階級だけは
`rm` ではなく **macOS のゴミ箱へ移動**する (`NSFileManager` の trash 相当。
CLI なら `Finder` に頼らず `~/.Trash` へ `os.Rename`、
ボリュームが異なる場合はコピー + 削除)。

- ゴミ箱なら**ユーザーが自分で戻せる**。インベントリ JSON は記録であって復元手段ではない
- ゴミ箱移動なので**即座には容量が空かない**。その旨を確認プロンプトに明記する
  (「ゴミ箱に移動します。空にするまで容量は戻りません」)
- `risk: safe` / `caution` は従来どおり直接削除 (再生成されるものをゴミ箱に積む意味がない)

## 4. サービス診断 — 壊れた launchd 登録の検出

### 背景 (2026-09-01 実測。ディスク棚卸しと同日)

同じ日にプロセス側も棚卸ししたところ、**構造がまったく同じ問題**が出た。
アンインストール済みのソフトが、launchd の登録だけ残って起動を試み続けていた。

| 事実 | 実測値 |
|---|---|
| 対象 | `homebrew.mxcl.mysql@8.0` (`~/Library/LaunchAgents/`) |
| launchd の状態 | `last exit code = 78: EX_CONFIG` / `properties = keepalive \| runatload \| penalty box` |
| 実行ファイル | `/opt/homebrew/opt/mysql@8.0/bin/mysqld_safe` → **存在しない** (brew uninstall 済み) |
| plist の設定 | `RunAtLoad=true` + `KeepAlive=true` (= 失敗しても launchd が再試行し続ける) |
| ログイン項目 (BTM) | `sfltool dumpbtm` に `mysqld_safe` が **enabled** のまま残存 |
| 気づいた経路 | **偶然**。`ps` を眺めていて気づいた。通知も警告も一切ない |

ディスクの件と同型である: **失敗し続けているのに、誰も気づけない。**
launchd は繰り返す失敗を penalty box に入れて起動間隔を延ばすだけで、ユーザーには何も出さない。
`brew uninstall` は plist を消さないことがあり、**アンインストールしたつもりの残骸が永久に残る**。

### 登録条件 — 「動いているか」ではなく「壊れているか」で拾う

ディスク側のカタログが「大きいこと」ではなく「消したまま戻らないこと」で登録を決めたのと同じく、
サービス側は **「使っていないこと」ではなく「壊れていること」で登録を決める。**

**正常に起動しているサービスが必要かどうかは、ツールには判定できない** (ユーザーしか知らない)。
一方、**起動に失敗し続けている / 起動対象が存在しない**のは環境の事実であり、機械的に確定する。
「無駄そう」を推測で並べると、後述の `-9` ノイズと同じ「読まれないリスト」になる。

検出する分類は 3 つで、いずれも**構造的に確定する事実**だけを根拠にする:

| # | 分類 | 判定根拠 | 偽陽性 |
|---|---|---|---|
| A | **起動対象が存在しない登録** | plist の **`Program`** (絶対パス) が `os.Stat` で不在 | 実質無し (下記の注意を守った場合) |
| B | **起動に失敗し続けている登録** | `launchctl list` の **正の** exit code + **再起動条件を持つ** (`KeepAlive` / `StartInterval` / `StartCalendarInterval` / `WatchPaths` 等) | 一時的失敗を拾う可能性あり → `penalty box` を併記して強度を示す |
| C | **パッケージマネージャの台帳に無い登録** | `homebrew.mxcl.<formula>.plist` の `<formula>` が `brew list` に無い | 実質無し (台帳が一次情報) |

今回の mysql は **A・B・C のすべて**に該当した。A だけで確定するので、
**A を主判定、B と C を補助**とする。
理由: exit code は環境依存で揺れる (一時的なポート衝突・権限) が、
**実行ファイルの不在は構造的に永久に直らない**。強い根拠を主にする。

**C を足す理由** (2026-09-01 レビューで追加): A は「バイナリのパスが消えたか」を見るが、
C は「**インストーラの台帳に無い**」を見るので、**バイナリが別経路で残っていても検出できる**
(`brew uninstall` 後に他の formula が同名のバイナリを提供している場合など、A は素通りする)。
`brew services list` も補助に使える (2026-09-01 実測: `redis` のみ `Status: none`)。

⚠️ **C は Homebrew に限定する。** 「台帳」に相当するものを持つのは
パッケージマネージャ経由でインストールされたものだけで、
手で置かれた plist に一般化すると「台帳に無い = 壊れている」が成立しなくなる。

> **C の検出はディスク側の `brew-orphan-state` と同じ孤児を指す** (`1. 対象ディレクトリの分類`)。
> mysql は `/opt/homebrew/var/mysql` (376MB) と壊れた plist の**両方**を残していた。
> 診断結果は相互に参照させ、**片面だけ消して終わったことにしない**。

#### ⚠️ A の判定で `Program` と `ProgramArguments[0]` を同じに扱ってはいけない

`man 5 launchd.plist` の原文 (codex 反証を受けて確認):

> NOTE: The Program key must be an absolute path. (…) In the absence of the Program key,
> the first element of the ProgramArguments array may be either an absolute path,
> **or a relative path which is resolved using `_PATH_STDPATH`**.

つまり `ProgramArguments = ["python3", "/path/to/job.py"]` は**正しく動く登録**であり、
`os.Stat("python3")` の失敗をもって「壊れている」と判定すると**偽陽性になる**。

| plist のキー | 判定 |
|---|---|
| `Program` がある | **絶対パス必須**。`os.Stat` で不在なら**壊れて確定** (A の主判定はここだけ) |
| `Program` が無く `ProgramArguments[0]` が絶対パス | 同上。不在なら壊れて確定 |
| `Program` が無く `ProgramArguments[0]` が相対名 | **`_PATH_STDPATH` (`/usr/bin:/bin:/usr/sbin:/sbin`) で解決してから**判定。解決できたら正常、できなければ候補 |
| `BundleProgram` がある | **判定しない**。SMAppService 経由の app-bundle 相対パスで、解決規則が別 |

⚠️ 相対名の解決に**呼び出し側の `$PATH` を使わないこと**。launchd は `$PATH` を見ない。

`_PATH_STDPATH` の値は実測でも裏が取れている: `launchctl print` の出力に
`PATH => /usr/bin:/bin:/usr/sbin:/sbin` が現れる (2026-09-01 実測)。
ただし**ハードコードせず `/usr/include/paths.h` の値と一致することをテストで確認**する。

#### ⚠️ B は「再起動条件を持つこと」まで見ないと「し続けている」にならない

`RunAtLoad=true` かつ `KeepAlive` **なし**のジョブは、ログイン時に**一度だけ**起動して
`exit 1` を返して終わる。`launchctl list` の Status は正の値になるが、
**繰り返してはいない** (codex 反証)。`RunAtLoad` 単独を B の条件に入れると、
「一度失敗して終わった一回限りのジョブ」を「失敗し続けている」と報告することになる。
→ B の条件は **再起動条件 (`KeepAlive` / `StartInterval` / `StartCalendarInterval` /
`WatchPaths` / `QueueDirectories`) のいずれかを持つこと**とする。

### ⚠️ 最大の罠: `launchctl list` の Status 列を「失敗」として読むと全部誤検出になる

**この節がサービス診断の実装で最も踏みやすい所**なので実測値を残す。
2026-09-01 の実測で `launchctl list` の Status が `0` 以外だったのは **約 60 件**。
そのうち**本物の失敗は 1 件 (mysql の 78) だけ**だった。残りの内訳:

| Status 列 | 意味 | 件数 (実測) | 扱い |
|---|---|---|---|
| `-9` | **そのシグナル (SIGKILL) で停止させられた**。実測ではほぼ全件が on-demand サービスのアイドル終了 | 約 60 | **除外** |
| `-` | PID なし = 今は動いていない。on-demand の通常状態 | 多数 | **除外** |
| 正の値 | プロセスが自分で異常終了コードを返した | **1** (`78`) | **候補** |

`man 1 launchctl` の定義はこうであり、**正常/異常を分類していない**:

> The second column displays the last exit status of the job. If the number in this column
> is negative, it represents the negative of the signal which stopped the job.

- ⚠️ **負値を「正常なアイドル終了」と一般化しないこと** (codex 反証)。
  負値が意味するのは**シグナルで停止した事実だけ**で、外部からの `kill -9` や
  メモリ逼迫による強制終了なら**本物の異常**である。今回の実測で約 60 件がアイドル終了
  だったのは**この 1 台のこの時点の観測**であって、負値の意味ではない
- それでも**負値は候補から外す**。理由は「正常だから」ではなく、
  **負値からは異常かどうかを判別できず、拾うとノイズが本物を埋める**から。
  拾うと `com.apple.cloudd` / `com.apple.tccd` / `com.apple.photolibraryd` … が 60 行並び、
  **本物の 1 件が埋もれる** (ディスク側の「サイズだけの行を作らない」と同じ問題)
- **`-` を「起動に失敗した」と読んではいけない。** on-demand サービスの平常状態

### 走査対象はサードパーティ領域に限定する (allowlist の代替)

ディスク側は「消していい場所」を allowlist で列挙できたが、
サービスは **どのラベルが不要かを事前に列挙できない** (`mysql@8.0` を先回りして知る方法は無い)。
そこで **判定は構造的条件 (A/B) で行い、走査範囲を絞ることで allowlist の代わりとする**:

| パス | 走査 | 理由 |
|---|---|---|
| `~/Library/LaunchAgents` | ⭕ | ユーザーが入れたもの。今回の mysql はここ |
| `/Library/LaunchAgents`, `/Library/LaunchDaemons` | ⭕ | サードパーティのインストーラが置く場所 |
| `/System/Library/**`, `/usr/lib/**` | ❌ | Apple 管理。SIP 下で消せず、**ユーザーが判断できない** |

⚠️ **除外はパス基準で行い、`com.apple.*` というラベル名で除外しないこと** (codex 反証)。
ラベルは**ただの文字列**で、`/Library/LaunchDaemons/com.apple.foo.plist` に
第三者やユーザーが置いた plist も同じ名前を名乗れる (マルウェアが偽装に使う手口でもある)。
ラベルで切ると**管理領域の外に置かれた壊れた登録を落とす**。
`/System/Library` 配下でないものは、ラベルが `com.apple.` で始まっていても**走査する**
(表示側で「Apple のラベルを名乗っているが `/Library` にある」と注記する方が有用)。

走査範囲をサードパーティ領域に限ること自体が、そのままノイズ対策になっている
(`-9` を出していた約 60 件はすべて `/System/Library` 配下だった)。

### 対象化しない判断と根拠 (2026-09-01)

**「使われていなさそうな待ち受けポート」は対象にしない。** 実測で以下を見つけたが、いずれも
**不要かどうかがユーザーの用途に依存する**ため、ツールが「無駄」と断定できない:

| 実測で見つけたもの | なぜ対象外か |
|---|---|
| `ARDAgent` が `*:3283` で LISTEN (リモートマネジメント) | リモート管理を実際に使っている可能性がある |
| `ControlCenter` が `*:5000` / `*:7000` で LISTEN (AirPlay レシーバー) | AirPlay 受信を使っている可能性がある。**ただし port 5000 は開発サーバーと衝突しやすい** |
| `Dropbox` が `127.0.0.1:17600` 等で LISTEN | 現に使用中のアプリ |

これらは A / B のどちらにも該当しない (**壊れていない。動いている**)。
登録すると「毎回出るが誰も消さない行」になり、リスト全体が読まれなくなる。
→ **将来の別 issue**。やるなら「無駄」ではなく「**開発でポートが衝突しうる**」という
別の切り口 (port 5000 / 3000 / 8080 を占有している常駐の一覧) にする方が価値が出る。

**「長時間起動しっぱなしのプロセス」も対象にしない。** 今回 Chrome が 13.8GB / 51 プロセス、
9 日前の作業セッションが残っていたが、これは**ユーザーが使っている最中かもしれない**。
プロセスの要不要は判定できない (`ps` を見れば分かる話でもある)。

### 出力は「検出とコマンド提示」まで。ツールは実行しない

**サービスの停止・削除はツールが実行しない。** `2. 安全性ハーネス > 第一原則` を
サービス診断では**全域に適用**する (ディスク側で `Tier 4` = sudo 必須を検出のみに留めたのと同じ扱い)。

理由: 誤って launchd 登録を落とすと**システムやアプリの機能が黙って壊れる**。
しかもディスクと違い、**壊れたことがすぐには分からない** (次に使おうとした時に気づく)。
消えたファイルより復旧が難しい。

出す情報:

```
 サービス診断                                        [r] 再スキャン  [Esc] 閉じる
 ────────────────────────────────────────────────────────────────────────────
  ⛔ homebrew.mxcl.mysql@8.0                              起動に失敗し続けています
     実行ファイルがありません:
       /opt/homebrew/opt/mysql@8.0/bin/mysqld_safe
     last exit 78 (EX_CONFIG) / KeepAlive / penalty box 入り
     アンインストール済みのソフトの登録が残っているようです。
     ログイン項目 (BTM) にも `mysqld_safe` が enabled で残っています。

     手動で実行してください (このツールは実行しません):
       launchctl bootout gui/$(id -u)/homebrew.mxcl.mysql@8.0
       rm ~/Library/LaunchAgents/homebrew.mxcl.mysql@8.0.plist
 ────────────────────────────────────────────────────────────────────────────
```

- **コマンドは表示するだけ**。コピーはできてよいが、実行キーは作らない
- 「なぜこれが出ているか」(不在の実行ファイル / exit code / penalty box) を必ず添える。
  ディスク側の `advice` と同じく、**判断材料なしの指摘を出さない**
- **BTM (`sfltool dumpbtm`) との突合は補助情報**として出す。plist を消しても
  ログイン項目側に残ると「背景項目」の残骸になるため
  (⚠️ `sfltool dumpbtm` の出力形式は非公開で macOS バージョン間の安定性が不明。
  **パースに失敗したら BTM の行を出さないだけ**にし、診断全体を落とさない)

#### ⚠️ 実測 (2026-09-01): plist を削除しても BTM は追随しない

この issue の起点になった `homebrew.mxcl.mysql@8.0` を実際に片付けて確認した:

```
launchctl bootout gui/501/homebrew.mxcl.mysql@8.0   → 成功 (launchctl list から消滅)
rm ~/Library/LaunchAgents/homebrew.mxcl.mysql@8.0.plist → 成功
```

**それでも BTM には残った**:

```
Name: mysqld_safe   /   Type: legacy agent (0x10008)
Identifier: 8.homebrew.mxcl.mysql@8.0
URL: file:///Users/koji/Library/LaunchAgents/homebrew.mxcl.mysql@8.0.plist   ← 存在しない
Executable Path: /opt/homebrew/opt/mysql@8.0/bin/mysqld_safe                 ← 存在しない
```

**BTM のデータベースは launchd の登録とも plist の実在とも独立している。** つまり:

- 「plist を消せば BTM も消える」と案内してはいけない (**実測で外れた**)
- **BTM 単独で「参照先が存在しない項目」を検出できる** —
  `URL` と `Executable Path` の両方が `os.Stat` で不在なら、それは確実に残骸。
  この判定は `4` 章の A (起動対象が存在しない) と同じ論法で、
  **plist が既に消えていても検出できる**点が強い
- ただし**掃除する手段が UI にしか無い可能性がある** (`legacy agent` タイプは
  システム設定のログイン項目に現れないことがある)。
  検出しても「消し方」を提示できないなら、**出す価値があるか要判断** (未決事項へ)

### 実装上の制約 — ここだけ外部コマンドの exec が要る

ディスク診断の受け入れ条件は「走査に外部コマンドを exec していない」だが、
**サービス診断はこれを満たせない。** launchd の実行時状態 (exit code / penalty box) は
plist を読むだけでは分からず、`launchctl` に聞くしかない。差異として明記する:

- `launchctl list` は **1 回だけ** 呼ぶ (全ラベルが一度に取れる)
- `launchctl print gui/<uid>/<label>` は**候補に絞ってから**呼ぶ。
  全ラベルに対して呼ぶと **`launchctl` 自体を数百回 exec する**ことになる
  (⚠️ `print` は状態を表示するだけで**ジョブを起動しない**。
  重いのは exec の回数であって、サービスが立ち上がるからではない)
- `2. 安全性ハーネス > プロセス使用中の判定` と同じく、**ラベルは完全一致で扱う**
  (部分一致で `pgrep` した結果の誤検出が既に実例としてある)
- `3. スキャンの三層構造 > 終了時の後始末` の方針に従い、
  **exec は `context.Context` 付きで起動**し、glogx quit / `Esc` で確実に殺す。
  子プロセスを残さない
- `launchctl` 自体が失敗したら **「診断できず」を第 3 の状態として表示**する
  (`2. 安全性ハーネス > 検出の健全性`)。0 件に畳まない

### テストハーネス (サービス診断)

- **偽の LaunchAgents ディレクトリ** + **`launchctl` の fake** で全ケースを回す
  (実環境の launchd を触らない)
- fake は**実際の出力形式を模す**こと。特に:
  - Status 列に `-9` / `-` / 正の値が混在するケース
  - `launchctl` が非 0 で終了するケース (fail-closed になること)
- 必ず作る異常系:
  - `-9` が 60 件 + 正の exit code が 1 件 → **候補が 1 件だけ**になること
    (このケースを落とすと本番でノイズ 60 行が出る)
  - plist が壊れている (XML パース失敗) → その 1 件を「診断できず」にし、**他を巻き込まない**
  - `ProgramArguments` が空配列 / `Program` も `ProgramArguments` も無い → クラッシュしないこと
  - **`ProgramArguments[0]` が相対名** (`["python3", "job.py"]`) で、
    `/usr/bin/python3` が存在する → **候補にならない** (`_PATH_STDPATH` で解決できるため)。
    ⚠️ このケースを落とすと、正常な登録を「壊れている」と報告する
  - `Program` が相対パス (仕様違反の plist) → 候補にする (launchd も起動できない)
  - `BundleProgram` だけを持つ plist → **判定対象外**として扱う (「診断できず」ではない)
  - `RunAtLoad` のみ (`KeepAlive` 無し) + 正の exit code → **B の候補にならない**
  - `launchctl` が存在しない / タイムアウト → **候補 0 件ではなく「診断できず」**
  - `/System/Library` 配下のラベルが候補に**入らない**こと。
    逆に **`~/Library/LaunchAgents/com.apple.foo.plist`** (ラベルだけ Apple を騙る) は
    **候補に入る**こと
- **変異検証** (`~/.claude/rules/mutation-verify-new-tests.md`): 
  「負値を除外する」フィルタを外す変異を当て、
  **`-9` 60 件のテストが red になる**ことを確認する。ここが緑のままなら、
  そのテストはノイズ対策を何も守っていない

## 5. 孤児・残骸プロセスの検出 — **実装しない**。判定材料が実測で全部崩れた記録

> **この章は機能仕様ではなく、検証の記録である。**
> 「無駄なプロセスも検出してほしい」という要求に対して設計を試み、
> **候補にした判定材料が 2026-09-01 の実測ですべて成立しないと分かった**。
> 次に同じことを考えたときに同じ検証を繰り返さないために、
> 何をどう試して何が崩れたかを残す。

### 何を作ろうとしたか

`4` 章と同じ線引きをプロセスに適用する案だった。**動いているプロセスが必要かどうかは
判定できない**ので、機械的に確定する **「これを起動したものが、もう存在しない」**
という関係だけを検出する。そのために「起動元を突合できる外部の正本」を 4 つ検討した。

### 検討した判定材料と、崩れた理由 (すべて実測)

| # | 判定案 | 実測結果 | 判定 |
|---|---|---|---|
| A | **`PPID=1` かつ `launchctl list` に対応が無い = 里子化** | `PPID=1` が **695 件**、`launchctl list` で PID を持つ job は **287 件**。差の **629 件が誤検出**される | ❌ **破綻** |
| B | **tmux の `pane_pid` と突合** | `pane_pid` は pane の**シェルの PID** (`/bin/zsh`)。直接の子すら 0 件で、そこから起動された孫以降は辿れない | ❌ 単体では不能 |
| C | **`simctl` の booted デバイスと突合** | 章を書く過程で自分で否定済み (下記「反例」) | ❌ |
| D | **実行ファイルが存在しないプロセス** | 絶対パス起動 **773 件**中 **1 件**のみ。しかもそれは Apple の MobileAsset 差し替えによるもので、ユーザーが対処するものではない | ❌ 実質ゼロ |

#### A の詳細 — 629 件の誤検出はシステムの中核デーモンだった

```
launchctl list で PID を持つ job:  287
PPID=1 のプロセス:                 695
→ 差分 (誤検出される母集団):        629   (うち XPCServices が 162 件)
```

差分の先頭に並んだのは `logd` / `configd` / `powerd` / `securityd` / `syslogd` /
`opendirectoryd` / `diskarbitrationd` — **システムが動くのに必要な中核デーモン**である。

原因は 2 つ (codex 反証で判明し、実測で確認):

1. **`launchctl list` はユーザードメイン (`gui/<uid>`) の job しか出さない。**
   システムドメインの daemon は root の launchctl でないと見えない
2. **XPC service は launchd 管理下だがラベル一覧に現れない。** アプリ内
   `Contents/XPCServices/` に束ねられた private service がこの形

さらに「実行中の PID からどの launchd 登録に由来するかを逆引きする」安定 API が無い。
`launchctl procinfo` は **root 必須かつ diagnostic only** (man に「出力に依存するな」と明記)。

⚠️ **この issue の初稿には「`PPID=1` の非 Apple 系プロセスは 33 件」と書いていたが、
これは `/System/` `/usr/libexec/` 等を除外した後の数字**で、母集団は 695 件だった。
**除外フィルタをかけた後の数字を母集団として提示すると、判定の危険性が 20 分の 1 に見える。**

#### B の詳細 — `pane_pid` は「pane で最初に起動したプロセス」でしかない

`tmux` の `pane_pid` は pane のシェルの PID であり、そこから起動されたプロセスの
親であるとは限らない (`exec` された / 孫以降 / `setsid` で切り離された)。
実測でも `pane_pid=84143` は `/bin/zsh` で、直接の子は 0 件だった。

**「pane が消えた」ことは、その pane で過去に起動されたプロセスが不要になった証拠にならない。**

#### C の詳細 (反例) — 「GUI アプリが起動していない = 残骸」は成立しない

当初「`Xcode.app` も `Simulator.app` も起動していないのに CoreSimulator のプロセスが
動いていたら残骸」と判定する予定だった。実測ではその状態が成立していた:

| 実測 | 値 |
|---|---|
| `Xcode.app` / `Simulator.app` | **どちらも起動していない** |
| `xcrun simctl list devices booted` | **0 件** |
| CoreSimulator 系プロセス | **4 つ動いている** |

しかし内訳を見ると崩れる:

| プロセス | 起動時刻 |
|---|---|
| `simdiskimaged` | 21 日前 |
| `CoreSimulatorService` / `SimulatorTrampoline` | **1 時間 24 分前** |
| `SimLaunchHost` | **1 時間 22 分前** |

後ろの 3 つは、**同時刻に別セッションが CLI (`simctl`) で作業していた**ことによる起動だった。
**CoreSimulator は GUI からも CLI (`simctl` / `xcodebuild`) からも起動される**ため、
`Xcode.app` の不在は「使われていない」ことを何も意味しない。
この判定を実装していたら、**今まさに CLI 作業中のプロセスを「残骸なので kill しろ」と
提示していた**。

### 崩れなかった規律 (将来この領域をやるなら前提にする)

判定材料は全滅したが、以下は**実装するかどうかに関わらず正しい**と確認できた
(codex も反証できなかった):

- **稼働時間の長さは異常の根拠にならない。** 35 日動く `WindowServer` は正常。
  `etime` は候補を安く絞る一次フィルタにしかならない
  (`1` 章の「mtime は削除の根拠にしない」と同じ構造)
- **プロセス名の部分一致で判定しない** (`2` 章の実例: `pgrep -i "tor"` が
  `thermalmonitord` / `CotEditor` / `Activity Monitor` にマッチした)
- **PID は再利用される。** 提示から人間が実行するまでの間隔は長い。
  同一性を担保するなら `(PID, 開始時刻)` のペアが要るが、
  ⚠️ **`ps -o lstart=` は秒粒度で、同一秒内の PID 再利用を区別できない**
  (codex 反証)。`kern.proc` の `KERN_PROC_PID` から取れる `p_starttime`
  (`struct timeval`, usec 粒度) が要る
- **`kill PID` はプロセスツリーに対して不完全。** 親だけ終了して子が launchd に
  reparent されると、**むしろ孤児を増やす**。他ユーザー / root 所有には権限で失敗する

### それでも将来やるなら — 必要になる前提

**外部の正本が無いなら、自分で記録を作るしかない。**

- glogx は tmux popup (`C-g`) で動くツールなので、**glogx 自身が起動したプロセスを
  記録する**なら「起動元が消えた」を自分の記録で判定できる。ただしこれは
  **新しい常設の仕組み**であり、この issue の範囲を超える
- ユーザーが「これは開発サーバーで、tmux セッション X に紐づく」と
  **明示的に登録するカタログ方式**なら実装できる。ただし登録しない限り何も出ないので、
  「気づけない放置を検出する」という本 issue の目的には効かない

いずれも**別 issue**。本 issue では**プロセス側は扱わない**。

## 8. 未決事項

- **doctor の起動キー**。既存キーバインドとの衝突確認が要る (例: `D` / `?d`)
- **保存結果が実態とずれる問題** (codex P3-3、未解決)。
  外部で掃除した場合 (`brew cleanup` を手動実行、Xcode が自分で DerivedData を消した等)、
  保存結果は古い数字を持ったままで、**トーストが「もう無いゴミ」を宣伝する**。
  起動時に走査しない以上、検知手段が無い。現状の緩和は `(N 日前の診断)` の添え字のみ。
  → doctor を開いた時点で必ず再スキャンするので実害は「トーストが一度空振りする」程度、
  という整理でよいか要判断
- **`speech-model-cache` を将来カタログに載せるか** (今回は保留)。
  載せるには `lsof` 判定 + 削除後に音声機能が壊れないことの実測が要る
- **トーストから doctor を直接開けるか**。トーストにアクションを持たせる機構が
  現状の `toast.go` にあるか要確認 (無ければトーストは文言で誘導するだけ)
- 閾値 10GB は妥当か (今回は 41GB 溜まっていた。10GB だと頻繁すぎる可能性)
- 再通知の抑止期間 3 日は妥当か
- 同時走査数の上限 4・エントリごとの timeout 60 秒は妥当か (実測して決める)
- `~/Downloads/*.crdownload` を対象に含めるか (今回 749MB あった。ユーザーデータ領域なので慎重)
- **`xcode-devicesupport` のグロブを `iOS` 以外へ広げるか** (2026-09-01 レビュー)。
  Xcode は watchOS / tvOS の実機を繋ぐと同名の DeviceSupport を作るはずだが、
  **この機には `iOS DeviceSupport` しか存在せず未実測**。
  カタログの登録条件 (実測してから登録) に従うなら、実機を繋ぐまで確認できない。
  グロブだけ広げて空振りさせるか、実測できるまで iOS 限定に戻すか要判断
- **小物の同型キャッシュを載せるか** (`electron-builder` 82MB / `typescript` 31MB /
  `deno` 27MB)。構造は Tier 1 と同じだが、1 件あたりが小さく**行が増えるだけ**になる。
  「合計 N MB のツールキャッシュ」と 1 行にまとめる案もある
- **`~/.Trash` (2026-09-01 実測 2.3GB) を扱うか。** 「ユーザーが既に消したもの」なので
  提案する価値はあるが、**空にすると復元不可**。ツールから消すのではなく
  「ゴミ箱に 2.3GB あります」と**表示するだけ** (`deleteVia: propose`) が妥当か要判断。
  ⚠️ `risk: confirm` の削除先がゴミ箱なので、**ゴミ箱を空にする機能と衝突する**
  (同じ画面で「ゴミ箱へ移す」と「ゴミ箱を空にする」を並べない)
- **`go-modcache` を `rm` でなく `go clean -modcache` にするか。**
  module cache は read-only で作られるため `rm -rf` には強制が要る一方、
  `go clean` は **go 本体が必要**で、goenv の版が壊れていると実行できない。
  `cli:` を主経路にしつつ、失敗時に「走査できず」に倒す設計でよいか要判断
- `~/src/**` のビルド成果物・`node_modules` を扱うか
  (プロジェクト単位の判断が要るので別 issue が妥当)
- 既存の `cli_health.go` を doctor 画面に統合するか (今回は**しない**方針。
  統合するなら別 issue で、起動時トーストの挙動を変えないこと)
- **サービス診断を起動時トーストの対象にするか** (今回は**しない**方針)。
  ディスクは「合計 GB」という自然な閾値があるが、サービスは件数しかない。
  「壊れた登録 1 件」で毎回トーストを出すと、**消すまで永久に鳴り続ける**
  (ディスクの `lastNotifiedAt` と違い、放置してよいケースがある)。
  → doctor を開いたときだけ出す、で足りるか要判断
- **`/Library/LaunchDaemons` の読み取りに権限が要るか** (要実測)。
  root 所有だが `0644` が通例なので読めるはず。読めない場合は「診断できず」に倒す
- **`sfltool dumpbtm` を使うか**。2026-09-01 の実測では**一般ユーザーで出力が取れた**が、
  出力形式は非公開で macOS バージョン間の安定性が不明。補助情報に留めるか、そもそも外すか
- **BTM の残骸を「独立した検出項目」に昇格させるか** (4 章の実測を受けて)。
  plist が消えていても検出できる強い判定だが、**`legacy agent` の消し方を提示できない**
  可能性がある。「検出できるが直せない」項目を出すべきかの判断が要る
- **`launchctl print` の出力パースの安定性**。`penalty box` は `properties = ` 行に出るが、
  これも非公開形式。**取れなければ「penalty box 情報なし」で続行**する設計にはしてある
- サービス診断の結果もキャッシュするか (ディスクと違い走査が軽いので、
  doctor を開くたびに実行でよい可能性が高い)
- **プロセス側の診断を別 issue として起こすか** (`5` 章の結論は「本 issue では扱わない」)。
  起こすなら前提は「外部に正本が無いので**自分で記録を作る**」ことで、
  glogx が起動したプロセスを追跡する常設の仕組みが要る。
  **`5` 章の実測 (629 件の誤検出 / `pane_pid` の限界) をそのまま前提として引き継ぐこと**
- ⚠️ **`cacheBaseDir()` は `package main` の unexported 関数** (`src/glogx/cache.go`)。
  codex 反証で判明した**ディスク側の受け入れ条件の実装不能点**:
  `src/diskdoctor` を「TUI 非依存の別パッケージ」にすると、**この関数を呼べない**。
  → 共有パッケージへ切り出す / 同一仕様の exported helper を diskdoctor 側に持つ /
  パスを呼び出し側から注入する のいずれかを選ぶ必要がある。
  **「`cacheBaseDir()` 経由」という受け入れ条件は、この決着後に文言を直すこと**
