## お願いしたいこと

**tmux の中と外の両方**で、実端末から次を実行して出力を控えてください。

```
cd ~/dotfiles/src/glogx && go run ./tools/width-probe
```

⚠️ **stdout をリダイレクトしないこと** (CPR の問い合わせが端末に届かなくなる。ツールが検出して
止まります)。結果を残すときは画面をコピーするか `script(1)` を使ってください。

⚠️ 実行中は**何もキーを押さないこと**。キー入力が CPR の応答に紛れると測定がずれます
(基準文字 `ASCII x` が 1 にならなければツールが「この run は無効」と言って止まります)。

## 何が知りたいか (issue 124)

「診断用」と付いた行の **`got` がどの列と一致するか**です。

| 一致した列 | 意味 |
|---|---|
| `grapheme` | 今の `dispWidth` のままでよい |
| `wc` | 描画エンジン (bubbletea v2) の既定側へ揃える議論になる |
| どれとも不一致 | 端末が独自。別の対策が要る |

特に見てほしい行: `カンナダ ಕಾ` / `タミル கா` / `Arabic sign U+0600` / `RI 単独 🇦` / `keycap 1️⃣` /
`⚠+VS16`。**tmux の内と外で `got` が違うなら、tmux が幅を書き換えています**。

## 出力と一緒に控えてほしいもの

ヘッダ行に出ます (ツールが出力します)。**`go-runewidth` の版は必須** — `wc` 列はその版に依存し、
版が変われば判定が反転しうるので、後から結果を再現できなくなります。

```
width-probe  TERM=…  TERM_PROGRAM=…  TMUX=…  SSH=…
  deps: x/ansi=…  uniseg=…  go-runewidth=… (wc 列はこの版に依存する)
```

## ⚠️ この測定だけでは決まらないこと (既知の限界)

bubbletea v2 は起動時に **mode 2027 (Unicode Core) を交渉し、対応端末では端末側の幅解釈も
切り替える**。width-probe は 2027 を要求も設定もしないので、**glogx が実際に描画する構成とは
別の構成の端末を測っています**。2027 対応端末では `got` が glogx 実行時と変わりえます。

したがってこの測定は「2027 OFF 側の答え」です。ここで `wc` と一致するなら揃える先の議論に進み、
そのとき初めて 2027 の交渉結果 (DECRQM `CSI ? 2027 $p`) を測る価値が出ます。

### 読み取り (tmux の中の層について)

**`got` は圧倒的に `grapheme` (= 今の `dispWidth` = `ansi.StringWidth`) と一致する。**
issue 124 の表に当てはめると「**今の `dispWidth` のままでよい**」= 描画エンジンの既定 (`wc`) 側へ
揃える議論は、この層に関しては不要。

例外は 2 行だけで、どちらも **glogx が出さない文字**:

- `RI 単独 🇦` は `wc` 側 (got=1)。単独の Regional Indicator は国旗を構成しない裸のコードポイントで、
  glogx が出す経路は無い
- `ベンガル母音 U+09BE` は `uniseg` 側 (got=0)。probe の `uniseg` 列はライブラリ間の差を見るための
  参考値で、**glogx の分割は 2026-08-28 に x/ansi へ一本化済み** (124 の (1) は解決済み)。
  つまりこの行は「今の glogx の経路」ではなくライブラリの版差 (uniseg=Unicode 15 / x/ansi=16) を
  示しているだけで、未解決の問題を指してはいない

### まだ決まらないこと

- **tmux の外での `got`** — 未測定。ここが違えば「tmux が幅を書き換えている」ことになる
- **mode 2027 を交渉した状態の `got`** — width-probe は 2027 を要求しないので測っていない
  (本文「既知の限界」節)。今回 `grapheme` 一致だったので、issue 124 の当初の想定
  (「wc へ揃える議論」) には進まず、2027 を測る動機も今のところ生じていない

### 結論: 「揃える先」は 1 つに決められない

issue 124 の当初の枠組み (grapheme か wc のどちらかへ揃える) は、**同じマシンの同じ日でも
環境で答えが反転する**ので成立しない。どちらへ揃えても、もう一方の環境でずれる。

したがって取るべきは「揃える先を選ぶ」ではなく **「環境で割れる文字を出さない」**。これは
`termsafe` が既に外部由来の文字列に対して実装している方針 (`DropEmojiVS16`: VS16 付き絵文字を
bare へ正規化) と同じで、新しい設計判断ではない。

### 実害 1 件とその対処

食い違った `⚠+VS16` は **`src/glogx/main.go`** の起動時警告が出していた
(`fmt.Fprintln(os.Stderr, "⚠️ "+widthenv.Message)`)。外部由来の文字列は termsafe が VS16 を
落とすのに、**glogx 自身のリテラルだけがその関門を通っていなかった**。

`src/glogx/CLAUDE.md` が「警告は 🚨 (U+1F6A8、常に 2 桁) を使い ⚠️ は使わない」と定めているので、
**🚨 へ置換**した (bare `⚠` も全層一致だが、規約が指定しているのは 🚨)。

この行は alt screen の外へ 1 行出すだけで桁揃えを持たないため見た目の実害は小さい。
直した理由は「自前リテラルだけ正規化の例外になっている」不整合の方。

### 再発防止 (テストで固定)

`src/glogx/vs16_literal_test.go` を追加。glogx の**自前の文字列リテラル**に VS16 が入ったら
ファイル名・行番号つきで落ちる (`go/ast` で `BasicLit` を走査。`_test.go` は対象外)。

変異検証: `main.go` を `⚠️` に戻すと `main.go:46 文字列リテラルに VS16 (U+FE0F) がある` で red。
ビルドが通ることを確認したうえで測っており、意図した assert が検知したことも確認済み。
