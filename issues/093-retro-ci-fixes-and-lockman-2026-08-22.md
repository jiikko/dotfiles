# 093 retro: CI 修正 3 連発と lockman v1 の実装 (2026-08-22)

起票日: 2026-08-22
種別: retro
関連: [091](091-feat-lockman-directory-lease-lock.md) / [092](092-human-verify-lockman-over-smb.md)

このセッションでやったこと: CI の Tests を 3 コミットかけて緑に戻し、issue 091 の設計を
詰め、`src/lockman` の v1 と `bin/lockman` を実装した。以下は踏んだ罠と改善案。

## 1. 「macOS では出ない」失敗を 3 回連続で踏んだ

同じセッションで、**ローカルでは緑・CI (Linux) でだけ落ちる**を 3 回踏んだ:

| # | 現象 | 実体 |
|---|---|---|
| 1 | date スタブが常に失敗 | `exec A \|\| exec B` は exec でプロセスが置き換わり後段が走らない。host が BSD date の macOS では 1 発目が成功するので差が出ない |
| 2 | ロケール候補が一致しない | glibc の `locale -a` は `C.utf8` (小文字・ハイフン無し)。macOS は `C.UTF-8` |
| 3 | 引き継ぎの勝者が 4 人 | 排他の穴 (下の 3 参照)。macOS は速すぎて 16 goroutine が TTL 内に終わり再現しない |

3 件とも「**手元の 1 環境で緑**」を根拠にしていた。CI に投げるまで気づけない構造だった。

**切り出し先の提案**: `_claude/rules/` に新規ルール
「**shell / FS の判定コードは、macOS と Linux で挙動が割れる点を最初に列挙してから書く**」
(具体例: `date -j` / `locale -a` の綴り / `tr` のオプション解釈 / mtime の粒度)。
既存の `path-shim-must-resolve-real-binary.md` は PATH 解決に閉じているので、別ルールが要る。

## 2. 自分が書いた「安全側に倒すための判定」に 3 つの欠陥を作り込んだ

ロケール判定 (20 行程度) に、**1 回の commit で 3 つ**バグを入れた:

- `locale -a | grep -q` が **pipefail + SIGPIPE** で偽陰性 (grep が先に抜けて locale が 141)
- BSD の `tr -d '-_'` が `-` をオプションと解釈して失敗し、**鍵が空になって全候補が一致**
  (macOS で `LC_ALL=fa_IR` になる実測)
- 「決まったか」を `LC_ALL` の中身で判定 → 外側から `POSIX` が来ていると 1 候補目で打ち切り

共通点は「**失敗が沈黙し、しかも安全側でない方向へ倒れた**」。特に 2 つ目は `tr` の
エラーが stderr に出ていたのに、WARN 行だけ見て見落とした。

**切り出し先の提案**: 新規ルール
「**判定に使うパイプラインは `| grep -q` で書かない**」(pipefail 下で偽陰性になる) +
「**BSD/GNU で解釈が割れるオプションを条件式に使わない**」。1 と統合してもよい。

## 3. CI が macOS では見つからない排他の穴を掘り当てた

`tryTakeover` / `Release` が期限切れを**呼び出し側が渡した `--ttl`** で判定していた。
`lockman acquire "$dir" --ttl 30s` と打つだけで 30 分の lease を持つ相手を追い出せる
= 排他が任意に破れる。ローカルでは 16 goroutine が速すぎて再現せず、CI の
「引き継ぎの勝者が 4 人」で露見した。

**ルールに落ちる部分は 091 に書いた** (「生死の判定に使う TTL は保持者が宣言したもの」)。
retro 側の残課題は無し。**却下: 汎用ルール化はしない** — 「権限の出典を要求側に置くな」は
一般論としては正しいが、抽象度が高すぎて発動条件を書けない。

## 4. 変異が「当たっていない」のに緑を合格と読みかけた

変異検証で 1 本目のパターン置換が失敗 (AssertionError) し、**コードが無変更のまま
テストが緑**になった。出力だけ見ると「変異を当てたが赤にならなかった」と区別できない。
気づいて当て直したが、気づかなければ「主張を守っている」と誤って報告していた。

**切り出し先の提案**: [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md)
に追記 —「**変異が実際にコードへ適用されたことを確認してからテストを走らせる**
(置換の失敗・パターン不一致は緑と区別できない)」。

## 5. 変異で赤になっても、テストが主張を測れているとは限らない

引き継ぎの競争テストは、変異 1 (rename → unlink) では正しく赤になったのに、
**別の理由で「勝者が複数」になる状態を「バグ」と誤認**した (引き継ぐ側も短い TTL で
取っていたため、勝者の新しい lock もすぐ期限切れになり、後続が**仕様どおり**正当に
引き継いでいた)。変異検証は「その変異を捕まえた」ことしか保証しない。

**切り出し先の提案**: 同じく `mutation-verify-new-tests.md` に 1 行
「変異が赤 = 主張全体が守られている、ではない。**テストが再現している状況が主張と
一致しているか**は別に確かめる」。4 と同じ commit で足せる。

## 6. CI が「1 件目で止まって 2 件目が見えない」ので往復が増えた

`make test-discovered-rest` は最初の失敗で止まる。そのため 1 回の push で 1 バグしか
見えず、retro-open を直した次の push で初めて mark-seen の失敗が現れた
(mark-seen は**それまで一度も走っていなかった**)。

**切り出し先の提案**: 新規 issue —「CI では失敗しても全テストを走らせて集計する
(`--keep-going` 相当)。ローカルは今のまま早期終了でよい」。

## 7. 並行セッションが私の未 push コミットをまとめて push した

「push は明示指示があるときだけ」で溜めていた 8 コミットが、並行セッション
(`dotfiles-8d`) の `git push` でブランチごと push された。pathspec 規律は**混入**は
防ぐが、**push の粒度**は守れない (push はブランチ単位のため構造的に無理)。

**切り出し先の提案**: 却下ではなく判断が要る。選択肢は
(a) 現状維持 (実害は「意図より早く公開される」だけ) /
(b) 溜めるなら worktree + 別ブランチに逃がす /
(c) 「未 push で溜める」運用自体をやめる。ユーザーの判断待ち。

## 8. 大きな仕様 issue を自己レビューだけで確定させた

091 は 490 行の設計仕様で、SMB の挙動という**実測していない前提**を多数含む。
規約 ([`issue-creation-codex-review.md`](../_claude/rules/issue-creation-codex-review.md)) は
新規 issue を codex の反証レビューに通すことを求めるが、このマシンでは codex を使わない
設定のため通していない。実機検証 (092) までは「反証されていない仕様」のまま。

**切り出し先の提案**: 判断が要る。(a) codex 不使用の環境では別視点レビューをどう代替するか
を決める (サブエージェントによる反証レビュー等) / (b) 「実測前の仕様は反証レビュー不要」と
割り切る。ユーザーの判断待ち。
