# 778 (retro): tmp/ の残骸の調査から skill-tmpdir と clean-tmp の改修まで

起票日: 2026-10-16

## 概要

issue 774 のセッションの振り返り。`tmp/` 直下に溜まったログの原因を調べ、置き場の規約を直し、skill の出力先を
`tmp/<skill名>/<session-id>/` に寄せ (`bin/skill-tmpdir`)、`make clean-tmp` をその形に合わせた。敵対的レビューは規約に 2 周、
skill-tmpdir に 1 周、clean_tmp に 4 周かけた。

## どこで踏んだか / 回りくどかったか

1. **規約の根拠に他の文書を引いたが、引用先を読んでいなかった**。置き場の規約に「後から確かめる run は codex-drive に従い ./tmp」
   「scratchpad はセッション終了で消える」と書いたが、codex-drive 自身が `./tmp/<タスク>/` と scratchpad で割れており、
   scratchpad は実際には再起動まで残っていた (過去 session の dir が 20 個)。1 周目の red team で崩れた
2. **作法を命じる規約が、出力の置き場と寿命を決めていなかった**。「`> log 2>&1` でファイルに落として読め」と「置き場は ./tmp」の
   組み合わせに忠実に従った結果が、直下の 1170 件だった。命じた側の規約には「誰が消すか」が無かった
3. **破壊的操作の直前の取り直しが、実体ではなく文字列を見ていた**。clean_tmp の削除を「親へ cd → pwd -P で確認 → 相対名で rm」に
   したが、builtin の `pwd -P` は cwd ではなく `$PWD` を解決し直すだけだった (3 周目で発覚。`/bin/pwd -P` は getcwd)
4. **承認の範囲を取り違えた**。ファイルの削除の承認でディレクトリまで消そうとして、auto mode に止められた。
   承認を求めたときに「ファイル」と「ディレクトリ」を分けて書いていなかった
5. 変異の置換文字列に `rm -rf` が含まれていたため、Claude Code の安全チェックに止められ、1 つの変異を当てられなかった

## 次に効きそうな改善 (提案)

| # | 一般形 | 切り出し先 | 状態 |
|---|---|---|---|
| 1 | 規約・コメント・issue に**根拠として他の文書を引くときは、引く行をその場で読む** (要約や記憶で引かない)。引用先の中で記述が割れていたら、引く前に割れを直すか、割れていると書く | 既存 rule `claude-md-maintenance.md` の「書き方」節への追記 (`pending-issue-rationale-in-code.md` は却下した指摘の理由をコードに残すときの rule で、発動点が違う) | 提案 (ユーザー判断待ち) |
| 2 | **出力を作らせる作法 (ファイルに落とせ・保存せよ) を規約に書くなら、置き場と消す人を同じ行に書く** | 決着: `_claude/CLAUDE.md`「一時ファイルの配置」に置き場を書いた (issue 774)。新しい rule は立てない | 済 |
| 3 | **破壊的操作の直前に取り直す値は、実体 (getcwd・inode・fd) から取る**。シェルの builtin や環境変数のように、前に覚えた文字列を返すものを確認に使わない | 既存 rule `adversarial-review-own-safeguards.md` の §0-B 近辺への追記 (`sandbox-real-destructive-test-apis.md` はテストから破壊的 API を呼ぶときが発動点で、今回は production の削除経路。「直前に取り直す」は同 rule に既にあり、足りないのは「値の出所を実体にする」の 1 点。実装側の正本は `scripts/clean_tmp.sh` 冒頭のコメント) | 提案 (ユーザー判断待ち) |
| 4 | 承認を求めるときは、対象の**種類** (ファイル / ディレクトリ / プロセス) を分けて列挙する | 既存 `~/.claude/CLAUDE.md`「確認を求めるときは、選択肢ごとに…」への追記 (その項は「何が起きるか / 失われるもの」の列挙までで、対象の種類を分けることは書いていない。反証レビューで却下理由が崩れた) | 提案 (ユーザー判断待ち) |
| 5 | 変異の置換文字列に破壊的コマンドを含めない | 却下: 当てられなかった変異は「未確認」と書けば足りる (その形が外を消すことはレビュアーが shim で別に再現済み)。破壊的コマンドを文字列に書かずに変異を当てる手段 (`mutate-verify --apply` のスクリプト) の要否は、次に同じことが起きたときに判断する | 却下 |
