## 踏んだ所

1. **自分の commit を組み直すために `git reset --soft origin/master` を打ったら、上流の 24 行を巻き戻す commit ができた** (push 前に気づいた)。
   rebase した後に別のセッションの push を `git fetch` で取り込んでいて、origin/master は rebase の土台より先へ進んでいた。soft reset で
   index が「新しい origin/master + 自分の木 (古い土台)」になり、pathspec で commit した自分のファイルのうち、上流も変えていた
   `model.go` が上流の変更を打ち消した。pathspec の規律は「他人のファイルを混ぜない」は守るが、**自分のファイルの中の上流の変更**は守らない。
   気づいたのは commit の後の `git status` に他人のファイルの打ち消しが並んだからで、`model.go` 自体の巻き戻しは stat では見えなかった
   (土台からの差分を `git diff --stat <土台> HEAD~1 -- <自分のファイル>` で見て分かった)。直し方: 自分の変更を土台からのパッチに保存し、
   worktree を最新に戻して `git apply --3way` で当て直した。
   **この形は `_claude/rules-checklists/commit-with-pathspec.md` の履歴操作の節にそのまま書いてある** (soft reset の起点は共有の ref ではなく
   hash で固定する)。`commit-with-pathspec.md` は soft reset の前にこのチェックリストを Read せよと言っているが、読まずに打った
2. **計測の台本の 2 段が、最初から空打ちだった** (move / search)。どちらもカーソルの列の中で動くキーなのに、台本は root (列は root だけ)
   にカーソルを置いたまま打っていた。段の後の状態 (カーソル) を記録する列は作っていたが、その値が `.` のままなのを 4 回の実測で
   読み流し (どの回の要約にも `move ... cursor=.` と出ていた)、反証レビューに指摘されるまで気づかなかった。直した後の煙テストも、2 周目のレビューで「まだ空打ちを通す」と指摘された
   (`l` が効けば満たされる確認だった)
3. **共有の Go のビルドキャッシュが、別の作業で消されている最中にビルドが 2 回落ちた** (`could not import ... no such file or directory`)。
   `GOCACHE` をこの作業用のディレクトリへ向けて回避した
4. 既存のルールで止まるはずだったもの (2 件目): 確保の予算のテストの 1 回目の赤を `| tail -1` で削って読み、原因を失った
   (`verify-execution-not-just-exit-code.md` の「出力を削って読まない」)

## 提案

1. (踏んだ所 1) 却下: 規範は既にチェックリストにある (起点を hash で固定する)。足りなかったのは「soft reset の前にチェックリストを Read する」
   を守ることで、書き足しても同じく読まれない。ルールの側で打てる手があるとすれば、`git reset --soft origin/...` の形を hook で止めることだが、
   字面の判定で他の正当な使い方を止めないかを確かめていないので、ここでは提案しない
2. (踏んだ所 2) **台本で操作を流す計測・検証の道具を作ったら、段ごとに「その段で状態が変わった」ことを、作った時点の煙テストで名前の
   完全一致で確かめる**。状態を記録する列を作るだけでは、読み手が空打ちを読み流す。「前と違う」「空でない」のような緩い確かめは、
   別のキーが効いただけで満たされる。計測の道具に限らず、E2E の台本・負荷の台本でも同じ。
   既存の近い規範 (同じ節の「派生どうしが違う値を出すことを先に確かめる」、「崩し・fixture が作る前と違う状態になったことを機械で
   確認する」、`instrument-before-second-fix.md` の「無反応が no-op の正しい状態から来ていないか」) は、道具の入力や読み手の側を見る。
   こちらは台本の段ごとの出口を見るもので、状態の列を作るだけでは足りず名前の完全一致まで要る、という点が足りていない。
   切り出し先: `_claude/rules/verify-execution-not-just-exit-code.md` の「抽出・判定を書いたら、同じ経路を通る canary を先に置く」へ追記。
   節の発動点 (抽出・判定を書いたとき) に「操作の台本を流す道具を書いたとき」を足す形で
3. (踏んだ所 3) 却下: 共有のビルドキャッシュを誰が消したかを確かめていない。並行のセッションの片付け (`go clean -cache` 等) なら
   その作業の側の問題で、ここで一般の規範にできるほど事実が無い。次に同じ形で落ちたら、その時点で `ps` で消している相手を見る
4. (踏んだ所 4) 却下: 既存のルールで足りている (守れなかっただけ)
