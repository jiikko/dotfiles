# `link(2)` が使えない FS では、`tryPlace` の tmp 書き込み (fsync 込み) が丸ごと捨てられる

起票日: 2026-09-18
カテゴリ: perf / priority: **medium**
対象: `src/lockman/lock.go` の `tryPlace`
出典: [issue 391](391-bug-lockman-os-exit-skips-defer-leaves-scratch.md) の調査中に発見
反証レビュー: 未実施。**数値は起票者の実測**（下表）

## 問題

`tryPlace` は必ず `writeFileSync(tmp, b)` (**fsync 込み**) してから `link(2)` を試すが、
**fallback 枝 (O_EXCL) は tmp を 1 バイトも読まない** — lock のパスを直接開いて
同じバイト列を書く。つまり `link` が失敗する FS では、fsync 付きの書き込みが 1 回分
丸ごと捨てられる (その後 `defer` で unlink もする)。

`lock.go` 自身が「macOS の smbfs では ENOTSUP になりうるので O_EXCL に落とす」と
書いており、**それが本番の経路**。

## 実測 (2026-09-18、ローカル APFS)

`tryPlaceLinkFn` を `syscall.ENOTSUP` 固定にしたビルドで、acquire の所要時間 (中央値、80 試行):

| 版 | 中央値 |
|---|---|
| 現行 (tmp を必ず書く) | 32.3ms |
| 計測専用 (tmp を書かない) | **24.0ms (-26%)** |

参考: `link` が使える枝の現行は 28.4ms。

🚨 **これは節約の上限であって、実装の効果ではない。** 計測版は「link を使わないと
分かっている」前提で tmp を省いただけで、**そのままでは実装にならない** (link の可否は
試すまで分からない)。

🚨 **SMB では未実測**。fsync が往復になるので差は開くはずだが、数字は無い。
`perf-claims-need-measurement.md` に従い、**「SMB で速くなる」とは書かない**。

## なぜ今の形になっているか (壊す前に確認したこと)

`link(2)` 経由だと lock は「最初から中身が入った状態」で現れる = **途中経過が他者に
見えない**。O_EXCL 枝はこの性質を持てず、そのぶん issue 383 が
「中身を書けなかった lock を消す」後始末 (`cleanupOwn`) を足している。
**tmp は link 枝の正しさのために要る**ので、単純に消すことはできない。

## 対応の候補 (未決。着手前に再評価すること)

- **何もしない**。26% は「起動時間込みの中央値」に対する比で、絶対値は約 8ms。
  `lockman` は 1 ファイル 1 回の呼び出しなので、体感に出るかは不明
- **link の可否を 1 度だけ判定して覚える**。判定自体が I/O で、どこに覚えるか
  (プロセス内 / dir 内のマーカー) で意味が変わる。**dir 内に持つと新しい状態が増える** ので、
  `adversarial-review-own-safeguards.md` §0-A の対象
- **link を先に試してから tmp を書く**。`link` の材料が無いと試せないので、
  「0 バイトの tmp で link を試す → 使えたら書き直す」等の形になり、
  **中身の無い lock が見える窓**を作る (383 が潰した failure mode の再導入)。おそらく不可
