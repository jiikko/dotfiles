## 気づき・反省

### 1. 監査観点の追加は「推測で軸を立てる」より「done を数える」が速い

最初は並行性・永続互換・platform 差を候補に挙げたが、どれも**この repo で実際に再発しているかを
確かめていなかった**。`issues/done/*-bug-*.md` を 108 件読むと軸の分布がそのまま出て、
最多軸が既存タイプの穴だと分かった。しかも `persistence-compat` は候補として**誤り**だった
(doctor_cache は版を持たない代わりに読み込み時検証で解いており、設計選択の証拠がコメントにある)。

- **切り出し先**: 既存タイプ `lint-from-done` の調査指針に「lint に落ちない軸は audit タイプの
  候補として報告する」を足す / または audit skill に「新しい監査タイプを足す前に done を数える」を書く
- 🚨 ただし**新規ルールは立てない**。発動点は「audit skill を触るとき」だけなので skill 本文に書く

### 2. 「実装が食い違う = 片方にバグ」を裏取りせずに書きかけた

3 箇所の実装差 (`if dropped > 0` の有無) を見て「片方にバグがある」と report しかけたが、
実際は disk 側だけが `Ref` の無害化を持つための差で、**3 箇所とも正しかった**。
advisor の指摘で commit 前に訂正した。

- CLAUDE.md「主張は証拠ではない」の自分版。**差分を見つけた時点では「差がある」までしか言えず、
  「どちらかが誤り」は別の根拠が要る**
- **切り出し先**: 既存ルールで足りている (再発したら `mutation-verify-new-tests.md` の
  「不在の主張の裏取り」節に「差の解釈も同じ」を足す) → **今回は却下**

### 3. E2 の修正で、過去のレビューが塞いだ穴を再導入しかけた

`Size` を無条件に引き直す形にしようとして、Items を持たない Reused の合計が 0 になる退行を
作る手前だった (2026-09-04 の敵対レビューが同じ穴を塞いでいた)。

- **切り出し先**: audit skill の E2 へ追記済み (「寄せる前に各呼び出し側の例外を先に列挙する」)。
  → **対応済み**

### 4. 今回の観点は「よく手入れされたコードベースほど効く」

壊れているものは既存タイプが拾っているので、残るのは「まだ壊れていないが silent に壊せる構造」だけ。
glogx には同じ形を症状が出てから直した痕跡が複数あった (issue 224 / 238 / 268 / 048 の
「唯一の出典」コメント群)。**観点として名前が付いていなかっただけ**で、発火点を書くと機械的に探せる。

- **切り出し先**: なし (知見の記録)
