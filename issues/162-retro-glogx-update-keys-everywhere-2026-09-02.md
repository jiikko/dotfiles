## 反省・気づき

   (非 nil) と、updateBeginMsg を直接 Update へ流した結果で取っていた。前者は maybeTick の副作用で
   overlay が飲んでも非 nil になる経路があり、後者は届かなくても updating が立つ。敵対レビューが
   変異 (配線を無効化) で status サブテストだけ緑のまま残ることを実証した。自分の変異 4 本は
   全部 red だったが、それは他のサブテストが落ちていたから。**サブテスト単位で red を見ていなかった**。
   → 切り出し先: `_claude/rules/mutation-verify-new-tests.md` の「よくある『守っていないテスト』の形」に
   「テーブル駆動テストは、変異で**全ケース**が red になるかを見る (1 ケースでも緑なら、そのケースは
   何も守っていない)」を 1 項足す
2. **到達範囲の洗い出しが「C/X を束ねている overlay」だけで、「全キーを飲む overlay」を見ていなかった**。
   grep で `"C"` / `"X"` を探して「他に割り当ては無い」で止め、diff / PR status ポップアップが未知キーを
   丸ごと飲んでいた (= 以前は届かなかった) ことを 2 体のレビューに指摘された。判定順を動かす変更では
   「その位置より後ろにある分岐が、素通りではなく飲んでいたか」を 1 つずつ見る必要がある。
   → 切り出し先: 却下 (`survey-receiver-guards-before-passing-new-values.md` の「新しい値が初めて到達する
   分岐を列挙する」がそのまま該当する。守らなかっただけ)

   担当範囲を聞いてから始め、相手の commit 後に rebase したら衝突なし。→ 切り出し不要 (既存ルールどおり)

   (status viewer で codex update も要るなら、X 以外のキーを決めてもらう)
