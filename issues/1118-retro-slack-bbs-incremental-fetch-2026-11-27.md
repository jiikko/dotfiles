# 1118 (retro): slack-bbs の差分の取得 (issue 1086) の振り返り

起票日: 2026-11-27

## 概要

issue 1086 (slack-bbs の取得を差分で取る) を、計測 → `R` の確認の板 → 案 1 の実装まで進めた。opus の敵対的レビューを 6 周回し、
本物の Slack で効果を確かめた (#discuss-銚子丸 でスレッドの読み込みが 15 本 → 0 本)。そのセッションで踏んだ所。

## どこで踏んだか / 何が回りくどかったか

1. **書き換えスクリプトの失敗を、別の道具の出力と読み違えた**。python で 2 つのファイルを書き換えるスクリプトが、1 つ目の置換が当たらずに `sys.exit` で止まった。
   止まったときの出力 (`main_test.go: 0 …`) を gofmt の出力と読み、テスト 4 本が足されていないまま「テスト green」を確かめ、実装をわざと壊す確認を 6 本回した。
   壊しても全部 green のままだったことで初めて気づき、`-v` で回すと `no tests to run` だった
2. **テストの補助の closure の中で `t.TempDir()` を呼び、呼ぶたびに別のディレクトリになった** (キャッシュの置き場を毎回変えて、前回の板が無いことになった)。テストの誤りだったが、実装の誤りを先に疑った
3. **CI の run を待つ commit を誤った**。複数の commit をまとめて push したのに、途中の commit の SHA で `ci-log -i` を引いた。push の run は先端の commit で走るので、run が無いまま再試行を使い切った
4. **敵対的レビューの指摘を直した差分に、また別の誤りが入った** (バージョンの違うキャッシュの中身を ok を見ずに使う / 警告の付いたスレッドを全部捨てる)。
   どちらも「直した差分にもう 1 周」(rule `adversarial-review-own-safeguards.md` §7) で見つかった

## 次に役立ちそうな改善

- 1: 書き換えのスクリプトの rc を、出力を読む前に名指しで見る (`; echo rc=$?` を付けていたのに、出力の 1 行目だけを読んで判断した)。
  あわせて、足したテストは `go test -run <名前> -v` で **実行された** ことを 1 回見てから、実装をわざと壊して確かめる。
  → 既存の rule が既に言っている。`verify-execution-not-just-exit-code.md` の「実行された証拠で判定する」と、`mutation-verify-new-tests.md` の手順 0 である。
  局所の手順の抜けで、新しい規範は要らない。却下: 既存の rule で足りる
- 2: 局所の書き間違い。却下: 汎用の規範に引き上げられない
- 3: `ci-log -i` に commit を渡すときは、push した範囲の先端を渡す。
  → rule `use-ci-log-for-ci-inspection.md` は「その commit の run」を引くとしか書いていない。複数の commit をまとめて push したときに、どれを渡すかが無い。切り出し先の案: その rule に 1 行足す (「まとめて push したら、名指すのは先端の commit」)。ユーザーの判断を待つ
- 4: §7 が機能した例。改善の提案は無い
