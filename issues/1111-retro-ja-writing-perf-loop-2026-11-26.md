# 1111 (retro): ja-writing の Go をベンチマークで 10 周改善したセッションの振り返り

起票日: 2026-11-26

## 概要

issue 1079 (epic 1072) の「ベンチマークで Go を改善するループ」を、上限の 10 周まで回したセッション (2026-11-25〜26) の振り返り。
採ったのは 6 周 (2・3・4・6・7・9 周目) で、最後の Go は測った全部のケースで本家の Python より速くなった。数字と各周の記録は 1079 の本文にある。
出典は 1079 の本文。1079 に無い出来事 (C・D) は、このセッションの transcript から書いた。

## どこで踏んだか

- A. **同じ lint のコードから作った別のバイナリどうしで、lint のケースに 1〜4% の「遅い」が出た**。`bench/compare.py` の揺れの帯は、同じバイナリを 2 回測った組
  (same と orig) の比から取るので、バイナリどうしの差を含まない。6 周目の 1 回目の run では lint の 3 ケースが 1.01〜1.05 倍で「遅い」と出て、計画の採用条件を満たさなかった。
  2 回目の run では it5 を対照として足した。it5 は 5 周目に戻した diff の直しのバイナリで、lint のコードは it4 と同じ。
  その it5 と it4 の組でも lint の 4 ケースが 1.013〜1.043 倍の「遅い」になり、揺れと読めた。
  9 周目でも、直しが触らない lint のケースに 0.964〜1.006 倍の「速い」「遅い」が付いた
- B. **5 周目に「効果なし」として戻した diff の直しが、9 周目に周の数を増やして測り直すと 0.945 倍で採れた**。5 周目の判断は 5 周の run 1 回だけで、
  2 回目の run (6 周目の対照として入れた) では 0.944 倍と食い違っていた。食い違いを見た時点では測り直さず、記録だけ残して先へ進んだ
- C. **比べるバイナリを作業ツリーから作り、当てたままのパッチが前の周のバイナリに混ざった** (9 周目のパッチを当てた木で jw-it7 を作り直した。transcript)。
  気づいてパッチを外して作り直し、`cmp` で 2 本が別物なのを見てから計測に入った
- E. **6 周目のレビューの勧めを当てると遅くなった**。勧めは、探索を添字を返す関数に分けて共有する形。分けると `inRanges` がインライン展開されなくなった。
  lint-len-1024k の in-process で 1 回 473 ms → 490〜515 ms。戻して、理由をコードのコメントに書いた

## 何が回りくどかったか

- D. **check を in-process で測るベンチマークを 3 回作り直してから、やめた** (transcript)。1 回落ちるたびに、check が起こし方で分かれる条件を 1 つずつ見つけた
  (作業フォルダの照合・作業フォルダの外のファイルの断り・子のプロセスとして起こされたときの印)。やめた理由は 1079 に書いたとおり、
  check は lint と diff を子のプロセスとして起こすので、in-process では子の分が見えないこと。これはコードを読めば作る前に分かった。diff の in-process のベンチマークに切り替えた

## 次に役立ちそうな改善 (提案。実行はユーザーの判断を待つ)

1. **別々にビルドしたバイナリどうしの所要を比べるときは、対象の経路のコードが同じ別のビルドを対照として同じ run に入れ、その組の比も並べて読む**。
   同じバイナリを繰り返し測った揺れは、ビルドどうしの差を含まない (差の原因は測っていない)。A の一般形。コンパイルする言語の性能の比べ全般に当てはまる。
   切り出し先: `_claude/rules/perf-claims-need-measurement.md` の「before / after の所要は、別の時間帯の run どうしで比べない」の項に追記
2. **同じ変更の測り直しで結論が割れたら、記録だけ残して先へ進まない。決着に使う run の回数と、何回で採るかを先に決めてから回す**。
   1079 の 9 周目は、3 回の run のうち 2 回が 5〜6% 速いことを根拠に採った。
   割れたまま戻した直しは、後から拾い直されない限り失われる。B の一般形。切り出し先: 1 と同じ項に追記
3. **比べるバイナリは、commit から切った worktree で作る**。作業ツリーで作ると、当てたままのパッチ・未コミットの直しが混ざる。
   C の一般形。作った後に別物かを確かめる段は、`verify-execution-not-just-exit-code.md` の「作る前と違う状態になったことを機械で確認する」で足りるので足さない。
   切り出し先: 1 と同じ項の近くに 1 行

却下:

- D: 既にある `perf-claims-need-measurement.md` の「測った経路がユーザーの実経路と同じかを、数字を書く前に確かめる」の項が当てはまる。in-process で子のプロセスの分が抜けるのは、その項の言う経路の違い。
  発動点 (計測を作る前) を踏み損ねただけなので、規範は足さない
- E: 局所的なこと (Go のインライン展開の予算)。理由と測った値は `src/ja-writing/internal/pyunicode/pyunicode.go` の `inRanges` のコメントに書いた
