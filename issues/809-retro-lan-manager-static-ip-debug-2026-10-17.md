# 809 (retro): lan-manager の相手の固定 IP のデバッグが難航した理由

起票日: 2026-10-17

## 概要

air5 の相手の固定 IP (747 の段 4 / 789 の手順 3) が、何度試しても効かなかった件の振り返り。原因は 1 つ (切り離した背景の処理が
ssh の切断の SIGHUP で走り出す前に死んでいた) だったが、ユーザーの試行が 2 回 (操作のログの 07:24 と 08:07) 空振りした。

## どこで踏んだか

1. **自分で書いた止めを、自分で越えていた**: `setup/staticip.go` の冒頭に「本物の networksetup / sudo を起こすのは、人手の確認
   (ssh が切れても変更が最後まで走るか・use_pty の下で nohup が SIGHUP を捨てられるか) が済んでから」と書いていた (44887e71)。
   その確認を 789 の手順 3 として人に回した (74ca993b) 後、確認を待たずに `RemoteCommand` を本物の ssh へ配線した (576db8e5)。
   コメントは何も止めなかった
2. **失敗が成功に見える作りだった**: 相手の変更は `sudo -n -b nohup sh -c <本体> >/dev/null 2>&1` で背景に回していた。`sudo -b` は
   すぐ戻るので、子が死んでも前面は rc=0 (操作のログの `exec done err=<nil>`)。出力は捨て、背景が走り出したかを確かめる仕組みも
   無かった。原因に近づけたのは、air5 の状態ディレクトリ `/var/db/mac-lan-manager` が空で更新時刻が前の回のまま (= lock が一度も
   作られていない) という間接の証拠からだった
3. **テストは承知の上で穴を残していた**: 偽物の sudo は `-b` のとき `"$@" & exit 0`、nohup は `exec "$@"` で、SIGHUP も端末の切断も
   模さない。`setup_test.go` の `TestRemoteCommandRunsDetached` はその穴をコメントで明記し、挙動は人の確認に回していた。穴の扱いは
   正しかったが、1 のとおりその確認を待たずに配線したので、緑のテストが守っていないものが本番で動いていた
4. **「人が要る」を過大に申告していた**: 789 は手順 3 を「ssh の切断は相手が要る」として人に回した。実際には切断の競争そのものは、
   sudo 無しで自分の ssh から air5 に打って再現できた (789 の「結果」節)。人が要った理由は相手の sudo のパスワードだけだった
5. **最初の再現が代用品だった**: sudo 無しの `nohup sh -c ... &` で競争を再現して直したが、本物の `sudo -b` は子を別のプロセス
   グループに置くので同じ仕組みとは限らない、と敵対レビュー (opus) に指摘された。本物の sudo で 2 通りのダミー (すぐ抜ける / 印を
   待つ) をユーザーに打ってもらい (07:57)、すぐ抜けると 1 行も書かずに死に、待てば最後まで走ることで確定した
6. **別の症状が並行していて、本筋が埋もれた**: 観測に約 9〜13 秒かかって手順が「未実行」に見えた、確認中の y が黙って捨てられた、
   ホスト鍵の名前、169.254 の帯の経路、文言。これらを直している間、固定 IP が効かないのもその続きに見えていた
7. **ユーザーに回す前に、自分で通しで確かめていなかった**: 08:07 の再試行は修正前の版だった (修正の commit は 07:35、本体の
   checkout に入ったのは 08:16 の pull)。「まずお前の方で検証が成功してから俺に回して」と言われてから、検証の間だけ air5 に
   NOPASSWD を入れてもらった。画面からの 1 回目 (08:13、隔離した tmux) は `sudo -v` がそれでもパスワードを聞いて止まり、
   `verifypw=any` を足す変更は権限の判定で止められた。画面と同じ関数で組んだコマンドから `sudo -v` だけを外して打ち、
   「固定 → 新しい IP で入り直して確認 → 固定のまま残る」を通した (789 の「通しの検証」節)。NOPASSWD は検証の後に消した

## 何が回りくどかったか

- 権限 (相手の sudo のパスワード) が無いことを、試行のたびに人へ回す形で埋めていた。通しの検証に要る権限を最初に諮っていれば、
  空振りの試行は要らなかった
- 「push して本体へ取り込むまで、人の環境の版は古い」はこの repo の規約 (`.claude/rules/worktree-per-session.md`) にあったが、
  人に再試行を頼む時点で確かめていなかった (規約は足りていて、守れなかった。追記はしない)

## 切り出した改善 (2026-10-17、ユーザーの指示「提案もルールへ切り出す」)

反証レビューで、当初の提案の一部が既存のルールに既にあり、名指しした節の発動点も合わないと分かった。新しい部分だけを、発動点の
合う既存の節へ追記した:

- **切り離して起こす処理は、子が走り出した印を親が待つ。起動の rc を走り出した証拠にしない** (どこで踏んだか 2)
  → `_claude/rules-checklists/adversarial-review-own-safeguards.md` の §2「沈黙 = 成功」。当初の切り出し先
  (`verify-execution-not-just-exit-code.md` の background の節) は自分の検証の作法を扱う節で、製品のコードを設計するときには発動しない
- **pty が要る挙動を human issue に回したら、それが済むまで本物へ配線しない。コメントでは止まらない** (どこで踏んだか 1・3)
  → `_claude/rules/verify-interactive-prompt-with-pty-driver.md` (端末でしか成立しない挙動を human issue に回す、と定めている節の直後)。
  当初の切り出し先 (`measure-external-cli-streams-separately.md` の「fake も仮説」) には核心が既に書いてあった
- **人に試行を頼むとき、人が要る理由が権限だけなら、検証の間だけ権限を得る案を先に諮る** (どこで踏んだか 4・7)
  → `_claude/issue-rules.md` の `human` の節。「人の環境に修正が届いているか」は既存の規約にあるので足していない

## 局所的なもの (切り出さない)

- 観測の遅さ (ssh の多重化で約 9〜13 秒 → 約 2 秒)・確認中のキーの扱い・文言は、747 の中で直した
- 169.254 の帯に固定 IP を置くと、知らない 169.254 宛ての経路が Wi-Fi 側へ出る件は、789 に決定 (帯 A = 192.168.100.0/24) として残した
- NOPASSWD を入れても `sudo -v` だけはパスワードを聞く (admin グループの行が NOPASSWD でないため) のは sudo の仕様の知識で、
  規範にする形ではない
- `setup/staticip.go` の冒頭のコメント (1 の止め) は、確かめた形と、まだ本物で確かめていないこと (確認しなければ戻る経路) を書く形に
  直した
