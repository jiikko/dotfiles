# `os.Exit` が defer を走らせないため、見捨てた goroutine の probe / tmp が残る

起票日: 2026-09-18
カテゴリ: bug / priority: **low**
対象: `src/lockman/lock.go` の `serverNow` (probe) と `tryPlace` (tmp)、`src/lockman/cleanup.go` の `sweepDir`
出典: [issue 362](362-bug-lockman-abandoned-timeout-goroutine-leaves-lock.md) の敵対的レビュー 3 周目 (観点「並行・中断」) のぼやき
反証レビュー: 未実施。**数値は起票者の実測**（下表）

## 問題

`serverNow` は probe を、`tryPlace` は tmp を作り、どちらも **goroutine 内の `defer` で自分で消す**
設計になっている。しかし `--io-timeout` で見捨てられた goroutine は `os.Exit` と競走しており、
**`os.Exit` は defer を走らせない**ので、負けた分がそのまま残る。

362 の本文が「④ 書きかけ (`tmp/<token>.json`) は数えなくてよい」としていた根拠は
「`defer os.Remove(tmp)` が見捨てられた goroutine の中でも走る (goroutine が完走すれば消える)」で、
**「完走すれば」の条件が満たされない割合が実測で無視できない**、というのが本 issue。

## 実測 (2026-09-18)

`--io-timeout 3ms`、8 並行 × 40 ラウンド = 320 起動、毎回新規 dir。
🚨 **計測には `minIOTimeout` を 1ms へ下げたビルドを使った** (製品の下限は 100ms)。
出荷バイナリはローカルの速い FS では timeout が発火しないため、この現象を再現できない
(実測: 出荷バイナリ + `--io-timeout 100ms` で 40 起動 / 残骸 0)。

| 版 | probe 残骸 | tmp 残骸 | lock 残骸 |
|---|---|---|---|
| 362 の修正前 (`a75ffe3d`) | 24 | 148 | **73** |
| 362 の修正後 (`e8fe1374`) | 24 | 135 | **0** |

- **この件は 362 の変更以前からの性質**で、悪化していない (probe は同数、tmp は微減)
- lock の 73 → 0 は 362 の成果であって本 issue の対象ではない

## なぜ気にするか (掃除の担当が居るのに)

残骸の担当は `Cleanup` の `sweepDir(tmp, 1h)` / `sweepDir(probe, 1h)` で、**通常はこれで足りる**。
気にするのは次の 2 点:

1. **残骸が出る条件と、掃除が効かない条件が同じ**。残骸は「I/O が `--io-timeout` を超えた」ときに
   出る = マウントが遅いとき。その同じマウントで `CleanupTimed` も同じ期限で切られるため、
   **最も残骸が出る場面で、最も掃除が届かない**
2. **`sweepDir` は 1 時間より新しいものを消さない**。高頻度で呼ぶ運用 (av1ify のような per-file の
   ロック) では、1 時間あたりの残骸が回収より速く積む状況がありうる

## 全数勘定 (2026-09-18 時点)

見捨てられた goroutine が残しうるもののうち、**362 が閉じたもの**と**本 issue のもの**:

| 物体 | 362 の扱い | 本 issue |
|---|---|---|
| lock 本体 | 閉じた (実測 73 → 0) | 対象外 |
| `tmp/<gen>.takeover` (claim) | 閉じた | 対象外 |
| `tmp/<gen>.takeover.<nanos>` (mark) | ほぼ閉じた (7 → 1) | 対象外 |
| **`probe/<token>`** | ④ として対象外とした | **本 issue** |
| **`tmp/<token>.json` (書きかけ)** | ④ として対象外とした | **本 issue** |

## 対応の候補 (未決。着手前に再評価すること)

- **何もしない**。残骸はロック dir の排他を 1 mm も壊さない (名前が一意で、誰も参照しない)。
  1 時間後に sweep が拾う。**これが既定の判断でよいと思われる**
- `sweepDir` の保持期間を probe / tmp について短くする。🚨 ただし `minRetention = 10 分` の
  下限があり、これは「飛行中の他プロセスの probe を消さない」ための下限なので、
  **下げるなら飛行中との区別を先に作る**必要がある
- 残骸を出さない構造にする (probe を作らずサーバ時刻を得る / tmp を使わず書く)。
  🚨 `adversarial-review-own-safeguards.md` §0-A の「作らずに済む構造」に当たるが、
  **probe は「サーバの時計を読む」唯一の手段**として選ばれた設計なので、代替の検討から要る
