## どこで踏んだか / 何が回りくどかったか

1. **集約の検査 (root の `make test`) が rc=2 のとき、失敗を自分が予想した種類の行 (Go の FAIL・shell の全腕合計) だけで拾い、
   別の種類の対象 (`test-unused-excluding-tests` = production から到達不能の検査) の赤を見落とした**。shell の 3 本を「単独で緑・無関係」と
   帰属させて push し、723 の commit で CI の `unused` を赤にした (714 の検査の rc=2 を追って気づき、`layoutAll` を test へ移して直した)。
   ローカルの root の `make test` も最後に `✗ 失敗したターゲット: test-unused-excluding-tests` を出していた (714 の検査のログで確認。723 のときも同じ対象が走っていた)
2. **最適化そのものが、ベンチの 1 回の操作の仕事の量を変えた**。723 で「空欄の検索は列を作らない」近道を足したため、
   backspace + 1 文字のベンチは before = 列 2 回・after = 列 1 回になり、after を最大 2 倍よく見せていた (5 万件で 6.3ms と出たものが、揃えると 10.6ms)。敵対レビューが指摘し、
   空欄を通らない操作に変えて origin/master と同じ実行で測り直した
3. **OS の資源を読む経路の差し替え (714) で、正解役との突き合わせの入力が合成した fixture だけだった**。symlink・fifo・NFD などは
   混ぜたが、マウントポイント・ファームリンク (`/` の Users 等) は一時ディレクトリに作れず、bulk が覆われた側の値を返す食い違いを
   敵対レビューが `/` で見つけるまで素通りした。テストに `/`・`/System/Volumes`・`/Volumes` の実物を入れて固定した
4. **issue に書かれた外部の振る舞いが 2 つ外れていた** (「大文字小文字だけの rename は RENAME_EXCL が EEXIST」→ 実測で通る・
   「操作の後の光は二重に走らない」→ 次のポーリングで光る)。実測で数分で分かり、外れた前提に合わせて書いた一時名の経路は消した
