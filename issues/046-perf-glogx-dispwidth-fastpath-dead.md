# glogx: dispWidth の ASCII fast-path が実質死んでいて、View 1 フレームの CPU の 64% が幅計測

起票日: 2026-08-14
種別: perf (実測駆動)
優先度: **P1** (フレーム描画の最大コスト。修正の効果が数値で確定している)

## 観測した事実

`BenchmarkViewSteady` (一覧 1 フレーム・120x40) の CPU プロファイルで、
`browseModel.View` の cum 2.01s のうち **`dispWidth` が 1.29s = View の CPU の 64%**。
その 98.8% は `ansi.StringWidth` → `FirstGraphemeCluster` → uax29 の grapheme 走査。
呼び出し元は `clipMeasure` が 81%。

`width.go` の `dispWidth` は 2026-07-29 に「印字可能 ASCII だけなら `len(s)` を返す」
fast-path を入れてある。**この fast-path がほぼ機能していない。**

計測 (200 フレーム分の全 `dispWidth` 呼び出しを分類。ログ: `tmp/glogx-perf/dispwidth_probe.txt`):

| 画面 | 総呼び出し | fast-path 到達 | slow-path |
|---|---|---|---|
| 一覧 | 16501 | 5900 (35.8%) | 10601 (**64.2%**) |
| status viewer | 53901 | 19700 (36.5%) | 34201 (**63.5%**) |
| diff popup | 28701 | 12100 (42.2%) | 16601 (**57.8%**) |

slow-path に落ちる要因の内訳 (fast-path を外した最初のバイト):

| 画面 | 要因 1 | 要因 2 | 要因 3 |
|---|---|---|---|
| 一覧 | `ESC` 96.2% | `→` U+2192 3.8% | `─` U+2500 0.0% |
| status | `ESC` 78.9% | `…` U+2026 18.7% | `─` / `→` 各 1.2% |
| diff | `ESC` 97.6% | `→` U+2192 2.4% | `─` U+2500 0.0% |

## なぜ死んでいるか (前提の誤り)

fast-path のガードは `s[i] < 0x20 || s[i] > 0x7e` で、**ESC (0x1b) が `< 0x20` に該当する**。
色付きの行は必ず SGR (`ESC[...m`) を含むので、**色を付けた行は 1 つ残らず fast-path を通れない**。
`colored` が既定 (TTY かつ `NO_COLOR` 未設定) なので、実運用ではほぼ全行が slow-path。

さらに、SGR だけを許しても足りない。「ASCII + SGR のみ」で構成される文字列は
実測で **0.0〜0.7%** しかない — glogx が出す行にはたいてい幅 1 の非 ASCII 記号
(CI 状態の `✓ ✗ ● ⊘ ↑`・枠線 `─ │`・切り詰めの `…`・`→`・スピナー `⠋`) が混ざるため。
**「ESC を通すだけ」の素朴な修正では効かない**ことが計測で確定している。

## 対応方針 (計測で裏付けのある形)

fast-path を「**印字可能 ASCII + SGR (`ESC[` 数字/`;` `m`) + 幅 1 の記号の許可リスト**」まで広げ、
それ以外 (`≥0x80` で許可リスト外 / SGR 以外のエスケープ / 途中で切れたエスケープ / C0) は
従来どおり `ansi.StringWidth` へ落とす。

この候補で拾える範囲を実測済み (同ログ):

| 画面 | slow のうち候補が拾える | 全体に対して | `ansi.StringWidth` との幅の不一致 |
|---|---|---|---|
| 一覧 | 10401/10601 (**98.1%**) | 63.0% | **0 件** |
| status | 33801/34201 (**98.8%**) | 62.7% | **0 件** |
| diff | 16201/16601 (**97.6%**) | 56.4% | **0 件** |

### 正しさが構造的に保てる理由

許可リストに入れるのは「単独で 1 個の grapheme クラスタを成し、幅 1」の記号だけ。
クラスタが結合するには**後続**が combining mark / ZWJ / 異体字セレクタ / regional indicator
である必要があり、**それらは許可リストに入れない**。よって許可リストの文字同士は
決して結合しない = 1 文字 1 幅の単純加算が `ansi.StringWidth` と一致する。

`truncateKeepANSI` が意図的に作る「閉じていない色」や途中で切れたエスケープは、
終端 `m` が見つからない時点で fallback に落ちるので誤らない (この repo は
`width.go` の doc どおり幅モデルをエンジンと一致させる必要があるため、
**一致が崩れる可能性のある入力は必ずライブラリへ委ねる**)。

### 検証条件 (これを満たさないと入れない)

- 許可リストの各文字について `ansi.StringWidth(string(r)) == 1` を **テストで実証**する
  (表を手で書いて信じない)
- `dispWidth` の新旧を **差分 fuzz** (`go test -fuzz`) で `ansi.StringWidth` と突き合わせる。
  部分的なエスケープ・8bit・結合文字・絵文字・CJK を含む入力で不一致 0 を確認する
- 変異検証: 許可リストから 1 文字外す / SGR の終端判定を壊すと red になること

## やらないこと

- **`dispWidth` のメモ化 (`sync.Map` 等) はしない。** 既存ベンチは毎 iteration で同じ内容を
  描き直すため、メモ化すると**測定が嘘をつく** (実運用ではフレームごとに内容が変わる)。
  fast-path はステートレスで O(n) なので、この罠を構造的に避けられる
- 幅モデルの変更はしない (`GraphemeWidth` のまま。`width.go` 冒頭の doc が一次情報)

## 参考: 同時に観測したが本 issue では扱わないもの

1 フレーム内で**同じ文字列を測り直している**割合 (幅を持ち回せば削れる分):

| 画面 | 全呼び出しの重複 | slow-path のみの重複 |
|---|---|---|
| 一覧 | 46.3% | 34.0% |
| status | 47.2% | 36.8% |
| diff | 14.7% | 1.2% |

重複の最多は `""` (33 回) や `"  "` (11 回) のように**既に fast-path で済む安い文字列**に
偏っており、コスト重み付けでは 1/3 程度。fast-path を入れると slow-path 自体が安くなるので、
**この lever の価値は fast-path 後に再測定して判断する** (先回りで最適化しない)。
