## 反省

### 1. 変異スクリプトの `git checkout -- .` が、直前に足した未コミットのテストを食べた

変異検証で M6 (描画のカーソル判定を論理カーソルへ戻す) が**全 green** だったので、それを塞ぐ
テストを書き足し、同じ変異スクリプトを回し直した。結果は再び全 green — 足したテストが
**1 回目の `run_case` の `git checkout -- .` で消えていた**。`grep -c` で 0 件と分かるまで
「変異を検知できないテストを書いてしまった」と誤読しかけた。

[`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md) の「復元の作法」は
この罠を名指ししているし、読んだうえで踏んだ。本文が挙げている発動点は「レビュー指摘を直した直後」で、
**「変異が全 green だったので新しいテストを足した直後」という発動点が書かれていない**。しかも
こちらの方が構造的に起きやすい — 変異検証をしている最中なので、必ずスクリプトをもう一度回す。

**切り出し先の提案**: `mutation-verify-new-tests.md` の「復元の作法」に 1 行追記 —
「🚨 **変異が緑だったので新しいテストを足したときも、回し直す前に commit する**。変異ハーネスの
`git checkout` は、いま足したばかりのテストを最初の 1 ケースで消す (実測 2026-09-17)」。

### 2. 「状態を見るテスト」は、描画がその状態を使わなくなっても緑のまま

最初に書いた 5 本は `curGlide.active` / `dispCursor()` の戻り値 / 論理カーソルの着地を見ていた。
`rowLine` のカーソル判定を `cur` から `v.cursor` へ戻す変異 (= アニメが画面に一切出なくなる)
を当てると **5 本とも緑**だった。ユーザーの要望そのもの (「滑って見える」) を 1 本も守っていない。

塞いだのは、描画結果からカーソル記号の行を拾い、それが論理カーソルと違うことを見るテスト
(`TestIssuesListGlideMovesTheDrawnCursor`)。一般形は「**演出のテストは状態ではなく描画結果で書く**」。

**切り出し先の提案**: `mutation-verify-new-tests.md` の「よくある『守っていないテストの形』」に
1 項目追記 — 「**演出・表示の主張を、状態 (フラグ・補間値を返す関数) だけで固定していないか**。
描画がその状態を読まなくなる変異は状態テストを全部素通りする。主張が『画面でこう見える』なら、
テストも描画結果 (出力行) から読む」。

### 3. 症状の言葉 (「無反応」) を仮説の反証として受け取ってしまった

ユーザーの動作確認は「shift+space はいまだに何も反応がしない」だった。私の仮説は「素の `0x20` として
届く = **下方向に動く**」だったので、観測と食い違って見え、「仮説が外れた」と判断して IME の横取りなど
別の筋を立てた。

実際は仮説が正しく、**カーソルが最下端にいたので下へ動けず、画面が動かなかった**だけだった
(`g` で先頭へ戻してから押すと下へ半ページ動くことをユーザーが確認)。

教訓は「**端で止まる操作は『無反応』と同じ見え方をする**」。移動系のキーの症状報告を受けたときは、
仮説を捨てる前に**端にいなかったかを先に潰す** (今回は `g` で先頭へ戻す 1 手で確定した)。
外部要因 (IME・端末・tmux) の仮説を立てるのはその後でよかった。

**切り出し先の提案**: [`instrument-before-second-fix.md`](../_claude/rules/instrument-before-second-fix.md)
の「『何度直しても直らない』と言われたら、まず**非対称**を特定する」節に 1 行追記 —
「🚨 **移動・スクロール系の『無反応』は、端で止まっているだけのことがある。** 仮説を捨てる前に
『対象が端にいなかったか』を潰す (実測 2026-09-17: 端にいたための無反応を、キーが届いていない証拠と
読んで別の仮説へ移りかけた)」。

### 4. shift+space の答えは repo の中に既にあった

bubbletea → ultraviolet → kitty flag と外部ソースを追ってから実測した。しかし
`scroll_glide_test.go` の `TestShiftSpaceScrollsUp` のコメントが、2026-07-31 時点で
「端末が shift+space を区別せず素の " " を送る環境ではこの case に入らない」と既に書いていた。
`grep -rn 'shift+space'` の 3 件目を読めば筋は立っていた。

[`instrument-before-second-fix.md`](../_claude/rules/instrument-before-second-fix.md) の
「観測を足す前に既存の観測を grep する」がそのまま当たる。**ルールの射程は足りているので新規の
切り出しは不要** — ただし発動点が「1 回目の修正が外れた後」なので、今回のような
「要望を受けて調査を始める瞬間」には読まれなかった。

**切り出し先の提案**: 切り出さない (記録のみ)。実測して推定を事実に変えたこと自体には価値があり
(Apple Terminal で届かないことは誰も確認していなかった)、grep を先にしても実測は必要だった。

### 5. 自分の書いた patch スクリプトが、読んだファイルと違うファイルへ書いた

`s=open(p2).read()` した内容を `open(p, "w").write(...)` で**別のファイルへ**書き、
`issues_view.go` をテストファイルの中身で丸ごと上書きした。worktree を切ったばかりで
`git checkout -- .` で戻せたので実害ゼロ。

一般化できる規範は薄い (変数名の取り違え) が、**ヒアドキュメント内の python で複数ファイルを
編集するときは、読みと書きの変数を 1 組ずつ対にする**のが予防になる。

**切り出し先の提案**: 切り出さない (記録のみ)。
