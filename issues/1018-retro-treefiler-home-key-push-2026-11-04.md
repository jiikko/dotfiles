# 1018 (retro): treefiler の ' (起動時のカーソルへ戻る) と、断続的な push の失敗で止まった件

起票日: 2026-11-04

## 概要

treefiler に `'` (起動時のカーソルへ戻る。commit「feat(treefiler): ' で起動時のカーソルへ戻る」) を足したセッションの振り返り。
実装・テスト・変異 3 本は詰まらずに通ったが、push が断続的に失敗し、作業を残したままユーザーへ手で push してもらうよう頼んで止まった。
ユーザーが続きを促した後、同じコマンドの再試行 1 回で push は通った。

## どこで踏んだか

1. **一時的に見える外部の失敗で、再試行を尽くさずに止まった**
   - 経過 (transcript で確認した順): sandbox の中の `git fetch` が `Permission denied (publickey)` → sandbox の外の fetch は成功 →
     外の push 1 回目が `publickey` → 2 回目が remote の `Internal Server Error` で rejected → 3 回目 (外で fetch + push) は両方 `publickey`。
     ここで「SSH の認証が通ったり通らなかったりする」と報告し、worktree を残してユーザーに `! git push` を頼んで止まった
   - 2 回目と 3 回目の間で compaction を挟んだ。要約の「次の一手」に「push を 1 回だけ再試行する」と自分で上限を書き、それをそのまま引き継いだ
   - ユーザーが続きを促した後、同じ push が 1 回で通った (`b8363d3ea..f47ecf97e`)
   - 同じ鍵で外の fetch は通り、push は publickey と 500 を行き来した。一時的な失敗の可能性が高かったが、間隔を空けて再試行を重ねずに人へ返した。
     再試行を重ねれば通ったとは言えない (原因は確かめていない)。ただ、人へ返すのは間隔を空けた再試行を尽くした後でよかった

2. **GitHub への SSH の認証が、sandbox の中でも外でも断続的に断られた** (原因は未確認)
   - sandbox の中で打ったのは fetch 1 回だけで、それが `publickey` で失敗した。外でも push 1 回・fetch 1 回・push 1 回が `publickey` で失敗している。
     sandbox の中だけの問題とは言えない
   - sandbox の network 許可、SSH agent の socket への到達、GitHub 側の一時的な障害のどれなのかは確かめていない

3. gofmt の指摘 (places.go のコメントの桁揃え) を lint で拾った: 手で桁を揃えたため。lint が止めたので局所の話として扱い、提案にはしない

## 提案

- **A. 一時的に見える外部の失敗 (5xx・タイムアウト・同じ認証が通ったり通らなかったりする) は、間隔を空けた上限つきの再試行
  (例: 30 秒〜数分空けて 3〜4 回) を尽くしてから人へ返す。返すときは試した回数と間隔を書く**。
  自分で上限を書いて次のコンテキスト (compaction の要約・引き継ぎ) へ渡すときも、その上限が失敗の性質に見合っているかを書く前に問う
  - 切り出し先: `~/.claude/CLAUDE.md`「応答・成果物の長さとスコープ」の「止まってよいのは」の項への追記 (既定どおり既存への追記)。
    止まってよい条件の「意図的に守られたもの (権限・hook)」と区別がつかずに止まったので、発動点は同じ。
    既存の規約に、外部の失敗を間隔を空けて再試行してから返す項は見つからない (反証レビューで「再試行」「一時的」を grep)。
    `no-osascript-for-ui-verification.md` の「2 回失敗したら別の手段に切り替える」は、決定的に失敗する手段の話なので衝突しない。追記ではその違いを 1 行添える
- 却下: B (`publickey` の断続的な失敗の原因を観測する)。ユーザー判断 (2026-11-04): 稀に起きるだけなので扱わない
