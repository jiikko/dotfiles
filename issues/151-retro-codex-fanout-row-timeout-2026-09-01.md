2. **並行セッション調整が2回機能した**。148 重複の解消 (改番側の選定を pushed commit の参照数で

   「make test の red は第三者の編集途中分」という情報も先にもらえた

## 反省点

### 1. 敵対レビューが変異検証 all-red の後に P1 を 2 件出した (実測 4 回目)

変異 3 本 (行 timeout 無視 / \r 剥がし除去 / 検証除去) を全部 red にした**後**で、
敵対レビュー (read-only subagent 2 lens) が再現つき P1 を 2 件出した:

- `*[!0-9]*` の範囲式が `ja_JP.UTF-8` (この開発機の既定ロケール) の照合順で**全角数字を通す**
  → 通過後は `[ -ge ]` が integer expected で常に偽 = watchdog の無音無効化
- 19 桁以上の純数字も同じ経路で無音無効化 (bash の `[ ]` は intmax_t 超で評価エラー)

自分の書いた「非数値は弾く」テスト (`abc`) は、ガードが実際に主張する防御範囲の最弱部
(ロケール依存・桁あふれ) を踏んでいなかった。「変異は自分が想定した不変条件しか試さない」の
教科書的な実例。

- 切り出し先候補: [`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md) /
  [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md) の「実測 3 回」を 4 回へ更新

### 2. shell の数字検証ゲートに `[0-9]` 範囲式を使う罠は横展開が広い

repo 内に `*[!0-9]*` は 25 箇所あるが、他は全て「非数値 → 安全な既定値へフォールバック」用途
なので今回は修正しなかった (却下理由は issue 150 に記録)。ただし**今後 die/reject ゲートを
新設するとき**に同じ罠を踏む。要点は 2 つ:

- 範囲式 `[0-9]` はロケール照合で全角数字を通す → 検証ゲートでは明示列挙 `[0123456789]`
- 文字種検査だけでは足りない → `[ ]` の整数評価が壊れる桁あふれ (19 桁) も上限で弾く

- 切り出し先候補: `_claude/rules/` 新規 (トリガー型: 「shell で数値検証の die ゲートを書く瞬間」)。
  ただし頻度が低ければ、正本を `bin/codex-fanout` の `validate_timeout` コメントに置いて
  却下でもよい (現状コメントには両方の理由を書いてある)

### 3. issue 番号の重複が commit 済み同士で発生した (137 retro に続き番号問題 2 回目)

148 が 2 セッションで別々に起票され、両方 push まで通っていた。`test_issue_numbers_unique.sh`
が捕まえたので実害は改番コストのみだが、検出が「次に make test を回した人」任せで遅い。
起票時の採番は `ls` の最大 + 1 で、並行起票には構造的に弱い。

- 切り出し先候補: 検討のみ。案: 起票 commit の前に `git fetch` して origin 側の issues/ も
  数える手順を issues/README.md に一行足す (完全な解決ではないが窓が縮む)。hook 化は
  過剰かもしれない
