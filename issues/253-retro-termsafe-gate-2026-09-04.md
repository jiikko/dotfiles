## うまくいったこと

### 1. issue の案を実測で否定してから作り直した

251 の案 2 は「表示に出る構造体のフィールドへ、無害化を通っていない値を渡すな」を lint で止める、

そのまま実装すれば 35 件全部が誤検出になると分かった（無害化は値の生成側で済ませており、
読み手には `termsafe` の呼び出しが現れない）。

軸を「読み手側の代入」から「**関門そのものの網羅性**」へ移して実装した。
CLAUDE.md の「issue の記述を鵜呑みにしない」がそのまま効いた事例。

### 2. 検査が本物の素通しを 1 件見つけた

## 反省

### 4. 「代入の有無」で無害化を判定したのは近似が粗すぎた

敵対的レビューの P1-1。`touched` をフィールド名だけのキーで持ったため、同じ関門の中で
**同名フィールドが互いをマスク**した（`it.Reason` の無害化を丸ごと消しても `e.Reason` が残る）。
さらに `r.Failures = append(...)` が `r.Failures = sanitizeLines(...)` をマスクする形もあった。

- **原因**: 「関門の中でそのフィールドが代入されていれば通っている」という前提を、
  受け手と右辺を見ずに置いた。ネストした型を親の関門が処理する設計なら、
  受け手が違えば別のフィールドだと最初に気づけたはず
- **切り出し先の提案**: 却下。これは「AST の近似を設計するときの一般則」に見えるが、
  発動点が広すぎてルールにすると効かない。**この検査のヘッダに実例として書いた**ので、
  次に同じ検査を触る人には届く

### 5. 変異を全部 red にした後でも、敵対的レビューが P1 を 3 件出した

`adversarial-review-own-safeguards.md` の「変異は自分が想定した不変条件しか試さない」が
またそのまま当たった（実測 9 回目）。今回の 3 件はいずれも**私が変異として思いつかなかった形**:

- 同名フィールドのマスク（変異は「無害化を消す」形しか当てていなかった）
- 書き戻しの一文の不可視（`r.Items = kept` は string ではないので検査対象ですらない）
- YAML のトリガー取り違え（`pull_request:   # コメント` という**この repo の地の文体**）

**提案なし**（ルールは既にあり、そのとおりに動いて救われた）。

### 6. 「検出しない形」を先に書いたのに、実装が変わって嘘になりかけた

§8 に従って README と test header に「検出しない形」を先に書いたが、レビューが
「実装が実際に検出しない形と一致していない」と指摘した（ポインタ / map / 匿名構造体 /
書き戻し / svc 未対応 が抜けていた）。

- **原因**: 脅威モデルは着手前に書けるが、「検出しない形」は**実装してみないと確定しない**。
  先に書いた版は「意図」であって「実装の射程」ではなかった
- **切り出し先の提案**: `adversarial-review-own-safeguards.md` の §8 に
  「**『検出しない形』は実装後にもう一度実装と突き合わせる**（先に書いた版は意図であって射程ではない）」
  を 1 行足す。発動点は §8 と同じなので新規ルールは立てない
