# 249 retro: doctor の削除まわり 4 件 (231 / 232 / 244 / 246) のセッション振り返り

起票日: 2026-09-04
対象セッション: dotfiles-85。231 / 232 (削除エンジンの勘定) と 244 / 246 (中断の結末と案内) を実装

## 1. 変異検証を通したテストのうち 2 本が、実は何も守っていなかった

244 と 246 で書いた回帰テストは、最初に書いた形では**変異を当てても緑**だった。

- **246**: `ctx` を最初から閉じて `Delete` を呼んだので、`Delete` の DryRun ループの打ち切りが
  手前で効き、狙った `planDelete` の分岐に**到達していなかった**。実際の中断は「走査の最中に
  Ctrl-C」なので、guard の呼び出しを seam にして走査の途中で閉じる形へ直した
- **244**: 期待値を production と同じ定数 (`deleteAbortKeys`) から作る**自己言及**で、案内側を
  削ると期待値も一緒に縮んだ。挙動 (browseModel の入口から押して実際に中断できたか) を
  独立の出典にして書き直した

どちらも `mutation-verify-new-tests.md` が既に名前を付けている形 (「差が出ない状況しか作って
いないか」「期待値を production と同じ式・同じ定数から作っていないか」)。**ルールを読んでいて
なお踏んだ**ので、追記より「変異が緑だったら、まずテストを疑う」を実行できたことの方が効いた。

**切り出し先の提案**: 既存 [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md)
の「よくある『守っていないテスト』の形」に **「先に効く別の防御が影になって、狙った分岐に
到達していないか」** を 1 項足す (自己言及は既に在る)。発動点は同じなので新規ルールは立てない。

## 2. 「環境のせい」と結論するとき、変数を 2 つ動かしていた

`make -C src/glogx test` が「全テスト PASS の後に `testing: can't write testlog.txt: file too large`」
で落ちた。私は `TMPDIR` を新しくして緑になったのを見て「Go のビルドキャッシュが肥大した環境要因」と
ユーザーへ報告した。**誤り**。実際は `doctor_cache_write_test.go` が `RLIMIT_FSIZE` を
プロセス全体で 0 にする窓に `go test` 自身の testlog 書き込みが当たっていた
(別セッションが特定して修正)。

🚨 `TMPDIR` を変えると **go のビルドキャッシュも空になる**ので、変数が 2 つ動く。
「別の一時ディレクトリでは再現しなかった」は原因の否定になっていない。正しい切り分けは

1. **条件を変えずに同じ HEAD で 2 回**回す (1 回目赤・2 回目緑なら環境ではなく非決定性)
2. **緑だった時点と赤い時点を、同じコマンドで**比べる

**切り出し先の提案**: 既存 [`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
の「有無で結果が変わらない観測を証拠に数えない」節に、**「切り分けで動かした変数を数える
(一時ディレクトリの差し替えはキャッシュも消す)」** を 1 行足す。同節の「前後の比較は同じ
抽出方法で行う」と発動点が同じ。

## 3. commit の帰属を推測で述べて 4 回外した

未 push の claim commit の持ち主、245 の実装者などを、開始時刻や「新しいセッションだから」と
いった根拠で推測し、他セッションへ伝えて訂正させた。全セッションが同じ git user で、
`git pull --rebase` が commit の時刻を前後させるので、**author も時刻も帰属に使えない**。
これは [`commit-with-pathspec.md`](../_claude/rules/commit-with-pathspec.md) に
🚨 付きで明記されており、**読んでいてなお踏んだ**。

使えるのは「commit が触ったファイル」と「本人に聞くこと」だけ。本人に聞く手段 (`ListAgents` +
`SendMessage`) はこのセッションで実際に機能した (4 セッションと調整し、二重 claim を 1 件検出)。

**切り出し先の提案**: 新規ルールは立てない。`commit-with-pathspec.md` の当該注記に
**「推測した帰属を第三者へ伝えない (伝えると誤情報が伝播し、真の当事者を探すのをやめる)」**
を 1 行足す。今回は私の誤情報を受けた別セッションが、無関係なセッションへ確認に行っている。

## 4. claim の窓 — 1 日で 7 回の見落とし / 衝突が起きた

実測 (2026-09-04、6 セッションが同じ backlog を消化):

| 回 | 形 |
|---|---|
| 1-2 | 240 / 241 を私が二重着手しかけた (単発指示の claim 免除で next を経由していなかった) |
| 3 | 003 を私が取ろうとしたら push 済みの claim があった (私の fetch が古かった) |
| 4 | 138 / 220 が 2 セッションで二重 claim (片方が未 push) |
| 5 | 245 を私が調整している最中に別セッションが claim して完走 |
| 6-7 | 帰属の誤りに起因する確認の往復 (項目 3) |

構造は 1 つで、**「claim を push するまでの窓」と「fetch から着手までの窓」**。hook
(`next-claim-push.sh`) は Bash 経由の移動しか見えず、`git fetch` の鮮度は誰も強制していない。

**切り出し先の提案**: 既存 [`claim-issue-in-next-and-push.md`](../_claude/rules/claim-issue-in-next-and-push.md)
に **「着手直前にもう一度 `git fetch` する」** と **「`ListAgents` に他セッションが居るなら、
next だけでなく本人へ 1 回聞く」** を足す。next は「push されるまで見えない」ので、
生きているセッションへの照会が唯一の即時性のある手段。

🚨 ただしこれは**規律を足しても守られるとは限らない**形 (今日の 7 回はどれも規律が既に在った)。
issue 化して hook で強制できないか検討する価値がある (例: `issues/next/` へ移す Write/Edit を
PostToolUse で拾う / 着手前に `git log origin/master..HEAD` の未 push claim を注入する)。
