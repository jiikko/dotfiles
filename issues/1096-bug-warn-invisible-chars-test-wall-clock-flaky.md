# 1096 (bug): test_warn_invisible_chars_in_tool_input.sh の 150 万行のケースが make test の負荷の下で時間切れになる

起票日: 2026-11-19

## 概要

`tests/claude/test_warn_invisible_chars_in_tool_input.sh` は hook を壁時計 10 秒 (本番の配線と同じ上限) で走らせ、
時間切れを失敗に数えていた。2026-11-19 の並列の `make test` で「150 万行の末尾に全部の字」が jq 1.7.1 / 1.8.2 の両方で
rc=124 になった。単独では 2 回とも緑。

## 詳細 (実測 2026-11-19)

- hook の所要は単独で real 0.15〜0.16 秒 (user 0.14〜0.15)。jq 1.7.1 / 1.8.2 とも
- 10 秒を越えるには 60 倍以上の遅れが要る。CPU を回し続けるプロセス 28 本 (コア数の 2 倍。`runtimeout 120` で区切った) を
  走らせても、変える前のテストは 152 件全部緑で再現しなかった。**遅れの原因は未特定** (CPU の取り合いだけでは説明できない)
- 字ごとに行を全部見る形の変異 (`p` を求める前に `$s | split("\n") | map(select(contains($ch)))`) は CPU 時間 21〜26 秒

## 対応

- 所要の判定を壁時計から hook の CPU 時間 (`/usr/bin/time -p -o` の user + sys) に替え、大きな入力の 2 ケースで予算 3 秒と比べる。
  壁時計は止まったときの打ち切り (60 秒) だけに使う
- 壁時計が本番の上限 10 秒を越えた run は、落とさずに stderr へ 🚨 の行を出す。🚨 make test の並列の runner (`Makefile` の `run_tests_parallel`) は
  緑のテストの出力を捨てるので、この行が見えるのはテストを直接回したときと、同じ run で別の assert が落ちたときだけ

## 検出しない形 (受ける)

- CPU を使わずに 10〜60 秒待つ退行 (lock・遅い FS を待つ)。本番では 10 秒で殺されて知らせが消える。hook は stdin を jq で読むだけで
  待つ相手を持たないので受ける。テストを直接回せば上の 🚨 の行で見える
- E コアに回ると CPU 時間が伸びる (`taskpolicy -c background` で同じ jq の仕事が 0.29 → 0.82 秒、約 2.8 倍)。今の 0.15 秒に対し予算 3 秒で約 6.7 倍の余裕

## 再開の trigger

- このテストを直接回して 🚨 hook の壁時計が本番の上限を越えた の行が出たら (または make test でこのテストが落ちたら)、そのときの user / sys / real を見る。
  real だけが大きければ待たされている (CPU 以外の原因)。user が大きければ hook の CPU が伸びている
