# 579 (retro): glogx issues viewer のパスジャンプ (Tab) と issue 577

起票日: 2026-09-29

## 概要

2026-09-28〜29 のセッションの振り返り。glogx の issues viewer に「本文中のファイルパスを Tab のジャンプモードで選んで開く」を
足した (設計の敵対レビュー 1 回 + 実装の敵対レビュー 5 周、続けて ubiregi-server で光らないパスの対応と「.md は viewer 内で開く」への
変更 + 1 周)。最後に issue 577 (ownership テストの flaky) を直した。

## どこで踏んだか / 何が回りくどかったか

1. **symlink による repo 外への脱出の判定で、敵対レビューが 5 周続いた**。2〜4 周目の指摘は全部同じ形で、「symlink の鎖の
   どこを観測するか」の近似 (最後の成分だけ → 書かれた prefix → Readlink を Clean して辿る) が次々に迂回された。
   4 周目の後にやっと「成分ごとに解決して出会った symlink を全部数え、終点を `filepath.EvalSymlinks` と突き合わせる」形へ
   移し、そこで収束した。`adversarial-review-own-safeguards.md` の 0-B (既に答えを出している経路を正解役にする) と §8
   (迂回を直すたびに新しい迂回が出るなら、軸が構文にある印) は両方あったのに、2 周目の時点で当てていなかった
2. **効果の測定を 1 つの repo の実データで閉じた**。dotfiles の issue 579 ファイルで「ローカルを指す markdown リンク 969 個中
   966 個が解決」と測って spec に書いたが、ユーザーが使う別の repo (ubiregi-server) は repo root 起点でリンクを書く規約で、
   そちらでは主要なリンクが 1 本も光らなかった。規約の違う入力源が在ることは、ユーザーが複数の repo で viewer を使う時点で
   予想できた
3. **依頼の「readonly で開く」を nvim -R に直訳した**。ユーザーに「nvim が開くのは合理的か」と問われて初めて、.md は
   viewer 内で整形して読む方が手数が少ないと比べた。CLAUDE.md の「もっと良い方法があると思ったら一文で述べてから進める」の
   適用漏れ
4. **変異が緑になったものが延べ 5 本あり、うち 4 本は fixture が狙った経路に届いていなかった** (相対パスの `..` の段数が
   1 つ多く存在しない場所を指していた / 行が幅を超えて clip される経路を作れていなかった / 全角が clip の縁に来る入力を
   作れていなかった / 波括弧の展開の配線を見ていなかった)。残る 1 本は `-run` の絞り込みで狙ったテストを外していた。変異で見つかったので実害は無いが、書いた時点で「前提が成立したこと」を assert していれば変異の前に分かった
5. 実装の敵対レビューの走行中に、同じ worktree のテストを 2 ファイル書き換えた (`parallel-write-agents-need-worktree-isolation.md`
   の「read-only のレビュー中は書き換えない」違反。報告に食い違いは出なかった)
6. `bin/mutate-verify` を 1 変異ずつ呼ぶための使い捨ての並べ役を `tmp/` に 4 回書き直した (bash 3.2 の `source <(...)` が
   関数を読まない、等で 1 回失敗)。1 セッションで変異を約 50 本当てた
7. 577 は並列 16 本 × 3 回の負荷では旧版でも再現しなかった。bg の `rm` を遅らせる shim で窓を広げて初めて決定論で再現できた

## 次に効きそうな改善 (提案)

- **A. 「同じ判定の近似が 2 周続けて迂回されたら、3 周目の修正の前に 0-B へ戻る」を発動点として足す** (項目 1)。
  今の §7 の「同じ判定の別々の書き方の食い違いから指摘が続けて出たら 1 つの関数へ寄せる」は**書き方が複数ある**場合の話で、
  **近似を 1 つずつ差し替えていく**形を捕まえない。判定: 直した後の指摘が「前の周と同じ不変条件を、別の入力で破る」なら、
  近似を直すのをやめて、本物の経路を正解役にする (本物を呼ぶ / 自前で全件観測して本物と突き合わせる)
  - 切り出し先: `_claude/rules/adversarial-review-own-safeguards.md` §7 へ追記 (新規ルールにしない。発動点は §7 と同じ「指摘を直した後」)
- **B. 効果を実データで測るなら、利用者が使う入力源を列挙して、規約の違うものを最低 2 つ含める** (項目 2)。1 つの母集合の
  成功率を一般の成功率として書かない。測れなかった入力源は「未測定」と書く
  - 切り出し先: `_claude/rules/verify-execution-not-just-exit-code.md` の「観測できた経路と、主張する範囲を一致させる」へ追記
    (あちらは経路の一般化、こちらは入力の母集合の一般化で、同じ規範の入力版)
- **C. `bin/mutate-verify` に、1 つの一覧から複数の変異を順に当てて結果を表にする形を足す** (項目 6)。使い捨てで 2 回目を
  書いた時点で `new-tool-requires-entrypoint-docs.md` の対象
  - 切り出し先: 新規 issue (dotfiles の `bin/mutate-verify`)
