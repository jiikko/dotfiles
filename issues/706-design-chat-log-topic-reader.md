## 概要

他人同士の会話ログ (まず Slack のチャンネル) を後から読んで追いつくのが苦痛。時系列に並んだ発言を
**トピックごとに組み直して**読めるようにする道具の構想。ユーザーの比喩は**フーリエ変換**: 時間軸の信号を、
別の軸 (= 話題軸) に移すと構造が見える。

困りごとは「要約が欲しい」ではなく「**混ざった話題を自分でほどく作業**が苦痛」。なので主役は要約ではなく
**組み直した原文**で、LLM の文章は見出しと数行の要点に留める。

## 経緯

1. **最初の案は Slack クライアントの自作** (読み書きの両方): チャンネル一覧はそのまま、中身は LLM が整理して
   スレッド掲示板風に見せ、ユーザーの発言も LLM が言葉を選んで返信・スレッドへ投稿する。「コアは人間、瑣末な言葉の
   チョイスは AI」(アイアンマンの比喩)
2. **調べて分かったこと**:
   - Slack は 2025-05-29 に API 規約を改定した (詳細は「リスク」節。禁じたのは LLM の**学習**で、対象は組織の外へ提供するアプリ)。
     同日、Marketplace 外で配布する「unlisted」アプリの `conversations.history` / `conversations.replies` は
     1 分 1 回・1 回 15 件まで絞られた (社内向けの internal app と Marketplace のアプリは従来の Tier 3 のまま)。
     **他人に配る製品にするのは事実上難しく、自分用に留めるのが現実的**
   - AI が書いたと分かったメッセージは、書き手が誠実でない・信頼できないと受け取られやすい (感謝・謝罪など
     気持ちを伝える文で強い)。書く側は信頼と責任の論点が重い
   - Slack AI のチャンネル要約・Recap は要約を出すが、**表示の構造 (話題ごとの組み直し) は変えない**
3. **書く側を切り離し、読む側だけを残した**。書く側を作るなら「LLM が下書きを出し、人が差分を見て確定する。
   自動送信しない」が前提になる (別の構想として扱う。この issue の範囲外)
4. **フーリエ変換との対比を整理した** (下の節)。この課題には自然言語処理の研究テーマとして名前があると分かった:
   **conversation disentanglement** (会話のもつれほどき)
5. **MVP はまだ作らず、設計を練る段階に留める** (ユーザー判断)
6. **規約の原文を読み直した**: 「LLM での利用が制限された」と書いていたが、原文が禁じているのは LLM の学習だけだった
   (「リスク」節で訂正)
7. **MVP を作ることにした** (2026-11-09 ユーザー指示)。名前を slack-bbs に決め、チャンネルの購読と、
   「スレッドで続いている話題も見逃さない」狙いを足した (下の 2 節)

## 狙い: スレッドで続いている話題も見逃さない (2026-11-09 ユーザー追記)

この道具が便利な理由は 2 つある。

1. チャンネルに混ざった話題をほどく (「概要」節)
2. **スレッドの中で会話が続いている話題も、話題の一覧に出る**。Slack ではスレッドの返信はチャンネルの流れに出ない
   (「チャンネルにも投稿する」を付けた返信を除く) ので、親の発言が古いスレッドで議論が続いていても、チャンネルを
   眺めるだけでは気づけない。slack-bbs は期間内に動きのあったスレッドを話題として浮かせ、**チャンネルの話題を見逃さない**ようにする

- 表示: 期間より前に始まったスレッドの話題には「続いている」印を付け、期間内の発言 (新しい返信) と、文脈として出す期間前の発言を見分けられるようにする
- 🚨 **今の slack-cli の口では取れない**。`history -oldest` は親の ts で絞るので、親が期間より前で返信だけが新しいスレッドは返らない。
  `conversations.history` の応答は親ごとに `reply_count` / `latest_reply` を持つが、slack-cli の `Message`
  (`~/src/slack-cli/internal/slack/types.go`) はそれを捨てる (2026-11-09 にコードで確認)。取り方の案:
  - **案 A**: `slack search` (search.messages。allowlist にある) で `in:<channel> after:<日付>` を引き、返信の親を集めて `thread` で取り直す。
    slack-cli の変更は要らない。**未実測**: 検索語なしの `after:` だけで引けるか / 返信が結果に入るか / 親の ts が JSON に載るか
    (`Message.ThreadTs` か permalink の `thread_ts=`) / 検索の索引の遅れ
  - **案 B**: slack-cli の `Message` に `reply_count` / `latest_reply` を足し、history を期間より長く遡って `latest_reply` が期間内の親を拾う。
    呼ぶメソッドは変わらない (読み取りの範囲は同じ) が、slack-cli 側の変更と、どこまで遡るかの上限が要る
  - 実測は案 A から。slack-bbs の実装の最初の段で、出力のフィールド名と件数だけを jq で見て決める

## MVP (slack-bbs) (2026-11-09)

- **名前と置き場所**: slack-bbs。`src/slack-bbs/` の Go の module。slack-cli には混ぜない (「構成の案」節の理由)
- **購読**: `slack-bbs sub` で、チャンネルの一覧 (`slack channels`) から読むチャンネルを選ぶ画面 (tuikit の `listnav`)。
  保存するのは購読したチャンネルの ID と名前だけ (`~/.config/slack-bbs/`)。会話の本文は保存しない
- **読む**: 端末で `slack-bbs [-since 2d]` を打つと読む画面 (TUI) が開く (2026-11-09 ユーザー指示「MVP は TUI で」)。左に話題の一覧、
  右に中身。`r` で今のチャンネル、`R` で全部を読み直す (読み直しは `claude -p`。ユーザー判断 2026-11-09)。パイプの先・`-md` は Markdown。
  話題の統合はチャンネルの中だけ
- **処理**: 取得 (スレッドで続いている話題を含む。上の節) → まとめ直し → `claude -p` で分類 → 検査 → 表示
  (「設計」節のとおり)。`-dry-run` は LLM を呼ばず、外へ送る件数と文字数だけを出す。`-json` で中間表現を出す
- **2 段の実行** (2026-11-09 ユーザー決定): 端末の `claude` が GUI と別のアカウントになるので、`slack-bbs prepare` → GUI のセッションの
  サブエージェントが分類 → `slack-bbs show -key` の経路も持つ。手順は skill `slack-bbs`。本文がそのセッションの記録に残ることは承知の上
- **作らない**: なんJ風の表示層、増分更新、チャンネルをまたいだ話題の統合、量が多いときの分割 (map-reduce)

## 設計

### 芯: LLM には「分類」だけをさせ、本文は原文を出す

| 層 | 誰が作るか | 間違えたときの害 |
|---|---|---|
| どの発言がどのトピックか (分類) | LLM | 発言が別のトピックに入る。**原文はどこかに必ず出る**ので、読み落としにはならない |
| トピックの見出しと要点 (2〜4 行) | LLM。各要点に根拠の発言 ID を付ける | 要約の誤りが読者に伝わる。根拠 ID から原文へ飛べるので確かめられる |
| 本文 (原文の発言を時系列のまま) | **機械的に並べるだけ。LLM の生成文は混ぜない** | なし |

- 時間の情報は捨てない。トピックの中は時系列、トピック同士は「最後の発言が新しい順」に並べる
- **全ての発言がちょうど 1 つのトピックに入る**ことを道具の側で検査する。LLM が落とした ID は「未分類」トピックへ入れ、
  存在しない ID (捏造) は捨てる。これは機械で検査できる不変条件で、要約の正しさ (機械では測れない) とは分けて扱う
- Slack のスレッドは**既に 1 つの話題**なので分割しない。親と返信をひとまとまりで LLM に渡し、1 単位として分類させる
- 範囲は**読む側だけ**。投稿・リアクション・既読の更新はしない
- **自動では走らせない** (常駐・定期実行をしない)。追いつきたいときに人が打つ。費用と、外部へ送る量を人が見える形にする
- ~~**結果を保存しない**。表示して終わり。規約の永続化の禁止は他組織のデータが対象で、自分の組織のデータには直接は当たらないが、
  社内規程も含めて安全側に倒す。再実行のたびに LLM を呼び直す費用は受け入れる~~
  → **2026-11-10 ユーザー決定で改めた: 取得した発言 (raw) と分類 (summary) をそれぞれキャッシュする** (「起動のたびに読み込んでサマライズしているの?
  キャッシュしないの?」→ 案 A を選択)。置き場は `~/.cache/slack-bbs/` (0700 / 0600)。中身と使い回しの条件は `src/slack-bbs/README.md` の「送るもの・残すもの」

### トピックの形 (LLM に返させる JSON)

```json
{"topics": [
  {"title": "リリース日を来週へずらす件",
   "state": "decided",
   "labels": [{"kind": "must_read", "reason": "リリース日が変わり、自分の作業の締め切りに響く", "refs": ["1728540000.123456"]}],
   "points": [{"text": "QA が終わらないため 10/17 へ延期", "refs": ["1728540000.123456"]}],
   "members": ["1728540000.123456", "1728541111.000100"]}
]}
```

- `state` は `decided` (決まった) / `open` (議論中・未回答の質問がある) / `info` (共有のみ) の 3 つ。
  追いつく人が知りたいのは「何が決まり、何が自分待ちか」なので、要点の文章より先にこれを見せる
- `members` は発言 ID (Slack の `ts`)。スレッドは親の `ts` で代表させる

### ラベル: 必読 / 要対応 (2026-10-10 ユーザー要望)

`state` (話題が今どうなっているか) とは別の軸で、**読む人にとってどうか**を付ける。

| ラベル | 意味 | 付け方 |
|---|---|---|
| `action` 要対応 | 自分が返事・作業・判断をしないと進まない | **機械で決まる部分と LLM の判断を分ける**。自分へのメンション (`<@自分の user ID>`) と、自分の発言への返信は機械で拾う (確実)。「名指しはされていないが自分の担当の話」は LLM の判断 (外れうる) として区別して見せる |
| `must_read` 必読 | 対応は要らないが、知らないと困る (決定事項・方針の変更・障害) | LLM の判断 |

- 自分の user ID は `slack whoami -json` の `user_id` で取れる
- 🚨 **ラベルにも理由と根拠の発言 ID を必須にする** (`reason` / `refs`)。要点と同じで、確かめられないラベルは信じられない
- 🚨 **ラベルの付けすぎに注意**。LLM は「念のため重要」と付けがちで、全部が必読になると意味がない。
  付いた割合を実測し、多すぎるなら prompt で基準を絞る (例: 必読は 1 回の実行で数件まで)
- 並べ順は 要対応 → 必読 → その他 (その中は最後の発言が新しい順)

### 表示層を差し替えられるようにする (2026-10-10 ユーザー要望)

**「整理する層」と「どう見せるかの層」を分ける**。整理した結果 (話題・状態・ラベル・要点・原文) を 1 つの中間表現 (JSON) に
まとめ、見せ方はそれを読む表示層 (renderer) を選んで変える。整理を 1 回やれば、見せ方を変えるたびに LLM を呼び直さなくてよい。

見せ方の候補:

- **掲示板風** (下の「表示の例」): 話題ごとの見出し・ラベル・要点、原文は折り畳み
- **なんJ風** (2ch のスレッド風): 話題 = 1 スレ。スレタイ = 話題の見出し、レス = 原文の発言 (レス番号・名前欄・時刻)、
  返信は `>>12` のアンカーで表す。Slack のスレッドの返信や、要点の `refs` がそのままアンカーになる
- **TUI**: 話題の一覧と本文の 2 ペイン (glogx の部品を使う)

🚨 **表示層は原文を書き換えない**。並べ方・番号・アンカー・名前欄の付け方を変えるだけにする。
なんJ風の口調に LLM で書き換えるのは「本文は原文」の原則を破り、要約の誤りと同じ害 (言っていないことを言ったように見える) が出る。
やるとしても「加工済み」と明示する別モードにし、各レスから原文へ戻れるようにする

```text
【決定】リリース日を来週へずらす件【必読】
1 名前：tanaka 10/09(水) 10:02
QA まだ半分くらいです
2 名前：suzuki 10/09(水) 10:15
>>1 じゃあ 17 日にずらしましょう
```

### 表示の例

```markdown
# #dev — 10/08 09:00 〜 10/10 18:00 (発言 214 / トピック 9)

## 🟢 決定 📌 必読: リリース日を来週へずらす件 (12 件, 最終 10/10 17:40)
- QA が終わらないため 10/17 へ延期 [↗](permalink)
<details><summary>原文 12 件</summary>

- 10/09 10:02 tanaka: QA まだ半分くらいです
- ...
</details>

## 🟡 議論中: CI のキャッシュが効かない (5 件, 最終 10/10 15:12)
...
## ⚪ 未分類 (3 件)
```

### 構成の案

```
slack-cli (既存。読み取り専用)          新しく作る道具
  slack users   -json  ─┐
  slack history -json  ─┼─> 正規化 ─> LLM で分類 ─> 不変条件の検査 ─> 中間表現 (JSON) ─> 表示層 (選べる)
  slack thread  -json  ─┘   (発言の列)  (claude -p)   (全件ちょうど 1 回)   話題・ラベル・原文     掲示板 / なんJ風 / TUI …
```

- **取得は既存の [jiikko/slack-cli](https://github.com/jiikko/slack-cli) に任せる**。Chrome のセッションを流用するので、
  Slack アプリの作成・管理者の承認・アプリ向けの rate limit の段階 (Tier) の話を避けられる
- **新しい道具は slack-cli に入れず、別コマンドにする**。slack-cli は「読み取り専用で、取得したものを外へ出さない」という
  安全の約束をテストと変異検証で固めている。会話の本文を LLM へ送るのは**その約束と別の性質の操作**なので、同じバイナリに
  混ぜない。パイプでつなぐ形にしておけば、入力を差し替えて Slack 以外のログ (会議の書き起こし・他人の Claude セッションの
  ログ) にも使える

## フーリエ変換との対比

| | フーリエ変換 | この道具 |
|---|---|---|
| 軸を変えて構造を見る | 時間 → 周波数 | 時間 → 話題 |
| 元に戻せるか | 戻せる (逆変換) | 戻せる (原文を全部残し、ts で並べ直せば元のログ) |
| 成分 (基底) | 事前に決まっている (sin 波) | データを見て初めて決まる (ログごとに違う) |
| 1 点の寄与 | 各時刻の値が全周波数に少しずつ寄与する | 1 発言は 1 話題にだけ入る (分割) |
| 時間の情報 | 結果には残らない | 話題の中に時系列を残す (短時間フーリエ変換 = スペクトログラムに近い) |
| 情報が落ちるところ | 高周波を捨てるとき (圧縮) | 要約 (主成分だけ残すのに相当)。原文で補う |

考え方は似ているが、数学的には**混ざった信号の分離** (カクテルパーティー問題 = 何人もの声が混ざった録音から
一人ずつを取り出す) に近い。自然言語処理では **conversation disentanglement** と呼ばれる。

## 実装時のヒント

### slack-cli から取るとき

- 🚨 **フラグは引数より前に置く**。slack-cli は引数の後ろのフラグを使い方の誤り (rc=2) として止める
  (`cmd/slack/main.go` の `checkNoTrailingFlags`)
- `slack history -json -oldest <ts> -n <件数> <channel>` で期間を切る (`-oldest` / `-latest` は ts で受ける。既定 50 件)
- 親の発言 (`thread_ts == ts`) ごとに `slack thread -json -n <件数> <channel> <ts>` (既定 200 件)。
  🚨 `-n` に達すると**警告なしで切る** (`internal/slack/api.go` の `collectMessages` は `-n` に達すると `out[:limit]` を返すだけ)。
  返ってきた件数が `-n` と同じなら、欠けている可能性を表示に書く
- `slack users -json -bots -deleted` で user ID を表示名に引く (history の JSON の `user` は ID)。
  既定はボットと無効化済みのユーザーを除くので、フラグを付けないと退職者やボットの発言が ID のまま残る
- 🚨 **同じ ts の重複を除く**。スレッドの返信をチャンネルにも送ったもの (「チャンネルにも投稿する」) は history と
  thread の両方に同じ ts で出る。slack-cli の `Message` は `subtype` を持たないので見分けられない。
  ts で重複を除き、スレッド側に寄せる (「全件ちょうど 1 回」の検査の前提)
- `Message` は `text` だけを持ち、`files` / `attachments` / `blocks` / `reply_count` は捨てる
  (`internal/slack/types.go`)。ファイルだけの発言は本文が空になるので「(添付のみ)」と出す
- チャンネルは `#name` でなく ID で渡す。`#name` だとチャンネル一覧を `~/.config/slack-cli/cache/` に保存する
  (チャンネル名とトピックだけで本文は入らないが、「保存しない」の範囲をはっきりさせるため)
- permalink は `search` の結果にしか入らない (`Message.Perma` を埋めるのは search だけ)。history / thread の発言は
  `https://<workspace>.slack.com/archives/<channel>/p<ts から . を除いた値>` で組み立てる
- 429 は slack-cli が `Retry-After` で待つ (1 回 60 秒・1 リクエスト 3 回・合計 180 秒まで)。超えたら取れた分を出して rc=1

### LLM を呼ぶとき (`claude -p` を使う場合)

- `claude -p --output-format json --json-schema <上の形>` で形を固定する。API キーを別に持たなくてよい
- `--no-session-persistence`: 付けないと、送った会話の本文がセッションとして `~/.claude` に残る (「保存しない」に反する)
- `--bare` (hooks を飛ばす): Stop hook が最後の返答を差し替えることがある (`.claude/rules/worktree-per-session.md` の
  headless 実行の注意。issue 573)。JSON を最終応答から読むので、hooks を通さない
- 書き込む道具を外す (`--disallowedTools "Edit,Write,NotebookEdit,Bash"`。prompt の後ろに置く)
- 安いモデルで分類、要点だけ高いモデル、と分けると費用を抑えられる

### 量が多いとき

- 1 回の呼び出しに載らない量なら、期間で切って分類したあと「トピックの統合」をもう 1 回呼ぶ (map-reduce)
- 最初は件数の上限 (例: 500 件) を超えたら止めて、期間を絞るよう案内するだけでよい

### 作ったときに確かめること

- 全発言がちょうど 1 つのトピック (または未分類) に出る (道具の検査で保証できる)
- 要点の `refs` が全て入力に存在する発言 ID である
- 同じ入力を 2 回通したとき、トピックの数と大きな分け方がどれだけ揺れるか (実測して書く)
- 実際のチャンネルで「時系列で読むより速く追いつけたか」はユーザーが判断する (機械では測れない。役に立つかが目的そのもの)

## 🚨 実用性への懸念 (2026-10-10 ユーザー提起。未解消)

ユーザーの言葉: 「フローのスレッドの話題が変わった時に、スレッドを作り直すか悩む。更新されないスレッドならいいけど、
更新中のスレッドならどうするか。なんか実用性がない気がしてきた」

### 更新中のスレッドで話題が変わったら、組み直した話題を作り直すか

- **この板挟みが本当に起きるのは「組み直した結果を保存し、更新し続ける」形** (最初のクライアント案 = 常に最新の掲示板)。
  前回の分け方を保つ (安定) か、正しく分け直す (正確) かを毎回選ぶことになり、避けられない。研究でも、発言が届くそばから
  分類する online disentanglement として別の難しい問題に分けられている ([Pointer Networks の論文](https://arxiv.org/pdf/2010.11080))
- **今の設計 (追いつきたいときに 1 回打ち、見て捨てる) では起きない**。毎回ゼロから組み直すので「作り直すか」を決める場面が無く、
  更新中のスレッドも打った時点の姿で分類される。🚨 引き換えに、打つたびに分け方が変わりうる (「同じ入力を 2 回通して
  どれだけ揺れるか」を実測する理由)。前回の分け方を引き継ぐ増分更新に踏み込むと、この懸念がそのまま戻ってくる
- **1 回の実行の中でも、スレッドの途中で話題が変わる問題は残る**。案は 2 つ:
  - (a) スレッドは分けずに丸ごと 1 つの話題に入れ、変わった位置だけ注記する (「後半は CI の話題へ移った → トピック B」)。
    いちばん簡単で、スレッドの流れも壊さない。**追いつく用途ならこれで足りる見込み**
  - (b) スレッドを途中で区切り、後半を別の話題に入れる。正確だが、元のスレッドの流れが見えにくくなる

### それ以外に、効かないかもしれない点

- **チャンネルの使われ方次第**: チームがスレッドをきちんと使っていれば、Slack 上で既に話題ごとに分かれている。
  その場合この道具で得られるものは小さい
- **分類が毎回変わると覚えられない**: 打つたびに分け方が変わると、頭の中に地図を作れない
- **結局原文を読むなら意味がない**: 分類を疑って原文を読み直すことになれば、時間は短くならない。
  「決定 / 議論中」の判定を信じられるかどうかが鍵

### 作らずに確かめる方法 (MVP の前にやる)

1. **スレッド外の発言の割合を数える**: 追いつきたいチャンネルで、スレッドに入っていない発言がどれだけあるか。
   `slack history -json -n 500 <channel>` を jq に通して、`thread_ts` が空の発言の割合を見る (`Message.ThreadTs` は `omitempty` でないので、スレッド外の発言は空文字で出る)。低ければこの道具の出番は少ない
2. **手作業で 1 回試す**: 2 日分のログを Claude に貼り、「設計」節の形で組み直させる。時系列で読むより速く追いつけるかを
   ユーザーが判断する (10 分ほど)

**どちらかで「時系列で読むのと大差ない」となったら、そこでやめる**。その場合は理由を書いて pending か done へ移す
(検討の跡はこの issue に残る)

## 🚨 リスク (MVP を作る前にユーザーが判断する)

  「Data Usage by Third Parties」節は「**自分の組織の外の人にアプリを提供する場合**」に、(A) API で取ったデータで

  Slack の通常の利用規約と会社のポリシーの問題になる (slack-cli の README も「組織のポリシーと Slack の利用規約に
  反しない範囲で」と書いている)
- **外部への送信**: 会話の本文 (プライベートチャンネルを含みうる) が LLM の提供元へ送られる。会社の情報の扱いの
  規程で、社外の LLM に送ってよいかを確かめる
  - **2026-11-09 ユーザー判断**: GitHub のコードや Notion (MCP) を既に Claude に読ませているのと同じ扱いとし、実データで動かしてよい。
    他と違うのは、書き手が社外へ出ると想定していない文 (プライベートチャンネル・DM・個人の情報) が混ざりやすい点で、
    規程がそれを分けて扱うようになったら見直す
- **要約の誤り**: 「提案しただけ」を「決定」と書く、発言者を取り違える、の 2 つは必ず起きる。要点に根拠 ID を必須にし、
