# 221 feat: doctor にプロセス側の診断を足す

起票日: 2026-09-03

      [issues/148](../done/148-feat-glogx-doctor-disk-diagnosis.md) の 5 章 (「本 issue では扱わない」と結論した分)
重要度: **P3** (常設の追跡機構が要るので、単発の実装では終わらない)

## 148 の 5 章が出した結論と、その前提となる実測

「置き去りのプロセス」を診断しようとしたが、**外部に正本が無い**ため
「自分で記録を作る」以外に方法が無いと結論した。引き継ぐべき実測:

- **629 件の誤検出**。「親が死んでいるプロセス」を素朴に拾うと、launchd に里子化された
  正常なプロセスまで全部候補になる
- **`pane_pid` の限界**。tmux のペインから起動したプロセスを追う手がかりが `pane_pid` しか
  無いが、これは「今そのペインで動いている最前面のプロセス」であって、
  そこから起こされた孫は辿れない

## 扱うなら要る設計

**glogx が起動したプロセスを追跡する常設の仕組み**が前提になる。「今の状態を見て推測する」
形では上の 629 件を切り分けられない。

- glogx / doctor が起こしたプロセスを記録する (pid + 起動時刻 + pgid + 何のために起こしたか)
- 記録と実在プロセスを突き合わせる (pid の再利用があるので起動時刻を鍵に含める)
- 記録に無いプロセスは**候補にしない** (誤検出の 629 件はここで落ちる)

⚠️ 記録を持つ = 状態を持つので、[`adversarial-review-own-safeguards.md`](../../_claude/rules/adversarial-review-own-safeguards.md)
の §0-A が発動する。「そもそも置き去りを発生させない構造」(= `Setpgid` + cancel で
グループごと殺す。issue 206 で実機確認済み) が既に在るので、**追跡機構が要るのは
「それでも残った場合」だけ**。着手前にその頻度を測ること。

## 受け入れ条件

- [ ] 「置き去りが実際に起きるか」を先に測る (206 の実測では 5 試行すべて 0.05 秒で消えた)
- [ ] 起きるなら追跡機構を設計し、記録に無いプロセスを候補にしないことを固定する
- [ ] 起きないなら**この issue を却下で閉じる** (理由つき。次の audit が再提案しないため)

## 保留 (pending へ。2026-09-03。ユーザー判断)

**作らない方に倒す。** 受け入れ条件 1 つ目「置き去りが実際に起きるかを先に測る」は
**`issues/done/206` で既に測り終えており、起きていない**:

- `runner.Exec` は `Setpgid: true` で子を別プロセスグループに置いている
  (実機で `pid == pgid` = 54324/54324 等、孫の `curl` も同じ pgid を継承)
- 子が生きている状態で閉じてから消えるまで **5 試行すべて 0.05 秒** (60 秒 timeout を待たない)
- ⚠️ 改良前のハーネスで **1 度だけ 10.07 秒**かかった試行がある (1/8)

つまり「そもそも置き去りを発生させない構造」(`Setpgid` + cancel でグループごと殺す) が既に
効いており、追跡機構が要るのは「それでも残った場合」だけ。守る対象が 0.05 秒で消えるものに
対して、**pid + 起動時刻 + pgid + 用途を持つ常設の状態**を新設するのは釣り合わない
(状態を持つ機構はそれ自体が新しい失敗の入口。`adversarial-review-own-safeguards.md` §0-A)。
629 件の誤検出は「素朴な実装が使えない」ことの裏付けであって、追跡機構が要る根拠ではない。

### 再開の trigger
