# 596 (design): restartable の再設計の候補 (daemon とクライアントに分ける / 宣言的な複数プロセス / 既存の道具に寄せる)

起票日: 2026-10-01

## 再開の条件 (trigger)

次のどれかが起きたら、この issue を pending から出して比較を詰める:

- 端末やペインを閉じてもアプリを生かしたくなった (今は runner が前面のプロセスなので、端末を閉じると SIGHUP で強制終了する)
- アプリ以外の付属のプロセス (テスト用のサーバ・コンテナ等) も一緒に起動・停止したくなった
- UI の不具合が監督 (子の起動・停止) を巻き込んだ
- 2 つ目の repo で restartable を使い始め、その repo の要件が今の形に収まらない

## 背景

[586](../done/586-feat-restartable-foreground-restart-runner.md) / [588](../done/588-feat-restartable-transition-dialog-and-ready-cmd.md) で作った restartable は、
1 本のプロセスに 4 つの役割が同居している: (1) ライフサイクルの管理 (ビルド → 起動 → 起動の確認 → 停止の段・止め方の段) (2) 生死と準備の判定 (pid / --ready-cmd)
(3) 外から操作する口 (control socket) (4) 端末の UI (最下行・板・キー・ログ)。ユーザーの見立て (2026-10-01): 「要はwrapperって感じ。別の切り口としての設計もいけるような気がする」。
その時点の判断は「一旦これでよい」(作り直す明確な理由がまだ無い)。比較を流さずに残すため、この issue に置く。

## 候補

| 案 | 形 | 得るもの | 失うもの・コスト |
|---|---|---|---|
| A. daemon とクライアントに分ける | 見張る側 (1〜3) を常駐させ、端末の UI は attach / detach するクライアントにする。Claude の dev-restart もクライアントの 1 つ | 端末を閉じてもアプリが生き残る / 複数の画面から同じ状態を見られる / UI の不具合が監督を巻き込まない (586 の敵対レビューの指摘の多くは UI と監督の同居から来ていた: キーのあふれで終了処理が止まる・出力の包みで端末の判定が外れる 等) | daemon の起動・発見・後始末という新しい失敗の入口。どの daemon が動いているかの管理 |
| B. 宣言的な設定で複数プロセスを扱う | Procfile / YAML にアプリ・付属のサーバ・ビルドを並べ、依存・readiness・再起動の方針を書く | 付属のプロセスも同じ仕組みで扱える。今の restartable はその 1 プロセスの特殊な場合になる | 設定の書式という新しい仕様。1 プロセスで足りる場面には重い |
| C. ファイルの変更で自動で再起動する | watchexec / air / nodemon の系統 | 保存で反映 | Xcode のビルドは重く、保存のたびに走るのは向かない。Claude の操作と衝突しやすい |
| D. 既存の道具に寄せる | process-compose (TUI・readiness probe・停止のコマンド・REST API) / overmind (tmux) / mprocs (複数プロセスの TUI) | 自作の保守が要らない | inline のログ表示 (スクロールバックに残す)・転送中の終了確認を待つ止め方・devLoop の照合をどこまで載せられるか。**各道具の機能は未確認** (2026-10-01 時点の Claude の知識からの比較で、実測していない) |

当時の見立て: 手を入れるなら A が一番効く (UI と監督の同居から出る穴の種類が構造ごと消える)。D は、作り直す前に「既存の道具でどこまで足りるか」を実測する価値がある。

## 名前

restartable は「再起動」という 1 つの機能だけを指していて、実態 (前面で見張る supervisor) より狭い。作り直すなら役割に合わせた名前 (`devloop` / `fgsup` / `runloop` 等) を検討する。
