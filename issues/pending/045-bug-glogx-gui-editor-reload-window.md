# glogx: `$EDITOR` が GUI エディタだと編集完了前に復帰し、鮮度が fsnotify 依存になる

起票日: 2026-08-13

**着手条件（trigger）**: `$VISUAL` / `$EDITOR` に GUI エディタ（`code` / `subl` / `mate` を
`-w` / `--wait` なしで指定）を設定して使う人が出たとき。または fsnotify が無音な FS
（NFS 等）上の repo で issue を編集して「反映されない」報告が出たとき。
**それまでは着手しない**（発火条件を実験で作れていないため。下記「未確認の理由」参照）。

## 何が起きるか

issues viewer の `e` は `tea.ExecProcess` で TUI を中断してエディタを起動し、**子プロセスの終了を
待って** `editorClosedMsg` を受け、そこで一覧と本文を取り直す（`reloadAfterEdit`）。

`-w` を持たない GUI エディタは**起動しただけで即座に終了する**ので、この経路は「編集が終わる前に」
復帰・取り直しをしてしまう。取り直しの結果は編集前の内容なので、鮮度の保証は
`editorClosedMsg`（同期）から **fsnotify の監視（非同期）** へ移る。

nvim 直書きだった時代はこの窓が存在しなかった（必ず nvim の終了を待った）。
`$VISUAL`/`$EDITOR` に追従した commit `98b5b52` 以降に生じた性質。

## 何が問題か

- `src/glogx/README.md` の「開いている間は別プロセス（Claude Code / 別ターミナルの `$EDITOR` /
  `git pull`）の編集を自動で反映する」は、これまで**保険**だったのが**主経路**になった
  （load-bearing になった）
- `issues_watch.go` は自ら「fsnotify を作れない環境では保険のポーリングが唯一の経路」
  「NFS では無音になりうる」と記録している。その環境 + GUI エディタの組み合わせでは、
  編集結果が最大でポーリング周期ぶん古いまま表示される
- 「保存したのに viewer が古い」ように見えるが、原因が 2 段（GUI エディタが待たない ×
  fsnotify が届かない）なので切り分けが難しい

## 未確認の理由（発火条件を示せていない）

- GUI エディタを `$EDITOR` にした実機での再現をやっていない（手元の `EDITOR` は nvim）
- fsnotify が無音になる FS を用意して観測していない
- 通常経路（ローカル FS + fsnotify 稼働）では監視が窓を埋めるため、**破綻を再現できていない**

推測に基づく防御コード（`-w` を自動で足す等）は入れない。まず観測できる形にしてから判断する。

## 対応案（着手時に再評価すること）

- **A: 何もしない + 文書化**。「GUI エディタを使うなら `-w` / `--wait` を付ける」を README に
  1 行書く。`git` も `GIT_EDITOR` に同じ要求をするので、慣習として一貫している。最小
- **B: 復帰後に短い猶予を置いて再取得**。`editorClosedMsg` の後、1 度だけ遅延して取り直す。
  ⚠️ 「いつまで待つか」の根拠が無いので、待ち時間がマジックナンバーになる
- **C: 待たないエディタを検出して警告**。子プロセスが極端に早く終わったらトーストで
  「`-w` を付けると確実に反映されます」と案内する。⚠️ 「極端に早い」の閾値が同じくマジックナンバーで、
  正当に速いケース（既に開いているウィンドウへ渡すだけ）を誤検知する

A から入るのが妥当。B / C は「実際に困った」観測が出てから。
