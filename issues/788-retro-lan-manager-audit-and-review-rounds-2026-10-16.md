# 788 (retro): lan-manager の監査 3 波と、直しへの敵対レビューを何周も回したセッション

起票日: 2026-10-16

issue 747 (mac-lan-manager) の監査 22 タイプ (3 波) と、その直しへの opus の敵対レビュー (第 2 波の直しに 5 周、第 3 波の直しに 6 周)、
issue 785 (案内の詰め方を tuikit/hintfit に寄せる) をやった。

## どこで踏んだか / 何が回りくどかったか

1. **直しの例外の経路が、次の周の退行になった (4 周続いた)**
   - 「足りない画面」を足すと、見えない確認の板に y が届いた
   - それを塞ぐと、層が開いたまま横断キーが glogx に渡って update が走った
   - それを塞ぐと、L が効かなくなった
   - 設定の画面は足りない画面の判定から漏れていた
   
   どれも「状態 (層の有無 × 足りない画面か) × 読み手 (HandleInput / Binds / Paste / Close / glogx)」の表を先に作れば、1 周で全部のセルが見えた。
2. **同じ判断を 2 つの粒度で持っていた**。有線かどうかを、サービスごと (Service.Wired) と I/F ごと (Classes / Kind) の 2 系統で決めていた。
   1 つの I/F に複数のサービスが載ると食い違い、それを敵対レビューが 3 周かけて別々の症状として掘り出した。
3. **変異が緑だった 4 回は、どれもテストの入力がその分岐まで届いていなかった**。
   - VALIDUSER: 不正な例が別の文字でも弾かれる
   - WIREDIF: 読めない I/F は先に Kind が「分からない」を返す
   - UNREADWIN: 読めないサービスが先に並ぶ
   - SKIP: 長い項目と短い項目の優先度が別
   
   「この assert は、ほかの守りが先に止めない入力で、この分岐だけを通るか」を書く前に問えば済んだ。
4. **同じ CI の失敗を並行セッションと二重に直した**。pro-con の paths に mac-lan-manager が無い件で、相手が先に push していた。
   rebase で同じ 2 行が重複し、自分の commit を外した。
5. **fitHintItems の「移していないのは意図的」の注記を、前提を確かめて覆した**。注記は「利用者が glogx の中だけ」を前提にしていた。
   今は別 module の lanmgr が同じ判断を別に持ち、同じ穴を踏み直していた。注記の前提を問わずに従えば、785 は「やらない」で閉じていた。

## 次に効きそうな改善 (提案)

- (1) **例外の経路 (足りない画面・読めない状態・無効のもの) を足すときは、その状態を読む経路の表を先に作る**。
  `survey-receiver-guards-before-passing-new-values.md` に「状態 × 読み手の表」は既にあるが、発動点は「どちらが正かの規則を決める・変える」になっている。
  「新しい状態 (例外の経路) を足す」も同じ表の発動点にする
  → 切り出し先: `_claude/rules/survey-receiver-guards-before-passing-new-values.md` に追記
- (2) **同じ判断を別の粒度・別の型で持っていないかを、判定を足すときに grep する**。上の「自分が宣言した不変条件」の節の「崩せる経路を全部挙げる」で拾える形
  → 却下: 既存の規範で足りる (適用が遅れただけ)
- (3) **新しいテストの入力が、守りたい分岐だけを通るか (他の守りが先に止めないか) を書く前に確かめる**
  → 切り出し先: `_claude/rules-checklists/mutation-verify-new-tests.md` の「到達しているか」に 1 行追記
- (4) **他人の commit が起こした CI の赤を直す前に、fetch して相手が直していないかを見る**
  → 却下: rebase で重複が見え、害は無かった (1 回の手戻り)。既存の「並行セッションと調整」の規範で足りる
- (5) **「意図的にこうしている」の注記に従う前に、その注記が置いている前提が今も成り立つかを確かめる**。
  `verify-design-intent-before-refactor.md` は「意図的なら取り下げる」側に寄っている
  → 切り出し先: `_claude/rules/verify-design-intent-before-refactor.md` の手順 1 に「注記の前提 (利用者の範囲など) が今も成り立つかを確かめる」を追記
