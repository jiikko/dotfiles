# retro: glogx の CLI health 警告 (codex-drive)

起票日: 2026-08-24

対象セッション: 「glogx 起動時に claude / codex の未インストール・ログアウトをエラートーストで
表示して」を codex-drive で実装 (commit 603d6b8 / 5ccb252)。

## 1. 外部コマンドの出力を `2>&1` で測り、stdout/stderr の別を取り違えた

最初の実測で `codex login status 2>&1 | head` のようにマージして測ったため、
「codex は stdout に `Logged in using ChatGPT` を出す」と誤認し、それを設計ファイルの
「実測事実」として書いた。codex (実装者) はその記述どおり stdout を読む実装を書いた。

分離して測り直したら **codex は stdout が 0 バイトで、判定材料は stderr** だった。
気づかず進んでいたら codex 側の判定は**常に unknown に落ちて一度も発火しない**機能になっていた。
同じ測り直しで、claude の exit code も初回の記述 (「未ログインでも exit 0」) が誤りだった
(実際は exit 1。最初は exit を測っていなかった)。

**切り出し先の提案**: `_claude/rules/` に新規ルール。
「外部コマンドの振る舞いを実測して設計の前提にするときは、**stdout / stderr / exit code を
最初から分離して**測る (`> out 2> err; echo $?`)。`2>&1` や `| head` で測った結果を
『実測事実』として設計に書かない」。判定ロジックの土台になる観測なので、ここが狂うと
実装・テスト・レビューが全部同じ誤読の上に建つ ([`instrument-before-second-fix.md`] の
「前提を今この環境で実測し直す」の観測手順版)。

## 2. fake が受け側の実挙動を模しておらず、致命的な欠陥がテスト green で通った

codex の初回実装は `err != nil` で早期 unknown に落としていた (= claude のログアウトを
一切検出できない)。設計ファイルには「exit code では判定しない。stdout の JSON を読む」と
明記してあったのに読み違えた。**そしてテストは green だった** — fake が claude 側で
`err == nil` しか返さず、実測どおりの exit 1 を模していなかったため。

私は「テストが通ったから OK」とせず diff を精読して気づいたが、気づけたのは
**先に実測表を作っていたから** (実装と実測を突き合わせられた)。

**切り出し先の提案**: 既存ルールの再確認で足りる (新規ルールは作らない)。
[`survey-receiver-guards-before-passing-new-values.md`] の「fake に受け側の reject 挙動を
模させる」と [`mutation-verify-new-tests.md`] が既にこの形を言っている。ただし
**「外部コマンドの exit code」も『受け側の挙動』に含まれる**という例が両ルールに無いので、
どちらかに 2〜3 行の実例追記を提案する。

## 3. 同型の「配線が検証されていない」穴を 1 セッションで 2 回作った

- M1: `browseModel.Init` の `tea.Batch` に検査を足したが、それを守るテストが無かった
  (レビューが指摘 → 追加 → 変異で red を確認)
- M2: `toastDrawBudget` の純関数テストは書いたが、**それを呼び出し側が使っているか**の
  テストが無かった。配線を元の式に戻す変異を当てたら**全テスト green のまま通った**

M1 で指摘されて直した直後に、別ファイルで同じ穴を作っている。純関数のテストは書きやすいので
そこで満足してしまい、「その値が実際に効いているか」が抜ける。

**切り出し先の提案**: `_claude/rules/` に新規ルール。
「計算ヘルパー (予算・閾値・設定値・判定関数) を新設したら、**純関数テストとは別に、
呼び出し側が実際にそれを使っていることを pin するテスト**を書く。確認は『ヘルパー呼び出しを
旧実装に戻す変異を当てて red になるか』で行う」。
[`adversarial-review-own-safeguards.md`] 節 4 (新設した検査が CI で実際に走るか) の親戚だが、
あちらは「検査が実行されるか」でこちらは「値が使われるか」なので別ルールが要る。

## 4. 実 CLI を 1 回走らせる一時テストが、seam テストより強い証拠になった

seam を全部差し替えたテストは「実測表どおりに書いたコードが実測表どおりに動く」ことしか
示さない。実測表そのものが誤っていた今回、それでは何も守れなかった。

commit 前に `CODEX_HOME` / `CLAUDE_CONFIG_DIR` / `PATH` を一時ディレクトリに向けて
**実 CLI で 5 条件を通す一時テスト**を書いたら、全部 PASS して初めて「本当に動く」と言えた
(テストには残さず削除。認証情報は一切触っていない)。

**切り出し先の提案**: `_claude/rules/` に新規ルール、または上記 1 のルールに統合。
「外部 CLI の出力に依存する判定を実装したら、**実 CLI を 1 回だけ走らせる一時テスト**で
裏を取る (環境変数の隔離で異常系も作れる。commit はしない)」。
[`no-ios-simulator-verification.md`] のような『実行を避ける』方針とは別で、
**プロセス 1 本・数百 ms で終わる検証は避ける理由がない**。

## 5. codex-drive の merger digest が設計案の比較に向いていない

`[D1]` の設計 4 案を `codex-fanout` で回したところ、digest が「指摘リスト / 重大度 / 全数勘定」
というレビュー向けの形になり、**案ごとの trade-off 比較表が出なかった**。skill の D1 節は
「軸ごとの trade-off 比較表・各案への批評の要点・推奨案ドラフト」を求めているので、
既定の `templates/merger.md` をそのまま使うと噛み合わない。結局 4 案の原文 (330 行) を
私が全部読んで統合した。

**切り出し先の提案**: `~/.claude/skills/codex-drive/templates/` に
**設計案集約用の merger prompt を追加**し、D1 節から `-m` で指定するよう書く。
(トークン経済の「digest 経由で読む」が D1 では機能していない)

## 6. 却下した指摘と、その理由 (`./tmp` の設計ファイルは gitignore なのでここに残す)

| 指摘 (出典: codex 敵対レビュー) | 却下理由 |
|---|---|
| 検査の ctx を `browseModel.cancel` (cancelAll) と結び、終了時に子プロセスを止めるべき | 既存の同種検査 (`checkCLIVersionCmd` / `usage.Fetch`) が全て `context.Background()` + timeout の契約で揃っている。ここだけ変えると規律が割れる。**検査群ごと揃える改修が来たら再評価** (理由は `checkCLIHealthCmd` の doc にも残した) |
| テストが `sh` を起動して `*exec.ExitError` を作っているのは環境依存 | `os.ProcessState` は外から合成できず代替手段が実質ない。`sh` は検査対象の CLI ではないので「実 CLI を起動しない」方針には抵触しない (理由は `exitOneError` の doc に残した) |
| 警告を 1 枚にまとめてスタック消費を抑えるべき | ユーザーが「CLI ごとに 1 枚」を選択済み (2026-08-24)。トーストは 1 行なので、まとめると修復コマンドが文言に入らない |
| `toastStackMax` を 4 に拡張すべき | 1 CLI につき最大 1 枚 = health は最大 2 枚。保持数ではなく**描画予算**が効いていたので、そちらを直した (5ccb252) |

## 7. codex exec が「これから書く」で exit 0 のまま終了した (空振り)

受け入れテスト (E2E) の追加を投げたとき、codex は既存テストの読解と方針を述べたところで
**何も書かずに exit 0** で終了した (`git status` に差分なし、`-o` の出力ファイルも作られず)。
成功終了なので、通知だけ見て次へ進むと「テストを足したつもり」で先に進んでしまう。

結局この 1 本は Claude が直接書いた (既存パターンの組み合わせで確定的だったため、
再投げより速い)。変異 3 本の red 確認も Claude 側で実施。

**切り出し先の提案**: `~/.claude/skills/codex-drive/SKILL.md` に 1〜2 行追記。
「codex の exit 0 を成功と見なさない。**`git status` の差分 (または `-o` の出力ファイルの存在)**
を毎回確認する。差分ゼロの exit 0 は空振りとして扱い、再投げか Claude 直筆に切り替える」。
既存の「主張は偽と仮定して裏を取る」の**実行有無**版で、skill には exit code の扱い
(`codex-fanout` の 0/1/2) しか書かれていない。

## 8. 変異検証のバックアップ復元を自分で壊した

変異を当てる前に `cp <file> $SCRATCH/<name>.bak` でバックアップし、後で戻す方式を取ったが、
同じセッション内で `tui.go` のバックアップを 3 世代 (`tui.go` / `tui.go.bak` / `tui.go.m2bak` /
`tui.e2e.bak`) 作ってしまい、**復元で古い世代を書き戻して配線が消えた状態を作った**
(全テストが FAIL になって気づいた)。commit 済みだったので `git checkout -- <file>` で無傷に戻せた。

**切り出し先の提案**: `_claude/rules/mutation-verify-new-tests.md` に 2〜3 行追記。
「変異の復元は **`git checkout -- <path>`** で行う (対象が commit 済みであることを先に確認する)。
`cp` のバックアップは世代を取り違えるので使わない。**未 commit の変更がある状態で変異を当てるなら、
変異は 1 ファイル 1 回に限り、当てる前後で `git diff --stat` を読む**」。
