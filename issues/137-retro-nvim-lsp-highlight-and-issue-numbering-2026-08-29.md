## 1. 変異を 2 回当て直した — 「red でも緑でもない」を最初に red と読みかけた

`tests/issues/test_issue_numbers_unique.sh` の変異検証で、最初に当てた 2 本が

- `sed` でガードの行を削除 → 構文が壊れて **rc=2**
- `uniq -d` を無意味な式に置換 → 壊れ方が不正で **rc=1 のまま**

になった。このとき判定を「rc が変異前と違うか」で書いていたため、**rc=2 を「✓ 素通り =
防御が効いている」と表示してしまった**。実際には「変異が壊れていて何も測れていない」であり、
`mutation-verify-new-tests.md` が言う第 3 の結果 (`<変異がビルド不能>`) だった。

気づけたのは出力を読んだからで、判定ロジックは間違ったままだった。直した形は
「`bash -n` で構文が通ることを先に確認 → rc=0 かつ変異前が rc=1 のときだけ ✓」。

**切り出し先の提案**: `_claude/rules/mutation-verify-new-tests.md` の手順 1.5 は既に
「変異がビルドできたことを確認する」と書いてあり、ルール自体は正しい。足りなかったのは
**判定式を「rc が変わったか」で書かない**という一段細かい話。ルール本文に 1 行足すか、
却下か。個人的には足す価値があると思う (「rc が変わった」は 3 値を 2 値に丸める典型で、
同じルールが別所で戒めている形そのもの)。

## 2. 「2 つとも漏れている」と一括で言ってしまった (実際は片方が分岐依存)

`ee5e2b7` の報告で「同じ Visual 漏れが `LspSignatureActiveParameter` と `SnippetTabstop` にも
及ぶ」と書いたが、issue 134 を書くために実測したら **`LspSignatureActiveParameter` は 256色
(retrobox) 分岐だけ**で、truecolor (gruvbox) 側は `Search` (reverse) を独自に持っていて無傷だった。

原因は、`Visual` に link しているグループを **1 回の `nvim_get_hl` 走査 (retrobox 側だけ) で
列挙して、そのまま両分岐の話として書いた**こと。同じセッションの中で「colorscheme 分岐で
`LspReferenceTarget` の link 先が違う」ことを既に踏んでいたのに、隣の項目に適用しなかった。

**切り出し先の提案**: ルールにするほど一般的ではない。`docs/theme-colors.md` に
「link の解決は colorscheme ごとに違うので、両分岐で採ること」を 1 行足すのが妥当か。
あるいは却下 (テスト側が両分岐を回す形になったので、次に同じ判断をする人は分岐差に気づく)。

## 3. 番号衝突が同日に 2 件出た — 「一声かける」では構造的に閉じない

> 初稿では「一声かけなかったこと」を根に置いていたが、並行セッション (dotfiles-87) の
> 指摘を受けて時刻を実測したところ**その説明では 127 が説明できない**と分かったので、
> 節ごと書き直した。相手の指摘した 133 の検出時間 (~3 時間) も実測とは違った (1:17)。

`acc5673` で**事後**の検出 (テスト) は入れたが、**事前**の導線は `issues/README.md` に
「番号を取る前に一声かける」と書いただけで、これは人間 (と Claude) の規律に戻っている。
衝突の解消コストは「参照の張り替え」か「改番」のどちらかを必ず払う形で、事後検出は
**払うべき額を教えてくれるだけ**で額そのものは減らさない。

### 実測 (git の commit 時刻)

| 番号 | 2 件の生成 | 生成の間隔 | 衝突成立 → 解消 |
|---|---|---|---|
| 133 | `35172a9` 21:44 / `d470d15` 21:47 | **3 分** | 21:47 → 23:04 = **1:17** |
| 127 | `c14a632` 07:33 / `7a2254d` 09:18 | **1 時間 45 分** | 09:18 → 23:09 = **13:51** |

**読み取れること 2 つ:**

**(a) 「同時に走査したから同じ max+1 を得た」では 127 を説明できない。** 133 は 3 分差なので
その説明が効くが、127 は 1 時間 45 分空いている。共有ツリーなら 2 本目の走査は 1 本目の
ファイルを見えるはずで、それでも衝突した。候補は「番号を決めた時刻とファイルを書いた時刻が
離れていた (セッション前半で採番し、実装後に書いた)」「別 worktree で走査した」など。
**どれが起きたかはこちらからは観測できない**ので断定しない。ただしどの候補でも、
**「ファイルを書く直前の一声」は効かない** (番号は既にもっと前に決まっている)。

**(b) 検出までの時間が 10.7 倍違う。** 133 は `issues/` 直下に並ぶので目に入ったが、127 は
片方が `issues/done/` にいて**視界から外れていた**。この差は「声かけの有無」では説明できず、
**「検出器が無い」+「ディレクトリを跨ぐと隠れる」**が効いている。

→ `acc5673` の検査を**ディレクトリ列挙ではなく `find -maxdepth 2` で掘る**形にしたのは、
まさにこの「14 時間隠れた形」を狙っている。変異検証で `-maxdepth 1` にすると 127 の形
(直下と `done/` の跨ぎ) だけが rc=0 へ素通りしたのは、その設計判断が単独で効いている証拠。

**切り出し先の提案**: 新規 issue。ただし**事前検出の設計は (a) の観測不足を埋めてから**。
「ファイルを書く瞬間に番号を検査する hook」は、番号がもっと前に決まっているなら遅すぎる。
まず「Claude が採番する導線は実際どこか」(セッションのどの時点で番号を決めているか) を
1 セッション観測してから設計する。案として `_claude/hooks/deny-bare-tmux-kill.sh` と同型の
PreToolUse hook はありうるが、**Write は `paths` フロントマターを発火させない**ことが
2026-08-27 に実測されている (CLAUDE.md に記載) ので、hook 側でパスパターンを見る必要がある。

## 4. `make test` を全体で回せなかった (並行セッションの中途状態)

並行セッションが `Makefile` / `_zshrc` / `zshlib/` / `.github/` / tests 4 本を編集中だったため、
全体 `make test` は「自分の変更で説明できない失敗」を生む状態だった。`make test-changed` で
範囲を絞って回し、そのことを報告した。

これは運用としては正しく回ったが、**判断の根拠が「git status を見て気づいた」という属人的な
もの**だった。セッション開始時は clean で、途中から他セッションの変更が現れた
(CLAUDE.md の「並行作業者がいるときの worktree 退避」が想定している状況そのもの)。
今回は worktree へ移らず、pathspec commit + 変異は使い捨て worktree、で凌いだ。

**切り出し先の提案**: 却下。CLAUDE.md の既存ルールで足りており、実際そのとおりに動けた。
強いて言えば「共有ツリーで並行作業者を検出したら、全体テストの結果は自分の変更の証拠に
ならない」は `verify-execution-not-just-exit-code.md` の親戚だが、新ルールを足すほどではない。
