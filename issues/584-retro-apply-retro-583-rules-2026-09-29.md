## どこで踏んだか / 何が回りくどかったか

1. **追記のつもりの python で、rationale の 2 ファイルを 425 行・343 行消した** (commit 前に気づいて戻した)。
   `open(p,'w').write(open(p).read() + add)` と 1 式で書いたため、書き込み用の `open(p,'w')` が先に評価されてファイルを
   空にし、その後の `open(p).read()` が空を読んだ。同じセッションの retro 579 の適用では「読んでから書く」2 文に分けていて
   無事だった (同じ作業を 2 回目に書くとき、1 行に縮めて壊した)
2. 気づけたのは、`tests/claude` を回す前に打った `git diff --stat` に `425 +----` と出たから。**追記しかしていないはずの
   変更に削除行があった**のが唯一の手がかりで、`tests/claude` は消えた状態でも緑だった (rationale の中身は検査されない)
3. `git -C $W …` のように行き先を変数で書くと、PostToolUse の git state の hook は `$W` を展開できず「判定不能」になった
   (retro 583 の項目 5 で「`git -C` なら拾う」と書いた直後に、変数で書いて拾わせ損ねた)

## 次に効きそうな改善 (提案)

- **A. 追記・置換だけのつもりの変更は、commit の前に差分の削除行を数え、想定と合うことを確かめる** (項目 1・2)。
  文書は検査が中身を見ないことが多く、消えても緑のまま通る。`git diff --stat` / `--numstat` の削除数が想定 (追記なら 0) と
  違えば止まる。今の規範は「commit 後に `git show --stat` で想定したファイルが入っているか」までで、**行数の向き**を見ていない
  - 切り出し先: `_claude/rules/commit-with-pathspec.md` の「commit 後に `git show --stat HEAD` を読み」の項へ追記
    (発動点は同じ「commit の前後で stat を読む」。新規ルールにしない)

却下 / 局所:

- 項目 1 の書き方そのもの (`open(p,'w')` と読み込みを 1 式に並べない): 局所の書き癖。A の「削除行を数える」が効けば、
  どの書き方で壊しても同じ場所で止まるので、書き方の規範は足さない
