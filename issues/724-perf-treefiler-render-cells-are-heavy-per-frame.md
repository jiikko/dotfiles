# 724 (perf): treefiler の 1 フレームの描画が画面のセル数に比例して重い (セルが大きく、色を毎回 10 進で組む)

起票日: 2026-10-12

## 概要

毎フレームの `View` は、画面の全セルを `canvas.reset` で消してから描き、`canvas.lines` で全セルを走査して SGR を組む (`src/treefiler/filer/render.go`)。
`cell` は `string` + `rgb` 2 つ (`[3]float64` × 2) + bool 4 つで約 72 バイトあり、200x50 の画面で reset が毎フレーム約 720KB を書く。
`lines` はセルごとに float 6 個を比べ、色が変わるたびに float を 10 進に変えて SGR を組む。712 の仮想化で木の大きさには依存しなくなったので、
残る重さは画面の大きさに比例するこの部分。

## 実測 (2026-10-12、Apple M3 Max・go1.26.0)

止まった画面の `View` 1 回 (別 module のベンチ。作り捨て):

| 画面 | 木 | ns/op | allocs/op |
|---|---|---|---|
| 80x24 | 1 フォルダ・20 件 | 49µs | 101 |
| 200x50 | 同 | 149µs | 141 |
| 300x80 | 同 | 260µs | 171 |
| 200x50 | 300 フォルダ (約 6,300 項目) | 190µs | 192 |

- 動いている間 (`j` 1 回 + 40 フレームの `Advance` + `View`): 200x50 で 4.5ms、300x80 で 8.8ms (1 フレーム約 110〜220µs)。60fps の 1 フレームの枠 (16ms) の 1〜2%
- pprof (View の中): `canvas.lines` 約 38% (`appendRGB` 約 11%・`strconv.AppendInt` 約 9%)、`canvas.reset` 約 19%、`drawLines` / `drawNames` 等 約 25%
- 既存のベンチ `perf_bench_test.go` の `BenchmarkViewHugeFolder` (n=5,000 / 50,000) は 184 / 187µs で、件数に依存しない (712 の効果)

## 対応方針 (案)

1. `cell` の色を詰めた整数 (8bit × 3 の `uint32` 等) で持ち、`cell` を小さくする。reset と走査の書く量・比べる量が減る
   - 🚨 セルに入った色を読み戻して混ぜる箇所がある (`canvas.dim` の `mix(p.fg, cBg, t)`・波紋の `p.fg = mix(p.fg, cRipple, …)`)。保存のときに 8bit へ丸めると、
     これらで丸めが 2 回になって色が変わる。混ぜる経路を全部挙げ、丸めを最後の 1 回に保つ形 (例: 混ぜる前の色をセルの外で持つ) を先に決める。テストもセルの色を
     float のまま比べている (`background_test.go` / `tileview_test.go` / `filer_test.go`)
   - 別に、`lines` が 72 バイトのセルを値でコピーしている (`p := c.cells[...]`)。ポインタで読むだけで減る分があるので、量子化とは分けて測る
   - 見積もり (見積もり): セルの大きさだけを真似た模擬 (1 万セル、72B → 32B) で reset 13.6 → 6.1µs・走査 18.5 → 8.0µs。実コードの View の約 15〜20% (25〜30µs) が減る見込み。
     実コードへの適用は未実測
   - 🚨 色を整数にすると丸めの時点が変わる。仮想化の等価性のテスト (`virt_test.go`) は新しいコードどうし (仮想化あり / なし) を比べるので、丸め方が変わっても落ちない。
     今の View を正解役にした突き合わせを別に置く。ただし文字列のままでは比べられない (今は float が違えば丸めた結果が同じでも SGR を出し直すので、量子化すると
     同じ色の区間がまとまってバイト列が短くなる)。デコードした (文字, 丸めた色, 属性) の格子で比べる
2. SGR の数値 (0..255) を表引きにする (`strconv.AppendInt` を毎回呼ばない)
3. 変わらなかった行の出力を使い回す (効きは大きいが、熱の色が `m.now()` で変わるので、時刻の刻みを鍵に含めないと等価にならない。1・2 の後に要るかを実測で決める)

## 小さいもの (記録。単独では直さない)

- `drawLines` が線のセルごとに `heat(m.heatAge(owner))` (`math.Log`) を計算している。持ち主ごとに 1 回で足りる。View の中で drawLines 約 10%、そのうち heat 約 3% (数 µs / フレーム)。
  線の格子 `m.lines` (`lineGrid` = `map[[2]int]*lineCell`。セルごとに `*lineCell` を確保) を毎フレーム作り直すのが約 13µs / フレーム (View の 6%)
- `takeBackground` が `Advance` のたびに配置された全フォルダへ `walker.request` (mutex + map) を打つ。動き終わった後の `Advance` は 20 フォルダ 4.7µs・300 フォルダ 52µs
  (ほぼ線形。同じループで `open` の slice を作り `m.watch.setDirs` も呼ぶが、その分は分けて測っていない)。explode の上限が 400 フォルダなので実害は小さい。
  開いたフォルダの集合が変わったときだけ頼む形にできる

## 優先度

効きは 1 フレーム 100µs 台の 15〜20% で、体感の差は小さいはず (見積もり)。重い端末 (大きい画面・遅いマシン) で描画が詰まるという報告が出たら着手する。
検索の issue 723 (1 打鍵 24ms) の方が先
