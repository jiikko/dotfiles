# 255 human: Finder 複数選択のクリップボード入力を実運用で確認する

起票日: 2026-09-04
期限: 2026-09-11
種別: human
関連: [094](094-human-verify-av1ify-clipboard-input.md)（前回のクリップボード入力の確認。項目 9 は本 issue で置き換わった）/ [095](095-retro-av1ify-clipboard-input-2026-08-22.md)

## 背景（2026-09-04 の報告と、その場で分かったこと）

`av1c` を引数なしで実行したところ、1 行 4197 文字（単一引用符付きのパスが空白区切りで 33 件）が
「✗ 見つかりません → 除外」になり、0 件でエラーになった。

実測で分かったこと:

1. **Finder の Cmd+C はペーストボードにプレーンテキストを載せない**。複数の `public.file-url` を
   載せた状態（Finder のコピーと同じ形）で `pbpaste` は空を返す。従来実装は `pbpaste` しか
   見ていなかったので、**Finder のコピーは必ず「クリップボードが空です」で落ちていた**
2. AppleScript の `the clipboard as «class furl»` は先頭 1 件しか返さない。複数取るには
   NSPasteboard の `readObjectsForClasses` が要る（JXA + ObjC bridge で 0.1 秒）
3. 報告された入力（単一引用符 + 空白区切り）を**実パスで再構成して現行コードに通すと、
   従来の「💡 空白区切りで複数のパスが並んだ行があります」の案内は出た**。実運用では出て
   いないので、**実際のクリップボードのバイト列が再構成と違う**（下の「未解決」）

## 入れた変更

- ペーストボードにファイル参照（file URL）があれば最優先で読む。無ければ従来どおり
  `pbpaste` のテキストへフォールバックする
- 1 行に空白区切りで複数パスが並んでいる行は、**案内で終わらせず分割してそのまま対象にする**
  （一覧に `[分割]` 付きで出す。判定は従来と同じ「パス区切りを含む語が 2 件以上実在する」）
- 読み取り経路を表示に出す（`クリップボードのファイル選択から読み取りました` /
  `クリップボードのテキストから読み取りました`）

## 確認してほしいこと

1. **Finder で複数選択 → Cmd+C → 引数なし `av1c`**: `クリップボードのファイル選択から
   読み取りました (N 件)` と出て、選択したファイルが全件 `✓` で並ぶこと。N が選択数と一致すること
2. **前回落ちた操作をもう一度**（今回報告してくれたコピー方法で）。読めるようになっていること。
   読めない場合は下の「未解決」の診断コマンドを流して出力を貼ってほしい
3. **`y` で実際に変換されること**。`n` / Enter で何も起きないこと
4. **`av1c` の警告**: 空白区切りとして解釈した行があるときに
   `↳ N行を空白区切りとして解釈しました。[分割] の一覧が意図どおりか確認してください` が出て、
   その下に `⚠️ 変換に成功したファイルは元ファイルをゴミ箱へ移します` が出ること
5. **誤爆が無いこと**: 空白入りのファイル名 1 個を貼ったときに `[分割]` されないこと
   （分割されるのは「パス区切りを含む語が 2 件以上実在する」ときだけ）

## 2026-09-04 の追試（1 回目の修正では直らなかった）

ファイル URL 経路を入れた後も同じ入力で落ちた。表示は `クリップボードのテキストから
読み取りました` だったので、**コピー元は file URL を載せていない**（パスを文字列で
書き出すツール）と確定した。

原因は分割の判定に zsh の字句解析 `(z)` を使っていたこと。`(z)` は**引用符の対応が
1 箇所でも崩れると行全体の解釈がずれ**、語には分かれても大半が解決できなくなる
（実測: 3 パスの列に余分な `'` を 1 個入れると分割が成立しなくなる）。ユーザーが送って
くれた 2 パスのサンプルは現行コードで分割できたので、4197 文字の列のどこかに
`(z)` を崩す文字が混ざっていたと考えられる。

そこで **シェルの字句解析に依存しない切り方**（絶対パスの開始位置 = 空白 + 引用符 0/1 個 + `/`
を境界にする）を後段に足し、`(z)` と両方採点して**多く拾えた方**を採るようにした。
実ディレクトリの 33 パスで測った結果:

| 入力の形 | 結果 |
|---|---|
| 半角スペース / 全角空白 / NBSP / タブ 区切り | 33 件 / 除外 0 |
| 引用符なし（空白入りファイル名） | 33 件 / 除外 0 |
| 二重引用符 / バックスラッシュ escape | 33 件 / 除外 0 |
| 末尾の閉じ引用符が欠けた | 33 件 / 除外 0 |
| 先頭の開き引用符が欠けた | 33 件 / 除外 0 |
| 途中に余分なアポストロフィ | 32 件 / 除外 1（壊れた語だけ ✗ に出る） |

## それでも読めなかったときに見るもの（バイト列は未取得のまま）

クリップボードは既に上書きされていて、失敗した入力そのものは取れなかった。次に同じ形で
落ちたら、**中身を出さずに構造だけ**見るこれを流してほしい:

```zsh
zsh -c 'source ~/dotfiles/zshlib/_av1ify.zsh
clip="$(pbpaste)"; line="${clip%%$'"'"'\n'"'"'*}"
print -r -- "bytes=${#clip} lines=$(print -r -- "$clip" | wc -l) line1=${#line}"
words=(${(z)line}); print -r -- "(z)語数=${#words[@]}"
n=0; for w in "${words[@]}"; do u="${(Q)w}"; [[ -e "$u" ]] && (( n++ )); done
print -r -- "実在=$n"
print -r -- "制御文字: $(print -rn -- "$line" | LC_ALL=C grep -c "[^[:print:]]")  NBSP: $(print -rn -- "$line" | grep -c $'"'"'\u00a0'"'"')  全角空白: $(print -rn -- "$line" | grep -c $'"'"'\u3000'"'"')"'
```

残っている仮説（上の表に無い壊れ方）:

- 区切りが半角スペースではなく NBSP / CR などで、`(z)` が 1 語に畳んだ
- ファイル名に対応の取れない `'` があり、`(z)` が 1 トークンに畳んだ
- 語のどれかが Unicode 正規化違いで `[[ -e ]]` を通らなかった（ただし当該 SMB ボリュームは
  NFC/NFD どちらでも `-e` が通ることを実測済み。この線は薄い）

**ファイル URL 経路が入ったので、Finder からのコピーであればこの謎に関係なく読める見込み**。
それでも読めなければ、コピー元が file URL を載せていない（パスを文字列で書き出す
サードパーティのツール）ということなので、上の診断でテキストの形を確定させる。
