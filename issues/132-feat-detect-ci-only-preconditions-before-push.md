# 132 feat: 「手元にはあるが CI に無い前提」を push 前に手元で出す

起票日: 2026-08-28 / 種別: feat / 優先度: **P3** (2026-08-28 に前提が変わって縮小した。下記)

> ⚠️ **前提の変更 (2026-08-28)**: Linux をサポート対象外にし、CI を macOS runner へ寄せることが
> 決まった ([133](133-chore-drop-linux-support-and-move-ci-to-macos.md))。これにより下表の
> **#1 / #2 (方言) は根本解決**され、**#4 (`go` の不在) も CI が macOS になれば消える**
> (macOS runner には Go が入っている)。本 issue に残るのは **#3 (`tmp/` = 新品チェックアウトとの差)
> だけ**で、これは OS と無関係。よって **Phase 1 のみが生き残り、Phase 2 は候補ごと却下**する。

元の優先度: **P2** (CI が最終的には捕まえるので P1 ではない。
削るのは往復コストと、赤が実装のバグに見えて調査が逸れるコスト)

## 事実 (2026-08-28 の 1 セッションで CI 赤が 4 件。全部「手元だけ緑」)

| # | 依存していた前提 | CI での壊れ方 | 現状 |
|---|---|---|---|
| 1 | `stat -f %m` が BSD 書式 | 年齢判定が常に「判定不能」→ 取り残しの回収が全滅 | **前提ごと消えた** (133 で CI が macOS に。検査も撤去) |
| 2 | `date -r <epoch>` が BSD 書式 | `touch -t ''` でテストごと死ぬ | **塞いだ** (同上) |
| 3 | repo 内に `tmp/` が存在する | `mkdtemp failed ... No such file or directory` | 個別対応済。**仕組みは未対応 (本 issue の残り)** |
| 4 | `go` が PATH にある | Makefile が `go not found; skipping` で exit 0 → assert 6 件が空振り | 個別対応済 (テスト側に go スタブ)。**133 で前提ごと消える** |

1・2 は**書き方**の問題なので静的検査で落とせた。3・4 は**存在**の問題で、書き方からは判定できない。

3 は「repo の `.gitignore` に `tmp/` が無く (ignore は `~/.gitignore_global` 由来)、追跡もされない
ので新品チェックアウトに存在しない」形。4 は**より危険**で、依存が無いと recipe が黙って skip
するため、assert が落ちるとは限らず**そのまま空振りの緑になりうる**。今回はたまたま集約を
見る assert だったので赤として出た。

## なぜ「CI が捕まえるからいい」で済ませないか

- 1 往復あたり push → 待ち (2〜8 分) → ログ確認 → 修正。今回は 4 回払った
- 赤の見た目が**実装のバグと区別できない**。3 は「mktemp が失敗」、4 は「集約されていない」と
  出るので、原因を環境ではなくコードに求めて調査が逸れる (実際に逸れた)
- 4 の系統は**赤にならずに空振りする**ことがあり、その場合は CI も捕まえない

## 対応案

### Phase 1: `make test-fresh` — 使い捨て worktree (= 新品チェックアウト) で回す

`git worktree add --detach <tmp> HEAD` は「追跡されているものだけがある状態」を正確に作る。
そこで `test-discovered` + `test-bats` を回して、終わったら worktree を消す。

- **捕まえるもの**: 未追跡のファイル / ディレクトリへの依存 (#3 の系統)。`tmp/` に限らず、
  手元にだけある生成物・キャッシュ・設定への依存が全部対象になる
- **形は opt-in に揃える** (かつて `make test-gnu` が同じ形だった。133 で撤去済み): 所要時間を倍にしない、push 前に回す、
  依存が無ければ skip せず**失敗する**。実装は `scripts/with_fresh_worktree.sh` + Makefile target
- **性質上の限界**: HEAD で回るので**未コミットの変更は検査されない**。これは欠陥ではなく
  「新品チェックアウト」の定義そのもの。push 前チェックとしては正しい粒度
- 実測済み: 今回の #3 は、この手順 (worktree で再現 → 修正 → 差し戻して赤を確認) でそのまま
  切り分けられた。**手順としては既に使っており、道具にしていないだけ**

### Phase 2: 却下 (2026-08-28)

`go` の系統 (#4) を捕まえるための案だったが、**133 で CI が macOS になれば前提ごと消える**
(macOS runner には Go が preinstall されている)。検討した 2 候補を、再提案されたときのために
理由つきで残す:

- **候補 A: CI 相当の PATH を許可リストで再現** — `CI_COMMANDS_*` (Makefile。2026-08-28 に
  `CI_PACKAGES_*` から改名した) を許可リストに
  使う案。難所は「apt パッケージ名 ≠ コマンド名」「ubuntu-slim の既定コマンド集合を手元で
  再現できない」で、**近似にしかならず、近似の粒度を人が保守し続ける**ことになる
- **候補 B: CI 自体をコンテナ化し、同じイメージを手元でも回す** — A の難所は消える
  (イメージ自体が baseline になり、近似ではなく同一物)。ただし **CI の検出力は上がらない**
  (CI は既に Linux で、買えるのは手元の再現性だけ)。加えて `tmp/` は bind mount では捕まらず、
  heavy/rest の 2 ジョブと `make test-ci-group-deps` の扱いを作り替える必要があった。
  **133 の「そもそも Linux を見ない」方が上位の解**なので採らない

## 却下した案 (次に同じ提案が出たとき用)

- **手元専用の道具として Docker で CI parity を作る**: docker 依存が増え、1 回の実行が重い。
  他のゲートが「軽い opt-in」で揃っているのに、ここだけ運用が変わる。
  ⚠️ CI 自体をコンテナ化する案は別物 (上の Phase 2 候補 B) で、こちらは 133 の決定により
  「そもそも Linux を見ない」方が上位なので不要になった
- **テストごとに `# requires: go` を宣言させる**: 宣言と実態の乖離を検出できないと意味がなく、
  検出するには結局 Phase 2 と同じ仕組みが要る。宣言だけ増やすと二重管理になる
- **CI に `go` を入れる**: 4 件のうち 1 件にしか効かず CI 時間が伸びる。しかも #4 は
  「go が無くても集約は検証できる」形に直せた (テスト側で go のスタブを置く) ので、そもそも不要
