# 1038 (retro): tmp/ 直下を止める hook (774) と issue-sync・観測待ちの消化 — 2026-11-06

起票日: 2026-11-06

## 概要

次の順で進めたセッションの振り返り。

1. start-issues-ops の refresh
2. issue-sync で 74 件を検証 (完了 0 件)
3. 774 / 816 の待っていた観測を測る (816 は done、774 は open に戻す)
4. 774 の B として `_claude/hooks/deny-tmp-root-write.sh` を実装し、敵対的レビュー (opus) を 4 周回す

## どこで踏んだか

1. **敵対的レビューが 4 周かかった**
   - 1 周目の指摘のうち、見逃しを直すために判定を広げた形が 2 つある: 先頭の `cd <repo> &&` と、`$PWD` / `$(pwd)` の展開。
   - 広げた判定が 2〜4 周目の指摘の大半を生んだ: 先頭以外の cd の誤検知、行継続や `{ cd` の数え漏れ、cd 先の展開の順序。
   - `rules-checklists/adversarial-review-own-safeguards.md` の §8 には、「止める範囲は確実に判定できる最小の形から始める」「迂回を直すたびに新しい迂回が出るなら軸が構文にある」が既に書いてある。これを 1 周目の採否のときに当てていなかった。
2. **背景の `make test` が同じ worktree で走っている間に、レビューの指摘を直す編集をした**
   - その run は止めて結果を捨て、最後の編集の後に回し直した。
   - `verify-execution-not-just-exit-code.md` の「検証がバックグラウンドで走っている間は同じ対象を編集しない」に反している。
3. **変異で、テストのケースが「機構の有無で答えが変わらない」形だったことを 3 回見つけた**
   - symlink の名前 `tmplink` が `tmp` の字面を含んでいた。
   - cd を 2 つ含むケースは、先頭の cd を採っても採らなくても答えが allow になる形だった。
   - 変数を含むパスのケースは、dir が無いのでどのみち allow だった。
4. **背景のタスクの最後の `grep -c` が 0 件で rc=1 を返し、`make test` が rc=0 なのにタスクが「failed」と表示された**

## 提案

- 却下 (1): §8 に既にある。踏んだ原因は規範が無いことではなく、指摘の採否を決めるときに §8 を読み直さなかったこと。新しい規範は足さない。
- 却下 (2): `verify-execution-not-just-exit-code.md` の「検証・計測がバックグラウンドで走っている間は、止めるか終了を見届けるまで同じ対象を編集・計測しない」がそのまま当たる。
- 却下 (3): `rules-checklists/mutation-verify-new-tests.md` の「fixture と前提」の「fixture を『検査対象が壊れない形』に選んでいないか」が当たる (入力の名前・並び・有無で機構を通らない形)。今回も変異で見つけて直した。
- 却下 (4): `verify-execution-not-just-exit-code.md` の「ラッパーの rc を本体の rc と読まない」の範囲 (最後のコマンドが `echo` でなく `grep -c` だっただけで、仕組みは同じ)。今回も、自分で仕込んだ `make_rc=` の行を読んで区別した。

残課題は無い (全項目を却下で決着)。
