# retro: 指紋の二重計算 (319) と「✗ が rc に出ない」(327) — 2026-09-08

対象セッション: issue 319 / 327 の対応（`2dba4e59` / `fa7c3bdf`）

## 何をやったか

- 319: `go_autobuild_exec` の指紋計算を同期分岐へ閉じ込め、F/I の呼び出し回数を pin
- 327: `test_av1ify_prefetch.sh` を fail カウンタ方式へ / 母集合を確定する
  `scripts/check_assert_reaches_exit.sh` を新設 / `tests/CLAUDE.md` に規約

## 気づき

### 1. 自分の新テストが vacuous だったことに、変異 2 本目で初めて気づいた

319 で「`--async` 経路の指紋計算は 1 回」を pin したが、最初の版は
**バイナリを作らずに `freeze` した**ため `[[ ! -x $bin ]]` の初回ビルド分岐に落ちており、
async を一度も通っていなかった（`freeze` の `touch -t` は不在のファイルを**非実行**で作る）。
変異 ① だけなら red が出るので気づけなかった。**変異 ②（別の場所を壊す形）を当てて
「async が green のまま」を見たとき**に発覚した。

- 切り出し先案: **既存ルールへの追記**
  [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md) の
  「前提が『早期 return で素通りしていないか』を assert しているか」に、
  **「変異を 1 本しか当てないと、素通りしているケースは red の陰に隠れる」**の一行を足す
  （既存項は「fixture を作った直後に Fatal で固定する」までで、
  「変異 1 本では検出できない」という**発見の仕方**が書かれていない）

### 2. 「ビルドできる変異」が挙動中立とは限らない（zsh の `local` の罠）

319 の 3 本目の変異候補「`local fp` を外側にも残したまま `else` 側でも宣言する」は、
zsh が**同一スコープの 2 度目の `local <name>` で変数の内容を stdout へ表示する**ため、
指紋が起動出力に混ざって既存テストが 6 件落ちた。`zsh -n` は通る。

- 切り出し先案: **既存ルールへの追記**
  [`mutation-verify-new-tests.md`](../_claude/rules/mutation-verify-new-tests.md) の手順 1.6
  （変異の diff を目視する）に、**「構文が通っても、変異が出力・副作用を足していないか見る。
  red が出ても、それが変異の副作用由来なら検知力を何も証明していない」**を足す
- 却下でもよい: 1.6 は既に「別の変異でも red は出る」と言っており、zsh 固有の実例は
  rationale 側へ回すだけで足りるかもしれない

### 3. 自作の検査の第 1 版が「たった今直したファイル」を誤判定した

327 の道具は最初「ファイル自身の報告文（`printf '✗ …'`）を正規化してトップレベルへ注入する」
方式だった。これは**末尾の集計行 `printf '✗ 失敗 %d 件'` を assert の形と読んで**しまい、
是正済みの `test_av1ify_prefetch.sh` を「出ない」と判定した。
「直したばかりの実物」を canary にしていたので即座に分かったが、
**先に母集合の sweep を回していたら誤った一覧を issue に残していた**。

- 切り出し先案: **既存ルールへの追記**
  [`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md)
  §4（その機構が CI で実際に走るか、同じ commit で確認する）に、
  **「新設した検査は、その検査が守るはずの修正を*直した直後の実物*に当てて、
  修正前 = 不合格 / 修正後 = 合格 の両方を見る」**を足す。
  §4 は「守っている修正を revert して CI が赤くなるか」を既に言っているが、
  **「合格側も見る」（偽陽性を出さないこと）が書かれていない**

### 4. 一時ファイル名を `$$` だけで作ると、誤判定が「エラーの顔」をせずに出る

並列 worker のプローブ名を `$$` だけで作っていた。timeout で殺した worker が残骸を置き、
pid が再利用されると**別のファイルのプローブを掴む**。エラーにはならず、
**もっともらしい「出ない」/「不明」**が出力の表に混ざる（表からは見分けられない）。
指摘を受けて `パスの cksum + $$ + $RANDOM` に直し、sweep をやり直した。

- 切り出し先案: **既存ルールへの追記**
  [`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md)
  §1 の一時ファイル注記（EXIT trap は 1 本 / `$(...)` の中の生成は親から見えない）に、
  **「並列で走る道具の一時名を `$$` だけで作らない。異常終了の残骸 + pid 再利用は
  *エラーではなく誤った判定結果*として出る」**を足す

### 5. 完了待ちの張り方が下手で、ターンを空回りさせた

`make test` / sweep の完了を待つのに、同じ条件の background waiter を**何本も重ねて張った**うえ、
そのあいだにも手動でポーリングした。完了は 1 秒も早くならず、ユーザーからは
「進行中です」の繰り返しに見える。
[`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
の「待つと決めたら待つ」がまさにこれを禁じている。

- 切り出し先案: **却下（ルールは既にある）**。読んでいたのに守れていないので、
  ルールの追記ではなく運用の問題。強いて言えば「waiter は 1 本だけ張る」を同節の
  ✓ 側に一行足す程度

### 6. `| tail` が rc を食う罠をまた踏んだ

道具の検証中に `... | tail -20; echo rc=$?` で rc=0 と読み、実際は rc=1 だった。
[`verify-execution-not-just-exit-code.md`](../_claude/rules/verify-execution-not-just-exit-code.md)
が名指ししている形そのもの。

- 切り出し先案: **却下（ルールは既にある）**
