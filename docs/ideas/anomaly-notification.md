# 暴走しているプロセスや「いつもと違う」状態を、楽に知らせる仕組み (案)

時点: 2026-09-28。**未着手のアイデア**。実装の前に、下の「確かめること」を実測する。

## きっかけ

2026-09-27〜28、OS を上げた直後の Mac で、Apple の `CursorUIViewService` (入力ソースの「あ / A」などを出す部品) が
起動直後から 4 時間半、CPU 99.9% に張り付いていた。Slack の入力欄の接続ごとに作る表示の部品が溜まり続けていたのが原因で、
Slack を終了したら 0% に戻った。**4 時間半、誰も気づかなかった**。

OS は張り付きに気づいて `cpu_resource.diag` を書いていたが (180 秒のあいだに平均 50% を超えたら書く)、
4 時間半のあいだに 1 件だけで、通知もしない。気づくには自分で見に行くしかなかった。
詳しい経緯と検査の項目は [`../macos-health-check.md`](../macos-health-check.md) の「CPU を張り付かせ続ける常駐」「OS の資源超過の記録」。

## 固定のしきい値では足りない理由

「CPU 90% 以上が 10 分続いたら知らせる」のような固定のしきい値は、この環境では毎日鳴る。
`go test -race` の並列実行やビルドで、load average が 30〜47 まで上がるのが普通だから。
一方で `CursorUIViewService` は、いつもは 0% 近くで動いている。**同じ 100% でも、プロセスによって「いつも」が違う**。

## 案 1: プロセスごとの「いつもの値」と比べる

- プロセス (実体のパスで同一視する) ごとに、CPU の使用率の平均と振れ幅を覚えておく
- そこから大きく外れた状態が数分続いたら知らせる。通知には、そのプロセスの名前・いつもの値・今の値を出す
- いつもは静かな OS の部品が 100% になったケース (今回) は、はっきり外れるので拾える
- ビルドやテストのように、いつも 100% になるプロセスは、いつもの値が高いので鳴らない

弱点:

- **初めて見るプロセスには「いつも」が無い**。起動したばかりのものは、しばらく判定できない (判定不能として扱う)
- 使い方が変わると (新しい言語のツールを使い始めた等)、しばらくは誤報が出る
- `ps` の %CPU は直近の平均なので、1 回の読み取りで判定しない (数秒あけて読む)

## 案 2: 「使っていないのに熱い」を異常にする

- 本体の温度は `macmon pipe -s 1` で sudo なしに読める (実測 CPU 68.7℃ / GPU 59.5℃。`../macos-health-check.md`)
- 操作していない時間は `ioreg -c IOHIDSystem` の `HIDIdleTime` で sudo なしに読める (実測していない)
- **「10 分以上操作していないのに、温度か消費電力が、操作していないときのいつもの値より高い」**を異常とする。
  ビルドやテストで熱いのは、操作している (か、直前まで操作していた) ので除ける
- もう一段: 「今の CPU の消費電力から見込まれる温度より高い」も見れば、冷却の不調 (ファンの故障・埃) のようなハードウェアの兆しも拾える

弱点:

- 温度は部屋の温度・充電中か・蓋を閉じて外部ディスプレイにつないでいるか、でも変わる
- **1 コアだけの暴走は、全体の温度に出にくいかもしれない** (今回の `CursorUIViewService` は 14 コアのうち 1 コア分。その時間は go のテストも走っていて、切り分けて測っていない)
- 温度で「何かおかしい」は分かっても、原因は分からない。通知には、そのとき CPU を多く使っているプロセスを添える

案 1 と案 2 は排他ではない。案 2 で「何かおかしい」に気づき、案 1 で「どのプロセスか」を示す、という組み合わせが本命。

## 既製品 (2026-09-28 に調べた。どれも試していない)

| 製品 | 方式 | この用途での評価 |
|---|---|---|
| [Netdata](https://www.netdata.cloud/blog/macos-monitoring/) (オープンソース) | 指標ごとに k-means で「いつもの動き」を学ぶ。1 指標に 18 個のモデル (6 時間分のデータで 3 時間ごとに学び直し、直近 約 54 時間が基準)。18 個がそろって外れと言ったときだけ異常にする | いちばん近い。2026-07 の版で macOS の監視を作り直し、アプリごとの指標も取る。ただし見るのはブラウザのダッシュボード (`localhost:19999`) で、メニューバーには出ない。機械学習でエージェントの CPU が 1 コアの約 2% → 約 4% になる。**プロセス単位で今回のケースを拾えるかは未確認** |
| [Runaway Process](https://apps.apple.com/us/app/runaway-process/id6463165050?mt=12) (App Store) | CPU のコアが設定した時間より長く張り付いたら通知 | 固定のしきい値の方式。この環境ではビルドで鳴りそう |
| [Mac Performance Monitor](https://github.com/Zesty0wl/mac-performance-monitor) (オープンソース) | メニューバーから CPU などを記録し、急な増加を検出 | 機械学習ではない |
| [CPU Load Bar](https://github.com/mguellsegarra/cpu-load-bar-mac) (オープンソース) | メニューバーに負荷を出し、警告中は上位 3 プロセスを出す | 固定のしきい値の方式 |

メニューバーのアプリで、機械学習で「いつもと違う」を判定するものは見つからなかった。

## 置き場所の候補

- glogx のヘルスチェック画面 (`H`。`../macos-health-check.md`) の「CPU を張り付かせ続ける常駐」の判定を、固定のしきい値から案 1 に置き換える。プロセスごとの記録は glogx のキャッシュに残す
- tmux のステータスラインに、異常があるときだけ小さな印を出す (メニューバーより目に入る)
- Netdata を入れて、しばらく今回のようなケースを拾えるかを見る (作る前の比較対象として)

## 確かめること (作る前に)

- 操作していないときの温度と消費電力が、数日でどれくらい振れるか (しきい値を決める材料)
- 1 コアだけの暴走で、温度と消費電力がどれだけ動くか (隔離して、`yes > /dev/null` を 1 本だけ回して測る)
- `HIDIdleTime` が sudo なしで読めるか、単位は何か
- Netdata のプロセス単位の異常検知が、今回の `CursorUIViewService` の形を拾えるか
