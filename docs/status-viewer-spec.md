# status viewer 仕様 — glogx で未コミットの変更を stage / unstage する画面の契約

glogx の status viewer (`s` キー) が作業ツリーをどう読み、どう書くかの規約。**write する画面**
なので「何ができるか」より「何を絶対にしないか」に紙面を割く。実装は
[`src/glogx/worktree_status.go`](../src/glogx/worktree_status.go) (読み取り) と
[`src/glogx/status_view.go`](../src/glogx/status_view.go) (画面)。

glog 本体 (read-only) にこの画面は置かない。write 操作を glogx 側へ隔離する方針は
[`src/glogx/README.md`](../src/glogx/README.md) 冒頭が正本。

## 1. 何を読むか

```
git status --porcelain -z          # v1 形式 (-z で NUL 区切り)
```

- **v1 (`--porcelain`) を使う。** v2 (`--porcelain=v2`) は 1 行に mode/oid/score まで載る
  代わりにフィールド数が状態で変わる。この画面が要るのは XY コードとパスだけなので、
  「安定を git 自身が約束している最小の形式」を選ぶ
- **`-z` は必須。** 空白・日本語・引用符を含むパスは既定 (LF 区切り) だと `"..."` で
  クォートされて配列がずれる。NUL 区切りならクォートされない
- **untracked は既定 (`normal`) のまま。** ディレクトリは `dir/` に畳まれて 1 行になる。
  `-uall` にすると畳まれず全ファイルが並ぶが、`.gitignore` されていない生成物ディレクトリ
  (`build/` 等) を抱えた repo で一覧が数千行になる。`git status` が人間に見せている形と
  同じにするのが判断の基準
- **ignored は取らない** (`--ignored` を渡さない)。`!!` は一覧に出ない
- **git へ渡すパスは必ず `:(top,literal)` 付きの pathspec にする。** `git status` のパスは repo root
  相対だが、pathspec は **cwd 相対**に解釈される。glogx は tmux popup から任意のサブディレクトリで
  起動される (`-d '#{pane_current_path}'`) ので、素のパスを渡すと別の場所を指す (実測 2026-08-03:
  `src/glogx` を cwd にすると diff が常に空・`add` が "did not match any files"・`clean` が無言で
  何もしない)。`literal` はファイル名の `*` `?` `[` を glob として解釈させないため
- ファイルを直接読む経路 (untracked のプレビュー) は `git rev-parse --show-toplevel` の
  repo root と結合する (pathspec では解決できないため)
- **解釈できなかったレコードは数えて画面に出す。** 壊れた行は捨てて「読めた分だけ出す」が、
  捨てた数を伏せると「出力を解釈できなかった」が「変更なし = クリーン」と同じ絵になり、
  変更を見せるための画面が黙って嘘をつく (0 件なら本文に、一部なら ヘッダーに `⚠ N 件解釈不能`)

## 2. XY コードとセクションの写像

git の XY は **X = index 側 / Y = 作業ツリー側**。この画面は 1 ファイルを最大 2 行として扱う。

| 条件 | セクション | 意味 |
|---|---|---|
| XY が conflict 集合 (`DD` `AU` `UD` `UA` `DU` `AA` `UU`) | Conflicted | **操作不可** (3 節) |
| `??` | Untracked | まだ git が知らない |
| X が空白でない | Staged | index に載っている変更 |
| Y が空白でない | Unstaged | index に載っていない変更 |

- **X と Y の両方が立つファイル (`MM` 等) は Staged と Unstaged の両方に出す**。同じパスが
  2 行に出るので、両方の行に `◐` を付けて「一部だけ staged」であることを示す
- 1 行にまとめて XY を出す案 (`git status --short` 流) は採らない。まとめると `MM` に対して
  「`Space` がどちらの向きか」が決まらず操作キーが 2 つ必要になる。**セクションが向きを持つ**
  なら `Space` 1 つで足りる (3 節)
- rename (`R`) は `new → old` を 1 行で表示し、操作は両方のパスを git へ渡す

セクションの並びは **Staged → Unstaged → Untracked → Conflicted**。カーソルの初期位置は
**Unstaged の先頭** (無ければ最初の行)。`git status` の出力順と、最初に触りたいものの近さで決めた。

## 3. キーと操作

| キー | 動作 | git |
|---|---|---|
| `j` `k` `↑` `↓` `C-n` `C-p` | カーソル移動 (セクションをまたぐ) | — |
| `Tab` | 次のセクションの先頭へ | — |
| `g` `G` `C-d` `C-u` | 先頭 / 末尾 / 半ページ | — |
| `Space` | **セクションを移す** (Unstaged/Untracked → Staged / Staged → Unstaged) | `add` / `restore --staged` |
| `a` | Unstaged + Untracked をまとめて Staged へ | `add --` (対象パスを列挙) |
| `X` | **作業ツリーの変更を捨てる** (y/N 確認。4 節。Staged 行では受けない) | `restore` / `clean -fd` |
| `Enter` `l` `→` `d` | そのファイルの diff を全画面 pager で開く | `diff` / `diff --cached` |
| `r` | 手動で読み直す | `status` |
| `p` | **pull --rebase** (y/N 確認。確認モーダルは viewer の上に重なる) | `pull --rebase` |
| `U` | usage モーダル (viewer の上に重なる既存挙動) | — |
| `q` `Esc` `s` | 閉じる | — |
| `C-g` `C-c` | glogx 終了 | — |

- **`u` を unstage に割り当てない。** glogx の `u` は `git pull --rebase` で、remote に触るキーを
  画面ごとに別の意味へ再利用すると誤爆の被害が大きい (tig は `u` だが、ここでは踏襲しない)
- **`b` (push) は viewer 内では効かない。** staging の途中から remote 操作へ滑る導線を作らない。
  押したら無効である旨を 1 回トーストで返す
- **pull は `p`** (ユーザー要望 2026-08-05)。当初は `b`/`u` をまとめて遮断していたが、
  「status を見て遅れに気づいたのに閉じてから pull し直す」手間の方が大きいと判断して開けた。
  一覧の `u` と別のキーにしているのが折衷点で、誤爆しやすい隣接キーではなく明示的な `p` の
  ときだけ remote に触る。viewer 内の `u` は「pull は `p`」と案内するだけで何もしない
- pull の確認モーダルは **viewer の上に重ねて描く**。キーは viewer より先に action モーダルが
  捌くので、描かないと「見えないモーダルが y/N を持つ」状態になる (押した先が画面と食い違う)
- pull の成功後は viewer をその場で読み直す (自動更新の 1.5 秒を待たせるとヘッダーの
  ahead/behind が古いまま残り「効いていない」ように見える)
- Conflicted 行では `Space` / `a` / `X` を受けない (`d` で差分を見るだけ)。conflict の解決は
  シェルの仕事という `git pull --rebase` の自動 abort と同じ方針
- **`X` は Staged 行では受けない** (「先に `Space` で unstage してください」と返す)。staged の変更を
  捨てるのは「index から降ろす」+「作業ツリーを破棄する」の二段の破壊で、同じキー・同じ確認文言では
  意味が変わってしまう。`X` の意味を「作業ツリーの変更を捨てる」1 つに保つ
- 全画面 pager は status viewer が自分で持つ (コミット diff の `diffOverlay` とは別の状態)。
  ただしスクロールの語彙 (1 行 / 半ページ + glide / 端ジャンプ) は `scroll_glide.go` の
  `pagerScrollKey` を共有するので、手触りは `d` のコミット diff と同じになる
- 操作結果 (成功・失敗) は右下トーストで出す。キー待ちのモーダルは `X` の確認だけが使う

### 実機で固定していること

破壊操作と「壊れないことを保証する側」のコードは自己レビューで閉じない
([`adversarial-review-own-safeguards.md`](../_claude/rules/adversarial-review-own-safeguards.md))。
pathspec の意味と削除の巻き込みはスタブでは検証できない (呼び出し引数の一致しか見られない) ので、
`src/glogx/worktree_status_real_test.go` が**使い捨ての実 repo** (`./tmp` 配下) に対して固定している:

| 実験 | 何を守っているか |
|---|---|
| `a?b.txt` を捨てて `axb.txt` が残る | glob 解釈で隣のファイルを巻き込まない (`literal`) |
| サブディレクトリを cwd にして diff / stage / unstage | cwd 相対解釈で別の場所を触らない (`top`) |
| untracked ディレクトリを捨てて兄弟が残る | `clean -fd` の範囲がその行だけ |
| 確認中に別プロセスが stage → 捨てない | 4 節の不変条件 1 |
| 新品 repo (変更 0 件) で全キーを叩く | 空の一覧で落ちない |
| 消えたファイルを stage → 失敗として報告 | 沈黙を成功にしない |

## 4. 破壊操作 (`X`) の不変条件

`X` は作業ツリーの変更を消す唯一のキーで、**復元手段が無い**。stash へ退避もしない
(`git pull --rebase` で自動 stash を却下した判断と同じ。復元 pop の衝突で壊れた状態を残しうる)。

```
┌─ 変更を捨てる ────────────────────────────────┐
│ 次のファイルの変更を捨てます (復元できません)   │
│   M src/glogx/render.go                        │
│                                                │
│ y/Enter: 実行   n/Esc: キャンセル                │
└────────────────────────────────────────────────┘
```

不変条件は 2 つ。どちらも「並行して別プロセスが同じツリーを編集している」ことを前提にする
(Claude Code / 別ターミナルの $EDITOR / `git pull` が同時に走るのが glogx の通常環境):

1. **確認に出した `(パス, XY)` と、`y` を押した時点の `(パス, XY)` が一致しなければ実行しない。**
   一致しなければ捨てずに警告トーストへ落とし、一覧を読み直す。確認中にファイルが変わっている
   なら、ユーザーが見て判断したものはもう存在しない
2. **カーソルはインデックスでなくパスで保持する。** 行の増減でカーソルが隣へ滑ると、`X` が
   「見ていたのとは別のファイル」を捨てる。パス固定ならその事故が構造的に起きない

untracked の `X` は `restore` ではなく削除 (`clean -fd`) なので、確認の文言を
「ファイルを削除します」/ ディレクトリ行 (`dir/`) では「ディレクトリを中身ごと削除します」に
差し替える。同じ見た目のキーで意味が変わるものを、同じ文言で確認しない。

## 5. 自動更新 (外部編集の追従)

- 開いている間は **1.5 秒周期のポーリング**で `git status` を読み直す。自己再アームの独立チェーンで、
  閉じたら止まる (フレーム tick には混ぜない。`autobuildWatch` / `issuesWatch` と同じ作法)
- issues viewer と違い **fsnotify を使わない**。issue は「特定ディレクトリの `.md`」だが、作業ツリーは
  repo 全体で、再帰 watch は対象数が読めない (`node_modules` 等) 一方、`git status` 自体は
  シェルの git prompt が毎コマンド叩いている程度のコストしかない
- 更新は**静か** (トーストを出さない)。commit までに何十回も起きるため
- **一覧は毎回 `git status` から作り直す派生ビュー**。stage 実行後にローカルの配列を書き換えて
  済ませない。書き換え型は外部編集が入った瞬間に画面が嘘になる
- カーソルはパスで復元する (4 節の不変条件 2)。stage して行が別セクションへ移ったときは
  **カーソルはその位置に留まる** (ファイルを追いかけない)。`Space` 連打で上から順に stage できる
- **取得に失敗しても、一度読めた一覧は消さない** (last-good を維持し、ヘッダーに `⚠ status 取得失敗`
  を出す)。自動更新が 1.5 秒ごとに走るので、一時的な失敗で一覧を空にすると「操作しようとした瞬間だけ
  画面が空になる」ことになる。まだ一度も読めていないときだけ失敗の案内を本文に出す

## 6. レイアウト

幅が足りるとき (目安 100 桁以上) は 2 カラム。左が一覧、右がカーソル行の diff プレビュー。

```
╔══ status ── master ↑1 ─────────────────── unstaged 3 / staged 2 ══════╗
║  Staged (2)                        │ src/glogx/tui.go        (staged) ║
║    M  src/glogx/tui.go             │ @@ -1188,6 +1188,9 @@            ║
║    A  src/glogx/status_view.go     │ +    if key == "s" {             ║
║                                    │ +        return m.openStatus()   ║
║  Unstaged (2)                      │ +    }                           ║
║  ▸ M  src/glogx/render.go      ◐   │                                  ║
║    M  README.md                    │  … 続きは d                      ║
║  Untracked (1)                     │                                  ║
║    ?  tmp/scratch.txt              │                                  ║
╟──────────────────────────────────────────────────────────────────────╢
║ Space: stage/unstage  a: 全 stage  X: 変更を捨てる  d: diff  q: 閉じる║
╚══════════════════════════════════════════════════════════════════════╝
```

- 幅が足りないとき (tmux popup / 小さい pane) は**一覧だけの 1 カラム**に落ちる。diff は `d`
- **プレビューにスクロールを持たせない**。`j`/`k` は常に一覧のカーソル移動で、フォーカス切り替えという
  モードを増やさない。全文を読むのは `d` (less 流儀のキーと `q` で 1 段戻る手触りは 3 節のとおり共有)
- プレビューはカーソルが止まってから 120ms 後に取る (キーリピート中に 1 行ごとに git を叩かない)。
  結果は `(パス, staged か, XY)` をキーにキャッシュし、`git status` の内容が変わったら捨てて取り直す
  (捨てるだけだと、外部編集のたびにプレビュー欄が空になりカーソルを動かすまで戻らない)
- **プレビューでは diff のファイルヘッダー (`diff --git` / `index` / `---` / `+++`) を飛ばして最初の
  hunk から見せる**。枠が 10 行前後しかないので、ヘッダー 4〜6 行に埋まると変更が 1 行も見えない。
  全画面 diff (`d`) では飛ばさない (全文を読む場なので mode 変更等も情報)
- untracked のプレビューはファイルの**先頭 64KB まで**しか読まない (untracked には巨大な生成物が
  混ざりうるので、カーソルを合わせただけで数百 MB を掴まない)
- 色は git 標準に寄せる: staged = 緑 / unstaged = 赤 / untracked = dim (値は
  [`theme/colors.yml`](../theme/colors.yml))。パスはディレクトリ部分を dim、basename を明るく
- 作業ツリーがクリーンでも**画面は開く**。自動更新があるので、別プロセスに作業させている間の
  ライブモニタとして開いたまま置ける

## 7. 開閉の演出

- 開き: **左端から 700ms で拭き出す** (行ごとの stagger + easeOutCubic。issues viewer の流し込みと
  同じ質感・同じ所要)。閉じ: 左へ 450ms で拭き取られる (全行同時・等速)。issues viewer が右から、
  こちらは左から: 方向でどちらの画面が出たか判別できる。当初の「下からせり上がる」縦スライドは
  解像度が行数しかなくカクつくためやめた (2026-08-06。理由の詳細は `slideLeftWindow` の doc)
- 演出中のキーは**即着地させるが飲み込まない** (開き)。**閉じ演出中のキーは viewer に届かない**
  (`issues_close_anim_test.go` が固定している契約と同じ)
- **セッション再開は持たない** (issues viewer の 30 分再開とは別扱い)。未コミットの状態は数十分で
  別物になり、復元した画面が嘘になる

## 8. 意図的に持たない機能

| 機能 | 理由 / 再評価の trigger |
|---|---|
| hunk 単位の stage | この画面はファイル単位。「1 ファイルの一部だけ commit したい」が実際に来たら再評価 |
| commit | メッセージ編集を TUI に持ち込む話になる。commit はシェル / Claude Code 側の仕事 |
| `git stash` | 4 節。復元 pop の衝突で壊れた状態を残しうる |
| conflict の解決 | 3 節。シェルの仕事 |
