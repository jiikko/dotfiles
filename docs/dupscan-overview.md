# dupscan の概要 — プログラムの構成・成果物・言語への対応

**状態: 未実装 (計画。epic 890)**。要件の正本は issue 891 で、この文書と食い違ったら 891 が正しい。
この文書は全体を 1 枚で掴むための要約で、細部 (受け入れ条件・実測・決めること) は 891 と子 issue 892〜905 にある。

## 1. 何をする道具か

repo の中で「中身が同じ / ほぼ同じメソッド」を構文木で見つける。用途は 2 つで、同じ土台の上に載る。

- **重複のチェック**: 既にある写しを組にして列挙する (できた写しを後から見つける)
- **探索の索引**: repo のメソッドの一覧を出し、書く前に「似たものが既にないか」を引けるようにする (写しを作る前に止める)

**主な使い方 (2026-10-24)**: Claude Code にコードを変更させている間に、重複したメソッドを作らせない・既存のメソッドを見つけやすくして実装を滑らかにする。効かせる時点は 2 つ。

| 時点 | 何をするか | issue |
|---|---|---|
| 書く前 | メソッドを定義するときに、索引で名前・署名の型・doc 文を気軽に引く。1 回の引きは安く、出力は短くする。本体はまだ無いので、本体の形では引けない | 903・897 |
| `make test` | 使う側の repo の `make test` (CI も同じ) の中で `dupscan gate` が走り、merge-base から作業ツリー (未コミット・untracked を含む) までに増えた重複を落とす。止めるかは実行コスト次第 | 905 |

編集のたびに走る Claude Code の hook (issue 902) は保留。`make test` まで待つと手戻りが大きい実例が続いたら再開する。
週次の audit のような後からの洗い出しはその次。

文字列ではなく構文木を正規化して比べるので、名前が違う写しや、同じ値を別の書き方 (直書き / プロパティ経由) で作る写しも拾う。
起点は obaket の PR 24 で、同じ値を組むテストのヘルパーが名前を変えて 6 つあった (obaket issue 1298)。

**やらないこと**: LSP を使うこと (6 節) / 共通化の修正の自動化 / 書き方が違って振る舞いが同じもの (Type-4) の検出 (構文木では原理的に取れない。止める保証もここまで)。

## 2. プログラムの構成

Go で書く。構文の解析は tree-sitter (cgo)。「言語に依らないコア」と「言語ごとの adapter」に分ける。

```
bin/dupscan (入口。初回に src/dupscan をビルドする)
    |
    v
+--------------------------- コア (Go。言語を知らない) ----------------------------+
|                                                                                  |
|  走査 ---> 分類 ---> parse ---> 単位の抽出 ---> 正規化 ---> ハッシュ ---> 組分け  |
|  git ls-files  test/prod  (adapter)  (adapter)    L1/L2/L3                Type-2   |
|  symlink は辿らない                                                       Type-3   |
|                                                                             |      |
|                                     単位の一覧 ----+---------------------+      |
|                                                    |           |         |      |
|                                                    v           v         v      |
|                                                  索引        gate    重複の報告   |
+----------------------------------------------------------------------------------+
    ^
    | 役割の対応表・単位の抽出・既定の規則
+--------------------- adapter (言語ごと) ---------------------+
|  Swift (最初)   |   Go (候補)   |   zsh (候補)   |  ...      |
+--------------------------------------------------------------+
```

| 段 | 中身 |
|---|---|
| 走査 | 対象の repo の `git ls-files` で列挙する (`gate` は untracked も含める)。build の出力・vendor・ignore 済みは読まない。symlink は辿らない (同じファイルを別ターゲットに取り込んでいても二重に数えない) |
| 分類 | 各ファイルを test / prod に分ける。既定の規則は adapter が持ち、設定で上書きする |
| 単位 | 比べる単位 = 関数・初期化子・クロージャ (本体と戻り値の型。引数の名前を添える)。引数ラベルは本体に出ないので比べない。テスト関数そのものは既定で除く |
| 正規化 | 段ごとに組を出す (下の「同じと判定する方法」) |
| 組分け | Type-2 (同じ形): 正規化した木のハッシュが一致するものを 1 組。Type-3 (少し違う。後回し): 部分木ハッシュの多重集合の重なりで類似度を測り、閾値を超える対を出す |
| 除外 | 小さすぎる単位 (ノード数・文の数の下限。既定値は obaket での実測で決める)。読めない構文 (tree-sitter の ERROR / MISSING) を含む単位は、件数と場所を報告に出し、黙って 0 組にしない |

### 同じと判定する方法

本体の構文木を段ごとに潰し、潰した木のハッシュが同じなら同じとする。

| 段 | 何を潰すか | 例 |
|---|---|---|
| L1 | 名前を、単位の中で初めて出た順の番号にする (一律の 1 記号にすると `a == a` と `a == b` が同じになるため)。リテラルは残す | 名前が違うだけで本体が同じ写しが 1 組になる |
| L2 | リテラルも種類ごとの記号にする | `"conn"` と `"c"` のように直書きの値だけが違う写しも 1 組になる |
| L3 | 単位の引数を参照しない最大の部分式を 1 記号に畳む | `ConnectionID(rawValue: "conn")` とプロパティ `connectionID` が同じになる |

ハッシュには、ノードの役割・木の形・匿名トークン (`+` / `-`、`==` / `!=`、`try` / `try?` など)・呼び出しの引数ラベルを入れる。

🚨 本体で引数を使わない単位は、L3 で本体全体が 1 記号に畳まれ、同じ型を返す単位がどれも一致しうる (自明な一致)。L3 の扱いは obaket での実測で決める (issue 898)。

## 3. 成果物

| 置き場所 | 中身 |
|---|---|
| `src/dupscan/` | Go の module (Makefile の lint / test、README、PACKAGES.md) |
| `bin/dupscan` | dotfiles の bin (PATH 上)。初回にビルドする |
| `.github/workflows/src_dupscan.yml` | dupscan 自身の CI (`_go-project.yml` を呼ぶ) |

| 入口 | 出力 |
|---|---|
| `dupscan <repo>` (重複の報告。issue 896) | 人が読む形と `--json`。test / prod / 両方にまたがる組を分けて出す。組ごとにメンバー (ファイル:行・関数名・test / prod・所属ターゲット・可視性・呼び出し元の数)・段・メンバー間のリテラルの違いの表 (プロパティの初期値は 1 段解決)。既にある共通のヘルパーと同じ組なら「既にあるものへ寄せる」と区別する |
| `dupscan index <repo>` (索引。issue 897) | 1 行 1 件の Markdown と JSON (名前と署名・ファイル:行・test / prod・所属ターゲット・可視性・doc comment の 1 行目・呼び出し元の数)。共通の置き場所にあるものを先に、private なものは「寄せる候補」として並べる。`--check` で生成し直した結果との差分を落とせる |
| `dupscan gate` (issue 905) | `make test` と CI の中で、新しく増えた重複の組を出し、あれば非 0 で終わる。段ごとに止める / 報告だけ / 回さないを選べ、既定は所要と誤って止める割合 (過去の commit の流し直し) を見て決める。意図した写しは理由つきの `dupscan:allow` で通し、新しく足された許可は別の一覧に出す。base が無い・読めない構文で確かめられなかったときは、黙って緑にしない |
| `dupscan near` / `explain` (人が試す入口。issue 904) | `near <file>:<関数名>` はその関数に近い既存のメソッドを段ごとに出す。`explain <file>:<関数名>` は段ごとに潰した形とハッシュを見せる (なぜ同じ / 違うと判定したか)。`gate` もわざと写しを書いてから手で回すと、`make test` でどう落ちるかが見える |

索引・重複の報告・`gate` は同じ単位の一覧から作る (片方だけ別の抽出をして食い違わないように)。
呼び出し元の数・所属ターゲットなど、構文木だけでは正確に決まらない値には近似の印を付ける (6 節)。

## 4. 異なる言語への対応

方針: コアは言語を知らない。言語の違いは adapter に閉じ込め、言語を足すときはコアを変えずに adapter を 1 つ足す。

tree-sitter の木は言語ごとに node の種類 (`call_expression` など) の名前が違う。adapter はそれを、コアが使う共通の「役割」に写す対応表を持つ。
コアは役割だけを見て正規化・ハッシュする。

| 役割 (コアが見るもの) | Swift の node の例 |
|---|---|
| 名前の参照 / 型の位置の名前 | `simple_identifier` / `type_identifier` |
| リテラル (種類つき) | `line_string_literal` / `integer_literal` … |
| 呼び出し | `call_expression` と `constructor_expression` の両方 |
| メンバー参照 | `navigation_expression`、暗黙のメンバー `.bucket(...)` |
| 文 | `statements` の各要素 |
| 匿名トークン | `+` `-` `==` `!=` `try` `try?` `.` (字面で区別する) |

adapter が持つもの:

1. **文法の pin**: tree-sitter の文法を go.mod の pseudo-version で固定する
2. **役割の対応表**: node の種類 (named / anonymous・field 名) → 役割。種類だけで決まらないものは字面で分ける (Swift の暗黙のメンバー `.x` は `-x` や `!x` と同じ `prefix_expression` なので、トークン `.` で分ける)
3. **網羅テスト**: 文法の node-types.json にある named な種類が全部、対応表で分類 (か明示して無視) されていること。文法の版を上げたときの対応漏れを黙らせない
4. **単位の抽出**: どの node が「比べる単位」か (関数・初期化子・クロージャ)
5. **test / prod の既定**: Swift は `Tests/` 配下・`*Tests.swift`、Go は `_test.go`、zsh は `tests/` 配下 (dotfiles)
6. **テスト関数の判別**: Swift は `@Test` / `func test…`、Go は `func TestXxx`
7. **所属ターゲット**: Swift は `Package.swift` と `project.pbxproj` を読む

| 言語 | 状況 |
|---|---|
| Swift | 最初に作る。alex-pinkus/tree-sitter-swift の `with-generated-files` branch を使う。obaket の 1626 ファイルで、読めない構文があるのは 50 ファイル (3%)、全体の parse と走査は 5.0 秒 (2026-10-24 実測)。読めないのは `switch await` / `for … where await` / `nonisolated(unsafe)` など。その部分だけ ERROR になり残りは読める |
| Go | 候補。tree-sitter-go で他の言語と同じ形の adapter にする案。標準の `go/ast` でも正確に取れるが、コアが tree-sitter の木を前提にすると形が揃わない。どちらにするかは未決 (issue 900)。重複のチェックは dupl が既に回っているので、足す価値は索引と `gate` の側にある |
| zsh | 候補。zsh 専用の成熟した文法が見つかっていないので tree-sitter-bash を使う案。`${(f)...}` や `*(N)` などの zsh だけの構文で ERROR が多い懸念があり、未実測 (issue 900) |

言語を足す前に、Swift と同じく「対象の repo の全ファイルを parse して ERROR / MISSING が出るファイルを数える」を測ってから決める。

## 5. 既存の道具との関係

issue 901。2026-10-24 の調査で、PR 24 の 6 つに当てた実測はまだ無い。

| 道具 | 何ができるか | 足りないところ |
|---|---|---|
| Claude Code の LSP ツール | 名前で引く・参照元・呼び出し元 (組み込み) | 本体の形では引けない。言語サーバと索引の待ちが要る (使わないと決めた。6 節) |
| Serena (MCP) | LSP を MCP で出す。Swift・Go・Bash を含む | 同上 |
| PMD CPD / jscpd | トークン列の一致で後から重複を見つける。Swift・Go に対応。jscpd は MCP サーバを持ち、それを使う Claude Code の plugin (DRYwall) もある | Swift で名前・リテラルを潰す設定が文書に無い。値の書き方の違い (L3) は見ない。MCP・DRYwall は呼んだときにだけ動く |
| dupl (golangci-lint) | Go で値を無視して比べる。dotfiles の 7 module で既に有効 | Go だけ。閾値 120 トークンより小さい写しは出ない |
| mizchi/similarity | 木の編集距離。AI に渡しやすい出力 | Swift と shell に対応していない |
| ast-grep | tree-sitter の構造パターンで検索 | 類似度は出さない (形を指定して探す道具) |
| 意味検索の MCP | 埋め込みで意味で引く | モデルと索引が要る。semantic-code-mcp は Python・Rust・Markdown だけ (Swift 非対応) |

dupscan が作るのは、Swift の L1〜L3 の正規化・索引・`gate` を候補とし、範囲は 901 の実測で決める
(既存の道具を `gate` から呼ぶ形で、依存と使い方が単純なまま足りるなら、そちらを使う)。

## 6. LSP は使わない (2026-10-24 の決定)

dupscan だけで依存も使い方もシンプルになるなら、LSP は使わない。

- 書く前の検索は、名前の検索も含めて dupscan の索引でまかなう (1 行 1 件のテキストなので grep でも引ける)
- 構文木だけでは正確に決まらない値は、近似と分かる形で出す
  - 呼び出し元の数: 名前と引数ラベルが一致する呼び出しの数 (別の型の同名のメソッドも数えうる)
  - プロパティの初期値: 同じ型の stored property の初期値を 1 段だけ解決する
  - 所属ターゲット: adapter が `Package.swift` と `project.pbxproj` を読む
- 理由: LSP は言語サーバの起動と最初の索引の待ち (obaket の SwiftPM の package で数分・1.6 GB) が worktree ごと・言語ごとに要る。dupscan だけなら、依存は実行ファイル 1 つ、使い方も 1 つで済む
- 失うもの: 索引は repo の中 (`git ls-files`) だけを読むので、依存の package や SDK の API は引けない
- 再開の条件: 索引で見つからなかったものが repo の中にあった実例・索引の管理が LSP より重いと分かったとき、または近似が誤りで判断を誤る実例が出たら、LSP か言語の解析の道具で補う案を再開する (issue 899。保留中)
