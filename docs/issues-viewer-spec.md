# issues viewer 仕様 — glogx が issue をどう読むか (repo を寄せるときの契約)

glogx の issues viewer (`i` キー) が `issues/` をどう解釈するかの規約。**複数 repo をこの規約に
寄せる**ための契約書なので、「viewer が何を読むか」だけでなく「なぜその読み方にしたか」を
実測とともに残す。実装は [`src/glogx/issues/`](../src/glogx/issues/)、状態判定の根拠は
`parse.go` 冒頭のコメント。

## 1. 探索

| 何を | どこから |
|---|---|
| 起点 | `git rev-parse --show-toplevel` (失敗したら cwd) |
| 対象 | `<root>/issues` と `<root>/*/issues` (深さ 1 まで。`issue` 単数形も可) |
| 除外 | `.git` / `node_modules` / `vendor` / `build` / `dist` / `tmp` / `Pods` 等の生成物 |
| 条件 | 直下またはその 1 段下に `.md` が 1 つ以上あること |

- 起点を cwd ではなく repo root にするのは、glogx が tmux popup から `-d '#{pane_current_path}'`
  で起動されるため。cwd 起点だと「repo に issues があるのに viewer が空」になる
- 深さ 1 まで掘るのは、`<root>/issues` と `<sub>/issues` の両方を持つ repo が実在するため
  (DualNoteApp は root に 3 件・`macOS/issues` に 102 件)
- `.md` の有無を条件にするのは、名前が `issues` でも issue 管理でないディレクトリがあるため
  (`ubiregi-server/script/issues/19951` は権限 fixture の `.yml` 置き場)

## 2. ファイル名 — 番号とカテゴリ

```
NNN-<カテゴリ>-<スラッグ>.md        例: 028-refactor-glogx-box-and-toast-cleanups.md
```

- **タブは「番号の次のトークン」で作る**。この語彙は viewer 側で固定しない: 実測で repo ごとに
  3 系統 (変更種別 19 語 / サブシステム名 / トークンなし) が併存しており、決め打ちにすると
  別 repo で空タブと欠落が出る。寄せるなら「番号の次に分類語を置く」だけ守れば足りる
- カテゴリを 1 件しか持たない語は `other` タブへ寄せる (コンポーネント名を置く repo で
  タブが数十個に膨らむのを防ぐ)。しきい値は `issues.TabMinCount`
- `CATEGORY-NNN-<スラッグ>.md` (大文字 ID) も認識する。番号なしファイル (`README.md`、
  素のスラッグ) はカテゴリを取らず `other` に入る
- **番号は一意でなくてよい**が、viewer の同一性キーは**パス**であって番号ではない
  (実測で同一ディレクトリ内の番号重複が dropbox 37 件・SnapTrim 4 件・DualNote 4 件ある)

## 3. 状態 — パス (ディレクトリ) が正本

| 置き場所 | 状態 | バッジ |
|---|---|---|
| issue ディレクトリ直下 | open (未完了) | `○` |
| `next/` | **次にやる** (viewer の `n` が付ける目印) | `▶` |
| `pending/` `hold/` `on-hold/` | 保留 (着手条件・trigger 待ち) | `⏸` |
| `done/` `closed/` `completed/` `resolved/` | 完了 | `✓` |
| 上記以外のサブディレクトリ | **状態にしない** (サブグループ扱い) | `?` |

未知のサブディレクトリを状態へ写像しないのは、状態でないサブディレクトリを持つ repo が
実在するため (`src/working/issues` はプロダクト名のディレクトリが 18 個、
`DualNoteApp/macOS/issues/mid-long-term` は状態ではなく時間軸)。黙って状態にすると
「存在しない状態」がタブに並ぶ。

### 既定は open だけ / `a` で 3 段の巡回

```
open のみ (既定)  →  open + pending  →  open + pending + done  →  (先頭へ戻る)
     ○                    ○⏸                   ○⏸✓
```

`done` を伏せるのは実測で done が全体の 8 割を占める repo があり、既定で混ぜると open が
埋もれるため。`pending` も伏せるのは「着手条件・trigger 待ち = 今は動かせない」もので、既定の
一覧で open と混ぜると「今やれること」が読み取りづらいため (2026-07-31)。

bool 2 本 (done / pending) でなく累積の段階にしたのは、操作を 1 キーの巡回に収めて hint 行
(1 行しかなく popup 実幅に詰まっている) を圧迫しないため。代償として「pending は伏せて done
だけ見る」は表現できない。実装は `issues.StatusFilter`。

今どこまで見えているかはタブ行の右端のバッジ (`○` / `○⏸` / `○⏸✓`)、次に何が増えるかは hint
(`a: +⏸` 等) が示す。`unknown` (`?`) はフィルタの対象にしない — 状態へ写像しない契約 (上表) の
帰結で、伏せると「存在しない状態」を操作させることになる。

### `n` で「次にやる」の目印を付ける (`next/` へ移動)

一覧で `n` を押すと確認モーダルが出て、`y`/`Enter` で選択中の issue を
`<issue ディレクトリ>/next/` へ移す (ユーザー要望 2026-08-01)。**`n` は toggle** で、既に目印が
付いている issue に対しては「外す」向き (issue ディレクトリ直下 = open へ戻す) になる。favorite のように「次に何をやるか」を
自分でマーキングするための機能で、**状態 (パスが正本) の語彙に `next` を 1 つ足す**形で実現する。
`next/` が無ければ作る。

- **`next` は常に見せる** (状態フィルタの段階に関係なく)。伏せると「目印を付けた issue が既定の
  一覧から消える」という逆の結果になる
- ⚠️ **確認を必ず挟む**。viewer で唯一、実ファイルを動かす操作なので glogx の push/pull と同じ作法に
  する。⚠️ **`y`/`Enter` 以外はすべて取り消し**に倒す — 「知らないキーを押したら実ファイルが動いた」
  を作らない
- ⚠️ **`git mv` を使わない**。実ファイルの移動だけを行い index には触れない: `git mv` は移動を即座に
  stage するため、同じ repo で並行作業しているセッションの pathspec なし commit に巻き込まれる
  (`commit-with-pathspec.md` が記録している実害)。commit するかどうかは人が決める
- ⚠️ **上書きしない**。宛先に同じ basename があれば失敗させる — それは viewer 自身が警告している
  異常 (下の「同じファイル名が 2 箇所にあったら警告する」) で、移動でそれを作らない
- 目印を付けたものは **タブ行の左端に固定の疑似カテゴリ `[next]`** から一覧できる
  (ユーザー要望 2026-08-01)。⚠️ これはファイル名のカテゴリではなく状態 (`next/` に居るか) で
  選ぶので、`issues.Filter` へ名前として渡さない — 渡すと「`@next` というカテゴリ」を探して
  常に 0 件になる。識別子を `@next` にしているのは、実在するカテゴリ語と同じ綴りだと同名タブが
  2 つ並んで位置で持つ選択 (`tabIdx`) が曖昧になるため (`other` と同型の問題)
- `[next]` は 0 件でも左端に出す (0 件を右へ寄せる並べ替えの対象にしない)。目印を付ける場所として
  常に同じ位置に居てほしいため。⚠️ `tabIdx` は `-1 = [next]` / `0 = All` / `1.. = カテゴリ` にする —
  `0` を `[next]` にすると zero value のビューが既定で `[next]` を選び「開いたら空の一覧」になる
- ⚠️ **外すときの戻り先は issue ディレクトリ直下 (= open) 固定**。元居た場所 (`done/` 等) は
  覚えていない — 目印は「次にやる」ものに付けるので戻り先は open が自然で、履歴を持つと
  「どこへ戻るか分からない」方が困る
- ⚠️ **向きはカーソル行で決めて選択範囲全体を揃える**。1 件ずつ toggle にしない: 目印つきと
  無しが混ざった選択で「何が起きるか」を確認ダイアログの 1 文で言えなくなる
- 対象は `y`/`p`/`Y` と同じ決め方 (複数選択中はその範囲、無ければカーソル行)
- 一覧モードだけで受ける。本文を開いたまま動かすと、開いている `Body` のパスが実体から外れて
  「読んでいるファイルがもう無い」状態になる (目印は一覧を見ながら付けるものなので実害もない)

### 本文は右から飛び出す引き出し (drawer)

issue を選ぶと本文が**画面の右外から飛び出して左へ滑り込み**、画面のほぼ全幅を占めて止まる。

幅の決め方は「本文 = 総幅 − 一覧の覗き見」で、**覗き見を `issuesDrawerMinList`(8)〜`issuesDrawerMaxPeek`(18)
桁に収める**のが要点。⚠️ 比率だけで決めると**画面が広いほど一覧が場所を食う**: popup は端末幅の 90%
(`_tmux.conf`) なので、312 桁の端末では一覧に 50 桁超を割いていた (ユーザー報告 2026-07-31
「まだ一覧が見えている」)。覗き見に要るのは「どの行から開いたか」が分かる幅だけなので、番号・状態・
カテゴリが見える 18 桁 (`→ 014 ○ research`) で止め、以降の幅は全部本文へ回す。

狭い端末では比率 `issuesDrawerRatio` + 上乗せ `issuesDrawerExtra` が下限として効く。⚠️ **比率ぶんより
狭くはしない** — 覗き見の下限が効いて「広げたのに本文が狭くなる」のは本末転倒 (総幅 20 桁で 16 → 12 に
縮む実測)。
`Enter`/`h`/`q` で閉じるときは同じ動きの**逆再生** (ユーザー要望 2026-07-31)。
⚠️ **`Enter` は開閉の toggle** (ユーザー要望 2026-08-01): 一覧の `Enter` で開き、本文の `Enter` で
閉じる。本文の `Enter` は以前 1 行送りだったが、glogx 本体の job パネルが既に「`Enter` = TUI 内の
開閉 toggle」なので、viewer だけ意味が違うと同じキーが画面ごとに別物になる。行送りは `j`/`k` に残す。
全画面で置き換えないのは、
「どの一覧のどこから開いたか」が画面から消えるため — 左に一覧の先頭 (番号・状態・カテゴリ) が
残れば開閉が位置関係として見える。

⚠️ **幅を 0 から伸ばす実装にしない**。それは「ページが開く」動きで、「飛び出してくる」動きに
ならない (最初の実装がこれでイメージ違いの指摘を受けた)。板は最終幅のまま**位置だけ**を動かす。
副次的に、位置で動かすと折り返しが変わらないので中身が組み直されて見えることもない。

- 所要は `issuesDrawerDuration` (450ms)。viewer を開く演出 (700ms) より速いのは、issue を次々に
  見るときに往復 1.4s が待たされる感じになるため
- カーブは開くとき easeOutCubic、閉じるときはその進捗を反転するだけ (別カーブだと開閉がちぐはぐ)
- 開き切る前に閉じたら、今見えている幅から折り返す (幅が飛ばない)
- ⚠️ **閉じる演出のあいだ本文の状態を捨てない**: 捨てると逆再生に何も映らない。破棄は着地後
  (`settleDrawer`)。キーが来たら演出は即着地させる (`q` が効かない時間を作らない)
- 本文は**最終幅で整形し、見えている幅へ切る**だけにする (幅ごとにキャッシュを持つ `Body` を
  毎フレーム再整形しない)
- 境界は板の**左辺**に `▏`。`│` は本文 pager のスクロールバーと隣り合って `││` に見える (実測)

### 閉じるときは板が 1 枚まるごと右へ抜ける

`i` で開くときは行ごとに `issuesAnimStagger` だけ開始をずらしながら 700ms かけて流し込む。
`q`/`Esc`/`i` で閉じるときは**全行同時・等速**で右へ抜け、所要は `issuesCloseDuration` (450ms)。

⚠️ **開く動きの逆再生にしないこと。** 一度そう作って 2 つの症状を出している:

- **動き出しが遅い**。`easeOutCubic` の緩やかな尾が逆再生では立ち上がりの平坦部になり、さらに
  stagger が視線のある最上行を最後に回す。両方が効いて、`Esc` を押してから最上行が幅の 5%
  ずれるまで 0.4 秒かかっていた
- **抜けた後に白い画面が残る**。終端で減速するカーブは残り数 % の距離に時間の後半を使うので、
  板が画面から消えても畳む時刻 (`settleClose`) まで空舞台が見える (280 桁端末で約 100ms)

減速は**着地するもの**のための演出で、画面外へ出ていく板には着地点が無い。出ていく向きは等速に
して、板が抜ける時刻と畳む時刻を揃える。

閉じる側で守ること (引き出しの `settleDrawer` と同型):

- ⚠️ **演出のあいだ viewer を畳まない** (`shown` を落とさない・本文と watcher を落とさない)。
  落とすと抜けていく板に何も映らない。片付けは `finishClose` に**一本化**する — 演出の着地
  (`settleClose`) とキーによる即着地の両方が同じ出口を通るので、片方が `stopWatch` を通らずに
  次の `watchCmd` が走る (= watcher が二重に居座る) 取りこぼしが構造的に起きない
- ⚠️ **`animating()` は「時間が過ぎたら false」にしない**。tick は `animating()` が false に
  なった拍で止まるので、時間で降ろすと片付け前にチェーンが切れて閉じかけの姿で固まる。
  `settleClose` が降ろして初めて false になる形にする (自分で終われる状態機械にする)
- ⚠️ **演出中のキーは即着地させ、かつ飲み込まない**。飲むと「`q` で閉じた直後の `q` が効かない」
  700ms ができる (アプリの終了演出はキーを飲んでも終わるだけなので事情が違う)。`i` なら
  そのまま開き直しになる = 閉じる演出の途中で開き直せる
- ⚠️ **演出中は画面を覚えない** (`screen()` が false を返す)。`shown` はまだ true だが、ユーザーは
  既に閉じている。覚えると「`q` で閉じてすぐ終了した」次の起動で閉じたはずの viewer が蘇る

テストは既定で演出を切る (`newTestIssuesView` / `newTestBrowse` の `closeAnimOff`)。既存テストは
「`close` したら即座に畳まれている」前提で書かれているため。演出そのものは
`issues_close_anim_test.go` が明示的に on にして検査する。

### 操作結果は glogx 共通の右下トーストで出す

コピー (`p`/`y`/`Y`/`N`)・URL 起動・本文の読み込み失敗といった**操作の結果**は、viewer 独自の
ヘッダー行ではなく glogx 全体と同じ右下トーストに出す (ユーザー要望 2026-07-31)。失敗は失敗色 +
`lastWarning` にも積む (`w` でコピーできる)。

⚠️ **viewer は全画面で `viewLines` が早期 return する**ため、トーストを合成し忘れると通知が画面に
一切出ない (それが以前ヘッダー行に出していた理由)。viewer の窓にもトーストを重ねること。

一方 **スキャン警告 (同名ファイルの二重化 = 静かな内容喪失) はヘッダーに残す**。操作結果と違って
「今この repo が抱えている状態」なので、消えるトーストでは受け皿にならない。以前は操作結果と
警告が同じ 1 行を奪い合っており、コピーするたびに警告が一瞬消えていた。

viewer 側は `setNotice` で結果を置くだけ・`browseModel` が `takeNotice` で取り出してトーストに
する。viewer 単体でも駆動できる契約 (トーストを知らない) を保つため。

### 本文の左にはソース (.md) の行番号を出す

本文 pager の左に、その行が `.md` の何行目かを常時表示する (ユーザー要望・選定 2026-08-01)。
**表示行の連番ではない**のが要点で、`v` で nvim を開いた先や Claude Code への指示
(「42 行目を直して」) にそのまま持ち出せる番号にする。

- ⚠️ **番号はブロックの先頭の表示行にだけ出す**。整形はソース行と 1:1 でない — 段落は複数の
  ソース行を 1 本に畳み (reflowJoin)、折り返しは 1 行を複数行に割る。同じ番号を続き行にも
  並べると「その番号の行がそこにある」と読めてしまい、持ち出した先で指す位置がずれる。
  畳まれた 2 行目以降と折り返しの続き行は空白にする
- コードブロックと表は折り返さないのでソース行と 1:1。行ごとに正しい番号を出す
  (コードは開きフェンスの次の行から)
- front matter は本文に出さないが、落とした行数ぶん番号をずらす (`skipFrontMatter` が返す)
- ⚠️ **溝は整形前に幅から引く**。後付けすると本文が枠を突き破る。桁数はソース行数から決める
  (整形しないと行番号が分からず、行番号が分からないと溝幅が決まらない循環を切るため)

### viewer の上でも `U` (usage) は効く

viewer は全画面だが、`U` の残量モーダルは**トーストと同じく viewer の窓へ合成する**
(ユーザー要望 2026-08-01)。⚠️ 合成せずにキーだけ通すと、取得 (subprocess) は走るのに画面には
出ず、viewer を閉じた後に突然現れる = 見えない層へ状態を書く経路になる (この理由で以前は
viewer 表示中の `U` を弾いていた)。前面順は一覧側と同じで usage → トースト。

`U` 以外のキーで引っ込むのも一覧と同じ語彙にする (`usageOverlay.dismiss`)。開閉の実体は
`browseModel.toggleUsage` 1 箇所で、一覧と viewer の両方がそこを呼ぶ — 2 箇所に書くと
「片方の画面でだけ取り直しの条件が違う」形でずれる。

### 本文中の URL は `u` のピッカーから開く

本文 pager で `u` を押すと URL の一覧が出て、**打った文字がそのまま絞り込み** (インクリメンタル
サーチ) になる。`ctrl+n`/`ctrl+p` (と矢印) で移動、`Enter` で開く、`Esc` で戻る。

⚠️ **`j`/`k` を移動に使わない**: インクリメンタルサーチでは `j` も `k` も検索語の一部で、両立
させると「`j` を打つとカーソルが動く」か「移動できない」のどちらかになる。同じ理由でピッカーは
`v` (nvim) や `y` (コピー) より**先に**キーを飲む — 後回しにすると "v" や "y" を含む URL を
検索できない。

⚠️ **hint 行もピッカー用に切り替える** (描画が 3 モードなら案内も 3 モード)。本文 pager の案内を
出したままにすると、案内した 9 キー (`j`/`k`/Space/`g`/`G`/`p`/`u`/`v`/`h`/`q`) がすべて検索語に
化けるため、**hint が案内するキーが 1 つも案内どおりに動かない**。ピッカー自身のヘッダーが正しい
案内を出しているので、矛盾する 2 つの案内が同じ画面に並ぶ (2026-07-31 のレビューで検出)。

順に開く方式 (最初の実装) をやめたのは本数の分布が偏るため。実測 (dotfiles の 6 issue):
1 本 ×4 / 2 本 ×1 / **24 本 ×1**。順送りだと 24 本の research issue で 17 番目に辿り着くまでに
16 個のタブが開いてしまう。

抽出は整形前の生ソースから行う — 折り返しで URL が行をまたいでも割れない。

一覧モードでは効かない (本文を読んでいないため。キー 1 打ごとにファイルを読むことになり、しかも
「その issue に URL があるか」は一覧に出ていない)。

**ローカルファイルパスは対象にしない** (2026-07-31 に検討して保留)。実測でパスらしき記述は
backtick 内に 231 個 (ユニーク 137) あるが、**repo root から実在するのは 62 件 (45%)** しかない:
別 repo のパスを書いている / 相対の基準が repo root・issue ディレクトリ・別ディレクトリで揺れる /
書かれた後に rename・削除された、の 3 つが構造的な原因。半分以上外す機能は信用できず、基準を
複数試すと別ファイルを誤って開く。issue 自体は `v` で nvim へ渡せるので、そこから `gf` で飛ぶのが
確実 (nvim は `path` 設定と実ファイルの有無を知っている)。再検討するなら実在率が高い
`file.go:123` 形 (行番号つき。実測 12 個) に絞る。

### タブは 0 件を右へ寄せる

タブ集合の順序は `issues.Tabs` が **done 込みの全件数**の降順で決めるが、チップに出す件数は
**現在のフィルタ後**の件数なので、既定表示では「0 件なのに左端」が構造的に起きる (done だけの
カテゴリが最左に並ぶ)。そこで描画前に **件数 > 0 のタブを左、0 のタブを右**へ寄せる (各群の中は
元の順序を保つ。`All` は左端固定)。

並べ替えは `v.tabs` 自体に対して行い、`Tab` キーの巡回順も同じにする (表示順と巡回順が食い違うと
右端のタブへ順番に辿り着けない)。選択は位置 (`tabIdx`) で持つため、並べ替えのたびに名前で追跡して
張り替える。フィルタを切り替えると件数が変わるのでタブの並びも変わる — 「今見えているものが左」を
優先した意図的な挙動。

### `/` で番号のインクリメンタルフィルタ

一覧で `/` を押すと番号の絞り込みが始まり、打つたびに一覧が絞られる (`41` → `415` / `141` /
`041`。部分一致)。`Enter` で入力を終え、`Esc` で解除する。

- ⚠️ **タブ (カテゴリ) と状態フィルタの両方を無視して全 issue から探す**。番号で引くのは
  「その issue へ飛びたい」ときで、`415` を探しているのに `done` だから出てこないのでは用を
  成さない。代わりにヘッダーへ **「全カテゴリ・全状態」と明記**する — 書かないと、直前まで見て
  いたタブのバッジ (`○`) と画面に並ぶ行が食い違って見える
- ⚠️ **`Enter` は「入力を終える」であって「絞り込みを解く」ではない**。絞り込みを残すことで
  `y`/`p`/`n` が結果に対して効く (ピッカーのように選んで閉じる形だとフィルタとして使えない)。
  検索語が空のまま確定したら絞り込み自体をやめる — ヘッダーだけが残ると嘘になる
- ⚠️ **行集合を作るのは `refresh` の 1 箇所** (`visibleIssues`)。`/` の処理側で `v.rows` を
  差し替える形にすると、再スキャン (`r`・見張り) や `applyScreen` が絞り込みヘッダーを出したまま
  タブの行へ黙って戻す
- ⚠️ **入力中、数字以外の印字文字は「無視」する** (一覧のキーとして実行しない)。番号だけなら
  `j`/`k` を移動に回せるが、タイトル検索を足した日に同じキーの意味が変わる。今から `urlPicker` と
  同じ作法 (移動は `ctrl+n`/`ctrl+p` と矢印) に寄せておく
- 絞り込み中の `Tab` と `a` は no-op。カテゴリも状態も無視しているので、押して画面が変わらない
  方がまだ良い (裏で選択だけ動かすと、解除した瞬間に別のタブに居ることになる)
- 絞り込みは**覚えない** (`issuesScreen` に持たない)。次の起動で復元すると「なぜか件数が少ない
  一覧」から始まり、その理由が画面から辿れない

タイトル検索は未実装。足すときは「数字以外を無視する」を外して検索語へ流す形になる (そのとき
`j`/`k` が検索語になるが、移動は既に `ctrl+n`/`ctrl+p` にあるので操作は壊れない)。

### 複数選択 (shift+↑/↓) と、まとめてコピー

一覧で `shift+↑` / `shift+↓` (または `K` / `J`) を押すと**範囲選択**になり、`y` (パス) /
`p` (番号) / `Y` (参照) が選択範囲すべてに効く (改行区切りでクリップボードへ。ユーザー要望
2026-08-01)。1 回押すと「元の行 + 隣の行」の 2 行が選ばれる (エディタ・Finder と同じ
錨 + カーソルの形)。

- 移動が矢印と `j`/`k` の 2 系統あるので、伸張も両方に付ける。⚠️ **矢印だけにしない**:
  `shift+矢印` は端末・多重化 (tmux) の設定次第でアプリまで届かないことがあり、そのとき機能ごと
  沈黙する。素の大文字 (`J`/`K`) は必ず届くので、確実に動く経路を 1 本持たせる

- **範囲は錨 (`markAt`) とカーソルから毎回導出する**。⚠️ 選択集合を別に持たない — 行集合は
  フィルタ・タブ・再スキャンで入れ替わるので、集合で持つと実体を失った選択が残り
  「画面に見えていない行がコピーされる」。錨だけなら行集合を作り直す `refresh` で畳める
- **素の移動・端ジャンプ・カテゴリ切替・状態フィルタ・本文を開く操作は選択を畳む**。選択したまま
  離れた場所へ動けるようにすると、同じ理由で「見えていない範囲が対象」になる
- `Esc` / `q` は**選択の解除が先**で viewer は閉じない (閉じると解除の手段が無い状態から再開する)
- 選択範囲の行は溝 `▌` で示す (カーソル行の `→` が優先。範囲は必ずカーソルを含むので競合しない)
- 通知には全文を載せず「N 件の…をコピーしました: 先頭 ほか」にする。⚠️ トーストは 1 行なので、
  改行を含む文字列を渡すと枠が壊れる
- 1 件のときの文言は単数のまま変えない (複数選択を足したせいで普段の操作の見た目を変えない)
- 対象を選択範囲にするのは yank 系 (`y`/`p`/`Y`) だけ。`v` (nvim) と `Enter` はカーソル 1 件のまま

### タブ行は選択に追従して横スクロールする

カテゴリが画面幅に収まらない repo では、タブ行を**選択中のチップが必ず入る窓**へ切り出す
(ユーザー要望 2026-08-01)。幅で切って捨てるだけだと、`Tab` で右端のカテゴリを選んでも画面に
現れず「選んだはずのタブがどこにも無い」状態になる (巡回順は右端まで届いているのに表示が動かない)。

- 隠れている側には `‹` / `›` を出す (その先にタブがあると分かるように)
- 窓の始点は「選択中のチップが収まる範囲でいちばん左」。選択が左寄りのうちは先頭 (`All`) から
  見え、右へ進んだぶんだけ最小限スクロールする = 1 タブずつ動かしたときに画面が飛ばない
- ⚠️ **窓を状態で持たない**。(選択位置, チップ幅, 使える幅) からの導出値として毎フレーム作り直す
  (一覧の `windowOffset` と同じ規律)。フィルタ切替とタブの並べ替えで幅も選択位置も変わるため、
  状態で持つと「選択中のタブが画面外なのに窓は動かない」ずれが残る

### 開いたまま閉じたら、次の起動は同じ画面から

viewer を出したまま `C-g` (= glogx ごと終了) したときだけ、**最後に見ていた画面を 1 つ**覚える。
次の起動でタブ・状態フィルタ・カーソル・開いていた本文・本文のスクロール位置が戻る。glogx は
tmux popup の開閉トグルとして使われるので、覚えないと C-g のたびに一覧から辿り直しになる
(ユーザー要望 2026-07-31)。

- **git log 一覧から終了したときは記憶を消す** (ユーザー指定)。残すと「一覧を見て閉じたのに
  次の起動で viewer が出る」= 2 回前の画面が後から蘇る。viewer 表示中の `q` は viewer を
  閉じるだけで終了経路 (`quit`) に来ないので、「終了時に viewer が見えていたか」だけで判定できる
- **issue はパスで指す** (3 節の同一性キー)。rename・`done/` への移動で見つからなければ黙って
  別の issue を当てず、カーソルは先頭・本文は開かない状態に落ちる
- **表示段階は名前で持つ** (`"open"` / `"pending"` / `"all"`)。序数で保存すると、段階を増減・
  並べ替えた瞬間に保存済みの記憶が別の段階で復元される (原因が保存形式だと気づけない形で出る)。
  知らない名前は既定 (open のみ) へ倒す — 見えすぎるより見えなさすぎる方が `a` 1 打で戻せる
- **TTL 30 分** (`issuesStateTTL`)。C-g のトグル感覚に効かせ、時間が経ってから開いたときは通常
  どおり一覧から始める。時計が巻き戻った (保存時刻が読み取り時刻より未来) 記憶も使わない
- **開く演出 (700ms) は出さない**。復元は「閉じたところから再開」なので、起動のたびに待たせない
- 記憶は `$XDG_CACHE_HOME/glog/issues-last-screen.json` に **1 本だけ**持ち、repo は中身の root で
  照合する。repo ごとに分けないのは、起動時に「記憶があるか」を知るために repo root の解決
  (git fork) を先に走らせたくないため — 記憶が無い通常の起動でコストを増やさない。代償は
  「repo A → repo B と開くと A の記憶が消える」だが、TTL が短いので「直前に見ていた画面」の
  意味は変わらない
- 復元の照合中に `i` が押されていたら復元しない (ユーザーの操作を奪わない)

### 同じファイル名が 2 箇所にあったら警告する

同一 issue ディレクトリ内で同じファイル名が複数の状態ディレクトリに現れたら、viewer は
警告を出す。これは並行セッションの `git mv` (即 stage される) と pathspec commit の
組み合わせで実際に起きる二重化で、**conflict も error も出ないまま片方が古い内容で残る**
(scratch repo で再現確認済み)。viewer が言えば静かな喪失に気づける。

## 4. ongoing (着手中) をどう扱うか

**決定: ファイル名に状態を入れない。`ongoing/` ディレクトリも作らない。表したいときは
本文先頭の front matter に `status:` を 1 行書く (任意)。**

```markdown
---
status: ongoing
---
# 028 refactor: ...
```

viewer は `status:` があれば表示し、**パスと食い違う場合は融合せず両方出す**
(`done ⚠ status:ongoing`)。どちらかを黙って採用すると viewer が確信を持って嘘をつく。

### なぜファイル名に入れないか (実測)

| 根拠 | 実測値 |
|---|---|
| 番号の次のトークンは既に 3 系統の語彙で埋まっており、状態語と分離できない | `119-open-with-app-context-menu.md` は `done/` にあるのに名前が `open`。`163-fix-...` は `fix` がカテゴリ |
| 「名前のどこかに状態語」に逃げても誤判定する | `lint-from-done-*` 5 件、`*-stays-open-on-blur` 等 3 件が誤爆 |
| 新しいファイル名フィールドは遵守されない | 既存のカテゴリトークン遵守率は dotfiles 30/30 だが SnapTrim 0/48・dropbox 106/218。規約は retroactive に適用されず、古い番号帯は rename されていない。「トークン不在」に既定値を当てるしかなく、未着手と付け忘れが区別できない |
| basename を含む既存参照が腐る | 35 箇所 (production のコメント 10 箇所を含む)。状態遷移ごとに rename すると毎回切れる |
| 先行事例が無い | md ベースの issue/task 管理 10 事例 (todo.txt / org-mode / Obsidian Tasks / MADR / Backlog.md / Jekyll / taskwarrior 等) でファイル名を状態 carrier にしているものは 0 件 |
| 番号の前に置く形は採番を壊す | `wip-030-...` にすると `issues/README.md` の次番号確認コマンドが `^[0-9]{3}-` で落とし、max が 029 に後退する (実測)。番号再利用は他 repo で 37 件発生済み |

### なぜ `ongoing/` ディレクトリも作らないか (実測)

- **記帳する時間が無い**: dotfiles の issue は作成→`done/` 移動が 4〜24 分 (単一セッション内、
  27 件中 13 件が同日)。誰も viewer を開かない数分のために 2 回の余分な `git mv` を要求する
  規律は定着しない
- **1 ファイル 1 ディレクトリでは表せない**: `pending/` の 2 件は両方とも「着手済み・一部完了・
  残りは trigger 待ち」を同時に満たしている。`ongoing/` と `pending/` のどちらにも該当する
- **採番コマンドの視界外になる**: `issues/README.md` の次番号確認はディレクトリを固定列挙して
  いるため、最大番号の issue が `ongoing/` に滞在すると番号が再利用される (実測)。
  もし `ongoing/` を作るなら**先に採番コマンドを全ディレクトリ走査へ直す**こと

### viewer がやらないこと

- **チェックボックスから状態を導出しない**。実測で両方向に嘘をつく: `done/` にあるのに 0/N の
  ファイルが 36 件 (dropbox 16 / DualNote 13 / SnapTrim 7)、逆に全チェック済みでも本文が未完を
  明記している open ファイルがある。チェックボックスは「作業項目」ではなく「将来の実装計画」
  「Phase 追跡」にも使われていて意味が固定されていない。出すのは生の事実 (`3/7`) だけ
- **本文を起動時に全件読まない**。ファイル名のみの走査に対して 26〜58 倍 (dropbox 229 ファイルで
  0.23ms → 13.6ms)。glogx の起動時間は Bench の監視対象なので、本文は遅延で読む

## 5. 表示の鮮度 (いつ読み直すか)

viewer は「確信を持って嘘をつく」ことを最も嫌うので、次の 3 経路で読み直す。

| 契機 | 何を読み直すか |
|---|---|
| 開く (`i`) / 再読込 (`r`) | 全ディレクトリを走査してメタデータまで読む (番号の鮮度が `N` の正しさに直結する) |
| viewer から `v` で編集して戻る | 開いている本文 + 全件の再走査 |
| 開いている間の**別プロセスの編集** | fsnotify のイベントで起こし、指紋が変わっていたら同じ経路で読み直す |

見張りは viewer を開いている間だけで、閉じたら watcher ごと畳む (fd を残さない)。**イベントは
起こす役だけで、真偽の正本は指紋** (ディレクトリの mtime + ファイルの mtime とサイズ): 1 回の保存で
複数イベントが飛ぶ・エディタの tmp+rename で inode が入れ替わる・NFS で無音になる、と嘘をつくため。
ディレクトリの mtime だけでは本文の書き換えを検出できない (create/delete/rename でしか動かない)
ので、ファイルはサイズまで見る。変化を見つけた次の観測でも同じなら読む (書きかけを掴まない)。
イベントを取りこぼしても追いつけるよう低頻度 (30s) のポーリングも回し、watcher を作れない環境では
それが唯一の経路になるので周期を上げる。実装は `src/glogx/issues_watch.go`。

## 6. repo を寄せるときのチェックリスト

- [ ] issue は `<root>/issues` または `<sub>/issues` に置く (深さ 1 まで)
- [ ] ファイル名を `NNN-<分類語>-<スラッグ>.md` にする (番号の次に分類語)
- [ ] 状態はディレクトリで表す (`pending/` `done/`)。状態でないサブディレクトリは作ってよいが
      状態としては扱われない (`other` になる)
- [ ] 同じファイル名を 2 箇所に置かない (viewer が警告する)
- [ ] 着手中を明示したいときだけ front matter に `status:` を 1 行足す
- [ ] ファイル名に状態語 (wip / ongoing / doing) を入れない
