# pro-con は便利か: 普通の Claude Code CLI のチャットと比べて (2026-09-27、Claude の観点)

2026-09-27 の 1 日を材料にした、Claude (このときチャット側で動いていた session) の見立て。前日の比較
[`pro-con-vs-parallel-sessions-2026-09-26.md`](pro-con-vs-parallel-sessions-2026-09-26.md) の結論 (混ぜた形がいちばん回る) は変わらないので、
ここでは**その日に新しく見えたこと**だけを書く。**実測**は出典を添え、それ以外は**見立て**と書く。

## その日に起きたこと (対照になった)

- **チャット側** (人と話す Claude の session 1 本): カーネルのメモリの漏れ (issue 500) の調査と、記録の道具 `bin/kernel-alloc-watch` の作り込み。
  作っている途中で人の要望が何度も変わった (判定を足す → Claude 用の JSON → 改名 → 旧名の記録を移す → 「互換は要らない」で移す処理を外す → help の縦揃え)。
  敵対的レビューを 5 周回し、P1 を 2 件 (ログを読めないと記録が全部消える / クライアント 0 を 1 と数える) 直した
- **pro-con 側**: 18:31〜19:31 の約 1 時間で、カード 10 枚 (C-001〜C-010。issue 553〜558 ほか) が閉じた。人が答えた質問は 2 件 (C-002 の色・C-005 の入口)。
  `pro-con stats` (実測): 3pt の中央値で所要 15 分・5 時間枠の 1.2%、5pt で所要 29 分・2.7%

## 便利だと思ったところ

- **人と Claude の手が空く**: 上の 10 枚は、チャット側が調査をしている裏で閉じた。人がしたのは、issue のパスを貼って「カードを作って」と言うことと、質問 2 件への回答だけ。
  チャットで同じ 10 本をやると、人がその数だけ session を見張るか、1 本の会話で順にやることになる
- **issue を起点にした規律が崩れない**: カードは issue に紐づき、取り込みの係が diff とテストを見てから master へ入れ、issue を done へ送る。
  チャットでは、この後始末 (進捗の書き戻し・done への移動) を Claude が忘れうる
- **途中で方針を変えられる**: C-005 に方針変更 (`card order --redirect`) を送ると、PG を止めて、worktree の途中の変更を残したまま同じ session を再開した (履歴 18:39)
- **外から測れる**: `pro-con e2e` (画面・dispatcher は本物、PG / PM は偽物) で、利用枠を使わずに実物を動かしてカーネルのメモリを測れた (issue 500 の 15:10 の節)

## 不便だと思ったところ

- **前提を問い直さない**: C-005 で PM が人に聞いたのは「残った worktree を判断する入口を、どちらの画面に置くか」だった。人の反応は「よくわからん。なぜ残るのか。起きないようにしたい」。
  チャット側で調べると、残る物の 3 個は取り込みの係ができる前の手作業の残り物で、今の流れで残る経路は `card close` と `card delete` の 2 つだけだった (issue 553)。
  pro-con は issue に書かれた問いの立て方のまま進むので、問いそのものが外れていると、人が気づくまで外れたまま進む (見立て: PM への指示に「質問の前に、その問題が起きない形を 1 度問う」を足せば減る)
- **人への質問に、答えるための材料が足りない**: C-002 の色の質問への人の答えは「わからん。ターミナルの設定次第かな」だった。見本は添付されていたが、何を基準に選べばよいかは届いていない
- **中の仕組みが人に見えてしまう**: 「設定では PG の枠が 2 なのに 3 つ動いている」は、作りどおりの動きだった (質問して turn を終えた PG は、生きていても枠に数えない。issue 455)。
  分かるには枠の定義を知っている必要があった → issue 557 (一覧を作業中と待機中に分ける)
- **回答してもすぐには進まない**: C-002 に 18:37 に答えたが、枠が空くまで再開を待った。方針変更も、PG の turn の区切りを待って届く
- **小さい作業は遅い**: ヘッダの 1 行を消すだけの C-010 は、依頼 (19:11) から完了 (19:31) まで 20 分 (実測。`pro-con card show C-010` の履歴)。
  内訳は PM が付けた順番待ち (C-007 の後) 8 分・PG の作業 7 分・レビュー 5 分。チャットで直接直せば数分 (見立て)。
  ただし、その 20 分の間、人と Claude は別のことができた。PG は幅 200 と 60 の見た目を添付し、codex の敵対的レビューまで回していた
- **常に回っている分の重さ**: dispatcher は何もしていなくても 3 秒ごとに `claude agents --json` を起こす (1 分 20 回。issue 500 の 15:10 の節)。
  PM と取り込みの係の session も動き続ける。どれだけ枠を食うかは役ごとに分けて測っていない

## チャットの方が向いていたもの (その日の実例)

- **要望が作りながら変わる作業**: `kernel-alloc-watch` は、要望が 6 回以上変わった。チャットでは 1 往復で直せたが、pro-con なら毎回、追加オーダーを出して turn の区切りを待つことになる
- **調べて問いを立て直す作業**: カーネルの漏れの調査、C-005 の「なぜ残るのか」。答えより先に、問いの形を人と決める必要があった
- **敵対的レビューを何周も回す作業**: 指摘を再現し、直し、変異で固定し、もう 1 周、を短い間隔で回す。取り込みの係のレビューは 1 回で、この周回は受け持たない (見立て)

## 結論 (Claude の観点)

便利だと思う。ただし、**問いの形が決まった作業を並べて流す実行の仕組み**としてであって、チャットの代わりではない。
その日いちばん回ったのは、前日と同じ混ぜた形だった。チャット側の Claude が人と話して調べ、issue を書き、カードに積み、PM の質問のうち前提がずれているものを問い直す。
チャット側の仕事で、pro-con だけでは埋まらないのは、**人へ届く前に質問の前提を確かめること**だった。ここを pro-con の側 (PM への指示・質問の形) に寄せられるかは、まだ試していない。

## 見立てのまま残っていること

- PM・取り込みの係・dispatcher の一覧取得が、それぞれ枠をどれだけ使うか (役ごとに測っていない)
- 「質問の前に、起きない形を 1 度問う」を PM への指示に足したとき、C-005 のような外れた質問が減るか
- 同じ 10 枚をチャットだけでやった場合の時間と枠 (対照を取っていない)
