dupscan の概要 — プログラムの構成・成果物・言語への対応
=========================================================

状態: 未実装 (計画。epic 890)。要件の正本は issue 891 で、この文書と食い違ったら 891 が正しい。
この文書は「全体を 1 枚で掴む」ための要約で、細部 (受け入れ条件・実測・決めること) は 891 と子 issue 892〜903 にある。


1. 何をする道具か
-----------------

repo の中で「中身が同じ / ほぼ同じメソッド」を構文木で見つける。用途は 2 つで、同じ土台の上に載る。

  (a) 重複のチェック  … 既にある写しを組にして列挙する (できた写しを後から見つける)
  (b) 探索の索引      … repo のメソッドの一覧を出し、書く前に「似たものが既にないか」を引けるようにする
                         (写しを作る前に止める)

主な使い方 (2026-10-24): Claude Code にコードを変更させている間に、重複したメソッドを作らせない・
既存のメソッドを見つけやすくして実装を滑らかにする。効かせる時点は 2 つ (issue 902・903):

  書く前     索引 (b) で名前・署名の型・doc 文を引く手順にする (issue 903)。
             本体はまだ無いので、本体の形では引けない
  書いた直後 Edit / Write の後に hook が走り (issue 902)、編集された関数を索引と比べて、近い既存のメソッドを知らせる

週次の audit のような後からの洗い出し (a) はその次。

文字列ではなく構文木を正規化して比べるので、名前が違う写しや、同じ値を別の書き方 (直書き / プロパティ経由) で
作る写しも拾う。起点は obaket の PR 24 で、同じ値を組むテストのヘルパーが名前を変えて 6 つあった (obaket issue 1298)。

やらないこと: LSP を使うこと (下の 6) / 共通化の修正の自動化 / 書き方が違って振る舞いが同じもの (Type-4) の検出 / obaket の lint への組み込み。


2. プログラムの構成
-------------------

Go で書く。構文の解析は tree-sitter (cgo)。「言語に依らないコア」と「言語ごとの adapter」に分ける。

    bin/dupscan (入口。初回に src/dupscan をビルドする)
        |
        v
    +--------------------------- コア (Go。言語を知らない) ----------------------------+
    |                                                                                  |
    |  走査 ---> 分類 ---> parse ---> 単位の抽出 ---> 正規化 ---> ハッシュ ---> 組分け  |
    |  git ls-files  test/prod  (adapter)  (adapter)    L1/L2/L3                Type-2   |
    |  symlink は辿らない                                                       Type-3   |
    |                                                                             |      |
    |                                     単位の一覧 ----+---------------------+      |
    |                                                    |                     |      |
    |                                                    v                     v      |
    |                                               索引 (index)          重複の報告   |
    +-----------------------------------------------------+----------------------------+
                                                          |
    Claude Code の hook (Edit / Write の直後) ------------+  編集された関数だけ parse して索引と比べ、
                                                             近い既存のメソッドを知らせる (issue 902)
        ^
        | 役割の対応表・単位の抽出・既定の規則
    +--------------------- adapter (言語ごと) ---------------------+
    |  Swift (最初)   |   Go (候補)   |   zsh (候補)   |  ...      |
    +--------------------------------------------------------------+

各段の中身:

  走査       対象の repo の git ls-files で列挙する。build の出力・vendor・ignore 済みは読まない。
             symlink は辿らない (同じファイルを別ターゲットに取り込んでいても二重に数えない)。
  分類       各ファイルを test / prod に分ける。既定の規則は adapter が持ち、設定で上書きする。
  単位       比べる単位 = 関数・初期化子・クロージャ (本体と戻り値の型。引数の名前を添える)。
             引数ラベルは本体に出ないので比べない。テスト関数そのものは既定で除く。
  正規化     段ごとに組を出す。
               L1: 名前を構文上の位置で区別し、単位の中で初めて出た順に番号を振る。リテラルは残す。
                   (一律の 1 記号にすると a == a と a == b が同じになるため番号にする)
               L2: リテラルも種類ごとの記号にする。
               L3: 単位の引数を参照しない最大の部分式を 1 記号に畳む。
                   ConnectionID(rawValue: "conn") とプロパティ connectionID が同じになる。
                   (値を作る式を全部畳むと、本体が 1 つの呼び出しの関数が全部同じになるので「最大の部分式」に限る)
             ハッシュには、ノードの役割・構造・匿名トークン (+ / -、== / !=、try / try? など)・
             呼び出しの引数ラベルを入れる。
  組分け     Type-2 (同じ形): 正規化した木のハッシュが一致するものを 1 組。
             Type-3 (少し違う。後回し): 部分木ハッシュの多重集合の重なりで類似度を測り、閾値を超える対を出す。
                   類似は推移的でないので連結成分で束ねない。関数とその中のクロージャの対は出さない。
                   obaket で単位が数万あり総当たりは数億対になるので、転置索引か MinHash の LSH で候補を絞る。
  除外       小さすぎる単位 (ノード数・文の数の下限。既定値は obaket での実測で決める)。
             読めない構文 (tree-sitter の ERROR / MISSING) を含む単位。件数と場所を報告に出し、黙って 0 組にしない。


3. 成果物
---------

  ソース        src/dupscan/            Go の module (Makefile の lint / test、README、PACKAGES.md)
  入口          bin/dupscan             dotfiles の bin (PATH 上)。初回にビルドする
  CI            .github/workflows/src_dupscan.yml   (_go-project.yml を呼ぶ)

  出力 1: 重複の報告 (bin/dupscan <repo>)  人が読む形と --json。test / prod / 両方にまたがる組を分けて出す。組ごとに:
        - メンバー: ファイル:行・関数名・test / prod・所属ターゲット (複数ありうる)・可視性・呼び出し元の数
        - ノード数・段 (L1/L2/L3)・類似度
        - メンバー間のリテラルの違いの表 (プロパティを読む版は、その初期値を 1 段解決して並べる)
        - 既にある共通のヘルパー (設定した置き場所) と同じ組なら「既にあるものへ寄せる」と区別する

  出力 2: 索引 (bin/dupscan index <repo>)  1 行 1 件の Markdown と JSON。各行:
        名前と署名・ファイル:行・test / prod・所属ターゲット・可視性・doc comment の 1 行目・呼び出し元の数。
        共通の置き場所にあるものを先に、ファイルの中の private なものは「寄せる候補」として区別して並べる。
        commit して置く使い方なら --check で「生成し直した結果との差分」を落とせる形にする
        (dotfiles の scripts/go_packages_index.sh --check と同じ考え方)。

  出力 3: hook の通知 (issue 902)  Edit / Write の直後に、近い既存のメソッドの名前・ファイル:行・一致した段を返す。
        止めずに知らせるだけが既定。索引が無い・読めないときは「確認できなかった」と返す (沈黙を「重複なし」にしない)。

  索引・重複の報告・hook は同じ単位の一覧から作る (片方だけ別の抽出をして食い違わないように)。


4. 異なる言語への対応
---------------------

方針: コアは言語を知らない。言語の違いは adapter に閉じ込め、言語を足すときはコアを変えずに adapter を 1 つ足す。

tree-sitter の木は言語ごとに node の種類 (call_expression など) の名前が違う。adapter はそれを、コアが使う
共通の「役割」に写す対応表を持つ。コアは役割だけを見て正規化・ハッシュする。

  役割 (コアが見るもの)          Swift の node の例
  -----------------------------  -----------------------------------------------
  名前の参照 / 型の位置の名前     simple_identifier / type_identifier
  リテラル (種類つき)             line_string_literal / integer_literal ...
  呼び出し                        call_expression と constructor_expression の両方
  メンバー参照                    navigation_expression、暗黙のメンバー .bucket(...)
  文                              statements の各要素
  匿名トークン                    + - == != try try? .  (字面で区別する)

adapter が持つもの:

  1. 文法の pin          tree-sitter の文法を go.mod の pseudo-version で固定する
  2. 役割の対応表        node の種類 (named / anonymous・field 名) → 役割。種類だけで決まらないものは字面で分ける
                         (Swift の暗黙のメンバー .x は -x や !x と同じ prefix_expression なので、トークン . で分ける)
  3. 網羅テスト          文法の node-types.json にある named な種類が全部、対応表で分類 (か明示して無視) されていること。
                         文法の版を上げたときの対応漏れを黙らせない
  4. 単位の抽出          どの node が「比べる単位」か (関数・初期化子・クロージャ)
  5. test / prod の既定  Swift: Tests/ 配下・*Tests.swift   Go: _test.go   zsh: tests/ 配下 (dotfiles)
  6. テスト関数の判別    Swift: @Test / func test…         Go: func TestXxx
  7. 所属ターゲット      Swift: Package.swift と project.pbxproj を読む

言語の状況:

  Swift  最初に作る。alex-pinkus/tree-sitter-swift の with-generated-files branch を使う。
         obaket の 1626 ファイルで、読めない構文があるのは 50 ファイル (3%)、全体の parse と走査は 5.0 秒 (2026-10-24 実測)。
         読めないのは switch await / for … where await / nonisolated(unsafe) など。その部分だけ ERROR になり残りは読める。
  Go     候補。tree-sitter-go で他の言語と同じ形の adapter にする案。標準の go/ast でも正確に取れるが、
         コアが tree-sitter の木を前提にすると形が揃わない。どちらにするかは未決 (issue 900)。
         Go の重複のチェックは dupl が既に回っているので、足す価値は索引と hook の側にある。
  zsh    候補。zsh 専用の成熟した文法が見つかっていないので tree-sitter-bash を使う案。
         ${(f)...} や *(N) などの zsh だけの構文で ERROR が多い懸念があり、未実測 (issue 900)。

言語を足す前に、Swift と同じく「対象の repo の全ファイルを parse して ERROR / MISSING が出るファイルを数える」を測ってから決める。

  索引・hook を候補とし、範囲は 901 の実測で決める (既存の道具を hook から呼ぶ形で依存と使い方が単純なまま足りるなら、そちらを使う)。


6. LSP は使わない (2026-10-24 の決定)
--------------------------------------

dupscan だけで依存も使い方もシンプルになるなら、LSP は使わない。

  - 書く前の検索は、名前の検索も含めて dupscan の索引でまかなう (1 行 1 件のテキストなので grep でも引ける)
  - 構文木だけでは正確に決まらない値は、近似と分かる形で出す
      呼び出し元の数     名前と引数ラベルが一致する呼び出しの数 (別の型の同名のメソッドも数えうる)
      プロパティの初期値 同じ型の stored property の初期値を 1 段だけ解決する
      所属ターゲット     adapter が Package.swift と project.pbxproj を読む
  - 理由: LSP は言語サーバの起動と最初の索引の待ち (obaket の SwiftPM の package で数分・1.6 GB) が worktree ごと・言語ごとに要る。
    dupscan だけなら、依存は実行ファイル 1 つ、使い方も 1 つで済む
  - 失うもの: 索引は repo の中 (git ls-files) だけを読むので、依存の package や SDK の API は引けない
  - 再開の条件: 索引で見つからなかったものが repo の中にあった実例・索引の管理が LSP より重いと分かったとき、または近似が誤りで判断を誤る実例が出たら、LSP か言語の解析の道具で補う案を再開する (issue 899。保留中)
