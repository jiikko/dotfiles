# dupscan が類似メソッドを検出する方法

**状態: Swift と Go に実装済み（2026-10-29 確認）**。現行の既定は L1・L2、関数等とクロージャの下限は各20節。L3 は明示して使う（gate の既定の停止段には入らない）。全体の構成は [`dupscan-overview.md`](dupscan-overview.md)、CLI の詳細は [`README`](../src/dupscan/README.md)。

## 流れ

1. **走査**: 対象の repo のファイルを `git ls-files` で列挙する (各コマンドとも ignore されていない untracked を含める)
2. **parse**: Swift は tree-sitter、Go は標準の go/ast で構文木にする。読めない構文 (ERROR / MISSING) を含む抽出済み単位は比較から外す (Swift の、tree-sitter-swift が読み違える書き方 (関数の中の `nonisolated(unsafe) let`・空のタプル・条件の中の `await` / `try`・変数名 `final`・クロージャの中の `;`・関数の属性の `#if` の分岐) は、読み違えの箇所だけを同じ長さの字面に置き換えて読み直す。規則の一覧は README の限界の節)。report はエラーのあるファイルも出す。gateはbase/headの失敗fileを通知する。探索のコマンドも通知する（下記）
3. **単位の抽出**: 比べる単位 = 関数・初期化子・クロージャ・computed property・subscript・deinit・accessorの本体。関数名と引数ラベルは比べない (名前が違う写しを拾うため)
4. **正規化**: 本体の構文木を段 (L1 / L2 / L3) ごとに潰す
5. **ハッシュ**: 潰した木のハッシュを段ごとに取る
6. **組分け**: 同じ段でハッシュが同じ単位を 1 組にする (Type-2)。少し違う写し (Type-3) は組にせず、候補だけを別の入口で出す (下)

## 段ごとの正規化

| 段 | 何を潰すか | 拾える写し |
|---|---|---|
| L1 | 局所の名前 (単位の引数・`let` / `var` などで束縛した名前・クロージャの引数) を番号にする。引数は宣言の順に先に振り、残りは初めて出た順。型名・呼び出す関数の名前・メンバー名・enum の case 名・リテラル・`$0` (位置に意味がある)・`$isOn` (projected value) は残す。戻り値の型もハッシュに入れる | 引数やローカル変数の名前だけが違う写し (関数名はもともと比べない) |
| L2 | L1 に加えて、リテラルを種類ごとの記号にする (文字列の中の式の埋め込みは式として残す) | 直書きの値だけが違う写し (`"conn"` と `"c"`) |
| L3 | L2 に加えて、**局所の名前 (と `$0`) を参照しない最大の式**を 1 つの記号に畳む。呼び出しの callee (`JSONEncoder().encode` の受け手を含む) と代入の左辺の下は畳まない。処理の呼び出し (`try`・`await`・`return`・代入の右辺の中でも) を含む式も畳まない。畳むのは値を作る式 (大文字で始まる型の初期化 `ConnectionID(…)`・暗黙のメンバー `.bucket(…)`・プロパティ・リテラル) | 同じ値を別の書き方で作る写し (直書きとプロパティ経由) |
| L1m | L1 に加えて、**メンバー名** (`a.b` の `b`) を記号にする。リテラルは残す。**既定では見ない** (`-levels L1,L2,L1m` で明示) | メンバー名 1 語だけが違う写し (`os.Stdout` と `os.Stderr`、`store.alphaTable` と `store.betaTable`) |

**L1m を既定にしない理由 (2026-10-28 の実測)**: dotfiles の Go の 4 module (統合前の木) では、既定の下限で新しく出る組は 5 組で、そのうち既存の見落としだった `captureStderr` / `captureStdout` を拾った。
Swift (obaket) では、既定の下限でも L1m が **本番の組を 59 組**足す (L1 / L2 だけなら本番は 3 組)。抜き取った 16 組のうち、実際の写しは 9〜10 組 (`executeResolvedCopy` と `executeResolvedMove`、2 つの型の `removeEmptyState`、待ち合わせの closure 群)、
ほかは SwiftUI の `body` の closure やハンドラの表 (`routes` の 74 件) など、メンバー名の連鎖が構造を決めている形だった。精度が約 6 割で組が倍増するので、明示して使う。

ハッシュに入れるもの: ノードの役割 (呼び出し・メンバー参照・文など)・木の形・匿名トークン (`+` / `-`、`==` / `!=`、`try` / `try?`、暗黙のメンバーの `.`)・
呼び出しの引数ラベル (`rawValue:` など。ラベルまで潰すと、ラベルの違う呼び出しがどれも同じになる)。

- 名前を一律の 1 記号にしないのは、`a == a` と `a == b` を区別するため。引数を宣言の順に振るのは、`a - b` と `b - a` を区別するため。代わりに、引数の並びが違う・前に引数が 1 つ多い写しは、本体が同じでも割れる (見逃しの向き)
- 型名や呼び出す関数の名前を番号にしないのは、別の型を組む薄い wrapper がどれも一致するのを避けるため (全部を番号にする案と比べるのは issue 898)
- L3 で「最大の部分式」に限るのは、値を作る式を全部畳むと、本体が 1 つの呼び出しである関数がどれも同じになるため

## 例

```swift
// A: 直書きで組む
func location(path: String) -> StorageLocation {
    StorageLocation(connectionID: ConnectionID(rawValue: "conn"), path: ObjectPath(rawValue: path))
}

// B: 名前が違い、接続の ID をプロパティから読む
func bucketLocation(_ p: String) -> StorageLocation {
    StorageLocation(connectionID: connectionID, path: ObjectPath(rawValue: p))
}
```

| 段 | A と B | 理由 |
|---|---|---|
| L1 | 違う | A は `ConnectionID(rawValue: "conn")` の呼び出し、B はプロパティ `connectionID` の参照で、木の形が違う (関数名は比べず、引数の名前 `path` / `p` は同じ番号になる) |
| L2 | 違う | リテラルを潰しても、呼び出しとプロパティの参照の違いは残る |
| L3 | **同じ** | `ConnectionID(rawValue: "conn")` も `connectionID` も引数を参照しないので、同じ記号に畳まれる。残るのは `StorageLocation(connectionID: ■, path: ObjectPath(rawValue: 引数1))` で、両方で同じ。引数を使う `ObjectPath(rawValue: path)` は残るので、本体全体は潰れない |

報告では一致した段と位置・署名を出す。2 単位の構造の差とリテラルの字面は `explain -compare A B` で並べて見られる (918)。プロパティの初期値は解決しない。
値はソースと explain を見比べる。同じ形・同じ値でも別々に変わるべきドメインなら統合しない。

## 検出しないもの

- **書き方が違って振る舞いが同じもの (Type-4)**: 構文木では原理的に取れない
- **少し違う写し (Type-3)**: 文が 1 つ多いなど。組にも gate の違反にもならない。L1 の部分木の重み付き多重集合の Dice で、`near -similar` (1 対象) と `sweep` の節 3 (全単位の総当たり。単位が 8000 を超えると飛ばす) が候補の対を出す (895)。同一動作・再利用は証明しない
- **小さすぎる単位**: ノード数の下限より小さいもの。関数・初期化子・property とクロージャはいずれも既定20節（898）
- **読めない構文**: gateは抽出できた変更単位に加え、単位が0件でもbase/headの解析失敗fileを通知する。通常rcは維持し、-strict-analysisではいずれかのfile parse errorでrc=2。def / refs / index / callers は stderr に解析失敗の件数と先頭のファイルを出す (読めないファイルがどれも問い合わせの名前を含まないときは 1 行に縮める。942)。rc=0や検索0件は全構文を読めた証明ではない
- **大文字で始まる処理の呼び出し**: Swift では `XCTUnwrap(a)` のような大文字で始まる関数は、構文だけでは型の初期化と区別できず、局所の名前を参照しなければ L3 で畳まれる (誤検知の向き)。小文字で始まる値の変換 (`.uppercased()`・`Calendar.current.date(…)`) は処理として畳まない (見逃しの向き)。Go は公開の関数も大文字で始まるので、組み込みの変換と型リテラルへの変換のほかは全部処理として畳まない (`UserID(s)` も畳まない。見逃しの向き)
- **局所の名前の有効範囲**: 名前がどこかで局所に宣言されていれば、単位の中の同じ名前を全部局所として扱う (`items.map { name in … }; print(name)` の後ろの `name` が `self.name` でも番号になる)。誤検知の向きに働く
- **`gate` の入れ替え**: 同じ組の古い写しを 1 つ消して新しい写しを 1 つ足しても、写しの数が増えないので落ちない (issue 905)

## 誤検知 (false positive) と除外

出やすい誤検知:

- **局所名を参照しない本体のL3一致**は偶然の一致になりやすいため、report / gate の組から除く（L3Trivial）。near は中身を見た一致と分けて示す。L3 自体も既定では無効で、明示して有効にしても停止段を指定しなければ報告だけ
- テストの表の形が似ているだけの関数、生成コード、意図して分けている写し
- 同じファイルの別の型に同じ名前の関数がある・クロージャ: 鍵に囲む型とクロージャの順番を入れて名指しする (issue 905)

除外の設定 (issue 906):

- 組の除外 (誤検知と判断した組を、メンバーの鍵の集合で指す。行がずれても効く)
- 単位の除外 (単位の直前の `dupscan:allow <理由>`)。組ごとなら、メンバーの 1 つに `dupscan:allow-group <人数> <理由>` (人数が合う間だけ効く。写しが増えれば効かなくなり、増えた写しが出る。956)
- パス・段の除外、下限・閾値の変更
- どの除外にも理由と種別 (誤検知 / 意図した写し) が要る。単位の除外 (`dupscan:allow`) は寄せる側の違反から外すだけで、数には入れたまま。組の除外は書いたメンバーの間にだけ効き、新しく増えたメンバーは出る。効いていない (指す先が無くなった) 除外は毎回出し、`gate` は新しく足された除外を別の一覧に出す (寄せる代わりに除外を書く抜け道を、人が見て止められるように)

## いつ使うか

| 時点 | 使い方 | issue |
|---|---|---|
| メソッドを書く前 | 索引で名前・署名の型・doc 文を引き、似たものが既に無いかを見る (気軽に引く。結果は短い)。引き忘れても、新しい関数の Write / Edit の直前に hook が名前の近い既存の定義を注入する (知らせるだけ) | 903・897・948 |
| 実装が終わったセルフレビュー | `dupscan gate` を回し、今の変更で増えた写しが無いかを見る。違反があれば既存のメソッドへ寄せるか、誤検知なら除外を書く | 903・905 |
| `make test` と CI | 同じ `gate` を網として回す (止めるかは実行コスト次第) | 905 |
| 判定を確かめたいとき | `dupscan near` で 1 つの関数に近いものを見る (`-similar` で少し違うものも)。`dupscan explain` で段ごとに潰した形とハッシュを、`explain -compare` で 2 単位の差を見る | 904・895・918 |
| 初めて入る module の既存の写しを掘るとき | `dupscan sweep` で 5 つの見方 (組 / 下限 12 節と L1m / 部分木の対 / 名前の束 / 手で展開した helper) をまとめて見る | 948・956 |
